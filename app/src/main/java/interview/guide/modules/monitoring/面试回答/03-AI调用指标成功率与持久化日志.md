# AI 调用指标、成功率与持久化日志

## 1. 模块基础讲解

AI 可观测性同时走两条链路：

```text
StructuredOutputInvoker
  ├─ Micrometer
  │   ├─ app.ai.structured_output.invocations/attempts/latency
  │   └─ AiMetricsRecorder: invocation.count/latency/retry/failure
  └─ AiInvocationLogService
      └─ ai_invocation_logs 数据库表
```

Micrometer 负责实时聚合，标签包括 scenario、provider、model、status；数据库日志保存 traceId、模型、
Prompt 版本/哈希/长度、重试次数、成功状态、延迟和错误信息，适合 Dashboard 统计和失败下钻。

`BusinessMetricsQueryService` 的 AI 调用量和成功率只来自 `ai_invocation_logs`。当前写入入口主要是
`StructuredOutputInvoker`，因此它更准确地表示“被该包装器记录的结构化 AI 调用”，不是平台所有
LLM 调用。普通聊天、语音流式调用等若未写该表，不在分母中。

数据库只保存 Prompt SHA-256 和长度，不保存 Prompt 原文，降低隐私和存储风险；错误消息截断到
1000 字符。写日志失败采用 fail-silent，不影响主业务。

## 2. 基础面试问题

**问题：为什么既记录指标又记录数据库日志？**

回答：指标低成本回答“成功率和延迟是否异常”，数据库日志回答“具体哪次调用、哪个 trace、什么错误”。
只有指标无法逐次审计，只有日志又不适合高频窗口聚合和告警。

**问题：attemptCount 和 retryCount 有什么区别？**

回答：attemptCount 包含首次调用，retryCount 是 `max(0, attemptCount-1)`。记录二者可以区分一次成功
和重试后成功，也能评估修复型重试是否有效。

**问题：为什么 Prompt 只存哈希？**

回答：完整 Prompt 可能含简历、面试回答和知识库内容。哈希可做重复识别与版本对比，又不直接存储
敏感正文；但字典可枚举的短 Prompt 仍可能被猜测，不能把哈希等同绝对匿名。

**问题：AI 调用成功的定义是什么？**

回答：当前 StructuredOutput 场景是“模型调用并完成结构化解析/修复后最终成功”，不是单纯 HTTP 200。
这更接近业务成功，但应与 transport success 分开记录，便于区分模型服务和解析问题。

## 3. 进阶面试问题

**问题：当前指标是否重复计数？**

回答：StructuredOutputInvoker 自己记录一组 context/status 指标，又委托 AiMetricsRecorder 记录一组
scenario/provider/model/status 指标；失败还有独立 Counter。它们是不同维度的并行指标，不应直接相加，
否则会重复。应建立指标目录说明主指标和辅助指标。

**问题：Provider 标签一定准确吗？**

回答：`recordBusinessAiMetrics` 通过 `LlmProviderProperties.defaultProvider` 解析，可能与数据库动态默认
Provider 或显式调用的实际 Provider 不一致。可观测数据应由实际执行的 Client/Provider 快照传入，
不能事后猜默认值。

**问题：fail-silent 有什么代价？**

回答：保护业务是正确的，但数据库故障时日志悄悄缺失，Dashboard 会显示低调用量甚至 0，形成假健康。
应额外记录 `observability.log.write.failure` Counter 和告警，监控系统也需要自监控。

**问题：为什么 success=null 不应默认为 failure？**

回答：null 可能代表旧数据、写入不完整或未知，和明确失败语义不同。把它放进失败分母会污染成功率。
字段应 non-null，历史数据迁移；统计时单独返回 unknownCount。

**问题：成功率告警为什么必须带流量门槛？**

回答：低流量下比例剧烈波动。应使用窗口内最小请求量、burn rate 或贝叶斯/置信区间思路；例如 5 分钟
至少 100 次且错误率超过阈值，再结合 1 小时窗口确认持续性。

## 4. 技术延伸问题

**问题：AI 监控还应记录哪些指标？**

回答：首 token 延迟、总延迟、输入/输出 token、费用、上下文长度、截断、429、超时、工具调用次数、
结构化解析失败类型、安全拦截和 fallback。标签需保持低基数，Prompt 内容只进安全日志或 Trace。

**问题：如何评估模型质量而不只看可用性？**

回答：在线记录任务成功、用户反馈、引用正确性和人工抽检；离线用版本化评测集比较准确率、格式遵循、
成本和延迟。质量指标必须按 promptVersion、modelVersion 和场景分组。

**问题：数据库日志量很大怎么办？**

回答：按日期分区、冷热分层、设置保留期；摘要走时序指标，原始日志采样；失败和高价值场景全量保留；
错误消息脱敏；必要时写入日志平台而不是 OLTP 主库。

## 5. 改进方案问题

**问题：如何让 AI 成功率覆盖全部调用？**

回答：在统一 Model Gateway/Registry Advisor 或 ObservationHandler 层记录所有 ChatModel 调用，再附加
业务 outcome。区分 transport、model、parse、business 四层状态，避免只覆盖 StructuredOutputInvoker。

**问题：如何修复 Provider/Model 标签？**

回答：客户端构建时附带不可变 `ProviderExecutionContext`，调用结果直接返回实际 providerId、model、
configVersion；Recorder 接收执行事实，不读取可能过期的默认配置。

**问题：数据库聚合查询怎么写？**

回答：Repository 返回 count、successCount、unknownCount、avgLatency、P95 所需数据或使用原生 SQL；
按 created_at、scenario、provider_id 建合理索引。Dashboard 不加载 errorMessage 和 promptHash。

**问题：如何避免错误消息泄密？**

回答：持久化前按错误类型映射并脱敏 API Key、Authorization、Prompt 片段和个人信息；前端摘要只显示
安全消息和 errorCode，详情需要高权限；设置保留期与访问审计。

## 6. 故障处理问题

**问题：Micrometer AI Counter 有增长，数据库调用数不增长，为什么？**

回答：检查 `AiInvocationLogService` 是否注入、数据库 save 是否失败、日志降级 warn、事务和表结构；
也可能该调用只记录 Micrometer 而不经过 StructuredOutputInvoker。两条链路不是强一致双写。

**问题：Dashboard Provider 分组与真实账单对不上，怎么查？**

回答：检查 Recorder 是否使用配置文件默认 Provider 而实际 Registry 已动态切换；检查显式 provider 调用、
fallback 和重试。应从执行响应或客户端上下文记录实际 Provider。

**问题：成功率高但用户仍报 AI 不可用，为什么？**

回答：样本可能只覆盖结构化调用，遗漏语音/普通聊天；最终解析成功不代表内容质量；还可能有前端、
WebSocket 或 TTS 故障。按用户旅程定义端到端 SLI，而不是只看模型子步骤。

**问题：AI 日志写入拖慢业务怎么办？**

回答：先确认数据库延迟和连接池；当前同步 save 在主调用返回路径上。可使用可靠异步队列或批量写，
但要处理丢失、背压和顺序；高压时优先保留失败和采样成功日志。
