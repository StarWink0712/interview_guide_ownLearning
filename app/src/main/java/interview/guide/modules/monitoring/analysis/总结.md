
          
## `BusinessMetricsQueryService` 分析

### 核心作用

这是一个**业务指标聚合查询服务**，为管理后台 Dashboard 监控面板提供最近 24 小时的全系统健康指标快照。它从一个统一的入口（`GET /api/monitoring/business-summary`）聚合四个完全不同的数据源，一次返回 7 个关键业务指标。

---

### 一、聚合的四个指标维度

| 指标域 | 数据源 | 查询方式 | 返回字段 |
|---|---|---|---|
| 异步任务 | `AsyncTaskRepository` | 数据库 `COUNT` 聚合（不加载全量） | `recentTaskCount`、`failedTaskCount` |
| AI 调用 | `AiInvocationLogRepository` | 数据库查询 + 内存流式计算 | `aiInvocationCount`、`aiSuccessRate` |
| RAG 检索 | `RagRetrievalLogRepository` | 数据库查询 + 内存流式计算 | `ragQueryCount`、`ragAverageHitCount` |
| 语音面试 | `MeterRegistry`（Micrometer） | 内存中读取 Timer 均值，零数据库开销 | `voiceAverageTurnLatencyMs` |

返回的 DTO：[`BusinessMetricsSummaryDTO`](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/monitoring/model/BusinessMetricsSummaryDTO.java)

### 三、各指标计算方法详解

#### 1. 异步任务统计（数据库端聚合，最优性能）

```java
// 第121-125行
long recentTaskCount = asyncTaskRepository.countByCreatedAtAfter(since);
long failedTaskCount = asyncTaskRepository.countByStatusInAndCreatedAtAfter(
    FAILED_TASK_STATUSES,  // FAILED + DEAD_LETTER 两种状态统一计入失败
    since
);
```

- **只用数据库 `COUNT` 聚合**，不加载任何实体到内存
- 失败状态包含 `FAILED` 和 `DEAD_LETTER`（死信队列）两种，因为死信意味着重试 3 次后仍失败

#### 2. AI 调用统计（内存流式计算，需加载全量数据）

```java
// 第129行：加载最近24小时所有 AI 调用日志
List<AiInvocationLogEntity> aiLogs = aiInvocationLogRepository.findByCreatedAtAfter(since);

// 第153-161行：内存中计算成功率
private double calculateAiSuccessRate(List<AiInvocationLogEntity> aiLogs) {
    long successCount = aiLogs.stream()
        .filter(log -> Boolean.TRUE.equals(log.getSuccess()))  // 安全处理 null
        .count();
    return successCount / (double) aiLogs.size();
}
```

- **调用次数** = 列表 `size()`（即最近 24 小时 LLM 调用总数）
- **成功率** = `success=true` 的记录数 / 总记录数，用 `Boolean.TRUE.equals()` 避免 null 误判

#### 3. RAG 检索统计（内存流式计算）

```java
// 第130行
List<RagRetrievalLogEntity> ragLogs = ragRetrievalLogRepository.findByCreatedAtAfter(since);

// 第173-179行：内存中计算平均命中数
private double calculateRagAverageHitCount(List<RagRetrievalLogEntity> ragLogs) {
    return ragLogs.stream()
        .filter(log -> log.getHitCount() != null)  // 过滤 null
        .mapToInt(RagRetrievalLogEntity::getHitCount)
        .average()
        .orElse(0);
}
```

- **查询次数** = 列表 `size()`
- **平均命中数** = 所有非 null 的 `hitCount` 求平均

这里和前面对接上了——`ragLogs` 数据正是由 [`RagRetrievalLogService.recordRetrieval()`](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/aiobservability/service/RagRetrievalLogService.java) 在每次 RAG 检索后写入的。

#### 4. 语音面试延迟（内存读取，零数据库开销）

```java
// 第199-206行
private double resolveVoiceAverageTurnLatencyMs() {
    if (meterRegistry == null) return 0;             // 优雅降级
    Timer timer = meterRegistry.find("app.voice.interview.turn.duration").timer();
    return timer == null ? 0 : timer.mean(TimeUnit.MILLISECONDS);
}
```

- 直接从 Micrometer 内存中的 Timer 读取均值，不查数据库
- 数据由 `VoiceMetricsRecorder` 在语音面试运行时实时写入

### 四、设计要点

| 设计点 | 说明 |
|---|---|
| **统一时间窗口** | 所有指标以 `LocalDateTime.now().minusHours(24)` 为统一起始时间，确保各指标之间时间对齐可比 |
| **混合数据源** | 数据库持久化数据（异步任务、AI 调用、RAG 检索）和内存实时指标（语音面试）共存于一个 DTO |
| **优雅降级** | `MeterRegistry` 使用 `@Autowired(required = false)` 可选注入，无 Micrometer 时语音面试指标返回 0，不影响其他指标 |
| **性能分级** | 异步任务用 `COUNT` 聚合（最优），AI/RAG 目前用全量查询 + 内存计算（代码备注提到数据量增长后应改为聚合查询） |
| **失败状态聚合** | `FAILED` + `DEAD_LETTER` 统一计入失败任务数 |

                    │  写入侧（运行时记录）         │

                                   │

                    ┌─────────────────────────────┐
                    │  BusinessMetricsQueryService │ ← 当前文件

                    └──────────────┬──────────────┘
                                   │
                                   ▼
                    ┌─────────────────────────────┐
                    │  MonitoringController        │

总结：`BusinessMetricsQueryService` 是"读取侧"的聚合入口，把前面我们分析过的 `RagMetricsRecorder`（Micrometer 写入）、`RagRetrievalLogService`（数据库写入）以及 AI 调用日志、异步任务、语音面试这几个分散的可观测性数据源，统一聚合成一个 Dashboard 能用的一次性查询接口。
