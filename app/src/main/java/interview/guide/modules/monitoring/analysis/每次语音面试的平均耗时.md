## `resolveVoiceAverageTurnLatencyMs` 方法详细分析

嗯，原理上就是这么简单：**总时间 ÷ 轮次数 = 平均耗时**。

有一点小区别需要再明确一下——它不是从数据库日志查的，而是从 **Micrometer 内存**中直接读取已经算好的平均值：

```
VoiceMetricsRecorder 每轮结束时记录一次
    ↓ Micrometer 自动算好了 mean
memory: count=150, totalTime=450000ms, mean=3000ms
    ↓
resolveVoiceAverageTurnLatencyMs()
    → 直接从内存读 timer.mean()
    → 返回 3000（毫秒）
```

Micrometer 相当于一个**一直在后台默默记账的会计**——每轮对话结束送一条数据给它，它实时更新手中的账本（count、total、mean）。你只需要问它"现在平均是多少？"就行，不需要自己翻数据库去算。

所以**其他三个指标是你自己去数据库翻账本来算**（查 SQL → Java stream 计算），而**这个指标是你直接问会计**（读内存中已有结果）。

<br />

```java
private double resolveVoiceAverageTurnLatencyMs() {
    if (meterRegistry == null) {
      return 0;
    }
    Timer timer = meterRegistry.find("app.voice.interview.turn.duration").timer();
    return timer == null ? 0 : timer.mean(TimeUnit.MILLISECONDS);
}
```

### 一句话描述

**从 Micrometer 内存中直接读语音面试每轮对话的平均耗时**，不需要查数据库。

***

### 这个方法和其他两个最大的区别

对比刚刚分析过的三个方法：

| 方法                                 | 数据从哪来                      | 怎么查                                 |
| ---------------------------------- | -------------------------- | ----------------------------------- |
| `calculateAiSuccessRate`           | 数据库 `ai_invocation_logs` 表 | `repository.findByCreatedAtAfter()` |
| `calculateRagAverageHitCount`      | 数据库 `rag_retrieval_logs` 表 | `repository.findByCreatedAtAfter()` |
| `resolveVoiceAverageTurnLatencyMs` | **Micrometer 内存**          | `meterRegistry.find(...).timer()`   |

前面两个都是——先去数据库 SELECT，数据拿到 Java 内存里再 stream 计算。

这个是——**根本不去数据库，直接读内存里已有的统计值**。

***

### 逐行拆解

#### 第 1 行：`if (meterRegistry == null) { return 0; }`

优雅降级。如果项目没引入 Micrometer 依赖（比如单元测试环境），`meterRegistry` 为 null，直接返回 0 而不是抛 `NullPointerException`。

#### 第 2 行：`Timer timer = meterRegistry.find("app.voice.interview.turn.duration").timer();`

从 Micrometer 的指标注册中心里找名叫 `app.voice.interview.turn.duration` 的 Timer。

这段代码的逻辑相当于：

```
meterRegistry（内存中的指标仓库）
    │
    └── Timer 名称: "app.voice.interview.turn.duration"
        │
        ├── count: 150      ← 总共记录了 150 次轮次
        ├── totalTime: 450s ← 150 轮总共花了 450 秒
        └── mean: 3s        ← 平均每轮 3 秒（450 / 150）
```

这个 Timer 是谁写入的？是 `VoiceMetricsRecorder` 在语音面试的每轮对话结束时调用的：

```java
// 在 VoiceMetricsRecorder 中（之前分析过的代码）
voiceMetricsRecorder.recordTimerSinceNanos(
    "app.voice.interview.turn.duration",  // 指标名称
    startNanos,                            // 该轮开始的时间戳
    "session_id", sessionId                 // 标签
);
// → Micrometer 自动更新 Timer 的 count、totalTime、mean、max 等统计值
```

#### 第 3 行：`return timer == null ? 0 : timer.mean(TimeUnit.MILLISECONDS);`

双重兜底：

- Timer 不存在（还没产生任何语音面试数据）→ 返回 0
- Timer 存在 → 返回平均耗时，单位毫秒

***

### 这个方法和其他三个的核心区别

| <br /> | 异步任务、AI 日志、RAG 检索      | 语音面试轮次延迟                  |
| ------ | ---------------------- | ------------------------- |
| 数据存储   | PostgreSQL 数据库         | Micrometer 内存             |
| 数据持久性  | 长期保存                   | 重启应用后丢失                   |
| 查询方式   | SQL → 网络传输 → Java List | 直接从内存读                    |
| 计算方式   | Java stream 自己算        | 读 Micrometer 算好的 `mean()` |
| 速度     | 快（但要走网络）               | 极快（纯内存操作）                 |

**为什么语音面试不也存数据库？**

因为"平均轮次延迟"是一个**实时流式指标**，每轮对话结束都需要更新。如果每次轮次结束都要 INSERT 一条数据库记录，再 SELECT 出来计算平均值，太浪费了。直接用 Micrometer 的 Timer 在内存中随写随算，性能最优。而且这个指标也不需要长期持久化——丢了也没关系，重新跑几轮语音面试就有了。

***

### 完整数据流

```
语音面试每轮对话结束
    ↓
VoiceMetricsRecorder.recordTimerSinceNanos("app.voice.interview.turn.duration", startNanos)
    ↓
Micrometer 内存中更新 Timer 统计值
    (count++, totalTime+=耗时, mean 自动重新计算)
    ↓
用户打开监控面板（GET /api/monitoring/business-summary）
    ↓
BusinessMetricsQueryService.getBusinessSummary()
    ↓
resolveVoiceAverageTurnLatencyMs()
    → meterRegistry.find("app.voice.interview.turn.duration").timer().mean()
    ↓
返回平均延迟（毫秒）
```

全程不碰数据库，纯内存操作。
