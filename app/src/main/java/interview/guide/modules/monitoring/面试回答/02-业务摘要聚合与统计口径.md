# 业务摘要聚合与统计口径

## 1. 模块基础讲解

`BusinessMetricsQueryService.getBusinessSummary()` 每次请求执行以下操作：

1. 计算 `since = LocalDateTime.now().minusHours(24)`。
2. 数据库 count 最近创建任务总数。
3. 数据库 count 最近创建且状态为 FAILED/DEAD_LETTER 的任务数。
4. 查询最近 24 小时全部 AI Invocation Entity，在内存计算成功率。
5. 查询最近 24 小时全部 RAG Retrieval Entity，在内存计算 hitCount 平均值。
6. 从 MeterRegistry 查找语音 turn Timer 并读取 mean。
7. 组装 record DTO 返回。

计算公式：

```text
AI 成功率 = success == true 的日志数 / AI 日志总数
RAG 平均命中 = 非 null hitCount 总和 / 非 null hitCount 日志数
语音平均延迟 = 某个匹配 Timer 的 totalTime / count
```

数据库表在 `created_at` 上有索引，时间过滤具备基本条件；但 AI/RAG 仍加载完整 Entity，包括错误正文、
问题和候选查询 JSON，统计数据量增大后成本明显。

## 2. 基础面试问题

**问题：为什么异步任务用 count 查询，而 AI/RAG 用 findAll 后计算？**

回答：任务 Repository 已有派生 count 方法；AI/RAG Repository 只提供按时间返回列表的方法。前者把
聚合下推数据库更高效，后者是当前实现的简化方案，应继续改为数据库投影聚合。

**问题：为什么失败任务包括 DEAD_LETTER？**

回答：DEAD_LETTER 表示超过重试或无法继续自动处理，运维意义上也是最终失败，需要纳入失败健康度。
FAILED 和 DEAD_LETTER 可在下钻页面再区分。

**问题：AI 成功率为什么用 double 0 到 1？**

回答：便于后端保持比率语义，前端乘 100 显示百分比；也便于和 Prometheus 错误率公式一致。但无
样本时不应简单返回 0。

**问题：RAG 平均命中越高越好吗？**

回答：不一定。命中数可能只是达到 topK，不代表相关性好；过多低质量片段还会污染 Prompt。应结合
零命中率、分数分布、答案质量、引用率和用户反馈。

## 3. 进阶面试问题

**问题：失败任务的时间口径准确吗？**

回答：当前按任务 `createdAt` 过滤，不是按 `failedAt/updatedAt`。一个 25 小时前创建、刚刚失败的任务
不会计入；一个刚创建后失败又修复的任务仍可能按当前 status 变化。指标名称应叫“最近创建任务中的
当前失败数”，或改为按状态事件时间统计。

**问题：四次数据库查询是否来自一致快照？**

回答：Service 没有 `@Transactional(readOnly=true)`，各 Repository 调用可能各自开启事务；查询期间
数据变化时，DTO 各项不是同一数据库快照。Dashboard 通常容忍近似一致，但应明确，必要时使用单条
聚合 SQL 或只读事务。

**问题：注释所说“同时发起查询”准确吗？**

回答：不准确，代码是顺序执行。盲目并发化也未必更好，会占更多连接；优先用数据库聚合、缓存和
独立时序后端，而不是用线程把低效查询同时打向数据库。

**问题：null success 和 null hitCount 如何影响结果？**

回答：`success=null` 被分母包含但不计成功，相当于失败；`hitCount=null` 既不进总和也不进平均分母，
但该日志仍计入 ragQueryCount。两者语义不一致，应在数据模型中将必要字段设为非空或显式统计 UNKNOWN。

**问题：`LocalDateTime` 有什么时间风险？**

回答：它不携带时区，应用和数据库时区不一致、夏令时切换或多区域部署会产生歧义。监控窗口最好用
UTC `Instant`，测试中注入 `Clock`，避免依赖真实当前时间。

## 4. 技术延伸问题

**问题：数据库端如何一次聚合？**

回答：使用 `COUNT(*) FILTER (WHERE ...)`、`AVG(hit_count)`、`SUM(CASE WHEN success THEN 1 END)` 等
SQL 或 Projection，只返回标量。也可为每个域独立聚合后在 Service 组合，避免加载 TEXT 列。

**问题：什么时候使用物化视图或预聚合表？**

回答：当原始日志量很大、Dashboard 高频刷新且允许分钟级延迟时，按分钟/小时预聚合。物化视图适合
定时刷新；流式聚合适合低延迟。原始日志仍保留有限周期供审计。

**问题：如何定义一个可靠的指标口径？**

回答：为每项记录名称、业务含义、事件时间、窗口、分母、过滤状态、实例范围、单位、无数据语义和
owner。没有这些元数据，数值本身很容易被误解。

## 5. 改进方案问题

**问题：DTO 应如何表达无数据？**

回答：将数值改为 `MetricValue(value, sampleCount, status, windowStart, windowEnd, scope)`；无样本返回
NO_DATA，Registry 缺失返回 UNAVAILABLE，真实 0 才是 AVAILABLE+0。前端据此显示 `--` 而不是 0%。

**问题：如何优化查询性能？**

回答：Repository 增加数据库聚合 Projection；只读事务；`created_at` 与筛选字段建组合索引；摘要
缓存 15 到 60 秒；限制可选窗口；对原始日志做保留期和分区；监控查询设置超时。

**问题：如何统一前后端统计窗口？**

回答：由一个后端 API 同时返回总体和按 scenario/provider 分组结果，并回传明确 window。不要让前端
用“最近 50 条”自行聚合去模拟 24 小时数据。

**问题：是否应该把四领域放在一个 DTO？**

回答：概览可以放一起，但每项必须有独立 availability 和 window。更复杂时按 domain 分 section，
允许某个数据源失败时部分返回，而不是一个仓库异常让整个 Dashboard 失败。

## 6. 故障处理问题

**问题：AI 成功率突然下降但调用量很少，如何判断？**

回答：先看样本数和置信度。1 次失败就是 0%，不应立即告警；设置最小流量门槛，再按 provider、model、
scenario、错误码下钻，并与上游 429/5xx 和部署事件关联。

**问题：RAG 平均命中一直等于 topK，说明什么？**

回答：可能检索永远返回满额候选，不代表质量好。检查 minScore、得分分布和低相关片段；增加零命中率、
平均最低分、引用命中和人工质量指标。

**问题：摘要接口导致数据库 CPU 升高怎么办？**

回答：查看慢 SQL 和返回行数，确认是否扫描 24 小时全部日志及 TEXT 列；立即加短缓存和频率限制，
随后改聚合 SQL、索引、分区或预聚合。

**问题：任务失败数和 Stream failed Counter 对不上，为什么？**

回答：数据库统计当前 Entity 状态且按创建时间；Counter 是进程生命周期事件累计，重启会变、重试
和最终失败记录时点也不同。先统一事件定义和窗口，再比较，不能期待两个不同口径天然相等。
