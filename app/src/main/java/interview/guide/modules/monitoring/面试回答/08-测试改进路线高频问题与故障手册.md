# 测试、改进路线、高频问题与故障手册

## 1. 模块基础讲解

当前相关测试主要验证：

- `BusinessMetricsQueryServiceTest`：任务计数、AI 1 成功 1 失败、RAG 2/4 命中和一个无标签语音 Timer。
- `AiMetricsRecorderTest`：Registry 缺失时 no-op，成功调用产生 Counter/Timer/Retry。
- `RagMetricsRecorderTest`：各阶段 Meter 和 noResult 行为。
- `TraceIdFilterTest`：自动生成、复用请求头、响应头写回和 MDC 清理。

这些测试证明基本计算和 Meter 注册可工作，但没有覆盖生产中最危险的边界：

- 实际语音 Timer 带 success/failure 标签时的多 Meter 选择。
- MeterRegistry 在真实 Spring Context 中是否存在。
- 数据库聚合大数据性能和时区边界。
- noData/unavailable 与真实 0 的区别。
- 多实例和重启后的指标口径。
- 超长/恶意 traceId、高基数标签和异步 MDC 传播。
- Controller 鉴权、限流和部分数据源故障。

## 2. 基础面试问题

**问题：请用一分钟介绍监控模块。**

回答：模块为后台提供业务摘要，聚合最近 24 小时异步任务、AI 调用和 RAG 日志，再读取语音面试
Micrometer Timer。它配套 Counter/Timer/Summary Recorder 和 traceId MDC。当前骨架完整，但指标
Registry/Prometheus 尚未真正接通，语音窗口和数据库窗口不一致，生产化需要统一口径和采集链路。

**问题：代码使用了哪些设计思想？**

回答：薄 Controller、Service 聚合、DTO record、Repository 数据源、Recorder 封装横切指标、Filter
注入关联 ID、fail-open 监控降级。未来可进一步使用 Adapter 和 Snapshot 模式隔离数据源。

**问题：当前代码最大的优点是什么？**

回答：业务指标覆盖 AI/RAG/异步/语音四个核心链路；数据库明细和实时指标互补；traceId 能关联失败；
Recorder 不阻塞主业务；测试覆盖了基本计算。

**问题：当前代码最大的缺点是什么？**

回答：指标依赖未落地导致 Recorder 可能 no-op；摘要混合不同窗口和实例范围；AI/RAG 全实体加载；
语音多标签 Timer 读取错误；无数据被当 0；监控接口缺鉴权/限流；前端分组只基于最近 50 条。

## 3. 进阶面试问题

**问题：如何测试 24 小时时间边界？**

回答：Service 注入 `Clock`，固定 now；构造窗口内、边界、窗口外数据，明确使用 after 还是 inclusive；
集成测试验证数据库时区和 SQL。不要用 `any(LocalDateTime.class)` 掩盖 since 是否正确。

**问题：如何测试语音 Timer 聚合 Bug？**

回答：在 SimpleMeterRegistry 注册 status=success 100ms 两次、failure 1000ms 一次，调用摘要；断言选择
规则或加权平均。现有测试只注册无标签单 Timer，无法复现实际 Handler 的 Meter 形态。

**问题：如何测试高基数保护？**

回答：配置 MeterFilter 最大 tag values，循环写入大量 sessionId/traceId，断言 Meter 数受限且产生
保护告警；静态检查禁止这些 key 出现在 Metrics API。

**问题：监控代码为什么需要故障注入？**

回答：要验证数据库超时、Registry 缺失、Prometheus 不可达、日志写失败时 Dashboard 的 PARTIAL/STALE
行为，以及监控失败不会拖垮业务。只测正常路径无法证明降级设计。

**问题：指标正确性如何做自动验算？**

回答：对同一可控事件同时读取数据库事实、Meter count/total 和 API 摘要，验证定义允许的差异；为每个
指标写 contract test，避免重构后名称、标签或分母悄悄改变。

## 4. 技术延伸问题

**问题：如何从监控走向 SRE 体系？**

回答：为核心用户旅程定义 SLI/SLO 和错误预算；用多窗口 burn rate 告警；建立 Runbook、值班、事故
复盘和容量规划；监控模块只是数据入口，可靠性需要组织流程闭环。

**问题：如何做合成监控？**

回答：定时执行最小简历分析、RAG 查询或语音探针，记录端到端成功和延迟；使用专用测试租户/数据，
限制成本，和真实用户指标分标签。合成成功不能替代真实流量 SLI。

**问题：如何监控监控系统本身？**

回答：Prometheus scrape success、采集延迟、规则评估失败、告警投递失败、日志丢弃、Trace exporter
队列和 Dashboard 数据新鲜度都要有元监控；否则“全是 0”可能只是监控坏了。

## 5. 改进方案问题

**问题：请给出分阶段改进路线。**

回答：

1. 接通采集：Actuator + Prometheus Registry + endpoint 安全，生产要求 Registry 必须存在。
2. 修正口径：NO_DATA/UNAVAILABLE、统一 window、语音按标签和集群聚合、前端不再用最近 50 条冒充窗口。
3. 优化性能：数据库 Projection、索引、分区、短缓存、查询超时和部分失败返回。
4. 完善信号：P95/P99、错误分类、Stream lag、RAG 零命中、语音首音频、实际 Provider/模型。
5. 建立追踪：W3C Trace Context、OpenTelemetry Span、异步上下文传播和日志关联。
6. 可靠性治理：SLO、burn rate 告警、Runbook、值班和复盘。

**问题：若只能先修三个 Bug，选什么？**

回答：先补真实 MeterRegistry/Prometheus，使指标不再静默失效；再修语音 Timer 时间窗和标签聚合；
最后把 AI/RAG 统计下推数据库并区分 noData，避免 Dashboard 既慢又误导。

**问题：代码可读性如何提升？**

回答：减少超长注释与实现不一致；为指标建立常量和 Catalog；DTO 每项带语义元数据；Repository 使用
命名 Projection；使用 Clock；统一英文低基数 Tag 值；测试 DisplayName 保持中文即可。

**问题：如何验证改造完成？**

回答：制造已知事件后，数据库、Actuator、Prometheus 和 Dashboard 数值可按公式验算；多实例总数正确；
重启不造成历史窗口丢失；无流量显示 NO_DATA；性能压测满足查询 SLO；越权访问被拒绝。

## 6. 故障处理问题

**问题：线上告警 AI 成功率下降，标准排查顺序是什么？**

回答：确认样本数和监控新鲜度；按 provider/model/scenario/errorCode 切片；查看 429、超时、解析失败；
下钻代表性 trace；对照发布、配置切换和上游状态；必要时降级/切 Provider，恢复后验证错误预算。

**问题：监控数值明显不可信怎么办？**

回答：先停止基于该指标的自动化动作，标记 Dashboard stale；用原始数据库事件和日志手工验算；检查
窗口、分母、标签、多实例和 Counter reset；修复后补 contract regression test。

**问题：监控查询失败是否应该让整个后台不可用？**

回答：不应。各 section 独立捕获并返回 PARTIAL，保留最近成功快照和错误状态；但不能用 0 伪装失败。
同时监控查询失败本身应告警。

**问题：如何回答“为什么不用现成 Grafana，自己写 Dashboard”？**

回答：业务后台摘要适合给产品/运营提供受权限控制、口径稳定的少量 KPI；Grafana 更适合工程师自由
探索时序指标。两者互补，业务 Dashboard 不应重新实现完整监控平台。

**问题：一句话总结改进方向。**

回答：当前模块已经有“采集点、明细、聚合、展示、下钻”的形状，下一步要让每个数字都具备可验证的
来源、窗口、样本和作用域，并确保监控链路本身可用、安全、低成本。
