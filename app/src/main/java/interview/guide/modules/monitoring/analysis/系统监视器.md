
## MonitoringController 分析

这是一个 **业务监控概览** 接口，很短——只有一个端点，但背后聚合了三个子系统的数据。

---

### 一、整体架构

```
前端 MonitoringPage（管理后台）
    ↓ GET /api/monitoring/business-summary
MonitoringController
    ↓
BusinessMetricsQueryService
    ├── AsyncTaskRepository         → 异步任务（总数 + 失败数）
    ├── AiInvocationLogRepository   → AI 调用（次数 + 成功率）
    ├── RagRetrievalLogRepository   → RAG 检索（次数 + 平均命中数）
    └── MeterRegistry               → 语音面试（平均轮次延迟）
    ↓
BusinessMetricsSummaryDTO ← 返回给前端
```

### 二、返回的数据

```java
public record BusinessMetricsSummaryDTO(
    LocalDateTime since,          // 统计时间范围：最近 24 小时
    long recentTaskCount,         // 最近 24 小时新增的异步任务数
    long failedTaskCount,         // 其中失败的任务数
    long aiInvocationCount,       // AI 调用次数
    double aiSuccessRate,         // AI 调用成功率（0~1）
    long ragQueryCount,           // RAG 检索次数
    double ragAverageHitCount,     // RAG 平均命中文档块数
    double voiceAverageTurnLatencyMs  // 语音面试平均轮次延迟（毫秒）
) {}
```

**其实就是项目整体的健康仪表盘**——把四个核心业务域（异步任务、AI 调用、RAG 检索、语音面试）的关键指标汇总到一条。可以理解成"7 个数字看懂系统今天状态"。

### 三、指标来源对照

| 指标 | 数据来源 | 统计方式 |
|------|---------|---------|
| `recentTaskCount` | `AsyncTaskRepository.countByCreatedAtAfter()` | 数据库 count |
| `failedTaskCount` | 同上，按状态 FILTER failed/dead_letter | 数据库 count |
| `aiInvocationCount` | `AiInvocationLogRepository.findByCreatedAtAfter()` | 获取列表后取 size() |
| `aiSuccessRate` | 同上，stream 过滤 success=true 后计算比例 | 业务层计算 |
| `ragQueryCount` | `RagRetrievalLogRepository.findByCreatedAtAfter()` | 获取列表后取 size() |
| `ragAverageHitCount` | 同上，mapToInt hitCount 求平均值 | 业务层计算 |
| `voiceAverageTurnLatencyMs` | Micrometer Timer，从内存中取均值 | Micrometer API |

### 四、Micrometer 的妙用：`resolveVoiceAverageTurnLatencyMs()`

这个方法跟其他六个指标不同——它**不从数据库查，而是从 Micrometer 的 Timer 中读**：

```java
private double resolveVoiceAverageTurnLatencyMs() {
    if (meterRegistry == null) return 0;  // 优雅降级
    Timer timer = meterRegistry.find("app.voice.interview.turn.duration").timer();
    return timer == null ? 0 : timer.mean(TimeUnit.MILLISECONDS);
}
```

语音面试的平均轮次延迟是一个**实时写入、内存中聚合**的指标，不需要先存数据库再查。直接从 Micrometer 的 Timer 中取 `mean()`，**零数据库开销**。

这也是两个子系统（AiInvocationLog、RagRetrievalLog 写数据库本表然后查询）和另外两个（`AsyncTaskRepository`、Micrometer）的 hybrid 方案。

### 五、设计评价

**做得好的地方**：
- 只用 7 个数字概括了四大业务域的概况，适合**管理后台 Dashboard 页面**的顶部概览卡片
- single endpoint，简单直接
- `@Autowired(required = false)` 保留了优雅降级，没有 Micrometer 不影响

**一个小缺陷**：

```java
// 当前：find 出所有记录，在 Java 内存中计算
List<AiInvocationLogEntity> aiLogs = aiInvocationLogRepository.findByCreatedAtAfter(since);
// 然后 size() + stream.filter().count() 计算成功率

// 更好的方案：直接在 SQL 层面聚合
// @Query("SELECT COUNT(e), SUM(CASE WHEN e.success = true THEN 1 ELSE 0 END) FROM ...")
```

如果 24 小时内有数万条 AI 调用记录，全量加载到 Java 内存中再计算会有 OOM 风险。比较好的做法是用 `@Query` 在数据库层面直接聚合：

```java
public interface AiInvocationLogRepository extends JpaRepository<...> {
    @Query("SELECT new interview.guide...AiInvocationStats(" +
           "COUNT(e), SUM(CASE WHEN e.success = true THEN 1 ELSE 0 END)) " +
           "FROM AiInvocationLogEntity e WHERE e.createdAt >= :since")
    AiInvocationStats getInvocationStatsSince(@Param("since") LocalDateTime since);
}
```

不过在当前项目规模下，这不算大问题。

### 六、一句话总结

> **MonitoringController 是系统的"体检报告"接口**——不关心细节，只看 7 个关键指标。前端 MonitoringPage 用它在 Dashboard 顶部展示系统健康概览。架构上的亮点是同时使用了数据库查询和 Micrometer 内存指标两种数据源，在实现简洁性和性能之间做了良好的平衡。
