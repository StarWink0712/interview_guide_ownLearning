# 性能、多实例、时间窗口与数据一致性

## 1. 模块基础讲解

当前 Dashboard 聚合的是两种不同作用域：

| 数据 | 窗口 | 持久性 | 多实例范围 |
|---|---|---|---|
| AsyncTask/AI/RAG 数据库 | 最近 24 小时 | 持久化 | 共享数据库范围 |
| Voice Timer | 当前进程累计 | 重启丢失 | 当前 JVM |
| 前端 scenario/provider 表 | 最近 50 条 AI 日志 | 持久化 | 共享数据库范围 |

因此“最近窗口内业务指标”只是部分成立。生产监控必须同时明确：event time、query window、service
instance、environment 和聚合规则。

当前摘要每次刷新顺序执行四个数据库查询和一次内存查找，没有缓存。AI/RAG 查询返回完整 Entity，
在高数据量下会导致：

- 数据库传输大量 TEXT/JSON 列。
- JVM 创建大量对象并做 Stream 聚合。
- 请求期间堆占用和 GC 增加。
- 多个管理员刷新会重复相同计算。

## 2. 基础面试问题

**问题：为什么内存 Timer 不能直接做集群平均值？**

回答：每个实例有独立 Registry，流量也可能不均衡。平均值不能简单平均各实例 mean，必须按各实例
count 加权，即 `sum(totalTime)/sum(count)`。Prometheus 能对所有时间序列做这种聚合。

**问题：应用重启对 Counter/Timer 有什么影响？**

回答：本地累计值从零开始。Prometheus 抓取的 Counter 会出现 reset，查询 rate 能处理；直接在应用
内读 mean 则窗口被截断。实例启动时间应作为指标元数据。

**问题：为什么摘要接口适合缓存？**

回答：Dashboard 不需要毫秒级实时，多个用户在几十秒内看到相同快照是可接受的。短缓存能显著减少
重复聚合，缓存 key 要包含窗口和环境。

**问题：监控查询为什么也要设置超时？**

回答：监控不能反过来拖垮业务数据库。慢聚合应快速失败或返回部分数据，并使用只读连接、资源隔离和
查询超时。

## 3. 进阶面试问题

**问题：如何计算最近 24 小时 Timer 平均值？**

回答：Prometheus 中对 Timer 的 `_seconds_sum` 和 `_seconds_count` 分别计算 24 小时 increase/rate，
再相除，并按需要 sum 掉 instance。直接调用当前 JVM `timer.mean()` 无法恢复精确窗口。

**问题：平均值为什么不能平均？**

回答：实例 A 1 次 100ms、实例 B 100 次 200ms，简单平均 mean 得 150ms，真实加权平均约 199ms。
必须聚合总耗时和总次数。

**问题：读事务能完全解决摘要不一致吗？**

回答：取决于数据库隔离级别。PostgreSQL READ COMMITTED 下同一事务的不同语句仍可能看到不同提交
快照；REPEATABLE READ 才固定快照。监控通常接受近似一致，更实际的是记录 windowEnd，并用单条
聚合 SQL 或预聚合快照。

**问题：日志表如何做生命周期管理？**

回答：按 createdAt 分区，保留近期热数据；成功日志可采样或短保留，失败/审计日志长保留；老分区
归档到对象存储。删除策略必须兼顾隐私合规和故障回溯。

**问题：为什么前端平均延迟可能偏低？**

回答：前端 `aggregateLogs` 把 `latencyMs=null` 当 0 加入总和，并以全部 count 为分母；而且只取最近
50 条。应由后端过滤 unknown 或单独统计，返回同一窗口的加权结果。

## 4. 技术延伸问题

**问题：如何做实时与历史两层监控？**

回答：Prometheus/时序库负责秒到天级趋势和告警；PostgreSQL/日志平台保存事件详情；按小时生成业务
报表快照供长期趋势。Dashboard 组合这些来源时明确各自更新时间和可用状态。

**问题：如何做跨地域监控？**

回答：指标带 region/cluster/environment 低基数标签，各区域本地采集，再远程写入中心时序库；告警
既看区域也看全局。LocalDateTime 改 UTC Instant，UI 再按用户时区展示。

**问题：何时用缓存，何时用预聚合？**

回答：查询本身不贵但刷新频繁时用短缓存；原始量巨大、复杂窗口频繁查询时做分钟/小时预聚合。两者
都要定义数据新鲜度和失效策略。

## 5. 改进方案问题

**问题：如何让 Dashboard 支持多实例？**

回答：数据库指标天然共享；实时指标交给 Prometheus 按 `sum by` 聚合，后端通过 Prometheus HTTP API
查询或让 Grafana 展示。不要从某个随机应用实例读取本地 Registry 代表集群。

**问题：如何优化数据库统计？**

回答：建立只返回标量的 Projection；组合索引；限制 window 最大值；日志表分区；缓存摘要；必要时用
只读副本和 statement timeout。避免 SELECT 整个 Entity 后在 Java 计算。

**问题：如何定义 Dashboard 快照？**

回答：统一 `windowStart/windowEnd/generatedAt`，每个 section 带 source/scope/status/sampleCount；允许
某一数据源失败时返回 PARTIAL，不把旧缓存伪装成实时数据，UI 标识 lastUpdated。

**问题：如何防止查询惊群？**

回答：前端请求去重和合理刷新间隔；后端 single-flight + TTL 缓存；超时后使用最近成功快照并标 stale；
不允许每个浏览器秒级轮询重型数据库聚合。

## 6. 故障处理问题

**问题：不同实例打开 Dashboard 数值不同，为什么？**

回答：数据库项应相同但查询时点可能略有差异；语音项必然是本机 Registry，实例流量和启动时间不同。
检查请求路由实例、instance 标签和启动时间，改由集群时序后端聚合。

**问题：应用重启后语音延迟突然变成 0，怎么办？**

回答：本地 Timer 被重置，等待新样本后才有值；UI 应显示 NO_DATA 而不是 0ms。历史趋势应从 Prometheus
读取，不依赖进程内累计。

**问题：24 小时查询跨午夜结果异常，怎么查？**

回答：检查 JVM、数据库和容器时区，LocalDateTime 的解释，以及夏令时。改为 UTC Instant 后，用明确
windowStart/windowEnd 查询，并注入 Clock 做边界测试。

**问题：Dashboard 刷新导致连接池耗尽怎么办？**

回答：立即限制接口频率、启用缓存和查询超时；查看慢 SQL/返回行数；长期下推聚合、使用只读副本或
时序后端，并为监控查询设置独立 bulkhead。
