对，一个 `KnowledgeBaseEntity` 就是数据库里的一条记录，对应一个上传的文档。都是元数据。

但有一个细节：**相同内容的文档不会新建实体**。因为 `fileHash` 字段有唯一索引，上传同一个 PDF 两次时，去重逻辑会命中已有实体，只累加访问计数，不建新记录。

```
数据库 knowledge_bases 表：

| id | name       | originalFilename | fileHash (唯一)    | vectorStatus |
|----|------------|------------------|---------------------|--------------|
| 1  | 面试题库    | 面试题.pdf        | a1b2c3...           | COMPLETED    |
| 2  | 项目文档    | 需求.docx         | d4e5f6...           | COMPLETED    |
| 3  | 技术规范    | spec.txt          | g7h8i9...           | PROCESSING   |
```

一个实体 = 一个文档，但注意它的 `chunkCount` 字段表示向量化后这个文档被切成了多少块存到 pgvector 里，所以查询时是一对多的关系（一个实体 → 多个向量块）。

<br />

对，`KnowledgeBaseEntity` 存的全是元数据，没有文件内容本身。

回顾一下它的字段就一目了然：

```
KnowledgeBaseEntity（数据库 knowledge_bases 表）
  ├── id              — 主键
  ├── fileHash        — SHA-256 哈希（去重用，唯一索引）
  ├── name            — 知识库名称（如"面试题库"）
  ├── category        — 分类（如"技术面试"）
  ├── originalFilename — 原始文件名（如"面试题.pdf"）
  ├── fileSize        — 文件大小（字节）
  ├── contentType     — MIME 类型
  ├── storageKey      — RustFS 的 key ← 指向文件本体的"指针"
  ├── storageUrl      — RustFS 下载 URL
  ├── vectorStatus    — 向量化状态
  ├── accessCount     — 访问次数
  └── questionCount   — 提问次数
```

**真实数据存在三个地方**：

| 数据       | 存在哪                                                       |
| :------- | :-------------------------------------------------------- |
| 文件二进制内容  | **RustFS**（Key-Value 对象存储）                                |
| 元数据      | **PostgreSQL**（`knowledge_bases` 表，`KnowledgeBaseEntity`） |
| 向量化后的文本块 | **pgvector**（一个文档被切成 N 个 chunk，每个 chunk 存一条向量记录）          |

所以 `KnowledgeBaseEntity` 只是"索引卡片"——告诉你文件叫什么、存在哪、状态如何，但卡片本身不包含文件内容和向量数据。
