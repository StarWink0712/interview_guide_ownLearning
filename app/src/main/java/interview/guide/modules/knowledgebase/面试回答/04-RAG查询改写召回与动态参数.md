# RAG 查询改写、召回与动态参数

## 1. 模块基础讲解

`KnowledgeBaseQueryService` 的检索阶段依次执行：问题 trim、可选 LLM Query Rewrite、构造“改写问题 + 原问题”
候选、按原问题长度选择 topK/minScore、逐候选向量检索、首个有效命中即返回，并把参数、延迟和 chunk 写入 RAG
Trace。短问题长度不超过 4 时 topK=20/minScore=0.18，中等问题 topK=12，长问题 topK=8，默认阈值 0.28。

Query Rewrite 会把多轮历史格式化到 Prompt，解决“它的优点呢”这类指代不清的追问；失败时降级为原问题，避免
改写模型不可用让整个问答失败。`LinkedHashSet` 保持改写优先并去除完全相同的候选。

当前策略简单、可解释且有降级，但它不是多路召回融合：一旦改写查询有非空结果就不再检索原问题，也没有去重、
分数归一化、重排或上下文预算控制。

## 2. 基础面试问题

**问题：为什么需要 Query Rewrite？**

回答：用户问题可能短、口语化或依赖上下文，直接 Embedding 会缺少检索词。改写把对话意图展开为自包含查询，常能
提升召回；但可能引入新事实，因此必须保留原问题兜底并评测改写收益。

**问题：topK 和 minScore 分别控制什么？**

回答：topK 限制最多返回多少块，影响上下文覆盖和成本；minScore 过滤弱相关块，影响噪声和零命中率。阈值不是跨
模型通用常量，要根据 Embedding、数据集和距离转换方式校准。

**问题：为什么短问题使用更大的 topK、更低阈值？**

回答：短问题语义信息少，向量分布更模糊，扩大召回可降低漏检；代价是噪声和上下文成本增加。当前仅按字符长度
启发式判断，属于经验规则，需要离线评测验证。

**问题：查询为什么要按 kbId 过滤？**

回答：会话只允许基于用户选择的知识库回答。过滤既是业务范围控制，也是未来权限隔离的一部分；它应尽量下推到
向量库，不能先全局取少量结果再本地过滤。

## 3. 进阶面试问题

**问题：首个非空候选返回有什么偏差？**

回答：非空不等于质量最好。改写查询可能返回一个刚过阈值的弱结果，而原问题可能命中多个高分块；当前不会比较。
更合理的是并行召回、按 document/chunk ID 去重，使用 RRF 或 reranker 合并。

**问题：阈值能直接当“相关概率”吗？**

回答：不能。`Document.getScore()` 的语义取决于 VectorStore 的距离到相似度转换，分布也受模型和语料影响。阈值应
在标注数据上用 precision-recall 曲线选择，并按查询类型监控，不应解释成 28% 的相关概率。

**问题：历史上下文处理有什么边界？**

回答：上游最多取配置消息数，但改写格式化只截断 assistant 到 200 字符，user 消息没有字符/token 上限。恶意或
异常长用户消息仍能放大 Prompt 成本。还需按 token 总预算、角色和轮次裁剪。

**问题：配置能热更新吗？**

回答：`KnowledgeBaseQueryProperties` 是可绑定 Bean，但 QueryService 构造时把开关和参数复制到 final 字段，并加载
Prompt 模板，因此运行期修改配置对象不会影响现有实例。需要刷新作用域、动态读取或显式配置版本发布。

## 4. 技术延伸问题

**问题：除了 Rewrite 还有哪些检索增强？**

回答：Multi-Query 生成多个视角；HyDE 先生成假设答案再检索；Parent-Child Retrieval 用小块召回、大块补上下文；
Self-Query 从问题提取 metadata filter；Reranker 对候选精排。每种方案都增加延迟和成本。

**问题：如何融合多路召回？**

回答：向量、BM25、原问题和改写问题分别取候选，使用稳定 chunkId 去重；不同分数不可直接相加时用 Reciprocal
Rank Fusion；再对前 N 条做 cross-encoder 重排，最后按 token 预算与多样性选上下文。

**问题：如何评测检索？**

回答：建立问题、相关 chunk/文档、不可回答标签；计算 Recall@K、MRR、nDCG、Precision@K 和零命中；按短问、
追问、专名、数字、跨文档问题切片，并同时记录延迟与成本。

## 5. 改进方案问题

**问题：如何改造当前 Retriever？**

回答：返回带 source、score、rank、candidateType 的 `RetrievedChunk`；并行执行候选检索；明确只捕获“过滤表达式
不支持”异常，Provider/DB 错误直接上抛；融合、去重、重排后再记录最终和各阶段候选。

**问题：查询前需要哪些校验？**

回答：去重 kbId，验证存在、归属和读取权限；要求 active vector version READY；限制知识库数量、问题长度和历史
token；没有 READY 的库返回明确状态，不能静默当作零命中。

**问题：如何调优动态参数？**

回答：不要只看字符长度；加入查询分类、专名密度、历史依赖和知识库规模。离线网格搜索 topK/threshold/rerankK，
线上 A/B 观察有答案率、人工满意度、TTFT 与 token，配置携带版本并写入 Trace。

## 6. 故障处理问题

**问题：Rewrite 后召回变差怎么排查？**

回答：在 Trace 对比原问题、改写问题和各自候选，不只记录最终首个结果；检查是否改变专有名词、数字或否定语义；
临时关闭 rewrite 或对特定查询分类 bypass；用回归集修 Prompt 和模型。

**问题：过滤检索报错后为什么结果仍为空？**

回答：当前会回退为全局 `topK * 3` 再本地过滤，目标知识库可能不在全局前列。先修正确 metadata 类型和过滤 DSL，
查看第一次异常堆栈；不要把所有异常都误判成过滤不兼容。

**问题：线上零命中率突然升高如何定位？**

回答：按 embeddingModel、vectorVersion、知识库状态和配置版本切片；查阈值是否变更、Provider 是否切换、向量行数
是否下降、过滤 metadata 是否丢失；用固定探针问题对比向量分数分布和原始 SQL。
