# 数据模型、统计口径、删除一致性与安全

## 1. 模块基础讲解

知识库元数据保存哈希、名称、分类、文件信息、访问/提问计数、向量状态、错误与 chunkCount。Repository 提供分类、
模糊搜索、状态和聚合；ListService 映射 DTO、内存排序、统计和下载。删除服务按“解除会话关联、删向量、删对象、
删元数据”执行，并对向量/对象失败采取 fail-open。

设计上的优点包括 Entity/DTO 隔离、批量 SQL 增加 questionCount、哈希唯一约束和状态统计。主要问题是统计口径互相
冲突：每次查询会给所有选中知识库 questionCount +1，但总提问数只统计 RAG 聊天 USER 消息，直接 `/query`
不计；accessCount 初始为 1 且只在重复上传时增加，并不代表真实访问。

删除跨会话关系、向量表、RustFS 和元数据，没有统一事务。吞掉向量/对象异常可保证主记录删除，却会制造无法从
业务表追踪的孤儿资源；也没有补偿任务或对账状态。

## 2. 基础面试问题

**问题：为什么提问计数使用单条批量 UPDATE？**

回答：一次多知识库查询不应循环 N 次查改写，批量 SQL 减少网络往返并由数据库原子自增，避免普通 Entity
read-modify-write 的 lost update。代码还先 distinct 并验证所有 ID 存在。

**问题：为什么下载不应直接返回 storageUrl？**

回答：后端可做权限、审计、Content-Disposition 和存储实现隔离；也可授权后生成短期 presigned URL，把大文件
传输卸载给对象存储。永久公开 URL 容易绕过权限。

**问题：为什么删除顺序要先解除会话关联？**

回答：中间表外键仍引用知识库时直接删主记录可能失败。先移除关联满足约束；但应批量执行并在数据库事务中保证
关系和元数据的一致性。

**问题：模糊搜索 `%keyword%` 有什么特点？**

回答：参数化 JPQL 可防 SQL 注入，但前导 `%` 通常不能使用普通 B-tree，数据大时全表扫描。PostgreSQL 可用
pg_trgm GIN/GiST，或全文检索并加入分页。

## 3. 进阶面试问题

**问题：当前统计为什么会“看起来都对但互相对不上”？**

回答：per-KB questionCount 统计参与查询次数，且多库查询每库都加一；总提问数只数聊天 user 消息；同步/直接
流式问答不进入聊天消息；失败或零命中在检索前已经加计数。指标名称没有表达这些口径差异。

**问题：删除服务为什么不是一个简单事务问题？**

回答：JPA 事务只能覆盖关系表和元数据，不能原子回滚 RustFS；向量表虽同 PostgreSQL，也通过独立调用且异常被
吞掉。把整个方法加 `@Transactional` 还会在对象删除时占连接，并不能解决外部副作用。

**问题：`deleteByKnowledgeBaseId` 的事务注解是否完全生效？**

回答：DeleteService 外部调用时会经过代理；但 VectorService 的 `vectorizeAndStore` 同类内部调用该方法，不经过
代理。底层 Repository 可能仍有自己的事务，但方法级“短事务”语义不能靠内部调用保证。

**问题：日志和 Trace 有哪些隐私风险？**

回答：Controller/QueryService INFO 日志记录完整问题；RAG 日志持久化原问题、改写问题、候选、kbId，并保存每个
chunk 前 500 字。内容可能含简历、公司资料和个人信息，需要脱敏、权限与保留期。

## 4. 技术延伸问题

**问题：跨资源删除如何做最终一致性？**

回答：先把知识库标 DELETING 并禁止查询；同事务写删除 outbox；Worker 幂等删除向量和对象并记录各步骤；全部完成
后删元数据或保留墓碑；失败指数重试并可人工介入。定期对账处理长期孤儿。

**问题：统计应该用 Counter 字段还是事件表？**

回答：Counter 读取快但口径固定、难回溯；事件表可按成功、入口、用户、知识库重新聚合，但成本高。常见做法是
保存不可变 QueryEvent，异步聚合到日报/计数表，业务元数据只保留明确含义的缓存字段。

**问题：大列表如何优化？**

回答：Repository 接收 Pageable 和白名单 Sort，把过滤排序下推 DB；列表使用 projection；批量查名称避免 N+1；
会话知识库用 EntityGraph/batch fetch；API 返回游标或页码和 total。

## 5. 改进方案问题

**问题：如何重新定义统计口径？**

回答：拆为 requestCount、answeredCount、noHitCount、failedCount、knowledgeBaseParticipationCount、downloadCount；每项
明确入口、去重单位和时间窗口。旧 questionCount 标注为 participation，不再与消息数混称“总提问”。

**问题：如何改进删除实现？**

回答：批量删除中间表关联；向量删除异常必须返回结果，不能双层吞异常；对象删除写 durable task；DELETING 状态
防止消费者重建；消费者写向量前后校验 desiredVersion/删除墓碑；管理端展示补偿进度。

**问题：Controller/API 有哪些可读性改进？**

回答：上传和分类使用 typed Request/Response；非法 VectorStatus 抛 BusinessException，由全局处理；详情不存在也
统一异常；下载流式返回 Resource；所有列表分页；查询/上传/下载/聊天按用户、IP 和全局维度限流。

## 6. 故障处理问题

**问题：删除返回成功但存储费用不降怎么办？**

回答：按已删除 kbId 查 vector metadata 和 RustFS key；检查吞掉的 WARN 日志；扫描孤儿对象/向量；建立补偿任务
重删并记录结果。以后不能在无 durable 状态的情况下把外部删除失败当最终成功。

**问题：统计数字异常增长如何排查？**

回答：先确认指标口径；按入口和 trace 去重；检查前端重试、SSE 重连、重复 Stream 消息和多库参与计数；对比事件
日志与聚合字段；修复后用幂等 queryId/eventId 防止重复计费。

**问题：知识库列表变慢怎么办？**

回答：查看总行数、返回 payload、SQL 和 EXPLAIN；确认是否全量加载后内存排序、会话列表 N+1 或 `%keyword%` 扫描；
加分页、DB 排序、projection 和 trigram 索引，并以 P95/堆内存验证效果。
