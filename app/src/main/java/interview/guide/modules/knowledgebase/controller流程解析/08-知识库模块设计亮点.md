# 知识库模块设计复盘：亮点、边界与改进优先级

> 本文不再罗列接口，而是基于前 8 篇真实调用链，解释当前设计为什么有效、哪里只是“尽力而为”，
> 以及最值得优先改造的部分。

## 1. 模块分层

```text
React 页面
  → knowledgeBaseApi / ragChatApi
  → KnowledgeBaseController / RagChatController
  → 专职 Service
      → Upload / List / Delete / Query / RagChatSession
  → Infrastructure
      → PostgreSQL JPA
      → pgvector / VectorStore
      → RustFS / FileStorageService
      → Redis Stream
      → ChatClient / Embedding
```

Controller 大体只做路由、参数绑定、限流和委托；上传、列表、删除、RAG 查询和聊天会话分别由
专职 Service 编排，避免单个“万能 KnowledgeBaseService”。

## 2. 值得保留的设计

### 上传先去重

文件哈希在解析、上传和向量化之前计算。重复文件直接复用旧记录，避免重复占用 RustFS、Embedding
额度和 pgvector 空间。

### 文件与大文本不进入 Stream

Stream 消息只携带 `taskId/kbId/retryCount/traceId`，统一异步任务 payload 只记录内容长度。Consumer
按 storageKey 从 RustFS 获取原文件，避免 Redis Stream 被大文本撑大。

### 向量任务有统一生命周期

`AbstractStreamProducer/Consumer + AsyncTaskService` 提供：

- 活跃任务去重；
- PENDING/PROCESSING/COMPLETED/FAILED 状态；
- 自动重试和死信；
- traceId 跨线程日志；
- pending 消息恢复；
- 管理后台人工重试/取消。

### 向量写入按批处理

文本使用 TokenTextSplitter 分块，Embedding 每批最多 10 个 chunk，适配 Provider 批量限制。每个
Document 带 `kb_id` metadata，为多知识库过滤和删除提供关联键。

### RAG 不只是“向量搜索 + Prompt”

查询链包含：

- 可选 Query Rewrite，失败回退原问题；
- 根据问题长度动态选择 topK/minScore；
- 改写问题与原问题双候选召回；
- pgvector 前置过滤失败后的本地过滤兜底；
- 无有效召回时不调用回答模型；
- Prompt 防注入附加指令；
- 统一无结果回答；
- trace、检索日志和 Micrometer 指标。

### RAG 会话消息可恢复

用户消息和 AI 占位在流开始前持久化，流完成后回写完整正文。会话详情将知识库和消息分两次
查询，避免多集合 fetch join 的笛卡尔积。

### DTO 隔离

普通 JSON 接口通过 MapStruct/record 返回 DTO，不直接暴露 JPA Entity。请求 DTO 在主要 RAG
入口使用 `@Valid`。

## 3. “看起来可靠”但尚未形成闭环的地方

### TransactionAfterCommit 在上传链中实际立即执行

Producer 支持事务提交后发送，但 UploadService 调用 Producer 时，持久化 Service 的事务已经结束。
所以执行器检测不到活动事务并立即 XADD。它提供了抽象能力，却没有在当前调用位置实现
“元数据事务提交后可靠投递”的原子闭环。

### 入队失败被吞掉

`AbstractStreamProducer.sendTask` 捕获异常、更新 FAILED 后返回 null。对后台容错有价值，但上层
上传/重试接口仍返回成功，甚至上传响应硬编码 PENDING，用户看到的同步结果可能与数据库不同。

### 删除是尽力删除

删除跨会话关联、pgvector、RustFS、知识库元数据，没有统一事务或删除状态机。向量/文件失败被
吞掉以保证主记录最终消失，代价是孤儿数据和难以自动修复。

### SSE 的“完成”不覆盖 cancel

`doOnComplete/doOnError` 能处理正常结束和错误，但客户端断开是 cancel。没有 cancel 补偿时，
AI 占位可能永久未完成。

## 4. 数据一致性矩阵

| 场景 | PostgreSQL | RustFS | Redis Stream | pgvector | 风险 |
|---|---|---|---|---|---|
| 新上传成功 | 元数据 | 原文件 | 消息 | 异步生成 | 正常 |
| DB 保存失败 | 无，尝试补偿 | 尝试删除 | 无 | 无 | 补偿失败留孤儿文件 |
| XADD 失败 | 元数据 FAILED | 原文件 | 无 | 无 | HTTP 仍可能成功 |
| 分批向量中途失败 | 元数据 FAILED | 原文件 | 重试消息 | 可能部分写入 | 重试前先删旧向量 |
| 删除向量失败 | 最终可能删除 | 最终可能删除 | 不处理 | 残留 | 孤儿向量 |
| 删除文件失败 | 最终可能删除 | 残留 | 不处理 | 已删/残留 | 孤儿文件 |
| 删除时 Consumer 运行 | 元数据删除 | 文件删除 | 任务仍运行 | 可能重新写入 | 孤儿向量竞态 |

## 5. 性能边界

- 知识库列表、搜索、分类和 RAG 会话列表都没有分页。
- 管理页向量处理中每 5 秒并行请求列表、分类和 5 项统计。
- 非时间列表排序在 Java 内存完成。
- 搜索使用 `%keyword%` 模糊匹配，规模增大后需要 trigram/全文索引。
- 同步查询获取知识库名称按 ID 循环查询。
- 统计由 5 次独立查询组成。
- RAG SSE 没有限流，同一会话也没有串行发送保护。

## 6. 安全与接口语义边界

- 上传和无会话查询有限流，RAG 会话创建与 SSE 没有限流。
- 当前接口没有用户/租户权限隔离，知道 ID 即可查询、更新或删除。
- 文件下载使用原始二进制响应，但业务异常仍走 HTTP 200 JSON，Blob 客户端难以识别。
- 流式错误大多转成普通文本并正常 complete，客户端不能只靠 HTTP/流终止判断成功。
- `updateSessionKnowledgeBases` 只校验非空，不校验所有 ID 存在。

## 7. 推荐改进优先级

### P0：数据正确性

1. 上传/重新向量化应让 Producer 入队失败向上返回明确结果，或采用 Outbox 保证元数据与任务投递。
2. 删除前协调活跃向量任务，防止删除后重新写孤儿向量。
3. 删除流程引入 `DELETING/DELETE_FAILED` 状态和可重试清理任务。
4. SSE 增加 `doFinally`，在 cancel 时把占位标为中断或保存已生成部分。
5. `updateSessionKnowledgeBases` 校验所有 ID，拒绝静默子集更新。
6. 向量化成功后持久化真实 `chunkCount`，恢复 Consumer 幂等判断和管理页统计字段。

### P1：接口一致性与安全

1. RAG 会话和 SSE 增加 GLOBAL/IP/USER 限流及身份授权。
2. 文件下载错误使用真实非 2xx 状态或让客户端校验 Content-Type/业务错误 Blob。
3. 统一错误码，避免 `Result.error(String)` 把参数/不存在问题记成通用 500。
4. 同一会话增加发送锁、幂等键或乐观版本，保护 messageOrder/messageCount。

### P2：性能与可维护性

1. 列表、搜索和会话增加分页。
2. 把 size/access/question 排序下推数据库。
3. 搜索增加合适索引。
4. 统计聚合成单次查询或缓存指标。
5. 批量查询知识库名称，消除循环查库。
6. 问答页搜索继续约束 `vectorStatus=COMPLETED`。

## 8. 面试式总结

这个模块的核心优点是把文件、异步向量化、RAG 检索和持久化聊天拆成了清晰组件，并加入任务
去重、自动重试、检索改写、动态参数、可观测 trace 和流式体验。当前主要短板不在“有没有这些
组件”，而在跨 PostgreSQL、RustFS、Redis 和 pgvector 的状态还没有形成可证明的一致性闭环；
下一阶段最有价值的工作是可靠投递、删除状态机、SSE 取消补偿和会话并发控制。
