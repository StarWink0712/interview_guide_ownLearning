# 代码审计、测试改进路线与故障手册

## 1. 模块基础讲解

现有测试覆盖了几个重要边界：向量分批与 `kb_id` metadata、过滤失败后的本地回退、向量方法的事务注解、消费者
从对象存储解析与实体删除取消、上传 DB 失败时补偿对象、RAG 日志降级写入。它们证明了主干意图，但部分测试把
当前缺陷固化为预期，例如“删除向量失败静默处理”。所谓 `KnowledgeBaseRagIntegrationTest` 实际使用 Mockito，
没有启动 PostgreSQL/pgvector、真实 Embedding 或 Spring Context，严格说仍是组件单元测试。

全面审计后的风险优先级：

| 优先级 | 问题 | 直接影响 |
|---|---|---|
| P0 | chunkCount 永不更新，幂等条件永不成立 | 重复向量化、展示错误 |
| P0 | 先删旧向量再分批写，无版本切换 | 失败后零/部分索引 |
| P0 | 流取消不完成占位消息 | 永久 completed=false |
| P1 | 删除吞异常且无 durable 补偿 | 孤儿对象/向量 |
| P1 | 会话消息序号无并发控制 | 重复顺序、丢计数 |
| P1 | 无 owner/tenant 授权边界 | 越权读取与问答 |
| P1 | Embedding 模型/版本未入 metadata | 混合向量空间 |
| P2 | 列表无分页、N+1、内存排序 | 数据增长后性能退化 |
| P2 | 统计口径冲突、全问题日志 | 数据误导与隐私风险 |

## 2. 基础面试问题

**问题：当前测试分为哪些层次？**

回答：多数是 Mockito 单元/组件测试和反射检查注解；缺少 `@SpringBootTest` 配置装配测试、Testcontainers
PostgreSQL/pgvector 集成测试、Redis Stream 集成测试、SSE 取消测试和端到端上传问答测试。

**问题：为什么测试不能只覆盖正常路径？**

回答：该模块的主要复杂度在分布式失败窗口：上传后 DB 失败、DB 后入队失败、批次中途失败、ACK 前崩溃、客户端
取消、删除与消费并发。正常返回只能证明功能可演示，不能证明数据可恢复。

**问题：Mock VectorStore 的局限是什么？**

回答：它无法验证 filter 语法如何转成 PostgreSQL JSON path、score 语义、HNSW 索引、维度、事务与真实 metadata
序列化。Mock 适合分支逻辑，向量契约必须用真实 pgvector 容器验证。

**问题：如何测试 Prompt？**

回答：模板加载/render 快照测试检查变量与边界文本；恶意文档测试检查不执行注入；固定检索文档配确定性模型 Stub
验证组装；线上模型质量用评测集而不是断言某句自然语言完全相等。

## 3. 进阶面试问题

**问题：最需要补哪几个回归测试？**

回答：向量成功后 chunkCount 写入且重复消息跳过；第 2 批失败时旧版本仍可查询；客户端 cancel 后消息为 CANCELLED；
并发发送不会重复 messageOrder；更新关联遇到缺失 ID 报错；删除失败会进入可重试补偿。

**问题：如何测试 at-least-once 幂等？**

回答：向同一 group 投递相同 taskId 多次，并模拟业务成功后 ACK 前崩溃；断言只产生一个 active vectorVersion、任务
最终 COMPLETED、重复执行计数增加但不重写索引。测试不能只调用一次 `processBusiness`。

**问题：如何做 RAG 质量回归？**

回答：数据集包含问题、相关 chunk、期望关键词/事实、不可回答和冲突文档；评测 Recall@K、MRR、忠实度、引用正确率、
拒答准确率；按改写开关、模型和 chunk 策略对比，并设质量/延迟/成本三重门禁。

**问题：如何验证安全隔离？**

回答：两个租户创建知识库和会话，穷举 list/detail/query/download/update/delete 路由，断言跨租户均不可见；向 metadata
filter 和 Prompt 放恶意内容；确认日志/Trace 脱敏，普通用户不能读取观测明细。

## 4. 技术延伸问题

**问题：如何做故障注入？**

回答：对 RustFS、Embedding、Redis、PostgreSQL 分别注入超时、429、断连和部分成功；在 commit/发送、批次写入、
完成/ACK 间杀进程；用 Toxiproxy/Testcontainers 或 Provider Stub；恢复后检查任务、版本和孤儿资源不变量。

**问题：如何做容量测试？**

回答：准备不同文件大小、chunk 数和并发任务，测上传内存、解析 CPU、Embedding QPS、Stream lag、pgvector 写入与检索
P95/P99、SSE 并发与慢客户端；容量结论必须带 Provider 配额和连接池配置。

**问题：如何建立代码契约测试？**

回答：为 `VectorizationResult`、SSE 事件、错误码、metadata schema、Prompt 变量和状态机转换定义契约；Provider、存储、
向量库 Adapter 都跑同一套 contract test，降低替换实现时的行为漂移。

## 5. 改进方案问题

**问题：给出可执行的四阶段路线。**

回答：

1. 正确性：修 chunkCount、向量版本切换、取消状态、会话并发唯一约束。
2. 可靠性：DB outbox、错误分类退避、删除补偿、墓碑与资源对账。
3. 质量性能：结构化 filter、中文语义分块、混合召回/重排、分页批查、token 预算。
4. 安全治理：租户授权、配额、Prompt/日志脱敏、Embedding/Prompt/config 版本和离线评测门禁。

**问题：代码可读性优先改什么？**

回答：统一 2 空格和导入规范；拆 662 行 QueryService；删除与实现不一致的长注释；typed DTO 替代 Map；使用明确
错误码并保留 BusinessException；为状态转换和 metadata key 建常量；测试名称区分 unit/integration。

**问题：上线前的验收标准是什么？**

回答：重复投递不重复建索引；任一批失败旧版本仍可查；取消无悬挂消息；删除最终无孤儿；跨租户全部拒绝；固定
评测集质量不退化；并发和大文件满足内存、lag、TTFT、P95 SLO；关键告警与 Runbook 可演练。

## 6. 故障处理问题

**问题：RAG 线上故障的统一排查顺序是什么？**

回答：先确认影响范围和最近发布；用 traceId 分段看 Rewrite、Embedding、检索、生成；核对知识库状态、vectorVersion
和行数；检查 Provider/Redis/DB/RustFS；比较固定探针；根据错误分类降级、限流或回滚，恢复后补回归测试。

**问题：数据库、向量和对象状态不一致如何修复？**

回答：先把知识库置为不可查询，保存现场；以元数据 desired state 为基准对账对象和向量版本；源文件存在则重建，
源文件缺失则请求重新上传；孤儿资源进入隔离清理；不要直接手工改 COMPLETED 掩盖数据缺失。

**问题：面试中如何总结优缺点与改进？**

回答：优点是端到端 RAG 链路、异步削峰、短事务、多 Provider、SSE 与 Trace 都已具备；缺点主要在生产可靠性，
尤其向量替换、幂等、取消、跨资源删除、权限和评测。改进应先保证状态与数据正确，再追求召回算法和吞吐优化。

**问题：本模块官方技术依据从哪里核对？**

回答：Spring AI 的 PgVector 文档用于确认 HNSW、维度、metadata filter 与 schema 配置；ETL 文档用于确认
TokenTextSplitter 默认参数；Spring Framework WebFlux 文档用于确认 `Flux<ServerSentEvent>` 的 SSE 返回语义。
