```java
@Table(name = "resumes", indexes = {
    @Index(name = "idx_resume_hash", columnList = "fileHash", unique = true)
})
```

## 含义拆解

| 部分 | 含义 |
|------|------|
| `name = "resumes"` | 映射到数据库的 `resumes` 表 |
| `indexes = {...}` | 在该表上创建索引 |
| `name = "idx_resume_hash"` | 索引名为 `idx_resume_hash` |
| `columnList = "fileHash"` | 对 `file_hash` 列建立索引 |
| `unique = true` | **唯一索引**——该列的值不能重复 |

## 实际效果

Hibernate 启动时根据这个注解自动执行建表语句，等价于：

```sql
CREATE TABLE resumes (
    id BIGINT PRIMARY KEY,
    file_hash VARCHAR(64) NOT NULL UNIQUE,
    -- ... 其他列
);

CREATE UNIQUE INDEX idx_resume_hash ON resumes (file_hash);
```

## 为什么需要这个索引？

对应的字段是 `fileHash`（SHA-256）：

```java
@Column(nullable = false, unique = true, length = 64)
private String fileHash;
```

**业务场景**：用户上传简历时，系统对文件内容做 SHA-256 哈希，然后通过 `fileHash` 查是否已有完全相同的简历入库。

**唯一索引做两件事**：
1. **去重**：同一份文件重复上传，数据库层面直接拒绝（`Duplicate entry`），不会产生两条相同的简历记录
2. **加速查询**：每次上传都要查 `WHERE file_hash = ?`，有索引是 O(log n)，没有是全表扫描 O(n)

## 为什么 `@Column` 已经写了 `unique = true`，还要在 `@Table` 里再建索引？

`@Column(unique = true)` 和 `@Index(unique = true)` 都是建唯一约束，两者会合并且不会重复创建。但显式写在 `@Table(indexes = {...})` 里可以**自定义索引名**（`idx_resume_hash`），否则 Hibernate 自动生成的名字可能是 `UK_xxx_random123`，不利于运维和排查时看懂。

## 一句话总结

> **在 `file_hash` 列上建唯一索引，确保同一份简历（SHA-256 哈希相同）不会重复入库，同时加速去重查询。**

好问题，触及了 JPA 设计的核心理念。

## 核心原因：Hibernate 负责自动建表

你的项目配置里大概率是：

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: update   # 开发环境
```

这意味着**你不需要手动执行任何 SQL**，Hibernate 启动时扫描所有 `@Entity` 注解，自动在数据库里创建表、索引、约束。

```
你写的 Java 代码                    数据库实际效果
─────────────────                   ────────────
@Entity                            创建 resumes 表
@Table(name = "resumes",            
  indexes = {@Index(... unique=true)})  →  创建唯一索引
@Id                                创建主键
@Column(nullable=false)            创建 NOT NULL 约束
```

## 那直接在数据库手动建索引呢？

技术上完全可以，但这个项目选择不手动的原因有两个：

### 1. 索引定义和字段定义放在一起，可读性更好

```java
// 数据库索引在 Java 里声明，一眼就知道这个字段有唯一索引
@Column(nullable = false, unique = true, length = 64)
private String fileHash;
```

对比一下，如果手动建索引，你要在两个地方维护：

```
Java 代码里：private String fileHash;    → "这个字段干嘛用的？"
数据库里：   CREATE UNIQUE INDEX ...      → "哦原来有唯一索引"
```

维护两个地方的映射关系是一种认知负担，而且容易不同步。

### 2. ddl-auto: update 模式下，Hibernate 自己做 diff

项目用 `ddl-auto: update`，意味着 Hibernate 每次启动会比较：

```
Java Entity 定义  vs  数据库实际结构
────────────────    ────────────────
有 @Index          有没有这个索引？没有 → ALTER TABLE ADD INDEX
有 @Column          有没有这个列？没有   → ALTER TABLE ADD COLUMN
```

如果你手动建了索引但没写在注解里，Hibernate 不会管（它认注解不认你手动建的），不会出错。但反过来——你写在注解里了，Hibernate 自动建，保证两者一致。

## 类比理解

| 方式 | 类比 | 优点 | 缺点 |
|------|------|------|------|
| 只在数据库手动建索引 | Excel 里手动加公式 | 灵活 | 和代码脱离，重构时容易忘 |
| 只在 JPA 注解声明 | Excel 模板里预设公式 | 代码即文档，自动同步 | 不直观（看不到实际 SQL） |
| 两者都做 | two sources of truth | - | 容易不一致，出 bug |

这个项目选了第二种——**以 JPA 注解为唯一真相来源**，数据库只是它的投影。

## 一句话总结

> **不是"不能"在数据库手动建，而是"不需要"——JPA 注解就是索引的定义，`ddl-auto: update` 会自动在数据库里创建。代码即文档，字段和索引定义放在一起，维护时不会漏。**
