消费者完整运作流程

消息已经在 Redis Stream 里了，消费者这边的运作是从应用启动时就开始的。

***

## 第 1 步：应用启动，消费者自动初始化

[AbstractStreamConsumer.java#L71-L94](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/async/AbstractStreamConsumer.java#L71-L94)

Spring 容器启动完成后，`AnalyzeStreamConsumer` 这个 Bean 上标注的 `@PostConstruct` 注解会触发父类的 `init()` 方法。这个方法做了三件事。

首先生成一个唯一消费者名称：`analyze-consumer-` 前缀拼接 UUID 的前 8 位，比如 `analyze-consumer-a3f2b01c`。这个名称用于在 Redis Stream 消费者组中唯一标识当前这台机器的这个消费实例。

然后创建一个单线程的守护线程池。核心线程和最大线程都是 1，队列是无界的。线程工厂里把线程设为守护线程，线程名叫 `analyze-consumer`。守护线程的意思是：如果主线程结束了，这个线程会自动跟着死掉，不会阻止 JVM 退出。

最后把 `running` 标志设为 `true`，然后把 `startConsumer` 方法提交给线程池里的那条守护线程去执行。

```java
this.consumerName = consumerPrefix() + UUID.randomUUID().toString().substring(0, 8);
this.executorService = new ThreadPoolExecutor(1, 1, ...);
running.set(true);
executorService.submit(this::startConsumer);
```

***

## 第 2 步：创建消费者组，进入消费循环

[AbstractStreamConsumer.java#L114-L125](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/async/AbstractStreamConsumer.java#L114-L125)

`startConsumer()` 先调用 `redisService.createStreamGroup` 创建 Redis Stream 的消费者组。三个关键参数是：`resume:analyze:stream`（流名）、`analyze-group`（消费者组名）、Stream 本身如果不存在也一并创建（`MKSTREAM`）。

如果消费者组已经存在（比如应用重启时），Redis 会返回 BUSYGROUP 错误，这里 catch 只打一条 warn 日志，然后继续往下走。创建完消费者组之后直接进入 `consumeLoop()` 死循环。

```java
redisService.createStreamGroup(streamKey(), groupName());
consumeLoop();
```

***

## 第 3 步：死循环拉取消息

[AbstractStreamConsumer.java#L131-L153](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/async/AbstractStreamConsumer.java#L131-L153)

`consumeLoop()` 是一个 `while(running.get())` 的死循环。每次循环调用 `redisService.streamConsumeMessages()`，传入 6 个参数：流名 `resume:analyze:stream`、消费者组名 `analyze-group`、消费者名 `analyze-consumer-a3f2b01c`、批次大小 10、阻塞超时 1000 毫秒，以及消息处理器 `this::processMessage`。

```java
redisService.streamConsumeMessages(
    streamKey(),           // resume:analyze:stream
    groupName(),           // analyze-group
    consumerName,          // analyze-consumer-a3f2b01c
    BATCH_SIZE,            // 10
    POLL_INTERVAL_MS,      // 1000
    this::processMessage   // 消息回调
);
```

## 第 4 步：从 Redis 拉取消息

[RedisService.java#L250-L285](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/infrastructure/redis/RedisService.java#L250-L285)

`streamConsumeMessages()` 通过 Redisson 获取 `resume:analyze:stream` 这个 Stream 的 `RStream` 接口，然后调用 `stream.readGroup()` 从消费者组拉取消息。关键参数是 `neverDelivered()`，意思是只拉取从未被任何消费者处理过的新消息。底层对应的 Redis 命令是：

```
XREADGROUP GROUP analyze-group analyze-consumer-a3f2b01c 
    BLOCK 1000 COUNT 10 STREAMS resume:analyze:stream >
```

拉回来的是一个 `Map<StreamMessageId, Map<String, String>>`，一条消息 ID 对应一个键值对的 Map。然后逐条调用 `processor.process(messageId, data)`，也就是回调 `processMessage` 方法。

```java
RStream<String, String> stream = redissonClient.getStream(streamKey, ...);
messages = stream.readGroup(groupName, consumerName,
    StreamReadGroupArgs.neverDelivered().count(count).timeout(...));
for (entry : messages) {
    processor.process(entry.getKey(), entry.getValue());
}
```

## 第 5 步：解析消息，拿到任务 ID 和简历 ID

[AnalyzeStreamConsumer.java#L111-L120](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/resume/listener/AnalyzeStreamConsumer.java#L111-L120)

`processMessage()` 先把消息 Map 传给子类实现的 `parsePayload()` 方法。这个方法从消息 Map 中取两个字段：`taskId` 和 `resumeId`。如果任一字段缺失，说明消息格式有问题，返回 `null`，父类收到 null 后直接 ACK 跳过这条消息。

正常情况下解析出一个 `AnalyzePayload` 对象，里面就两个字段：`taskId`（异步任务表的自增 ID）和 `resumeId`（简历 ID）。

```java
protected AnalyzePayload parsePayload(StreamMessageId messageId, Map<String, String> data) {
    String taskIdStr = data.get("taskId");
    String resumeIdStr = data.get("resumeId");
    return new AnalyzePayload(Long.parseLong(taskIdStr), Long.parseLong(resumeIdStr));
}
```

注意：消息里没有简历文本，只有简历 ID。文本在后面通过 ID 回查数据库获取。

## 第 6 步：标记任务为"处理中"

[AnalyzeStreamConsumer.java#L132-L136](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/resume/listener/AnalyzeStreamConsumer.java#L132-L136)

拿到 `AnalyzePayload` 之后，先调用 `asyncTaskService.markProcessing(payload.taskId())`，把异步任务表里对应 taskId 的状态从 PENDING 改成 PROCESSING。再调用 `updateAnalyzeStatus()` 把简历表里对应 resumeId 的 `analyzeStatus` 字段也改成 PROCESSING。

这样前端轮询时就能看到状态从 PENDING 变成了 PROCESSING，知道分析正在进行。

```java
asyncTaskService.markProcessing(payload.taskId());           // 异步任务表
updateAnalyzeStatus(payload.resumeId(), PROCESSING, null);   // 简历表
```

***

## 第 7 步：执行业务逻辑——AI 分析简历

[AnalyzeStreamConsumer.java#L139-L154](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/resume/listener/AnalyzeStreamConsumer.java#L139-L154)

这里是业务核心。先通过 `resumeId` 从数据库查出完整的 `ResumeEntity`。如果查不到（简历在上传后、分析前被删了），抛出一个 `AsyncTaskCancelledException`，父类会走取消路径。再检查幂等——如果简历已经是 COMPLETED 状态且分析结果已存在，直接返回，不做重复处理。

拿到简历文本的过程是先看数据库里有没有缓存的 `resumeText`，没有的话从 RustFS 重新下载解析。拿到文本后调用 `gradingService.analyzeResume(resumeText)`，这个方法会用 Spring AI 调用 LLM，加载配置好的 Prompt 模板，把简历文本填入模板发送给大模型，等待返回评分和建议。AI 调用可能耗时 10-30 秒。

AI 返回后在保存分析结果前，再查一次数据库确认简历没被删（因为 AI 调用期间可能被用户手动删除）。最后把分析结果持久化到 `resume_analysis` 表。

```java
ResumeEntity resume = resumeRepository.findById(resumeId)
    .orElseThrow(() -> new AsyncTaskCancelledException("简历已被删除"));
String resumeText = resolveResumeText(resume);
ResumeAnalysisResponse analysis = gradingService.analyzeResume(resumeText);
resume = resumeRepository.findById(resumeId)
    .orElseThrow(() -> new AsyncTaskCancelledException("简历在分析期间被删除"));
persistenceService.saveAnalysis(resume, analysis);
```

***

## 第 8 步：标记完成，ACK 确认

[AnalyzeStreamConsumer.java#L157-L160](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/resume/listener/AnalyzeStreamConsumer.java#L157-L160)

业务处理成功后，调用 `asyncTaskService.markCompleted()` 把异步任务状态改为 COMPLETED，同时把简历表的 `analyzeStatus` 改为 COMPLETED。然后父类调用 `ackMessage()` 执行 ACK 确认：

```
XACK resume:analyze:stream analyze-group 1747300000000-0
```

ACK 之后，Redis 把这条消息从 PEL（Pending Entries List）中移除。消息才真正"消费完成"。前端下次轮询就能看到状态已经是 COMPLETED 了。

***

## 异常路径

如果第 7 步抛出的是 `AsyncTaskCancelledException`（简历被删了）：

```
markCancelled(payload, reason) → 异步任务 CANCELLED，ACK，不重试
```

如果抛出的是其他异常（LLM 超时、网络错误等）且重试次数还没到 3：

```
retryMessage(payload, retryCount + 1) → XADD 新消息（retryCount+1）→ ACK 原消息
```

新消息重新进入 `resume:analyze:stream`，等待再次被消费。

如果重试次数已经到 3 了：

```
markFailed(payload, error) → 异步任务 FAILED → ACK，不再重试，等人工介入
```

## 完整链路总结

```
应用启动
    │
    ▼ init()
消费者初始化：生成 consumerName → 创建单线程守护线程池 → 启动消费
    │
    ▼ startConsumer()
创建消费者组 →    
    │
    ▼ consumeLoop()
死循环拉取 → while(running) 
    │
    ▼ streamConsumeMessages()
Redisson → XREADGROUP GROUP analyze-group analyze-consumer-xxx BLOCK 1000 COUNT 10 STREAMS resume:analyze:stream >
    │
    ▼ processMessage()
parsePayload → 消息 Map → AnalyzePayload(taskId, resumeId)
    │
    ▼ markProcessing()
异步任务表 PENDING→PROCESSING, 简历表 analyzeStatus→PROCESSING
    │
    ▼ processBusiness()
resumeRepository.findById(resumeId) → 查数据库拿简历文本
    → gradingService.analyzeResume(resumeText) → 调 AI 评分
    → persistenceService.saveAnalysis() → 保存分析结果
    │
    ▼ markCompleted()
异步任务表 PROCESSING→COMPLETED, 简历表 analyzeStatus→COMPLETED
    │
    ▼ ackMessage()
XACK → 消息从 PEL 移除 ✅
```

和生产者链路一样，消费者也是 4 层调用：`AnalyzeStreamConsumer` → `AbstractStreamConsumer` → `RedisService` → Redisson → Redis，再加上 AI 服务调用和数据库读写，构成完整的异步消费闭环。
