# 数据模型、持久化与历史查询

## 1. 模块基础讲解

简历模块核心数据模型是两张表：

```text
resumes
  id
  fileHash
  originalFilename
  fileSize
  contentType
  storageKey
  storageUrl
  resumeText
  uploadedAt
  lastAccessedAt
  accessCount
  analyzeStatus
  analyzeError

resume_analyses
  id
  resume_id
  overallScore
  contentScore
  structureScore
  skillMatchScore
  expressionScore
  projectScore
  summary
  strengthsJson
  suggestionsJson
  analyzedAt
```

`ResumeEntity` 保存简历资产和当前分析状态，`ResumeAnalysisEntity` 保存每次分析结果。两者是多对一关系：一份简历可以有多条分析记录。

持久化由 `ResumePersistenceService` 封装，历史查询由 `ResumeHistoryService` 编排。

## 2. 基础面试问题

### Q1：为什么简历和分析结果分两张表？

因为简历是用户上传的原始资产，而分析结果可能多次产生。分表后可以保留历史分析记录，支持重新分析后对比评分变化。

如果把分析字段都放在 `resumes` 表，只能保存最新结果，会丢失历史。

### Q2：`ResumeEntity` 的 `analyzeStatus` 有什么用？

它是前端展示当前分析状态的业务字段：

```text
PENDING：等待分析
PROCESSING：分析中
COMPLETED：分析完成
FAILED：分析失败
```

它和统一异步任务表里的状态互补：`resumes.analyzeStatus` 面向简历页面，`async_tasks.status` 面向任务管理和运维。

### Q3：分析建议为什么用 JSON 字段？

`strengths` 和 `suggestions` 是列表结构，建议项还包含 category、priority、issue、recommendation 等字段。当前查询主要是按整份分析展示，不需要频繁按建议字段检索，所以用 JSON 字符串存 TEXT 简单直接。

### Q4：简历列表如何组装？

`ResumeHistoryService.getAllResumes()` 获取所有简历，然后逐条查询最新分析和面试次数，组装 `ResumeListItemDTO`。

返回字段包括文件名、上传时间、访问次数、最新评分、最近分析时间、面试次数、分析状态和错误信息。

## 3. 进阶面试问题

### Q1：当前列表查询有什么性能问题？

`getAllResumes()` 当前先 `findAll()`，再对每份简历查询最新分析和面试次数，存在 N+1 查询风险。数据量小可以接受，生产环境应优化。

优化方案：

1. 分页查询。
2. 使用 JPQL 聚合查询最新分析和面试次数。
3. 在 `resumes` 表冗余 latestScore/latestAnalyzedAt/interviewCount。
4. 用 projection DTO 一次性查询列表页字段。

### Q2：`ResumePersistenceService.entityToDTO()` 有什么注意点？

它会反序列化 `strengthsJson` 和 `suggestionsJson`，并通过 MapStruct 转换分数字段。如果 JSON 损坏，会抛 `BusinessException(ErrorCode.RESUME_ANALYSIS_FAILED)`。

这说明分析结果 JSON 是前端展示依赖的重要字段，保存时要保证格式稳定。

### Q3：MapStruct 在这里解决了什么问题？

MapStruct 用于减少重复手写映射：

1. `ResumeAnalysisResponse -> ResumeAnalysisEntity`
2. `ResumeAnalysisEntity -> ScoreDetail`
3. `ResumeAnalysisEntity -> AnalysisHistoryDTO`

但 JSON 字段和 Resume 关联需要 Service 手动处理，因为它们不是简单字段映射。

### Q4：重新分析时数据怎么更新？

`reanalyze()` 先获取简历文本，如果数据库没有缓存文本，则从对象存储下载并解析。然后调用 `prepareReanalyze()` 更新：

```text
resumeText
analyzeStatus=PENDING
analyzeError=null
```

再发送分析任务。新的分析结果会作为一条新的 `ResumeAnalysisEntity` 保存。

## 4. 技术延伸问题

### Q1：如果要支持分析版本对比，怎么设计？

可以给 `ResumeAnalysisEntity` 增加：

```text
model
providerId
promptVersion
analysisVersion
taskId
latencyMs
createdBy
```

这样可以比较不同 Prompt/模型版本的评分变化。

### Q2：如果要支持搜索简历内容，怎么做？

可以把 `resumeText` 同步到 Elasticsearch/OpenSearch，支持关键词搜索和高亮。也可以对简历做向量化，支持语义搜索候选人简历。

当前模块只是存储文本，不提供全文搜索。

### Q3：JSON 字段什么时候应该拆表？

当需要频繁按建议类别、优先级统计或筛选时，应拆成 `resume_analysis_suggestions` 表。当前只是展示分析详情，用 JSON 足够。

## 5. 改进方案问题

### Q1：当前数据模型优点是什么？

1. 简历资产和分析结果分离。
2. fileHash 唯一索引用于去重。
3. 分析历史可追溯。
4. DTO 不直接暴露 Entity。
5. JSON 字段简化复杂列表结构存储。

### Q2：当前数据模型不足是什么？

1. `resumeText` 直接返回详情，有隐私风险。
2. 缺少用户/租户字段。
3. 缺少分析版本、模型、Prompt 版本。
4. 列表查询有 N+1 风险。
5. `ResumeEntity` 手写 getter/setter，和项目其他 Lombok Entity 风格不完全统一。

### Q3：如何优化历史查询？

1. 列表接口分页。
2. 最新分析结果用子查询或冗余字段。
3. 面试次数用聚合查询。
4. 详情页再加载 `resumeText` 和完整历史。
5. 增加缓存热门简历详情。

## 6. 故障处理问题

### Q1：详情页分析历史为空怎么办？

排查：

1. `resume_analyses` 是否有对应 `resume_id`。
2. 异步任务是否完成。
3. `ResumePersistenceService.saveAnalysis()` 是否抛 JSON 序列化异常。
4. `analyzeStatus` 是否错误地变为 COMPLETED。

### Q2：列表最新分数不对怎么办？

检查 `findFirstByResumeIdOrderByAnalyzedAtDesc()` 返回的是否是最新分析。确认 `analyzedAt` 是否正确写入，是否存在时区或手动修改问题。

### Q3：JSON 反序列化失败怎么办？

可能是旧版本建议结构和当前 DTO 不兼容。处理方式：

1. 增加兼容反序列化。
2. 历史数据迁移。
3. 保存 schema version。
4. 前端对异常字段降级展示。
