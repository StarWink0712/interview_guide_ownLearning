# AI 评分与结构化输出

## 1. 模块基础讲解

简历 AI 评分由 `ResumeGradingService` 实现。它使用 Spring AI 调用 LLM，并通过 `StructuredOutputInvoker` 要求模型返回可解析的 JSON。

流程：

```text
加载 system prompt 模板
加载 user prompt 模板并填充 resumeText
BeanOutputConverter 生成格式约束
systemPrompt + format
  -> LlmProviderRegistry.getDefaultChatClient()
  -> StructuredOutputInvoker.invoke()
  -> ResumeAnalysisResponseDTO
  -> ResumeAnalysisResponse
```

评分维度来自 Prompt 和 DTO：

| 维度 | 分值 |
|---|---|
| projectScore | 项目经验/技术深度，0-40 |
| skillMatchScore | 技能匹配度，0-20 |
| contentScore | 内容完整性，0-15 |
| structureScore | 结构清晰度，0-15 |
| expressionScore | 表达专业性，0-10 |

输出内容包括总分、五维评分、摘要、优势列表、改进建议列表和原始简历文本。

## 2. 基础面试问题

### Q1：简历 AI 分析是怎么实现的？

通过 `ResumeGradingService` 读取 Prompt 模板，把简历文本填入 user prompt，然后调用默认 ChatClient。为了让模型返回稳定结构，使用 `BeanOutputConverter` 提供 JSON 格式说明，并用 `StructuredOutputInvoker` 做重试、JSON 修复和异常包装。

### Q2：为什么要用结构化输出？

前端和数据库需要稳定字段：总分、五维评分、摘要、优势、建议。如果直接让模型输出自然语言，很难持久化和展示。结构化输出可以把 AI 结果变成可查询、可导出、可对比的数据。

### Q3：Prompt 模板放在哪里？

通过 `ResumeAnalysisProperties` 配置：

```text
app.resume.analysis.systemPromptPath
app.resume.analysis.userPromptPath
```

默认是：

```text
classpath:prompts/resume-analysis-system.st
classpath:prompts/resume-analysis-user.st
```

这样 Prompt 不写死在 Java 代码里，方便迭代。

### Q4：AI 返回失败怎么办？

`StructuredOutputInvoker` 内部会按配置重试。如果最终仍失败，`ResumeGradingService` catch 后返回一个错误型 `ResumeAnalysisResponse`，总分为 0，并给出“AI 分析服务暂时不可用”的建议。

注意：当前 `analyzeResume()` 外层 catch 会返回错误响应，而不是继续抛异常，这会让消费者把错误响应也保存为分析结果。这是一个值得改进的点。

## 3. 进阶面试问题

### Q1：`BeanOutputConverter` 的作用是什么？

它基于 Java DTO 类型生成模型输出格式说明，并把模型返回内容转换成 Java 对象。这里中间 DTO 是 `ResumeAnalysisResponseDTO`，包含评分详情和建议列表。转换成功后再映射为业务层 `ResumeAnalysisResponse`。

### Q2：为什么使用中间 DTO，而不是直接让模型返回业务 DTO？

中间 DTO 更贴合模型输出，避免业务对象和模型响应格式强耦合。比如业务对象可能包含 `originalText`，这个字段不需要模型生成，而是在 `convertToResponse()` 时由系统补充。

### Q3：`StructuredOutputInvoker` 带来了哪些工程能力？

1. 结构化 JSON 输出重试。
2. 重试时追加严格 JSON 指令。
3. 常见 JSON 格式修复。
4. 防 Prompt 注入指令追加。
5. Micrometer 指标记录。
6. AI 调用日志记录。

所以它不是简单封装 ChatClient，而是结构化输出可靠性组件。

### Q4：AI 评分结果是否可信？

要谨慎表达。它适合做辅助建议和自动初筛，但不应宣称绝对客观。模型评分受 Prompt、模型版本、简历文本质量影响。生产中应结合人工反馈、评分分布监控和评测集持续校准。

## 4. 技术延伸问题

### Q1：如何做多 Provider 路由？

当前使用 `LlmProviderRegistry.getDefaultChatClient()` 获取默认模型。可以扩展为：

1. 按用户选择 provider。
2. 按任务类型选择模型。
3. 主模型失败后 fallback 到备用模型。
4. 对高成本模型做限流。

### Q2：如何做评分一致性评估？

可以固定一批简历样本，多次运行分析，观察：

1. overallScore 方差。
2. 各维度评分方差。
3. 建议类别一致率。
4. 和人工评分相关性。

如果波动大，需要优化 Prompt 或降低 temperature。

### Q3：如何做岗位匹配评分？

增加 JD 输入，将 user prompt 从单简历分析改成：

```text
resumeText + jobDescription + targetRole
```

输出增加：

1. jdMatchScore。
2. missingSkills。
3. roleSpecificRewriteSuggestions。

## 5. 改进方案问题

### Q1：当前 AI 评分设计优点是什么？

1. Prompt 模板配置化。
2. 使用结构化输出，便于持久化。
3. 输出维度和业务面试目标匹配。
4. 复用统一 LLM Provider 注册器。
5. 复用结构化输出重试和观测能力。

### Q2：当前不足是什么？

1. 外层 catch 返回错误响应，可能把失败结果当作成功分析保存。
2. 没有记录模型、Provider、Prompt 版本到 `ResumeAnalysisEntity`。
3. 没有 token/cost 统计进入分析记录。
4. 没有输入长度截断策略，超长简历可能导致 prompt 过大。
5. 没有评分校准和人工反馈闭环。

### Q3：如何改进失败处理？

建议让 `ResumeGradingService` 对不可恢复失败抛出 `BusinessException`，由 `AnalyzeStreamConsumer` 触发异步任务重试。只有在明确想保存“失败分析报告”时，才保存错误型响应。

这能避免把模型服务故障误记为一次正常 0 分分析。

## 6. 故障处理问题

### Q1：AI 返回 JSON 解析失败怎么办？

1. 查看 `StructuredOutputInvoker` 重试日志。
2. 查看 AI 调用日志里的 `errorMessage`。
3. 检查 Prompt format 是否过于复杂。
4. 降低输出自由度。
5. 添加更严格 JSON 指令或减少字段嵌套。

### Q2：分析结果都是 0 分怎么办？

可能是 AI 调用失败后返回了错误型响应。需要查日志是否有 “简历分析AI调用失败”，再看是否应该改为抛异常触发重试。

### Q3：评分建议质量差怎么办？

1. 优化 system prompt 的评分标准。
2. 增加优秀/糟糕示例。
3. 加入岗位目标。
4. 保存用户反馈。
5. 建立评测集对比不同 Prompt 版本。
