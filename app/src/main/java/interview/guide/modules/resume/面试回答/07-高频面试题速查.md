# 高频面试题速查

## 1. 模块基础讲解

面试快速总括：

> 简历模块是 AI 面试平台的入口。用户上传简历后，系统会做文件校验、MIME 检测、SHA-256 去重、Apache Tika 文本解析、RustFS 对象存储、数据库持久化，然后通过 Redis Stream 异步调用 LLM 进行结构化评分。分析结果会保存为历史记录，支持详情查看、PDF 导出、重新分析，并和后续模拟面试历史关联。

推荐讲解顺序：

```text
业务价值
  -> 上传链路
  -> 文件解析和存储
  -> 异步 AI 分析
  -> 分析结果持久化
  -> 历史/导出/删除
  -> 可靠性与改进
```

## 2. 基础面试问题

### Q1：简历模块怎么从 0 到 1 落地？

从用户上传开始，先校验文件和类型，计算 hash 去重；新文件用 Tika 提取文本，原文件上传到 RustFS，元数据和解析文本保存到数据库；然后发送 Redis Stream 异步任务，由消费者调用 LLM 生成结构化评分和建议，最后保存分析历史并给前端展示。

### Q2：为什么要做文件 hash 去重？

避免同一份简历重复解析、重复上传、重复调用 LLM，节省存储和模型成本。hash 基于文件内容，不依赖文件名。

### Q3：为什么要保存原文件和解析文本？

原文件用于下载、重新解析和留档；解析文本用于 AI 分析和详情展示。这样重新分析时不必每次都下载解析，除非数据库文本为空。

### Q4：为什么分析结果要有历史表？

同一简历可能重新分析多次，或者 Prompt/模型升级后重新评分。历史表能保留每次评分，便于对比。

## 3. 进阶面试问题

### Q1：上传链路如何保证一致性？

对象存储上传成功后，如果数据库保存失败，会补偿删除已上传文件。数据库保存成功后，分析任务通过 afterCommit 发送到 Redis Stream，避免消费者读到未提交数据。

### Q2：异步分析如何保证可靠？

使用 Redis Stream 消费者组和 ACK 机制，失败自动重试，重试耗尽进入死信；消费者处理前检查简历是否存在，已删除则取消任务；分析结果已存在则跳过，保证重复消费幂等。

### Q3：AI 结构化输出如何保证稳定？

通过 `BeanOutputConverter` 生成格式约束，通过 `StructuredOutputInvoker` 做 JSON 输出重试、修复、防注入和指标记录。最终把模型输出转换为中间 DTO，再转为业务响应对象。

### Q4：这个模块有什么真实不足？

1. 列表没有分页。
2. 去重是文件级，不是语义级。
3. 不支持 OCR 扫描版 PDF。
4. LLM 失败当前可能保存 0 分错误响应。
5. 分析结果没有记录模型/Prompt 版本。
6. 删除对象存储失败缺少补偿任务。

## 4. 技术延伸问题

### Q1：如果不用 Tika，你会怎么做？

可以针对不同格式选择专门解析器：PDFBox 解析 PDF，docx4j 或 Apache POI 解析 DOCX，Markdown 用文本解析。Tika 的优点是统一入口和自动检测，适合多格式上传场景。

### Q2：如果要支持大规模批量简历分析，怎么改？

1. 批量上传生成父任务。
2. 每份简历创建子任务。
3. 限制 LLM 并发。
4. 增加进度统计。
5. 失败任务批量重试。
6. 结果导出为 Excel/PDF。

### Q3：如何把简历模块和岗位推荐结合？

在分析时加入岗位 JD，计算 JD 匹配度、缺失技能和针对岗位的项目改写建议。后续可以将简历文本向量化，用于岗位语义匹配。

## 5. 改进方案问题

### Q1：最值得优先优化什么？

1. 修正 LLM 失败保存 0 分结果的问题，改为抛异常触发重试。
2. 列表分页和详情权限控制。
3. 分析结果记录模型、Prompt 版本和耗时。
4. 增加 OCR fallback。
5. 删除失败补偿任务。

### Q2：如何让简历分析更有业务价值？

1. 支持目标岗位/JD。
2. 输出项目经历改写前后对比。
3. 给出面试追问题。
4. 把薄弱点同步到知识库补弱或模拟面试题目生成。
5. 统计用户修改后简历评分变化。

### Q3：如何面试时讲出亮点？

不要只说“我做了文件上传”。可以这样讲：

> 我把简历上传设计成 AI 面试平台的入口链路，上传后自动解析和分析，生成评分和改进建议，并把结果沉淀为后续模拟面试的输入。技术上用了 hash 去重、Tika 解析、对象存储、Redis Stream 异步分析和结构化 LLM 输出，解决了同步调用慢、重复分析成本高、AI 输出不稳定的问题。

## 6. 故障处理问题

### Q1：上传接口报错如何定位？

按顺序看文件大小、MIME 类型、hash 计算、Tika 解析、对象存储上传、数据库保存、Stream 入队。

### Q2：分析失败如何定位？

看 `resumes.analyzeError`、`async_tasks.lastError`、消费者日志和 AI 调用日志。区分是文件文本为空、LLM 超时、JSON 解析失败、Redis 重试失败还是数据库保存失败。

### Q3：删除后异步任务还在执行怎么办？

消费者再次查简历时会发现记录不存在，抛取消异常并 ACK，不会无限重试。若已经进入 LLM 调用，则可能要等调用返回后再取消。

### Q4：PDF 导出没有结果怎么办？

说明没有最新分析记录。需要先等异步分析完成，或调用重新分析。如果 `resume_analyses` 有记录但导出失败，再查 PDF 生成日志。
