# 可靠性、事务边界与改进方案

## 1. 模块基础讲解

简历模块跨越文件、数据库、Redis Stream、LLM 四类资源，所以可靠性重点在事务边界和补偿策略。

当前关键设计：

| 场景 | 当前处理 |
|---|---|
| 文件校验失败 | 直接抛 `BusinessException`，不进入后续链路 |
| 重复文件 | 返回历史结果，不重复分析 |
| 对象存储成功但 DB 保存失败 | 补偿删除对象存储文件 |
| DB 保存成功后发送分析任务 | afterCommit 后投递 Stream |
| Stream 发送失败 | 简历状态和异步任务标记失败 |
| 消费者业务失败 | 自动重试，耗尽后死信 |
| 简历被删除 | 消费者取消任务，ACK 不重试 |
| 删除对象存储失败 | 记录 warn，继续删数据库 |

这些设计体现了不同场景下的一致性取舍：上传链路尽量避免孤儿文件，删除链路优先保证用户业务数据删除。

## 2. 基础面试问题

### Q1：上传链路有哪些事务边界？

对象存储上传不是数据库事务的一部分，所以需要补偿。数据库保存简历是事务方法，成功后再通过 Producer 在事务提交后发送 Stream 消息。

所以完整边界是：

```text
对象存储上传
  -> 数据库事务保存简历
  -> 事务提交后发送 Redis Stream
```

### Q2：为什么不能在事务内调用 LLM？

LLM 调用耗时长且不稳定。如果放在数据库事务内，会长时间占用连接，导致锁等待和连接池压力。当前设计把 LLM 调用放到异步消费者中，并且 `markProcessing()`、`saveAnalysis()`、`markCompleted()` 分别是短事务。

### Q3：为什么 afterCommit 很重要？

如果在数据库提交前就发送消息，消费者可能提前消费并查不到简历。afterCommit 保证业务数据已持久化后才让后台任务可见。

### Q4：哪些地方有降级设计？

1. 删除对象存储失败继续删除数据库。
2. 去重检查异常返回 Optional.empty，继续上传。
3. 分析状态更新失败只记录日志，不打断消费者主逻辑。

这些降级有利有弊，需要结合业务风险评估。

## 3. 进阶面试问题

### Q1：当前一致性还有什么风险？

1. DB 保存成功但 afterCommit 入队失败，任务会失败但简历已保存，需要重试入口。
2. 去重异常时可能重复入库，最终依赖唯一索引。
3. 删除对象存储失败可能留下孤儿文件。
4. 保存分析结果成功但标记完成失败，可能出现结果存在但状态仍处理中。
5. LLM 失败被包装成 0 分错误响应，可能被当作成功结果保存。

### Q2：如何用 Outbox 改造？

上传事务中同时写 `resumes` 和 `outbox_messages`：

```text
DB transaction:
  save resume
  save outbox event RESUME_ANALYZE

Outbox dispatcher:
  scan unsent events
  XADD Redis Stream
  mark sent
```

这样 Redis 短暂不可用时不会丢任务，只是延迟投递。

### Q3：如何处理保存分析结果成功但状态更新失败？

可以增加补偿扫描：

```text
查找 analyzeStatus != COMPLETED
且 resume_analyses 存在最新记录
  -> 修正 analyzeStatus=COMPLETED
```

更严格的做法是把保存分析结果和更新业务状态放在同一个事务里。

### Q4：如何防止重复分析记录？

当前消费者先检查已有结果再分析，但并发下仍可能存在窗口。可以：

1. 对同一 resumeId 活跃任务用 `activeKey` 限制。
2. 在 `resume_analyses` 增加 taskId 并设置唯一约束。
3. 保存前再次检查是否已有当前 task 的结果。

## 4. 技术延伸问题

### Q1：如何做完整补偿机制？

可以引入补偿任务表：

```text
compensation_tasks
  type
  businessId
  payloadJson
  retryCount
  nextRetryAt
  status
```

用于对象存储删除、Stream 投递、状态修复等场景。

### Q2：如何做幂等接口？

上传接口可以支持 Idempotency-Key。客户端重复提交同一个 key 时，后端返回同一结果。当前文件 hash 去重解决内容重复，但不等同于请求级幂等。

### Q3：如何做异步任务 SLA？

可以记录：

1. 从上传到入队耗时。
2. 从入队到开始处理耗时。
3. LLM 分析耗时。
4. 从上传到分析完成总耗时。

超过阈值告警。

## 5. 改进方案问题

### Q1：当前可靠性优点是什么？

1. 上传失败补偿对象存储。
2. afterCommit 发送 Stream。
3. 消费端幂等检查。
4. 删除后消费者可取消任务。
5. 自动重试和死信由通用异步模块处理。

### Q2：当前可靠性不足是什么？

1. 没有 Outbox。
2. 没有对象存储删除失败补偿。
3. 没有状态修复任务。
4. LLM 失败处理容易保存 0 分结果。
5. 没有完整 SLA 指标。

### Q3：优先改哪三点？

1. 修改 `ResumeGradingService` 失败策略，让真正 LLM 失败触发重试。
2. 增加 Outbox 或失败任务自动补偿，增强入队可靠性。
3. 增加分页和状态修复任务，提升运维能力。

## 6. 故障处理问题

### Q1：数据库保存失败但对象存储有文件怎么办？

正常代码会补偿删除。如果补偿也失败，日志会 warn。应根据 fileKey 手动清理，长期用补偿任务自动重试删除。

### Q2：Stream 入队失败怎么办？

简历状态会变为 `FAILED`。可以在修复 Redis 后调用重新分析接口，或通过统一异步任务管理重试。

### Q3：分析结果保存了但状态没变怎么办？

可以手动核对 `resume_analyses` 最新记录，再修正 `resumes.analyzeStatus`。长期加状态修复扫描器。
