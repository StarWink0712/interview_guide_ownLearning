# 上传、解析、存储与去重链路

## 1. 模块基础讲解

简历上传的核心编排在 `ResumeUploadService.uploadAndAnalyze()`。它不是直接保存文件，而是按顺序完成多个步骤：

```text
1. FileValidationService.validateFile()
2. ResumeParseService.detectContentType()
3. validateContentType()
4. ResumePersistenceService.findExistingResume()
5. ResumeParseService.parseResume()
6. FileStorageService.uploadResume()
7. ResumePersistenceService.saveResume()
8. AnalyzeStreamProducer.sendAnalyzeTask()
9. 返回 PENDING 状态
```

关键设计点：

1. 文件大小限制是 10MB。
2. 文件类型通过内容检测服务识别 MIME，再和配置允许列表对比。
3. 去重使用文件内容 SHA-256 hash。
4. 文本解析委托 `DocumentParseService`，底层是 Apache Tika。
5. 文件原件上传到 RustFS/S3，对象 key 使用日期路径 + UUID + 安全文件名。
6. 数据库保存失败时会补偿删除已上传对象存储文件。

## 2. 基础面试问题

### Q1：上传接口完整流程是什么？

可以这样讲：

> 上传接口先校验文件是否为空、大小是否超限，再检测 MIME 类型；然后基于文件 hash 查重，重复则直接返回历史分析；新文件会用 Tika 解析文本，再把原文件上传到 RustFS，把文件元数据和解析文本保存到数据库，最后投递 Redis Stream 异步分析任务。

### Q2：为什么要先去重再解析？

去重基于文件内容 hash，不需要解析全文。先去重可以避免重复文件反复 Tika 解析、对象存储上传和 LLM 分析，节省 IO 和模型调用成本。

当前代码是在 MIME 检测后、文本解析前调用 `findExistingResume()`，这个顺序比较合理。

### Q3：文件去重怎么做？

`FileHashService` 对文件内容计算 SHA-256，`ResumeEntity.fileHash` 有唯一索引。上传时通过 `ResumeRepository.findByFileHash()` 查询是否已存在。重复时会增加访问次数并返回旧记录。

这是内容级去重，不依赖文件名。

### Q4：文件存储路径怎么设计？

`FileStorageService` 生成 key：

```text
resumes/yyyy/MM/dd/{uuid}_{safeName}
```

文件名会做安全处理：汉字转拼音，保留字母、数字、点、下划线和连字符，其他字符替换为下划线。这样适合 S3 兼容存储。

## 3. 进阶面试问题

### Q1：为什么既存对象存储，又把 resumeText 存数据库？

对象存储保存原始文件，便于下载、重新解析、合规留档。数据库保存解析后的文本，便于后续 AI 分析、重新分析、详情展示，避免每次分析都重新下载和解析文件。

这是一种“原始文件 + 解析结果缓存”的设计。

### Q2：对象存储上传成功但数据库保存失败怎么办？

`ResumeUploadService` 在 `persistenceService.saveResume()` 外层 catch 异常，调用 `compensateUploadedResume(fileKey, e)` 删除刚上传的对象存储文件，然后继续抛出原异常。

已有测试覆盖了这个场景：DB 保存失败时会删除文件，并且不会发送分析任务。

### Q3：为什么删除时对象存储删除失败不阻断数据库删除？

删除简历时，如果对象存储删除失败，代码记录 warn，然后继续删除面试会话和数据库记录。这是另一种一致性取舍：用户删除业务数据优先，文件残留可以后续清理。

它的风险是产生孤儿文件，所以生产上应增加定时清理或删除失败补偿表。

### Q4：Tika 解析有哪些优化点？

`DocumentParseService` 使用：

1. `AutoDetectParser` 自动识别格式。
2. `BodyContentHandler` 限制最大文本长度 5MB。
3. `NoOpEmbeddedDocumentExtractor` 禁用嵌入资源解析，避免图片/附件噪声。
4. `PDFParserConfig.setExtractInlineImages(false)` 关闭图片提取。
5. `setSortByPosition(true)` 改善 PDF 多栏文本顺序。
6. `TextCleaningService` 清洗提取文本。

## 4. 技术延伸问题

### Q1：扫描版 PDF 怎么办？

当前 Tika 主要提取文本层，对扫描版 PDF 可能提取不到文本，上传链路会抛出“无法从文件中提取文本内容”。要支持扫描版 PDF，需要接 OCR，例如 Tesseract、PaddleOCR 或云 OCR。

可以把 OCR 作为解析失败后的 fallback，并标记解析来源。

### Q2：如果文件很大怎么优化 hash 计算？

当前 `FileHashService.calculateHash(MultipartFile)` 使用 `file.getBytes()`，10MB 限制下可以接受。但大文件场景更推荐使用流式 hash：`calculateHash(InputStream)`，避免一次性读入内存。

### Q3：如果要做病毒扫描或内容安全怎么办？

可以在对象存储前或后接入：

1. 文件类型白名单。
2. ClamAV 病毒扫描。
3. 文件魔数检测。
4. 内容敏感词/隐私检测。
5. 隔离区审核后再进入正式 bucket。

## 5. 改进方案问题

### Q1：当前上传链路优点是什么？

1. 先校验再处理，避免无效文件进入后续链路。
2. hash 去重节省存储和 AI 成本。
3. Tika 解析细节较完整。
4. 对象存储和数据库保存有补偿逻辑。
5. 上传完成后异步分析，接口响应更快。

### Q2：当前上传链路有什么不足？

1. 列表/详情中可能暴露完整 `resumeText`，需要权限和脱敏。
2. 文件 hash 计算用 `getBytes()`，大文件场景不够优。
3. 去重异常时直接返回 Optional.empty，可能导致重复入库。
4. DB 唯一索引冲突没有显式兜底。
5. 不支持 OCR。
6. 对象存储删除失败缺少补偿任务。

### Q3：如何提升去重可靠性？

1. 捕获唯一键冲突后回查已有简历。
2. hash 计算失败时直接失败，而不是默认当作不重复。
3. 增加文件大小 + hash 组合校验。
4. 支持用户维度去重和全局去重配置。

## 6. 故障处理问题

### Q1：提示“不支持的文件类型”怎么办？

排查：

1. `ContentTypeDetectionService.detectContentType()` 检出的 MIME 是什么。
2. `appConfig.getAllowedTypes()` 配置里是否包含对应类型。
3. 文件扩展名和真实内容是否一致。
4. 浏览器上传的 content-type 是否异常。

### Q2：提示“无法提取文本内容”怎么办？

可能原因：

1. 扫描版 PDF，没有文本层。
2. 文件加密。
3. Tika 不支持该格式。
4. 文件损坏。
5. 文本被图片化。

处理方式：提示用户上传可复制文本的 PDF/DOCX，或接入 OCR。

### Q3：重复简历返回旧结果不符合预期怎么办？

说明两个文件内容 hash 一样。可以让用户使用“重新分析”接口，或未来增加“强制重新分析”参数。在面试中要说明当前去重策略是为了节省 AI 调用成本。
