# 数据模型、持久化与历史导出

## 1. 模块基础讲解

面试模块的数据层由 `interview_sessions`（会话表）和 `interview_answers`（答案表）两张核心表组成，会话与答案是一对多关系，会话删除时级联删除答案。会话表存储面试的完整生命周期数据：`sessionId` 作为业务主键，`skillId`/`difficulty`/`llmProvider` 记录面试配置，`currentQuestionIndex`/`status` 追踪答题进度，`questionsJson` 保存生成时的题目快照（含题干、分类、追问关系），`overallScore`/`overallFeedback` 存储最终报告概要，`strengthsJson`/`improvementsJson`/`referenceAnswersJson` 存储报告结构化内容，`abilityProfileJson`/`adaptiveTraceJson` 存储自适应评估的能力画像和决策追踪链，`evaluateStatus`/`evaluateError` 独立追踪异步评估状态。答案表以 `(session_id, question_index)` 建立唯一约束，实现 upsert 语义——同一道题多次提交只保留最新答案，避免重复记录；字段包括 `question`/`category` 作为题目快照、`userAnswer` 用户答案、`score`/`feedback` 评分反馈、`referenceAnswer`/`keyPointsJson` 参考答案和要点。设计上将题目和报告用 TEXT JSON 存储以保留生成时刻的完整快照，即便后续 Skill 配置变化，历史面试仍展示当时内容；答案单独成表则便于逐题 upsert、更新评分和历史详情展示。历史详情由 `InterviewHistoryService` 将 `questionsJson` 所有题目与答案表按 `questionIndex` 对齐合并，未答题目用空答案和 0 分占位，确保提前交卷也能完整显示题单，最后通过 MapStruct 映射为 `InterviewDetailDTO`。报告保存时同时更新会话表（总分、总体反馈等）和答案表（逐题评分、反馈、参考答案），兼顾列表页快速展示和详情页逐题评估。当前 TEXT JSON 方案的局限在于难以做结构化查询和索引，若需后续数据分析，可迁移为 PostgreSQL JSONB 或拆出独立的维度/分类表。

<br />

面试模块的数据模型主要由会话和答案两张表构成：

- `InterviewSessionEntity`：一场面试的主记录。
- `InterviewAnswerEntity`：每道题的回答、评分、反馈和参考答案。

`InterviewSessionEntity` 的核心字段包括：

- `sessionId`：业务会话 ID。
- `skillId` / `difficulty` / `llmProvider`：面试方向、难度和模型 provider。
- `resume` / `resumeId`：可选关联简历。
- `totalQuestions` / `currentQuestionIndex` / `status`：用户流程状态。
- `questionsJson`：题目快照。
- `overallScore` / `overallFeedback`：最终报告概要。
- `strengthsJson` / `improvementsJson` / `referenceAnswersJson`：报告结构化内容。
- `abilityProfileJson` / `adaptiveTraceJson`：自适应能力画像和决策追踪。
- `evaluateStatus` / `evaluateError`：异步评估状态。
- `answers`：一对多答案记录，级联删除。

`InterviewAnswerEntity` 的核心字段包括：

- `questionIndex`：题号。
- `question` / `category`：题目快照和分类。
- `userAnswer`：用户答案。
- `score` / `feedback`：评分和反馈。
- `referenceAnswer` / `keyPointsJson`：参考答案和关键点。
- `answeredAt`：回答时间。

数据库设计上的一个重点是 `(session_id, question_index)` 唯一约束。它让每个会话的每道题只有一条答案记录，`saveAnswer` 可以实现 upsert：有则更新，没有则创建。

历史详情由 `InterviewHistoryService.getInterviewDetail()` 组装：

1. 根据 sessionId 查会话。
2. 解析题目、优势、改进建议、参考答案、能力画像、追踪链等 JSON 字段。
3. 把所有题目和已答记录按 questionIndex 合并。
4. 对未回答题目构造空答案占位。
5. 通过 MapStruct `InterviewMapper` 转为 `InterviewDetailDTO`。

PDF 导出由 `InterviewHistoryService.exportInterviewPdf()` 委托 `PdfExportService` 完成，Controller 以 `application/pdf` 返回二进制。

面试讲法：

> 数据层的设计重点是“既保留面试当时的快照，又支持历史复盘”。题目和报告用 JSON 保存快照，答案单独成表方便逐题评分和详情展示。历史详情不是简单查答案表，而是把所有题目和已答记录对齐，这样提前交卷时未答题也能完整显示。

## 2. 基础面试问题

**问题：为什么题目列表要存 JSON？**

回答：题目是一次面试生成时的快照，包含题干、分类、追问关系、知识点摘要等结构。用 JSON 保存开发效率高，也能保证之后即使 Skill 配置变化，历史面试仍然展示当时生成的题目。

**问题：为什么答案要单独建表？**

回答：答案是用户逐题产生的动态数据，需要频繁保存、更新评分、展示历史详情。单独建表可以按题号查询、upsert、保存评分和参考答案，也方便一对多级联删除。

**问题：`InterviewDetailDTO`** **为什么要包含未回答题目？**

回答：用户可能提前交卷。如果只展示答案表，未回答题目会消失，前端无法看到完整面试题单。`buildAnswerDetailList` 会把 `questionsJson` 中的所有题目和答案表按题号合并，未回答题目用空答案和 0 分占位。

**问题：MapStruct 在这里做什么？**

回答：`InterviewMapper` 负责 Entity 到 DTO 的机械映射，比如答案详情、历史列表和会话详情。JSON 字段解析仍然在 Service 层做，因为 MapStruct 不适合直接处理这些业务转换。

**问题：删除会话时答案会被删除吗？**

回答：会。`InterviewSessionEntity` 和 `InterviewAnswerEntity` 是一对多关系，配置了 `cascade = CascadeType.ALL` 和 `orphanRemoval = true`，删除会话实体时会级联删除答案。

## 3. 进阶面试问题

**问题：为什么会话表既有** **`resumeId`** **字段又有关联** **`resume`？**

回答：`resumeId` 使用 `insertable=false, updatable=false` 直接映射外键列，用于列表展示时避免触发懒加载。`resume` 是真正的 `@ManyToOne` 关联，用于需要加载简历文本的场景。这样能兼顾查询性能和对象关系表达。

**问题：答案 upsert 如何实现？**

回答：`saveAnswer` 先按 `sessionId + questionIndex` 查答案，存在就更新，不存在就创建新实体。数据库唯一约束 `uk_interview_answer_session_question` 保证并发下不会出现多条同题答案。若并发插入冲突，生产环境还应捕获唯一键异常并重试查询更新。

**问题：当前 JSON 字段设计有什么优缺点？**

回答：优点是灵活、开发快、适合保存 LLM 生成的复杂结构快照。缺点是难以做结构化查询、索引和统计，也缺少强类型约束。比如想统计某个能力维度平均分，就需要解析 JSON；想按 reference keyPoints 搜索也不方便。

**问题：`answeredAt`** **有什么边界？**

回答：它通过 `@PrePersist` 在首次创建答案时设置。如果用户后续修改同一题答案，当前代码不会自动更新 `answeredAt`，因为没有 `@PreUpdate` 或显式更新时间。如果业务希望展示最后修改时间，应新增 `updatedAt` 或在更新答案时刷新时间。

**问题：索引设计需要注意什么？**

回答：会话表按 resume、status、createdAt 和 skillId 建索引，支持历史列表、未完成会话和历史题去重。需要注意 `@Index(columnList = "skillId,createdAt")` 是否和实际数据库列名一致；在 Spring/Hibernate 命名策略下物理列可能是 `skill_id`、`created_at`，这个 DDL 需要实际验证。

**问题：报告保存为什么会同时更新会话和答案？**

回答：会话保存整体报告字段，如总分、总体反馈、优势和改进建议；答案保存逐题评分、反馈、参考答案和关键点。这样列表页可以快速展示总分，详情页可以展示每道题的评估。

## 4. 技术延伸问题

**问题：如果使用 PostgreSQL JSONB，会有什么好处？**

回答：JSONB 可以对 JSON 字段建立索引、做路径查询和部分更新。比如可以查询能力画像里某个 category 的分数，或者统计 referenceAnswers 中包含某个关键词的记录。比 TEXT JSON 更适合后续数据分析。

**问题：如果要做面试数据分析，表结构怎么改？**

回答：可以增加 `interview_question_snapshots` 表保存每题快照，`interview_category_scores` 表保存分类得分，`ability_dimensions` 表保存能力画像维度。保留原 JSON 作为报告快照，同时把分析字段拆出来做查询。

**问题：如果要支持报告版本，怎么设计？**

回答：增加 `interview_reports` 表，一场 session 可以有多个 report version。字段包括 promptVersion、modelProvider、referenceVersion、inputHash、createdAt。当前会话表只保存最新报告概要，历史版本可追溯。

**问题：如果要做软删除，应该怎么改？**

回答：会话和答案增加 `deletedAt` 或 `deleted` 字段，Repository 查询默认过滤未删除记录。删除接口只标记删除，同时取消异步任务、清理 Redis。PDF 和历史详情也要检查删除状态。

**问题：如果要支持大规模历史记录查询，怎么优化？**

回答：列表接口应分页、按用户过滤、只查询投影字段，不加载大 JSON。可以为 `createdAt`、`userId`、`status`、`skillId` 建组合索引。历史详情按需查询，PDF 导出再加载完整数据。

## 5. 改进方案问题

**问题：当前** **`listSessions`** **有什么问题？**

回答：它调用 `findAllByOrderByCreatedAtDesc()` 返回所有会话，没有分页、没有用户隔离，也可能加载大字段。数据量上来后会慢且有安全风险。建议改成分页 DTO 投影，并根据当前登录用户过滤。

**问题：当前 JSON 解析失败如何处理，是否合理？**

回答：`InterviewHistoryService.parseJson` 解析失败会记录错误并返回 null。这能避免详情接口整体失败，但可能导致前端数据缺失而不明显。建议对关键字段如 `questionsJson` 解析失败时抛业务异常，对非关键字段才降级为空列表。

**问题：删除会话需要补充什么？**

回答：除了数据库级联删除答案，还需要删除 Redis 会话缓存和 resumeId 映射，取消或标记未完成的异步任务，并记录操作日志。如果有用户权限，还要校验当前用户是否拥有该会话。

**问题：报告保存异常现在怎么处理，应该怎么改？**

回答：`saveReport` 捕获 `JacksonException` 后只记录日志，没有向上抛出。这可能导致消费者认为处理成功但报告字段不完整。建议让关键序列化失败抛出 `BusinessException`，触发异步任务重试。

**问题：如何提升 Entity 可维护性？**

回答：当前 Entity 手写 getter/setter 较长，可以按项目规范使用 Lombok，或者至少将 JSON 快照字段、状态字段分组注释。更重要的是把复杂字段的读写封装在 Service，不让 Controller 直接接触 Entity。

## 6. 故障处理问题

**问题：历史详情中题目列表为空，但答案存在，怎么办？**

回答：说明 `questionsJson` 解析失败或保存为空。当前代码会回退到仅显示已回答题目。排查时查看会话表 `questionsJson` 内容、Jackson 反序列化异常、生成题目时是否保存成功。

**问题：未回答题没有显示，怎么办？**

回答：检查 `buildAnswerDetailList` 是否拿到了完整 `allQuestions`。如果 `questionsJson` 为 null 或解析失败，就无法构建未答占位。修复重点是保证创建会话时题目 JSON 成功持久化。

**问题：删除简历后关联面试是否会残留？**

回答：`InterviewPersistenceService.deleteSessionsByResumeId` 支持删除简历下所有面试会话，并依靠级联删除答案。要确认简历删除流程是否实际调用了这个方法。还要清理相关 Redis 缓存。

**问题：PDF 导出中文乱码怎么办？**

回答：从 `PdfExportService` 检查字体配置、iText 字体加载、编码和模板。面试模块只负责传 session，真正排查在 PDF 基础设施层。同时确认报告字段不是 null，避免 PDF 模板渲染异常。

**问题：分类得分不准确怎么办？**

回答：最终分类得分来自逐题评估结果按 category 平均。先确认题目的 category 是否生成准确，再看 LLM 是否返回了对应题号的评分。若某批次评估失败，零分兜底会拉低分类平均分。
