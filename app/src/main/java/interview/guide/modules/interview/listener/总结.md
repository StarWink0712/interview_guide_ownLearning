这两个文件是一对**生产者-消费者**，通过 Redis Stream 实现异步评估。

---

## 整体架构

```
面试完成（最后一题 / 提前交卷）
  │
  ▼
EvaluateStreamProducer.sendEvaluateTask()
  │  将 (sessionId, taskId) 写入 Redis Stream
  ▼
Redis Stream（interview:evaluate:stream）
  │
  ▼
EvaluateStreamConsumer（后台轮询消费）
  │  读取消息 → 加载题目和答案 → 调用 LLM 评估 → 保存报告
  ▼
数据库（报告写入 InterviewSessionEntity）
```

---

## EvaluateStreamProducer — 生产者

**职责**：发一条消息到 Redis Stream，告诉"有一份面试需要评估"。

```java
public void sendEvaluateTask(String sessionId) {
    // ① 幂等检查：同一会话只创建一条待处理任务
    AsyncTaskEnqueueResult result = asyncTaskService.createOrReusePendingTask(...);
    if (!result.created()) {
        return;  // 任务已存在，跳过
    }

    // ② 事务提交后才发消息（保证 DB 写完再入队）
    afterCommitExecutor.execute(() -> {
        String messageId = sendTask(payload);       // XADD 到 Redis Stream
        asyncTaskService.markEnqueued(taskId, messageId);  // 记录消息 ID
    });
}
```

**关键设计**：
- **幂等**：`createOrReusePendingTask` 保证同一个会话不会重复入队
- **事务后发**：`TransactionAfterCommitExecutor` 确保数据库事务提交成功后才发消息，避免回滚后消息已被消费

## EvaluateStreamConsumer — 消费者

**职责**：轮询 Redis Stream，拿到消息后执行实际的 LLM 评估。

```java
// 继承模板类，只需重写 processBusiness
protected void processBusiness(EvaluatePayload payload) {
    // ① 从数据库加载会话和题目
    InterviewSessionEntity session = sessionRepository.findBySessionIdWithResume(sessionId);
    
    // ② 会话已被删除？→ 标记取消，丢弃消息
    if (sessionOpt.isEmpty()) {
        throw new AsyncTaskCancelledException(...);
    }

    // ③ 已评估过？→ 跳过（幂等）
    if (session.status == EVALUATED && overallScore != null) {
        return;
    }

    // ④ 反序列化题目 + 填充用户答案
    questions = objectMapper.readValue(session.getQuestionsJson(), ...);
    answers = persistenceService.findAnswersBySessionId(sessionId);
    // ...填充答案到题目

    // ⑤ 调用 LLM 评估
    InterviewReportDTO report = evaluationService.evaluateInterview(chatClient, sessionId, ...);

    // ⑥ 保存报告到数据库
    persistenceService.saveReport(sessionId, report);
}
```

**生命周期回调（继承自模板）**：

| 回调方法 | 触发时机 |
|---------|---------|
| `markProcessing()` | 消费前 → 标记 PROCESSING |
| `processBusiness()` | 核心逻辑 |
| `markCompleted()` | 成功 → 标记 COMPLETED |
| `markFailed()` | 超过最大重试次数 → 标记 DEAD_LETTER |
| `retryMessage()` | 失败但未达上限 → 重新 XADD 入队（最多 3 次） |

## 和 `getReport()` 的关系

面试完成后**两条路可走**：

| 路径 | 触发 | 阻塞？ | 含自适应分析？ |
|------|------|:---:|:---:|
| 异步（Consumer） | 自动触发，后台运行 | 否 | ❌ |
| 同步（`getReport()`） | 用户主动请求报告 | 是 | ✅ |

`sendEvaluateTask` 触发异步评估在后台运行。用户之后访问 `/report` 时，`getReport()` 触发**又一次同步评估 + 自适应附加**。Consumer 有幂等检查（如果已 EVALUATED 则跳过），避免被同步评估的结果覆盖。

---

## 一句话总结

**生产者负责"把这个任务排队"（发消息到 Redis Stream），消费者负责"真正干活"（调 LLM 评估 + 存报告），两者通过 Redis Stream 解耦**，面试完成不等评估结果、立即返回给用户。
