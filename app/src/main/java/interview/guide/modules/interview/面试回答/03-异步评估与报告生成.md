# 异步评估与报告生成

## 1. 模块基础讲解

最终评估是面试完成后的重任务，涉及多题答案、简历上下文、Skill reference、LLM 结构化输出和报告持久化。模块把它拆成生产者、消费者、评估适配器和通用评估引擎几部分。

主要代码：

- `EvaluateStreamProducer`：创建或复用评估任务，并把消息写入 Redis Stream。
- `EvaluateStreamConsumer`：消费消息，加载会话和答案，调用评估服务，保存报告。
- `AnswerEvaluationService`：把 `InterviewQuestionDTO` 转成通用 `QaRecord`，调用 `UnifiedEvaluationService`。
- `UnifiedEvaluationService`：真正执行分批评估、二次汇总和兜底逻辑。
- `InterviewPersistenceService.saveReport()`：把总分、反馈、优势、改进建议、参考答案和逐题评分落库。

生产端流程：

1. `InterviewSessionService` 在最后一题提交或提前交卷时设置 `evaluateStatus=PENDING`。
2. `EvaluateStreamProducer.sendEvaluateTask(sessionId)` 被调用。
3. `AsyncTaskService.createOrReusePendingTask` 确保同一会话不会重复创建活跃任务。
4. 使用 `TransactionAfterCommitExecutor` 在事务提交后写 Redis Stream。
5. 写入成功后标记任务 `ENQUEUED`，失败则标记会话和任务为 `FAILED`。

消费端流程：

1. 消费者从 Redis Stream 消费消息，解析 `taskId` 和 `sessionId`。
2. 标记 async task 为 `PROCESSING`，会话评估状态也改为 `PROCESSING`。
3. 加载会话和关联简历；如果会话已删除，标记任务取消并 ack。
4. 如果会话已经评估且有总分，跳过重复处理。
5. 反序列化题目 JSON，把数据库答案填回对应题目。
6. 根据会话 provider 获取 ChatClient。
7. 调用 `AnswerEvaluationService.evaluateInterview`。
8. 保存报告，标记任务完成和评估状态完成。
9. 失败时按父类模板重试，超过次数进入死信。

通用评估引擎的三阶段：

- 分批评估：按 `app.interview.evaluation.batchSize` 把题目分批调用 LLM。
- 合并批次：逐题评分合并，缺失项零分兜底，优势/改进建议去重。
- 二次汇总：再调用 LLM 生成统一的综合评价，失败则降级到批次聚合结果。

面试讲法：

> 最终评估被设计成可靠异步任务。生产者负责幂等入队和事务后发送，消费者负责处理、重试、死信和幂等跳过。真正的 AI 评估又被拆成适配器和通用评估引擎，这样文字面试和语音面试可以复用同一套评分逻辑。

## 2. 基础面试问题

**问题：为什么最终评估不用同步接口直接做？**

回答：最终评估需要多次 LLM 调用，耗时不可控，还可能触发重试。如果同步做，提交最后一题的接口容易超时。异步化后，用户流程先完成，后台慢慢生成报告，前端根据 `evaluateStatus` 展示进度。

**问题：Redis Stream 消息里有哪些关键字段？**

回答：消息包含 `taskId`、`businessId`、`sessionId` 和 `retryCount`。`taskId` 对应异步任务表，`sessionId` 是业务会话，`retryCount` 用于失败重试控制。

**问题：消费者如何处理会话已删除？**

回答：消费者查不到会话时抛出 `AsyncTaskCancelledException`。父类消费者模板会把任务标记为取消，并 ack 这条消息，避免一直重试一个已经没有业务意义的任务。

**问题：报告里包含哪些内容？**

回答：报告包含总题数、总分、分类得分、逐题评分和反馈、整体评价、优势、改进建议、参考答案和关键点。同步生成报告时还会把自适应能力画像和追踪链附加到 DTO 中。

**问题：评估参考基线来自哪里？**

回答：`AnswerEvaluationService` 会根据会话的 `skillId` 调用 `InterviewSkillService.buildEvaluationReferenceSectionSafe`，加载该 Skill 下配置的 reference 材料，作为评估 Prompt 的辅助上下文。

## 3. 进阶面试问题

**问题：异步评估如何保证幂等？**

回答：生产端通过 async task 的 active 机制避免重复入队；消费端在处理前检查会话是否已经 `EVALUATED` 且存在 `overallScore`。如果消费者在保存报告后、标记任务完成前失败，重试时会发现报告已存在并跳过，随后仍能执行 markCompleted。

**问题：为什么生产者要事务提交后再发送消息？**

回答：如果数据库事务还没提交就把消息发出去，消费者可能读不到刚保存的答案或会话状态，甚至事务回滚后消息仍然存在，造成脏任务。`TransactionAfterCommitExecutor` 保证数据库提交成功后才入队，降低本地事务与消息队列的不一致。

**问题：通用评估为什么要分批？**

回答：题目和回答可能很长，一次性发给 LLM 容易超过上下文窗口，也容易让模型输出过大导致 JSON 解析失败。分批可以控制单次 Prompt 大小。二次汇总再把多个批次合成整体评价，兼顾稳定性和全局视角。

**问题：单批次评估失败会怎样？**

回答：`UnifiedEvaluationService.evaluateBatch` 失败时返回 null。合并阶段会为该批次每道题生成 0 分兜底反馈，系统不会中断整个报告生成。这种策略保证可用性，但会让部分评分偏低，需要在监控中关注批次失败率。

**问题：`getReport` 同步生成和异步消费者生成有什么区别？**

回答：`InterviewSessionService.generateReport()` 是同步接口路径，会直接调用评估服务，并通过 `adaptiveInterviewService.attachAdaptiveAnalysis` 把能力画像附加进返回结果。异步消费者主要负责后台保存报告，不直接返回 DTO；历史详情会从会话 JSON 字段再解析能力画像和追踪链。

**问题：为什么最终评估使用 `getChatClientOrDefault` 而不是 plain client？**

回答：最终评估是对多轮回答的综合判断，可以利用对话式 ChatClient 的上下文能力和 provider 默认配置。结构化输出仍由 `UnifiedEvaluationService` 控制。即时评估和自适应决策则更强调纯 JSON 输出，因此使用 plain client。

## 4. 技术延伸问题

**问题：Redis Stream、RabbitMQ 和 Kafka 在这个场景下怎么选？**

回答：Redis Stream 适合已有 Redis、任务量中等、希望轻量消费组和重试的场景；RabbitMQ 更适合可靠任务队列、死信交换机、延迟重试；Kafka 更适合高吞吐日志流和可回放事件，但单任务状态管理要额外设计。面试评估是业务任务，不是海量日志，Redis Stream 或 RabbitMQ 都合理。

**问题：如果要做任务进度条，怎么实现？**

回答：在 async task 表中增加进度字段，例如 `currentBatch/totalBatch`、`stage`、`lastUpdatedAt`。消费者在分批评估前后更新进度，前端轮询或通过 SSE 获取。当前只有粗粒度状态，无法显示百分比。

**问题：如果评估成本很高，如何优化？**

回答：可以缓存 reference、压缩简历和回答、按题目重要性分层评估、只对已回答题调用 LLM、低价值题用规则评分、对长报告做异步二次汇总。还可以按 provider 做成本路由，高价值场景用强模型，普通练习用低成本模型。

**问题：如何提升评分客观性？**

回答：引入 rubric 明确评分标准；为每个 category 配置关键点；使用 reference baseline 校准；对同一答案可多模型交叉评估或抽样复核；收集人工标注数据做校准。当前实现已经有评分维度和 reference，但还没有人工校准闭环。

**问题：如何支持报告重新生成？**

回答：需要区分首次评估和再评估。可以允许用户修改答案后创建新的 async task，并给报告加 version。旧报告保留为历史，新报告覆盖当前展示。当前幂等逻辑会跳过已评估会话，因此要有显式的 `forceReevaluate` 入口。

## 5. 改进方案问题

**问题：异步消费者保存报告后还有哪些可增强点？**

回答：异步消费者可以像同步 `generateReport` 一样调用 `attachAdaptiveAnalysis`，让保存前的报告对象完整包含自适应数据。虽然历史详情会从会话字段解析能力画像，但统一报告生成路径更易维护。

**问题：失败重试如何做得更精细？**

回答：当前重试主要按统一次数处理。可以按错误类型区分：LLM 限流走延迟重试，JSON 解析失败走 Prompt 修复重试，业务数据缺失直接取消，权限错误直接失败。死信任务可以提供后台人工重放入口。

**问题：如何避免重复 LLM 调用？**

回答：可以给评估输入计算 hash，包括 sessionId、题目、答案、reference 版本和 prompt 版本。如果 hash 一致且已有报告，直接复用。修改答案或 prompt 版本变化时才重新评估。

**问题：如何改造为 outbox 模式？**

回答：在提交最后一题的同一数据库事务里写 `async_task` 或 `outbox_event` 记录，不直接 XADD。后台 outbox dispatcher 读取未发送事件并写 Redis Stream，成功后标记已发送。这样数据库状态和待发送消息在同一个事务里提交，可靠性更高。

**问题：如何让前端感知评估状态？**

回答：增加 `GET /api/interview/sessions/{sessionId}/evaluate-status` 或在会话详情中返回 evaluateStatus。更进一步可以通过 SSE 订阅 sessionId 状态，后台任务状态变化时推送。

## 6. 故障处理问题

**问题：任务进入 `FAILED` 或死信后如何恢复？**

回答：先看 async task 的错误信息和会话 `evaluateError`，确认是临时 LLM 错误、数据错误还是代码错误。临时错误可以提供“重新生成报告”按钮创建新任务；数据错误要修复会话 JSON 或答案记录；代码错误修复后可重放死信任务。

**问题：消费者一直不消费怎么办？**

回答：检查应用实例中消费者是否启动、Redis Stream key 和 group name 是否正确、消费者线程是否报错退出、Redis 连接是否正常。再用 Redis 命令查看 stream 长度、pending entries、consumer group 状态。

**问题：报告总分为 0，可能是什么原因？**

回答：可能用户全部未回答；也可能 LLM 批次评估失败导致零分兜底；还可能答案没有从数据库填回题目。排查时看 `interview_answers` 是否有 userAnswer、消费者日志是否有批次评估失败、`questionsJson` 是否能正确解析。

**问题：评估结果已保存但任务状态还是处理中怎么办？**

回答：可能消费者在 `saveReport` 后、`markCompleted` 前失败。重试时幂等检查会发现会话已评估并跳过业务处理，然后执行完成标记。若没有重试成功，可以手动修复 async task 状态，或提供后台补偿任务。

**问题：参考答案质量差怎么办？**

回答：检查 Skill reference 是否覆盖该 category，Prompt 中 referenceContext 是否被截断，LLM 是否遗漏关键点。可以增强 reference 文件、减少单次上下文噪音、要求模型列出关键点，并对参考答案做二次质量校验。
