## 为什么用虚拟线程而不是普通线程池？

核心原因就一个：**等 LLM 返回是纯等待，不消耗 CPU**。

***

### 先理解普通线程的问题

假设用传统的 `Executors.newFixedThreadPool(2)`：

```
线程1：发 LLM 请求 ─── 等 8 秒（CPU 空闲）─── 收到结果
线程2：发 LLM 请求 ─── 等 6 秒（CPU 空闲）─── 收到结果
```

这 8 秒里线程 1 **什么都不做**，只是等网络响应。但它实实在在地占着一个操作系统线程——占用约 1MB 栈内存，而且受 JVM 能创建的总线程数限制。

如果同时有 100 个用户创建面试，就需要 200 个线程，内存开销约 200MB，还可能触及线程数上限。

***

### 虚拟线程怎么解决的？

Java 21 虚拟线程的关键特性：**阻塞时不占物理线程**。

```
虚拟线程1：发请求 → 阻塞等 LLM → JVM 自动让出物理线程
虚拟线程2：发请求 → 阻塞等 LLM → JVM 自动让出物理线程
```

等的时候虚拟线程"挂起"，物理线程被释放去干别的事。所以无论开 200 个还是 2000 个虚拟线程，底层可能只需要 10 个物理线程就够了。

***

### 对比

| <br />     | 固定线程池              | 虚拟线程                      |
| :--------- | :----------------- | :------------------------ |
| 每个任务占用     | 1 个系统线程 + \~1MB 栈  | 一个极轻量的对象                  |
| 同时 200 个任务 | 需要 200 个线程 ≈ 200MB | 同样 200 个任务，内存几乎忽略         |
| 阻塞等待时      | 浪费线程资源             | 自动释放，不浪费                  |
| 适用场景       | CPU 计算密集型          | **IO 等待密集型** ← 等 LLM 属于这个 |

***

### 这个项目选虚拟线程的理由

调用 LLM 的时候，95% 的时间在**等网络返回**，CPU 几乎空闲。用虚拟线程最合理——既实现了并行出题加速用户体验，又没有创建大量系统线程的内存和上限压力。

<br />

<br />

因为两类题目考察的东西不同，放在一起才能全面评估面试者。

***

### 只出一种题的问题

如果只出**简历题**（根据张三的项目经验出）：

- 只能考察他做过什么，但测不出他的 Java 基础理论、算法、系统设计等通用能力
- 万一简历是虚构的，题目就全废了

如果只出**方向题**（Java 后端通用题）：

- 只能考察理论知识，但和他实际工作经历脱节
- 面试体验感差，候选人觉得"问的问题和我经历无关"

***

### 两路混合出题的设计意图

```
简历题 60%：考察"你做过什么"
  "你在项目中用 HashMap 时遇到过扩容问题吗？怎么解决的？"

方向题 40%：考察"你会什么"
  "请讲一下 HashMap 的底层实现原理"
```

| 维度   | 简历题            | 方向题             |
| ---- | -------------- | --------------- |
| 考察目标 | 项目经验、实际解决问题的能力 | 基础知识、理论深度       |
| 出题依据 | 简历文本           | 技能方向（如 Java 后端） |
| 优势   | 千人千面，防伪        | 覆盖该方向核心知识点      |

***

### 为什么比例是 60% + 40%？

简历题占比更高，因为**基于真实经历的提问更有区分度**——两个人都能背 HashMap 原理，但能从自己项目里讲出坑和经验的才有说服力。留 40% 方向题作为基础能力兜底。

***

### 为什么没简历就纯方向题？

没简历时没有"项目经验"这个出题素材，所以只走一路方向题。两种情况都会兜底——两路都失败时，有 6 道内置通用题保底，保证面试总能开始。
