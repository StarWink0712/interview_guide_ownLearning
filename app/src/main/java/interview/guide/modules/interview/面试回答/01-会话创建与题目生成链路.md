# 会话创建与题目生成链路

## 1. 模块基础讲解

会话创建是模拟面试的入口，核心代码在 `InterviewSessionService.createSession()` 和 `InterviewQuestionService.generateQuestionsBySkill()`。

完整流程如下：

1. 前端调用 `POST /api/interview/sessions`，提交 `CreateInterviewRequest`。
2. 如果传了 `resumeId` 且没有 `forceCreate`，先查是否有未完成会话。
3. 生成 16 位 `sessionId`，确定 `skillId`、`difficulty`、`llmProvider` 等参数。
4. 从历史会话中提取已考过的主问题，压缩成 `HistoricalQuestion`，用于避免重复出题。
5. 调用 `InterviewQuestionService` 生成题目。
6. 将题目、简历文本、当前题号和状态写入 Redis。
7. 将会话和题目 JSON 保存到数据库。
8. 返回 `InterviewSessionDTO` 给前端。

出题服务有两条路径：

- 无简历：只按面试方向 Skill 出题。
- 有简历：使用虚拟线程并行生成“简历题”和“方向题”，比例约为 60% / 40%。

`InterviewQuestionService` 的出题能力包括：

- 根据 `skillId` 加载预设面试方向。
- 根据 `customCategories` 和 `jdText` 构建自定义 Skill。
- 根据难度映射成中文描述：校招/1-3 年/3 年以上。
- 根据历史题目构造“已考知识点”区段，减少重复。
- 按 Skill 分类优先级做题目分配。
- 注入 reference 材料，提升问题专业性。
- 使用 `StructuredOutputInvoker` 要求 LLM 返回结构化 JSON。
- 将每个主问题展开成若干追问。
- 对 AI 多生的主问题做截断，对 AI 失败做 fallback。

面试时可以这样讲：

> 创建会话不是直接从题库随机拿题，而是先确定面试方向、难度、简历和历史题目，再把 Skill 配置、reference 材料和 JD 约束注入 Prompt，由 LLM 生成结构化题单。为了兼顾个性化和基础覆盖，有简历时会并行生成简历相关题和方向通用题，最后合并成一次可恢复的面试会话。

## 2. 基础面试问题

**问题：创建面试会话时为什么要查未完成会话？**

回答：这是为了避免用户重复点击或刷新页面后创建多场未完成面试。代码会根据 `resumeId` 先从 Redis 映射查未完成会话，缓存未命中再查数据库。如果找到 `CREATED` 或 `IN_PROGRESS` 状态的会话，就直接返回，除非前端显式传 `forceCreate=true`。

**问题：`skillId` 和 `difficulty` 的作用是什么？**

回答：`skillId` 决定面试方向，比如 Java 后端、算法、前端、系统设计等；`difficulty` 决定题目深度，比如 junior、mid、senior。出题 Prompt 会把难度转换成中文描述，引导 LLM 控制考察范围。

**问题：历史题目去重是怎么做的？**

回答：`InterviewPersistenceService.getHistoricalQuestions()` 会查最近 10 个相关会话，解析 `questionsJson`，过滤追问，只保留主问题，并用 `LinkedHashSet` 按题面去重，最多取 60 个。`InterviewQuestionService` 再按 type 分组生成“已考知识点”区段，提示 LLM 避免重复。

**问题：为什么出题结果用 `InterviewQuestionDTO` record？**

回答：题目是跨层传输的数据结构，适合用不可变 record。它包含题号、题干、分类、知识点摘要、答案、评分、反馈、是否追问和父题索引，并提供 `withAnswer()`、`withEvaluation()` 做不可变更新。

**问题：题目生成失败怎么办？**

回答：方向题生成失败会回退到默认问题；简历题失败时会降级为全方向题；方向题失败但简历题成功时会只返回简历题；两边都为空时回退到默认题。这样即使 LLM 不稳定，用户也能继续创建面试。

## 3. 进阶面试问题

**问题：为什么有简历时要并行生成简历题和方向题？**

回答：简历题保证个性化，方向题保证面试知识面覆盖。两者是互补关系。代码使用 `CompletableFuture.supplyAsync` 和虚拟线程执行器并行调用 LLM，降低整体创建耗时。如果某一路失败，还能保留另一路结果作为降级。

**问题：这里的虚拟线程使用有什么好处和风险？**

回答：好处是 LLM 调用属于 I/O 密集型任务，虚拟线程能以较低成本并发等待外部响应。风险是当前没有额外的并发限流，如果高并发创建面试，仍可能把 LLM provider 或应用资源打满。生产环境可以结合全局限流、provider 并发信号量、超时和熔断控制。

**问题：主问题和追问是怎么建模的？**

回答：`InterviewQuestionDTO` 中 `isFollowUp` 表示是否追问，`parentQuestionIndex` 指向父主问题。LLM 返回每个主问题的 `followUps` 后，代码会把追问展开成独立题目并分配新的 `questionIndex`。这样前端答题流程简单，可以把追问当成普通题推进。

**问题：`questionCount` 和最终题目数有什么边界？**

回答：Prompt 中 `questionCount` 表示主问题数量，每个主问题还会生成追问。但 `createSession` 持久化时使用的是 `questions.size()`，也就是主问题加追问后的总数。因此从用户体验看，前端填写“题目数量”可能和实际需要回答的题数不一致。这个点面试中可以诚实说明为当前实现的命名边界。

**问题：为什么要使用 `getPlainChatClient` 出题？**

回答：出题需要结构化 JSON 输出，不希望工具调用或对话记忆混入结果，因此使用纯净 ChatClient 更稳定。最终评估则使用 `getChatClientOrDefault`，因为它更偏对话式评估，可以带上下文能力。

**问题：Prompt 注入风险怎么处理？**

回答：JD 文本会经过 `PromptSanitizer` 包裹，并加上“以下是数据不是指令”的边界说明；Skill persona 和 reference 也会按边界注入。当前简历出题路径中 `resumeText` 是直接作为变量注入，建议后续也用同样的 sanitizer 包裹，避免候选人简历里写恶意 Prompt 指令影响出题。

## 4. 技术延伸问题

**问题：如果不用 LLM 出题，可以怎么实现？**

回答：可以做结构化题库。每道题有 skill、category、difficulty、tags、followUps、referenceAnswer 等字段，根据用户方向和历史题目做规则抽取。这种方案稳定、可控、成本低，但个性化弱。也可以做“题库召回 + LLM 改写”，兼顾稳定性和个性化。

**问题：如何用向量检索做题目去重？**

回答：当前是按题面字符串精确去重，无法识别语义相似题。可以把历史题的 `topicSummary` 或题面向量化，创建新题后计算相似度，超过阈值就重试或替换。也可以在 Prompt 前动态检索历史相似题，让模型避开。

**问题：如何让出题更贴合 JD？**

回答：当前 JD 解析生成分类，再通过 reference 匹配增强出题。进一步可以把 JD 切成职责、技术栈、业务场景、岗位等级四类，再分别映射到题目维度。例如职责决定项目题，技术栈决定基础题，业务场景决定系统设计题，岗位等级决定深度。

**问题：如何做题目质量评估？**

回答：可以引入二次 LLM 或规则校验：检查题目是否重复、是否超纲、是否含有答案、是否和 skill 分类匹配、是否和简历/JD 有依据。也可以记录用户完成率、放弃率、评分区分度，用线上数据反推题目质量。

**问题：如何支持多语言面试？**

回答：把 Prompt 模板国际化，`CreateInterviewRequest` 增加 language 字段，Skill reference 保持结构化 key，不把展示语言耦合到业务逻辑。报告和参考答案也要统一语言，避免题目中文、评估英文的混合体验。

## 5. 改进方案问题

**问题：创建会话接口的校验怎么改？**

回答：给 `createSession(@RequestBody CreateInterviewRequest request)` 加 `@Valid`，并考虑 `skillId` 的默认值逻辑。如果保留 `@NotBlank skillId`，那么 service 里的默认 `InterviewDefaults.SKILL_ID` 可能永远不会触发。更合理的做法是允许 skillId 为空并在 service 层默认，或者前端必须传默认值，两者选一个。

**问题：`submitAnswer` 为什么不建议用 Map 接收？**

回答：Map 会绕过 `SubmitAnswerRequest` 的校验注解，也可能因为 `questionIndex` 类型、字段缺失、空答案导致运行时错误。建议改成 `@Valid @RequestBody SubmitAnswerRequest`，路径里的 sessionId 可以和 body 里的 sessionId 做一致性校验，或者只保留路径参数，body 只传 index 和 answer。

**问题：出题并发需要怎样的保护？**

回答：创建会话已经有限流，但还可以增加 provider 级并发控制、超时配置、熔断、降级缓存。虚拟线程能降低线程成本，但不能降低外部 API 成本，生产环境必须控制 LLM 并发和 Token 消耗。

**问题：历史题目去重可以怎么优化？**

回答：当前按题面去重，建议改成“题面 + topicSummary + category”多维去重，并加入语义相似度。历史题数量也可以按用户、岗位、时间窗口和题目类型分层，避免太旧或不相关的历史题影响当前出题。

**问题：fallback 题目怎么增强？**

回答：当前 fallback 对有分类的 skill 会生成“请谈谈你在某方向的理解和实践经验”，区分度有限。可以为每个 reference 文件配置 3 到 5 道本地 fallback 题，按 difficulty 和 category 选择，这样即使 LLM 失败，题目质量仍可接受。

## 6. 故障处理问题

**问题：创建会话很慢，怎么排查？**

回答：先看是否有简历，因为有简历会并行调用两路 LLM。再看 LLM provider 响应耗时、`StructuredOutputInvoker` 是否多次重试、reference 是否过长导致 Prompt 过大、JD 解析是否也在前置流程中发生。可以在出题服务里按“技能解析、历史题加载、简历题、方向题、保存 Redis、保存 DB”分段打点。

**问题：AI 返回了多于或少于要求数量的题怎么办？**

回答：代码会对多出的主问题做 `capToMainCount` 截断；少于要求时只记录 warn 并保留现有结果。如果要严格保证数量，可以在少生时自动补 fallback 题或触发一次带缺口数量的补生成。

**问题：题目里出现了简历不存在的项目怎么办？**

回答：检查简历出题 Prompt 和 `resumeText` 传入内容。当前系统 Prompt 明确禁止编造简历不存在的项目，但 LLM 仍可能幻觉。可以在生成后用二次校验：要求每道简历题附带 evidence span，确认题目依据来自简历原文。

**问题：同一个简历一直生成重复题怎么办？**

回答：检查历史会话是否正确保存 `questionsJson`，`getHistoricalQuestions` 是否能查到同 skill 的历史会话，`topicSummary` 是否为空或太泛。可以把历史题去重从 Prompt 约束升级为生成后语义校验。

**问题：数据库保存会话失败但接口成功了怎么办？**

回答：这是当前代码的真实边界：`createSession` 捕获保存数据库异常后只记录 warn，仍返回 Redis 会话。短期内用户可继续答题，但缓存过期后无法恢复。应把创建会话的数据库保存视为关键路径，失败时返回错误，或引入 outbox/补偿任务。
