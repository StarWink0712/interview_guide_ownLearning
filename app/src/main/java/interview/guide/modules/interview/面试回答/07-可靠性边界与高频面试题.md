# 可靠性边界与高频面试题

## 1. 模块基础讲解

这个模块在面试中最适合讲成“AI 业务工作流 + 工程可靠性治理”。它既有传统后端的状态机、缓存、持久化、异步任务，也有 AI 应用特有的 Prompt、结构化输出、模型降级、reference 注入和评估校准。

可以用这条主线组织回答：

1. 业务闭环：简历/JD/方向出题，逐题答题，报告复盘。
2. 会话状态：Redis 保存进行中状态，数据库保存历史快照。
3. AI 出题：Skill + reference + 历史去重 + 结构化输出。
4. 即时分析：单轮评估、能力画像、策略建议。
5. 最终评估：Redis Stream 异步任务、分批评估、二次汇总。
6. 可靠性：幂等、重试、死信、fallback、缓存恢复。
7. 边界诚实：权限、动态自适应、强一致、报告校准仍有优化空间。

当前代码的亮点：

- 业务流程完整，从创建到答题到报告再到历史导出。
- 使用 Redis 缓存提升进行中会话体验。
- 使用数据库保存题目和答案快照，支持缓存失效恢复。
- 出题和评估都使用结构化输出，降低 LLM 输出不确定性。
- 最终评估异步化，并接入 async task 状态管理。
- 自适应能力失败不阻断主流程。
- Skill 体系把面试方向配置化，便于扩展。

当前代码的真实边界：

- Controller 部分接口没有启用 `@Valid`，提交答案还使用 Map。
- 没有用户权限和租户隔离，列表接口查询全部会话。
- 提交答案没有校验题号必须等于当前题号，存在乱序/并发边界。
- 创建会话和提交答案中部分关键失败被 warn 吞掉，强一致性不足。
- 删除会话没有显式清理 Redis 缓存。
- 自适应决策没有真正改变下一题，只是返回建议。
- 报告评分依赖 LLM，缺少人工标注或离线校准闭环。
- JSON 字段便于快照，但不利于统计分析。

面试时要把亮点和边界同时讲出来。这样比只说“我用了 Redis 和 AI”更可信。

## 2. 基础面试问题

**问题：请你用 2 分钟介绍模拟面试模块。**

回答：这个模块实现了一个 AI 模拟面试闭环。用户可以基于简历、岗位方向或 JD 创建面试，系统通过 Skill 配置和 reference 材料生成结构化题目；答题过程中 Redis 保存会话进度，数据库保存题目和答案；每道题提交后做即时评估并更新能力画像；面试完成后通过 Redis Stream 异步生成最终报告；最后用户可以查看历史详情和导出 PDF。核心设计点是把 AI 能力放进一个可恢复、可追踪、可降级的后端工作流里。

**问题：这个模块里你最想强调的技术点是什么？**

回答：我会强调三个点。第一是业务流程拆分，把出题、答题、评估、复盘分层编排；第二是 AI 稳定性治理，包括结构化输出、Prompt 模板、reference 注入和 fallback；第三是可靠异步评估，用 Redis Stream、异步任务表、幂等检查和失败重试处理耗时 LLM 任务。

**问题：为什么说它不是普通 CRUD？**

回答：普通 CRUD 只是对会话和答案做增删改查，但这个模块有 AI 出题、历史去重、Skill 配置、即时评估、异步报告、能力画像和 PDF 导出。它的核心价值是把用户准备面试的过程变成闭环，而不是管理几张表。

**问题：这个模块和简历模块怎么联动？**

回答：创建面试时可以传 `resumeId` 和 `resumeText`。有 resumeId 时会关联简历实体，查未完成会话和历史题目也会按 resumeId 过滤。最终评估会把简历文本作为上下文，让评分和问题更贴近候选人经历。

**问题：这个模块和异步任务模块怎么联动？**

回答：完成面试后，`EvaluateStreamProducer` 创建或复用 `INTERVIEW_EVALUATE` 类型异步任务，并写入 Redis Stream。消费者执行评估后更新 async task 状态和会话 evaluateStatus。这样评估任务有统一状态、重试和死信管理。

## 3. 进阶面试问题

**问题：如果面试官追问“你怎么保证 AI 输出可用”，怎么回答？**

回答：可以从四层回答。第一，Prompt 模板明确角色、输入数据边界和输出格式；第二，使用 `BeanOutputConverter` 要求 JSON Schema；第三，`StructuredOutputInvoker` 负责调用、重试和输出修复；第四，业务层做标准化和兜底，比如题目数量截断、默认 fallback 题、即时评估得分钳位、最终评估批次失败零分兜底。

**问题：如果追问“Redis 挂了怎么办”，怎么回答？**

回答：当前设计依赖 Redis 保存进行中状态和 Stream 任务。如果 Redis 只是缓存丢失，代码可以从数据库恢复会话；但如果 Redis Stream 不可用，最终评估任务无法入队。生产方案可以增加数据库 outbox 作为待发送任务源，Redis 恢复后补发，或者用更专业的消息队列承担评估任务。

**问题：如果追问“数据库保存失败但 Redis 成功怎么办”，怎么回答？**

回答：这是当前实现的一个一致性边界。创建会话保存 DB 失败时只 warn，提交答案里的 DB 和入队失败也可能被吞掉。面试中应该诚实说明：当前偏向保证用户交互不中断，但生产级方案应以数据库为事实来源，通过事务后更新 Redis 或 outbox 模式保证最终一致。

**问题：如果追问“怎么处理重复点击提交”，怎么回答？**

回答：答案表用 sessionId + questionIndex 唯一约束保证一题一答，保存是 upsert；最终评估任务通过 async task active 机制防重复入队；消费者也有已评估跳过逻辑。但提交答案推进 currentIndex 还缺少严格幂等和版本校验，后续可加 currentIndex 校验和乐观锁。

**问题：如果追问“自适应面试是否已经完整实现”，怎么回答？**

回答：要诚实说当前实现了即时评估、能力画像、策略建议和追踪链，但下一题仍来自预生成题单，决策还没有真正驱动题目队列。因此它是自适应分析能力的第一阶段。下一步是让 `AdaptiveDecisionDTO` 参与动态出题或插入追问。

**问题：如果追问“怎么评价候选人答案是否准确”，怎么回答？**

回答：当前用 LLM 根据评分 rubrics、简历上下文、问答记录和 Skill reference 生成评估，包含逐题反馈和参考答案。为了更客观，系统按批次评估并二次汇总，失败有兜底。但真正生产级准确性还需要人工标注数据、抽样复核、评分一致性评估和模型版本对比。

## 4. 技术延伸问题

**问题：同样功能如果用纯规则系统实现，架构会怎样？**

回答：题目来自结构化题库，评分基于关键词和规则 rubrics，报告由模板生成。优点是可控、成本低、结果稳定；缺点是对自由文本回答理解弱，个性化差。适合基础知识练习，不适合项目经验深挖。

**问题：同样功能如果用 Agent 实现，架构会怎样？**

回答：可以把面试官设计成 Agent，拥有出题、追问、评分、查 reference、生成报告等工具。Agent 更灵活，能动态决策，但可控性和测试难度更高。当前模块选择了“工作流编排 + 局部 LLM 调用”，更适合工程落地和稳定交付。

**问题：如果要接入 WebSocket 实时面试，哪些代码可以复用？**

回答：题目生成、答案保存、即时评估、能力画像、最终评估和历史报告都可以复用。需要新增的是实时通信层、会话心跳、前端事件协议，以及可能的流式输出。语音面试模块会更接近 WebSocket 场景。

**问题：如果要做 A/B 测试模型效果，怎么设计？**

回答：会话记录中保存 promptVersion、modelProvider、modelVersion、referenceVersion 和实验组。报告保存 inputHash 和评分结果。之后可以比较不同模型的完成率、用户满意度、人工复核一致率和成本。

**问题：如果要做权限隔离，最小改动是什么？**

回答：给面试会话加 userId，所有 Repository 查询加 userId 条件，Redis key 增加 userId 前缀，Controller 从认证上下文取当前用户。删除、导出、详情和未完成会话查询都必须校验所属用户。

## 5. 改进方案问题

**问题：面试中被问“你会如何重构这个模块”，怎么答？**

回答：我会分三步。第一步修接口和一致性：强类型 DTO、`@Valid`、currentIndex 校验、删除清理缓存。第二步补可靠异步：outbox、状态查询、死信重放、任务进度。第三步提升 AI 效果：动态自适应出题、RAG reference、评分校准和 Skill 热更新。

**问题：如何改进代码可读性？**

回答：可以减少 Service 中过多中文注释，把显而易见的注释去掉，保留关键业务解释；把 `submitAnswer` 中 Redis、DB、自适应、入队拆成更小方法；把状态转换封装成独立组件；把请求 DTO 强类型化。

**问题：如何提升性能？**

回答：创建会话阶段控制 LLM 并发和 Prompt 大小；列表页分页投影；缓存 reference；评估分批并发可配置；提交答案减少同步 LLM 调用或设置短超时；历史详情避免不必要的大 JSON 解析。

**问题：如何提升可观测性？**

回答：为出题、即时评估、最终评估、Redis Stream 入队/消费、报告保存增加耗时指标和失败计数。日志里统一带 sessionId、taskId、provider、skillId。AI 调用记录 token、重试次数、模型和 promptVersion。

**问题：如何让报告更可信？**

回答：增加评分依据展示，比如每题关键点命中情况；保存 reference 版本；引入人工复核样本；做模型评分一致性统计；对低置信度评估标记提示。这样用户能理解分数为什么这么给。

## 6. 故障处理问题

**问题：线上出现“用户无法创建面试”，优先查什么？**

回答：先看限流是否触发，再看 Skill 是否加载成功、LLM provider 是否可用、Prompt 模板是否存在、出题结构化输出是否失败。若 fallback 也失败，再查数据库和 Redis 写入。

**问题：线上出现“用户提交答案后卡住”，优先查什么？**

回答：看提交接口耗时是否卡在自适应即时评估；看 LLM provider 是否超时；看 Redis 更新和数据库保存是否报错；看前端是否误用暂存接口。必要时先关闭或异步化即时评估，保证主流程。

**问题：线上出现“报告一直生成中”，优先查什么？**

回答：查 `evaluateStatus`、async task 状态、Redis Stream pending、消费者日志、LLM 调用错误和死信记录。如果任务没有入队，看生产者和事务后回调；如果已消费失败，看 `evaluateError`。

**问题：线上出现“报告内容和答案不匹配”，优先查什么？**

回答：检查 questionsJson 和 answers 是否按 questionIndex 对齐，是否发生乱序提交或重复提交。再看消费者填充答案的逻辑是否找到对应 index。也要检查 LLM 是否返回了错误 questionIndex，最终报告构建是否按输入顺序合并。

**问题：线上出现“用户看到别人面试记录”，优先查什么？**

回答：当前模块没有用户维度过滤，是一个明确安全边界。需要立刻加 userId 权限过滤，历史列表、详情、导出、删除、未完成会话查询都必须限制在当前用户范围内，并清理可能被缓存的跨用户映射。

**问题：线上出现“删除后还能恢复会话”，优先查什么？**

回答：检查 Redis 中 `interview:session:{sessionId}` 和 `interview:resume:{resumeId}` 是否仍存在。当前删除只删数据库，不主动删缓存。修复时需要在删除流程中调用缓存删除，并取消相关异步任务。
