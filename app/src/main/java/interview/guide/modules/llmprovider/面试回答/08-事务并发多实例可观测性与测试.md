# 事务、并发、多实例、可观测性与测试

## 1. 模块基础讲解

这个模块同时协调四种一致性边界：

- 数据库事务：Provider 和全局默认设置。
- JVM 并发：Registry 缓存、Properties、读写锁。
- 文件一致性：外部 YAML 和 `.env`。
- 分布式一致性：多个应用实例各自持有本地 ChatClient 缓存。

当前并发手段：

- `LlmProviderConfigService` 使用非公平 `ReentrantReadWriteLock`。
- `LlmProviderRegistry` 使用两个 `ConcurrentHashMap` 和 `computeIfAbsent`。
- 数据库写方法使用 `@Transactional`。
- 缓存失效是本地 `clear()`，没有配置版本和跨实例事件。

现有测试覆盖：

- Registry 创建、缓存、默认回退和 reload。
- 真实本地 HTTP Server 验证 `/v1`、无版本、`/v3` 请求路径。
- ConfigService 基础校验、Legacy CRUD、YAML/.env 文本操作。
- Controller 有少量委托测试。

测试不足：数据库模式 CRUD/事务、Bootstrap 初始化、AES-GCM、Embedding、并发 reload、多实例同步、
SSRF、ASR/TTS reload、鉴权、事务提交后缓存失效都缺少覆盖；还有 disabled Provider 占位测试被禁用。

## 2. 基础面试问题

**问题：数据库事务能否回滚文件写入和缓存清理？**

回答：不能。Spring 数据库事务只管理数据库资源，普通文件和 Map 不参与。必须避免在同一事务里假装
它们原子，使用单一事实来源、afterCommit 事件、Outbox 或补偿机制。

**问题：`ConcurrentHashMap` 是否意味着整个 Registry 没有并发问题？**

回答：它只保证 Map 操作线程安全，不保证“读取配置、构建客户端、配置变更、清缓存”这一组操作的
业务原子性。复合流程仍然需要版本或快照设计。

**问题：为什么多实例下本地缓存会不一致？**

回答：配置写入数据库后，只有处理该 API 的实例执行 `registry.reload()`。其他实例没有通知，会继续
使用旧客户端直到重启或手工 reload。

**问题：单元测试和集成测试如何分工？**

回答：单元测试验证校验、映射和异常；集成测试用 H2/PostgreSQL 验证事务、JPA 和加密字段，用本地
HTTP Server 验证真实 SDK 路径；并发测试验证版本和缓存不倒退。

## 3. 进阶面试问题

**问题：事务提交前 reload 会出现哪些时序？**

回答：写线程保存但未提交 -> 清缓存 -> 读线程查询数据库只能看到旧提交值 -> 创建旧客户端并缓存
-> 写事务提交。最终数据库是新值，缓存却是旧值。这个问题即使单实例也存在。

**问题：如何正确实现提交后事件？**

回答：事务内写数据库和 Outbox，提交后由 `@TransactionalEventListener(AFTER_COMMIT)` 或 Outbox
消费者发布 `ProviderChanged(id, version)`。本实例和其他实例收到后只失效不低于当前版本的缓存。
关键业务推荐 Outbox，避免提交成功但消息发布失败。

**问题：读写锁可能造成什么性能问题？**

回答：网络探测持有读锁会延迟写操作；默认非公平锁在持续读流量下可能让写线程饥饿；所有 Provider
共享一把锁放大竞争。数据库模式的普通读本就有事务隔离，锁收益有限。

**问题：如何观测多 Provider？**

回答：Spring AI 提供 ChatClient、ChatModel、EmbeddingModel、Advisor 和 Tool Calling 的 Micrometer
观测；项目还应补低基数标签 `provider/model/operation/outcome`。Provider ID 数量受控时可做标签，
Prompt 和 API Key 绝不能成为指标标签。

**问题：当前是否已经启用完整 Spring AI Observability？**

回答：Registry 向模型传了 `ObservationRegistry`，但 `app/build.gradle` 未看到 Actuator 依赖。官方文档
说明启用完整观测通常需要 Spring Boot Actuator，因此不能仅凭传入 Registry 就宣称所有指标已落地，
应通过 `/actuator/metrics` 或测试实际验证。

## 4. 技术延伸问题

**问题：配置广播可以使用什么技术？**

回答：Redis Pub/Sub 适合低成本失效通知但不保证离线消费；Redis Stream/Kafka 可回放且更可靠；配置
中心自带 watch；PostgreSQL LISTEN/NOTIFY 简单但也需补版本读取。无论选什么，数据库版本仍是最终准绳。

**问题：如何压测 Registry？**

回答：构造并发读、单 Provider 高频更新、默认切换和慢客户端创建；注入可控 barrier 重现 clear/
compute 竞态；断言发布版本单调、每版本构建次数受控、P99 不出现全局停顿。

**问题：如何验证事务边界？**

回答：使用真实 Spring Context 和数据库，故意让保存后抛异常，断言 DB 回滚且没有发布 reload 事件；
提交成功时断言 afterCommit 只触发一次。Mockito 直接调用 Service 无法证明 AOP 事务生效。

## 5. 改进方案问题

**问题：推荐的生产一致性方案是什么？**

回答：数据库保存版本化配置 -> 同事务写 Outbox -> 后台发布变更 -> 每实例消费并更新
`AtomicReference<RegistrySnapshot>` -> 请求携带/记录配置版本。文件不再参与运行时事实来源。

**问题：测试矩阵如何补齐？**

回答：增加四层：纯单元测试 Validator/Crypto/Resolver；JPA 集成测试 Bootstrap/CRUD/乐观锁；HTTP
契约测试 Chat/Embedding/错误映射；并发测试 reload/version。安全测试覆盖越权、SSRF、日志泄密。

**问题：日志和指标如何设计？**

回答：日志记录 providerId、model、configVersion、operation、latency、status、correlationId；异常作为
最后参数。指标监控请求量、P50/P95/P99、token、429/5xx、缓存命中/重建、配置发布滞后；不记录 Key。

**问题：官方资料如何支撑面试回答？**

回答：Spring 官方说明事务代理未完全初始化时不应依赖 `@PostConstruct` 上的事务；Spring AI 官方
说明 Memory Advisor 每次调用必须提供 conversationId，并提供 ChatClient/ChatModel/EmbeddingModel
观测。可参考：

- [Spring Framework `@Transactional` 官方文档](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)
- [Spring AI ChatClient 官方文档](https://docs.spring.io/spring-ai/reference/api/chatclient.html)
- [Spring AI Advisors 官方文档](https://docs.spring.io/spring-ai/reference/api/advisors.html)
- [Spring AI Observability 官方文档](https://docs.spring.io/spring-ai/reference/observability/index.html)

## 6. 故障处理问题

**问题：只有部分实例使用新配置，怎么定位？**

回答：查询每个实例的 configVersion、缓存创建时间和 Provider 模型标签；确认变更事件是否发出、消费
offset 是否推进。临时可逐实例 reload，根治是可靠广播和启动时版本对账。

**问题：更新流量一高，AI 请求延迟尖峰怎么查？**

回答：看是否每次更新全量 clear 导致三类 ChatClient 与 Embedding 同时冷启动；统计重建次数和耗时；
检查读写锁等待。改为单 key 失效和后台预热。

**问题：单测通过但生产出现旧缓存，为什么？**

回答：现有 reload 测试是串行的，只证明 clear 后下一次会创建新对象，没有覆盖构建与 clear 交错、
事务未提交和多实例。需要可控并发集成测试而不是增加更多串行 mock 断言。

**问题：监控看不到 Spring AI 指标怎么查？**

回答：确认 Actuator/Micrometer 依赖和 endpoint 暴露、ObservationRegistry 是否真实 Bean 而非 NOOP、
调用是否走 ChatClient/Model、采集端是否抓取正确指标名。Prompt 日志默认关闭是安全行为，不是故障。
