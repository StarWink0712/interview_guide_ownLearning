# 高频面试题、改进路线与故障手册

## 1. 模块基础讲解

面试中建议按“背景、方案、难点、结果、反思”五步讲，而不是逐类背代码：

> 平台有多个 AI 业务和多个模型厂商，我设计了统一 Provider 管理模块。配置通过数据库持久化，API
> Key 使用 AES-GCM 加密；运行时 Registry 按 Provider ID 懒创建并缓存 ChatClient/EmbeddingModel，
> 再根据普通、结构化和语音场景提供三类客户端。配置更新后热失效缓存，业务无需重启。难点在配置
> 一致性、厂商路径兼容、向量模型契约和密钥安全。当前实现能支撑动态切换，但多实例同步、事务后
> 发布、管理接口安全和语音配置持久化仍是下一阶段重点。

面试官最关注的不是“会不会调用大模型”，而是：

- 为什么抽象 Provider，边界如何划分。
- 配置和缓存如何保持一致。
- 密钥是否真正安全、如何轮换。
- 多实例下热更新如何传播。
- Embedding 切换是否破坏已有向量。
- 外部服务失败如何重试、熔断和降级。
- 是否识别当前代码缺陷并给出可落地改进。

## 2. 基础面试问题

**问题：请在一分钟内介绍这个模块。**

回答：它是平台的多模型配置和运行时路由中心。管理面支持 Provider CRUD、默认 Chat/Embedding 切换、
连通性测试和 ASR/TTS 配置；运行时从数据库读取启用 Provider，解密 API Key，构建 Spring AI
ChatClient/EmbeddingModel 并缓存。业务可显式选模型，也可使用全局默认值，配置变更后无需重启。

**问题：用了哪些设计模式？**

回答：Registry 统一查找客户端，Factory 创建模型，Strategy 体现 Provider 动态选择，Proxy 桥接动态
Embedding 与静态 Bean，Cache 降低构建成本，DTO 隔离 Entity，单例行保存全局设置。

**问题：模块有哪些优点？**

回答：业务与厂商配置解耦；Provider 可动态切换；API Key 数据库加密且接口脱敏；Chat 和 Embedding
默认值独立；Plain/Voice 客户端按场景隔离；真实 HTTP 测试覆盖版本路径回归。

**问题：模块有哪些明显缺点？**

回答：ConfigService 过大；双存储模式行为不一致；事务提交前清缓存；本地 reload 不支持多实例；
外部语音配置文件未被启动导入；管理接口缺少鉴权；任意 baseUrl 测试有 SSRF 风险；部分异常没有
使用 BusinessException；测试主要覆盖 Legacy 而非生产数据库路径。

## 3. 进阶面试问题

**问题：你如何证明热重载是弱一致而不是强一致？**

回答：在途请求继续持有旧对象；事务提交前可能重建旧缓存；clear 与 compute 存在竞态；其他实例不
知道本机 reload。因此只能保证大多数后续本机请求最终看到新配置，不能保证某个全局时刻原子切换。

**问题：如何定义可接受的一致性目标？**

回答：配置发布成功后，每个实例在限定时间内达到同一 version；单次业务请求固定一个 version；缓存
不允许从高版本回退；发布失败不改变 activeVersion；能够审计和回滚。无需中断在途旧版本请求。

**问题：为什么“连通性测试成功”仍可能是伪安全感？**

回答：它只验证最小 Chat 请求，而且测试与真实 SDK 使用不同路径构造；不验证流式、工具、Embedding
和配额。ASR 更只验证 TCP。健康状态应按能力拆分，并结合真实请求被动指标。

**问题：如何处理 Provider 限流？**

回答：控制面 `@RateLimit` 只限制管理 API，不限制业务对上游的调用。数据面应按 provider/model/tenant
维护并发信号量和 token bucket，识别上游 429 的 Retry-After，配合队列、熔断和降级，避免重试风暴。

**问题：虚拟线程能解决 Provider 并发问题吗？**

回答：虚拟线程降低阻塞线程成本，但不会增加上游配额、数据库连接或 socket 数量。没有并发上限时，
反而更容易快速压垮 Provider。必须结合 bulkhead、超时、限流和背压。

**问题：模型路由如何考虑成本和质量？**

回答：任务先声明能力和质量等级，再在候选 deployment 中按健康度、P95、单价、上下文长度和租户
预算打分。高价值评估可选强模型，文本改写用便宜模型；记录路由原因和实际成本用于持续优化。

## 4. 技术延伸问题

**问题：如果改成 AI Gateway，模块还需要吗？**

回答：仍需要控制面，只是运行时工厂变为调用 Gateway。Provider 密钥、重试和路由可下沉 Gateway，
业务侧保留任务 profile、默认策略、审计和能力声明。Gateway 减少 SDK 差异，但不能替代业务配置治理。

**问题：如何实现租户级 Provider？**

回答：配置主键增加 tenantId，密钥按租户隔离，默认设置改为 `(tenantId, capability)`；缓存 key 带
tenant 和 version；鉴权校验调用者只能访问本租户；指标避免 tenantId 高基数，可按套餐聚合。

**问题：如何支持灰度发布新模型？**

回答：新 deployment 先 shadow 请求比较质量和延迟，再按用户哈希灰度 1%、10%、50%；设置自动
回滚阈值；会话类业务固定模型版本，不能一场面试中途随机切换。

**问题：怎样实现 Provider 容灾但避免重复副作用？**

回答：纯生成调用通常可重试，但工具调用可能产生写副作用。先把工具执行与模型重试分层，使用
idempotency key 和工具调用状态机；只在模型尚未确认执行副作用时切 Provider。

## 5. 改进方案问题

**问题：请给出分阶段改进路线。**

回答：

1. 安全止血：管理 API 加 RBAC、CSRF/审计，baseUrl 做 SSRF 防护，生产强制加密主密钥。
2. 正确性修复：语音外部配置真正导入或迁库；修 Legacy 默认 Embedding NPE；统一 BusinessException；
   Bootstrap 改为代理可生效的事务入口。
3. 一致性升级：afterCommit + Outbox + configVersion，多实例可靠广播，版本化缓存快照。
4. 架构拆分：Command/Query/Health/Secret/Voice Config 分离，移除双模式分支漂移。
5. 模型治理：能力目录、熔断、限流、成本路由、灰度、Embedding profile 与重建流程。

**问题：哪些改进不能只靠重构代码完成？**

回答：管理员身份体系、Secret Manager/KMS、消息基础设施、数据库迁移、监控告警和 Provider SLA 都
需要平台与运维配合。面试时应明确工程改进包含代码、数据和运行体系。

**问题：如何衡量改造成功？**

回答：配置发布 P99 生效时间、版本不一致实例数、旧缓存命中数、Provider 成功率/P95、429 比例、
密钥泄漏事件为零、Embedding 混合版本数为零、配置回滚时间和测试覆盖率。

**问题：当前最值得保留的设计是什么？**

回答：业务统一依赖 Registry、Chat/Embedding 默认值分离、三类 ChatClient profile、AES-GCM 密文存储、
动态 Embedding 代理和真实 HTTP 路径回归测试。这些方向正确，改造重点是补齐生产级边界。

## 6. 故障处理问题

**问题：出现 401、429、5xx 时分别如何处理？**

回答：401 检查密钥、权限和加密主密钥，不盲目重试；429 尊重 Retry-After、限流和切换有配额的备选；
5xx 对幂等调用做有限指数退避并触发熔断，持续失败降级或排队。

**问题：测试连接能通，Embedding 不可用，怎么查？**

回答：Chat 测试不覆盖 Embedding。检查能力标志、模型名、维度、最终 `/embeddings` 路径、账号权限和
VectorStore schema；用独立 Embedding probe 验证。

**问题：默认 Provider 更新后旧会话和新会话模型不同是否是 Bug？**

回答：不一定。会话应固定创建时 Provider，避免上下文行为中途变化；没有显式 Provider 的无状态新
请求才跟随最新默认值。应在 Session 中记录实际 provider/model/version，便于解释和审计。

**问题：管理接口被未授权调用后应如何处置？**

回答：立即下线或网关封禁接口，轮换所有可能泄漏的 API Key 和加密主密钥，审计配置变更与上游调用，
恢复可信版本，补管理员鉴权、最小权限、审计和 SSRF 防护，再进行安全复盘。

**问题：如何用一句话收尾？**

回答：这个模块已经完成了“多模型可配置、可切换、可加密、可复用”的核心闭环；要达到生产级，
关键不是再加几个 Provider，而是把配置发布、安全边界、向量版本和跨实例一致性做成可证明的系统能力。
