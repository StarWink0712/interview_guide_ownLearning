## ReentrantReadWriteLock — 读写锁

`LlmProviderConfigService` 是一个有状态的单例服务，同时处理读写请求——多个用户可能同时在设置页面查看 Provider 配置（读），而管理员可能在修改 Provider 参数（写）。为了在保证线程安全的同时不牺牲并发性能，我使用了 `ReentrantReadWriteLock`。它的核心规则是：读锁之间不互斥，允许多个读操作并发执行，比如 10 个用户同时打开设置页不需要排队；但当写操作发生时，写锁会阻塞所有读写，确保配置修改是原子性的。比如 `listProviders` 方法加读锁遍历 Provider 列表，`createProvider` 方法加写锁写入新配置并调用 `registry.reload()` 热重载，两者互斥——保证了不会出现"一边遍历列表一边删除元素导致数组越界"的并发问题。相比 `synchronized`，读写锁的优势在于读多写少的场景下——设置页面以查看为主、修改为低频操作——大部分请求只需加读锁就能无阻塞并发，只有少数写请求才短暂阻塞全局，整体吞吐量远高于互斥锁。

### 为什么需要它？

这个 Service 里有两类操作**可能同时发生**：

| 操作    | 场景                              | 谁在做      |
| ----- | ------------------------------- | -------- |
| **读** | 列出 Provider 列表、获取配置             | 用户打开设置页面 |
| **写** | 创建/更新/删除 Provider、修改 ASR/TTS 配置 | 用户提交表单   |

如果没有锁，可能出现这种情况：

```
线程A（读）：正在遍历 Provider 列表        线程B（写）：同时删除了一个 Provider
        ↓                                              ↓
      读到第3个                                   顺便改了 Map 结构
        ↓
      跳到第4个 → 报错！因为第4个已经被删了，list 变短了
```

### 怎么起作用？

读写锁的核心规则：**多个人可以同时读，但写的时候只能一个人，且读和写互斥**。

```
读锁 + 读锁 → ✅ 可以同时（多个用户同时打开设置页没事）
读锁 + 写锁 → ❌ 互斥（有人在看配置时不能改）
写锁 + 写锁 → ❌ 互斥（只能一个人改）
写锁 + 读锁 → ❌ 互斥（有人改配置时不能看）


              读    写
            ┌─────┬─────┐
         读 │ ✅  │ ❌  │
            ├─────┼─────┤
         写 │ ❌  │ ❌  │
            └─────┴─────┘
```

### 在这个代码中怎么用的？

**读操作加读锁**（以 `listProviders` 为例）：

```java
rwLock.readLock().lock();        // 开始读，阻止写操作进来
try {
    // 读配置、遍历 Provider...
} finally {
    rwLock.readLock().unlock();   // 读完释放
}
```

**写操作加写锁**（以 `createProvider` 为例）：

```java
rwLock.writeLock().lock();       // 开始写，阻止所有读和写
try {
    // 修改配置、写 YAML 文件...
} finally {
    rwLock.writeLock().unlock();  // 写完释放
}
```

### 实际效果

正常情况（没人写）→ 100 个人同时看设置页，都加读锁，互不影响，**不需要排队**。

有人要改配置 → 等所有读锁释放 → 加写锁 → 改完释放 → 其他人继续读。**写操作短暂阻塞所有读，写完之后立即恢复正常**。

### 为什么不用 synchronized？

`synchronized` 是互斥锁——**任何时候只允许一个人**。如果 3 个人同时打开设置页，用 `synchronized` 就要排队等，但读操作其实不需要互斥。读写锁让"只读不写"的请求可以并发，只在真正修改时才加锁，性能好得多。
