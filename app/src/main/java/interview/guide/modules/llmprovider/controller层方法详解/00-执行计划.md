# LLM Provider Controller 完整调用流程总览

本文不是接口清单，而是整个 `LlmProviderController` 模块的阅读入口。重点回答五个问题：

1. 前端哪个页面、哪个事件发起请求？
2. 请求经过哪些公共组件后进入 Controller？
3. Controller 委托 Service 后，最终读写数据库、YAML、`.env` 还是运行时对象？
4. 配置修改后怎样影响 `ChatClient`、`EmbeddingModel`、ASR 和 TTS？
5. 成功、业务失败和“连接测试失败”分别怎样回到页面？

---

## 1. 本组代码的角色

Controller 基路径：

```text
/api/llm-provider
```

核心参与者如下：

| 层次 | 文件/类 | 职责 |
|---|---|---|
| 页面 | `frontend/src/pages/SettingsPage.tsx` | 展示 Provider、默认模型和语音配置，处理按钮事件 |
| 前端 API | `frontend/src/api/llmProvider.ts` | 把页面动作映射成 15 个 HTTP 接口 |
| HTTP 公共层 | `frontend/src/api/request.ts` | Axios 请求；解包后端 `Result<T>`；业务码非 200 时抛 `Error` |
| Controller | `LlmProviderController` | 路由、限流、请求体接收、调用 Service、包装 `Result<T>` |
| Service | `LlmProviderConfigService` | 校验、加解密、持久化、文件编辑、锁、热重载编排 |
| Repository | `LlmProviderRepository` | 读写 `llm_provider_config` |
| Repository | `LlmGlobalSettingRepository` | 读写单例行 `llm_global_setting(id=1)` |
| 加密 | `ApiKeyEncryptionService` | AES-256-GCM 加密/解密 Provider API Key |
| LLM 运行时 | `LlmProviderRegistry` | 缓存并按需创建 ChatClient 与 EmbeddingModel |
| 语音运行时 | `QwenAsrService` / `QwenTtsService` | 使用当前语音配置建立后续 ASR/TTS 连接 |
| 启动初始化 | `LlmProviderBootstrapService` | 数据库为空时把 YAML 种子配置加密后导入数据库 |

Controller 本身没有业务判断。完整逻辑都在 `LlmProviderConfigService` 以及它调用的组件中。

## 2. 15 个接口与实际前端使用情况

`@RateLimit` 没有显式设置时间单位，因此这里的 `30`、`10`、`5` 都是“每 1 秒”的全局滑动窗口限额。

| Controller 方法 | HTTP 接口 | 限流 | 当前 SettingsPage 是否调用 |
|---|---|---:|---|
| `listProviders` | `GET /list` | GLOBAL 30/s | 是，页面初始化和写操作后刷新 |
| `getProvider` | `GET /{id}` | GLOBAL 30/s | 否；API 封装存在，但编辑直接使用列表数据 |
| `createProvider` | `POST /` | GLOBAL 5/s | 是 |
| `updateProvider` | `PUT /{id}` | GLOBAL 5/s | 是 |
| `deleteProvider` | `DELETE /{id}` | GLOBAL 5/s | 是 |
| `testProvider` | `POST /{id}/test` | GLOBAL 10/s | 是 |
| `reloadProviders` | `POST /reload` | GLOBAL 5/s | 否；API 封装存在，页面无按钮调用 |
| `getDefaultProvider` | `GET /default-provider` | GLOBAL 30/s | 是 |
| `updateDefaultProvider` | `PUT /default-provider` | GLOBAL 5/s | 是 |
| `updateDefaultEmbeddingProvider` | `PUT /default-embedding-provider` | GLOBAL 5/s | 是 |
| `getAsrConfig` | `GET /voice/asr` | GLOBAL 30/s | 是 |
| `updateAsrConfig` | `PUT /voice/asr` | GLOBAL 5/s | 是 |
| `getTtsConfig` | `GET /voice/tts` | GLOBAL 30/s | 是 |
| `updateTtsConfig` | `PUT /voice/tts` | GLOBAL 5/s | 是 |
| `testAsrConfig` | `POST /voice/asr/test` | GLOBAL 10/s | 是 |

当前没有 TTS 测试接口。

## 3. 页面首次打开时的完整闭环

`SettingsPage` 挂载后，`useEffect()` 调用 `loadData()`。它不是依次请求，而是用 `Promise.all()` 同时发出四个请求：

```text
SettingsPage.useEffect()
  → loadData()
    → Promise.all(
        llmProviderApi.list(),
        llmProviderApi.getDefaultProvider(),
        llmProviderApi.getAsrConfig(),
        llmProviderApi.getTtsConfig()
      )
```

其中 Provider 列表的后端链路为：

```text
浏览器 GET /api/llm-provider/list
  → Axios instance
  → Spring MVC 路由到 LlmProviderController.listProviders()
  → RateLimitAspect.around()
      → Redis Lua 滑动窗口检查 GLOBAL 30/s
  → LlmProviderConfigService.listProviders()
      → 获取 ReentrantReadWriteLock 读锁
      → 判断数据源
          ├─ 数据库模式：查询全局设置 + Provider 表 + 解密后脱敏
          └─ Legacy 模式：读取 LlmProviderProperties 内存对象 + 脱敏
      → 构造 List<ProviderDTO>
      → 释放读锁
  → Controller 用 Result.success(data) 包装
  → HTTP 200 + { code: 200, message: "success", data: [...] }
  → Axios 响应拦截器检查 code
  → 解包并把 data 返回给 loadData()
  → setProviders(...)
  → React 重新渲染 Provider 卡片
```

另外三个请求分别填充默认 Provider、ASR 和 TTS 状态。只要四个 Promise 中任意一个 reject，整个 `Promise.all()` 就进入 `catch`，页面显示“加载数据失败”；已经成功的其他请求不会在这次调用中写入 React state。

## 4. 数据库模式与 Legacy 模式

`LlmProviderConfigService.isDatabaseBacked()` 的判断不是读取配置开关，而是检查三个依赖是否都存在：

```java
providerRepository != null
    && globalSettingRepository != null
    && encryptionService != null
```

正常 Spring 生产构造器会注入这三个 Bean，所以实际应用通常走数据库模式。另一个五参数构造器主要让测试或兼容场景进入 Legacy 模式。

### 4.1 数据库模式

```text
application.yml 中的 app.ai.providers（启动种子）
  → LlmProviderBootstrapService.seedProvidersIfNecessary()
  → ApiKeyEncryptionService.encrypt()
  → llm_provider_config

默认聊天/向量 Provider
  → llm_global_setting 固定 id=1
```

数据库中不保存明文 Key，而是保存：

```text
api_key_nonce + api_key_ciphertext
```

创建、更新、查询和实际调用 LLM 时再由 `ApiKeyEncryptionService` 加解密。

### 4.2 Legacy 模式

```text
LlmProviderProperties 内存对象
  ↕
运行时 YAML 文件 app.ai.providers.*
  +
.env 中 PROVIDER_{ID}_API_KEY
```

Legacy 写操作通过文本编辑器修改 YAML，目的是尽量保留注释和格式；API Key 写入 `.env`。但 Provider 查询实际读取的是已经绑定到 Spring Bean 的 `LlmProviderProperties`，不是每次都重新解析磁盘文件。

当前 `spring.config.import` 只导入 classpath 的 `voice-interview-opening.yml`，没有导入 `config-yaml-path` 和 `config-env-path` 指向的外部文件。因此这些文件目前只是写出副本：当前进程依靠内存对象热更新，应用重启后不会自动从这两个文件恢复修改，除非部署层另外把它们加入 Spring 配置源。

### 4.3 必须分清“启动种子”和“运行时数据源”

数据库模式下，`application.yml` 的 Provider 配置主要是首次启动时的种子。一旦 `llm_provider_config` 已有数据，Bootstrap 不会每次启动都覆盖数据库。之后管理接口读写的是数据库。

## 5. 写操作的通用闭环

以数据库模式更新 Provider 为例：

```text
用户点击“保存”
  → SettingsPage.handleUpdate()
  → llmProviderApi.update(id, request)
  → PUT /api/llm-provider/{id}
  → RateLimitAspect 检查 GLOBAL 5/s
  → Controller.updateProvider()
  → LlmProviderConfigService.updateProvider()
      → @Transactional 开启数据库事务
      → 获取 JVM 内写锁
      → Repository 查询原 Entity
      → 合并非 null 字段
      → 校验最终 Embedding 配置
      → 新 API Key 存在时 AES-GCM 重新加密
      → Repository.save(entity)
      → LlmProviderRegistry.reload()
          → 清空 ChatClient 缓存
          → 清空 EmbeddingModel 缓存
      → 释放写锁
      → 方法返回后事务提交
  → Result.success()
  → Axios 解包
  → 页面 toast“Provider 更新成功”
  → await loadData()
  → 重新查询四类配置并刷新页面
```

`registry.reload()` 只清空缓存。下一次业务代码调用 `getChatClient*()` 或 `getEmbeddingModel*()` 时，Registry 才重新查询数据源并创建对象。这是“失效后懒加载”，不是“立即重建所有客户端”。

## 6. Provider 配置怎样影响真正的业务调用

修改 Provider 不是只影响设置页。业务模块通过 Registry 获取模型：

```text
面试出题 / 回答评估 / 简历分析 / JD 解析 / 语音追问
  → LlmProviderRegistry.getChatClientOrDefault(providerId)
      ├─ 显式传 providerId：使用指定 Provider
      └─ null/空字符串：读取默认聊天 Provider
  → clientCache.computeIfAbsent(...)
  → 从数据库或 LlmProviderProperties 加载配置
  → 解密 API Key
  → 创建 OpenAiChatModel + ChatClient
  → 调用兼容 OpenAI 协议的远端模型

知识库向量化 / RAG
  → getDefaultEmbeddingModel() 或 getEmbeddingModel(providerId)
  → embeddingModelCache.computeIfAbsent(...)
  → 创建 OpenAiEmbeddingModel
```

Registry 中至少存在以下缓存形态：

```text
providerId          → 默认 ChatClient
providerId:plain    → 无工具的结构化输出 ChatClient
providerId:voice    → 语音场景 ChatClient
providerId          → EmbeddingModel（独立 Map）
```

所以一次 `reload()` 会让后续请求重新创建这些对象，但正在执行中的请求仍持有旧对象，不会被中途替换。

## 7. ASR/TTS 配置是另一条持久化链

Provider 配置主要进入数据库；ASR/TTS 更新则直接处理运行时属性和文件：

```text
SettingsPage 语音配置弹窗
  → PUT /voice/asr 或 /voice/tts
  → LlmProviderConfigService
      → 修改 VoiceInterviewProperties 中的可变配置对象
      → API Key 非 null 时写 AI_BAILIAN_API_KEY 到 .env
      → 文本方式重写 YAML 的 asr/tts 配置块
      → QwenAsrService.reload(...) 或 QwenTtsService.reload(...)
  → 后续新建语音连接使用新配置
```

ASR 已经存在的 WebSocket 会话不会重建；TTS 每次合成都建立临时连接，因此后续合成自然使用重新加载后的字段。

## 8. 统一响应与三类“失败”

### 8.1 正常成功

```json
{ "code": 200, "message": "success", "data": {} }
```

Axios 拦截器把 `data` 直接返回给页面。

### 8.2 业务异常

例如 Provider 不存在、重复创建、不能删除默认 Provider：

```text
Service 抛 BusinessException
  → GlobalExceptionHandler
  → HTTP 200 + Result.error(业务码, message)
  → Axios 发现 code !== 200
  → Promise.reject(new Error(message))
  → SettingsPage catch
  → error toast
```

### 8.3 连通性测试结果为失败

Provider 测试和 ASR 测试把网络失败转换成普通 DTO：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "success": false,
    "message": "连接失败: ...",
    "model": "..."
  }
}
```

因此 Axios 不会 reject；页面通过 `data.success` 自己显示红色测试结果。只有测试开始前就找不到 Provider 等业务异常才进入 `catch`。

## 9. 并发、事务与生效边界

| 机制 | 实际作用 | 边界 |
|---|---|---|
| Redis `@RateLimit` | 按 Controller 方法做全局滑动窗口限流 | 所有实例共享 Redis 时可跨实例计数 |
| `ReentrantReadWriteLock` | 防止同一 JVM 中配置读写互相穿插 | 不是分布式锁，多实例之间不互斥 |
| `@Transactional` | CRUD 和默认 Provider 的数据库事务 | 不覆盖 Registry 缓存、YAML、`.env`、远端网络 |
| `registry.reload()` | 清空本实例两个缓存 Map | 不通知其他实例，不重建当前在途对象 |
| YAML/`.env` 文件写入 | 写出 Legacy Provider 与语音配置副本 | 不是数据库事务，且当前未被 Spring 启动配置导入 |

需要特别注意：数据库写方法在事务提交前调用 `registry.reload()`。缓存失效和数据库事务不是一个原子操作；文档后续会分别标出这一时序。

此外，`LlmProviderConfigService.validateWritablePaths()` 在 Bean 初始化时始终检查并创建这两个外部路径的父目录，即使生产实际走数据库模式。路径不可创建或不可写会直接阻止 Service 初始化。
