# API Key 加密、密钥管理与配置文件安全

## 1. 模块基础讲解

数据库中的 Provider API Key 使用 `AES/GCM/NoPadding` 加密：

1. `ApiKeyEncryptionService` 启动时解析主密钥。
2. 若配置值是 Base64 且解码后恰好 32 字节，直接作为 AES-256 Key。
3. 否则对可读字符串做 SHA-256，得到 32 字节 Key。
4. 每次加密生成新的 12 字节随机 nonce。
5. GCM 生成密文和 128 bit Authentication Tag，二者一起由 `doFinal` 输出。
6. nonce 和 ciphertext 分别 Base64 后存入 Entity。

AES-GCM 同时提供机密性和完整性：不知道 Key 无法读取，篡改密文或 nonce 会在解密时认证失败。
nonce 不需要保密，但同一个 Key 下绝不能重复使用。

如果没有配置主密钥且 `requireEncryptionKey=false`，代码使用固定开发回退字符串派生 Key；若
`requireEncryptionKey=true` 则启动失败。生产必须开启 fail-fast，不能使用仓库内固定回退值。

返回前端时先解密再执行固定脱敏。Legacy Provider 和 ASR/TTS 密钥写入 `.env`，没有使用数据库
AES-GCM，这构成另一套秘密存储路径。

## 2. 基础面试问题

**问题：为什么不能只把 API Key 放数据库明文？**

回答：数据库备份、只读账号、SQL 注入和运维查询都可能泄漏明文。应用层加密使拿到数据库的人仍需
额外获得主密钥。它不能防御已完全控制应用进程的攻击者，但显著减少静态数据泄露面。

**问题：为什么选择 GCM 而不是 ECB/CBC？**

回答：GCM 是 AEAD 模式，同时加密和认证；ECB 会泄漏模式，CBC 单独使用不验证完整性，容易受到
篡改攻击。GCM 的关键要求是每次随机且不重复的 nonce。

**问题：nonce 为什么可以和密文一起存？**

回答：nonce 的作用是保证同一 Key 下每次加密唯一，不是秘密。解密必须知道 nonce，所以公开存储
是正常设计；真正必须隔离的是主密钥。

**问题：脱敏和加密有什么区别？**

回答：加密是可逆的静态数据保护，持有 Key 可恢复明文；脱敏是展示策略，减少 UI 和接口泄漏，通常
不用于恢复。两者解决不同环节的问题。

## 3. 进阶面试问题

**问题：直接 SHA-256 可读口令作为 Key 有什么问题？**

回答：SHA-256 很快，弱口令容易被离线暴力破解，没有 salt 和成本参数。若允许人类口令，应使用
Argon2id、scrypt 或 PBKDF2 并保存 salt；更推荐直接注入高熵 32 字节随机 Key 或使用 KMS 数据密钥。

**问题：如何轮换主密钥？**

回答：当前表没有 keyVersion，直接替换环境变量会让全部历史密文无法解密。正确方案是密文记录
`keyId/version`，解密支持旧 Key，后台逐条解密并用新 Key 重加密，验证完成后再下线旧 Key。

**问题：为什么“数据库加密”仍可能泄密？**

回答：应用运行时必须持有明文，heap dump、调试器、错误日志或恶意依赖仍可能读取；测试接口还会
把 Key 放入 Authorization Header 发往用户配置的 URL。必须同时做进程权限、日志脱敏、SSRF 防护、
最小权限和密钥定期轮换。

**问题：固定开发回退 Key 有什么风险？**

回答：任何知道源码的人都能解密使用回退 Key 生成的数据库密文。如果生产忘记设置 require flag，
就形成静默的全局已知密钥。生产 profile 应默认 `requireEncryptionKey=true`，并拒绝已知回退值。

**问题：当前 `.env` 写入有什么一致性与安全问题？**

回答：写入失败只 `log.warn`，调用仍可能成功；文件权限未显式设为 owner-only；值未处理换行，存在
格式注入；写入不是原子操作；而且当前外部 env 文件没有被启动流程读取，持久化并不闭环。

## 4. 技术延伸问题

**问题：使用云 KMS/Secret Manager 会怎样设计？**

回答：数据库只存 secret reference，运行时通过工作负载身份取密钥；或使用 envelope encryption，
KMS 只解密数据密钥，数据密钥加密 API Key。好处是审计、轮换和权限集中，代价是外部依赖和延迟。

**问题：是否应该允许前端回显密钥片段？**

回答：取决于威胁模型。高安全系统只返回 `configured=true` 和更新时间；需要人工辨识时可返回末四位，
但接口必须强认证并审计。任何情况下都不应返回可直接复制使用的明文。

**问题：还可以使用什么算法？**

回答：ChaCha20-Poly1305 也是 AEAD，适合无 AES 硬件加速环境；重点不是追逐算法，而是 nonce 唯一、
主密钥管理、版本轮换和正确库实现。代码注释声称 XChaCha20-Poly1305 与实际 AES-GCM 不一致，应修正。

## 5. 改进方案问题

**问题：如何改造当前加密数据结构？**

回答：引入 `EncryptedSecret(algorithm, keyVersion, nonce, ciphertext)`；使用 AAD 绑定 Provider ID 和
字段名，防止密文被复制到另一个 Provider；主密钥从 Secret Manager/KMS 获取；增加轮换任务和审计。

**问题：如何处理 String 中的明文生命周期？**

回答：Java String 无法主动擦除，尽量缩短作用域、禁止日志、避免 DTO 传播；底层支持时使用 `char[]`
或专用 Secret 类型并及时清零。现实中更重要的是限制 heap dump 和诊断端点访问。

**问题：如何修复 `.env` 文件路径？**

回答：优先取消应用运行时写 secret 文件，改存数据库密文或 Secret Manager。若必须保留，使用 0600
权限、临时文件原子替换、输入换行校验，并通过明确的配置导入验证重启可恢复。

**问题：测试应覆盖哪些密码学属性？**

回答：同一明文两次加密产生不同 nonce/密文且都可解；错误 Key、篡改 nonce、篡改密文必须失败；
Key 版本轮换兼容；空值策略明确；生产 require flag 缺 Key 时启动失败。不要断言具体随机密文。

## 6. 故障处理问题

**问题：更换环境变量后所有 Provider 都无法解密怎么办？**

回答：立即恢复原主密钥，不要批量覆盖密文。确认是否 Base64 形式变化、空格被 trim 或使用了不同
环境。恢复服务后按版本化方案轮换，不能直接“一刀切”。

**问题：只有一条 Provider 解密失败怎么查？**

回答：主密钥大概率正确，检查该行 nonce/ciphertext 是否截断、被手工修改或错配；从备份恢复该行，
或让管理员重新提交 API Key。不要在错误响应中输出密文和底层异常细节。

**问题：数据库泄露后应做什么？**

回答：即使密钥加密也要按安全事件处理：确认主密钥是否同时暴露、吊销并轮换上游 API Key、轮换
数据加密 Key、审计异常调用、检查备份和日志泄漏，并通知相关责任人。

**问题：`.env` 中出现两条同名 Key 怎么处理？**

回答：当前正则会替换所有行，但不同 dotenv 解析器对重复键可能取首个或最后一个。应解析成结构化
键值、检测重复并拒绝模糊状态，修复后用单一来源生成完整文件。
