# 面试邀约解析：规则解析与 AI 兜底怎么讲

## 1. 一句话定位

`InterviewParseService` 负责把用户粘贴的面试邀请文本解析成 `CreateInterviewRequest`，用于前端回填创建日程表单。它采用“规则优先，AI 兜底”的策略。

面试中可以这样说：

> 用户收到的面试邀请可能来自邮件、飞书、腾讯会议、Zoom 或聊天记录，格式不统一。我的设计是先用确定性的正则规则解析已知平台格式，规则提取不到关键字段时再调用 LLM 解析非结构化文本。这样兼顾性能、稳定性和覆盖面。

## 2. parse 接口做什么

前端请求：

```text
POST /api/interview-schedule/parse
```

请求体：

```text
ParseRequest {
  rawText: 用户粘贴的邀约文本,
  source: feishu / tencent / zoom / other，可选
}
```

响应体：

```text
ParseResponse {
  success,
  data: CreateInterviewRequest,
  confidence,
  parseMethod,
  log
}
```

关键点：

> 解析接口不创建数据库记录，只返回可回填表单的数据。用户确认后，再调用创建日程接口。

## 3. 为什么解析结果用 CreateInterviewRequest

`CreateInterviewRequest` 本来就是创建日程表单的请求体，字段包括：

```text
companyName
position
interviewTime
interviewType
meetingLink
roundNumber
interviewer
notes
reminderEnabled
reminderEmail
```

解析服务直接填充这个对象，有两个好处：

1. 前端可以直接拿 `data` 回填创建表单。
2. 解析结果和最终创建日程的数据结构一致，减少中间 DTO 转换。

面试表达：

> 解析阶段不直接入库，是因为 LLM 或规则解析可能有误，需要让用户确认。后端返回的是创建请求对象，前端回填后用户可以修改，再提交创建。

## 4. 解析流程

```text
InterviewScheduleController.parse
  -> InterviewParseService.parse(rawText, source)
      -> rawText 为空：返回 success=false
      -> tryRuleParsing(rawText, source)
          -> 根据 source 或文本特征选择平台规则
          -> 飞书 / 腾讯会议 / Zoom 正则解析
      -> isValidResult(result)
          -> companyName + position + interviewTime 都非空才算成功
      -> parseWithAI(rawText, source)
          -> PromptSanitizer 清洗
          -> wrapWithDelimiters 包裹用户数据
          -> LlmProviderRegistry.getChatClientOrDefault
          -> 调用 LLM
          -> 剥 Markdown 代码块
          -> ObjectMapper 反序列化
      -> 仍失败：返回 success=false
```

## 5. 规则解析为什么优先

规则解析的优点：

| 优点 | 说明 |
| --- | --- |
| 快 | 正则本地执行，毫秒级 |
| 稳 | 已知格式下结果确定 |
| 便宜 | 不消耗 LLM token |
| 可解释 | 哪个字段由哪个正则提取很清楚 |

AI 解析的优点：

| 优点 | 说明 |
| --- | --- |
| 覆盖面广 | 可处理自然语言、邮件正文、聊天记录 |
| 灵活 | 可推断“明天下午两点”等相对时间 |
| 用户体验好 | 不要求用户按固定格式粘贴 |

所以组合策略是：

```text
已知格式：规则解析
不规则文本：AI 解析
两者失败：返回可解释的失败结果
```

## 6. 支持哪些规则格式

### 飞书

能提取：

```text
时间/时段
会议链接 meeting.feishu.cn
公司/单位/组织
岗位/职位/职务
轮次
```

并默认：

```text
interviewType = VIDEO
```

### 腾讯会议

能提取：

```text
日期 + 时间
会议号
密码
公司/单位
岗位/职位
```

会议号和密码会拼成会议链接文本。

### Zoom

能提取：

```text
zoom.us 链接
日期
时间
```

Zoom 通常缺公司和岗位，规则解析可能不能满足必需字段，因此经常需要 AI 兜底。

## 7. 有效结果怎么判断

`isValidResult` 要求三个必需字段都存在：

```text
companyName
position
interviewTime
```

原因是 `CreateInterviewRequest` 中这三个字段有校验：

```text
@NotBlank companyName
@NotBlank position
@NotNull interviewTime
```

面试表达：

> 规则解析允许提取部分字段，但只有公司、岗位、时间都齐全才算解析成功。否则宁愿走 AI 兜底或返回失败，也不创建半残缺日程。

## 8. AI 解析怎么防 Prompt 注入

AI 解析前做了两步防护：

1. `PromptSanitizer.sanitize(rawText)` 清理用户输入中的可疑指令。
2. `promptSanitizer.wrapWithDelimiters("parse-input", safeRawText)` 用随机边界包裹用户数据。

Prompt 中还追加：

```text
PromptSecurityConstants.DATA_BOUNDARY_INSTRUCTION
```

面试表达：

> 邀约文本本质是用户输入，不能直接拼进 Prompt 里。它可能包含“忽略上文指令”之类的注入内容，所以我先清洗，再用数据边界包裹，并明确告诉模型边界内是数据不是指令。

## 9. AI 输出如何解析

当前 AI 解析不是走 `StructuredOutputInvoker`，而是手动处理：

```text
chatClient.prompt().user(prompt).call().content()
  -> content 为空则失败
  -> 如果包含 ```json 代码块，则剥掉外壳
  -> ObjectMapper.readValue(jsonContent, Map)
  -> 逐字段填充 CreateInterviewRequest
```

时间字段特殊处理：

```text
YYYY-MM-DDTHH:mm
  -> 补 :00
YYYY-MM-DDTHH:mm:ss
  -> 直接 LocalDateTime.parse
```

面试时要诚实说明：

> 当前 AI 解析有基本 JSON 去壳和字段容错，但没有统一使用项目里的 `StructuredOutputInvoker`。后续可以迁移过去，让输出格式约束、重试和 JSON 修复都统一。

## 10. 当前实现边界

| 边界 | 当前情况 | 优化方向 |
| --- | --- | --- |
| source 语义 | `source` 既作为平台提示，也传给 `getChatClientOrDefault` | 拆成 `source` 和 `provider` 两个字段 |
| AI 输出 | 手动剥 JSON 和反序列化 | 改用 `StructuredOutputInvoker` |
| 日期理解 | 规则只支持固定日期格式，AI 才能推相对时间 | 增加本地中文日期解析 |
| 平台覆盖 | 规则只覆盖飞书、腾讯会议、Zoom | 扩展邮件模板和更多会议平台 |
| 数据校验 | `interviewType` 是 String，没有枚举校验 | 改成枚举或加白名单校验 |
| 置信度 | rule 固定 0.95，AI 固定 0.8 | 根据字段完整性和来源动态计算 |

## 11. 面试回答模板

> 邀约解析这块我做的是规则优先、AI 兜底。用户在前端粘贴邮件或会议邀请后，请求 `/parse` 接口，后端先根据 `source` 或文本特征判断是飞书、腾讯会议还是 Zoom，再用正则提取时间、公司、岗位、会议链接和轮次。规则解析速度快、成本低、结果稳定，所以优先使用。
>
> 但真实邀约格式很复杂，所以当规则解析拿不到公司、岗位、面试时间这三个必需字段时，就降级到 AI 解析。AI 解析前会先用 `PromptSanitizer` 清洗用户输入，再用随机边界包裹文本，避免用户数据反向影响 Prompt。LLM 返回后，我会剥掉可能的 Markdown 代码块，用 Jackson 反序列化为 Map，再逐字段填充 `CreateInterviewRequest`。
>
> 解析成功后不会直接创建日程，而是返回给前端回填表单，让用户确认后再提交。这个设计既提升录入效率，又避免 AI 解析错误直接污染数据库。
