# 邮件与站内提醒完整面试回答

## 1. 先用一句话介绍

> 我在面试日程模块中增加了邮件和站内双渠道提醒。日程事务只负责持久化提醒计划，定时任务每分钟认领到期任务，再通过 Redis Stream 异步投递；邮件渠道使用 `JavaMailSender` 发送真实 HTML 邮件，站内渠道通过持久化消息和前端提醒铃展示，并通过唯一约束、状态机、悲观锁和失败重试控制重复任务与并发问题。

这不是只打印日志的演示代码。SMTP 邮件的创建、HTML 内容构建和
`JavaMailSender.send()` 都已经实现。当前只是没有启动完整后端并接入真实 SMTP
账号做端到端送达验证，而且自动派发开关默认关闭。

---

## 2. 为什么要做这个优化

原来的面试日程模块已经能够完成：

```text
粘贴面试邀请
  → 规则或 AI 解析
  → 用户确认日程
  → 保存并展示在日历中
  → 完成、取消或自动处理过期日程
```

但它只解决了“记录面试”的问题，没有解决“防止用户忘记面试”的问题。因此我增加了：

1. 面试前 24 小时提醒，让用户提前准备。
2. 面试前 1 小时提醒，避免临近面试时遗忘。
3. 站内提醒作为平台内的持久化通知。
4. 邮件提醒作为用户不在平台时的补充渠道。

最终形成：

```text
邀约解析 → 创建日程 → 生成提醒 → 到期投递 → 用户收到/查看 → 日程状态联动
```

## 3. 模块是怎么拆分的

| 分层 | 关键类 | 职责 |
|---|---|---|
| 接口层 | `InterviewReminderController` | 查询站内提醒、未读数、单条已读、全部已读 |
| 计划层 | `InterviewReminderService` | 生成、刷新、取消提醒计划，维护状态和已读时间 |
| 调度层 | `InterviewReminderScheduler` | 每分钟扫描并认领到期提醒 |
| 生产者 | `InterviewReminderStreamProducer` | 将轻量的 `reminderId` 写入 Redis Stream |
| 消费者 | `InterviewReminderStreamConsumer` | 读取任务、校验日程、执行渠道投递和重试 |
| 邮件渠道 | `SmtpReminderEmailSender` | 构建并发送真实 SMTP HTML 邮件 |
| 数据访问 | `InterviewReminderRepository` | 到期任务加锁查询、站内列表和未读数查询 |
| 前端组件 | `ReminderBell.tsx` | 轮询未读数、展示提醒、处理已读状态 |

我把“什么时候提醒”和“通过什么渠道发送”解耦。以后增加短信、企业微信或者
WebSocket 推送时，可以扩展投递渠道，不需要重写日程创建流程。

## 4. 创建日程后，提醒是怎么生成的

### 4.1 前端入口

用户在 `InterviewFormModal` 中填写日程，同时提交：

```text
reminderEnabled：是否启用提醒，默认 true
reminderEmail：收件邮箱，可选
```

不填写邮箱时仍然生成站内提醒；填写合法邮箱后，同时生成邮件提醒。

### 4.2 后端完整调用链

```text
InterviewSchedulePage / InterviewFormModal
  → interviewScheduleApi.create(request)
  → POST /api/interview-schedule
  → InterviewScheduleController.create()
  → InterviewScheduleService.create()
      → BeanUtils.copyProperties(request, entity)
      → normalizeReminderSettings(entity)
      → status = PENDING
      → InterviewScheduleRepository.save(entity)
      → InterviewReminderService.synchronizeReminders(saved)
          → 校验计划开关、日程状态和面试时间
          → upsertPlan(IN_APP, DAY_BEFORE)
          → upsertPlan(IN_APP, HOUR_BEFORE)
          → 有邮箱时：
              → upsertPlan(EMAIL, DAY_BEFORE)
              → upsertPlan(EMAIL, HOUR_BEFORE)
          → InterviewReminderRepository.save(reminder)
  → 返回 InterviewScheduleDTO
```

因此，一个启用提醒的待面试日程会生成：

| 是否填写邮箱 | 生成的计划 |
|---|---|
| 未填写 | 24 小时前站内提醒 + 1 小时前站内提醒，共 2 条 |
| 已填写 | 两个站内提醒 + 两个邮件提醒，共 4 条 |

如果计算出的提醒时间已经过去，但面试本身还没有开始，`resolveRemindAt()` 会把
`remindAt` 调整为当前时间，使提醒能够立即展示或进入投递流程。

## 5. 为什么单独建 `interview_reminder` 表

如果只在日程表增加 `reminded=true`，无法表达：

- 24 小时和 1 小时两个提醒时点。
- EMAIL 和 IN_APP 两个渠道。
- 每个任务独立的发送状态、失败次数和错误原因。
- 站内提醒的已读时间。

因此系统使用独立提醒实体，核心字段包括：

```text
scheduleId   关联的日程 ID
channel      EMAIL / IN_APP
timing       DAY_BEFORE / HOUR_BEFORE
status       PENDING / QUEUED / PROCESSING / SENT / FAILED / CANCELLED
recipient    邮件收件人，站内提醒为空
title        提醒标题
content      提醒正文
remindAt     应触发时间
sentAt       投递完成时间
readAt       站内提醒已读时间
retryCount   已重试次数
lastError    最近错误或取消原因
```

表上还有两个重要索引：

```text
(status, remind_at)       加速扫描到期任务
(channel, read_at, remind_at)  加速站内提醒和未读数查询
```

## 6. 到期提醒是怎么异步投递的

### 6.1 调度与入队

```text
InterviewReminderScheduler.dispatchDueReminders()
  → 每分钟执行一次
  → InterviewReminderService.claimDueReminderIds()
      → findDueForUpdate(PENDING, now, PageRequest)
      → 悲观写锁锁定本批记录
      → PENDING 改为 QUEUED
      → 返回 reminderId 列表
  → InterviewReminderStreamProducer.sendReminder(reminderId)
      → Redis Stream Add
```

生产者只传 `reminderId`，不把整份日程和邮件正文放入 Redis。这样消息体更小，而且
消费者处理时会重新读取数据库，能够拿到最新的日程状态。

### 6.2 消费与投递

```text
InterviewReminderStreamConsumer
  → parsePayload() 解析 reminderId
  → markProcessing()：QUEUED → PROCESSING
  → getDeliveryContext()
      → 提醒记录必须存在
      → 日程记录必须存在
      → 日程状态必须仍为 PENDING
  → 根据 channel 分流
      ├─ EMAIL
      │    → ReminderEmailSender.send(context)
      │    → SmtpReminderEmailSender.send(context)
      │    → JavaMailSender.send(message)
      └─ IN_APP
           → 无需外部调用，完成状态流转
  → markSent()：PROCESSING → SENT
  → ACK Redis Stream 消息
```

如果日程已经删除，或者状态已经变为完成、取消、改期，消费者会抛出
`AsyncTaskCancelledException`，将提醒标记为 `CANCELLED` 后 ACK，不再重试。

## 7. 为什么不能在日程事务中直接发邮件

SMTP 是外部网络调用，可能连接慢、超时或者被服务商限流。如果在
`InterviewScheduleService.create()` 的数据库事务中直接发送邮件，会产生三个问题：

1. 数据库连接会被长时间占用。
2. 邮件服务异常可能导致日程创建回滚。
3. 用户必须等待邮件发送完成才能得到接口响应。

所以这里采用“事务内写计划，事务外异步投递”：

```text
短事务：保存日程 + 保存提醒计划
事务结束
定时器认领任务
Redis Stream 解耦
消费者调用 SMTP
```

这也符合项目中“事务内禁止调用外部 API”的规范。

## 8. 邮件发送是真实实现吗

是。`SmtpReminderEmailSender.send()` 的执行流程是：

```text
校验 recipient
  → JavaMailSender.createMimeMessage()
  → new MimeMessageHelper(message, false, "UTF-8")
  → 设置发件人、收件人和主题
  → buildHtml(context)
  → helper.setText(html, true)
  → JavaMailSender.send(message)
```

HTML 邮件包含公司、岗位、时间、面试形式、会议链接、面试官和备注。实现中还做了：

1. 使用 `HtmlUtils.htmlEscape()` 转义日程内容，防止用户输入直接注入 HTML。
2. 只把 `http://` 或 `https://` 开头的会议地址渲染为链接。
3. 日志中使用 `maskEmail()` 隐藏完整收件地址。
4. 将邮件异常包装为 `BusinessException` 和
   `INTERVIEW_REMINDER_SEND_FAILED` 错误码。
5. SMTP 主机、端口、账号、密码、TLS 和连接/读/写超时通过配置管理，不在代码中硬编码。

准确的面试表述是：

> 邮件发送代码已经完整实现，并不是日志模拟；但当前自动派发默认关闭，也没有使用真实生产 SMTP 账号做端到端送达验证。配置 SMTP 并打开派发开关后，代码会执行真实发送。

## 9. 站内提醒的完整闭环

前端 `Layout` 全局挂载 `ReminderBell`，调用四个接口：

```text
GET   /api/interview-schedule/reminders/unread-count
GET   /api/interview-schedule/reminders/in-app?unreadOnly=false
PATCH /api/interview-schedule/reminders/{id}/read
PATCH /api/interview-schedule/reminders/read-all
```

调用流程如下：

```text
页面加载
  → ReminderBell.loadUnreadCount()
  → 每 60 秒重新查询未读数量
  → 显示红色角标

用户打开提醒铃
  → loadReminders()
  → 查询 channel=IN_APP 且 remindAt<=now 的可见记录
  → 展示标题、正文和提醒时间

用户点击提醒
  → markRead(id)
  → 后端写入 readAt
  → 前端减少未读数
  → 跳转面试日程页面

用户点击全部已读
  → markAllInAppRead()
  → 批量设置 readAt
```

站内提醒是否可见主要由 `remindAt <= now` 决定。因此即使自动派发开关关闭，计划到期后
前端仍可以查到站内提醒；打开派发开关后，消费者还会把它的状态推进为 `SENT`。

## 10. 状态机和失败重试

正常状态流转：

```text
PENDING → QUEUED → PROCESSING → SENT
```

异常分支：

```text
PROCESSING → QUEUED      未达到重试上限，重新入队
PROCESSING → FAILED      达到最大重试次数
任意活动状态 → CANCELLED  日程失效或提醒被关闭
```

消费者继承公共的 `AbstractStreamConsumer`。业务处理异常后：

1. 当前消息先重新写入 Stream，并把 `retryCount + 1`。
2. 提醒状态重新改为 `QUEUED`。
3. 当前消息 ACK，避免同一条消息一直卡在 pending list。
4. 达到最大重试次数后标记为 `FAILED`，保存 `lastError`。

当前公共模板配置的最大重试次数是 3。

## 11. 怎么处理重复和并发

系统目前做了三层控制。

### 第一层：计划唯一性

数据库唯一约束为：

```text
schedule_id + channel + timing
```

同一日程、同一渠道、同一时点只能有一条计划。修改日程时调用的是 upsert，而不是不断
插入新记录。

### 第二层：并发认领

扫描到期任务时使用 `PESSIMISTIC_WRITE`。同一条 `PENDING` 记录被一个调度实例认领并
改为 `QUEUED` 后，其他实例不会在同一轮再次认领它。

### 第三层：状态校验

发送前重新读取日程，只有仍为 `PENDING` 的日程才继续发送。日程被取消或删除后，即使
Redis 中还有旧消息，消费者也会取消任务。

需要诚实说明：这些设计可以防止重复创建计划和大部分重复调度，但 SMTP 本身不是事务性
资源。在“邮件服务已经接收邮件，但应用在写 `SENT` 前宕机”这种极端窗口下，仍然可能
重复发送。生产环境要进一步做到更强的投递幂等，可以增加业务幂等键、发送记录表，或使用
支持幂等请求的邮件服务商 API。

## 12. 日程变化后提醒怎么联动

| 日程操作 | 提醒处理 |
|---|---|
| 创建 PENDING 日程 | 生成两条站内计划，可选生成两条邮件计划 |
| 修改时间或邮箱 | 更新原计划并重置为 PENDING，清理旧发送/已读状态 |
| 关闭 reminderEnabled | 取消所有活动提醒 |
| 状态改为 COMPLETED/CANCELLED/RESCHEDULED | 取消活动提醒 |
| 状态重新改为 PENDING | 重新同步提醒计划 |
| 删除日程 | 先取消活动提醒，再删除日程 |
| 每小时处理过期日程 | 批量取消日程，并批量取消关联提醒 |

这保证提醒不是一套孤立数据，而是跟随日程生命周期变化。

## 13. 配置和运行边界

提醒配置集中在 `InterviewReminderProperties`，没有在 Service 中散落 `@Value`：

```text
planningEnabled       是否生成提醒计划，默认 true
dispatchEnabled       是否启动调度和消费者，默认 false
scanCron              扫描表达式，默认每分钟
zone                  时区，默认 Asia/Shanghai
batchSize             每批认领数量，默认 50
dayBeforeHours        提前小时数，默认 24
hourBeforeMinutes     临近提醒分钟数，默认 60
email.fromAddress     发件地址
email.fromName        发件名称
email.subjectPrefix   邮件主题前缀
```

`InterviewReminderScheduler`、Producer 和 Consumer 都通过
`@ConditionalOnProperty` 控制，只有：

```text
app.interview-reminder.dispatch-enabled=true
```

时才会启动自动派发链路。

## 14. 面试官高频追问

### Q1：为什么用 Redis Stream，不直接让定时任务发邮件？

定时任务只负责发现和认领任务，Redis Stream 负责缓冲和解耦。SMTP 变慢时不会拖住扫描
事务；消费者还可以统一复用 ACK、重试、错误状态和链路追踪能力。

### Q2：为什么不用 RabbitMQ 或 Kafka？

项目本身已经使用 Redis Stream 处理简历分析、知识库向量化和面试评估。提醒任务量不大，
继续复用现有基础设施可以减少运维复杂度。如果以后提醒规模明显增大，需要延迟队列、死信
队列和更强的投递治理，再评估 RabbitMQ 或 Kafka。

### Q3：为什么不用 WebSocket 做站内提醒？

当前需求不是秒级即时聊天，而是面试前 24 小时和 1 小时提醒。数据库持久化加一分钟轮询
实现简单，而且用户离线后重新登录仍能看到。后续需要即时推送时，可以增加 SSE 或
WebSocket，但数据库提醒仍应作为离线兜底。

### Q4：为什么不用 Redis Key 直接设置 24 小时过期？

提醒计划属于重要业务数据，需要支持查询、取消、改期、失败追踪和已读状态。只放 Redis
不利于长期审计，也容易因为缓存淘汰或数据丢失而漏提醒，所以数据库是事实来源，Redis
Stream 只承担异步投递。

### Q5：多实例部署会不会重复扫描？

到期查询使用数据库悲观写锁，并在同一事务内把状态从 `PENDING` 改为 `QUEUED`，可以
避免同一条记录被多个实例同时认领。不过如果数据库压力较大，可进一步使用 PostgreSQL
`FOR UPDATE SKIP LOCKED`，降低不同调度实例之间的锁等待。

### Q6：邮件失败了怎么办？

消费者捕获异常并重新入队，最多重试三次；超过上限后标记 `FAILED`，同时记录
`retryCount` 和 `lastError`，便于后续运维查询和人工补偿。

### Q7：站内提醒为什么还需要 `SENT` 状态？

`readAt` 表示用户是否看过，`SENT` 表示提醒是否走完投递状态机，两者语义不同。即使站内
提醒没有外部网络发送，也保留统一状态，便于不同渠道使用同一套任务治理模型。

### Q8：怎样防止邮件内容出现 XSS 或恶意链接？

公司、岗位、备注等动态内容全部经过 HTML 转义；会议地址只有以 HTTP/HTTPS 开头时才
生成链接。更严格的生产方案还可以增加 URL 白名单、邮件模板引擎和内容安全策略。

### Q9：当前有什么不足？

1. 项目尚未接入用户认证，站内提醒目前没有 `userId` 隔离。
2. 邮件代码完整，但尚未在真实 SMTP 环境做端到端送达验证。
3. 暂无管理端查看失败任务和手工重发。
4. 极端宕机窗口下还不能承诺邮件 exactly-once。
5. 提醒时点目前固定为 24 小时和 1 小时，尚未开放用户偏好配置。

## 15. 一分钟面试回答

> 面试日程最初只有记录和状态管理，我后来增加了邮件加站内双渠道提醒，形成从创建日程到到期触达的完整闭环。创建或修改待面试日程后，`InterviewReminderService` 会生成面试前 24 小时和 1 小时的提醒计划；不填邮箱生成两条站内提醒，填了邮箱再增加两条邮件提醒。提醒计划持久化在独立表中，定时器每分钟通过悲观锁批量认领到期任务，先把状态从 PENDING 改成 QUEUED，再通过 Redis Stream 交给消费者。邮件渠道使用 `JavaMailSender` 和 `MimeMessageHelper` 发送真实 HTML 邮件，站内渠道由前端提醒铃每分钟查询未读数，并支持单条和全部已读。整个链路复用了统一消费者模板，失败最多重试三次；数据库唯一约束保证同一日程、渠道和提醒时点只有一条计划。日程改期、取消、完成、删除或者自动过期时，未完成提醒会同步取消。这样既避免在数据库事务中调用 SMTP，也让提醒具备状态追踪、失败重试和生命周期联动能力。

## 16. 三十秒精简回答

> 我把日程提醒拆成计划、调度、队列和渠道四层。日程事务只写提醒计划，定时任务每分钟用悲观锁认领到期记录，再通过 Redis Stream 异步投递。邮件使用 JavaMailSender 发送真实 HTML 内容，失败最多重试三次；站内提醒持久化后由前端提醒铃轮询并维护已读状态。唯一约束防止重复计划，日程改期、取消和删除会同步撤销提醒。这个优化把原来的日程 CRUD 补成了真正的用户触达闭环。
