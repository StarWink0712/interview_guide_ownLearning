是的，但完整功能比你说的再多一层：

```
┌─────────────────────────────────────────────────────┐
│                    面试日程模块                         │
├─────────────────┬───────────────────────────────────┤
│  录入方式        │  智能解析                          │
│  - 手动填写表单   │  粘贴邀约文本 → 自动提取：            │
│  - 解析邀约文本   │  公司名、岗位、时间、链接、轮次         │
├─────────────────┼───────────────────────────────────┤
│  展示方式        │  日历视图（周/月/日）                  │
│                 │  列表视图                           │
│                 │  拖拽调整时间、拖拽调整时长              │
├─────────────────┼───────────────────────────────────┤
│  状态管理        │  PENDING → COMPLETED（标记完成）     │
│                 │  PENDING → CANCELLED（主动取消）      │
│                 │  定时任务自动将过期的 PENDING 改为 CANCELLED │
└─────────────────┴───────────────────────────────────┘
```

你总结的"手动输入 + 粘贴解析 → 日历展示"是对的，再加上一层**生命周期管理**（面试过了自动标记为已取消、手动标记完成/取消），就是这个模块的完整闭环了。

## 面试应答策略：为什么设计面试日程管理？

可以从三个层次来回答，从浅到深体现你的思考。

***

### 第一层：直接痛点（用户视角）

> 既然这是一个模拟面试平台，用户最关心的就是"什么时候面试、面什么公司"。没有日程管理的话，用户只能靠记忆或者自己找个日历 App 来记录，数据和面试功能是割裂的。把日程管理和面试平台放在一起，用户在一个地方就能完成"安排面试 → 复习准备 → 模拟练习"的完整闭环，不用切来切去。

***

### 第二层：智能解析是稀缺功能（差异化视角）

> 面试邀约通常以邮件、短信、聊天记录的形式发给用户，里面格式五花八门——飞书的格式、腾讯会议的格式、Zoom 的格式都不一样。用户需要手动把公司名、岗位、时间、链接逐条复制粘贴到日历里，特别烦。
>
> 所以我们做了智能解析功能：用户直接把邀约文本一贴，系统用三重策略（飞书正则 → 腾讯正则 → AI 兜底）自动提取所有字段。这比市面上任何通用日历 App 都更针对性地面向求职场景。

***

### 第三层：状态生命周期自动化（工程视角）

> 一般日历 App 只管记录时间，过期的日程不会自动处理。但在面试场景里，面试时间过去了你没标记完成，页面会一直显示"待面试"，给用户造成焦虑。
>
> 我们在后端设计了一个定时任务，每小时检查一次，自动把"面试时间已过且仍为PENDING状态"的日程标记为CANCELLED。这看似是个小功能，但背后有一些工程考量：用的是 `@Modifying` 批量更新而非逐条查询更新（减少数据库压力）、`@Transactional` 保证原子性、只在有数据变化时才打日志避免刷屏。这些细节让功能体量小但质量不低。

***

### 回答总结模板

> 面试官问这个的时候，我可以这么回答：
>
> "面试日程管理这个模块的设计初衷是让求职闭环更加完整。我们平台有模拟面试功能，但用户在实际求职过程中还会收到各种真实的面试邀约，如果不做日程管理，用户就要在多个工具之间切换，体验是割裂的。
>
> 具体来说有三个设计要点：
> 第一，智能解析——用户粘贴邀约文本后自动提取公司、岗位、时间等信息，支持飞书、腾讯会议、Zoom 三种格式的正则解析，识别不了的交给 AI 兜底。
> 第二，日历可视化——用 react-big-calendar 做周/月/日视图，支持拖拽调整时间，比表格列表直观得多。
> 第三，状态自动化——定时任务把已过期的面试自动标记为已取消，保证数据时效性。批量更新 + 事务保护，工程上也做到位了。"

**灵活选择**：如果面试官只想知道"拿来干什么"，说第一层就行。如果追问"有什么亮点"，把第二层的智能解析展开。如果面试官是偏后端的，把第三层的定时任务和批量更新细节展开。
