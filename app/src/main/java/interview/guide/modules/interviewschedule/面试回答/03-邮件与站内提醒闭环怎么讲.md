# 邮件与站内提醒闭环怎么讲

## 1. 一句话定位

提醒子模块负责根据面试日程生成站内和邮件提醒计划，并在提醒时间到达后通过定时扫描、Redis Stream 和消费者完成异步投递。

面试中可以这样说：

> 我没有在创建日程的事务里直接发邮件，而是把提醒设计成持久化任务。日程创建或更新时只生成提醒计划，到期后由定时器认领，再写 Redis Stream 异步投递。这样既不会阻塞日程接口，也能支持重试、取消和状态追踪。

## 2. 创建日程后会生成哪些提醒

`InterviewReminderService.synchronizeReminders(schedule)` 根据日程生成计划。

前提：

```text
planningEnabled = true
schedule.reminderEnabled != false
schedule.status == PENDING
schedule.interviewTime != null
```

生成规则：

| 条件 | 生成计划 |
| --- | --- |
| 未填写邮箱 | IN_APP 提前一天 + IN_APP 提前一小时 |
| 填写邮箱 | 上面两条 + EMAIL 提前一天 + EMAIL 提前一小时 |

也就是：

```text
DAY_BEFORE = interviewTime - dayBeforeHours
HOUR_BEFORE = interviewTime - hourBeforeMinutes
```

默认配置：

```text
dayBeforeHours = 24
hourBeforeMinutes = 60
```

如果计算出的提醒时间已经过去，则调整为当前时间，让提醒可以立即展示或投递。

## 3. 为什么要单独建 interview_reminder 表

如果只在日程表里加一个 `reminded` 字段，无法表达：

1. 提前一天和提前一小时两个时点。
2. 站内和邮件两个渠道。
3. 每条提醒独立的发送状态。
4. 邮件失败重试次数和错误原因。
5. 站内提醒是否已读。

所以使用独立实体 `InterviewReminderEntity`：

```text
scheduleId
channel: EMAIL / IN_APP
timing: DAY_BEFORE / HOUR_BEFORE
status: PENDING / QUEUED / PROCESSING / SENT / FAILED / CANCELLED
recipient
title
content
remindAt
sentAt
readAt
retryCount
lastError
```

表上还有唯一约束：

```text
schedule_id + channel + timing
```

作用：

> 同一个日程、同一个渠道、同一个提醒时机只保留一条计划。更新日程时走 upsert，而不是重复插入。

## 4. 提醒计划如何更新和取消

### 创建或更新 PENDING 日程

```text
InterviewScheduleService.create/update
  -> reminderService.synchronizeReminders(saved)
  -> upsertPlan(IN_APP, DAY_BEFORE)
  -> upsertPlan(IN_APP, HOUR_BEFORE)
  -> 如果有 reminderEmail
       upsertPlan(EMAIL, DAY_BEFORE)
       upsertPlan(EMAIL, HOUR_BEFORE)
     否则
       cancelChannel(EMAIL)
```

`upsertPlan` 如果发现提醒时间或收件人变化，会：

```text
status = PENDING
retryCount = 0
lastError = null
sentAt = null
readAt = null
```

也就是让提醒按新计划重新投递。

### 状态变化或删除

```text
COMPLETED / CANCELLED / RESCHEDULED
  -> cancelActiveReminders

delete schedule
  -> 先 cancelActiveReminders
  -> 再 deleteById

过期自动取消
  -> 批量改日程 CANCELLED
  -> 批量取消关联活跃提醒
```

活跃提醒包括：

```text
PENDING
QUEUED
PROCESSING
```

## 5. 到期提醒如何入队

自动派发由配置控制：

```text
app.interview-reminder.dispatch-enabled
```

默认是 `false`。启用后，`InterviewReminderScheduler` 生效。

调度流程：

```text
@Scheduled(cron = app.interview-reminder.scan-cron, zone = app.interview-reminder.zone)
  -> reminderService.claimDueReminderIds()
      -> findDueForUpdate(PENDING, now, PageRequest)
      -> 悲观写锁锁定本批到期提醒
      -> PENDING 改为 QUEUED
      -> 返回 reminderId 列表
  -> producer.sendReminder(reminderId)
      -> 写 Redis Stream
```

为什么只投递 `reminderId`：

1. Redis 消息更小。
2. 消费时重新查数据库，可以拿到最新状态。
3. 日程如果已取消或删除，消费者能及时跳过。

## 6. Redis Stream 消费怎么处理

`InterviewReminderStreamConsumer` 继承 `AbstractStreamConsumer`。

消费流程：

```text
parsePayload
  -> 解析 reminderId
markProcessing
  -> QUEUED/其他状态改 PROCESSING
processBusiness
  -> reminderService.getDeliveryContext(reminderId)
      -> 提醒存在
      -> 日程存在
      -> 日程仍为 PENDING
  -> 根据 channel 分流
      EMAIL: emailSender.send(context)
      IN_APP: 只记录到达展示时间
markCompleted
  -> markSent
  -> status = SENT
```

如果日程已删除或不再 PENDING：

```text
AsyncTaskCancelledException
  -> markCancelled
  -> ACK
  -> 不重试
```

如果投递失败：

```text
AbstractStreamConsumer 重试
  -> retryMessage
  -> retryCount 增加
  -> 状态回到 QUEUED
重试耗尽
  -> markFailed
```

## 7. 站内提醒怎么展示

站内提醒不依赖外部 SMTP。前端通过接口查询：

```text
GET /api/interview-schedule/reminders/in-app?unreadOnly=false
GET /api/interview-schedule/reminders/unread-count
PATCH /api/interview-schedule/reminders/{id}/read
PATCH /api/interview-schedule/reminders/read-all
```

查询条件：

```text
channel = IN_APP
remindAt <= now
status not in CANCELLED, FAILED
unreadOnly=true 时 readAt is null
```

所以即使 `dispatch-enabled=false`，站内提醒也可以在 `remindAt` 到达后被前端查询展示。

面试表达：

> 站内提醒的本质是数据库可见消息，不一定需要异步消费者投递。派发关闭时，到期 PENDING 站内提醒也能展示；派发开启后，它会进一步经历 QUEUED、PROCESSING、SENT 的状态流转。

## 8. 邮件发送怎么实现

邮件通道使用 `SmtpReminderEmailSender`：

```text
校验 recipient
  -> JavaMailSender.createMimeMessage()
  -> MimeMessageHelper UTF-8
  -> 设置 from/to/subject
  -> buildHtml(context)
  -> helper.setText(html, true)
  -> mailSender.send(message)
```

安全细节：

1. HTML 内容使用 `HtmlUtils.htmlEscape` 转义。
2. 日志中邮箱会脱敏。
3. SMTP 失败抛 `BusinessException(ErrorCode.INTERVIEW_REMINDER_SEND_FAILED, ...)`。

## 9. 为什么不在事务中直接发邮件

事务中调用 SMTP 会有三个问题：

1. SMTP 是外部网络调用，可能慢或超时。
2. 数据库事务会被长时间占用。
3. 邮件失败会影响日程创建体验。

当前设计：

```text
事务内：保存日程 + 保存提醒计划
事务外：定时扫描 + Redis Stream + 消费者发邮件
```

这符合项目规范：事务方法内不调用外部 API。

## 10. 当前实现边界

| 边界 | 当前情况 | 优化方向 |
| --- | --- | --- |
| 自动派发 | 默认关闭 | 部署时配置 SMTP 和开启 dispatch |
| 用户隔离 | 站内提醒全局可见 | 增加 userId |
| 实时性 | 前端轮询未读数 | 可加 WebSocket 或 SSE |
| 邮件送达 | 只调用 SMTP，不跟踪真实送达 | 接入邮件服务回执 |
| 重复投递 | 用唯一约束和悲观锁降低风险 | 多实例下继续压测幂等 |
| 模板 | HTML 模板写在 Java 字符串中 | 可抽成模板文件 |

## 11. 面试回答模板

> 提醒功能我设计成持久化任务，而不是创建日程时直接发邮件。日程创建或更新后，`InterviewReminderService` 会根据面试时间生成提前一天和提前一小时的提醒。站内提醒默认生成两条，如果用户填写了邮箱，就再生成两条邮件提醒。表上用 `scheduleId + channel + timing` 做唯一约束，保证同一个计划不会重复插入。
>
> 到了提醒时间后，如果开启了自动派发，`InterviewReminderScheduler` 每分钟扫描到期的 PENDING 提醒，用悲观锁认领一批，改成 QUEUED，然后把轻量的 `reminderId` 写入 Redis Stream。消费者拿到 ID 后重新查数据库，确认日程还存在且仍为 PENDING，再按通道处理：邮件通道调用 `SmtpReminderEmailSender` 发送真实 HTML 邮件，站内通道只完成状态流转，前端通过提醒铃查询展示。
>
> 这样做的好处是日程事务很短，外部 SMTP 调用被隔离到异步消费者里，同时提醒有状态、可重试、可取消、可查询。边界是当前没有用户隔离和实时推送，后续可以加 userId、WebSocket/SSE 和邮件送达回执。
