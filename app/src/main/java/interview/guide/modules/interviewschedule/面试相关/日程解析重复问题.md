## 当前代码的情况：会重复创建

先诚实承认现状——当前代码**没有任何去重逻辑**。解析和创建是两条独立的链路：

```
第一次：粘贴文本 → parse() → 返回 CreateInterviewRequest → create() → 入库（id=1）
第二次：粘贴同一文本 → parse() → 返回同样的 CreateInterviewRequest → create() → 又入库（id=2）
```

结果是数据库里有两条一模一样的日程（id 不同，其他字段全相同）。

---

## 面试中的标准答法

应该分两层讲：**你的思考框架 + 具体方案**。

### 第一层：先分清楚"去重应该在哪一层做"

```
前端（防抖/节流）         → 防止用户手抖连点，治标
后端解析阶段（缓存）       → 同一文本不重复调 LLM，省钱
后端创建阶段（唯一性校验）  → 真正的数据去重，治本
```

**关键表态**：去重应该做在创建阶段，因为即使解析缓存命中了，也不代表用户一定创建了——他可能解析完觉得不对、没点确认就走了。

---

### 第二层：三种方案，按投入产出比排列

#### 方案一：创建时查重（推荐，投入最小）

```java
@Transactional
public InterviewScheduleDTO create(CreateInterviewRequest request) {
    // 检查是否已存在相同日程：同一公司 + 同一岗位 + 同一时间 = 重复
    List<InterviewScheduleEntity> existing = repository
        .findByCompanyNameAndPositionAndInterviewTime(
            request.getCompanyName(),
            request.getPosition(),
            request.getInterviewTime()
        );
    
    if (!existing.isEmpty()) {
        throw new BusinessException(
            ErrorCode.DUPLICATE_INTERVIEW_SCHEDULE,
            "该面试日程已存在，请勿重复创建"
        );
    }
    
    // 原有创建逻辑...
}
```

**为什么用这三个字段作为唯一键？** 同一家公司在同一时间面试同一个岗位，基本不可能是两场不同的面试。`(companyName, position, interviewTime)` 构成业务上的自然唯一键。

**追问**："为什么不用 id 做唯一键？"
回答：id 是数据库自增的，两次创建 id 肯定不同，无法用于去重判断。

---

#### 方案二：解析阶段加缓存（省钱，辅助方案）

```java
// 用 rawText 的 MD5 作为缓存 key
String cacheKey = DigestUtils.md5Hex(rawText);
CreateInterviewRequest cached = redisService.get(cacheKey);
if (cached != null) {
    return new ParseResponse(true, cached, 1.0, "cache", "命中缓存");
}

// 原有解析逻辑...
// 解析成功后写入缓存，过期时间 1 小时
redisService.set(cacheKey, result, Duration.ofHours(1));
```

**好处**：同一段文本不重复调 LLM，省 Token、省时间
**局限**：只防同一文本重复解析，防不了用户手动创建重复日程

---

#### 方案三：前端防抖（辅助，用户体验）

```typescript
// 解析按钮加 2 秒防抖
const handleParse = useMemo(() => debounce(async (text: string) => {
    const result = await interviewScheduleApi.parse({ rawText: text });
    // ...
}, 2000), []);
```

**好处**：防止用户手抖连点
**局限**：治标不治本，用户过两秒再点一次还是能发出去

---

### 第三层：综合推荐方案（三级防控）

```
前端防抖（2秒）
    │  防止手抖连点
    ▼
解析缓存（MD5 + Redis，1小时过期）
    │  防止同一文本重复调 LLM
    ▼
创建时唯一性校验（companyName + position + interviewTime）
    │  数据库层面的数据唯一性保证 ← 最后一道防线
    ▼
返回 BusinessException(Duplicate, "该日程已存在")
```

---

## 面试中的完整回答模板

> "当前代码没有做去重，如果同一段文本重复提交会产生两条相同的日程。我会在三个层面做防控：
>
> **第一层**，创建接口加上 `(companyName, position, interviewTime)` 三个字段的联合唯一性校验，已存在就抛 BusinessException。这是最后一道防线，保证数据库里不会有重复数据。
>
> **第二层**，解析阶段用 rawText 的 MD5 做 Redis 缓存，同一段文本一小时内不重复调 LLM，省 Token 也省时间。
>
> **第三层**，前端解析按钮加防抖，防止用户手抖连点。
>
> 三层里最重要的是创建阶段的唯一性校验，因为前两层只能减少重复，不能根除。"

## 面试官可能的追问及应对

| 追问 | 应对 |
|------|------|
| "万一是真的两场不同面试呢？" | 时间是精确到分钟的，同一公司同一岗位同一分钟有两场面试的概率极低。如果真的发生了，可以让用户手动改一下时间（比如 14:00 改成 14:01）再创建 |
| "为什么不加数据库唯一索引？" | 可以加，但 `interviewTime` 是 `LocalDateTime` 类型，不同时区可能导致误判。业务层校验更灵活，可以先查再抛异常 |
| "如果用户就是要创建两个呢？" | 返回的异常信息里提示"该日程已存在"，并附带已存在的日程 ID，前端可以直接跳转到已有日程的详情页 |
