# 面试日程模块：Controller 调用流程总览

本文是 `interviewschedule` 模块的阅读入口。后续文档按 Controller 方法拆解，并把前端事件、请求封装、Controller、Service、Repository、数据库、定时任务以及页面回显连成闭环。

---

## 1. 模块组成

| 层次 | 类/文件 | 作用 |
|---|---|---|
| 页面 | `InterviewSchedulePage.tsx` | 日历/列表展示，创建、编辑、删除和状态操作 |
| 表单 | `InterviewFormModal.tsx` | 粘贴邀约解析、手动编辑、提交表单 |
| Hook | `useInterviewSchedule.ts` | 管理日程 state，封装页面 CRUD 动作 |
| 前端 API | `api/interviewSchedule.ts` | 封装 7 类后端请求 |
| Controller | `InterviewScheduleController` | 路由、参数绑定、`@Valid` 和统一响应 |
| CRUD Service | `InterviewScheduleService` | Entity 转换、事务、查询分支和状态更新 |
| 解析 Service | `InterviewParseService` | 正则规则优先，失败后调用 LLM |
| Repository | `InterviewScheduleRepository` | JPA CRUD、状态/时间查询、批量状态更新 |
| 定时器 | `ScheduleStatusUpdater` | 每小时把过期 PENDING 日程改为 CANCELLED |
| 提醒服务 | `InterviewReminderService` | 生成/刷新/取消邮件和站内提醒计划 |
| 提醒调度 | `InterviewReminderScheduler` | 每分钟认领到期任务并写 Redis Stream |
| 邮件发送 | `SmtpReminderEmailSender` | 通过 JavaMailSender 发送真实 HTML 邮件 |
| 站内组件 | `ReminderBell.tsx` | 未读数、提醒列表和已读操作 |
| 数据表 | `interview_schedule` | 保存日程、状态和时间戳 |
| 提醒表 | `interview_reminder` | 保存渠道、时点、状态、重试和已读信息 |

模块基路径：

```text
/api/interview-schedule
```

## 2. Controller 的 7 个业务方法

状态接口同时接受 PATCH 和 PUT，所以从 HTTP 路由看共有 8 种请求方式。

| Controller 方法 | HTTP | 路径 | 作用 |
|---|---|---|---|
| `parse` | POST | `/parse` | 解析面试邀约，不写数据库 |
| `create` | POST | `/` | 新建日程，默认 PENDING |
| `getById` | GET | `/{id}` | 按主键查询 |
| `getAll` | GET | `/` | 时间范围、状态或全量查询 |
| `update` | PUT | `/{id}` | 更新日程业务字段，不改状态 |
| `delete` | DELETE | `/{id}` | 物理删除 |
| `updateStatus` | PATCH/PUT | `/{id}/status` | 更新状态 |

这些接口当前都没有 `@RateLimit`，与其他模块的 Controller 限流策略不同。

## 3. 通用 HTTP 返回闭环

成功流程：

```text
React 页面事件
  → interviewScheduleApi
  → frontend/src/api/request.ts
  → Spring MVC 参数绑定
  → InterviewScheduleController
  → Service
  → Repository/LLM
  → Controller Result.success(data)
  → HTTP 200 + {code: 200, message: "success", data: ...}
  → Axios 拦截器检查 code
  → 解包 data
  → Hook/Modal 更新 React state
```

业务异常流程：

```text
Service 抛 BusinessException
  → GlobalExceptionHandler
  → HTTP 200 + Result.error(code, message)
  → Axios 发现 code != 200
  → Promise reject Error(message)
  → 页面 catch 显示错误
```

这里必须同时区分外层 `Result.code` 和业务 DTO 内部的 `success`。例如邀约解析失败不会抛业务异常，而是返回：

```json
{
  "code": 200,
  "data": {
    "success": false,
    "data": null,
    "confidence": 0.0,
    "parseMethod": "none",
    "log": "解析失败"
  }
}
```

Axios 会正常 resolve，由弹窗检查内层 `success`。

## 4. 日程数据怎样进入数据库

```text
CreateInterviewRequest
  → BeanUtils.copyProperties(request, entity)
  → Service 强制 status=PENDING
  → repository.save(entity)
  → JPA INSERT interview_schedule
  → @PrePersist 填 createdAt、updatedAt
  → BeanUtils.copyProperties(entity, dto)
  → InterviewScheduleDTO 返回前端
```

主要字段：

```text
id                  数据库自增主键
companyName         公司，必填
position            岗位，必填
interviewTime       LocalDateTime，必填，无时区
interviewType       String，约定 ONSITE/VIDEO/PHONE
meetingLink         TEXT
roundNumber         默认 1
interviewer         面试官
notes               TEXT
status              PENDING/COMPLETED/CANCELLED/RESCHEDULED
createdAt/updatedAt JPA 生命周期维护
```

`CreateInterviewRequest` 只严格校验公司、岗位和时间。`interviewType` 是 String 而不是枚举，后端没有限制取值；`roundNumber` 也没有最小值校验。

## 5. 页面设计上的完整业务链

设计链路是：

```text
打开 /interview-schedule
  → useInterviewSchedule.fetchInterviews()
  → GET /api/interview-schedule
  → 日历/列表展示数据库记录

添加面试
  ├─ 粘贴邀约 → POST /parse → 结果回填表单
  └─ 手动输入
  → POST /api/interview-schedule
  → 创建后重新查询列表

编辑/拖动日历
  → PUT /api/interview-schedule/{id}
  → 更新后重新查询

完成/取消
  → PATCH /api/interview-schedule/{id}/status?status=...
  → 更新后重新查询

删除
  → DELETE /api/interview-schedule/{id}
  → 本地列表移除
```

## 6. 当前前端真实运行状态

日程 Hook 已导入 `interviewScheduleApi`，`fetchInterviews()` 会真实调用列表接口，不再使用硬编码演示数据：

```text
页面挂载/写操作完成
  → fetchInterviews(params)
  → interviewScheduleApi.getAll(params)
  → setInterviews(数据库返回值)
```

表单新增了 `reminderEnabled` 和 `reminderEmail`。布局中的 `ReminderBell` 每分钟查询站内未读数，打开时加载到期提醒，并提供单条/全部已读操作。

## 7. 查询分支的优先级

`getAll(status, start, end)` 不是组合查询，而是三选一：

```text
start != null 且 end != null
  → findByInterviewTimeBetween(start, end)
  → status 即使存在也被忽略

否则 status != null
  → InterviewStatus.valueOf(status)
  → findByStatus(status)

否则
  → findAll()
```

只传 start 或只传 end 时，单边时间参数被忽略。结果没有分页，也没有显式排序。

## 8. 状态管理与定时任务

手动状态接口：

```text
PATCH/PUT /{id}/status?status=COMPLETED
  → findById
  → entity.setStatus(status)
  → save
```

当前没有状态机校验，任何已有状态都能改为任意枚举状态，包括重新改回 PENDING。

自动状态链：

```text
App.java @EnableScheduling
  → 每小时整点触发 ScheduleStatusUpdater
  → 一条 JPQL UPDATE
  → status=PENDING 且 interviewTime<LocalDateTime.now()
  → status 改成 CANCELLED
```

该任务本身只做过期状态清理，但现在会同步取消这些日程尚未完成的邮件和站内提醒。真正的提醒派发由独立的 `InterviewReminderScheduler → Redis Stream → Consumer` 链路负责。

批量 JPQL UPDATE 绕过 Entity 的 `@PreUpdate`，所以自动取消不会同步刷新 `updatedAt`。

## 9. 事务边界

| 方法 | 事务 | 说明 |
|---|---|---|
| `parse` | 无 | 可能同步调用外部 LLM，不占数据库事务 |
| `create` | 有 | INSERT 与 DTO 转换在事务内 |
| `update` | 有 | 查询、覆盖、保存为一个事务 |
| `delete` | 有 | 物理删除 |
| `updateStatus` | 有 | 查询和状态保存 |
| `getById/getAll` | 无显式事务 | Repository 自身负责查询调用 |
| `updateExpiredInterviews` | 有 | 一条批量 UPDATE |

解析接口遵守“事务中不调用外部 API”的原则：它没有数据库事务。
