# 前端页面交互与站内提醒闭环

## 1. 日程页面数据源

`useInterviewSchedule` 已接入真实 API：

```text
页面挂载
  → fetchInterviews(params)
  → GET /api/interview-schedule
  → setInterviews(数据库列表)
```

创建、更新、状态变更成功后都会重新查询；删除成功后使用函数式 state 更新移除本地记录。

## 2. 提醒配置表单

`InterviewFormModal` 新增：

```text
reminderEnabled：是否生成提醒计划，默认 true
reminderEmail：邮件收件地址，可选
```

提醒开启时会展示邮箱输入框。不填写邮箱仍会创建站内提醒；填写合法邮箱后同时创建邮件提醒。

表单随 create/update 请求提交，后端 `@Email` 再做一次格式校验。

## 3. 站内提醒铃

`Layout` 顶部挂载 `ReminderBell`：

```text
组件挂载
  → GET /reminders/unread-count
  → 每 60 秒刷新一次未读数字

点击铃铛
  → GET /reminders/in-app
  → 展示已经到 remindAt 的提醒

点击提醒
  → PATCH /reminders/{id}/read
  → 跳转 /interview-schedule

点击全部已读
  → PATCH /reminders/read-all
```

未读提醒显示红色数量角标和蓝色圆点。

## 4. 站内提醒为什么无需开启邮件派发

提醒计划在日程事务中直接写入数据库。站内查询按：

```text
channel=IN_APP
remindAt <= 当前时间
status 不为 CANCELLED/FAILED
```

筛选，因此即使 `dispatch-enabled=false`，到期站内提醒仍可被前端查询和标记已读。

开启自动派发后，站内提醒也会经过 Redis Stream，把状态从 PENDING 推进到 SENT；这不影响其展示条件。

## 5. 邮件与站内提醒的共同计划

每个启用提醒的 PENDING 日程生成：

```text
DAY_BEFORE  → 面试前 24 小时
HOUR_BEFORE → 面试前 60 分钟
```

对应任务数量：

```text
未填邮箱：2 条 IN_APP
填写邮箱：2 条 IN_APP + 2 条 EMAIL
```

如果计算出的提醒时间已经过去，但面试仍为 PENDING，提醒时间调整为当前时间，使其可以立即进入展示/派发链。

## 6. 日程变更联动

```text
创建/修改 PENDING 日程
  → synchronizeReminders
  → 更新提醒时间、文案和收件人

关闭提醒
  → 取消 PENDING/QUEUED/PROCESSING 提醒

COMPLETED/CANCELLED/RESCHEDULED
  → 取消活动提醒

重新设为 PENDING
  → 恢复提醒计划

删除日程
  → 先取消提醒，再删除日程
```

修改面试时间或邮箱会重置对应任务为 PENDING，并清除旧的发送/已读状态，允许按新计划重新提醒。

## 7. 当前用户边界

项目尚未接入登录用户，日程和站内提醒都没有 `userId`。因此当前提醒铃展示系统内全部到期站内提醒。

接入用户体系后，需要在 `interview_schedule` 和 `interview_reminder` 增加用户字段，并让所有查询按当前用户过滤。

## 8. 完整前端闭环

```text
日程表单保存提醒配置
  → 后端创建提醒计划
  → 到达提醒时间
  → ReminderBell 轮询到未读数量
  → 用户打开提醒列表
  → 查看提醒并标记已读
  → 跳转日程页查看公司、岗位、时间和会议链接
```
