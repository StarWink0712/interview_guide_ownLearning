# 配置、可观测性、测试与生产边界

## 1. 模块基础讲解

语音面试模块的复杂度不只在实时语音链路，还在于它依赖很多运行时参数：ASR 模型、TTS 模型、音频采样率、阶段时长、LLM 流式推送、TTS 并发、开场问题模板、评估任务状态、WebSocket 超时等。这个模块把大部分配置集中在 `VoiceInterviewProperties` 和 `application.yml` 中，再通过服务层和 Handler 消费这些配置。

配置可以分成几类：

- 面试阶段配置：`intro`、`tech`、`project`、`hr` 四个阶段都有最小时长、建议时长、最大时长、最小题数和最大题数。
- ASR 配置：DashScope realtime WebSocket 地址、`qwen3-asr-flash-realtime` 模型、API Key、语言、PCM 格式、16kHz 采样率、服务端 VAD。
- TTS 配置：`qwen3-tts-flash-realtime` 模型、`Cherry` 音色、PCM 输出、24kHz 采样率、commit 模式、语速和音量。
- LLM 流式配置：`llmStreamingEnabled` 控制是否流式下发，`aiStreamPushIntervalMs` 和 `aiStreamMinCharsDelta` 控制前端文本刷新频率，`aiQuestionMaxChars` 控制面试官单轮回复长度。
- TTS 并发配置：`maxConcurrentTtsPerSession` 控制每个会话同时进行的 TTS 请求数，`chunkedAudioEnabled` 控制是否逐句推送音频。
- 开场问题配置：`voice-interview-opening.yml` 按 skillId 配置不同方向的第一问，例如 Java 后端、字节后端、算法、前端、系统设计、AI Agent 等。
- 限流和音频规格配置：`rate-limit` 与 `audio` 配置描述了消息频率、IP 并发、全局并发、音频格式、采样率、分片时长等意图。

配置设计的优点是集中化和可调参。面试中可以强调：实时语音模块的延迟、稳定性和成本高度依赖参数，不能把模型名、采样率、超时时间、并发数散落在业务代码里。通过 `@ConfigurationProperties(prefix = "app.voice-interview")` 可以让配置项有类型、有默认值，也便于不同环境覆盖。

这个模块也有比较清晰的可观测性埋点。`VoiceMetricsRecorder` 基于 Micrometer 的 `MeterRegistry` 封装了 Timer 和 Counter，并且支持 MeterRegistry 不存在时静默降级。`VoiceInterviewWebSocketHandler` 已经记录了多个关键指标：

- `app.voice.interview.asr.final_segments`：ASR 最终片段数。
- `app.voice.interview.asr.merge_wait`：用户语音合并等待耗时。
- `app.voice.interview.llm.first_token_latency`：LLM 首 token 延迟。
- `app.voice.interview.llm.duration`：LLM 完整回复耗时。
- `app.voice.interview.llm.calls`：LLM 调用次数，并带 streaming 标签。
- `app.voice.interview.tts.duration`：TTS 合成耗时。
- `app.voice.interview.tts.empty_audio`：TTS 空音频次数。
- `app.voice.interview.turn.duration`：一轮用户回答到 AI 回复结束的总耗时。
- `app.voice.interview.turn.completed`：成功或失败的 turn 数量。
- `app.voice.interview.errors`：turn 级异常计数。

这些指标可以支撑面试官追问的生产问题：为什么用户觉得卡顿、到底卡在 ASR 还是 LLM 还是 TTS、哪类失败最多、是否某个 provider 性能退化。监控侧的 `BusinessMetricsQueryService` 也会读取 `app.voice.interview.turn.duration`，把语音面试平均轮次延迟纳入业务指标摘要。

测试方面，当前已有可运行的底层单元测试：

- `QwenAsrServiceTest`：覆盖初始化、会话开始/停止、多会话、无会话发送音频异常、partial transcript 提取、配置 reload。
- `QwenTtsServiceTest`：覆盖初始化、空文本返回空数组、销毁、配置 reload。
- `VoiceInterviewSessionStatusTest`：覆盖会话状态枚举数量和名称。

同时也要诚实说明：`VoiceInterviewServiceTest`、`VoiceInterviewServicePauseTest`、`DashscopeLlmServiceTest`、`VoiceInterviewPromptServiceTest` 目前是 `@Disabled` 待重写状态；集成测试文件存在，但命名和注释也体现出还处于待修复状态。也就是说，核心实时 Handler、会话生命周期、LLM 提示词和端到端 WebSocket 还缺有效自动化测试。

当前代码的生产边界也很明显：

- `application.yml` 中有 `user-utterance-debounce-ms`、`min-silence-before-commit-ms`、`min-commit-chars`、`max-wait-for-continuation-ms`，但 `VoiceInterviewProperties` 没有完整字段，Handler 也没有完整使用这些配置做自动提交。
- `rate-limit` 配置存在，但没有看到 WebSocket 握手限流、消息频率限流、IP 并发限流的实际接入。
- `RateLimitConfig`、废弃的 `AliyunConfig.SttConfig` 和 `TtsConfig` 没有 Lombok `@Data`，配置绑定能力不如其他配置类完整。
- `app.voice-interview.tts.default-voice` 在配置文件中存在，但当前主路径实际使用的是 `qwen.tts.voice`。
- `buildSessionResponse` 固定返回 `ws://localhost:8080/ws/voice-interview/{id}`，生产部署需要改成外部化 `wss` 地址。
- WebSocket 连接状态、SessionState、openingAudioCache 都是单机内存结构，多实例部署要考虑粘性会话或外部状态。

面试时不要把这些缺口包装成已经完成的能力。更好的表达是：当前代码已经具备实时语音闭环和基础指标，但生产化还需要补齐配置绑定、真实限流、端到端测试、分布式运行和告警体系。

## 2. 基础面试问题

问题：为什么语音面试模块需要单独的配置类？

回答：因为它依赖大量可变参数，包括 ASR/TTS 模型、API Key、采样率、VAD 静音阈值、阶段时长、LLM 流式推送、TTS 并发数等。如果写死在代码里，调延迟、调成本和换模型都会很困难。集中到 `VoiceInterviewProperties` 后，可以按环境覆盖，也便于启动时校验。

问题：`voice-interview-opening.yml` 的作用是什么？

回答：它把不同岗位方向的开场问题从代码中抽离出来。比如 Java 后端会问项目业务链路，字节后端偏算法与数据结构，AI Agent 方向会问 Agent 架构。这样新增岗位模板时优先改配置，而不是改 Handler 代码。

问题：语音面试模块有哪些关键指标？

回答：最核心的是一轮总耗时 `turn.duration`，然后拆成 LLM 首 token 延迟、LLM 完整生成耗时、TTS 合成耗时、ASR final 片段数、TTS 空音频次数和 turn 失败次数。它们能判断用户卡顿具体发生在哪一段。

问题：`VoiceMetricsRecorder` 为什么要可选注入 `MeterRegistry`？

回答：这样在没有完整监控依赖或测试环境中不会影响业务启动。指标记录失败不应该阻断面试流程，所以 recorder 对 `meterRegistry == null` 做静默跳过。

问题：当前有哪些测试已经覆盖？

回答：ASR 服务、TTS 服务和会话状态枚举有基础单元测试，覆盖初始化、配置 reload、空文本、会话开始停止、异常发送等场景。它们主要验证底层服务对象行为，不覆盖真实 DashScope 网络链路。

问题：哪些测试还不充分？

回答：会话服务、暂停恢复、提示词、LLM 服务和端到端 WebSocket 测试目前存在待重写或待修复状态。核心 Handler 的并发、断连、回声控制、TTS 分块和评估入队都缺自动化验证。

问题：为什么要记录 LLM 首 token 延迟？

回答：语音产品的体验不只看总耗时，还看用户多久看到 AI 开始响应。首 token 延迟能衡量“等待感”，完整生成耗时衡量“总处理时间”，两者定位的问题不同。

问题：为什么 TTS 空音频要单独计数？

回答：TTS 空音频会造成“前端有文字但没有声音”的体验问题。它不是普通异常，因为请求可能成功返回但音频为空，所以要单独记录，便于发现模型、音色、超时或文本格式问题。

## 3. 进阶面试问题

问题：如何判断语音面试卡顿是 ASR、LLM 还是 TTS 引起的？

回答：看分段指标。ASR 可以看 final segment 到 flush 的等待时间；LLM 看 first token latency 和 llm.duration；TTS 看 tts.duration 和 empty_audio；turn.duration 是总耗时。如果 turn 高但 LLM/TTS 都正常，可能是前端 submit、WebSocket 发送缓冲或 ASR 合并等待导致。

问题：当前的配置绑定有什么隐患？

回答：`application.yml` 中有部分配置项没有在 `VoiceInterviewProperties` 中对应字段，比如自动提交相关配置；部分内部配置类缺少 `@Data`，JavaBean getter/setter 不完整。结果是配置文件看起来支持某能力，但运行时可能没有绑定或没有被使用。

问题：生产环境为什么不能固定返回 `ws://localhost:8080`？

回答：生产环境通常经过域名、HTTPS 网关、负载均衡和路径转发，浏览器页面在 HTTPS 下也需要 `wss`，否则会被混合内容策略拦截。WebSocket URL 应该从配置读取外部地址，或由前端根据当前 origin 拼接。

问题：为什么指标标签不能随意加 sessionId？

回答：Micrometer/Prometheus 的标签维度如果带高基数字段，比如 sessionId、userId，会导致时间序列爆炸，内存和存储成本急剧上升。生产指标应使用低基数标签，如 status、stage、provider、streaming、error_type。

问题：多实例部署时当前内存状态会有什么问题？

回答：`sessions`、`sessionStates`、`lastActivityTime`、`openingAudioCache` 都在单实例内存中。若 WebSocket 连接被负载均衡到不同实例，后续控制消息或超时检测可能找不到状态。需要粘性会话，或把运行时状态改成 Redis/集中式状态，并把 WebSocket 路由固定到同一节点。

问题：如何给 WebSocket 增加限流？

回答：握手阶段按 IP、用户、全局连接数做连接级限流；消息阶段按 session 做音频消息频率和大小限制；AI 阶段按 provider 做 LLM/TTS 并发限流。可以复用 Redis Lua 滑动窗口，也可以使用网关连接数限制加应用内细粒度限流。

问题：如何设计语音面试告警？

回答：至少包括 turn 失败率、平均 turn 延迟、P95/P99 turn 延迟、LLM 首 token P95、TTS 空音频率、ASR 重连次数、WebSocket 异常关闭次数、评估任务失败率。告警要按 provider 和 stage 分组，避免只看到总体平均值。

问题：为什么只靠日志不够？

回答：日志适合定位单个 session 的异常，指标适合发现整体趋势和告警。例如某个时段 TTS 延迟上升，不可能靠人工翻日志发现；而指标能直接看到 P95 上升，再用日志按 sessionId 追踪个案。

## 4. 技术延伸问题

问题：如果不用 Micrometer，还能怎么做可观测性？

回答：可以直接接入 OpenTelemetry Metrics/Tracing，把 ASR、LLM、TTS、Redis Stream 作为 span；也可以使用日志采样加 ClickHouse/ELK 做离线分析。Micrometer 更适合 Spring Boot 应用内指标，OpenTelemetry 更适合跨服务链路追踪。

问题：语音模块如何和链路追踪结合？

回答：HTTP 创建会话时生成 traceId，WebSocket 握手时带上 traceId 或 sessionId，ASR/LLM/TTS 调用都写入同一上下文。日志中带 traceId，指标中只带低基数标签，详细的 session 级事件写入数据库或日志系统。

问题：配置热更新可以怎么做？

回答：简单方案是重启生效；进阶方案是把 provider、TTS 音色、VAD 阈值、回复长度等放到可写配置中心，服务层提供 reload 方法。当前 ASR/TTS 服务已有 `reload` 测试思路，但需要配合配置源、权限控制和灰度发布。

问题：如何验证语音链路的端到端质量？

回答：准备标准音频样本，走 WebSocket 发送 PCM，断言 ASR 字幕、LLM 回复、TTS 音频格式、消息持久化和评估入队。还要模拟断网、ASR 重连、TTS 超时、WebSocket 关闭、重复提交等异常。

问题：如果要做压测，关注哪些指标？

回答：关注并发 WebSocket 连接数、音频消息吞吐、ASR 上游连接数、LLM 并发、TTS 并发、Redis Stream 积压、DB 写入延迟、虚拟线程数量、堆内存和直接内存。压测不能只测 HTTP 创建会话，因为核心瓶颈在实时通话链路。

问题：如何使用其他技术方案实现同样监控能力？

回答：Spring Boot 可以用 Actuator + Micrometer + Prometheus；云原生可以用 OpenTelemetry Collector + Grafana Tempo/Prometheus；日志分析可以用 ELK/ClickHouse；实时业务看板可以把 turn 事件写入 Kafka，再用 Flink 聚合。

问题：如何做成本观测？

回答：每轮记录 ASR 音频时长、LLM token 输入输出、TTS 字符数、provider、模型、成功状态。再按 provider 单价计算 session 成本，形成“平均每场面试成本”和“失败浪费成本”。

问题：如何做质量观测？

回答：除性能指标外，还要记录 ASR 置信度、用户重复提交率、AI 问题重复率、无效回答率、评估生成失败率、用户中途退出率。语音面试的质量不是单纯延迟低，还包括问题是否自然、追问是否贴合、评估是否可信。

## 5. 改进方案问题

问题：配置层第一优先级应该改什么？

回答：先让配置文件和 `VoiceInterviewProperties` 完全对齐。补齐 `userUtteranceDebounceMs`、`minSilenceBeforeCommitMs`、`minCommitChars`、`maxWaitForContinuationMs`、默认 WebSocket 外部地址、TTS 默认音色等字段，并给内部配置类加 `@Data` 或显式 getter/setter。

问题：限流配置如何真正落地？

回答：把 `rate-limit` 接入 WebSocket 握手和消息处理。握手时用 Redis 记录 IP 和用户并发连接数；消息处理时限制每秒音频消息数和单条消息大小；调用 AI 前用信号量或 Redis 令牌桶限制 LLM/TTS 并发。

问题：可观测性还可以补哪些指标？

回答：补 ASR 重连次数、ASR appendAudio 失败次数、WebSocket close code 分布、打开连接数 Gauge、当前 processing 会话数 Gauge、评估任务等待时间、评估任务处理耗时、AI provider 错误码、TTS 单句字符数分布。

问题：日志如何改得更适合排障？

回答：统一把 sessionId、provider、phase、turnIndex、traceId 放进结构化日志。异常日志保留堆栈，用户可见错误只返回友好文案。对高频音频包日志降级到 trace，避免生产日志过量。

问题：测试体系如何补齐？

回答：第一层补 Service 单元测试，覆盖创建、暂停、恢复、结束、评估入队和缓存失效。第二层补 Handler 单元测试，用 mock WebSocketSession、mock ASR/LLM/TTS 验证消息流。第三层补端到端集成测试，用本地 fake ASR/LLM/TTS 服务模拟完整通话。

问题：如何验证配置绑定没有漂移？

回答：加一个 `@SpringBootTest` 或 `ApplicationContextRunner` 测试，加载 `application.yml` 和 `voice-interview-opening.yml`，断言关键字段都成功绑定。还可以用 `@ConfigurationPropertiesScan` 元数据或启动校验发现未知字段。

问题：生产告警阈值怎么设？

回答：初期用相对阈值更稳：比如 turn.duration P95 超过基线 2 倍、TTS empty_audio 连续 5 分钟高于 1%、LLM 调用失败率高于 5%、评估任务失败率高于 3%。上线稳定后再设绝对阈值。

问题：如何让面试回答更有说服力？

回答：不要只说“我们做了监控”，要讲出闭环：埋点记录 ASR/LLM/TTS/turn 指标，业务看板展示平均轮次延迟，告警发现 P95 异常，日志用 sessionId 定位单场面试，最后根据 provider、stage、error_type 判断是上游故障、网络问题还是代码问题。

## 6. 故障处理问题

问题：启动时报 ASR API Key 未配置怎么办？

回答：检查 `.env` 或环境变量 `AI_BAILIAN_API_KEY`，再确认 `app.voice-interview.qwen.asr.api-key` 和 `app.voice-interview.qwen.tts.api-key` 是否正确引用。ASR/TTS 服务初始化时会读取这些配置，未配置会导致启动或调用失败。

问题：修改 `application.yml` 后配置没有生效怎么办？

回答：先确认字段在 `VoiceInterviewProperties` 中是否存在 getter/setter，再确认缩进和前缀是否是 `app.voice-interview`。如果是 `user-utterance-debounce-ms` 这类当前未完整建模的字段，需要先补 Java 配置字段，否则不会被业务代码使用。

问题：线上用户反馈“响应越来越慢”怎么排查？

回答：先看 `turn.duration` 的 P95 是否升高，再拆 LLM、TTS、ASR merge wait。若 LLM 首 token 高，查 provider；若 TTS 高或 empty_audio 上升，查 TTS 服务；若 WebSocket close 多，查网关超时和发送缓冲；若只有部分用户慢，查网络和客户端音频包大小。

问题：业务看板语音平均延迟一直是 0 怎么办？

回答：检查 Micrometer `MeterRegistry` 是否存在，Handler 是否真正调用了 `recordTimerSinceNanos("app.voice.interview.turn.duration", ...)`，以及是否至少完成过一轮 turn。如果没有完整走到 LLM/TTS 结束，turn 指标不会记录成功。

问题：日志太多导致排查困难怎么办？

回答：把音频包级别日志放到 trace 或 debug，只在关键生命周期记录 info，比如连接建立、ASR 重连、LLM 开始和结束、TTS 空音频、评估入队。排障时按 sessionId 或 traceId 过滤，不要依赖全文搜索。

问题：TTS 空音频告警触发怎么办？

回答：先看是否所有 provider 都失败，还是特定 voice/model 失败。检查文本是否为空或过长、API Key 是否有效、TTS 30 秒超时、DashScope 错误码和返回事件。短期可降级为只显示文字，长期要加重试和 provider fallback。

问题：WebSocket 频繁断开怎么办？

回答：检查前端心跳、网关 idle timeout、服务端 10 秒发送超时、512KB 缓冲区、消息大小限制、移动网络抖动。若断开发生在 AI 音频发送阶段，重点看 WAV 大小和前端播放处理。

问题：为什么配置里有限流但系统还是可能被打满？

回答：因为配置只是声明意图，必须有代码在握手、消息处理和 AI 调用前读取并执行限制。当前语音模块还没有看到完整限流接入，因此生产环境需要补这一层，否则高并发会打满 ASR/TTS/LLM 和 WebSocket 资源。
