# 完整流程总结

## 从创建会话到评估完成的完整旅程

一次完整的语音面试从用户在前端配置面试模板（技能方向、难度、四个阶段开关）并点击"开始面试"开始。前端调用 `POST /api/voice-interview/sessions` 经由 `VoiceInterviewController` 委托 `VoiceInterviewService.createSession()` 创建会话实体——处理 skillId/difficulty/llmProvider 等字段的默认值、通过 `determineFirstPhase()` 按优先级检查阶段开关确定首个面试阶段、使用 Lombok Builder 构建 `VoiceInterviewSessionEntity` 并通过 JPA `save()` 写入 PostgreSQL 获取自增 Long 型 ID、调用 `cacheSession()` 将完整实体写入 Redis（Key: `voice:interview:session:{id}`，TTL 1 小时）、最后通过 `buildSessionResponse()` 构建包含 `sessionId` 和 `webSocketUrl`（`ws://localhost:8080/ws/voice-interview/{id}`）的 `SessionResponseDTO` 返回前端。至此 Controller 的 HTTP 层面职责彻底结束——它不参与任何实时通信。

前端拿到 URL 后调用 `new WebSocket(webSocketUrl)` 发起 HTTP Upgrade 握手。这个请求绕过 DispatcherServlet 直接由 Spring WebSocket 框架根据 `WebSocketConfig` 的路由规则（`/ws/voice-interview/{sessionId}`）匹配到 `VoiceInterviewWebSocketHandler`。框架完成协议升级后调用 `afterConnectionEstablished()`，Handler 同步完成六门初始化：从 URI 提取 sessionId；设置消息大小限制（256KB，可容纳约 6 秒 Base64 PCM 音频）；创建 `ConcurrentWebSocketSessionDecorator` 并发安全装饰器（10 秒发送超时、512KB 缓冲区）；将 WebSocket 会话存入三个 `ConcurrentHashMap`（`sessions` 存会话引用、`sessionStates` 存 `SessionState` 运行时状态、`lastActivityTime` 存活动时间戳供超时检测）；调用 `startDashScopeStt()` 启动第二条约 ASR 语音识别 WebSocket——后端到阿里云 DashScope 的独立连接，配置中文识别、16kHz 采样率、PCM 格式、服务端 VAD（400ms 静默断句），设置 onFinal 回调（追加文本到合并缓冲区）、onPartial 回调（实时字幕推送）、onError 回调（前端错误通知）和 onClose 的 `AtomicReference` 引用比较机制（防止重连场景下旧连接延迟 onClose 误删新连接——「第三轮起无声」的根因）；在虚拟线程中异步触发起始开场白与第一个提问——通过 `triggerOpeningQuestionIfNeeded()` 检查对话历史无历史消息后，按 skillId 从配置的 `skillQuestions` Map 查找专属模板或选择算法/后端默认模板，先推送文本让前端立即显示再保存消息到数据库，最后从应用启动时 `@PostConstruct warmupOpeningAudioCache()` 预热的 TTS 缓存获取 WAV 音频推送，确保首次用户体验流畅无 TTS 等待延迟。

用户开始说话后，浏览器持续采集麦克风 PCM 音频（16kHz 16bit 单声道），Base64 编码后通过 WebSocket 的 `{"type":"audio","data":"..."}` 消息发送到后端。Handler 的 `handleTextMessage()` 解析 JSON 获取 type 字段并分发——`audio` 类型进入 `handleUserAudio()`，方法首先检查 `isAiSpeakingOrCooldown()`：AI 的 TTS 音频正在播放（`aiSpeaking=true`）或播放结束后的 800ms 冷却期内直接丢弃麦克风输入，防止 AI 音频经扬声器→麦克风→ASR→LLM→TTS 形成无限回声循环。通过检测后将 Base64 解码为 PCM 字节数组，调用 `QwenAsrService.sendAudio()` 通过 `OmniRealtimeConversation.appendAudio()` 发送到 DashScope。ASR 识别过程中部分结果通过 `handleSttResult(isFinal=false)` 转换为 `{"type":"subtitle","text":"...","isFinal":false}` 字幕推送，最终定稿（VAD 400ms 静默断句）通过 `handleSttResult(isFinal=true)` 追加到 `SessionState` 的 `mergeBuffer`（`AtomicReference<String>` 原子累积拼接），同时推送 `isFinal:true` 字幕。ASR 连接异常断开时，`handleUserAudio()` 捕获 `IllegalStateException` 后通过 `shouldRecoverAsrConnection()` 判断是否可恢复，可恢复则调用 `restartDashScopeStt()` 执行重连（同一把会话锁保护下 `stopTranscription` + 200ms 等待 + `startTranscriptionLocked` + 10 次轮询验证），重连后重试发送音频（最多 15 次，每次 80ms）。

用户确认 ASR 识别文本无误后点击"提交"按钮，前端发送 `{"type":"control","action":"submit"}`。Handler 的 `handleControl()` 分发到 `flushMergedUtteranceToLlm()`——首先用 `AtomicBoolean.compareAndSet(false, true)` 做 CAS 锁防止并发触发（失败则通过 `utteranceMergeScheduler` 排期 400ms 重试），然后调用 `takeMergeBufferAndClear()` 原子取出合并缓冲区的全部累积文本，提交到虚拟线程池 `voicePipelineExecutor` 执行阻塞的 LLM+TTS 管线（同时 `setProcessingThread` 保存线程引用供断连时中断）。

`triggerLlmResponse()` 设置 `aiSpeaking=true` 封锁麦克风，通过 `getSessionEntity()` 查询会话实体（优先 Redis 缓存再查数据库）和 `getHistory()` 从 `voice_interview_messages` 表查询对话历史（格式化为"候选人：xxx"/"面试官：xxx"列表），调用 `DashscopeLlmService.chatStreamSentences()` 流式生成 LLM 回复——`onPartialToken` 回调每收到一个 token 通过 `sendTextMessage` 实时推送到前端实现打字机效果，`onSentenceComplete` 回调每检测到一个完整句子通过 `CompletableFuture.supplyAsync` 在虚拟线程池中并行启动 TTS 合成（`Semaphore` 控制每会话并发上限）。至此本系统的核心创新"句子级并发 TTS"发挥作用——LLM 生成第一句话后立即启动 TTS 合成第一句话，同时 LLM 继续生成第二句话，LLM 生成和 TTS 合成在时间上重叠，首音频延迟从"LLM 全部生成 + 全部 TTS 合成"降为 max(首个句子生成时间, 首个句子 TTS 时间)。

每个句子的 TTS 合成通过 `QwenTtsService.synthesize(sentence)` 执行七阶段管线：先用构造时从 `VoiceInterviewProperties` 读取并缓存到成员变量的 model 和 apiKey 构建 `QwenTtsRealtimeParam` 连接参数，创建 `QwenTtsRealtimeCallback` 回调（onEvent 委托 `handleServerEvent` 按 type 分发处理：`session.created` 记录会话 ID、`session.updated` 确认配置生效、`response.audio.delta` 将 Base64 音频分片解码后追加到 `ByteArrayContainer`、`response.done` 执行 `countDown` 解除主线程阻塞），onClose 中也执行 `countDown` 兜底防止 WebSocket 异常断开时未收到 `response.done` 导致死锁。通过 `QwenTtsRealtime.connect()` 同步建立到 DashScope 的第三条独立 WebSocket 连接（临时连接，用完即关，与 ASR 的持久连接不同）。连接成功后 `updateSession()` 下发合成配置——24kHz PCM 单声道、预置音色、1.0 倍语速和音量、"commit" 模式（一次性提交文本完整合成，区别于流式实时模式）。配置生效后 `appendText(text)` 发送文本并 `commit()` 告知服务端开始合成，服务端逐个 `response.audio.delta` 事件推送音频分片，每个分片在 `handleServerEvent` 中 Base64 解码后累积到 `ByteArrayContainer`，最后 `response.done` 事件触发 `countDown()` 解除 `synthesisLatch.await(30s)` 阻塞。主线程苏醒后通过 `audioContainer.toByteArray()` 获取合并后的完整 PCM 音频数据，在 `finally` 块中 `qwenTtsRealtime.close()` 关闭 WebSocket 释放资源。注意此时主线程运行在虚拟线程上，`await()` 阻塞时 JVM 将平台线程释放给其他虚拟线程，不消耗 OS 线程资源——这是 Java 21 虚拟线程在 IO 密集型场景的核心优势。

所有 TTS 结果收集后，分块模式通过 `sendAudioChunk` 逐句推送 `{"type":"audio_chunk","data":"Base64 WAV","index":0,"isLast":false}` 消息（适合长回复，用户无需等全部合成完就能听到第一句），合并模式通过 `System.arraycopy` 将各句 PCM 合并为一个完整 WAV 通过 `sendAudio` 推送 `{"type":"audio","data":"Base64 WAV","text":"原文"}`。管线完成后设置 `aiSpeaking=false` 和 800ms 冷却期（CD 结束后 AI 不再说话时麦克风输入窗口重新打开），记录整轮对话耗时指标。出现任何异常时 catch 块中必设置 `aiSpeaking=false` 防止麦克风永久封锁，`flushMergedUtteranceToLlm()` 的 finally 块中必设置 `processing=false` 释放 CAS 锁防止后续提交永久阻塞。所有 TTS 异常均返回空数组而非抛异常——保证单个句子的合成失败不影响整个面试流程，用户最多丢失一句音频而非整个 AI 回复。

面试进行中，用户可通过 REST API 主动暂停（`PUT /pause`，校验状态必须为 `IN_PROGRESS`，设置 `PAUSED` 并记录 `pausedAt` 时间，清除 Redis 缓存确保后续查询获取最新状态）和恢复（`PUT /resume`，校验状态必须为 `PAUSED`，设置 `IN_PROGRESS` 并记录 `resumedAt` 时间，重新写入 Redis 缓存，返回新 WebSocket URL 供前端重连）。Handler 内置 `@Scheduled(fixedRate=30000)` 定时检测——遍历 `lastActivityTime` Map，4 分 30 秒无活动发送 30 秒警告消息，5 分钟无活动自动暂停（发送通知、调用 `pauseSession("timeout")` 更新 DB、停止 ASR 释放 DashScope 连接、关闭 WebSocket 并清理内存 Map）。

用户结束面试时，通过前端按钮调用 HTTP `POST /end` 接口或 WebSocket 控制消息 `{"type":"control","action":"end_interview"}` 触发结束流程。`VoiceInterviewService.endSession()` 在 `@Transactional` 保护下设置 `endTime`、`phase=COMPLETED`、`status=COMPLETED`，通过 `Duration.between(startTime, now).toSeconds()` 计算实际时长，设置 `evaluateStatus=PENDING`，保存 DB 并清除 Redis 缓存，最后调用 `voiceEvaluateStreamProducer.sendEvaluateTask()` 将会话 ID 通过 Redis Stream `XADD` 入队。如果 WebSocket 异常断开，Spring WebSocket 框架回调 `afterConnectionClosed()`——依次清除三个 Map、调用 `t.interrupt()` 中断正在执行的 LLM 虚拟线程、调用 `sttService.stopTranscription()` 停止 ASR 释放连接、最后调用 `endSessionIfInProgress()` 兜底结束。`endSessionIfInProgress()` 的幂等保护从 DB 查询实体，仅当 `status==IN_PROGRESS` 时才执行结束操作——防止正常结束后 WebSocket Close 帧的重复触发。

后台 `VoiceEvaluateStreamConsumer` 轮询消费 Redis Stream，调用 `VoiceInterviewEvaluationService.generateEvaluation()` 执行评估——从 `voice_interview_messages` 表按 `sequence_num ASC` 查询所有消息，通过 `buildQaRecords()` 构建 QaRecord 列表（AI 提问 → 用户回答配对，通过 `inferCategory()` 从 AI 文本关键词推断分类：技术问题/项目深挖/自我介绍/HR问题/综合），无消息时调用 `saveEmptyEvaluationTransactional()` 保存兜底空评估（总分 0、"暂无评估内容"），非空时通过 `LlmProviderRegistry` 获取 ChatClient、`buildEvaluationReferenceSectionSafe()` 构建技能参考上下文，调用 `UnifiedEvaluationService.evaluate()` 进行 LLM 评估（⚠️ 在 `@Transactional` 外部执行，避免长时间占用数据库连接），评估结果通过 `saveEvaluationTransactional()` 持久化到 `voice_interview_evaluations` 表的四个 JSON 字段（`questionEvaluationsJson`、`strengthsJson`、`improvementsJson`、`referenceAnswersJson`）。消费者失败时最多重试 3 次，超过后标记 `evaluateStatus=FAILED`。

前端面试结束后跳转到评估等待页面，以固定间隔轮询 `GET /evaluation`——Controller 从会话实体读取 `evaluateStatus`，PENDING 显示"排队中"、PROCESSING 显示"AI 正在评估"、COMPLETED 时额外调用 `evaluationService.getEvaluation()` 从 `voice_interview_evaluations` 表反序列化完整评估详情（包含 `overallScore` 总分、`overallFeedback` 总评、`strengths` 优势列表、`improvements` 改进建议、`answers` 逐题评分与反馈和参考答案及关键点），构建 `VoiceEvaluationDetailDTO` 返回前端。前端停止轮询，渲染评估面板——总分圆环、分类得分、优劣势卡片、逐题评估折叠面板和参考答案。如果自动评估超时或失败，可通过 `POST /evaluation` 手动触发——三级判断：COMPLETED 直接返回缓存结果（幂等保护）、PENDING/PROCESSING 返回当前状态（不重复入队）、FAILED 或 null 调用 `triggerEvaluation()` 重新入队。

至此，一轮完整的语音面试结束——从 HTTP 创建会话到 WebSocket 实时语音对话再到 LLM 异步评估和前端渲染评估报告，整个流程涉及三条独立 WebSocket 连接（前端-后端双向通道、后端-DashScope ASR 持久连接、后端-DashScope TTS 临时连接）、三个 AI 服务（ASR 语音识别、LLM 对话生成、TTS 语音合成——其中 TTS 采用句子级并发合成，LLM 仍在流式生成后续句子时已完成的句子即开始 TTS，将首音频延迟从串行等待降为并行重叠）、两种通信协议（HTTP REST 和 WebSocket）、四种并发控制机制（`synchronized` 会话锁、`AtomicBoolean.CAS` 锁、`Semaphore` TTS 并发控制、虚拟线程池 `voicePipelineExecutor`）、五层状态管理（`VoiceInterviewSessionStatus` 会话状态、`AsyncTaskStatus` 评估状态、`SessionState` 运行时内存状态（含 `aiSpeaking` 封锁标记、`mergeBuffer` 识别文本累积、`isProcessing` CAS 锁、`processingThread` 断连中断引用）、`lastActivityTime` 超时检测状态），以及完善的异常兜底设计（ASR 断线自动重连与 `AtomicReference` 引用比较防误删、TTS `onClose` 兜底 `countDown` 防死锁和空数组降级、WebSocket 异常断开的 `endSessionIfInProgress` 幂等保护、空对话的空评估兜底、全部 finally 块保证锁和标记必释放）。
