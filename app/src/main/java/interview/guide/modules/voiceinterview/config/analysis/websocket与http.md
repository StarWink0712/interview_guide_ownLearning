### 🚀 HTTP vs WebSocket 对比

#### **HTTP（短连接）**
```
客户端 ──请求──> 服务器 ──响应──> 客户端（连接断开）
                   ↓
            下次请求重新建立连接
```

**适用场景**：
- 页面浏览、数据查询（如获取用户列表）
- 表单提交（如登录、注册）
- 资源下载（图片、文件）

**特点**：
- 请求-响应模式，单向通信
- 每次请求都要重新建立连接
- 不适合实时更新场景

#### **WebSocket（长连接）**
```
客户端 ──握手──> 服务器（连接建立）
                   ↓
            双向实时通信（持续保持）
            客户端 ←──────→ 服务器
                   ↓
            显式关闭才断开
```

**适用场景**：
- 实时聊天、语音/视频通话
- 实时数据推送（股票行情、新闻）
- **语音面试**（持续的双向音频流）

**特点**：
- 一次握手，持续连接
- 双向通信，服务器可主动推送
- 适合实时交互场景

### 🎙️ 在语音面试中的具体应用

### 🌊 数据流对比

**HTTP方式（不适用）**：
```
用户说一句话 → 发送HTTP请求 → 服务器处理 → 返回响应
用户说第二句 → 发送新HTTP请求 → 服务器处理 → 返回响应
...（每次都要重新建立连接，延迟高）
```

**WebSocket方式（正确）**：
```
连接建立（一次握手）
用户说一句话 → 直接发送数据（无需重新连接）
用户说第二句 → 直接发送数据（连接保持）
服务器推送音频 → 直接接收（服务器主动推送）
...（持续双向通信，延迟极低）
```

### 📊 性能对比

| 指标 | HTTP | WebSocket |
|-----|------|-----------|
| 连接开销 | 每次请求都有 | 只有一次握手 |
| 延迟 | 高（需重新连接） | 低（连接保持） |
| 服务器主动推送 | 不支持 | 支持 |
| 实时性 | 差 | 优秀 |
| 适用场景 | 普通请求 | 实时交互 |
