# 高频面试问题与改进路线

## 1. 模块基础讲解

面试中讲语音面试模块，建议不要一上来就说 WebSocket、ASR、TTS。更有说服力的讲法是先讲业务闭环：

求职者在平台里上传简历、选择岗位方向和难度，进入一场模拟真实沟通节奏的语音面试。系统通过实时语音识别理解候选人的回答，通过大模型生成追问，再通过语音合成把面试官问题读出来。面试结束后，系统异步生成评分、优势、改进建议和参考答案，帮助求职者定位表达短板。

这个模块的技术主线可以概括成一句话：

它是一个“WebSocket 实时通话网关 + ASR/LLM/TTS AI 编排 + Redis Stream 异步评估 + Micrometer 指标观测”的复杂业务模块。

按代码结构讲，可以分成七层：

- REST 会话层：`VoiceInterviewController` 和 `VoiceInterviewService` 负责创建、查询、暂停、恢复、结束、删除会话。
- 实时通信层：`WebSocketConfig` 注册 `/ws/voice-interview/{sessionId}`，`VoiceInterviewWebSocketHandler` 处理实时消息。
- ASR 层：`QwenAsrService` 维护后端到 DashScope 的实时识别 WebSocket。
- LLM 层：`DashscopeLlmService` 通过 `LlmProviderRegistry` 获取 voice ChatClient，生成面试官追问。
- TTS 层：`QwenTtsService` 把 AI 文本合成为 PCM，再由 Handler 转成 WAV 发送给前端。
- 持久化层：session、message、evaluation 三张核心表记录会话、对话和报告。
- 异步评估层：`VoiceEvaluateStreamProducer` 入队，`VoiceEvaluateStreamConsumer` 消费，`VoiceInterviewEvaluationService` 调用统一评估服务。

这个模块的设计亮点有：

- 使用 WebSocket 承载前端实时音频和字幕/文本/音频回传，适合低延迟交互。
- 使用两个独立 WebSocket：前端到后端、后端到 DashScope ASR，职责清楚。
- 使用虚拟线程执行 LLM/TTS/JDBC 这类 I/O 阻塞任务，降低平台线程成本。
- 使用 `AtomicBoolean` 防止同一 session 并发触发多轮 LLM。
- 使用 `Semaphore` 控制每个 session 的 TTS 并发，避免句子级并行合成打爆上游。
- 使用 AI 说话标记和 800ms 冷却期防止扬声器回声被 ASR 当成用户回答。
- 使用 Redis Stream 将评估从实时通话链路中解耦，避免用户结束面试后阻塞等待报告。
- 使用 Micrometer 指标拆分 ASR、LLM、TTS 和 turn 总耗时，支撑排障和性能优化。

同时要能说出真实不足，这反而会显得你真的读过代码：

- 异常 WebSocket 断连时 `endSessionIfInProgress` 只做会话结束，没有像正常 `endSession` 一样入队评估任务，可能导致评估状态是 PENDING 但没有消费任务。
- 当前消息模型把“用户回答”和“AI 下一问”存在同一条 message 中，评估时可能把 A1 和 Q2 配成一组，问答配对语义不够严谨。
- `application.yml` 中的自动静音提交配置没有完整绑定和接入，实际主要依赖前端 `submit` 控制消息。
- WebSocket URL 固定为 localhost，不适合生产环境。
- WebSocket 运行时状态在单机内存中，多实例部署需要粘性会话或集中式状态。
- 一些核心测试还处于 disabled 状态，端到端信心不足。

面试回答的策略是：先讲业务价值，再讲链路，再讲并发与可靠性，最后主动补一句“我也知道当前代码还有哪些生产化改进点”。这比只讲功能更像后端工程师。

## 2. 基础面试问题

问题：一句话介绍语音面试模块？

回答：这是一个实时语音模拟面试模块。前端通过 WebSocket 推送麦克风音频，后端用 ASR 转文字，用 LLM 生成面试官追问，用 TTS 合成语音回传，结束后通过 Redis Stream 异步生成评估报告。

问题：为什么不用普通 HTTP 做语音面试？

回答：HTTP 请求响应适合离散操作，不适合持续音频流、实时字幕和 AI 音频回传。语音面试需要双向、低延迟、持续通信，所以用 WebSocket 更合适。

问题：创建会话和 WebSocket 连接是什么关系？

回答：前端先调用 REST 创建 session，拿到 sessionId 和 WebSocket URL；然后用 sessionId 建立 WebSocket。REST 管理生命周期和查询，WebSocket 负责实时通话。

问题：这个模块用了哪些 AI 能力？

回答：三类：ASR 把用户语音转文字，LLM 根据简历、历史对话和阶段生成追问，TTS 把 AI 问题转成语音。面试结束后还会用 LLM 评估整场表现。

问题：为什么评估要异步？

回答：评估需要读取历史对话、构造 QA、调用 LLM、保存报告，耗时不稳定。放到 Redis Stream 异步处理可以让结束面试接口快速返回，前端用状态轮询查看报告进度。

问题：语音面试有哪些状态？

回答：会话状态有 `IN_PROGRESS`、`PAUSED`、`COMPLETED`、`FAILED`。评估状态复用异步任务状态，如 PENDING、PROCESSING、COMPLETED、FAILED。

问题：如何防止 AI 的语音被 ASR 识别成用户回答？

回答：Handler 里维护 `aiSpeaking` 和 `aiSpeakEndAt`。AI 说话期间丢弃麦克风音频，AI 说完后再冷却 800ms，减少扬声器尾音被拾取造成的误触发。

问题：为什么 LLM 回复要控制长度？

回答：语音场景下长答案体验很差，用户需要的是像真人面试官一样短句追问。`aiQuestionMaxChars` 会限制回复长度，提示词也要求 2 到 4 句、一个主问题、最多一个追问。

## 3. 进阶面试问题

问题：这个模块的实时链路完整流程是什么？

回答：创建 session 后建立 WebSocket；Handler 初始化 SessionState、启动 ASR、发送欢迎和开场问题；前端发送 Base64 PCM 音频；后端送入 ASR；ASR partial 推字幕，final 进入合并缓冲；用户 submit 后触发 LLM；LLM 流式输出文本，按句子并发 TTS；TTS 音频转 WAV 通过 WebSocket 回传；同时保存对话消息。

问题：为什么使用虚拟线程？

回答：LLM、TTS、ASR、数据库和 WebSocket 发送都属于 I/O 密集型工作。虚拟线程可以用较低成本承载大量阻塞等待，避免传统平台线程池因为外部 AI 调用等待而被占满。

问题：`AtomicBoolean` 在 Handler 中解决什么问题？

回答：它是同一 session 的 processing 锁，避免用户连续点击 submit 或 ASR 多段触发导致同时发起多轮 LLM。若当前正在处理，会延迟 400ms 再尝试，保证同一会话的轮次顺序。

问题：句子级 TTS 并发有什么收益和风险？

回答：收益是 LLM 流式生成时，一旦出现完整句子就可以提前合成 TTS，减少首音频等待。风险是并发过高会打满 TTS provider，所以用 `Semaphore` 限制每会话并发数，并按顺序收集结果。

问题：ASR 重连为什么要做引用比较？

回答：重连时旧连接的 onClose 可能晚于新连接建立。如果 onClose 直接删除 session，会误删新连接，导致“明明重连成功但后续无声”。用当前 conversation 引用比较，可以避免旧连接关闭事件影响新连接。

问题：当前评估问答配对有什么风险？

回答：开场问题是单独保存的 AI 文本；后续一条消息常常保存“用户本轮回答 + AI 下一轮问题”。评估时如果简单用同一条 message 的 aiGeneratedText 和 userRecognizedText 组 QA，就可能出现 Q2 对 A1 的错配。更好的模型是单独建立 turn：上一问、用户回答、下一问分开存。

问题：为什么异常断连可能导致评估不执行？

回答：正常结束会调用 `endSession`，它会设置状态并通过 producer 入队评估任务；但 WebSocket 关闭兜底调用的是 `endSessionIfInProgress`，它只结束会话，没有明显入队逻辑。这样可能出现会话完成但没有 Redis Stream 任务。

问题：`countBySessionId + 1` 生成 sequenceNum 有什么问题？

回答：并发保存消息时两个线程可能同时读到相同 count，生成重复 sequenceNum。虽然当前通过 session 级处理降低了概率，但更稳的方式是数据库唯一约束、悲观锁、原子递增器或 turn 表自增序号。

## 4. 技术延伸问题

问题：如果不用 WebSocket，可以用什么实现？

回答：可以用 WebRTC，它更适合实时音视频和回声消除；也可以用 SSE + HTTP 上传分片，但 SSE 只能服务端推送，双向实时性差；还可以用 gRPC bidirectional streaming，但浏览器端接入成本更高。

问题：WebSocket 和 WebRTC 怎么选？

回答：WebSocket 适合业务消息、字幕、控制命令和轻量音频流，后端开发简单；WebRTC 适合低延迟音视频、浏览器原生回声消除、弱网自适应和点对点/媒体服务器场景。如果要做真正电话级语音面试，WebRTC 更专业。

问题：如果不用 DashScope ASR/TTS，可以换什么？

回答：ASR 可以换 Azure Speech、Google Speech、OpenAI Realtime、科大讯飞或本地 Whisper；TTS 可以换 Azure TTS、火山、讯飞或本地 CosyVoice。服务接口应抽象成 `AsrService` 和 `TtsService`，减少 provider 绑定。

问题：如果不用 Redis Stream 做评估任务，可以用什么？

回答：可以用 Kafka、RabbitMQ、RocketMQ、数据库任务表或 Spring Batch。Redis Stream 轻量、适合当前单体项目；Kafka 更适合高吞吐和事件回放；数据库任务表简单但吞吐和并发控制弱。

问题：如何做多模态面试？

回答：可以保留现有语音链路，再加入摄像头视频、表情和眼神检测、屏幕共享、代码编辑器事件。后端要把音频 turn、视频事件、代码事件统一到时间轴，评估时做多源特征融合。

问题：如何支持实时打断 AI？

回答：前端在检测到用户开始说话时发送 interrupt 控制消息，Handler 停止当前 TTS 播放、取消正在处理的 TTS future、设置 aiSpeaking=false，并把新用户音频送入 ASR。LLM 侧如果支持流式取消，也要取消当前生成。

问题：如何让评估更可信？

回答：评估输入要结构化成 question、answer、phase、duration、ASR confidence、追问上下文；输出要包含逐题评分依据、关键证据片段、改进建议和参考答案。还可以引入知识库标准答案或岗位能力模型，避免纯主观评分。

问题：如何支持大规模并发语音面试？

回答：前端到后端 WebSocket 层做水平扩展和粘性会话；ASR/TTS/LLM 做 provider 并发池和降级；评估任务用消息队列削峰；监控 P95 延迟和错误率；必要时拆分实时通话服务和评估服务。

## 5. 改进方案问题

问题：如果只能先改三个问题，你会改什么？

回答：第一，修复异常断连不入队评估的问题，保证 session 完成后一定有评估任务。第二，重构消息模型为 turn 表，解决问答错配。第三，把 WebSocket URL、自动提交参数和限流配置真正配置化并接入生产。

问题：如何修复异常断连不入队评估？

回答：让 `endSessionIfInProgress` 复用正常结束逻辑，或在结束成功后调用 `voiceEvaluateStreamProducer.sendEvaluateTask(sessionId)`。同时保证幂等：如果已有 evaluation 或已有活跃任务，不重复入队。

问题：如何重构问答存储模型？

回答：新增 `voice_interview_turns` 表，字段包括 sessionId、turnIndex、phase、questionText、answerText、nextQuestionText、answerStartTime、answerEndTime、asrConfidence、llmLatency、ttsLatency。评估直接按 turn 读取，避免从 message 推断问答关系。

问题：如何落地自动断句提交？

回答：补齐配置字段，然后在 ASR final 后启动 debounce 定时任务。若一段时间内没有新的 partial/final，且文本长度超过 `minCommitChars` 或等待超过 `maxWaitForContinuationMs`，自动 flush 到 LLM。前端 submit 仍保留为手动确认模式。

问题：如何让 WebSocket 支持生产地址？

回答：新增 `app.voice-interview.websocket.external-url` 或 `public-base-url` 配置。开发返回 `ws://localhost:8080`，生产返回 `wss://domain/ws/voice-interview/{id}`。也可以只返回 sessionId，由前端根据当前 location 拼接。

问题：如何提高核心链路测试覆盖？

回答：用 fake ASR/LLM/TTS 替代真实外部服务，模拟 partial、final、LLM sentence、TTS audio、TTS timeout。针对 Handler 写“音频输入到文本/音频输出”的集成测试，再覆盖断连、重复 submit、暂停超时和评估入队。

问题：如何支持多 provider fallback？

回答：在 ASR/TTS/LLM 服务层抽象 provider 接口，配置主备 provider。调用失败时按错误类型判断是否可重试或切换 provider，并记录 fallback 指标。注意不要对用户同一轮无限重试，否则延迟会失控。

问题：如何减少 TTS 延迟？

回答：保留开场问题预热缓存；对 LLM 回复做短句化；启用句子级 TTS 并行；控制每句字符数；对常见提示语做缓存；支持 chunked audio，让第一句合成完就播放，而不是等整段合并。

## 6. 故障处理问题

问题：用户说话后没有任何字幕，怎么排查？

回答：先看前端是否发送了音频消息，Base64 是否有效，采样率是否 16kHz PCM；再看 Handler 是否因 `aiSpeaking` 或冷却期丢弃音频；然后看 ASR session 是否存在、appendAudio 是否异常、DashScope 是否返回 error 事件。

问题：字幕有了，但 AI 不回答，怎么排查？

回答：看前端是否发送 `control submit`。当前代码主要靠 submit 触发 LLM，不是所有 ASR final 都自动触发。再看 `processing` 锁是否卡住、mergeBuffer 是否为空、sessionEntity 是否能查到、LLM provider 是否调用失败。

问题：AI 有文字但没有声音，怎么排查？

回答：重点查 TTS。看 TTS API Key、model、voice、超时、返回 PCM 是否为空、`convertPcmToWav` 后大小是否合理、前端是否支持 Base64 WAV。指标上看 `app.voice.interview.tts.empty_audio` 是否上升。

问题：用户听到 AI 重复问同一个问题，怎么排查？

回答：看 conversationHistory 是否正确加载，开场问题是否重复触发，WebSocket 重连时历史消息是否为空，LLM prompt 是否明确禁止重复开场。当前开场问题只在无历史时触发，但如果保存失败，重连会再次开场。

问题：评估报告迟迟不出来，怎么排查？

回答：先查 session.evaluateStatus，是 PENDING、PROCESSING 还是 FAILED。若一直 PENDING，检查 Redis Stream 是否有任务，尤其是异常断连路径是否没有入队。若 PROCESSING 很久，看 LLM 评估调用是否超时。若 FAILED，看 evaluateError 和消费者日志。

问题：评估内容明显问答错位，怎么排查？

回答：查看 `voice_interview_messages` 的 sequenceNum、userRecognizedText、aiGeneratedText。若一条记录是用户回答上一题加 AI 下一题，评估按同条 message 配 QA 就会错位。解决思路是按 turn 建模，或评估时用上一条 AI 问题配当前用户回答。

问题：WebSocket 断开后会话显示完成但没有报告，为什么？

回答：可能走了异常关闭兜底 `endSessionIfInProgress`，它会把会话结束，但不一定发送评估任务。需要补入队逻辑或让异常结束复用正常结束流程。

问题：线上出现大量连接占用资源，怎么处理？

回答：短期用网关限制连接数和 idle timeout，应用内关闭长时间无活动 session。长期接入 Redis 限流，按 IP、用户和全局并发控制；监控当前连接数、ASR session 数、TTS 并发数和 LLM 调用队列。

问题：如何向面试官总结这个模块的最大挑战？

回答：最大挑战不是某一个 AI 调用，而是实时链路编排：要同时处理双 WebSocket、ASR 分段、LLM 流式、TTS 并发、回声控制、状态持久化、异常断连、异步评估和观测指标。核心能力是把这些不稳定的外部服务组织成一个用户感觉自然、可恢复、可排障的面试流程。
