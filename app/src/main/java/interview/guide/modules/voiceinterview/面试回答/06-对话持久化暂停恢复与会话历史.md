# 对话持久化、暂停恢复与会话历史

## 1. 模块基础讲解

语音面试的持久化主要围绕三张表：

- `voice_interview_sessions`：会话元信息、阶段、状态和评估状态。
- `voice_interview_messages`：每轮对话消息。
- `voice_interview_evaluations`：最终评估结果。

消息保存发生在 Handler 的 `saveMessage(sessionId, userText, aiReply)`，最终委托 `VoiceInterviewService.saveMessage`。

消息实体字段：

- `sessionId`：所属会话。
- `messageType`：当前代码保存为 `DIALOGUE`。
- `phase`：当前面试阶段。
- `userRecognizedText`：用户语音识别文本。
- `aiGeneratedText`：AI 生成回复。
- `sequenceNum`：会话内序号。
- `timestamp/createdAt`：时间。

历史查询：

- `getConversationHistory(sessionId)` 返回实体列表。
- `getConversationHistoryDTO(sessionId)` 返回前端 DTO。
- Handler 的 `getHistory` 会把历史格式化为“候选人：xxx”“面试官：xxx”，注入 LLM Prompt。

开场问题持久化：

- 首次 WebSocket 连接且没有历史消息时，后端发送开场问题。
- 开场问题会调用 `saveMessage(sessionId, null, aiReply)` 保存。
- 重连时如果已有历史消息，就不会重复开场。

暂停恢复：

- 超过 4 分 30 秒无活动发送暂停警告。
- 超过 5 分钟无活动，调用 `pauseSession(sessionId, "timeout")`。
- 暂停时记录 `pausedAt`，状态设为 `PAUSED`，清缓存，关闭 WebSocket，停止 ASR。
- 恢复时状态设回 `IN_PROGRESS`，记录 `resumedAt`，重新缓存，并返回 WebSocket URL。

需要特别认真说明的边界：

当前消息表一条记录同时保存“用户本轮文本”和“AI 本轮生成回复”。但真实面试语义通常是“AI 上一问 -> 用户回答 -> AI 下一问”。这会导致最终评估构造 `QaRecord` 时容易错位：

- 开场问题保存为 `aiGeneratedText=Q1, userRecognizedText=null`。
- 用户回答 Q1 后，LLM 生成 Q2，并保存为 `userRecognizedText=A1, aiGeneratedText=Q2`。
- 评估时 `VoiceInterviewEvaluationService` 把 `aiGeneratedText` 当 question、`userRecognizedText` 当 answer。
- 于是可能出现 Q2 对 A1 的错配。

这是当前模块的关键改进点。更合理的数据模型是显式记录 turn：

```text
turnId
questionText = 上一轮 AI 问题
answerText = 用户回答
followUpText = 本轮 AI 追问
phase
timestamps
```

## 2. 基础面试问题

**问题：语音面试如何保存对话历史？**

回答：每轮 LLM 回复完成后，Handler 调用 `saveMessage`，保存用户 ASR 文本、AI 生成文本、当前阶段和序号。前端可以通过 `/messages` 查询完整历史。

**问题：为什么重连后不会重复开场？**

回答：发送开场问题前，Handler 会查询历史消息。如果历史不为空，说明之前已经开场或有对话记录，就不会重复发送开场问题。

**问题：暂停会保存哪些状态？**

回答：暂停会把会话状态设为 `PAUSED`，记录 `pausedAt`，保留数据库里的消息历史和当前阶段。WebSocket 和 ASR 连接会关闭，用户恢复时重新建立连接。

**问题：恢复会话时怎么接续上下文？**

回答：恢复后前端重新建立 WebSocket，后端加载数据库里的历史消息，LLM Prompt 会带上历史对话，因此 AI 可以基于之前内容继续追问。

**问题：消息序号怎么生成？**

回答：`getNextSequenceNum` 用当前会话消息数 `countBySessionId + 1` 生成下一序号。简单可用，但并发写入时不够强，需要进一步加锁或数据库约束。

## 3. 进阶面试问题

**问题：当前消息模型为什么可能影响评估准确性？**

回答：因为消息保存的是“用户回答 + AI 下一问”，而评估需要的是“AI 问题 + 用户回答”。如果直接把同一条记录的 aiText 当问题、userText 当答案，就可能把用户上一题答案配到 AI 下一题问题上，导致评分不准确。

**问题：如何修复这个问题？**

回答：可以在 Handler 中维护 `lastAiQuestion`。用户 submit 后，把 `lastAiQuestion` 和 userText 保存为一个回答 turn；LLM 生成 nextQuestion 后，更新 `lastAiQuestion`，并单独保存 AI 消息或更新下一 turn。评估时按 turn 的 question/answer 构造 QaRecord。

**问题：暂停恢复是否能恢复内存状态？**

回答：数据库能恢复历史消息和会话阶段，但不能恢复 ASR mergeBuffer、processing、aiSpeaking 等连接内存状态。这是合理的，因为这些状态只对当前 WebSocket 连接有效。恢复后应重新开始当前轮输入。

**问题：sequenceNum 使用 count+1 有什么风险？**

回答：如果同一会话并发保存多条消息，两个线程可能都读到相同 count，从而写出相同 sequenceNum。当前没有唯一约束保护。生产环境可用数据库序列、乐观锁、唯一约束或按 session 加锁。

**问题：为什么对话历史注入 Prompt 时要格式化为角色文本？**

回答：模型需要理解谁说了什么。把历史格式化为“候选人：”“面试官：”能保留对话角色，帮助模型进行连续追问。

**问题：历史消息过多有什么问题？**

回答：Prompt 会越来越长，增加成本和延迟，也可能超过上下文窗口。长面试需要历史摘要、最近 N 轮窗口或阶段摘要。

## 4. 技术延伸问题

**问题：如何设计更适合语音面试的 Turn 表？**

回答：可以建 `voice_interview_turns`：sessionId、turnIndex、phase、questionText、answerText、nextQuestionText、asrConfidence、answerStartedAt、answerEndedAt、llmLatency、ttsLatency。这样评估、复盘和可观测性都更清楚。

**问题：如何保存 ASR 置信度和原始音频？**

回答：如果 ASR 返回置信度，可保存到 turn 或 message。原始音频可以存对象存储，数据库保存音频 URL、duration、format、sampleRate。评估时可标记“低置信度转写”，避免误判用户表达。

**问题：如何支持用户编辑 ASR 文本后再提交？**

回答：前端可以展示 final transcript，用户编辑后通过 `control submit data.text` 提交。后端应区分 rawAsrText 和 finalSubmittedText，评估使用用户确认后的文本。

**问题：如何做历史记录回放？**

回答：需要保存每轮 AI 音频 URL 或可重新 TTS 的文本。前端按 sequence 播放 AI 问题和用户回答。若保存原始用户音频，可以还原真实语音面试过程。

**问题：如何支持多端恢复？**

回答：会话状态和历史必须在数据库中完整保存，WebSocket runtime 只保留短期状态。新设备连接后根据 sessionId 加载历史，并重新启动 ASR。需要防止多个设备同时连接同一 session。

## 5. 改进方案问题

**问题：对话持久化最优先改什么？**

回答：优先改 turn 对齐模型，确保最终评估的 question 和 answer 一一对应。这会直接影响报告准确性，是比 UI 优化更核心的质量问题。

**问题：暂停恢复还要补什么？**

回答：恢复时可以返回最近一轮 AI 问题，让用户知道该继续回答哪个问题。当前只返回会话信息，前端需要再查历史并自己定位。

**问题：删除会话还要清理什么？**

回答：除了删除 messages 和 evaluation，还要清 Redis 缓存、关闭可能活跃的 WebSocket、停止 ASR、取消评估任务。如果保存了音频文件，也要删除对象存储文件。

**问题：消息表可以加哪些索引？**

回答：建议给 `(session_id, sequence_num)` 加索引或唯一约束，支持历史按序查询并防重复序号。评估表的 `session_id` 已是 unique。

**问题：如何提升历史查询性能？**

回答：消息历史可分页或按阶段查询；长会话可先返回最近 N 条，展开时再加载全部。列表页不应加载消息内容，只统计 messageCount。

## 6. 故障处理问题

**问题：历史消息顺序错乱怎么办？**

回答：检查 sequenceNum 是否重复或为空。当前用 count+1 生成，理论上并发保存可能冲突。可以按 createdAt 辅助排序，长期应加唯一约束和原子序号生成。

**问题：重连后 AI 重复问开场问题怎么办？**

回答：检查历史消息是否保存成功，`getHistory` 是否能查到记录。如果开场消息保存失败，重连时会认为历史为空而再次开场。

**问题：暂停后恢复不了怎么办？**

回答：检查会话当前状态是否为 PAUSED。`resumeSession` 只允许 PAUSED 恢复；如果异常断开已经把会话设为 COMPLETED，就不能恢复，只能新建或做特殊恢复逻辑。

**问题：最终报告问题和回答对不上怎么办？**

回答：重点检查 `VoiceInterviewEvaluationService.buildQaRecords`。当前它按同一条 message 的 aiText 和 userText 构造 QaRecord，可能错位。需要重构消息模型或评估构造逻辑。

**问题：会话删除后仍能从缓存读到怎么办？**

回答：`deleteSession` 当前没有显式调用 `invalidateSessionCache`。如果删除前会话被缓存，短时间可能存在脏缓存。修复是删除时同步清缓存。
