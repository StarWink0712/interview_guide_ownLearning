### 正确的理解

**RPC 是一种思想（没错）**——让"调用远程服务"用起来就像"调用本地方法"一样简单。

但它不是一个**跨层**的概念，而是一个**固定属于应用层**的概念：

```
OSI 七层模型                      
                                     
应用层     ← RPC 属于这里（和 HTTP、FTP 同层）
表示层     ← 序列化方式（JSON/Protobuf/Hessian）可选
会话层
传输层     ← TCP/UDP/HTTP/2（底层传输方式）可选
网络层
数据链路层
物理层
```

### 你刚才说的"应用层、传输层、表示层都可以用不同的实现方法"

这句话稍微修正一下更准确：

> **RPC（应用层概念）可以有多种实现方式，在不同层次做不同的选型：**

```
                       应用层
         RPC 框架（如 Dubbo、gRPC、Feign）
               │
    ┌──────────┼──────────┐
    │          │          │
  表示层       │        传输层
 (序列化)      │       (传输协议)
    │          │          │
 JSON /       │      TCP / HTTP / HTTP/2
 Protobuf /   │
 Hessian      │
              │
           自定义应用层协议
          (如 Dubbo 二进制协议)
```

也就是说：**表示层（序列化）和传输层（TCP/HTTP）是可选的实现细节，但 RPC 本身始终属于应用层。**

### 文档中的例子帮你对应一下

| RPC 框架               |   应用层（RPC 协议）   |     表示层（序列化）     |        传输层       |
| -------------------- | :-------------: | :--------------: | :--------------: |
| Dubbo                |     自定义二进制协议    |  Hessian / Kryo  |        TCP       |
| gRPC                 | gRPC（基于 HTTP/2） | Protocol Buffers | HTTP/2（底层还是 TCP） |
| Feign / RestTemplate |     HTTP/1.1    |       JSON       |  HTTP（底层还是 TCP）  |

RPC 是"应用层那个让你感觉在调本地方法的东西"。至于底下是用 TCP 裸奔、用 HTTP 包装、还是用 Protobuf 序列化，都是实现方式——**你选哪个，就决定了性能、兼容性、易用性的取舍**。
