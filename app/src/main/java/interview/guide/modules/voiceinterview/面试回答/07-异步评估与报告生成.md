# 异步评估与报告生成

## 1. 模块基础讲解

语音面试结束后，最终评估通过 Redis Stream 异步执行。相关代码包括：

- `VoiceEvaluateStreamProducer`
- `VoiceEvaluateStreamConsumer`
- `VoiceInterviewEvaluationService`
- `UnifiedEvaluationService`
- `VoiceInterviewEvaluationEntity`

触发路径：

1. REST `endSession` 或手动 `generateEvaluation` 调用 Service。
2. Service 设置会话 `evaluateStatus=PENDING`。
3. Producer 创建或复用 `VOICE_INTERVIEW_EVALUATE` 异步任务。
4. 事务提交后写入 Redis Stream。
5. Consumer 消费任务，标记 PROCESSING。
6. 调用 `VoiceInterviewEvaluationService.generateEvaluation(sessionId)`。
7. 生成并保存评估结果。
8. 标记 async task 和会话评估状态为 COMPLETED。

Producer 消息字段：

- `taskId`
- `businessId`
- `voiceSessionId`
- `retryCount`

Consumer 处理逻辑：

1. 解析 taskId 和 voiceSessionId。
2. 标记任务和会话为 PROCESSING。
3. 检查会话是否存在；不存在则抛 `AsyncTaskCancelledException`。
4. 检查评估结果是否已存在；存在则跳过。
5. 调用评估服务。
6. 成功后标记 COMPLETED。
7. 失败时按抽象消费者模板重试，超过次数进入 dead letter。

`VoiceInterviewEvaluationService` 的核心流程：

1. 查询会话实体。
2. 查询对话消息并按 sequenceNum 排序。
3. 如果无消息，保存空评估。
4. 将消息构造成 `QaRecord`。
5. 根据 session 的 provider 获取 ChatClient。
6. 根据 skillId 构建 referenceContext。
7. 调用 `UnifiedEvaluationService.evaluate`。
8. 保存总分、总评、逐题评估、优势、改进建议和参考答案 JSON。

评估状态查询：

- `GET /evaluation` 返回 evaluateStatus 和 evaluateError。
- 如果 status 是 COMPLETED，则加载完整 `VoiceEvaluationDetailDTO`。

重要边界：

当前语音评估复用了文字面试通用评估引擎，这是架构亮点；但 `buildQaRecords` 的问答构造依赖消息表同条记录的 aiText/userText，可能存在问题和答案错位，需要重构 turn 模型。

## 2. 基础面试问题

**问题：语音面试评估为什么要异步？**

回答：评估需要读取整场对话并调用 LLM，耗时较长且可能失败。异步化后，结束面试接口可以快速返回，前端通过轮询查看评估进度。

**问题：评估报告包含什么？**

回答：包含总分、总体反馈、优势、改进建议、逐题评分和反馈、参考答案和关键点。结构和文字面试评估对齐，方便前端复用展示组件。

**问题：没有对话消息时怎么评估？**

回答：`generateEvaluation` 发现 messages 为空时，会保存空评估，总分 0，提示“未形成有效对话记录”，并给出改进建议。

**问题：重复触发评估怎么办？**

回答：Producer 用 `createOrReusePendingTask` 避免重复入队；Consumer 处理前也检查 evaluation 是否已存在，存在就跳过。这是生产端和消费端双重幂等。

**问题：评估结果怎么查？**

回答：前端轮询 `GET /api/voice-interview/sessions/{sessionId}/evaluation`。如果状态是 COMPLETED，接口会嵌入完整 evaluation；否则只返回状态和错误。

## 3. 进阶面试问题

**问题：为什么评估服务强调“LLM 调用在事务外”？**

回答：LLM 调用可能耗时很长，如果放在事务里会长时间占用数据库连接和锁。当前 `generateEvaluation` 先在事务外调用 LLM，拿到 report 后才进入事务保存结果，这是更合理的事务边界。

**问题：语音评估如何复用文字面试评估？**

回答：它把语音对话转成通用 `QaRecord`，然后调用 `UnifiedEvaluationService`。这个通用服务负责分批评估、结构化输出、失败兜底和二次汇总。语音模块只做输入适配和结果持久化。

**问题：评估参考上下文怎么来？**

回答：根据 session 的 `skillId` 调用 `InterviewSkillService.buildEvaluationReferenceSectionSafe`，把 Skill reference 作为评估参考基线。这样语音面试的评分也能基于技术方向知识库。

**问题：消费者失败重试怎么做？**

回答：`VoiceEvaluateStreamConsumer` 继承 `AbstractStreamConsumer`，失败时调用 `retryMessage` 重新写入 Stream，并通过 async task 标记 RETRYING。超过最大次数后 `markFailed` 标记 dead letter，并把会话评估状态设为 FAILED。

**问题：为什么会话删除后任务要取消？**

回答：如果用户删除了会话，评估任务已经没有业务对象。Consumer 检查会话不存在时抛 `AsyncTaskCancelledException`，父类会标记取消并 ack，避免无意义重试。

**问题：评估结果已存在时为什么跳过？**

回答：这是幂等保护。异步任务可能重复投递或重试，如果评估已经保存，再重复调用 LLM 会浪费成本且可能覆盖结果。跳过能保证结果稳定。

## 4. 技术延伸问题

**问题：如果要做评估进度条，怎么扩展？**

回答：在 async task 或 session 上保存 stage、currentBatch、totalBatch、percent。`UnifiedEvaluationService` 分批前后回调更新进度。前端轮询或用 SSE 推送进度。

**问题：如果要重新生成报告，怎么设计？**

回答：增加 force 参数和报告版本。已有 evaluation 时默认返回，不重复生成；用户明确重新生成时创建新版本，保存 model/prompt/reference/inputHash，旧版本保留。

**问题：如果要提升评估准确性，怎么做？**

回答：先修复问答 turn 对齐，再加入 ASR 置信度、阶段、题目类型和 Skill rubric。可以用人工标注样本校准评分，也可以对低置信度 ASR 文本降低评分权重。

**问题：如果要做报告实时生成，是否可行？**

回答：可以在每轮对话后做轻量评分，最终只做汇总。但语音场景中每轮问题答案配对要先准确，否则实时评分会错。当前更适合结束后异步评估。

**问题：如果 Redis Stream 不可用怎么办？**

回答：可以引入 outbox 表。结束会话时在数据库事务内写待评估事件，后台 dispatcher 写 Redis Stream。Redis 恢复后继续补发，避免 PENDING 任务丢失。

## 5. 改进方案问题

**问题：当前评估链路最重要的改进是什么？**

回答：修复 `buildQaRecords` 的输入模型。要确保 question 是 AI 实际问的问题，answer 是用户对这个问题的回答。否则再强的评估模型也会基于错配数据评分。

**问题：异常断开后评估状态 PENDING 但没任务怎么办？**

回答：补偿方案是定时扫描 `evaluateStatus=PENDING` 且没有 active async task 的 completed 会话，重新调用 producer 入队。根本修复是在 `endSessionIfInProgress` 中也触发 producer，或明确不设置 PENDING。

**问题：空评估保存是否幂等？**

回答：空评估用 `findBySessionId().orElseGet`，可以复用已有实体；正常评估保存当前直接 builder 新实体，如果重复保存可能依赖 sessionId unique 约束报错。虽然 Consumer 会先检查存在，保存层也可以做 upsert 更稳。

**问题：评估状态更新和缓存有什么关系？**

回答：`updateEvaluateStatus` 直接更新数据库，没有更新 Redisson 缓存。由于结束会话会清缓存，通常查询能读 DB；但如果某路径仍有缓存，可能读到旧状态。建议更新状态时也清缓存或更新缓存。

**问题：报告查询 JSON 解析失败怎么办？**

回答：`buildDetailDTO` 解析失败会抛 `VOICE_EVALUATION_FAILED`。可以对非关键字段降级为空列表，对关键字段保留错误提示。更好的方案是结构化拆表或 JSONB 校验。

## 6. 故障处理问题

**问题：评估任务重复入队怎么办？**

回答：看 async task 表是否只有一个 active task。Producer 会复用 pending task，Consumer 也会检查 evaluation 是否存在。若仍重复，检查 businessId 是否统一使用同一个 sessionId 字符串。

**问题：评估失败后如何排查？**

回答：先看 session.evaluateError 和 async task 错误；再看 Consumer 日志；然后检查 messages 是否为空、JSON 序列化是否失败、LLM provider 是否可用、referenceContext 是否异常。

**问题：评估结果和真实对话不匹配怎么办？**

回答：检查消息表 userRecognizedText 和 aiGeneratedText 的对应关系。当前设计可能把 AI 下一问和用户上一答放在同一 QaRecord，需要重构 turn 配对。

**问题：评估状态一直 PROCESSING 怎么办？**

回答：可能 Consumer 在 LLM 调用中卡住，或保存报告后 markCompleted 失败。检查 async task 状态、消费者线程、LLM 超时和数据库连接。必要时手动重试或标记失败。

**问题：手动触发评估返回 PENDING 后没变化怎么办？**

回答：确认 producer 是否写入 Stream，消费者组是否启动，Redis 是否可用。还要确认事务后回调是否执行，如果当前没有事务上下文，`TransactionAfterCommitExecutor` 的行为也要检查。
