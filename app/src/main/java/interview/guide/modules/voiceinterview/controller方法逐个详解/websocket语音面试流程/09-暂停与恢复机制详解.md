# 暂停与恢复机制详解

## 概述

语音面试支持三种暂停与恢复方式：用户通过前端 API 主动暂停、用户主动恢复、以及 Handler 层定时任务自动检测超时暂停。暂停机制的核心是通过数据库状态字段管理面试的生命周期状态，通过 Redis 缓存的失效与重建保证状态查询的一致性，并在 Handler 中通过 `@Scheduled` 定时任务实现 5 分钟无活动的自动暂停。

## 一、用户主动暂停

用户在前端点击"暂停"按钮后，前端调用 `PUT /api/voice-interview/sessions/{sessionId}/pause`，请求体为 `{"reason": "user_initiated"}`。

### Controller 层

```java
@PutMapping("/sessions/{sessionId}/pause")
public Result<Void> pauseSession(
    @PathVariable Long sessionId,
    @RequestBody Map<String, String> request
) {
    log.info("Pausing session: {}", sessionId);
    String reason = request.getOrDefault("reason", "user_initiated");
    voiceInterviewService.pauseSession(sessionId.toString(), reason);
    return Result.success();
}
```

请求体使用原始 `Map<String, String>` 而非 DTO 类，`reason` 有默认值 "user_initiated" 也可传 "timeout" 等值区分暂停来源。

### Service 层

```java
@Transactional
public void pauseSession(String sessionId, String reason) {
    Long sessionIdLong = parseSessionId(sessionId);

    // 查询会话——使用 findById 直接从 DB 查，不经过 Redis 缓存，
    // 确保获取到最新的状态（可能已被其他操作修改）
    VoiceInterviewSessionEntity session = sessionRepository.findById(sessionIdLong)
        .orElseThrow(() -> new BusinessException(ErrorCode.NOT_FOUND, "会话不存在: " + sessionId));

    // 状态校验：仅 IN_PROGRESS 状态的会话可以暂停
    // COMPLETED 已结束无需暂停，PAUSED 已经暂停不能重复暂停
    if (session.getStatus() != VoiceInterviewSessionStatus.IN_PROGRESS) {
        throw new BusinessException(ErrorCode.BAD_REQUEST,
            "会话状态为 " + session.getStatus() + "，无法暂停");
    }

    // 更新状态：设置 PAUSED 并记录暂停时间
    session.setStatus(VoiceInterviewSessionStatus.PAUSED);
    session.setPausedAt(LocalDateTime.now());

    // 持久化到 DB 并清除 Redis 缓存
    sessionRepository.save(session);
    invalidateSessionCache(sessionIdLong);  // 关键：让下一次 getSession 从 DB 读到 PAUSED

    log.info("Session {} paused, reason: {}", sessionId, reason);
}
```

清除 Redis 缓存是暂停操作中最关键的一步。如果不执行 `invalidateSessionCache`，Redis 中 `voice:interview:session:{id}` 仍然缓存着 IN_PROGRESS 状态的旧数据。下一次 `getSession` 会从缓存命中返回旧的 IN_PROGRESS 状态，造成数据库和缓存的不一致——数据库已是 PAUSED，但前端看到的是 IN_PROGRESS。

## 二、用户主动恢复

用户点击"继续面试"按钮，前端调用 `PUT /api/voice-interview/sessions/{sessionId}/resume`。

```java
@Transactional
public SessionResponseDTO resumeSession(String sessionId) {
    Long sessionIdLong = parseSessionId(sessionId);

    VoiceInterviewSessionEntity session = sessionRepository.findById(sessionIdLong)
        .orElseThrow(() -> new BusinessException(ErrorCode.NOT_FOUND, "会话不存在: " + sessionId));

    // 状态校验：仅 PAUSED 状态的会话可以恢复
    if (session.getStatus() != VoiceInterviewSessionStatus.PAUSED) {
        throw new BusinessException(ErrorCode.BAD_REQUEST,
            "会话状态为 " + session.getStatus() + "，无法恢复");
    }

    // 更新状态
    session.setStatus(VoiceInterviewSessionStatus.IN_PROGRESS);
    session.setResumedAt(LocalDateTime.now());

    // 持久化并重新写入 Redis 缓存
    VoiceInterviewSessionEntity saved = sessionRepository.save(session);
    cacheSession(saved);  // 重新写入缓存（1h TTL）——面试继续，需要缓存加速查询

    log.info("Session {} resumed with {} messages in conversation history",
        sessionId, messageRepository.countBySessionId(sessionIdLong));

    // 返回 SessionResponseDTO 而非 Result<Void>
    // 因为前端需要新的 WebSocket URL 重新建立连接
    return buildSessionResponse(saved);
}
```

恢复操作与暂停的关键区别在于缓存操作——恢复执行 `cacheSession(saved)` 而非 `invalidateSessionCache()`。因为恢复后面试继续，后续 Handler 中的 `getSession` 查询需要缓存加速。此外恢复返回 `SessionResponseDTO` 包含新的 `webSocketUrl`——暂停期间的 WebSocket 可能已被关闭（特别是超时暂停场景），前端需要调用 `new WebSocket(webSocketUrl)` 重新建立连接。

### Redis 缓存的失效与重建

```java
// 清除缓存：暂停和结束操作调用
private void invalidateSessionCache(Long sessionId) {
    String cacheKey = "voice:interview:session:" + sessionId;
    RBucket<VoiceInterviewSessionEntity> bucket = redissonClient.getBucket(cacheKey);
    bucket.delete();
}

// 写入缓存：创建和恢复操作调用
private void cacheSession(VoiceInterviewSessionEntity session) {
    String cacheKey = "voice:interview:session:" + session.getId();
    RBucket<VoiceInterviewSessionEntity> bucket = redissonClient.getBucket(cacheKey);
    bucket.set(session, Duration.ofHours(CACHE_TTL_HOURS));  // 1 小时 TTL
}
```

两种操作的语义不同——`invalidateSessionCache` 删除缓存使下一次查询从 DB 读取（状态已变更），`cacheSession` 写入缓存供后续查询直接命中（状态已就绪）。

## 三、自动暂停超时检测

`VoiceInterviewWebSocketHandler` 内置 `@Scheduled(fixedRate = 30000)` 定时任务，每 30 秒执行一次超时检测。

### 活动时间戳的管理

Handler 在 `handleTextMessage()` 中每次收到前端消息时更新活动时间：

```java
// 任何消息（audio 或 control）到达时都更新时间戳
lastActivityTime.put(sessionId, System.currentTimeMillis());
```

这意味着只要用户持续说话（音频消息不断到达）或操作界面（控制消息触发），计时器就会持续重置。

### 超时检测逻辑

```java
// 超时阈值
private static final long WARNING_TIME_MS = (long) (4.5 * 60 * 1000);  // 4分30秒
private static final long PAUSE_TIMEOUT_MS = 5 * 60 * 1000;            // 5分钟

@Scheduled(fixedRate = 30000)  // 每 30 秒执行
public void checkPauseTimeout() {
    long now = System.currentTimeMillis();

    lastActivityTime.forEach((sessionId, lastTime) -> {
        long elapsed = now - lastTime;

        // 阶段一：超过 4 分 30 秒，发送 30 秒预警
        if (elapsed > WARNING_TIME_MS && elapsed < PAUSE_TIMEOUT_MS) {
            sendPauseWarning(sessionId);
        }
        // 阶段二：超过 5 分钟，自动暂停
        else if (elapsed >= PAUSE_TIMEOUT_MS) {
            log.warn("Session {} inactive for {} minutes, pausing",
                sessionId, PAUSE_TIMEOUT_MS / 60000);
            handlePauseTimeout(sessionId);
        }
    });
}
```

两个阶段的分级处理给用户缓冲时间——收到警告后有 30 秒继续说话或点击按钮来延续会话。

### 警告与暂停的具体实现

```java
// 发送暂停警告通知（30 秒倒计时）
private void sendPauseWarning(String sessionId) {
    WebSocketSession session = sessions.get(sessionId);
    if (session != null && session.isOpen()) {
        sendMessage(session, toJson(Map.of(
            "type", "control",
            "action", "pause_timeout_warning",
            "message", "会话将在30秒后暂停，请继续说话或点击继续",
            "timestamp", System.currentTimeMillis()
        )));
    }
}

// 处理暂停超时
private void handlePauseTimeout(String sessionId) {
    WebSocketSession session = sessions.get(sessionId);
    try {
        // 1. 发送暂停通知给前端
        if (session != null && session.isOpen()) {
            sendMessage(session, toJson(Map.of(
                "type", "control", "action", "pause_timeout",
                "message", "会话因超时已暂停,可在历史记录中恢复"
            )));
        }

        // 2. 更新数据库状态为 PAUSED，原因标记为 "timeout"
        interviewService.pauseSession(sessionId, "timeout");

        // 3. 停止 ASR 识别——释放 DashScope 的 WebSocket 连接
        sttService.stopTranscription(sessionId);

        // 4. 关闭 WebSocket 连接
        if (session != null && session.isOpen()) {
            session.close(CloseStatus.GOING_AWAY);
        }

        // 5. 清理 Handler 内存中的三个 Map
        sessions.remove(sessionId);
        sessionStates.remove(sessionId);
        lastActivityTime.remove(sessionId);
    } catch (Exception e) {
        log.error("Error handling pause timeout for session {}", sessionId, e);
    }
}
```

自动暂停与主动暂停的关键区别在于：主动暂停不关闭 WebSocket（用户可能很快恢复，保留连接可更快恢复），超时暂停关闭 WebSocket 释放连接资源（长时间无活动没必要保持连接）。

## 四、恢复后的重新连接

恢复面试后，前端需要重新建立 WebSocket 连接。这涉及 `VoiceInterviewWebSocketHandler.afterConnectionEstablished()` 的重新执行。此时 `triggerOpeningQuestionIfNeeded()` 会通过 `getHistory()` 查询到已有历史消息，判断为重连场景，不会重复发送开场问题。同样 ASR 会重新启动一个新的识别会话，LLM 的对话历史会从数据库中加载恢复，面试从暂停前的状态继续。

---

## 五、总结

暂停与恢复机制通过 `VoiceInterviewSessionStatus` 枚举的 `PAUSED` 状态标记区分面试的进行与暂定。主动暂停和恢复通过 `@Transactional` 保证 DB 状态更新的原子性，通过 `invalidateSessionCache` 和 `cacheSession` 的双向缓存操作保证 Redis 与 DB 的状态一致性——暂停时清除缓存迫使下次查询走 DB，恢复时重新写入缓存加速后续查询。Handler 内置的 `@Scheduled` 定时任务通过 `lastActivityTime` Map 追踪所有会话的活动时间，4 分 30 秒预警 + 5 分钟超时的两级机制给用户缓冲时间。主动暂停不关闭 WebSocket（用户可能很快恢复），超时暂停关闭 WebSocket 释放连接资源并停止 ASR 释放 DashScope 连接。恢复时需要前端通过返回的 `webSocketUrl` 重新建立连接，Handler 通过历史消息判断为重连场景跳过开场问题。
