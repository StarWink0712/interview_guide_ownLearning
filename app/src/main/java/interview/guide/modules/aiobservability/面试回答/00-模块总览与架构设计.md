# AI 可观测性模块总览与架构设计

## 1. 模块基础讲解

`aiobservability` 模块是 AI 面试平台里的“观测与评测中心”。它不直接完成简历评分、知识库问答或面试评估，而是把这些 AI/RAG 能力从黑盒变成可查询、可追踪、可评估的白盒系统。

模块可以拆成三条主线：

| 子系统 | 代表类 | 解决的问题 |
|---|---|---|
| AI 调用日志 | `AiInvocationLogService` | 每次结构化 LLM 调用了哪个模型、耗时多久、是否成功、重试几次 |
| RAG 检索 Trace | `RagRetrievalLogService` | 用户问了什么、查询被改写成什么、检出了哪些 chunk、分数和排序如何 |
| RAG 离线评测 | `RagEvaluationService` | 用固定测试集批量验证检索质量，统计关键词命中率和平均检索延迟 |

`AiObservabilityController` 是统一 API 入口，提供 AI 调用日志查询、RAG Trace 查询、RAG 评测集管理和评测执行接口。数据持久化使用 7 张表：

```text
ai_invocation_logs
rag_retrieval_logs
rag_retrieved_chunk_logs
rag_eval_datasets
rag_eval_cases
rag_eval_runs
rag_eval_run_case_results
```

这个模块的面试价值在于：它不是单纯“加日志”，而是围绕 AI 应用落地中最难排查的三类问题提供工程化答案：

1. 模型调用是否稳定。
2. RAG 为什么没有检出正确内容。
3. 知识库更新后检索效果有没有变好。

需要诚实说明当前边界：RAG 评测主要是“检索侧评估”，指标是关键词命中和检索延迟，不等同于最终回答正确率，也还不是完整的幻觉评估系统。

## 2. 基础面试问题

### Q1：这个模块解决了什么问题？

它解决 AI 功能上线后难排查、难复盘、难评估的问题。传统业务接口可以看 SQL 和状态码，但 AI/RAG 失败时常见问题是：模型慢、结构化输出解析失败、RAG 没检出相关文档、检索分数太低、query rewrite 改坏了问题。这个模块把这些中间过程落库，便于后台查看和后续评测。

可以这样回答：

> 我在项目里做了一个 AI 可观测性模块，用来记录 LLM 调用日志、RAG 检索链路和离线评测结果。它让我们能看到一次 AI 请求用了哪个模型、耗时多少、RAG 检索到了哪些 chunk、每个 chunk 的相似度分数是多少，并且可以用评测集批量验证知识库检索质量。

### Q2：为什么 AI 应用需要专门的可观测性？

因为 AI 调用不是确定性函数，错误来源也比普通 CRUD 多：Prompt 变化、模型输出格式不稳定、Provider 抖动、向量检索阈值不合理、知识库 chunk 质量差、query rewrite 改写错误等。如果没有中间过程记录，只能看最终回答，无法定位问题发生在哪一层。

这个模块把 AI 链路拆成可观察的阶段：调用、检索、评测。

### Q3：三个子系统之间是什么关系？

它们是从运行时到离线评估的三层能力：

```text
AI 调用日志：记录一次模型调用的收据
RAG Trace：记录一次 RAG 检索的过程
RAG 评测：批量执行测试用例，衡量检索质量
```

AI 调用日志回答“模型调用发生了什么”；RAG Trace 回答“检索阶段发生了什么”；RAG 评测回答“整体检索效果是否达标”。

### Q4：这个模块有哪些接口？

接口分三组：

1. `/api/ai-observability/invocations`：查询 AI 调用日志，支持按 `traceId` 过滤。
2. `/api/ai-observability/rag-traces`：查询 RAG 检索链路。
3. `/api/ai-observability/rag-eval`：创建评测集、添加用例、执行评测、查看评测运行结果。

Controller 层只做路由和委托，核心逻辑都在 Service。

## 3. 进阶面试问题

### Q1：这个模块和普通日志有什么区别？

普通日志主要是文本，适合临时排查；这个模块把 AI/RAG 关键字段结构化落库，可以按 traceId、时间、场景、模型、知识库、命中文档等维度查询和统计。

例如 RAG Trace 不只记录“检索完成”，而是保存：

```text
question
rewrittenQuestion
candidateQueries
knowledgeBaseIds
topK
minScore
hitCount
latencyMs
chunks(rank, score, preview, metadata)
```

这比普通日志更适合做后台页面、质量分析和回归评测。

### Q2：为什么日志写入失败时不能影响主流程？

`AiInvocationLogService.recordInvocation()` 和 `RagRetrievalLogService.recordRetrieval()` 都采用降级写入：内部 catch 异常，返回 `Optional.empty()`，不向主流程抛出。原因是观测能力是辅助系统，不能因为“记录日志失败”导致用户的简历分析或知识库问答失败。

面试里可以总结为：观测系统要尽量 fail-open，业务主链路优先。

### Q3：这个模块在链路追踪上做到了什么？有什么边界？

项目有 `TraceIdFilter`，会从 `X-Trace-Id` 请求头读取或生成 traceId，并写入 MDC。`StructuredOutputInvoker` 记录 AI 调用日志时会优先使用当前 MDC traceId。

RAG 检索 Trace 当前由 `KnowledgeBaseQueryService` 调用 `retrievalLogService.createTraceId()` 生成独立 traceId，并返回给前端。也就是说，当前 RAG 检索 traceId 和结构化输出日志 traceId 是两个可观测入口，概念上可以统一，但代码里并不是所有 RAG 答案生成都会写入 `AiInvocationLogService` 的同一个 traceId。

这是面试中要诚实讲清楚的边界。

### Q4：为什么 RAG 评测不等于最终答案评测？

当前 `RagEvaluationService` 是检索评测：它把检索出的文档文本拼起来，然后判断期望关键词是否出现。它能衡量“检索结果有没有召回包含答案线索的 chunk”，但不能判断最终 LLM 是否正确使用了这些 chunk，也不能判断回答是否忠实、完整、无幻觉。

所以它是 RAG 质量治理的第一层，不是全部。

## 4. 技术延伸问题

### Q1：如果要做完整 AI 可观测性，还需要哪些层？

可以扩展为四层：

1. 请求层：traceId、用户、接口、耗时、状态码。
2. 检索层：query rewrite、topK、minScore、命中 chunk、分数。
3. 模型层：provider、model、prompt version、tokens、latency、retry。
4. 质量层：检索召回率、答案正确率、忠实度、用户反馈。

当前模块已经覆盖检索层、部分模型层和基础质量层。

### Q2：这个模块和 Prometheus/Grafana 是什么关系？

这个模块主要把明细数据落库，适合按 trace 查看和离线评测。`common/observability` 下的 `AiMetricsRecorder`、`RagMetricsRecorder` 则把指标写入 Micrometer，适合 Prometheus/Grafana 做时间序列监控。

两者互补：

```text
数据库日志：查单次问题、复盘链路、看具体 chunk
Micrometer 指标：看整体趋势、延迟分布、失败率、告警
```

### Q3：为什么不只用 APM？

APM 能看到接口延迟和调用拓扑，但看不到 RAG 的业务语义，比如 query rewrite 内容、命中文档 chunk、相似度分数、期望关键词是否命中。这些是 AI 应用特有的业务观测字段，需要应用自己记录。

## 5. 改进方案问题

### Q1：模块当前的优点是什么？

1. 三个子系统边界清晰：调用日志、检索 Trace、离线评测。
2. 对主业务链路友好，日志写入失败不影响用户请求。
3. 不保存完整 prompt 和完整 chunk，降低存储和隐私风险。
4. RAG 评测有数据集、用例、运行、结果四层模型，便于长期积累。
5. 已有单元测试覆盖核心降级和评测逻辑。

### Q2：模块当前主要不足是什么？

1. 查询接口没有分页和复杂筛选。
2. RAG 评测是同步执行，用例多时会阻塞请求。
3. 评测指标偏基础，只是关键词命中，不是语义正确率。
4. RAG Trace 和 AI 调用日志的 traceId 尚未完全统一。
5. `RagEvalRunStatus.FAILED` 枚举存在，但 `runDataset()` 顶层异常时没有统一落库为 FAILED。
6. 没有 token 用量、成本、首 token 延迟等模型侧关键指标。

### Q3：优先改进路线是什么？

建议优先级：

1. RAG Trace 和 AI 调用日志统一 traceId。
2. 查询接口增加分页、时间范围、场景、模型、成功状态过滤。
3. RAG 评测改为异步任务，避免同步阻塞。
4. 增加答案级评测指标，例如 LLM judge、人工标注、用户反馈。
5. 增加 token/cost 统计和 Provider 维度对比。

## 6. 故障处理问题

### Q1：用户反馈 RAG 答案不相关，怎么用这个模块排查？

排查顺序：

1. 查 RAG Trace，看原始问题和 rewrittenQuestion 是否合理。
2. 看 candidateQueries 是否包含原问题，避免改写丢失语义。
3. 看 topK、minScore、hitCount，判断是不是阈值过高或召回不足。
4. 看 chunks 的 score、rank、preview，确认是否检出了正确知识库内容。
5. 如果检索正确但回答错误，再看答案生成 Prompt 和模型调用日志。

### Q2：模型调用很慢，怎么排查？

先查 `ai_invocation_logs` 的 `latencyMs`、`providerId`、`model`、`scenario`，确认是哪个场景、哪个模型慢。再结合 Micrometer 的 `app.ai.invocation.latency` 看是否普遍慢。如果只有某个场景慢，可能是 prompt 太长或重试次数多；如果所有场景慢，可能是 Provider 网络或限流问题。

### Q3：评测结果突然下降怎么办？

先对比同一评测集最近几次 Run：

1. `matchedCases / totalCases` 是否下降。
2. `avgLatencyMs` 是否上升。
3. 失败用例的 retrievedPreview 是否变了。
4. 知识库是否重新向量化，chunk 策略是否变更。
5. topK/minScore 策略是否调整。

如果只是关键词没命中但语义正确，说明评测集关键词需要扩充同义词或升级语义评测。
