# 代码优缺点与高频面试题速查

## 1. 模块基础讲解

这个模块在面试里可以概括为：

> 我给 AI 面试平台做了一个可观测与评测模块。运行时记录结构化 LLM 调用日志和 RAG 检索 Trace，离线侧提供 RAG 评测集、用例和运行结果。它能帮助排查模型调用慢、结构化输出失败、RAG 召回不足、query rewrite 改写错误等问题。当前评测主要衡量检索关键词命中率和检索延迟，还没有扩展到最终答案正确率和幻觉评估。

代码优点：

1. 三个子系统职责清晰。
2. 使用 Entity/DTO/Request 分层。
3. 写日志失败降级。
4. Prompt 和 chunk 都只存摘要/预览。
5. RAG 评测模型完整。
6. 有单元测试覆盖核心路径。

代码不足：

1. 查询缺分页。
2. 评测同步执行。
3. 指标偏检索侧。
4. traceId 尚未全链路统一。
5. 缺少权限、脱敏、保留期。
6. 缺少 token/cost 和答案级质量评估。

## 2. 基础面试问题

### Q1：请介绍 AI 可观测性模块。

标准回答：

> 这个模块主要解决 AI 功能上线后难排查的问题。我把它拆成三部分：第一是 AI 调用日志，记录模型、场景、耗时、成功状态和 prompt hash；第二是 RAG 检索 Trace，记录用户问题、改写结果、检索参数和命中 chunk；第三是 RAG 评测，用固定测试集批量验证知识库检索的关键词命中率和平均延迟。这样当用户说回答不准时，我可以从模型调用、检索链路和离线评测三个角度定位问题。

### Q2：这个模块为什么不是普通日志？

因为它保存的是结构化的 AI 业务字段，不只是文本日志。比如 RAG Trace 可以展示 topK、minScore、hitCount、chunk score、rank 和 metadata，这些字段可以被后台页面查询和用于质量分析。

### Q3：为什么要做 RAG 评测？

因为 RAG 效果不能只靠人工感觉。评测集可以固定一批问题和期望关键词，每次调整 chunk、embedding、topK、minScore 或 query rewrite 后都跑一遍，判断检索命中率和延迟是否变好。

### Q4：当前 RAG 评测指标是什么？

主要是关键词命中率和平均检索延迟：

```text
matchedCases / totalCases
avgLatencyMs
```

这是检索质量指标，不是最终答案正确率。

## 3. 进阶面试问题

### Q1：如何排查 RAG 回答不准确？

先查 RAG Trace：看原始问题、改写问题、候选查询、topK、minScore、hitCount 和命中 chunk。如果 chunk 不相关，问题在检索；如果 chunk 相关但答案错，问题在 prompt 或模型生成；如果 hitCount 为 0，排查知识库 ID、向量化状态、阈值和 embedding。

### Q2：为什么 recordInvocation 和 recordRetrieval 都要 catch 异常？

因为它们是观测写入，不是业务主逻辑。观测系统故障不能影响用户主流程，所以采用 fail-open 策略：写失败只记录 warn，返回 empty。

### Q3：当前 traceId 设计有什么不足？

HTTP 请求有 `TraceIdFilter` 注入 MDC，结构化输出日志会使用这个 traceId；但 RAG 检索 traceId 当前由 `RagRetrievalLogService.createTraceId()` 独立生成。未来最好统一 traceId，使一次请求里的 RAG 检索、答案生成和 AI 调用日志能完整串联。

### Q4：这个模块用了哪些设计模式？

1. DTO 模式：Entity 和接口返回解耦。
2. Service 层门面：Controller 不直接操作 Repository。
3. 降级模式：日志写入失败不影响主流程。
4. 事件/Trace 思想：通过 traceId 串联调用。
5. 评测运行模型：dataset/case/run/result 类似测试平台设计。

## 4. 技术延伸问题

### Q1：如何扩展成完整 AI 质量平台？

可以增加：

1. 线上用户反馈。
2. 自动把差评 trace 加入评测集。
3. 答案级 LLM-as-judge。
4. token/cost 统计。
5. Prompt 版本管理。
6. RAG 策略 A/B 测试。
7. OpenTelemetry 或 Langfuse/LangSmith 集成。

### Q2：如何回答“你怎么衡量 RAG 准确率”？

要诚实回答：

> 当前实现的是检索侧评估，不直接叫最终准确率。我们用评测集中的问题和期望关键词，检查向量检索返回的 chunk 是否包含答案线索，统计关键词命中率和检索延迟。它能反映召回质量，但不能完全代表最终回答正确率。下一步我会加入标准答案、引用校验和 LLM-as-judge 做答案级评估。

### Q3：如何用这个模块支持生产告警？

数据库日志用于排查，Micrometer 指标用于告警。可以对 AI 失败率、结构化输出重试次数、RAG no result count、retrieval latency P95、answer latency P95 设置告警。告警触发后再用 traceId 查数据库明细。

## 5. 改进方案问题

### Q1：短期最该优化什么？

1. 查询分页和筛选。
2. 统一 RAG Trace 和 AI 调用 traceId。
3. 评测运行异步化。
4. 增加 token/cost 字段。
5. 增加权限和脱敏。

### Q2：中期最该优化什么？

1. 线上反馈闭环。
2. 答案级评测。
3. 评测集版本管理。
4. 评测阈值和趋势对比。
5. 外部可观测平台集成。

### Q3：如何让它更适合面试展示？

讲法不要从“我建了几张表”开始，而要从业务问题开始：

```text
AI 回答不准如何排查？
  -> 看 RAG Trace
模型调用慢如何定位？
  -> 看 invocation latency 和 provider/model
知识库更新后效果如何证明？
  -> 跑 RAG eval dataset
```

这样能体现 AI 工程化思维，而不是 CRUD 表设计。

## 6. 故障处理问题

### Q1：AI 调用慢，怎么用模块排查？

查 `ai_invocation_logs`：按 scenario、provider、model 看 latencyMs 和 attemptCount。如果 attemptCount 高，说明重试多；如果某 provider 全部慢，可能是模型服务或网络问题；如果 promptLength 很大，可能是上下文过长。

### Q2：RAG 没命中，怎么用模块排查？

查 RAG Trace：看 rewrittenQuestion 是否合理、candidateQueries 是否包含原问题、knowledgeBaseIds 是否正确、topK/minScore 是否合适、chunks 是否为空。如果 chunks 为空，检查向量化和阈值；如果 chunks 错误，检查 chunk 策略和 metadata 过滤。

### Q3：评测命中率下降，怎么用模块排查？

对比同一 dataset 的不同 run，查看失败 case 的 retrievedPreviewJson。判断是检索参数变化、知识库内容变化、chunk/embedding 变化，还是 expectedKeywords 设计过窄。

### Q4：面试官问“这个模块有什么没做完”，怎么回答？

可以回答：

> 当前已经完成 AI 调用摘要、RAG 检索 Trace 和检索侧离线评测，但还没做到完整生产级 AI 质量平台。缺少统一 traceId、答案级评测、token/cost、用户反馈闭环、权限脱敏和异步评测。我的下一步会先统一 traceId 和分页查询，再把 RAG eval 改成异步任务，并加入答案级评估。
