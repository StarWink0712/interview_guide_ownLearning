# 技术方案对比与扩展实践

## 1. 模块基础讲解

当前模块采用的是“数据库明细日志 + Micrometer 指标 + 应用内评测框架”的组合方案。

```text
数据库明细日志：AiInvocationLog / RagRetrievalLog / RagEvalRun
Micrometer 指标：AiMetricsRecorder / RagMetricsRecorder
评测框架：RagEvaluationService
```

这个方案适合当前单体项目阶段：实现成本低、能直接和业务代码结合、可解释性强。它没有引入复杂的外部可观测平台，但已经覆盖 AI 应用最关键的问题排查路径。

## 2. 基础面试问题

### Q1：为什么不用纯日志文件？

日志文件适合全文搜索和临时排查，但不适合结构化查询和前端展示。比如按 traceId 查 RAG chunk、按 dataset 看评测结果、按模型统计失败率，用数据库表更直接。

当前模块把重要字段结构化，方便后台页面和后续统计。

### Q2：为什么不用只接 Prometheus？

Prometheus 适合指标趋势，不适合保存每次调用的详细上下文。它能告诉你 RAG 零命中率升高，但不能告诉你某次查询到底检出了哪些 chunk。

所以数据库明细日志和 Prometheus 指标是互补关系。

### Q3：为什么不用 LangSmith、Langfuse 这类平台？

这些平台更专业，能做 Prompt、Trace、Dataset、Evaluation 的完整管理。但当前项目自己实现一套轻量模块，优点是数据完全在本地、和业务模型结合紧密、依赖少，适合学习和面试展示。

如果进入生产并且团队愿意引入外部平台，可以把当前日志模型作为本地兜底，或接入 OpenTelemetry/OTLP 输出到专业平台。

## 3. 进阶面试问题

### Q1：数据库日志和 OpenTelemetry Trace 怎么选？

OpenTelemetry 更适合跨服务链路追踪，能把 HTTP、数据库、外部 API 调用串成统一 trace。数据库日志更适合保存 AI 业务语义字段，例如 rewrittenQuestion、chunk preview、expectedKeywords。

最佳实践是二者结合：

```text
OTel Trace：统一链路、耗时、span
业务数据库日志：AI/RAG 特有字段和评测结果
```

### Q2：如果接入 Langfuse/LangSmith，当前模块怎么演进？

可以把当前模块作为抽象层：

```text
AiObservationService
  -> 本地数据库实现
  -> Langfuse 实现
  -> OpenTelemetry 实现
```

业务代码只调用抽象接口，底层可以同时写本地库和外部平台。

### Q3：如何做线上反馈闭环？

可以在回答页面增加用户反馈：

```text
有帮助 / 没帮助
答案不准确
引用不相关
缺少信息
```

反馈与 RAG traceId 绑定，后续可以把低评分 trace 自动转成评测候选 case，形成“线上问题 -> 评测集 -> 回归测试”的闭环。

### Q4：如何做 A/B 测试？

在 RAG Trace 和评测 Run 中记录策略版本：

```text
chunk_strategy=v1/v2
embedding_model=text-embedding-v1
rewrite_prompt_version=v3
topK=8
minScore=0.28
```

然后对同一评测集运行不同策略，比较命中率和延迟。

## 4. 技术延伸问题

### Q1：如何做 LLM-as-judge？

在评测结果中保存检索上下文、生成答案和标准答案，然后调用另一个模型判断：

1. 是否回答了问题。
2. 是否基于上下文。
3. 是否存在幻觉。
4. 是否覆盖标准答案要点。

注意：LLM-as-judge 本身也有不稳定性，需要固定 judge prompt、模型版本，并抽样人工复核。

### Q2：如何做 RAG 回归测试流水线？

可以在 CI 或发布前跑一组核心评测集：

```text
向量化测试知识库
  -> 执行 RagEvaluationService.runDataset()
  -> 检查 matchedCases / totalCases >= 阈值
  -> 检查 avgLatencyMs <= 阈值
  -> 失败则阻止发布或输出报告
```

当前 Service 已具备手动运行基础，缺的是命令行/CI 入口和阈值判断。

### Q3：如何做自动告警？

结合 Micrometer：

1. RAG no result count 突增。
2. RAG retrieval latency P95 升高。
3. AI invocation failure rate 升高。
4. structured output retry count 升高。
5. 某 Provider/model 延迟异常。

数据库日志用于告警后的下钻排查。

## 5. 改进方案问题

### Q1：当前方案最适合什么阶段？

适合项目从“功能可用”走向“可排查、可评估”的阶段。它成本不高，但能展示 AI 工程落地能力：不是只会调模型，而是知道如何观测模型、检索链路和质量变化。

### Q2：如果系统规模扩大，最先扩展哪里？

1. 明细查询分页和归档。
2. 评测异步化。
3. 指标告警。
4. traceId 统一。
5. token/cost 统计。
6. 接入外部观测平台或 OpenTelemetry。

### Q3：如何避免可观测模块变成性能瓶颈？

1. 写入失败降级。
2. 明细日志异步化。
3. 成功调用采样。
4. 大字段预览和截断。
5. 后台查询分页。
6. 旧数据归档。

## 6. 故障处理问题

### Q1：监控显示 RAG 零命中率升高，怎么处理？

先用 Micrometer 指标确认趋势，再用 RAG Trace 下钻具体样本：

1. 看是否集中在某个知识库。
2. 看 query rewrite 是否异常。
3. 看 topK/minScore 是否变更。
4. 看向量化任务是否失败。
5. 用评测集复现并调参。

### Q2：某个模型失败率升高，怎么处理？

1. 查 `ai_invocation_logs` 按 provider/model 聚合失败。
2. 查看 errorCode 和 errorMessage。
3. 对比其他模型是否正常。
4. 临时切换 provider 或降级模型。
5. 检查 API Key、限流、网络和模型服务状态。

### Q3：评测结果和线上反馈不一致怎么办？

说明评测集覆盖不足或指标过于简单。应把线上差评 case 加入评测集，补充标准答案和关键词，必要时增加答案级评测，而不是只依赖当前关键词命中。
