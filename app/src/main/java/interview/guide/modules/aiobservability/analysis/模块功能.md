## aiobservability 模块完整分析

这是一个 **AI 可观测性**模块，专注于把"黑盒"的 AI 调用变成"白盒"——让开发者能看到每一次 AI 调用发生了什么。模块分为 **三个子系统**，层层递进。

---

### 一、整体架构概览

```
┌─────────────────────────────────────────────────────────────────┐
│                    aiobservability 模块                            │
├─────────────────┬──────────────────────┬──────────────────────────┤
│  子系统 1        │  子系统 2              │  子系统 3                 │
│  AI 调用日志      │  RAG 检索日志           │  RAG 评测                 │
│  (InvocationLog) │  (RetrievalLog)        │  (Evaluation)            │
├─────────────────┼──────────────────────┼──────────────────────────┤
│  每个 LLM 调用   │  每次 RAG 检索过程       │  离线批量评估 RAG 检索质量    │
│  的"收据"        │  的"全程回放"           │  的"自动测试框架"            │
└─────────────────┴──────────────────────┴──────────────────────────┘
         │                    │                        │
         ▼                    ▼                        ▼
  数据库表 7 张（含索引）
```

### 二、子系统详解

#### 子系统 1：AI 调用日志（AiInvocationLog）

**核心文件**：
- [AiInvocationLogService.java](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/aiobservability/service/AiInvocationLogService.java)
- [AiInvocationLogEntity.java](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/aiobservability/model/AiInvocationLogEntity.java)
- [AiInvocationLogCreateRequest.java](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/aiobservability/model/AiInvocationLogCreateRequest.java)

**一句话解释**：每次项目调用大模型（LLM）时，把这次调用的"收据"记录到数据库。

**记录了哪些信息**：

```
一次 LLM 调用
    → 谁发的？          traceId（链路追踪 ID）
    → 哪个业务场景？     scenario（"面试评估"、"题目生成"等）
    → 用的哪个模型？     providerId + model（"openai/gpt-4o"）
    → 多少次的 Prompt？  promptHash（SHA-256 去重标识）
    → 调了多久？         latencyMs（延迟，毫秒）
    → 成功还是失败？     success + errorCode + errorMessage
    → 重试了几次？       attemptCount（含首次）
```

**值得注意的设计细节**：

1. **`hash()` 方法**：把 systemPrompt + userPrompt 做 SHA-256 哈希，生成 `promptHash`。这样不需要存完整的 Prompt 内容（可能会很大），但可以通过哈希值识别相同的 Prompt 被调用了多少次。

```java
// 只存哈希，不存原文——省空间，又能做精确去重
entity.promptHash(hash(promptSource));
entity.promptLength(promptSource.length());
```

2. **`Optional.empty()` 降级**：`recordInvocation()` 内部 catch 住了所有异常，日志写入失败不会影响业务——这是正确的设计选择，因为"日志"不能成为"被日志记录的那个业务"的故障点。

3. **错误消息截断**：`truncate(request.errorMessage(), MAX_ERROR_MESSAGE_LENGTH)` — 错误消息可能很长（如 LLM 返回的完整堆栈），截断到 1000 字符防止撑爆字段。

#### 子系统 2：RAG 检索日志（RagRetrievalLog）

**核心文件**：
- [RagRetrievalLogService.java](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/aiobservability/service/RagRetrievalLogService.java)
- [RagRetrievalLogEntity.java](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/aiobservability/model/RagRetrievalLogEntity.java)
- [RagRetrievedChunkLogEntity.java](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/aiobservability/model/RagRetrievedChunkLogEntity.java)
- [RagTraceDTO.java](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/aiobservability/model/RagTraceDTO.java)

**一句话解释**：把一次 RAG 检索的"全过程"记录下来——用户问了什么、怎么改写的、检出了哪些文档块、每块的得分是多少。

**RAG 检索流程记录**：

```
用户提问                               → question
    ↓
查询改写（可选）                         → rewrittenQuestion
    ↓
生成候选查询语句                         → candidateQueriesJson
    ↓
在 pgvector 中检索                       → topK, minScore, hitCount, latencyMs
    ↓
返回命中的文档块                         → chunks[]
    ├── 知识库 ID
    ├── 文档内容预览（前 500 字符）
    ├── 向量相似度得分
    ├── 排序位置（rank）
    └── 元数据（metadataJson）
```

**涉及两张表（一对多）**：
- `rag_retrieval_logs`：检索的主记录（1 条）
- `rag_retrieved_chunk_logs`：命中的文档块（N 条，按 rank 排序）

**不存储完整的文档内容**，只存储 `chunkTextPreview`（前 500 字符预览），避免数据库变得过大。

#### 子系统 3：RAG 评测（RagEvaluation）

**核心文件**：
- [RagEvaluationService.java](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/aiobservability/service/RagEvaluationService.java)
- [RagEvalDatasetEntity.java](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/aiobservability/model/RagEvalDatasetEntity.java)
- [RagEvalCaseEntity.java](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/aiobservability/model/RagEvalCaseEntity.java)
- [RagEvalRunCaseResultEntity.java](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/aiobservability/model/RagEvalRunCaseResultEntity.java)

**一句话解释**：这是一个 **RAG 检索质量的自动化测试框架**——你准备好测试用例（问题 + 期望答案关键词），系统自动执行检索并报告结果，看知识库的 RAG 检索是否达到了预期效果。

**三层数据结构**：

```
RagEvalDataset（评测集）
    └── RagEvalCase（评测用例）N 条
            ├── question           → "Spring 的 IoC 和 DI 有什么区别？"
            ├── knowledgeBaseIds   → [1, 2]（从哪个知识库检索）
            └── expectedKeywords   → ["控制反转", "依赖注入", "容器"]
                    ↓
            RagEvalRun（一次评测执行）
                └── RagEvalRunCaseResult（每个用例的执行结果）N 条
                        ├── hitCount          → 实际检出了多少文档块
                        ├── matchedKeywordCount  → 期望关键词命中了几个
                        ├── expectedKeywordHit → true/false（是否命中至少一个关键词）
                        ├── latencyMs         → 检索耗时
                        └── retrievedPreviewJson → 检出文档的预览
```

**评测执行流程**（`RagEvaluationService.runDataset()`）：

```
1. 获取数据集下的所有评测用例
2. 为每个用例执行：
   a. 调用 KnowledgeBaseVectorService.similaritySearch() 进行向量检索
   b. 将检出的文档文本拼起来
   c. 用 String.contains() 检查期望关键词是否出现在文档中
   d. 记录匹配结果（命中关键词数、是否命中、耗时）
3. 汇总统计：
   - totalCases（总用例数）
   - matchedCases（命中关键词的用例数）
   - avgLatencyMs（平均检索耗时）
4. 将结果存入数据库
```

**评测包含 4 张数据库表**：
- `rag_eval_datasets` — 评测集
- `rag_eval_cases` — 评测用例
- `rag_eval_runs` — 单次评测执行
- `rag_eval_run_case_results` — 每个用例的执行结果

### 四、三个子系统之间的关系

这三个子系统是**从粗到细的观测层次**：

```
层次 1：AI 调用日志
    每次 LLM 调用都记一条日志 → 用于排查"哪个模型出了问题"
    粒度：一次 API 调用

层次 2：RAG 检索日志
    每次 RAG 检索的完整过程 → 用于排查"为什么没检出想要的文档"
    粒度：一次 RAG 查询的完整链路

层次 3：RAG 评测
    批量执行测试用例 → 衡量"整个 RAG 系统的检索质量"
    粒度：一个测试用例集的分析报告
```

### 五、为什么要这个模块？

**没有这个模块**，遇到 AI 相关问题只能靠猜：

| 问题 | 没有可观测性 | 有了可观测性 |
|------|------------|------------|
| "用户说面试评估好慢" | "我查查日志..." | 看 `ai_invocation_logs` 的 `latencyMs` 分布，直接定位哪个模型慢了 |
| "RAG 检不出相关内容" | "不知道向量检索出了什么问题..." | 看 `rag_retrieval_logs`，看到用户问的是什么、改写后是什么、检索出了什么 |
| "新加了一批知识库文档，效果好没好？" | "凭感觉..." | 建一个评测集跑一遍评测，直接看 `matchedCases / totalCases` 的比率 |

**这个模块把 AI 调用从"黑盒"变成了"透明白盒"**。

### 六、模块的结构特点总结

| 维度 | 评价 |
|------|------|
| **分层清晰** | Controler → Service → Repository → Entity，严格遵循项目 MVC 架构 |
| **数据完整性** | 7 张数据库表，每张都有索引和外键关联 |
| **异常降级** | 写日志的 catch 都返回 `Optional.empty()`，不影响业务 |
| **配置合理** | 字段长度限制（SHA-256 哈希 64 字符、错误消息 1000 字符、文档预览 500 字符） |
| **JSON 存字段** | `candidateQueriesJson`、`knowledgeBaseIdsJson` 等复杂结构用 JSON 存入 TEXT 字段，省去复杂的关联表设计 |
| **前端无实现** | 只有后端 API，前端页面（如 AI 调用日志列表页）尚未实现 |

**一句话总结**：这个模块是 AI 功能的"黑匣子记录仪"和"质量检测仪"——一个管运行时排障，一个管离线质量评估。
