# 隐私、安全、可靠性与降级设计

## 1. 模块基础讲解

AI 可观测性模块天然会接触敏感信息：用户问题、简历内容摘要、知识库 chunk 预览、模型错误、Prompt 长度和哈希等。因此它的设计不能只考虑“记录越多越好”，还要兼顾隐私、安全和主流程可靠性。

当前代码体现了几个关键原则：

| 原则 | 代码体现 |
|---|---|
| 不影响主流程 | 日志写入失败返回 `Optional.empty()` |
| 不存完整 Prompt | 只存 `promptHash` 和 `promptLength` |
| 不存完整 chunk | 只存 `chunkTextPreview` 前 500 字符 |
| 错误信息限长 | AI 调用错误截断到 1000 字符 |
| DTO 对外暴露 | 不直接返回 Entity |
| 请求参数校验 | 创建评测集和添加 case 使用 `@Valid` |

这个模块的可靠性目标不是“日志一定百分百写入”，而是“日志尽量写入，但绝不能拖垮业务主链路”。

## 2. 基础面试问题

### Q1：为什么日志写入失败不抛异常？

因为日志和观测是辅助能力。用户真正关心的是简历分析、面试评估或知识库回答是否成功。如果数据库日志表暂时不可用，不应该让业务请求失败。

这是一种降级设计：观测失败可以接受，业务失败不能被观测系统放大。

### Q2：为什么不保存完整 Prompt？

完整 Prompt 可能包含用户简历、面试回答、内部系统指令、知识库内容。保存完整 Prompt 会带来隐私泄露、权限控制、存储膨胀和合规风险。

当前用 SHA-256 hash 和长度代替原文，是一个比较稳妥的折中。

### Q3：chunk 预览会不会也有隐私风险？

会有。虽然只保存前 500 字符，但仍可能包含用户上传资料中的敏感内容。所以生产环境应该配合权限控制、脱敏、保留期和审计。

当前实现降低了风险，但没有完全消除风险。

### Q4：为什么错误信息要截断？

外部模型错误可能包含长响应或堆栈，直接保存可能导致数据库膨胀，也可能把敏感内容带入错误信息。截断能降低存储和展示风险。

## 3. 进阶面试问题

### Q1：降级写入会不会导致排查信息丢失？

会有这个风险。降级写入的取舍是：业务主流程优先。如果观测写入失败，确实会失去某些排查信息。

生产上可以补偿：

1. 记录本地 warn 日志。
2. 异步队列写观测日志。
3. 使用 Outbox 或缓冲队列。
4. 对日志写入失败率做 Micrometer 指标和告警。

### Q2：Prompt hash 有什么安全边界？

hash 不是加密，不能从 hash 直接还原原文，但如果 prompt 空间很小，理论上可以暴力猜测。对大段用户输入风险较低，但对固定短 prompt 可能被枚举。

因此 hash 适合做去重和统计，不适合当作强隐私保护的唯一手段。如果需要更强保护，可以加盐或 HMAC。

### Q3：Trace 数据如何做权限隔离？

需要在日志表加 `userId`、`tenantId`、`requestPath` 等字段，并在查询接口加权限过滤。否则只要知道 traceId，就可能查到其他用户的 RAG Trace 或 AI 调用摘要。

当前模块偏后台管理视角，还没有完整用户权限隔离。

### Q4：AI 可观测数据是否应该入版本控制？

不应该。可观测数据是运行时数据，可能包含用户输入摘要、chunk 预览和错误信息，只应存在数据库或受控日志系统中，不应进入代码仓库。

## 4. 技术延伸问题

### Q1：如何设计更安全的观测日志？

可以采用分级记录：

| 等级 | 内容 |
|---|---|
| Basic | traceId、scenario、model、latency、success |
| Debug | promptHash、promptLength、错误摘要 |
| Sensitive | 脱敏 prompt、chunk preview，仅短期保存 |

默认生产环境只开 Basic 和部分 Debug，需要临时排障时按 traceId 开启短时敏感采样。

### Q2：如何做敏感信息脱敏？

可以在保存前统一经过脱敏器：

1. 手机号、邮箱、身份证。
2. API Key、Token。
3. 地址、姓名等个人信息。
4. 公司内部文档关键标识。

脱敏器应在 `RagRetrievalLogService.preview()` 和未来 prompt 记录处统一接入。

### Q3：如何保证观测日志高可用？

如果日志对业务分析非常关键，可以从同步写数据库改为异步写：

```text
业务线程 -> 内存队列/Redis Stream -> 日志消费者 -> 数据库
```

但仍要设置队列容量和丢弃策略，避免观测流量反压业务。

## 5. 改进方案问题

### Q1：当前安全设计的优点是什么？

1. 不保存完整 Prompt。
2. chunk 只存预览。
3. 错误信息截断。
4. DTO 隔离 Entity。
5. 观测失败不影响主业务。

### Q2：当前安全和可靠性还有哪些不足？

1. 缺少用户/租户字段，权限隔离不完整。
2. chunk preview 未脱敏。
3. 没有日志保留期策略。
4. 没有观测写入失败率指标。
5. traceId 查询如果暴露给普通用户，需要防止越权。
6. 没有对评测集操作做审计。

### Q3：如何制定数据保留策略？

建议：

1. AI 调用日志保留 30-90 天。
2. RAG Trace 明细保留 30 天，之后归档或只保留摘要。
3. 评测集和评测结果长期保留。
4. 敏感 preview 设置更短 TTL。
5. 提供手动清理和归档任务。

## 6. 故障处理问题

### Q1：观测日志写入失败怎么办？

短期：看应用 warn 日志和数据库连接状态。因为主流程不会失败，用户可能无感。

长期：增加观测写入失败计数器、告警和异步重试机制。如果日志非常关键，可以将观测事件先写入队列再异步落库。

### Q2：用户要求删除个人数据怎么办？

需要能按用户、traceId、时间范围定位相关日志。目前模型没有 userId 字段，删除会比较困难。生产改进应给 AI 日志和 RAG Trace 增加用户/租户归属字段，并提供清理工具。

### Q3：排查时发现 chunk preview 包含敏感信息怎么办？

处理：

1. 立即限制相关接口权限。
2. 清理或脱敏历史数据。
3. 缩短 preview 长度或关闭 preview。
4. 增加保存前脱敏。
5. 增加访问审计。
