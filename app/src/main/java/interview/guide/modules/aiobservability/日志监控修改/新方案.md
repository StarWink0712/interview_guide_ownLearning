之前的设计是监控的结构化重试的日志，是错误的，应该记录的是llm调用重试的日志。
可以这样设计：**把“结构化输出质量”和“Provider 调用质量”拆成两套观测体系**。

你现在的 `StructuredOutputInvoker` 更适合记录：

> 模型返回内容能不能转成 Java DTO。

但真正的 provider 监控应该记录：

> 这次 HTTP/API 调用有没有成功、重试了几次、是超时、5xx、429 还是网络异常。

**一、整体架构**
建议加一层 `LlmCallExecutor` 或 `ProviderCallRecorder`：

```text
业务 Service
  ↓
LlmCallExecutor / StructuredOutputInvoker
  ↓
ChatClient
  ↓
OpenAiChatModel
  ↓
RetryTemplate
  ↓
RestClient / OpenAiApi
  ↓
模型 Provider
```

其中观测分两层：

```text
Provider 层指标：
HTTP 调用次数、状态码、超时、5xx、429、retry 次数、最终是否成功

结构化层指标：
JSON 解析是否成功、结构化 attemptCount、schema 错误、最终 DTO 是否成功
```

这样就不会混淆“模型服务失败”和“JSON 解析失败”。

**二、Provider 调用日志表**
建议新增一张总表，记录一次逻辑上的模型调用。

比如 `ai_provider_invocation_logs`：

```sql
create table ai_provider_invocation_logs (
  id bigserial primary key,
  trace_id varchar(64),
  invocation_id varchar(64) not null,

  scenario varchar(100),
  provider_id varchar(80),
  model varchar(120),
  client_variant varchar(30), -- DEFAULT / PLAIN / VOICE / EMBEDDING
  operation varchar(40),      -- CHAT / STREAM_CHAT / EMBEDDING

  streaming boolean default false,
  structured_output boolean default false,

  started_at timestamp not null,
  completed_at timestamp,
  latency_ms bigint,

  success boolean,
  attempt_count int,
  retry_count int,

  final_http_status int,
  error_category varchar(50), -- TIMEOUT / NETWORK / RATE_LIMIT / SERVER_5XX / CLIENT_4XX
  exception_type varchar(160),
  error_message text,

  fallback_from_provider varchar(80),
  fallback_to_provider varchar(80),

  created_at timestamp not null default now()
);

create index idx_ai_provider_trace on ai_provider_invocation_logs(trace_id);
create index idx_ai_provider_provider_time on ai_provider_invocation_logs(provider_id, created_at);
create index idx_ai_provider_success_time on ai_provider_invocation_logs(success, created_at);
```

这张表回答的是：

> 一次业务调用最终有没有成功？用了哪个 provider？重试了几次？最终失败原因是什么？

**三、Provider 尝试明细表**
如果你想看到 Spring AI 每一次底层重试，可以再加一张明细表。

比如 `ai_provider_attempt_logs`：

```sql
create table ai_provider_attempt_logs (
  id bigserial primary key,
  invocation_id varchar(64) not null,

  provider_id varchar(80),
  model varchar(120),
  operation varchar(40),

  attempt_no int not null,
  started_at timestamp not null,
  latency_ms bigint,

  http_status int,
  success boolean,
  retryable boolean,

  error_category varchar(50),
  exception_type varchar(160),
  error_message text,

  created_at timestamp not null default now()
);

create index idx_ai_attempt_invocation on ai_provider_attempt_logs(invocation_id);
create index idx_ai_attempt_provider_time on ai_provider_attempt_logs(provider_id, created_at);
```

这张表回答的是：

> 第 1 次请求失败原因是什么？第 2 次是不是 5xx？第 3 次有没有成功？到底是不是 Spring AI 在重试？

如果担心数据量太大，明细表可以只记录失败 attempt，成功只在总表里汇总。

**四、Micrometer 指标**
数据库用于排查，Micrometer 用于监控和告警。可以设计这些指标：

```text
app.ai.provider.request.count
tags: provider, model, operation, status, error_category

app.ai.provider.request.latency
tags: provider, model, operation, status

app.ai.provider.retry.count
tags: provider, model, operation, error_category

app.ai.provider.attempt.count
tags: provider, model, operation, http_status, error_category

app.ai.provider.failover.count
tags: from_provider, to_provider, reason

app.ai.provider.circuit.state
tags: provider
value: 0=CLOSED, 1=HALF_OPEN, 2=OPEN
```

这些指标可以在 Prometheus/Grafana 里看：

- 某个 provider 的失败率
- 5xx 是否突然升高
- 平均延迟和 P95/P99
- retry 次数是否变多
- 是否频繁切换 provider

**五、代码怎么接入**
你项目里现在是手动创建 `OpenAiChatModel`：

```java
new OpenAiChatModel(
  openAiApi,
  options,
  toolCallingManager,
  RetryUtils.DEFAULT_RETRY_TEMPLATE,
  observationRegistry
);
```

更好的做法是不要直接用默认模板，而是做一个工厂：

```java
RetryTemplate retryTemplate = aiRetryTemplateFactory.create(providerId, model);
```

这个 `RetryTemplate` 里挂 `RetryListener`：

```java
retryTemplate.setRetryListener(new RetryListener() {
  @Override
  public void onRetryFailure(RetryPolicy policy, Retryable<?> retryable, Throwable throwable) {
    recorder.recordRetry(providerId, model, throwable);
  }
});
```

注意：`RetryListener` 适合记录“发生了一次 retry failure”，但它不适合做 provider 切换。因为切换 provider 是业务级决策，应该放在外层调用器里。

要记录每一次真实 HTTP 请求，最好在 `ApiPathResolver` 构建 `RestClient` 时加 `ClientHttpRequestInterceptor`：

```java
restClientBuilder.requestInterceptor(
  new AiProviderHttpObservationInterceptor(providerId, model, recorder)
);
```

这个 interceptor 负责记录：

- 请求开始时间
- HTTP status
- latency
- 网络异常
- exceptionType
- errorCategory

这样 Spring AI 内部无论重试几次，每一次 HTTP 请求都会经过 interceptor，指标才是真实的。

**六、Provider 熔断和切换**
切换 provider 不要放在 Spring AI RetryTemplate 里面，而是放在更外层：

```text
调用 provider A
  ↓
Spring AI 内部重试
  ↓
最终还是失败
  ↓
ProviderHealthService 记录失败
  ↓
如果连续失败达到阈值，标记 A 为 OPEN
  ↓
选择 provider B
  ↓
重新组装 prompt，再调用 B
```

可以加一个 provider 健康状态表，或者用 Redis 存运行时状态。

例如 `llm_provider_health`：

```sql
create table llm_provider_health (
  provider_id varchar(80) primary key,
  state varchar(20) not null, -- CLOSED / OPEN / HALF_OPEN
  consecutive_failures int not null default 0,
  open_until timestamp,
  last_error_category varchar(50),
  last_error_message text,
  updated_at timestamp not null default now()
);
```

多实例部署时，建议用 Redis 存状态，因为熔断状态需要所有应用实例共享。

**七、很关键的一点**
不是所有失败都应该影响 provider 健康。

应该计入 provider 失败的：

```text
超时
连接失败
5xx
429
网络异常
```

不应该计入 provider 失败的：

```text
JSON 解析失败
字段不符合 DTO
业务校验失败
用户输入太长
Prompt 设计不好
```

因为 JSON 解析失败可能是 prompt/schema 问题，不一定是 provider 服务不稳定。

你可以这样总结：

> 我会把 AI 监控拆成两层。Provider 层记录真实的模型 API 调用，包括每次 HTTP attempt、状态码、异常类型、Spring AI retry 次数和最终成功失败，用于判断模型厂商是否稳定；结构化层记录 JSON 解析成功率和 DTO 转换失败原因，用于优化 prompt 和 schema。Provider 连续失败时再由外层调用器做熔断和备用 provider 切换，而不是把切换逻辑塞进 Spring AI 的 RetryTemplate。
