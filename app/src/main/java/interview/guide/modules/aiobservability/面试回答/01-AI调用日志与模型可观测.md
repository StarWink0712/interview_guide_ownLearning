# AI 调用日志与模型可观测

## 1. 模块基础讲解

AI 调用日志由 `AiInvocationLogService`、`AiInvocationLogEntity`、`AiInvocationLogRepository` 组成，核心目标是记录每次结构化 LLM 调用的“调用收据”。

它记录的信息包括：

| 字段 | 含义 |
|---|---|
| `traceId` | 链路追踪 ID，用于关联同一次请求 |
| `scenario` | 调用场景，如简历评分、面试评估 |
| `providerId` / `model` | 使用的 LLM Provider 和模型 |
| `promptVersion` | Prompt 或调用策略版本 |
| `promptHash` | systemPrompt + userPrompt 的 SHA-256 哈希 |
| `promptLength` | Prompt 总字符长度 |
| `streaming` | 是否流式调用 |
| `structuredOutput` | 是否结构化输出 |
| `attemptCount` | 总尝试次数，含首次调用和重试 |
| `success` | 最终是否成功 |
| `latencyMs` | 总耗时 |
| `errorCode` / `errorMessage` | 失败错误码和截断后的错误信息 |

数据来源主要是 `StructuredOutputInvoker`。它在结构化输出成功或重试耗尽失败时调用 `recordAiInvocation()`，再委托 `AiInvocationLogService.recordInvocation()` 落库。

这个设计的重点不是保存完整 Prompt，而是保存摘要信息：Prompt hash、长度、模型、耗时、成功状态。这样既能做排查和统计，又避免把敏感输入和大段 prompt 直接写入数据库。

## 2. 基础面试问题

### Q1：AI 调用日志记录了什么？

记录一次 LLM 调用的关键元数据：业务场景、Provider、模型、Prompt 版本、Prompt hash、Prompt 长度、是否结构化输出、尝试次数、是否成功、耗时、错误码和错误信息。

一句话：它记录“调用过什么模型、为什么调用、花了多久、成没成功”。

### Q2：为什么只存 prompt hash，不存完整 prompt？

完整 prompt 可能包含用户隐私、简历内容、面试回答、知识库片段，也可能非常长。直接保存会带来存储成本和安全风险。

存 hash 的好处是：

1. 可以判断两个调用是否使用了相同 prompt。
2. 可以统计 prompt 版本或模板的调用频率。
3. 不暴露原始用户内容。
4. 数据库体积可控。

当前测试也验证了 `recordInvocation` 只保存 hash 和长度，不保存完整 prompt 字段。

### Q3：日志写入失败会怎样？

`recordInvocation()` 内部 catch 所有异常，记录 warn 日志并返回 `Optional.empty()`，不会影响主业务流程。

这是合理设计，因为可观测系统不能成为业务主链路的单点故障。比如简历评分已经成功，不应该因为日志表写入失败让用户看到评分失败。

### Q4：如何按 traceId 查一次请求里的 AI 调用？

Controller 提供：

```text
GET /api/ai-observability/invocations?traceId=xxx
```

Service 调用 `findByTraceIdOrderByCreatedAtAsc()`，按创建时间升序返回同一 traceId 下的所有 AI 调用。

## 3. 进阶面试问题

### Q1：traceId 是怎么来的？

HTTP 请求进入时，`TraceIdFilter` 从 `X-Trace-Id` 读取 traceId；如果请求头没有，就生成 UUID，并写入 SLF4J MDC 和响应头。

`StructuredOutputInvoker` 调用时会先从 `TraceIdFilter.currentTraceId()` 读取当前线程 MDC。如果拿不到，且注入了 `AiInvocationLogService`，就生成一个新的 traceId。

这保证同步 HTTP 请求里的结构化 LLM 调用可以被串起来。异步任务或非 HTTP 线程则可能生成独立 traceId。

### Q2：`attemptCount` 有什么用？

`StructuredOutputInvoker` 支持结构化输出重试。`attemptCount` 记录总尝试次数，可以判断某个业务场景是不是经常需要重试。

例如：

```text
attemptCount=1：首次成功
attemptCount=2：重试一次后成功
attemptCount=3 且 success=false：多次重试后仍失败
```

这对优化 prompt、模型选择、JSON 修复策略非常有价值。

### Q3：为什么错误消息要截断到 1000 字符？

模型错误、网络异常、解析异常可能包含长堆栈或大段响应。如果不截断，数据库字段和前端展示都会有风险。截断保留排查核心信息，同时防止异常数据撑大日志表。

### Q4：`AiMetricsRecorder` 和 `AiInvocationLogService` 有什么区别？

`AiMetricsRecorder` 记录 Micrometer 指标，适合看趋势和告警；`AiInvocationLogService` 记录数据库明细，适合查单次问题。

| 能力 | 适合用途 |
|---|---|
| Micrometer 指标 | 成功率、延迟分布、按模型聚合、告警 |
| 数据库日志 | 追踪某次调用详情、错误原因、trace 查询 |

## 4. 技术延伸问题

### Q1：如果要做模型成本统计，还需要记录什么？

需要增加：

1. input tokens。
2. output tokens。
3. total tokens。
4. 单价版本。
5. cost。
6. first token latency。
7. provider request id。

这样可以按场景和模型统计成本，例如简历评分每天消耗多少 token，哪个模型性价比最高。

### Q2：如果要记录完整 Prompt，怎么保证安全？

不建议默认记录完整 Prompt。如果确实需要，可以：

1. 只在 debug 环境开启。
2. 对简历、手机号、邮箱等敏感信息脱敏。
3. 加密存储。
4. 设置短 TTL。
5. 严格限制访问权限和审计。
6. 前端默认不展示，仅管理员可临时查看。

### Q3：如何判断是模型问题还是 Prompt 问题？

结合字段看：

1. 同一 promptHash 在不同模型都失败，可能是 Prompt 或输出格式约束有问题。
2. 同一 scenario 某个 model 失败率高，可能是模型能力或 Provider 稳定性问题。
3. `attemptCount` 普遍较高，说明结构化输出格式不稳定。
4. `promptLength` 过长且 latency 高，说明可能上下文太大。

## 5. 改进方案问题

### Q1：当前 AI 调用日志的优点是什么？

1. 只存摘要，兼顾可观测和隐私。
2. 写入失败降级，不影响业务。
3. 支持 traceId 和场景维度查询。
4. 能记录重试次数和最终成功状态。
5. 已有测试覆盖 hash 生成、降级写入和不存完整 prompt。

### Q2：当前还有哪些不足？

1. 没有分页和按 scenario/provider/model/success 的组合筛选。
2. 没有 token 和成本统计。
3. 没有保存 provider request id，不便于和模型厂商后台对账。
4. 仅记录结构化输出调用，直接 `ChatClient` 调用不一定进入这张表。
5. `promptVersion` 当前固定为 `structured-output-v1`，还没有和真实 Prompt 模板版本管理打通。

### Q3：怎么优化查询能力？

可以增加：

```text
GET /api/ai-observability/invocations?page=0&size=20
  &scenario=resume_grading
  &providerId=dashscope
  &model=qwen-plus
  &success=false
  &from=...
  &to=...
```

Repository 使用 `Specification` 或 QueryDSL 构建动态查询，并增加组合索引。

## 6. 故障处理问题

### Q1：结构化输出经常失败，怎么排查？

1. 查失败日志的 `scenario`，定位哪个业务场景。
2. 看 `attemptCount`，判断是否经过多次重试。
3. 看 `errorCode` 和 `errorMessage`，判断是模型返回非法 JSON、网络超时还是业务解析失败。
4. 看 `promptHash` 是否集中在同一模板。
5. 对比不同 `providerId/model` 的成功率。

### Q2：AI 调用日志查不到，可能是什么原因？

可能原因：

1. 该调用没有走 `StructuredOutputInvoker`，例如 RAG 普通知识库回答直接使用 `ChatClient`。
2. `AiInvocationLogService` 没有注入或写入失败。
3. traceId 查错了，HTTP traceId 和 RAG 检索 traceId 当前不一定是同一个。
4. 数据库日志表连接异常。

### Q3：日志表增长太快怎么办？

可以：

1. 增加保留策略，比如只保留最近 30/90 天。
2. 定期归档到冷存储。
3. 列表查询默认分页。
4. 只保存失败和慢调用的详细日志，成功调用采样。
5. 对高频场景做采样率配置。
