# 接口与数据模型面试问答

## 1. 模块基础讲解

`AiObservabilityController` 统一暴露 AI 可观测性 API，分为三组：

| 分组 | 接口 | 作用 |
|---|---|---|
| AI 调用日志 | `/api/ai-observability/invocations` | 查询最近调用或按 traceId 查询 |
| RAG Trace | `/api/ai-observability/rag-traces` | 查询单次或最近检索链路 |
| RAG 评测 | `/api/ai-observability/rag-eval` | 管理评测集、用例、运行结果 |

数据模型上，模块采用 Entity + DTO + Request record 的方式：

```text
Request：前端入参，如 CreateRagEvalDatasetRequest
Entity：JPA 持久化，如 RagEvalRunEntity
DTO：接口返回，如 RagEvalRunDTO
Repository：Spring Data JPA 查询
```

复杂结构如 `knowledgeBaseIds`、`expectedKeywords`、`candidateQueries` 用 JSON 字符串存储到 TEXT 字段，降低表结构复杂度。

## 2. 基础面试问题

### Q1：为什么 Controller 只做路由和委托？

因为日志记录、评测执行、JSON 序列化、异常降级都属于业务逻辑，应该放在 Service。Controller 只负责参数绑定、校验和返回 `Result<T>`，符合项目的分层规范。

### Q2：为什么用 record 作为 Request/DTO？

Request/DTO 是不可变数据载体，用 Java record 简洁清晰，天然提供构造器和访问方法，也符合项目规范。

### Q3：为什么不直接返回 Entity？

Entity 是持久化模型，可能包含 JPA 细节和内部字段。DTO 是稳定的 API 视图，能避免前端依赖数据库结构，也符合“禁止直接返回 Entity 给前端”的项目规范。

### Q4：为什么部分列表只取最近 50 或 20 条？

AI 调用日志和 RAG Trace 是高频数据，不适合默认返回全部。当前 `listRecentInvocations()` 返回最近 50 条，`listRecentTraces()` 返回最近 20 条，是一种保护性设计，避免接口和前端被大量日志拖慢。

## 3. 进阶面试问题

### Q1：JSON TEXT 存复杂字段有什么优缺点？

优点：

1. 表结构简单。
2. 写入和读取方便。
3. 适合低频查询的展示型字段。

缺点：

1. 不方便按 JSON 内部字段过滤。
2. 无法强约束数组元素类型。
3. 统计分析能力弱。
4. 数据库索引利用有限。

当前 `expectedKeywordsJson`、`knowledgeBaseIdsJson`、`candidateQueriesJson` 主要用于展示和复盘，所以用 JSON TEXT 可以接受。如果后续要按知识库 ID 大量筛选评测用例，应拆表或用 PostgreSQL JSONB。

### Q2：`RagTraceDTO` 为什么包含 chunks 列表？

因为排查 RAG 问题时只看主记录不够。必须看到每个命中 chunk 的内容预览、分数、排序和元数据，才能判断是召回不足、排序错误还是知识库内容本身质量差。

所以 `RagTraceDTO` 是主从结构，包含 `List<RagRetrievedChunkDTO>`。

### Q3：评测运行结果为什么分 run 和 case result 两张表？

一次 run 是整体评测执行，保存策略、总用例数、命中用例数、平均延迟和状态。case result 是每个用例的执行结果，保存问题、命中数、关键词匹配数、预览和错误。

拆成两张表后，可以：

1. 查看整体趋势。
2. 下钻到失败用例。
3. 同一个 dataset 多次运行形成历史对比。

### Q4：当前 Repository 查询有什么改进空间？

当前 Repository 多是简单方法，例如 `findTop50ByOrderByCreatedAtDesc()`、`findByTraceIdOrderByCreatedAtAsc()`、`findByDatasetIdOrderByIdAsc()`。它们简单可靠，但缺少分页和动态筛选。

随着日志量增长，应增加 Pageable 和组合查询。

## 4. 技术延伸问题

### Q1：如果做前端页面，怎么组织？

可以做三个 tab：

1. AI 调用日志：按时间、场景、模型、成功状态筛选。
2. RAG Trace：展示问题、改写、参数、命中 chunk 列表。
3. RAG 评测：管理 dataset/case，执行 run，查看失败 case。

RAG Trace 页面最好支持从 `traceId` 直接打开详情，这样用户反馈问题时能快速定位。

### Q2：如何设计权限？

AI 可观测性包含用户问题、chunk 预览、错误信息，可能有敏感数据。权限应分层：

```text
普通用户：只能看自己的请求状态或有限 trace
开发/运维：可看日志摘要和脱敏预览
管理员：可看完整排障信息
```

还应对访问详情接口记录审计日志。

### Q3：如何做数据生命周期管理？

可以按数据类型设置不同保留期：

| 数据 | 推荐保留 |
|---|---|
| AI 调用日志 | 30-90 天 |
| RAG Trace 明细 | 30 天在线，之后归档 |
| RAG 评测集和结果 | 长期保留 |
| chunk preview | 可配置脱敏或缩短保留期 |

评测结果是质量资产，通常比线上 trace 保存更久。

## 5. 改进方案问题

### Q1：接口层最需要补什么？

1. 分页。
2. 时间范围过滤。
3. 按 scenario/provider/model/status 筛选 AI 调用。
4. 按 knowledgeBaseId、hitCount、minScore 筛选 RAG Trace。
5. 删除或归档评测集/用例。
6. 批量导入评测用例。

### Q2：数据模型最需要补什么？

1. `tenantId/userId`，支持权限隔离。
2. token/cost 字段。
3. RAG Trace 的 answer generation 字段。
4. 评测集版本、标签、创建人。
5. case 的标准答案或相关 chunk 标注。
6. run 的失败状态和失败原因。

### Q3：索引可以怎么优化？

已有索引包括 trace、scenario、created_at、dataset_id、run_id、knowledge_base_id 等。后续可以增加：

1. AI 日志：`scenario, created_at`，`provider_id, model, created_at`，`success, created_at`。
2. RAG Trace：`created_at`，`session_id`，`trace_id` 唯一或普通索引。
3. 评测结果：`run_id, expected_keyword_hit`。

## 6. 故障处理问题

### Q1：列表接口慢怎么办？

原因通常是数据量增长但没有分页。处理方式：

1. 增加分页参数。
2. 默认按时间范围查询。
3. 加合适索引。
4. 对 chunk 明细延迟加载，列表只返回摘要。
5. 归档旧数据。

### Q2：RAG Trace 详情慢怎么办？

可能是 chunks 查询或 JSON 字段太大。优化：

1. 限制每次记录的 chunk 数。
2. 列表页不加载 chunks，详情页再查。
3. 批量查询 recent traces 的 chunks，避免 N+1。
4. 缩短 chunk preview。

### Q3：评测集误删或用例污染怎么办？

当前代码没有删除接口，也没有版本管理。生产上应增加：

1. 软删除。
2. 评测集版本。
3. 用例修改历史。
4. 导入导出。
5. 管理员审计。
