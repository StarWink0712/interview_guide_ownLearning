是的，但**存储的内容和目的完全不同**，不存在冗余。

## 数据库（AsyncTaskEntity）

**存储完整生命周期信息，是任务状态的真源（Source of Truth）。**

| 字段 | 说明 |
|------|------|
| `id` / `taskType` / `businessId` | 任务标识 |
| `status` | 生命周期状态（PENDING → PROCESSING → COMPLETED/FAILED...） |
| `retryCount` / `maxRetryCount` | 重试信息 |
| `messageId` | 对应的 Stream 消息 ID |
| `lastError` | 失败原因 |
| `payloadJson` | 原始载荷（如简历文本，用于人工排查） |
| `activeFlag` / `activeKey` | 活跃任务去重 |
| `createdAt` / `updatedAt` | 时间戳 |

**用途**：前端轮询查状态、管理后台列表、重试/取消操作、历史追溯。

---

## Redis Stream（消息体）

**只存消费者干活需要的最少字段，是任务流转的运输层。**

```java
// buildRetryMessage 构建的消息体（以 RESUME_ANALYZE 为例）
{
    "taskId": "42",
    "businessId": "123",
    "retryCount": "0",
    "resumeId": "123"
}
```

只有 4 个字段，消费者拿到后：通过 `taskId` 调 `markProcessing()` 更新数据库状态，通过 `resumeId` 查简历内容开始分析。

## 两者关系

```
Producer（业务Service）
    │
    ├── ① 数据库: createOrReusePendingTask(taskId=42, status=PENDING)
    │
    └── ② Stream: XADD {taskId:42, resumeId:123, ...}
            │
            ▼
Consumer 拉取消息
    │
    ├── ③ 数据库: markProcessing(taskId=42) → status=PROCESSING
    ├── ④ 执行业务逻辑（AI分析/向量化）
    └── ⑤ 数据库: markCompleted(taskId=42) → status=COMPLETED
```

数据库是**状态机**，Stream 是**运输带**。消费者从 Stream 拿到"谁要处理"（taskId + businessId），然后去数据库读完整信息、更新状态。Stream 消息本身不存状态，消费完就 ACK 删除。
比如需要异步ai分析简历，简历的文本内容不会存到消息队列中，只会存到数据库中。消费者拿到消息id之后，再去数据库中查询简历文本即可。
没错，你理解得完全正确。看实际代码就能印证：

**Stream 消息体**（构建于 `AsyncTaskService.buildRetryMessage`）：

```java
// 消息只存标识字段，不存业务数据
{taskId: "42", businessId: "123", retryCount: "0", resumeId: "123"}
```

**数据库**（`AsyncTaskEntity`）存了 `payloadJson` 存业务数据：

```java
payloadJson → {"resumeText": "张三，3年Java开发经验..."}  // 完整简历文本
```

消费者拿到消息后的实际流程：

```
Consumer 拉取消息 → {taskId:42, resumeId:123}
    │
    ├── markProcessing(taskId=42)           → 数据库更新状态
    ├── resumeRepo.findById(123)            → 从数据库查简历文本
    ├── AI分析(resumeText)                  → 用简历文本调 LLM
    └── markCompleted(taskId=42)            → 数据库更新状态
```

Stream 消息只有几十字节的标识字段，简历文本再大也只走数据库。这是正确的设计——**消息队列不该当数据库用**，大文本进 Stream 会撑爆 Redis 内存，也违背 Stream 轻量传递的设计意图。`payloadJson` 存数据库主要是给运维人工排查用的，消费者正常走自己的业务查询链路。
