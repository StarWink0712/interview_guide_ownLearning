# 高频面试题速查

## 1. 模块基础讲解

这一篇用于面试前快速复习。异步任务模块可以用一段话总括：

> 这个模块是 AI 面试平台的统一异步任务控制面。简历分析、知识库向量化、面试评估、语音面试评估这些耗时操作都会先写入 `async_tasks` 任务表，再通过 Redis Stream 投递轻量消息给后台消费者。数据库负责状态查询、重试、取消和审计，Redis Stream 负责异步消费、ACK 和 pending 恢复。公共 Producer/Consumer 模板封装了投递、消费、重试、ACK、TraceId 和指标记录，具体业务只实现自己的 payload 解析和业务处理。

建议面试表达顺序：

```text
业务背景
  -> 为什么要异步
  -> 整体架构：任务表 + Redis Stream
  -> 状态机
  -> 可靠性：幂等、重试、pending 恢复
  -> 可运维：查询、取消、手动重试
  -> 不足与优化
```

## 2. 基础面试问题

### Q1：请介绍一下你的异步任务模块。

标准回答：

> 我把平台里的耗时 AI 操作抽象成统一异步任务，包括简历分析、知识库向量化、面试评估和语音面试评估。设计上分成两部分：数据库任务表保存任务状态和错误信息，Redis Stream 负责消息投递和后台消费。前端拿到 taskId 后可以查询任务状态，管理后台可以筛选失败任务、手动重试或取消。消费者侧用公共模板封装 ACK、重试和 pending 恢复，业务模块只关心自己的处理逻辑。

### Q2：为什么要异步？

因为这些任务耗时且不稳定：文件解析、LLM 调用、向量化写入都可能几秒到几十秒。如果同步放在 HTTP 请求里，用户等待时间长，也容易超时。异步后，请求快速返回，后台慢慢处理，前端通过任务状态展示进度。

### Q3：你用了什么技术实现异步？

使用 Redis Stream 作为消息队列，配合消费者组、ACK、PEL 和 XAUTOCLAIM。任务状态用 PostgreSQL/JPA 保存，服务层用 `AsyncTaskService` 管理生命周期。

### Q4：异步任务有哪些状态？

`PENDING`、`PROCESSING`、`COMPLETED`、`FAILED`、`CANCELLED`、`DEAD_LETTER`。其中 `DEAD_LETTER` 主要表示自动重试耗尽或重试入队失败，需要人工介入。

### Q5：前端如何知道任务完成？

前端拿到 `taskId` 后调用 `GET /api/async-tasks/{id}` 轮询。状态为 `COMPLETED` 时展示结果，`FAILED` 或 `DEAD_LETTER` 时展示失败，`CANCELLED` 时提示取消。

## 3. 进阶面试问题

### Q1：如何保证消息不丢？

分三层：

1. Redis Stream 消费者组要求处理后 XACK，未 ACK 消息会进入 PEL。
2. `PendingMessageRecoveryService` 在启动和每 60 秒定时用 XAUTOCLAIM 恢复 pending 消息。
3. 任务表保存状态，即使消息失败，也能通过管理后台重试。

但要诚实说明：它不是严格 exactly-once，而是至少一次投递 + 业务幂等。

### Q2：如何保证幂等？

第一层是创建任务时用 `taskType + businessId` 查活跃任务，并用 `activeKey` 唯一索引防止重复活跃任务。第二层是消费者处理前检查业务结果是否已存在，例如简历分析结果已存在就跳过。这样即使 pending 恢复导致重复投递，也不会重复生成结果。

### Q3：消费者挂了怎么办？

如果消费者拿到消息但没 ACK，消息会留在 Redis Stream 的 PEL。应用启动后和每 60 秒定时恢复服务会调用每个 Consumer 的 `recoverPendingMessages()`，通过 XAUTOCLAIM 把空闲超过 60 秒的 pending 消息认领回来重新处理。

### Q4：任务失败后怎么重试？

自动重试由 Consumer 完成，普通异常且 `retryCount < 3` 时重新 XADD 消息并 ACK 当前消息。超过 3 次后进入 `DEAD_LETTER`。人工重试通过 `POST /api/async-tasks/{id}/retry`，会把状态重置为 `PENDING`、`retryCount=0`，并重新投递轻量消息。

### Q5：任务取消是怎么实现的？

`cancelTask()` 只允许取消 `PENDING` 和 `PROCESSING`。它把任务状态改成 `CANCELLED`，清除 `activeKey`。如果消费者还没开始处理，`markProcessing()` 会发现取消并抛出 `AsyncTaskCancelledException`，然后 ACK 不重试。若已经在业务处理中，当前还不能强制中断，只能通过后续检查点增强。

## 4. 技术延伸问题

### Q1：如果让你用 RabbitMQ 实现，会怎么改？

任务表和 `AsyncTaskService` 保留，只替换消息层。Producer 改为发送 RabbitMQ 消息，Consumer 改为 `@RabbitListener`，ACK/NACK、死信队列和延迟重试交给 RabbitMQ。`PendingMessageRecoveryService` 可以弱化，因为 RabbitMQ 对未 ACK 消息有自己的重投机制。

### Q2：如果只用线程池可以吗？

可以做 demo，但不适合这个场景。线程池任务在服务重启时会丢，失败重试和前端查询都要额外实现。当前任务和用户体验强相关，需要持久化状态和可靠恢复，所以选择 Redis Stream 更合理。

### Q3：如何做延迟重试？

可以用 `nextRetryAt` 字段 + 定时扫描，或 Redis ZSET 延迟队列。失败后不立即 XADD，而是写入下次重试时间，到期再投递。这样可以实现指数退避，避免外部服务故障时立刻打满重试。

### Q4：如何支持任务进度条？

在任务表增加 `progressPercent`、`progressMessage`、`completedSteps`、`totalSteps`。消费者在解析、调用 AI、保存结果等阶段更新进度。前端继续轮询或用 SSE 推送。

## 5. 改进方案问题

### Q1：这个模块目前最大的不足是什么？

可以回答：

1. 列表接口没有分页，任务量大后有性能风险。
2. `FAILED` 和 `DEAD_LETTER` 语义需要统一。
3. 高并发创建任务时唯一冲突还缺少优雅兜底。
4. 重试是立即重试，没有指数退避。
5. 取消处理中任务不是强中断，需要更多取消检查点。
6. 任务状态没有事件历史，排查复杂故障不够方便。

### Q2：你会优先改哪三点？

优先改：

1. 分页查询和管理后台筛选，解决运维基本体验。
2. 唯一冲突捕获和状态语义统一，提升正确性。
3. 延迟重试和指数退避，提升外部依赖故障时的稳定性。

### Q3：如何证明这个模块不是简单 CRUD？

它有完整的异步任务生命周期和可靠性设计：幂等创建、事务后投递、消费者组消费、状态机、自动重试、pending 恢复、人工重试/取消、TraceId 透传和指标记录。这些都是面向真实后台任务处理的工程能力，而不是普通增删改查。

## 6. 故障处理问题

### Q1：任务卡在 PENDING，怎么排查？

看 `messageId` 是否为空。为空说明可能没成功入队；不为空就查 Redis Stream 和消费者组。再查消费者是否启动、日志是否报错、Stream 是否堆积。

### Q2：任务卡在 PROCESSING，怎么排查？

查消费者是否崩溃、外部 LLM 是否卡住、业务结果是否已经保存、Redis PEL 是否有未 ACK 消息。必要时等 pending 恢复或人工修复状态。

### Q3：任务进入 DEAD_LETTER，怎么排查？

先看 `lastError`，按错误类型处理。外部服务故障恢复后可以手动重试；数据问题要先修数据；代码问题要修复发布后再重试。

### Q4：重复执行了怎么办？

重点查幂等：

1. 是否重复创建了活跃任务。
2. `activeKey` 唯一索引是否生效。
3. 消费者是否在保存结果前检查已有结果。
4. ACK 是否失败导致 pending 恢复重复消费。

### Q5：Redis Stream 里消息很多怎么办？

先看消费者是否正常消费，再看外部依赖是否拖慢处理。可以临时扩容消费者、调大 batch、限制新任务提交。长期要做吞吐压测、优先级队列和监控告警。
