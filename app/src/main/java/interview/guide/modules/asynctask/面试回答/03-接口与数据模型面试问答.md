# 接口与数据模型面试问答

## 1. 模块基础讲解

`AsyncTaskController` 暴露四个接口：

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/api/async-tasks` | 查询任务列表，可按类型和状态过滤 |
| `GET` | `/api/async-tasks/{id}` | 查询单个任务详情 |
| `POST` | `/api/async-tasks/{id}/retry` | 手动重试失败、取消或死信任务 |
| `POST` | `/api/async-tasks/{id}/cancel` | 手动取消等待中或处理中的任务 |

Controller 层只做路由和委托，返回统一 `Result<T>`。真正的状态判断、异常抛出、Redis Stream 重投递都在 `AsyncTaskService`。

数据模型主要有：

| 类型 | 作用 |
|---|---|
| `AsyncTaskEntity` | JPA 实体，映射 `async_tasks` 表 |
| `AsyncTaskDTO` | 返回给前端的任务详情，不直接暴露 Entity |
| `AsyncTaskEnqueueResult` | Producer 创建任务后的结果，包含任务 DTO 和是否新创建 |
| `AsyncTaskType` | 任务类型枚举 |
| `AsyncTaskStatusDTO` | 任务状态枚举 |
| `AsyncTaskRepository` | JPA 查询接口 |

`AsyncTaskEntity` 上建立了多个索引：按任务类型和业务 ID 查重、按状态筛选、按 active key 做唯一约束、按创建时间排序。这些索引对应的都是实际查询和运维场景。

## 2. 基础面试问题

### Q1：为什么 Controller 不直接操作 Repository？

因为 Controller 层应该只负责 HTTP 参数绑定和调用 Service。异步任务的状态流转、可重试状态判断、可取消状态判断、重试消息构建都属于业务逻辑。如果放在 Controller，会导致接口层过重，也不利于 Producer/Consumer 复用。

当前结构符合：

```text
Controller -> Service -> Repository
Service -> RedisService
```

### Q2：为什么返回 `AsyncTaskDTO` 而不是 `AsyncTaskEntity`？

直接返回 Entity 会暴露持久化内部结构，而且后续 Entity 增加懒加载关联或内部字段时可能影响 API。DTO 是稳定的对外视图，可以明确哪些字段允许前端看到。

本项目规范也要求禁止直接返回 Entity 给前端。

### Q3：`AsyncTaskEnqueueResult.created` 有什么用？

它用于告诉 Producer：这次调用到底是创建了新任务，还是复用了已有活跃任务。

如果 `created=false`，Producer 会跳过重复入队，避免同一个简历或知识库在 `PENDING/PROCESSING` 状态下被重复消费。

### Q4：`businessId` 为什么设计成 `String` 而不是 `Long`？

因为不同任务的业务 ID 类型不一样：

1. 简历 ID、知识库 ID 通常是 Long。
2. 面试会话 ID、语音会话 ID 可能是 UUID/String。

统一用 String 可以让 `AsyncTaskEntity` 支撑多种业务模块，不需要泛型表或多张任务表。

## 3. 进阶面试问题

### Q1：`listTasks()` 现在有什么性能问题？

当前 `listTasks()` 没有分页。无参数时会调用 `findAllByOrderByCreatedAtDesc()` 返回所有任务。如果任务表增长到几十万条，接口会慢、内存占用高，前端也难以渲染。

改进方式：

1. Controller 增加 `page`、`size`、`createdFrom`、`createdTo`。
2. Repository 使用 `Pageable` 返回 `Page<AsyncTaskDTO>`。
3. 前端管理页做分页和筛选。
4. 对高频筛选条件建立组合索引，例如 `status, created_at`。

### Q2：`payloadJson` 应该存完整业务数据吗？

不建议存完整大文本。当前 Producer 的 `payloadJson()` 多数只保存业务 ID 和内容长度，例如 `contentLength`。这更符合“消息和任务台账只保存摘要，业务数据在业务表或对象存储中”的原则。

如果把简历全文或知识库全文存进 `payloadJson`，会导致任务表膨胀、敏感数据暴露风险增加、管理后台加载变慢。生产上更适合保存摘要、文件 key、内容 hash 或脱敏片段。

### Q3：`active_key` 唯一索引在数据库里有什么注意点？

`active_key` 在终态会被设置为 null。多数数据库允许唯一索引中存在多个 null，因此已完成任务不会相互冲突。活跃任务则有 `taskType:businessId`，同一业务对象只能有一个活跃任务。

注意点：

1. 要确认目标数据库对 unique + null 的行为，PostgreSQL 允许多个 null。
2. 如果使用其他数据库，要确认行为是否一致。
3. 高并发插入冲突需要在 Service 层捕获并回查。

### Q4：为什么 `lastError` 要截断？

异常堆栈或外部服务返回内容可能很长。如果不截断，可能导致数据库字段过大、日志和前端展示异常。`AsyncTaskService` 用 `MAX_ERROR_LENGTH=1000` 截断终态错误，Producer/Consumer 模板也有 500 字符截断。

可以进一步统一截断长度和工具方法，避免不同地方不一致。

## 4. 技术延伸问题

### Q1：如果要做任务管理后台，接口还需要哪些能力？

可以增加：

1. 分页列表。
2. 按时间范围、业务 ID、错误关键字搜索。
3. 批量重试、批量取消。
4. 查看任务状态变更历史。
5. 查看同业务对象最近 N 次任务。
6. 导出失败任务列表。
7. 只展示当前用户有权限看到的任务。

### Q2：如何设计多租户场景下的异步任务模型？

需要在 `AsyncTaskEntity` 加上 `tenantId`、`userId` 或 `ownerId`。查询、重试、取消都必须带权限过滤：

```text
普通用户：只能查自己的任务
管理员：可按租户查看和操作任务
平台运维：可跨租户查看，但敏感 payload 脱敏
```

同时唯一键也可能从 `taskType:businessId` 扩展为 `tenantId:taskType:businessId`，避免不同租户业务 ID 相同导致冲突。

### Q3：如何把任务状态实时推给前端？

当前适合用轮询：前端每隔几秒调用 `getTask()`。如果想实时，可以：

1. SSE：后端在任务状态变化时推送状态事件，适合单向通知。
2. WebSocket：适合需要双向实时交互的语音面试或实时控制。
3. 前端轮询 + 指数退避：实现最简单，任务少时足够。

本项目已有 SSE 用于 RAG 流式回答，如果未来要做任务实时通知，可以复用 SSE 思路。

## 5. 改进方案问题

### Q1：接口层可以怎么优化？

1. 给重试和取消接口增加 `@RateLimit`，防止误操作或恶意频繁操作。
2. 增加权限校验，防止普通用户操作他人任务。
3. `listTasks()` 增加分页。
4. `getTask()` 可以根据用户身份脱敏 `payloadJson` 和 `lastError`。
5. 重试接口可以支持传入重试原因或操作者，写入审计日志。

### Q2：Repository 可以怎么优化？

1. 增加 `findByActiveKey()`，用于唯一冲突后回查。
2. 增加分页查询方法。
3. 增加状态和创建时间组合索引。
4. 增加 `findByBusinessIdAndTaskTypeOrderByCreatedAtDesc()`，方便查看某个业务对象历史任务。
5. 监控统计方法当前预留但未使用，可以接入监控模块或删除以减少误导。

### Q3：DTO 可以怎么优化？

可以拆分列表 DTO 和详情 DTO。列表页不一定需要 `payloadJson` 和完整 `lastError`，否则数据量大、敏感信息风险高。

推荐：

```text
AsyncTaskListItemDTO：列表展示字段
AsyncTaskDetailDTO：详情页完整字段
AsyncTaskStatusDTO：前端轮询最小字段
```

不过当前项目规模下，一个 `AsyncTaskDTO` 也能接受，优点是简单。

## 6. 故障处理问题

### Q1：调用重试接口返回“当前任务状态不允许重试”怎么办？

说明任务当前状态不在 `FAILED`、`CANCELLED`、`DEAD_LETTER` 中。比如任务仍是 `PENDING` 或 `PROCESSING`，此时重复重试可能产生并发执行，所以被拒绝。

排查时先调用 `GET /api/async-tasks/{id}` 查看状态。如果任务长期卡在活跃状态，应先排查消费者和 pending，再决定是否取消或修复状态。

### Q2：调用取消接口返回“当前任务状态不允许取消”怎么办？

说明任务已经进入终态，比如 `COMPLETED`、`FAILED`、`DEAD_LETTER` 或 `CANCELLED`。终态任务取消没有意义。如果想重新执行，应该调用 retry；如果已经成功但想重新生成结果，需要业务层提供“重新分析/重新向量化”入口。

### Q3：任务查询接口返回不存在怎么办？

可能原因：

1. 前端拿错了 `taskId`。
2. 创建任务失败，业务接口没有正确返回任务 ID。
3. 数据库被清理或连接了错误环境。
4. 用户无权限时未来可能也返回不存在。

当前代码会抛 `BusinessException(ErrorCode.NOT_FOUND, "异步任务不存在")`，由全局异常处理器统一包装。
