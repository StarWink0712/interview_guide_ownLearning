# 技术方案对比与扩展实践

## 1. 模块基础讲解

当前异步任务模块选择的是：

```text
Spring Boot Service + JPA 任务表 + Redis Stream + 公共 Producer/Consumer 模板
```

这个方案适合当前 AI 面试平台的规模：单体后端、已有 Redis 依赖、任务类型明确、需要前端查询进度、需要失败后人工重试。它不是最重的企业级 MQ 方案，但已经覆盖了可靠异步处理中最重要的几个点：任务台账、消费者组、ACK、pending 恢复、自动重试、人工干预。

面试中讲技术选型时，不要只说“我用了 Redis Stream”。更好的表达是：

> 我把异步任务拆成状态管理和消息运输两部分。数据库任务表负责可查询、可运维、可审计；Redis Stream 负责异步调度和消费者组；公共模板封装 ACK、重试、pending 恢复。这个设计比简单 `@Async` 更可靠，又比单独引入 RabbitMQ/Kafka 成本低，适合当前项目阶段。

## 2. 基础面试问题

### Q1：为什么不用 `@Async`？

`@Async` 适合简单后台任务，但它本质是本地线程池。进程重启后任务会丢失，前端也很难统一查询任务状态，失败重试和 pending 恢复都要自己补。

当前项目的任务包括 LLM 调用和向量化，耗时长、失败概率高、需要用户看到进度。所以用 Redis Stream + 任务表更稳。

### Q2：为什么不用定时任务扫数据库？

定时扫表也可以实现异步任务，甚至可靠性很好，因为任务都在数据库中。但缺点是延迟取决于扫描周期，高并发时数据库压力较大，也没有消费者组这种天然分发能力。

本项目用 Redis Stream 是为了让任务提交后尽快被消费者处理，同时保留数据库任务表做状态查询。

### Q3：为什么不用 RabbitMQ？

RabbitMQ 是更专业的 MQ，但会增加中间件运维和项目复杂度。当前项目已经依赖 Redis，Redis Stream 支持消费者组、ACK、PEL、XAUTOCLAIM，足够支撑中等规模的后台 AI 任务。

如果未来服务拆分、任务量显著增加、需要复杂路由和死信交换机，再引入 RabbitMQ 会更合适。

### Q4：为什么不用 Kafka？

Kafka 适合高吞吐事件流和日志回放，但单个任务的状态查询、人工取消、手动重试不是 Kafka 的强项，仍然需要任务表。对当前项目来说，Kafka 的部署和运维成本偏高。

## 3. 进阶面试问题

### Q1：不同异步方案的可靠性怎么比较？

| 方案 | 进程崩溃任务是否保留 | 是否支持消费者组 | 是否方便查询任务状态 | 实现成本 |
|---|---|---|---|---|
| `@Async` | 否 | 否 | 否，需要另做 | 低 |
| 数据库扫表 | 是 | 需要自己实现 | 是 | 中 |
| Redis List | 部分支持 | 否 | 否，需要任务表 | 低中 |
| Redis Stream | 是，未 ACK 进 PEL | 是 | 需要任务表 | 中 |
| RabbitMQ | 是 | 是 | 需要任务表 | 中高 |
| Kafka | 是，基于 offset | 是 | 需要任务表 | 高 |

本项目选择 Redis Stream，是在可靠性和复杂度之间做了折中。

### Q2：如果项目从单体演进到微服务，这个模块怎么拆？

可以保留任务控制面，拆分执行面：

```text
任务管理服务
  -> 保存 async_tasks
  -> 提供查询、重试、取消 API
  -> 发送消息到 MQ

简历服务消费者
  -> 消费 RESUME_ANALYZE
  -> 更新简历结果和任务状态

知识库服务消费者
  -> 消费 KB_VECTORIZE
  -> 写向量库和任务状态
```

关键是任务 ID 要在跨服务消息中传递，任务服务提供状态更新接口或共享数据库表。更推荐通过任务服务 API 更新状态，避免多个服务直接写同一张表。

### Q3：如何做优先级任务？

Redis Stream 本身没有直接优先级。可以设计多个 Stream：

```text
resume:analyze:high
resume:analyze:normal
resume:analyze:low
```

消费者优先读取 high，再读取 normal 和 low。或者使用 RabbitMQ 的 priority queue。数据库任务表需要增加 `priority` 字段，管理后台也可以调整优先级。

### Q4：如何做任务分片？

对于大知识库向量化，可以把一个大任务拆成多个 chunk 子任务：

```text
parent task: KB_VECTORIZE
child task: KB_VECTORIZE_CHUNK_1
child task: KB_VECTORIZE_CHUNK_2
...
```

`AsyncTaskEntity` 已经有 `parentTaskId` 字段，但当前没有实际使用。未来可以用它表达父子任务关系，父任务负责汇总进度和最终状态，子任务并行处理各 chunk。

## 4. 技术延伸问题

### Q1：如何使用 Outbox Pattern 改造？

当前 after-commit 投递已经避免消息早于事务提交，但仍存在“事务提交成功、Redis 投递失败”的窗口。Outbox 改造可以这样做：

1. 业务事务中写业务数据、`async_tasks`、`outbox_messages`。
2. 后台 Outbox Dispatcher 扫描未发送消息。
3. Dispatcher XADD 到 Redis Stream。
4. 成功后标记 outbox 已发送，并调用 `markEnqueued()`。
5. 失败则保留 outbox 等待下次投递。

这样 Redis 短暂不可用时任务不会直接失败，而是最终投递成功。

### Q2：如何用 Redisson 延迟队列实现延迟重试？

可以把重试消息先放进 Redisson 延迟队列，到期后再进入 Stream。但要注意延迟队列和 Stream 的一致性，最好仍以数据库 `nextRetryAt` 为准。更简单稳定的是 ZSET 延迟队列。

### Q3：如何和监控告警系统结合？

可以把以下指标接入 Micrometer：

1. 每类任务创建数。
2. 每类任务成功/失败/取消/死信数。
3. 重试次数分布。
4. 平均处理耗时和 P95。
5. PENDING/PROCESSING 堆积数量。
6. PEL 中 pending 数量。
7. 最老 pending idle time。

告警规则示例：

```text
5 分钟内 DEAD_LETTER > 10
PROCESSING 超过 10 分钟未更新
某类任务成功率低于 95%
PEL pending 数持续增长
```

## 5. 改进方案问题

### Q1：如果保持 Redis Stream，下一步最值得做什么？

优先级建议：

1. 分页查询和管理后台批量操作。
2. 失败终态语义统一。
3. `active_key` 并发冲突兜底。
4. 延迟重试和指数退避。
5. 任务状态历史表。
6. Outbox 投递保障。

这些改动能在不换技术栈的情况下显著提升可靠性和可运维性。

### Q2：如果换 RabbitMQ，需要改哪些代码？

保留：

1. `AsyncTaskEntity`
2. `AsyncTaskService`
3. `AsyncTaskController`
4. `AsyncTaskRepository`

替换：

1. `AbstractStreamProducer` -> RabbitMQ Producer 模板。
2. `AbstractStreamConsumer` -> RabbitMQ Listener 模板。
3. `RedisService.streamAdd/streamAck/streamAutoClaim` -> RabbitMQ ack/nack/dlx。
4. `PendingMessageRecoveryService` 可能不再需要，改为 RabbitMQ 自带未 ACK 重投和死信处理。

这说明当前代码把任务控制面和消息执行面拆开是有迁移价值的。

### Q3：如果做云原生部署，需要注意什么？

1. 多实例消费者的 `consumerName` 必须唯一，当前 UUID 后缀可以满足。
2. pending 恢复在多实例下可能多个实例同时调度，需要依赖 XAUTOCLAIM 和幂等处理兜底。
3. Redis 连接池、超时、重连策略要配置。
4. 任务处理线程不能无限增加，要按外部 LLM 限流。
5. 应用优雅停机时要停止消费循环，减少处理中断。
6. 配置项如最大重试、批次大小、Stream 长度应外置化。

## 6. 故障处理问题

### Q1：技术选型被质疑“Redis 不适合做 MQ”怎么回答？

可以诚实回答：

> Redis Stream 不是所有场景下都替代专业 MQ。它适合当前项目这种已有 Redis、任务量中等、需要消费者组和 pending 恢复的场景。为了避免把 Redis 当数据库，我只在 Stream 里放轻量 ID，状态和历史放在 PostgreSQL 的任务表。如果未来出现复杂路由、高吞吐、多服务强解耦，我会保留任务表控制面，把执行面迁移到 RabbitMQ 或 Kafka。

### Q2：任务量突然暴涨怎么办？

应急处理：

1. 临时扩容消费者实例。
2. 调大批量读取数量。
3. 限制新任务提交或排队。
4. 对低优先级任务延迟处理。
5. 观察 Redis 内存和 Stream 长度。
6. 检查外部 LLM 限流，避免盲目扩容导致更多失败。

长期处理：

1. 拆分高耗时任务。
2. 引入优先级队列。
3. 做容量评估和压测。
4. 迁移专业 MQ。

### Q3：任务表越来越大怎么办？

可以做生命周期管理：

1. 最近 30 天任务保留在线表。
2. 更老任务归档到历史表。
3. `payloadJson` 和 `lastError` 做脱敏和压缩。
4. 管理后台默认只查最近时间范围。
5. 建立合适索引并定期维护。
