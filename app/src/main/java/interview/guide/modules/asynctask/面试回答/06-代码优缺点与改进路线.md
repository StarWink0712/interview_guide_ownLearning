# 代码优缺点与改进路线

## 1. 模块基础讲解

从代码质量角度看，`asynctask` 模块已经具备一个统一异步任务中心的雏形。它把任务表、状态机、Controller API、Redis Stream 关联、pending 恢复组织在一起，能支撑多个业务模块复用。

当前代码的亮点主要是：

1. 状态管理集中在 `AsyncTaskService`。
2. 使用 `activeKey` 做活跃任务幂等去重。
3. 手动重试能根据 `taskType` 重新构造轻量消息。
4. `PendingMessageRecoveryService` 通过 `List<AbstractStreamConsumer<?>>` 自动覆盖所有消费者。
5. JPA Repository 查询方法清晰，索引和查询场景基本匹配。
6. 已有单元测试覆盖状态流转、任务复用、手动重试和 pending 恢复委托。

不足主要集中在生产级可靠性和可运维细节上：分页缺失、状态语义不够统一、并发唯一冲突未兜底、延迟重试字段未落地、状态历史缺失、权限和审计缺失。

## 2. 基础面试问题

### Q1：你觉得这个模块设计得好的地方是什么？

好的地方是职责分离清楚。`AsyncTaskService` 管任务生命周期，Redis Stream 管消息调度，具体业务 Consumer 管业务执行，Controller 只暴露查询和操作入口。这样既能复用，又不会让每个业务模块重复造一套任务管理。

面试中可以重点讲：

> 我把异步任务抽象为统一的业务对象，而不是散落在各个模块里。数据库保存任务当前状态，Stream 负责异步执行，Consumer 模板统一 ACK、重试、pending 恢复。这样简历分析、知识库向量化、面试评估都能复用一套基础设施。

### Q2：代码里用了哪些设计模式？

主要有：

| 设计模式 | 体现 |
|---|---|
| 模板方法模式 | `AbstractStreamConsumer` 定义消费骨架，子类实现解析和业务处理 |
| 策略/多态 | 不同 Consumer 对不同任务类型实现不同 `processBusiness()` |
| 门面/服务层 | `AsyncTaskService` 封装任务生命周期，外部不用知道实体细节 |
| DTO 模式 | `AsyncTaskDTO` 对外返回，避免暴露 Entity |
| 工厂式枚举分派 | `buildRetryMessage()` 根据 `AsyncTaskType` 构建不同字段 |
| 观察者/事件思想 | `ApplicationReadyEvent` 触发启动恢复 |

### Q3：当前已有测试说明了什么？

`AsyncTaskServiceTest` 覆盖了：

1. `PENDING -> PROCESSING -> COMPLETED` 状态流转。
2. 活跃任务复用，避免重复创建。
3. 手动重试会重置 retry count，并发送轻量消息。

`PendingMessageRecoveryServiceTest` 覆盖了：

1. 恢复服务会委托所有消费者执行 pending 恢复。

这说明核心行为不是只靠注释描述，而是有测试保护。不过测试还可以继续补充并发冲突、取消边界、重试失败和分页等场景。

## 3. 进阶面试问题

### Q1：代码中最值得警惕的语义不一致是什么？

最值得注意的是 `FAILED` 和 `DEAD_LETTER`。`AbstractStreamConsumer` 的抽象方法叫 `markFailed()`，注释里说超过最大重试次数标记失败，但多个具体 Consumer 的实现实际调用 `asyncTaskService.markDeadLetter()`。

这不是一定错误，但语义需要明确：自动重试耗尽叫 `DEAD_LETTER`，Producer 入队失败叫 `FAILED`。如果团队不统一认知，前端和运维可能不知道应该筛选哪个状态。

改进方式是：

1. 重命名抽象方法为 `markRetryExhausted()`。
2. 明确 `FAILED` 和 `DEAD_LETTER` 的状态说明。
3. 管理后台默认把两者都归为失败类任务。

### Q2：当前事务边界有什么需要注意？

`AsyncTaskService` 的状态更新方法有 `@Transactional`，这是对的。但外部 API 调用不应该放在事务内。当前业务 Consumer 先 `markProcessing()`，再执行 `processBusiness()`，再 `markCompleted()`，这三个步骤分开，避免长时间持有数据库事务。

Producer 使用 after-commit 投递消息，也避免消费者读到未提交数据。

需要进一步注意的是：业务结果保存和任务完成状态之间可能不是同一个事务。如果保存成功但 `markCompleted()` 失败，会出现业务结果已存在但任务仍处理中。当前通过消费者幂等判断可以缓解，但最好增加补偿或状态修复机制。

### Q3：当前代码有没有过度注释问题？

部分源码注释非常详细，适合学习阶段，但在生产代码中可能显得重复，甚至有少量注释与真实行为不完全一致。比如消费者注释说超过后标记 `FAILED`，但具体实现标记 `DEAD_LETTER`。

改进方向是保留“为什么这样设计”的注释，减少逐行解释“代码做了什么”的注释，把详细讲解放在文档或面试材料里。

### Q4：`AsyncTaskStatusDTO` 命名是否合适？

不太合适。它不仅用于 DTO，也作为 JPA Entity 的持久化枚举。更准确的命名是 `AsyncTaskStatus`。如果担心和 `common.model.AsyncTaskStatus` 冲突，可以统一模型，或命名为 `AsyncTaskLifecycleStatus`。

## 4. 技术延伸问题

### Q1：如何把这个模块演进为通用任务平台？

可以增加：

1. 任务定义表：描述任务类型、最大重试、超时时间、是否允许取消。
2. 任务实例表：当前 `async_tasks`。
3. 任务事件表：记录状态变化历史。
4. 调度器：支持延迟、优先级、定时、并发度控制。
5. 执行器注册：不同任务类型映射不同 handler。
6. 管理后台：查询、重试、取消、批处理、告警。

当前代码已经有任务实例表和执行模板，后续可以逐步扩展，不需要推倒重来。

### Q2：如何支持任务进度？

在 `AsyncTaskEntity` 增加：

```text
progressPercent
progressMessage
totalSteps
completedSteps
```

消费者在处理大文档分块、长面试评估时定期更新进度。前端轮询或 SSE 推送进度。对于知识库向量化，可以按 chunk 数更新；对于简历分析，可能只有“解析中、AI评分中、保存中”几个阶段。

### Q3：如何支持父子任务？

当前 `parentTaskId` 字段已经预留。可以用于：

1. 一个知识库大文档拆成多个 chunk 子任务。
2. 一个批量简历分析任务拆成多个简历子任务。
3. 父任务统计子任务完成率。

父任务状态可以由子任务聚合：

```text
所有子任务 COMPLETED -> 父任务 COMPLETED
任一子任务 DEAD_LETTER -> 父任务 PARTIAL_FAILED 或 FAILED
用户取消父任务 -> 批量取消未完成子任务
```

当前枚举没有 `PARTIAL_FAILED`，如果做批量任务可以扩展。

## 5. 改进方案问题

### Q1：短期最推荐的改进清单是什么？

优先级从高到低：

1. 给 `listTasks()` 做分页，防止数据量增长后接口拖垮。
2. 捕获 `active_key` 唯一冲突并回查旧任务。
3. 统一 `FAILED` 和 `DEAD_LETTER` 语义，更新方法命名和前端筛选。
4. `parsePayload()` 捕获数字格式异常，避免坏消息无意义重试。
5. 最大重试、批次大小、Stream 长度配置化。
6. 增加取消后的二次检查，避免取消后仍保存结果。

### Q2：中期改进清单是什么？

1. Outbox Pattern，解决事务提交成功但 Redis 投递失败。
2. 延迟重试和指数退避。
3. 任务状态事件表。
4. 任务执行超时扫描。
5. 失败任务聚合和告警。
6. 权限控制和审计日志。

### Q3：长期改进清单是什么？

1. 多实例消费者并发度配置。
2. 优先级队列。
3. 父子任务和进度追踪。
4. 专业 MQ 迁移适配层。
5. 独立任务管理服务。
6. 更完整的可观测指标和自动化运维。

## 6. 故障处理问题

### Q1：面试官问“你这个模块有没有缺点”，怎么诚实回答？

可以这样答：

> 当前模块已经覆盖了异步任务的基本可靠性：任务台账、Redis Stream 消费者组、ACK、自动重试、pending 恢复和人工重试。但它还不是完整生产级任务平台。比如列表没有分页，延迟重试字段还没真正用起来，`FAILED` 和 `DEAD_LETTER` 语义需要统一，高并发唯一键冲突也要加兜底。我的优化顺序会先做分页和状态语义统一，再做 Outbox 和指数退避。

这个回答既展示理解，也不会过度包装。

### Q2：如果任务状态和业务状态不一致，怎么处理？

例如 `async_tasks` 是 `PROCESSING`，但简历分析结果已经保存。处理方式：

1. 查业务结果是否完整。
2. 查消费者日志是否在保存结果后 `markCompleted()` 失败。
3. 如果结果完整，可以人工或脚本修复任务状态为 `COMPLETED`。
4. 长期应增加状态修复任务，扫描“业务已完成但任务未完成”的记录。

### Q3：如果管理后台误点重试已取消任务，会有什么风险？

当前代码允许 `CANCELLED` 手动重试。这对“误取消”或“临时业务条件恢复”有价值，但也有风险：如果取消原因是业务实体已删除，重试仍会再次取消或失败。

改进方式：

1. 重试前展示 `lastError` 和确认弹窗。
2. 对实体不存在类取消，重试前校验业务实体是否恢复。
3. 区分用户取消和系统取消，只有部分取消类型允许重试。
