# 核心生命周期与状态机

## 1. 模块基础讲解

异步任务模块的核心是 `AsyncTaskService` 维护的一套状态机。任务从创建到结束大致经历：

```text
PENDING
  -> PROCESSING
  -> COMPLETED
  -> FAILED
  -> CANCELLED
  -> DEAD_LETTER
```

真实流转可以拆成两条线：

```text
正常成功：
createOrReusePendingTask()
  -> markEnqueued()
  -> markProcessing()
  -> markCompleted()

异常重试：
markProcessing()
  -> processBusiness() 抛异常
  -> retryMessage()
  -> markRetrying()
  -> 再次 PENDING
  -> 超过上限后 markDeadLetter()
```

状态枚举定义在 `AsyncTaskStatusDTO`：

| 状态 | 含义 |
|---|---|
| `PENDING` | 任务已创建或已入队，等待消费者处理 |
| `PROCESSING` | 消费者已经拉取消息，正在执行业务逻辑 |
| `COMPLETED` | 任务成功完成 |
| `FAILED` | 入队失败或人工判定失败，当前代码主要用于 Producer 发送失败 |
| `CANCELLED` | 任务被用户取消，或业务实体不存在/内容为空等无需重试场景 |
| `DEAD_LETTER` | 消费失败超过最大重试次数，或重试入队失败，需要人工介入 |

`AsyncTaskService` 通过事务方法更新状态。`finishTask()` 是终态收口方法，会清理 `activeFlag` 和 `activeKey`，表示该业务对象不再有活跃任务，可以重新发起。

## 2. 基础面试问题

### Q1：异步任务的状态有哪些？分别代表什么？

可以按生命周期回答：

1. `PENDING`：任务刚创建或重新入队，等待被消费。
2. `PROCESSING`：消费者已拿到消息并开始执行。
3. `COMPLETED`：业务处理成功。
4. `FAILED`：任务失败，当前主要表示 Producer 发送失败。
5. `CANCELLED`：任务被取消或业务对象已不存在，不再重试。
6. `DEAD_LETTER`：重试耗尽或重试入队失败，需要人工介入。

面试时要特别说明：当前代码中 Consumer 自动重试耗尽后多数调用 `markDeadLetter()`，而不是 `markFailed()`。所以在讲真实实现时，失败终态要区分 `FAILED` 和 `DEAD_LETTER`。

### Q2：任务从创建到完成的完整流程是什么？

以简历分析为例：

```text
ResumeUploadService
  -> AnalyzeStreamProducer.sendAnalyzeTask()
  -> AsyncTaskService.createOrReusePendingTask()
  -> 事务提交后 sendTask() XADD
  -> AsyncTaskService.markEnqueued()
  -> AnalyzeStreamConsumer 拉取消息
  -> AsyncTaskService.markProcessing()
  -> ResumeGradingService.analyzeResume()
  -> ResumePersistenceService.saveAnalysis()
  -> AsyncTaskService.markCompleted()
  -> Redis Stream XACK
```

这个流程的关键点是：数据库任务先创建，消息再投递，消费者执行时不断回写任务状态，前端通过任务 ID 查询状态。

### Q3：`markEnqueued()` 有什么作用？为什么创建任务时不直接认为入队成功？

`createOrReusePendingTask()` 只是把任务记录写进数据库，真正的 Redis Stream 投递由 Producer 在事务提交后执行。`markEnqueued()` 会把 Redis 返回的 `messageId` 写入任务表，表示消息确实进入 Stream。

这样做可以区分两个状态：

| 阶段 | 数据库表现 | 含义 |
|---|---|---|
| 创建后 | 有任务，可能没有 `messageId` | 任务台账已创建，但消息未必投递成功 |
| 入队后 | 写入 `messageId` | Stream 已接收消息，可被消费者处理 |

这对排查“任务卡住”很重要。

### Q4：为什么取消任务只允许取消 `PENDING` 和 `PROCESSING`？

因为这两个是活跃状态。`COMPLETED` 已经成功，`FAILED`、`DEAD_LETTER` 已经是失败终态，`CANCELLED` 已经取消，再取消没有意义。代码里用 `ACTIVE_STATUSES` 控制可取消状态，用 `RETRYABLE_STATUSES` 控制可重试状态。

## 3. 进阶面试问题

### Q1：取消 `PROCESSING` 中的任务真的能立即中断业务执行吗？

不能保证立即中断。当前实现是把任务表状态改成 `CANCELLED`，并清理活跃标记。消费者在 `markProcessing()` 时会检测任务是否已取消，如果在消费者开始处理前取消，就会抛出 `AsyncTaskCancelledException` 并 ACK 消息。

但如果消费者已经进入 `processBusiness()`，例如正在调用 LLM 或向量化，当前代码没有线程中断或外部 API 取消能力。也就是说，取消更像“状态层取消”和“下次检查时生效”，不是强制 kill 正在运行的业务逻辑。

可改进方案是为长耗时步骤增加协作式取消点，例如处理前、LLM 返回后、保存结果前再次检查任务状态。

### Q2：为什么要区分 `FAILED` 和 `DEAD_LETTER`？

理想语义可以这样区分：

| 状态 | 推荐语义 |
|---|---|
| `FAILED` | 任务执行失败，已经没有自动重试，可能由业务失败或发送失败产生 |
| `DEAD_LETTER` | 消息流转层面已经无法继续自动处理，必须人工介入 |

当前代码中 Producer 发送失败会调用 `markFailed()`，Consumer 重试耗尽会调用 `markDeadLetter()`。这能表达“发送阶段失败”和“消费阶段重试耗尽”的区别，但命名上还可以更清晰，例如把 `FAILED` 定义为业务失败，把 `DEAD_LETTER` 定义为队列死信。

### Q3：`activeFlag` 和 `activeKey` 为什么都需要？

`activeFlag` 表示任务是否处于活跃状态，便于业务理解和前端展示。`activeKey` 是数据库唯一约束的关键字段，格式是 `taskType:businessId`，用于阻止同一业务对象重复创建活跃任务。

只用 `activeFlag` 很难做唯一约束，因为唯一性需要一个稳定键。只用 `activeKey` 又不够直观，不便于查询和展示。两者组合后，既方便业务读，又能依赖数据库兜底。

### Q4：高并发下 `createOrReusePendingTask()` 有没有竞态？

有潜在竞态。当前逻辑是先查活跃任务，再创建新任务。如果两个请求几乎同时进来，都查不到旧任务，就可能都尝试插入相同 `activeKey`。由于数据库有唯一索引，最终应该只有一个成功，另一个会抛出唯一约束异常。

当前代码没有显式捕获这个唯一约束异常并回查旧任务，所以高并发下用户可能看到异常。改进方式是捕获 `DataIntegrityViolationException`，再按 `activeKey` 回查已有任务并返回 `created=false`。

## 4. 技术延伸问题

### Q1：如何设计更严格的状态机？

可以引入状态转移校验表，明确哪些状态允许流向哪些状态：

| 当前状态 | 允许转移到 |
|---|---|
| `PENDING` | `PROCESSING`、`CANCELLED` |
| `PROCESSING` | `COMPLETED`、`CANCELLED`、`PENDING`、`FAILED`、`DEAD_LETTER` |
| `FAILED` | `PENDING` |
| `DEAD_LETTER` | `PENDING` |
| `CANCELLED` | `PENDING` |
| `COMPLETED` | 不允许自动转移 |

这样可以防止误调用，例如把 `COMPLETED` 任务又标为 `PROCESSING`。可以在 `AsyncTaskService` 内统一做 `assertTransitionAllowed(old, next)`。

### Q2：如何实现延迟重试或指数退避？

当前消费者失败后立即重新 XADD，`nextRetryAt` 字段没有真正参与调度。要做指数退避，可以有两种方案：

1. 数据库调度：失败时写 `nextRetryAt = now + backoff`，定时任务扫描到期任务再投递。
2. MQ 延迟队列：如果换 RabbitMQ，可以用 TTL + DLX 或延迟插件；如果用 Redis，可以用 ZSET 做延迟队列，到期后转入 Stream。

指数退避公式可以是：

```text
delay = min(baseDelay * 2 ^ retryCount, maxDelay)
```

这样能避免外部 LLM 或数据库短暂故障时瞬间重试放大压力。

### Q3：状态机如何和业务状态保持一致？

每个业务 Consumer 在调用 `asyncTaskService.markProcessing()` 的同时，会更新业务对象自己的状态。例如简历更新 `analyzeStatus`，知识库更新 `vectorStatus`，面试会话更新 `evaluateStatus`。

这是一种“双状态”设计：

| 状态表 | 面向对象 | 用途 |
|---|---|---|
| `async_tasks.status` | 统一任务平台 | 运维、轮询、重试、恢复 |
| 业务表状态 | 具体业务页面 | 简历分析结果、知识库向量状态、面试报告状态 |

缺点是两边可能出现短暂不一致。生产上可以把状态更新包在同一事务里，或以异步任务表为准，业务表只保存业务结果状态。

## 5. 改进方案问题

### Q1：当前状态机设计有哪些优点？

1. 状态足够覆盖常见场景：等待、处理中、成功、失败、取消、死信。
2. 终态统一清理 `activeKey`，支持后续重新发起。
3. 手动重试会重置 `retryCount` 并重新进入 `PENDING`。
4. 状态变更集中在 Service 层，Controller 和 Consumer 不直接操作实体。

### Q2：当前状态机有哪些不足？

1. 缺少严格状态转移校验，部分方法可以在不合理状态下被调用。
2. `FAILED` 和 `DEAD_LETTER` 的真实语义需要进一步统一。
3. `nextRetryAt` 字段未实际使用。
4. `PROCESSING` 超时没有自动处理。
5. 取消处理中任务不是强中断，只能在下一次检查点生效。
6. 没有记录每次状态变化历史，排查复杂问题时只能看当前状态和最后错误。

### Q3：如何增强可观测性？

可以新增 `async_task_events` 表，记录每次状态变化：

```text
taskId, oldStatus, newStatus, messageId, retryCount, reason, operator, createdAt
```

这样面试中可以说：当前实现保存的是任务当前态和最近错误，如果要做生产级审计，可以增加事件表，把任务状态机从“当前状态模型”升级为“状态事件模型”。

## 6. 故障处理问题

### Q1：任务一直是 `PENDING` 怎么办？

排查顺序：

1. 看 `messageId` 是否为空。为空说明 Producer 没成功入队或 after-commit 回调没执行。
2. 看 Redis Stream 是否存在对应消息。
3. 看消费者是否启动，消费者组是否创建成功。
4. 看 Stream 是否被裁剪。当前 `STREAM_MAX_LEN=1000`，极端情况下旧消息可能被裁剪。
5. 看消费者日志是否在循环报错。

### Q2：任务一直是 `PROCESSING` 怎么办？

可能原因：

1. 消费者执行中崩溃，消息在 PEL 中未 ACK。
2. 外部 LLM 或文件解析卡住。
3. 业务逻辑执行完但更新状态失败。
4. 任务取消后业务逻辑仍在执行，没有协作式取消点。

处理方式：

1. 等待 `PendingMessageRecoveryService` 自动 claim。
2. 查 Redis PEL 和消费者日志。
3. 查业务表是否已经有结果，如果有，可以人工修正状态。
4. 增加任务执行超时和处理中超时扫描。

### Q3：手动重试后还是失败怎么办？

先不要无限重试，要判断失败类型：

| 错误类型 | 处理方式 |
|---|---|
| LLM 超时、限流 | 等服务恢复后重试，必要时切换 provider |
| Redis 短暂不可用 | 恢复 Redis 后重试 |
| 文件无法解析 | 重新上传文件或优化解析服务 |
| 业务实体已删除 | 标记取消，不应重试 |
| 代码 bug | 修复代码后再重试或批量补偿 |
