# 异步任务模块总览与架构设计

## 1. 模块基础讲解

`asynctask` 模块不是某一个业务任务的执行器，而是整个平台异步任务的统一控制面。它负责记录任务台账、维护任务状态机、支撑前端查询、提供人工重试和取消入口，并配合 Redis Stream 消费者完成 pending 消息恢复。

在业务场景上，它服务的是求职者闭环里的耗时动作：简历上传后的 AI 分析、知识库文档上传后的向量化、模拟面试结束后的 AI 评估、语音面试结束后的多轮评估。这些操作都不适合阻塞 HTTP 请求，所以项目把“用户请求”和“后台耗时处理”拆开：请求侧只创建任务并投递轻量消息，后台消费者再异步执行。

核心代码分为四层：

| 层次 | 代表类 | 职责 |
|---|---|---|
| API 层 | `AsyncTaskController` | 提供 `/api/async-tasks` 查询、重试、取消接口 |
| Service 层 | `AsyncTaskService` | 创建/复用任务、状态流转、手动重试、取消 |
| Repository 层 | `AsyncTaskRepository` | 基于 JPA 查询任务实体和统计数据 |
| Recovery 层 | `PendingMessageRecoveryService` | 启动和定时扫描 Redis Stream PEL，恢复未 ACK 消息 |

模块本身的数据库模型是 `AsyncTaskEntity`，它把异步任务当作一个可以观察、可以运维、可以人工介入的业务对象。Redis Stream 只承担消息运输，数据库才是任务生命周期的状态真源。

整体链路可以概括为：

```text
业务 Service
  -> 具体 Producer
  -> AsyncTaskService.createOrReusePendingTask()
  -> 事务提交后 XADD 到 Redis Stream
  -> AsyncTaskService.markEnqueued()
  -> 具体 Consumer 消费消息
  -> markProcessing()
  -> processBusiness()
  -> markCompleted() / markCancelled() / markDeadLetter()
  -> XACK
```

这里采用的是“控制面 + 执行面”设计。`asynctask` 管理任务状态和运维能力，`common/async` 的 `AbstractStreamProducer`、`AbstractStreamConsumer` 负责统一的 Stream 投递、消费、ACK、重试骨架，具体业务模块只实现解析 payload 和执行业务逻辑。

## 2. 基础面试问题

### Q1：这个异步任务模块解决了什么业务问题？

它解决的是 AI 面试平台中耗时任务不能同步阻塞用户请求的问题。例如简历分析、知识库向量化、面试评估都可能涉及文件解析、LLM 调用、向量写入等慢操作。模块把这些操作封装为异步任务，前端先拿到 `taskId`，后台通过 Redis Stream 执行，前端再查询任务状态。

面试中可以这样回答：

> 我没有把 AI 分析和向量化放在上传接口里同步执行，而是抽象了一个统一的异步任务控制面。它用数据库记录任务生命周期，用 Redis Stream 做消息运输，前端可以轮询任务状态，运维也可以对失败任务重试或取消。这样用户请求更快返回，耗时任务也具备可观测和可恢复能力。

### Q2：为什么要单独抽一个 `asynctask` 模块，而不是每个业务模块自己维护状态？

因为四类任务的共性非常明显：都有任务创建、入队、处理中、成功、失败、取消、重试、死信、pending 恢复这些生命周期。如果每个业务模块各写一套，会出现状态语义不一致、重试策略不一致、前端无法统一展示的问题。

抽成统一模块后，简历、知识库、文本面试、语音面试只需要接入同一套任务台账和状态机。新增任务类型时扩展 `AsyncTaskType`、新增 Producer/Consumer，并复用 `AsyncTaskService` 即可。

### Q3：这个模块对前端有什么价值？

前端不需要关心后台到底是 LLM、向量库还是文件解析。它只关心任务 ID 和状态：

```text
PENDING -> 显示等待处理
PROCESSING -> 显示正在处理
COMPLETED -> 拉取结果或跳转报告页
FAILED / DEAD_LETTER -> 展示失败并提示重试
CANCELLED -> 展示已取消
```

`AsyncTaskController.getTask()` 就是前端轮询的统一出口，`listTasks()` 则适合管理后台查看任务总览。

### Q4：`AsyncTaskEntity` 和 Redis Stream 消息有什么区别？

`AsyncTaskEntity` 是任务状态的完整记录，包含任务类型、业务 ID、状态、重试次数、Stream 消息 ID、错误信息、payload 摘要、创建更新时间等。Redis Stream 消息只保存消费者干活需要的轻量字段，比如 `taskId`、`businessId`、`resumeId`、`retryCount`。

一句话：数据库是状态机，Stream 是运输带。

## 3. 进阶面试问题

### Q1：为什么不能只用 Redis Stream，不存数据库任务表？

如果只用 Redis Stream，前端无法方便地按任务 ID 查询进度，管理后台也很难筛选失败任务、查看历史错误、手动重试。Stream 更适合消息流转，不适合作为长期可查询的业务状态表。

数据库任务表提供了三个关键能力：

1. 可查询：按类型、状态、创建时间过滤。
2. 可运维：失败后能看到错误原因并重试。
3. 可审计：任务历史和状态变化不会因为消息 ACK 后消失。

所以当前设计更接近“数据库保存状态，Redis Stream 负责调度执行”。

### Q2：这个模块如何保证同一业务对象不会重复创建活跃任务？

`AsyncTaskService.createOrReusePendingTask()` 会先按 `taskType + businessId + ACTIVE_STATUSES` 查询是否存在活跃任务。活跃状态包括 `PENDING` 和 `PROCESSING`。如果存在，就返回旧任务并标记 `created=false`；如果不存在，才创建新任务。

同时 `AsyncTaskEntity` 上有唯一索引 `idx_async_task_active_key`，`activeKey` 格式是 `taskType:businessId`。任务进入终态时会清空 `activeKey`，这样同一个业务对象在活跃期只能有一个任务，终态后又可以重新发起。

### Q3：为什么任务入队放在事务提交之后？

具体 Producer 使用 `TransactionAfterCommitExecutor`，在业务事务提交后再执行 `sendTask()`。这样可以避免一种典型不一致：数据库里的简历或知识库还没提交成功，消费者已经拿到消息开始处理，结果查不到业务实体。

这体现了一个可靠异步系统的基本原则：消息最好在本地事务成功之后再投递。如果要进一步增强，可以引入 Outbox Pattern，把“待发送消息”也写入数据库，再由后台扫描投递。

### Q4：`PendingMessageRecoveryService` 为什么要注入 `List<AbstractStreamConsumer<?>>`？

这是 Spring 的集合注入能力。只要容器中存在 `AbstractStreamConsumer` 的子类 Bean，Spring 就会自动收集到这个 List 中。当前会包括简历分析、知识库向量化、面试评估、语音面试评估四个消费者。

恢复服务不需要知道每个业务消费者的细节，只负责遍历它们并调用 `recoverPendingMessages()`。新增一种异步任务时，只要新增 Consumer Bean，pending 恢复能力会自动覆盖，符合开闭原则。

## 4. 技术延伸问题

### Q1：如果不用 Redis Stream，还能用什么方案实现？

可以有多种替代方案：

| 方案 | 适合场景 | 优点 | 缺点 |
|---|---|---|---|
| `@Async` + 线程池 | 单体应用、低并发后台任务 | 简单，开发成本低 | 进程重启任务丢失，缺少可恢复性 |
| 定时任务扫表 | 强一致、低吞吐任务 | 数据库就是任务队列，易排查 | 高并发下 DB 压力大，延迟取决于扫描频率 |
| Redis List | 简单队列 | 实现简单 | 消费者组、pending 恢复能力弱 |
| Redis Stream | 中小型系统可靠队列 | 消费者组、PEL、XAUTOCLAIM、ACK 语义完整 | 运维和语义比普通队列复杂 |
| RabbitMQ | 复杂路由、可靠投递 | 成熟 MQ，ACK/DLX/TTL 丰富 | 需要额外中间件和运维 |
| Kafka | 高吞吐日志流 | 横向扩展强、吞吐高 | 对单任务状态管理不直接，成本较高 |
| XXL-JOB / Quartz | 定时调度类任务 | 适合周期性任务管理 | 不适合细粒度实时消息消费 |

本项目选择 Redis Stream 是合理的，因为项目已经依赖 Redis，而且任务吞吐属于中等规模，需要消费者组、ACK、pending 恢复和轻量运维能力。

### Q2：Redis Stream 和 RabbitMQ 的面试对比怎么说？

Redis Stream 更像 Redis 内置的轻量消息流，优势是接入成本低、和现有 Redis 复用、支持消费者组和 PEL。RabbitMQ 更像专门的消息中间件，ACK、死信队列、延迟队列、路由模型更成熟。

如果面试官问生产级系统如何选，可以回答：当前项目用 Redis Stream 足够支撑简历分析和向量化这类后台任务；如果未来任务量更大、需要复杂路由、消息 TTL、死信交换机、优先级队列、跨服务解耦，可以迁移到 RabbitMQ 或 Kafka，但 `AsyncTaskService` 的任务台账设计可以保留。

### Q3：这个模块和 Saga、Outbox 有什么关系？

它已经有任务状态机和事务后投递，但还不是完整 Outbox。Outbox 的关键是：业务数据和消息记录在同一个数据库事务中落库，然后由独立投递器把 Outbox 消息可靠发送到 MQ。这样可以处理“数据库提交成功但 MQ 投递失败”的窗口。

当前代码通过 `afterCommitExecutor` 降低了“消息早于业务事务”的问题，但如果 after-commit 回调中 Redis 不可用，任务会被标记失败，需要人工或业务接口再次触发。生产增强可以把 Stream 投递动作改为 Outbox。

## 5. 改进方案问题

### Q1：当前模块架构上最大的优点是什么？

优点是把异步任务的通用生命周期抽象出来了，而且数据库状态和消息运输职责分离清晰。业务模块不用重复实现任务表、重试次数、失败原因、管理后台查询，新增任务类型也能复用统一的控制面。

### Q2：当前模块可以怎么优化？

可以从这些方向优化：

1. `listTasks()` 增加分页和时间范围过滤，避免任务表大了以后一次性返回全部记录。
2. 把 `AsyncTaskStatusDTO` 改名为 `AsyncTaskStatus`，它实际是持久化状态枚举，不只是 DTO。
3. 统一 `FAILED` 和 `DEAD_LETTER` 的语义。目前 Producer 入队失败走 `FAILED`，Consumer 重试耗尽多处走 `DEAD_LETTER`，需要在文档和代码上明确。
4. 给 `createOrReusePendingTask()` 增加唯一索引冲突兜底处理，解决高并发下两个请求同时查不到活跃任务的问题。
5. 手动重试时可以记录 `parentTaskId` 或 retry history，便于追踪人工重试前后的任务关系。
6. `nextRetryAt` 字段当前未真正用于延迟重试，可以实现指数退避或删除该字段避免误导。

### Q3：如果要做成生产级任务平台，还差什么？

还可以补充：

1. 分页查询、批量重试、批量取消。
2. 任务指标面板：创建数、成功率、平均耗时、失败率、pending 数、重试次数分布。
3. 告警：失败率超过阈值、DEAD_LETTER 堆积、pending 过久。
4. Outbox 保证数据库和消息投递最终一致。
5. 权限控制：只有管理员可以取消或重试所有任务，普通用户只能看自己的任务。
6. 任务超时机制：`PROCESSING` 超过阈值自动标记异常或重新调度。

## 6. 故障处理问题

### Q1：用户上传简历后一直显示处理中，怎么排查？

可以按链路排查：

1. 查 `async_tasks` 表：任务是否存在，状态是 `PENDING` 还是 `PROCESSING`。
2. 查 `messageId`：是否已经 `markEnqueued()`，如果为空说明 Stream 投递可能失败。
3. 查 Redis Stream：对应 Stream 是否有消息，消费者组是否存在。
4. 查消费者日志：是否启动、是否持续报错。
5. 查 pending：如果消息在 PEL 里，等待 `PendingMessageRecoveryService` 恢复或手动检查 XAUTOCLAIM。
6. 查业务表：简历是否被删除、文本是否为空、LLM 调用是否超时。

### Q2：任务状态是 `DEAD_LETTER`，应该怎么处理？

`DEAD_LETTER` 表示任务已经超过自动重试上限，或者重试入队本身失败。处理流程是先看 `lastError` 判断根因：如果是 LLM 超时、Redis 短暂不可用、外部服务限流，可以修复环境后调用 `POST /api/async-tasks/{id}/retry`；如果是数据本身错误，例如文件无法解析、业务实体缺失，则不应该盲目重试，需要修数据或取消任务。

### Q3：消费者崩溃会不会导致消息丢失？

正常不会。Redis Stream 消费者组里，消息被投递给消费者但没有 ACK 时，会进入 PEL。应用启动后和每 60 秒定时任务都会调用 `recoverPendingMessages()`，通过 `XAUTOCLAIM` 认领空闲超过 60 秒的 pending 消息，再重新走处理流程。

需要注意的是，业务逻辑本身必须幂等。因为恢复 pending 或手动重试可能导致同一业务对象被重新处理，所以消费者里也做了“结果已存在就跳过”的幂等判断。
