# 并发、幂等、重试、取消与故障处理

## 1. 模块基础讲解

异步任务最容易被追问的不是“怎么发消息”，而是并发和异常场景：重复上传怎么办、消费者崩了怎么办、LLM 超时怎么办、用户取消怎么办、任务执行一半服务重启怎么办。

本项目用以下机制处理这些问题：

| 问题 | 当前机制 |
|---|---|
| 重复提交 | `createOrReusePendingTask()` + `activeKey` 唯一约束 |
| 临时失败 | Consumer 捕获异常后最多重试 3 次 |
| 重试耗尽 | 标记 `DEAD_LETTER`，等待人工介入 |
| 消费者崩溃 | Redis Stream PEL + `PendingMessageRecoveryService` |
| 用户取消 | `cancelTask()` 设置 `CANCELLED`，消费者检查取消状态 |
| 重复消费 | 业务 Consumer 内部做结果已存在的幂等判断 |
| 入队失败 | Producer `onSendFailed()` 更新业务状态和任务状态 |

核心思想是：异步系统默认要接受“至少一次执行”的现实，然后通过任务状态、唯一键、幂等判断、重试和人工兜底把风险压住。

## 2. 基础面试问题

### Q1：如何防止用户重复点击导致重复任务？

Producer 调用 `AsyncTaskService.createOrReusePendingTask()` 时，会先查同一 `taskType + businessId` 是否已有 `PENDING` 或 `PROCESSING` 任务。如果有，就返回已有任务并且 `created=false`，Producer 看到后直接跳过入队。

同时数据库有 `active_key` 唯一索引作为兜底，避免并发下产生两个活跃任务。

### Q2：自动重试是怎么实现的？

`AbstractStreamConsumer` 捕获业务异常后读取消息里的 `retryCount`。如果小于 `MAX_RETRY_COUNT=3`，调用子类 `retryMessage()` 重新 XADD 一条消息，重试次数加 1，再 ACK 当前消息。子类重试成功后调用 `asyncTaskService.markRetrying()`，把任务状态重新设为 `PENDING` 并记录新的 `messageId`。

### Q3：什么时候取消任务？

取消分两种：

1. 人工取消：调用 `POST /api/async-tasks/{id}/cancel`。
2. 业务取消：消费者发现业务对象不存在或无法获取有效内容，抛出 `AsyncTaskCancelledException`。

取消任务会进入 `CANCELLED`，并 ACK 消息，不再重试。因为这类错误通常不是临时故障，重试没有意义。

### Q4：为什么消费者要做幂等判断？

因为 Redis Stream 是至少一次消费语义。消费者可能在业务执行成功后、ACK 前崩溃，pending 恢复后同一消息会再次执行。如果没有幂等判断，可能重复生成报告、重复写向量、重复扣费或覆盖数据。

当前消费者会检查结果是否已经存在，存在则跳过。

## 3. 进阶面试问题

### Q1：当前重试策略会不会造成雪崩？

有可能。当前失败后立即重新入队，没有退避。如果外部 LLM 服务大面积超时，很多任务会快速重试 3 次，放大外部服务压力。

改进方式：

1. 指数退避：第一次 10 秒，第二次 30 秒，第三次 2 分钟。
2. 加随机抖动：避免大量任务同一时刻重试。
3. 按任务类型限流：比如 LLM 任务和向量任务用不同限流器。
4. 熔断：外部服务连续失败时暂停投递或直接进入延迟重试。

### Q2：ACK 失败会产生什么问题？

如果业务已经执行成功，但 `streamAck()` 失败，消息会留在 PEL。之后 pending 恢复会重新处理，导致重复执行风险。这就是为什么幂等判断是必需的。

当前 `ackMessage()` 捕获异常并记录日志，没有向上抛出。优点是不会让消费者线程崩掉；缺点是 ACK 失败只能靠后续 pending 恢复和幂等处理。

### Q3：手动重试和自动重试有什么区别？

| 类型 | 触发方 | 适用状态 | retryCount | 使用场景 |
|---|---|---|---|---|
| 自动重试 | Consumer | 执行异常且未超过上限 | 递增 | 临时故障 |
| 手动重试 | 管理后台/API | `FAILED`、`CANCELLED`、`DEAD_LETTER` | 重置为 0 | 人工确认故障已恢复 |

手动重试会重新构造轻量 Stream 消息，并把任务设回 `PENDING`。

### Q4：取消一个正在调用 LLM 的任务，会发生什么？

当前代码不能强制中断已经发出的 LLM 请求。取消会先更新任务表。如果消费者还没进入 `markProcessing()`，会检测到取消并结束；如果已经在 `processBusiness()` 里调用 LLM，可能仍会等 LLM 返回。

改进方式是增加协作式取消检查：

```text
markProcessing 前检查
LLM 调用前检查
LLM 调用后保存结果前检查
长循环处理每个 chunk 前检查
```

这样即使不能取消外部请求，也能避免取消后继续保存结果。

## 4. 技术延伸问题

### Q1：如何实现 exactly-once？

严格 exactly-once 在分布式系统里成本很高。更现实的答案是：消息系统提供至少一次投递，业务侧通过幂等实现“效果上的 exactly-once”。

常见做法：

1. 业务唯一键：例如一个 session 只允许一份最终评估报告。
2. 幂等表：记录已经处理过的 messageId 或 taskId。
3. 乐观锁：更新时带 version。
4. 结果存在则跳过。
5. 数据库事务保证状态和结果一致。

本项目采用的是“结果存在则跳过”的幂等方式，简单有效。

### Q2：如何做分布式锁防重复？

可以用 Redis 分布式锁锁住 `taskType:businessId`，创建任务和投递消息前先加锁。但本项目已经用数据库唯一约束做最终兜底。相比 Redis 锁，数据库唯一约束更可靠，因为任务状态本来就在数据库里。

更推荐的方案是：保留唯一约束，在代码层捕获唯一冲突后回查已有任务。只有在业务处理阶段需要保护共享资源时，再考虑分布式锁。

### Q3：如何处理任务超时？

可以增加一个定时扫描器：

```text
查找 status=PROCESSING 且 updatedAt < now - timeout
  -> 检查 Redis PEL 是否仍有消息
  -> 如果有，等待 pending 恢复
  -> 如果没有，标记 FAILED 或重新入队
```

不同任务类型的 timeout 应该不同，例如简历分析 2 分钟，知识库大文档向量化可能 10 分钟。

## 5. 改进方案问题

### Q1：并发控制可以怎么加强？

1. 捕获 `active_key` 唯一冲突并回查已有任务。
2. `markProcessing()` 增加状态前置校验，只允许 `PENDING -> PROCESSING`。
3. 状态更新时使用乐观锁版本号，避免并发覆盖。
4. 手动取消和消费者完成之间做冲突处理，避免取消后又被标记完成。
5. 对管理操作增加审计日志。

### Q2：重试机制可以怎么加强？

1. 实现 `nextRetryAt`，支持延迟重试。
2. 区分可重试异常和不可重试异常。
3. 按错误类型决定是否进入 `CANCELLED`、`FAILED` 或 `DEAD_LETTER`。
4. 增加 retry history，记录每次错误。
5. 支持人工选择“从头重试”或“从失败步骤继续”。

### Q3：取消机制可以怎么加强？

1. 增加取消原因参数，而不是固定“用户手动取消任务”。
2. 在业务处理关键节点检查任务状态。
3. 对大文档向量化按 chunk 保存进度，取消后停止后续 chunk。
4. 对外部 API 调用设置短超时，避免取消后长时间阻塞。
5. 前端展示取消是否已生效，而不是只展示状态已取消。

## 6. 故障处理问题

### Q1：重复生成了两份结果，怎么查？

排查：

1. 查是否同一 `businessId` 出现多个活跃任务。
2. 查 `active_key` 是否为空或唯一索引是否生效。
3. 查是否存在并发创建任务时唯一冲突未处理。
4. 查消费者幂等判断是否完整。
5. 查 ACK 是否失败导致 pending 恢复重复处理。

修复：

1. 补唯一冲突兜底。
2. 强化业务唯一键。
3. 幂等判断放到保存结果的同一事务里。

### Q2：大量任务进入 `DEAD_LETTER` 怎么办？

先按 `taskType` 和 `lastError` 聚合，判断是单一外部依赖故障还是某类数据问题。

如果是 LLM 超时或 API Key 失效，先修复配置，再批量重试。如果是文件解析失败，应该筛出异常文件重新上传或优化解析逻辑。如果是代码 bug，修复并发布后再重试。

不要直接全量重试，否则可能再次打爆外部服务。

### Q3：任务被取消但结果仍然生成了怎么办？

原因通常是取消发生在消费者已经进入业务执行之后，而业务执行完成后没有再次检查取消状态。

解决方案：

1. 在保存结果前查询任务状态，如果是 `CANCELLED` 则不保存。
2. 保存结果和标记完成放在一个带状态条件的事务里。
3. 给长任务增加取消检查点。
