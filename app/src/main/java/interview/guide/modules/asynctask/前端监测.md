是的，但不只是前端——这个 Controller 实际服务于**两种场景**：

### 1. 管理后台（运维视角）

`GET /api/async-tasks?status=FAILED` 这种带过滤条件的列表查询，以及重试、取消操作，是给**运维/管理员用的管理后台**。可以全局扫一眼哪些任务挂了，手动重试或取消。

### 2. 业务前端（用户视角）

当用户上传简历后触发异步分析时，前端的典型交互流程是：

```
用户点击"上传简历"
    │
    ▼
前端调 POST /api/resumes/upload
    │
    ▼
后端返回 { taskId: 42, status: "PENDING" }
    │
    ▼
前端开始轮询:
  每 2 秒调 GET /api/async-tasks/42
    │
    ├── status=PENDING     → 显示"处理中..."
    ├── status=PROCESSING  → 显示"AI 分析中..."
    ├── status=COMPLETED   → 展示分析结果 ✓（停止轮询）
    └── status=FAILED      → 提示"分析失败，请重试"（停止轮询）
```

所以 `GET /api/async-tasks/{id}` 这个接口就是前端**轮询异步任务状态的出口**——前端拿着任务 ID，每隔几秒查一次，状态变成终态（`COMPLETED`/`FAILED`/`CANCELLED`）就停止轮询。

总结：这个 Controller 同时承担了**管理后台的运维入口**和**业务前端的状态轮询入口**两个角色。
