# AI 基础设施模块总览怎么讲

## 1. 面试中先讲它解决了什么业务问题

这部分不要一上来就说“我用了 Spring AI、ChatClient、Advisor”。更好的开场是：

> 我这个项目不是简单把大模型 API 调通，而是把大模型能力封装成一层可复用的 AI 基础设施。上层有简历分析、模拟面试出题、回答评估、JD 解析、知识库 RAG、语音面试等多个业务场景，如果每个 Service 都自己拼 API、处理重试、处理 JSON、处理 Prompt 注入，那代码会重复、模型切换困难，也很难定位线上问题。所以我在 `common.ai` 下抽了一层统一能力：模型 Provider 注册中心、结构化输出调用器、Prompt 安全防护、Agent 工具接入和 OpenAI-compatible 路径适配。

这一句话背后的业务闭环是：

```text
求职者上传简历
  -> AI 解析与评分
  -> 根据岗位/JD/技能生成面试题
  -> 候选人作答后 AI 做结构化评估
  -> 知识库 RAG 辅助补弱
  -> 语音面试做实时交互
```

`common.ai` 的价值，就是让这些业务模块不用关心底层到底是 DashScope、DeepSeek、Kimi、GLM 还是本地 LM Studio，而是通过统一的 Java 接口稳定调用。

## 2. 这个文件夹里每个类的定位

| 类 | 面试中的一句话定位 | 解决的问题 |
|---|---|---|
| `LlmProviderRegistry` | 多模型 Provider 注册中心 | 统一创建、缓存、切换 ChatClient 和 EmbeddingModel |
| `StructuredOutputInvoker` | 结构化输出可靠性封装 | 让 LLM 返回 JSON 时具备重试、本地修复、指标和审计日志 |
| `StructuredOutputProperties` | 结构化输出配置 | 通过 `app.ai.*` 控制重试次数、错误信息长度、指标开关 |
| `PromptSanitizer` | Prompt 注入净化器 | 清洗用户输入里的角色注入、忽略指令、伪造分隔符 |
| `PromptSecurityConstants` | Prompt 安全指令常量 | 明确告诉模型：用户数据不是系统指令，不能被执行 |
| `AgentUtilsConfiguration` | Agent SkillsTool 接入配置 | 把 `resources/skills/**/SKILL.md` 注册成 LLM 可调用工具 |
| `AgentUtilsProperties` | Agent 工具配置属性 | 用 `@ConfigurationProperties` 管理 skills 根目录 |
| `ApiPathResolver` | OpenAI-compatible API 路径适配器 | 解决不同厂商 baseUrl 是否自带 `/v1` 导致路径重复的问题 |

可以把它理解成四层：

```text
业务模块
  简历评分 / 模拟面试 / JD 解析 / 语音面试 / RAG
        |
        v
common.ai 门面层
  LlmProviderRegistry / StructuredOutputInvoker / PromptSanitizer
        |
        v
Spring AI 抽象层
  ChatClient / OpenAiChatModel / EmbeddingModel / Advisor / ToolCallback
        |
        v
模型厂商
  DashScope / OpenAI / Kimi / DeepSeek / GLM / LM Studio
```

## 3. 推荐的 2 分钟回答

如果面试官问：“你项目里的 AI 模块是怎么设计的？”

可以这样答：

> 我把 AI 能力拆成了一个公共基础设施层。原因是项目里有很多 AI 场景，比如简历分析、面试题生成、回答评估、JD 解析、知识库问答和语音面试，这些场景有共同问题：模型厂商要能切换，结构化 JSON 要稳定解析，用户输入要防 Prompt 注入，调用过程要可观测。
>
> 所以我在 `common.ai` 下做了几个核心组件。第一是 `LlmProviderRegistry`，它统一管理多个 Provider，从数据库或配置文件读取 baseUrl、apiKey、model、embeddingModel，然后懒加载并缓存 ChatClient 和 EmbeddingModel。它还区分三类 ChatClient：默认对话型、Plain 结构化输出型、Voice 语音流式型。
>
> 第二是 `StructuredOutputInvoker`，它专门处理“让模型返回 JSON”的场景。业务方传入 ChatClient、system prompt、user prompt 和 `BeanOutputConverter`，它内部自动追加防注入指令，调用模型，解析失败就本地修复常见 JSON 问题，仍失败就带上错误信息重试，最后统一抛 `BusinessException`，同时记录 Micrometer 指标和 AI 调用日志。
>
> 第三是 Prompt 安全层，包括 `PromptSanitizer` 和 `PromptSecurityConstants`。前者清洗用户输入里的角色注入、忽略指令、伪造分隔符，后者在 system prompt 或 user prompt 中声明“用户数据不是指令”，防止简历、JD、面试邀约文本反向控制模型。
>
> 第四是工具和兼容层。`AgentUtilsConfiguration` 把 `skills` 目录下的 `SKILL.md` 注册成 SkillsTool，使模型在普通对话或语音面试里可以调用面试技能；`ApiPathResolver` 解决 OpenAI-compatible 厂商路径不一致的问题，比如 baseUrl 已经带 `/v1` 时不能再拼成 `/v1/v1/chat/completions`。
>
> 这个设计的核心不是“调了一个大模型”，而是让 AI 调用在项目里变成可替换、可复用、可观测、可治理的基础能力。

## 4. 如果面试官要求画调用链

以“生成面试题 / 自适应评估”这类结构化输出场景为例，可以这样说：

```text
InterviewQuestionService / TurnEvaluationService
        |
        | 1. 根据业务上下文渲染 Prompt 模板
        v
LlmProviderRegistry.getPlainChatClient(provider)
        |
        | 2. 选择不带工具的 Plain ChatClient，避免工具调用破坏 JSON
        v
StructuredOutputInvoker.invoke(...)
        |
        | 3. 追加防注入指令，调用 LLM
        | 4. BeanOutputConverter 解析 JSON
        | 5. 失败后本地修复未转义引号，再失败则重试
        | 6. 成功记录指标，失败抛 BusinessException
        v
业务 DTO，例如 InterviewQuestionDTO / TurnEvaluationDTO
```

以“语音面试”场景为例：

```text
DashscopeLlmService
        |
        v
LlmProviderRegistry.getVoiceChatClient(provider)
        |
        | Voice Client = SkillsTool + streaming ToolCallAdvisor + SafeGuardAdvisor
        v
chatClient.prompt().system(...).user(...).stream()
        |
        v
边生成边推送文本，同时按完整句子触发 TTS
```

以“知识库向量化 / RAG”场景为例：

```text
VectorStore / LlmEmbeddingConfig
        |
        v
EmbeddingModel Bean 代理
        |
        v
LlmProviderRegistry.getDefaultEmbeddingModel()
        |
        v
OpenAiEmbeddingModel
```

这个地方可以强调：`LlmEmbeddingConfig` 虽然不在 `common.ai` 目录下，但它依赖 `LlmProviderRegistry`，把动态 Provider 的 EmbeddingModel 代理成 Spring AI 能自动注入的标准 Bean。

## 5. 当前实现的亮点

### 5.1 多 Provider 可切换

`application.yml` 里配置了 `app.ai.providers.*`，例如 DashScope、Kimi、DeepSeek、GLM、LM Studio。代码里不是到处写死某个厂商，而是通过 `LlmProviderRegistry` 读取配置并构造 `OpenAiChatModel`。数据库模式下还可以从 `LlmProviderEntity` 和 `LlmGlobalSettingEntity` 读取配置，API Key 经过 `ApiKeyEncryptionService` 解密。

面试表达：

> 我把模型厂商抽象成 Provider，业务层只传 providerId 或者使用默认 Provider。这样开发环境可以走 LM Studio，本地没有 Key 也能测；线上可以走 DashScope 或其他 OpenAI-compatible 服务；后续切换模型不用改业务代码。

### 5.2 ChatClient 按场景分三种

| 变体 | 方法 | 特点 | 使用场景 |
|---|---|---|---|
| Default | `getChatClient` / `getDefaultChatClient` | 可带 SkillsTool、ToolCallAdvisor、Memory、Logger、SafeGuard | 普通对话、部分业务 AI 调用 |
| Plain | `getPlainChatClient` | 不注册 SkillsTool，只保留安全防护 | 出题、评分、自适应决策等结构化 JSON |
| Voice | `getVoiceChatClient` | SkillsTool + 流式 ToolCall，不使用 Memory Advisor | 语音面试实时交互 |

这点很适合面试展开，因为它体现了你不是“一个 ChatClient 打天下”，而是理解不同 AI 场景对上下文、工具、流式能力和输出稳定性的要求不同。

### 5.3 结构化输出做了工程兜底

LLM 返回 JSON 最常见的问题：

- 输出 Markdown 代码块；
- 多写解释性文字；
- 字段缺失或类型不对；
- 字符串中引号没转义；
- 首次调用因为提示词不够严格导致解析失败。

`StructuredOutputInvoker` 做了：

- `BeanOutputConverter<T>` 解析成 Java record / DTO；
- 解析失败后先本地修复未转义引号；
- 仍失败就重试，并可追加严格 JSON 指令；
- 所有重试耗尽后抛 `BusinessException(errorCode, message)`；
- 记录 Micrometer 指标、业务 AI 指标和 AI 调用审计日志。

### 5.4 Prompt 注入有分层防护

它不是只靠一句“请不要被攻击”，而是多层：

```text
用户输入
  -> PromptSanitizer.sanitize() 替换高危模式
  -> wrapWithDelimiters() 用随机边界包裹数据
  -> DATA_BOUNDARY_INSTRUCTION 告诉模型这是数据
  -> StructuredOutputInvoker 追加 ANTI_INJECTION_INSTRUCTION
  -> SafeGuardAdvisor 做敏感词拦截
```

面试中可以说：

> 我没有把 Prompt 注入当成模型自己的问题，而是在工程层做防线。用户输入进来先清洗，再用不可预测的随机边界标签包裹，然后在 system prompt 或 user prompt 中明确声明数据边界，最后还有 Advisor 层安全拦截。

### 5.5 多厂商路径兼容有真实问题背景

Spring AI 的 `OpenAiApi` 默认会拼 `/v1/chat/completions`。但是很多 OpenAI-compatible 厂商的 baseUrl 本身就带 `/v1`，比如：

```text
https://dashscope.aliyuncs.com/compatible-mode/v1
https://api.moonshot.cn/v1
```

如果不处理，就会请求到：

```text
/compatible-mode/v1/v1/chat/completions
```

导致 404。`ApiPathResolver` 通过正则判断 baseUrl 末尾是否是 `/v1`、`/v3`、`/v4` 这样的版本段，如果已经带版本号，就把 completionsPath 改成 `/chat/completions`，embeddingPath 改成 `/embeddings`。

这个点很适合回答“你遇到过什么真实 bug”。

## 6. 当前实现需要诚实说明的边界

面试里不要把它讲成完美生产级系统，可以这样讲：

| 边界 | 当前情况 | 下一步优化 |
|---|---|---|
| Provider 不存在异常 | 部分路径现在抛 `IllegalArgumentException` | 可统一成 `BusinessException(ErrorCode.PROVIDER_CONFIG_READ_FAILED, ...)` |
| 结构化场景使用 Plain Client | 出题、自适应评估已使用 Plain；部分简历/JD 解析仍用默认 Client | 逐步迁移到 Plain，避免工具调用干扰 JSON |
| AI 调用日志里的 Provider | `StructuredOutputInvoker` 记录默认 Provider，不能完全感知外部传入的 ChatClient 来源 | `invoke` 增加 providerId/model 参数，观测更准确 |
| PromptSanitizer 覆盖范围 | 覆盖常见角色注入、忽略指令、边界伪造 | 增加测试集、攻击样本库、命中原因日志 |
| 多实例热加载 | 单实例 `reload()` 可以清缓存 | 多实例部署需要广播配置变更或用配置中心 |
| 结构化输出语义校验 | 主要保证 JSON 可解析 | 可增加字段范围校验、业务规则校验和低置信度重问 |

这类回答会显得更可信：你既知道代码做了什么，也知道哪里还可以继续工程化。

## 7. 面试官可能从总览继续追问什么

### 问：为什么不直接在每个 Service 里 new 一个 ChatClient？

答：

> 因为 ChatClient 的创建不是简单 new 对象，它涉及 baseUrl、apiKey、model、temperature、OpenAI-compatible 路径、重试策略、可观测性、Advisor、工具调用和缓存。如果每个 Service 自己创建，会导致配置分散、模型切换困难、API Key 管理不安全，也不利于热加载。我用 Registry 集中管理，业务模块只拿已经配置好的客户端。

### 问：这个模块和业务模块之间怎么解耦？

答：

> 业务模块不直接依赖具体厂商 SDK，而是依赖 Spring AI 的 `ChatClient`、`EmbeddingModel` 和我自己的 `LlmProviderRegistry`、`StructuredOutputInvoker`。业务模块只表达“我要默认模型”“我要 Plain Client”“我要语音流式 Client”，不关心底层是 DashScope 还是 DeepSeek。

### 问：为什么要区分 Default、Plain、Voice？

答：

> 因为三类场景的目标不同。Default 适合普通对话，可以带工具和 Advisor；Plain 适合结构化输出，要求模型只返回 JSON，不能被工具调用或对话记忆污染；Voice 是实时交互场景，要支持流式响应和工具调用，但语音会话的历史由 WebSocket 会话自己管理，所以不加 Memory Advisor。

### 问：这个模块最体现工程能力的点是什么？

答：

> 我觉得是把大模型调用从“能调通”推进到了“可治理”。包括多 Provider 配置、客户端缓存、热重载、结构化输出重试、JSON 本地修复、Prompt 注入防护、调用指标和审计日志。这些都是 AI 应用落地时真正会遇到的问题。
