## 一、项目角色分析

### 1.1 核心定位

`StructuredOutputInvoker` 是 LLM 结构化输出场景的**统一调用门面**，在整个项目中扮演"AI 调用兜底者"的角色。它不直接调用 LLM API，而是在 Spring AI 的 `ChatClient` 之上封装了一层可靠性保障——重试、JSON 修复、防注入、指标采集。

业务方只需传入提示词和期望的返回类型，调用方无需关心底层是否失败、JSON 是否合法，StructuredOutputInvoker 自动处理所有异常路径。

### 1.2 系统职责

| 职责 | 说明 |
|------|------|
| **可靠性保障** | 重试机制 + 本地 JSON 修复，最大化 LLM 调用成功率 |
| **安全防护** | 每次调用自动追加防注入指令 |
| **可观测性** | 三层监控：Micrometer 指标、业务指标、审计日志 |
| **配置驱动的行为控制** | 通过 6 个配置开关灵活控制重试策略和监控行为 |
| **错误统一处理** | 所有失败路径统一抛出 `BusinessException`，包含可追溯的错误码 |

## 二、代码调用与交互

### 2.1 上游调用方

| 调用方 Service | 场景 | 期望输出 |
|----------------|------|---------|
| `ResumeGradingService` | 简历 AI 评分 | `ResumeAnalysisResponse`（评分、优缺点） |
| `UnifiedEvaluationService` | 面试答案评估 | 评估结果对象（正确性、完整性、建议） |
| `InterviewSkillService` | 技能评估 | 技能等级评估结果 |
| `InterviewQuestionService` | 面试题生成 | 面试题对象 |

所有调用方使用相同的调用模式：

```java
T result = invoker.invoke(
    chatClient,
    systemPrompt,       // 含 JSON Schema 的提示词
    userPrompt,         // 用户输入
    outputConverter,    // BeanOutputConverter<T>
    errorCode,          // 业务错误码
    "简历分析失败：",    // 错误前缀
    "简历评分",          // 日志上下文
    log                 // SLF4J Logger
);
```

### 3.2 职责边界

| 区域 | 职责 | 不负责 |
|------|------|--------|
| 常量区 | 定义静态配置和不变量 | 运行时可变行为 |
| 配置区 | 持有构造时注入的配置 | 动态决策（由方法实现） |
| 公共接口 | 对外暴露唯一调用入口 | 内部实现细节 |
| JSON 修复链 | 本地修复 JSON 格式问题 | 语义级别的内容修复 |

| 辅助工具 | 标签规范化、配置解析 | 业务逻辑 |

## 四、关键关注点

### 4.1 不可变设计

所有配置字段均为 `final`，构造函数一次性赋值后不可变。这确保了 `@Component` 单例在多线程环境下的线程安全——不需要任何同步机制。

### 4.2 可选依赖处理

三个外部依赖使用 `@Autowired(required = false)`：
- `MeterRegistry` — Micrometer 可选
- `AiInvocationLogService` — 审计日志可选
- `AiMetricsRecorder` — 业务指标可选

所有使用这些依赖的方法都以 null 检查开头，遵循 fail-silent 原则（不可用则静默跳过）。

### 4.3 边界保护

```java
this.maxAttempts = Math.max(1, ...);           // 确保至少执行 1 次
this.errorMessageMaxLength = Math.max(20, ...); // 防止错误信息太短
```

防止配置错误导致的功能退化。

## 五、设计决策理由

### 5.1 为什么选择"门面模式"而非让每个 Service 自行处理？

- **关注点分离**：业务 Service 应专注于业务逻辑，不应关心 LLM 的 JSON 格式问题
- **统一行为**：所有结构化输出场景共享相同的重试策略和监控标准
- **可配置性**：通过 `StructuredOutputProperties` 集中管理，无需在每个 Service 中重复配置

### 5.2 为什么本地修复优先于重试？

- **零成本**：本地修复不产生额外的 LLM API 调用费用
- **低延迟**：不需要等待第二次网络请求
- **高命中率**：未转义引号是 LLM JSON 输出中最常见的错误

### 5.3 为什么用 final 字段而非 setter？

- **线程安全**：不可变对象天然线程安全
- **配置一致性**：避免运行时被意外修改导致行为不一致

## 六、流程总结

StructuredOutputInvoker 作为 LLM 结构化输出的统一门面，被简历评分、面试评估、技能评估和出题等业务 Service 通过唯一的公开方法 invoke() 调用。每次调用时，它首先规范化上下文标签并追加防注入指令，然后进入配置驱动的重试循环：首次调用使用原始提示词，重试调用通过 buildRetrySystemPrompt() 根据三层开关构建增强提示词（可选追加严格 JSON 指令和上次失败原因）。每次 LLM 返回内容后，convertWithRepair() 先尝试直接 JSON 转换，失败则调用 repairUnescapedQuotesInJsonStrings() 进行本地状态机修复再转换，两层兜底失败则进入下一轮重试。成功时记录三层指标（Micrometer、业务指标、审计日志）并返回 Java 对象；所有重试耗尽后统一抛出 BusinessException。整个类的设计遵循不可变模式和 fail-silent 原则，通过 final 字段保证线程安全，所有可选依赖均以 null 检查静默降级。
