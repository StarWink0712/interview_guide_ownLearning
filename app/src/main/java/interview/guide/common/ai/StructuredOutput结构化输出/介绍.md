## StructuredOutputInvoker 完整分析

### 一、定位与职责

它是 LLM 结构化输出调用的**统一门面**。业务代码只需要告诉它"帮我调用 LLM 并返回某种 Java 对象"，它自动处理重试、JSON 修复、防注入和指标记录，业务方无需关心底层复杂性。

```
业务 Service（简历评分、面试评估、出题...）
        │
        ▼
StructuredOutputInvoker.invoke(chatClient, prompt, converter, ...)
        │
        ├── 追加防注入指令
        ├── 重试循环（最多 maxAttempts 次）
        │     ├── 首次：原始提示词 → LLM
        │     └── 重试：修复提示词 → LLM
        ├── JSON 本地修复（未转义引号）
        ├── 指标记录（Micrometer + 业务指标 + 观测日志）
        └── 返回 Java 对象 或 抛 BusinessException
```

---

### 二、核心流程（invoke 方法）

```
invoke(chatClient, systemPrompt, userPrompt, converter, errorCode, errorPrefix, logContext, log)
│
├─ 1. 初始化
│     ├── System.nanoTime() — 计时开始
│     ├── normalizeContextTag(logContext) — "简历评分" → "resume_scoring"
│     └── 追加 PromptSecurityConstants.ANTI_INJECTION_INSTRUCTION
│
├─ 2. 重试循环 (attempt = 1 → maxAttempts)
│     │
│     ├── 构建本次提示词
│     │     attempt==1 → securedSystemPrompt（原始+防注入）
│     │     attempt>1  → buildRetrySystemPrompt(原始+修复指令+错误原因)
│     │
│     ├── 执行 LLM 调用
│     │     chatClient.prompt().system(...).user(...).call().content()
│     │
│     ├── JSON 修复 + 转换
│     │     convertWithRepair(content, converter, ...)
│     │     ├── 直接转换 → 成功 ✅
│     │     └── 失败 → repairUnescapedQuotesInJsonStrings() → 再转换
│     │           ├── 成功 ✅（日志：已在本地修复后解析成功）
│     │           └── 失败 → 抛异常，进入下一轮重试
│     │
│     ├── 成功 → 记录指标 → return result
│     └── 失败 → recordAttempt(failure) → 日志 warn → 继续循环
│
└─ 3. 全部失败
      ├── 记录失败指标
      ├── 记录观测日志（含完整 systemPrompt/userPrompt）
      └── throw new BusinessException(errorCode, errorPrefix + lastError)
```

---

### 三、JSON 修复引擎（repairUnescapedQuotesInJsonStrings）

这是代码中最精巧的部分——一个**状态机**，逐字符扫描 JSON 并修复未转义引号。

```
状态转换图：

         ┌──────────────────────────────────┐
         │        字符串外部 (inString=false) │
         │                                    │
         │  遇到 '"' → inString = true       │
         │  其他字符 → 直接复制               │
         └────────────┬───────────────────────┘
                      │ 进入字符串
         ┌────────────▼───────────────────────┐
         │        字符串内部 (inString=true)   │
         │                                    │
         │  遇到 '\\' → escaping = true       │
         │  遇到 '"'  → 判断是否结束符 ──────┐ │
         │  其他     → 直接复制              │ │
         └──────────────────────────────────┘ │
                                              │
         ┌────────────────────────────────────┘
         │
         ▼
isLikelyJsonStringTerminator(content, 引号位置+1)
         │
         ├── 跳过空白字符
         ├── 第一个非空白字符是 , } ] : → true（字符串结束，不转义）
         └── 其他字符 → false（字符串内部引号，加 \ 转义）
```

**关键精巧之处**：通过"引号后面的第一个非空白字符"来判断引号是分隔符还是内容。这是启发式算法，不需要完整解析 JSON。

### 四、重试提示词构建（buildRetrySystemPrompt）

```
buildRetrySystemPrompt(原始提示词, 上次错误)

retryUseRepairPrompt == false?
  → 直接返回原始提示词（不增强）

retryUseRepairPrompt == true?
  → 原始提示词
    + (retryAppendStrictJsonInstruction? → STRICT_JSON_INSTRUCTION)
    + "上次输出解析失败，请仅返回合法 JSON。"
    + (includeLastErrorInRetryPrompt? → "\n上次失败原因：{sanitized error}")
```

三层开关各自独立，可灵活组合：

| 组合 | 效果 |
|------|------|
| 全关 | 原样重试，不加任何修复提示 |
| 仅开 strictJson | 追加格式约束，但不告知错误原因 |
| 全开 | 格式约束 + 失败原因，LLM 知道哪里错了 |

### 五、三层监控体系

```
┌─ Micrometer 指标（recordAttempt / recordInvocation）──────────────┐
│ 维度：context（业务场景）+ status（success/failure）                │
│ 指标：计数器（调用次数、重试次数）+ 计时器（延迟）                   │
│ 用途：Grafana 大盘、Prometheus 告警                                │
└──────────────────────────────────────────────────────────────────┘
                              │
┌─ 业务指标（recordBusinessAiMetrics）──────────────────────────────┐
│ 维度：context + providerId + model                                │
│ 用途：观察不同 LLM 厂商/模型的表现差异                              │
│ 委托：AiMetricsRecorder                                           │
└──────────────────────────────────────────────────────────────────┘
                              │
┌─ 观测日志（recordAiInvocation）───────────────────────────────────┐
│ 内容：traceId + 完整 prompt + 耗时 + 错误信息                      │
│ 持久化：数据库（AiInvocationLogService）                           │
│ 用途：事后审计、调试、Prompt 优化分析                               │
│ 策略：fail-silent（写入失败不影响主流程）                           │
└──────────────────────────────────────────────────────────────────┘
```

### 六、配置参数（StructuredOutputProperties）

| 参数 | 默认值 | 作用 |
|------|--------|------|
| `structuredMaxAttempts` | 2 | 最多试 2 次（1 次正常 + 1 次重试） |
| `structuredIncludeLastError` | true | 重试时告诉 LLM 上次为什么失败 |
| `structuredRetryUseRepairPrompt` | true | 启用修复提示词 |
| `structuredRetryAppendStrictJsonInstruction` | true | 追加"只输出纯 JSON"指令 |
| `structuredErrorMessageMaxLength` | 200 | 错误信息截断长度 |
| `structuredMetricsEnabled` | true | 指标开关 |

**默认就是最佳配置**：试 2 次，重试时告诉 LLM 错在哪并要求输出纯 JSON。

### 七、防御性设计

| 设计点 | 体现 |
|--------|------|
| **不可变配置** | 构造函数中所有配置字段赋值后为 final，线程安全 |
| **参数边界** | `Math.max(1, maxAttempts)` 保证至少执行 1 次 |
| **null 安全** | `meterRegistry`、`aiInvocationLogService`、`aiMetricsRecorder` 全部 `@Autowired(required = false)` |
| **fail-silent** | `recordAiInvocation` 写入失败只打 warn，不抛异常 |
| **防注入** | 每次调用自动追加 `ANTI_INJECTION_INSTRUCTION` |
| **错误隔离** | JSON 修复失败用 `addSuppressed` 保留修复异常但不覆盖原始异常 |

---

### 八、一句话总结

`StructuredOutputInvoker` 是一个"调用一次、内部自动兜底"的 LLM 结构化输出门面——它把重试、JSON 修复、防注入和监控四件事封装在一个方法里，业务方只需传入提示词和期望的返回类型，失败自动重试加修复，最终要么拿到正确的 Java 对象、要么得到明确的 BusinessException。
