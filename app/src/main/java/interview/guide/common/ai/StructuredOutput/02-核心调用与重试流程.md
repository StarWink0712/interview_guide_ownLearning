## 一、项目角色分析

### 1.1 invoke() 的角色

`invoke()` 是 StructuredOutputInvoker 唯一的公开方法，是整个类的**业务入口**和**控制中心**。它负责编排整个结构化输出调用的生命周期：从初始化到多次尝试、从成功返回到底层兜底异常抛出。

### 1.2 buildRetrySystemPrompt() 的角色

负责构建重试时的增强系统提示词，是"告诉 LLM 上次哪里错了、这次应该怎么改"的实现者。通过三个独立开关控制提示词的增强程度。

### 1.3 sanitizeErrorMessage() 的角色

负责将异常信息清洗为适合嵌入提示词的格式（单行、截断），避免过长的堆栈信息干扰 LLM。

## 二、代码调用与交互

### 2.1 invoke() 内部调用关系

```
invoke(chatClient, systemPrompt, userPrompt, converter, errorCode, errorPrefix, logContext, log)
│
├─ 阶段1：初始化
│   ├── System.nanoTime()                    — 计时起点
│   ├── normalizeContextTag(logContext)       — "简历评分" → "resume_"
│   ├── TraceIdFilter.currentTraceId()       — 获取链路追踪 ID
│   └──  拼接 PromptSecurityConstants         — 追加防注入指令
│
├─ 阶段2：重试循环 (attempt = 1 → maxAttempts)
│   │
│   ├── attempt == 1?
│   │   └── 使用 securedSystemPrompt（原始 + 防注入）
│   │
│   ├── attempt > 1?
│   │   └── buildRetrySystemPrompt(securedSystemPrompt, lastError)
│   │         ├── retryUseRepairPrompt?       — 是否启用修复
│   │         ├── retryAppendStrictJsonInstruction? — 是否追加严格指令
│   │         └── includeLastErrorInRetryPrompt?    — 是否附带错误原因
│   │              └── sanitizeErrorMessage(lastError.getMessage())
│   │
│   ├── chatClient.prompt().system().user().call().content()
│   │
│   ├── convertWithRepair(content, converter, logContext, log)
│   │   ├── 成功 → 记录指标 → return result
│   │   └── 失败 → 抛异常，进入 catch
│   │
│   └── catch (Exception e)
│       ├── recordAttempt(contextTag, STATUS_FAILURE)
│       ├── attempt < maxAttempts? → log.warn("准备重试")
│       └── attempt == maxAttempts? → log.error("已达最大重试次数")
│
└─ 阶段3：全部失败
    ├── recordInvocation(STATUS_FAILURE)
    ├── recordBusinessAiMetrics(..., false)
    ├── recordAiInvocation(..., errorCode, lastError)
    └── throw new BusinessException(errorCode, errorPrefix + lastError)
```

### 2.2 与 ChatClient 的交互

```java
String content = chatClient.prompt()
    .system(attemptSystemPrompt)  // 设置 System role 提示词
    .user(userPrompt)             // 设置 User role 输入
    .call()                       // 同步阻塞 HTTP 请求
    .content();                   // 提取响应文本
```

调用方传入的 `chatClient` 已经预配置了 SkillsTool 和 Advisors（由 `LlmProviderRegistry` 构建），所以这次 LLM 调用会自动带上工具定义和拦截器链。

## 四、组件功能

### 4.1 invoke() 重试循环决策树

```
开始循环 attempt=1
    │
    ├─ attempt==1 ?
    │   是 → 使用 securedSystemPrompt
    │
    ├─ attempt>1 ?
    │   是 → buildRetrySystemPrompt() 返回三种可能：
    │         (A) retryUseRepairPrompt=false → 原样返回（不增强）
    │         (B) retryUseRepairPrompt=true, 其余两个 false
    │             → 仅追加"上次输出解析失败，请仅返回合法 JSON"
    │         (C) 三个开关全开
    │             → 追加严格指令 + 失败提示 + 具体错误原因
    │
    ├─ call LLM
    ├─ convertWithRepair()
    │   成功 → 记录成功指标 → return ✅
    │   失败 → lastError = e, recordAttempt(failure)
    │
    └─ attempt++ < maxAttempts? → 继续循环

循环结束 → 记录失败指标 → throw BusinessException
```

### 4.2 buildRetrySystemPrompt() 三层开关

```java
// 第 1 层：总开关
if (!retryUseRepairPrompt) return systemPromptWithFormat;  // 直接返回原样

// 第 2 层：严格 JSON 指令（可选）
if (retryAppendStrictJsonInstruction) {
    prompt.append(STRICT_JSON_INSTRUCTION);              // 追加严格 JSON 指令
}

// 基础修复：始终追加
prompt.append("上次输出解析失败，请仅返回合法 JSON。");

// 第 3 层：错误信息（可选）
if (includeLastErrorInRetryPrompt && lastError != null) {
    prompt.append("\n上次失败原因：")
          .append(sanitizeErrorMessage(lastError.getMessage()));
}
```

三层开关组合出的提示词效果：

| 配置 | 重试提示词内容 |
|------|--------------|
| 全关 | 原样（与首次相同） |
| 仅开 retryUseRepairPrompt | 上次输出解析失败，请仅返回合法 JSON。 |
| 全部开启 | 严格JSON指令 + 上次输出解析失败... + 上次失败原因：Cannot deserialize value... |

### 4.3 sanitizeErrorMessage() 清洗规则

```java
"JSON parse error:\n Cannot deserialize value of type..."  // 原始多行错误
    ↓
"JSON parse error:  Cannot deserialize value of type..."   // 换行 → 空格
    ↓ 超长截断
"JSON parse error:  Cannot deserialize value of type......" // 200字符 → "......"
```

**设计理由**：过长的堆栈嵌入提示词会浪费 token 且干扰 LLM 理解，截断至 200 字符在提供有用信息和避免干扰间取得平衡。

## 五、组件交互

### 5.1 异常传播路径

```
convertWithRepair() 内:
  ├── converter.convert() 失败 → catch firstError
  │     ├── repairJSON() 有变化 → converter.convert(repaired) 成功 → return ✅
  │     ├── repairJSON() 有变化 → converter.convert(repaired) 失败
  │     │     → firstError.addSuppressed(repairError) → throw firstError
  │     └── repairJSON() 无变化 → throw firstError
  │
  └── 异常向上传播到 invoke() 的 catch 块
        → lastError = e
        → recordAttempt(STATUS_FAILURE)
        → 判断是否继续重试
```

### 5.2 成功/失败的指标记录时机

```
成功路径：
  recordAttempt(SUCCESS)          ← 当前这次尝试是成功的
  recordInvocation(SUCCESS)       ← 整个调用是成功的
  recordBusinessAiMetrics(true)   ← 业务指标
  recordAiInvocation(true)        ← 审计日志

失败路径（全部重试耗尽后）：
  recordInvocation(FAILURE)       ← 整个调用是失败的
  recordBusinessAiMetrics(false)  ← 业务指标
  recordAiInvocation(false, errorCode) ← 审计日志（含错误码）
  throw BusinessException
```

注意：失败路径中不调用 `recordAttempt(FAILURE)`（已在每次 catch 中调用过），也不重复调用 `recordAttempt(SUCCESS)`。

## 六、关键关注点

### 6.1 重试终止条件

仅有一个：`attempt` 达到 `maxAttempts`。没有其他终止条件——即使连续两次失败原因完全相同也不会提前退出。

### 6.2 重试提示词的 token 消耗

重试提示词相比首次多了一段内容（严格指令 + 错误信息），这意味着重试会消耗更多的 token。但相比于写代码处理多种 JSON 异常，这是可控的成本。

### 6.3 错误日志分级

```java
if (attempt < maxAttempts) {
    log.warn("...准备重试...");   // warn 级别：预期内，会重试
} else {
    log.error("...已达最大重试次数");  // error 级别：需要关注
}
```

根据重试状态选择合适的日志级别，避免误触发告警。

## 七、设计决策理由

### 7.1 为什么重试时追加"请仅返回合法 JSON"而非修改原始提示词？

- **保持原始意图**：业务方传入的 systemPrompt 已经精确定义了输出 schema，不应该被替换
- **追加而非覆盖**：重试指令作为**补充约束**追加在末尾，LLM 阅读时能识别"原要求不变 + 新增要求"

### 7.2 为什么不使用指数退避？

结构解析失败（JSON 格式错误）不是网络问题，延迟等待无法解决问题。LLM 的输出质量不会因为等待时间增加而改善，因此不需要退避策略，直接立即重试。

### 7.3 为什么错误前缀和错误码由调用者传入？

不同的业务场景有不同的错误码和错误消息前缀（如"简历分析失败："vs"面试评估失败："），这保持了 StructuredOutputInvoker 的业务无关性。

## 八、流程总结

invoke() 方法作为唯一公开入口，首先完成三项初始化：记录调用开始时戳、规范化上下文标签（中文转英文下划线格式）并通过 TraceIdFilter 获取链路追踪 ID，然后将防注入常量追加到系统提示词末尾。进入重试循环后，首次尝试使用原始增强提示词直接调用 ChatClient，后续重试则通过 buildRetrySystemPrompt() 根据三层独立开关（是否启用修复提示词、是否追加严格 JSON 指令、是否附带清洗后的错误信息）构建渐进增强的修复提示词。每次 LLM 返回内容后立即交由 convertWithRepair() 进行 JSON 转换，捕获任何异常后记录为 lastError 并进入下一轮重试。成功路径上会依次调用 recordAttempt、recordInvocation、recordBusinessAiMetrics 和 recordAiInvocation 完成三层指标采集后返回结果对象；失败路径在所有重试耗尽后记录最终失败指标，抛出携带 errorCode 和错误前缀的 BusinessException。整个调用过程遵循"先本地修复（零成本）→ 再重试调用（有成本）→ 最终宕出异常"的降级策略，以配置驱动的方式在可靠性和成本之间取得平衡。
