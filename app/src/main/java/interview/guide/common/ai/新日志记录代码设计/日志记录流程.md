**10. 日志写库为什么不会影响主流程**

`AiProviderObservationLogService` 使用 `TransactionTemplate`，并设置：

```java
PROPAGATION_REQUIRES_NEW
```

对应代码：[AiProviderObservationLogService.java](/Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/aiobservability/service/AiProviderObservationLogService.java:54)

这样日志写库是独立事务。并且 `recordInvocation()` 和 `recordAttempt()` 内部都 catch 异常，失败时只打 warn，返回 `Optional.empty()`。

这保证：

```text
LLM 调用成功，但日志库失败 -> 不影响用户结果
LLM 调用失败，日志库也失败 -> 不覆盖原始业务异常
```

**13. 最终你可以这样总结**

现在项目的 LLM 调用流程是：

```text
业务 Service
  -> LlmProviderRegistry 获取 Default / Plain / Voice ChatClient
  -> Registry 从数据库或配置文件读取 provider 配置
  -> ApiPathResolver 创建 OpenAiApi
  -> OpenAiChatModel 绑定 OpenAiApi、Options、RetryTemplate、ObservationRegistry
  -> ChatClient 注册 SkillsTool / Advisors
  -> 业务调用 chatClient.prompt().call() 或 stream()
  -> Advisor 打开一次 invocation Scope
  -> 普通 call 走 RetryTemplate + RestClient
  -> 流式 stream 走 WebClient
  -> Interceptor / Filter 记录每次真实 HTTP attempt
  -> RetryListener 记录真实 retry
  -> Advisor 记录最终 invocation
  -> Micrometer 看趋势，数据库日志查单次问题
```

结构化输出单独说：

```text
StructuredOutputInvoker 只负责 JSON 结构化解析、修复和格式失败重试。
它不再记录 AI 调用成功率，因为 JSON 格式失败不等于 Provider 调用失败。
真正的 Provider 调用日志和指标在 ChatClient/OpenAiApi/RetryTemplate/HTTP 层记录。
```
