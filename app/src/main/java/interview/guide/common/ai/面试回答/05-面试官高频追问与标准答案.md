# 面试官高频追问与标准答案

这篇可以当作复习题库。建议先背总览，再按问题展开。

## 1. 你这个 AI 模块整体是怎么设计的？

答：

> 我把 AI 能力抽成了公共基础设施层，而不是让每个业务模块直接调用大模型 API。核心原因是项目里有多个 AI 场景：简历分析、面试出题、回答评估、JD 解析、RAG 问答、语音面试。它们都需要模型切换、结构化输出、Prompt 安全和调用观测。
>
> 所以我在 `common.ai` 下做了四类能力。第一，`LlmProviderRegistry` 统一管理多 Provider，负责创建和缓存 ChatClient、EmbeddingModel。第二，`StructuredOutputInvoker` 统一处理 JSON 输出的调用、解析、修复、重试、指标和异常。第三，`PromptSanitizer` 和 `PromptSecurityConstants` 做 Prompt 注入防护。第四，`AgentUtilsConfiguration` 和 `ApiPathResolver` 分别处理工具调用接入和 OpenAI-compatible 厂商路径适配。
>
> 这样业务层不用关心底层厂商，也不用重复写重试和安全逻辑，只要选择合适的 Client 并传入业务 Prompt。

## 2. 你为什么要自己封装 LlmProviderRegistry？

答：

> 因为项目不是只接一个固定模型。开发、测试、生产可能用不同模型，聊天和向量也可能用不同 Provider。`LlmProviderRegistry` 把 Provider 配置、客户端创建、缓存、热加载集中起来，业务模块只通过 providerId 获取客户端。这样新增 Kimi、DeepSeek、GLM 或本地 LM Studio 时，不需要改简历分析、面试出题这些业务 Service。

## 3. Provider 配置是从哪里来的？

答：

> 支持两种来源。配置文件模式下读取 `app.ai.providers.*`，适合开发测试。数据库模式下读取 `LlmProviderEntity` 和 `LlmGlobalSettingEntity`，适合管理后台动态配置；API Key 通过 `ApiKeyEncryptionService` 解密，避免明文散落。默认 Chat Provider 和默认 Embedding Provider 也是独立配置的。

## 4. 为什么 ChatClient 要缓存？

答：

> ChatClient 背后包含 OpenAiChatModel、HTTP 客户端、模型参数、Advisor、工具回调和观测组件，不适合每次请求都重复创建。Registry 用 `ConcurrentHashMap.computeIfAbsent` 做线程安全懒加载，第一次使用某个 Provider 时创建，后面复用。配置变更后调用 `reload()` 清空缓存，下一次请求重新加载。

## 5. 为什么要区分 Default、Plain、Voice 三种 ChatClient？

答：

> 因为场景不同。Default Client 适合普通对话，可以带工具调用、日志、安全防护等 Advisor。Plain Client 用于结构化输出，不注册 SkillsTool，也不加 Memory Advisor，避免工具调用或历史上下文污染 JSON。Voice Client 用于语音面试，支持 SkillsTool 和流式 ToolCall，但语音会话历史由 WebSocket/session 管理，所以不加 Memory Advisor。

## 6. 为什么结构化输出要用 Plain Client？

答：

> 结构化输出最重要的是返回纯 JSON。如果 Client 带工具调用，模型可能触发 tool call，响应就不是一个干净 JSON；如果带对话记忆，也可能把历史内容混进当前格式里。Plain Client 尽量保持调用环境纯净，只保留必要的安全防护。

## 7. 你是怎么保证 LLM 返回 JSON 能被解析的？

答：

> 我用了 `BeanOutputConverter` 生成格式指令并转换 Java DTO，同时在外层封装了 `StructuredOutputInvoker`。它会追加防注入指令，调用模型后先直接解析；解析失败时本地修复常见的未转义引号问题；仍失败就带着上一次错误和严格 JSON 指令重试；最终失败统一抛业务异常并记录指标和审计日志。

## 8. BeanOutputConverter 和 StructuredOutputInvoker 各自负责什么？

答：

> `BeanOutputConverter` 负责两件事：生成格式说明、把 JSON 字符串转 Java 对象。`StructuredOutputInvoker` 负责完整调用流程：安全提示、模型调用、解析失败修复、重试、指标、日志和异常包装。它不是替代 Converter，而是把 Converter 放进更可靠的工程流程里。

## 9. JSON 修复具体修什么？

答：

> 当前主要修复字符串内部未转义引号。比如模型返回 `{"comment":"He said "hello""}`，这是非法 JSON。代码用状态机扫描字符串，判断引号是 JSON 字符串结束符还是字符串内容的一部分，如果是内容引号就补成 `\"`。修复后仍然要经过 Converter 解析，解析通过才会返回。

## 10. 为什么不修复所有 JSON 错误？

答：

> 因为修复范围越大，误修风险越高。我只修复高频、低风险、可验证的格式问题。其他复杂错误交给重试和严格 Prompt。工程上要在“自动修复成功率”和“不要错误理解模型输出”之间平衡。

## 11. 结构化输出失败后怎么处理？

答：

> 如果所有重试都失败，`StructuredOutputInvoker` 会抛出调用方传入的 `BusinessException`，错误码由业务决定。例如简历分析失败用简历域错误码，面试评估失败用面试域错误码。这样全局异常处理器可以统一返回标准 Result。

## 12. 你怎么做 AI 调用观测？

答：

> 结构化输出里记录了三层信息。第一是 Micrometer 指标，包括调用次数、尝试次数和延迟。第二是业务指标，通过 `AiMetricsRecorder` 记录业务上下文、Provider、模型、是否成功和尝试次数。第三是 AI 调用审计日志，通过 `AiInvocationLogService` 记录 traceId、Prompt、错误码、耗时等，方便排查问题。

## 13. Prompt 注入你是怎么防的？

答：

> 我做了分层防护。输入层用 `PromptSanitizer` 清洗行首角色注入、忽略指令、伪造分隔符和伪造边界标签；Prompt 构造时用随机 `<data-boundary-uuid-label>` 包裹用户数据；提示词里加 `DATA_BOUNDARY_INSTRUCTION` 或 `ANTI_INJECTION_INSTRUCTION`，告诉模型边界内是数据不是指令；ChatClient Advisor 链里还有 `SafeGuardAdvisor` 做敏感词拦截。

## 14. Prompt 注入能完全防住吗？

答：

> 不能承诺完全防住。Prompt 注入是持续对抗问题，我这里是降低风险：输入清洗、随机边界、系统安全指令、Advisor 拦截、结构化输出约束和审计日志。后续更生产级的做法是维护红队攻击样本、做 Prompt 安全回归测试、增加输出侧业务校验和告警。

## 15. 为什么 wrapWithDelimiters 要用随机 UUID？

答：

> 固定分隔符容易被用户伪造。例如用户在简历里写 `---简历内容结束---`，模型可能误以为后面是新指令。随机 UUID 边界是运行时生成的，攻击者无法提前知道闭合标签，能降低数据区逃逸的风险。

## 16. SafeGuardAdvisor 和 PromptSanitizer 有什么区别？

答：

> `PromptSanitizer` 是业务拼 Prompt 前的输入净化；`PromptSecurityConstants` 是提示词层面的规则声明；`SafeGuardAdvisor` 是 Spring AI 调用链上的拦截器。一个处理文本，一个声明边界，一个做调用级拦截，属于不同层次的防御。

## 17. AgentUtilsConfiguration 是干什么的？

答：

> 它读取 `app.ai.agent-utils.skills-root`，默认是 `classpath:skills`，加载 skills 目录下的技能资源，构建 `SkillsTool`，注册成 `interviewSkillsToolCallback`。Registry 创建 Default 或 Voice ChatClient 时把它作为 ToolCallback 注册进去，让模型可以调用预定义的面试技能。

## 18. ToolCallback、ToolCallingManager、ToolCallAdvisor 怎么区分？

答：

> `ToolCallback` 是工具定义和描述，告诉模型有哪些工具。`ToolCallingManager` 是工具执行器。`ToolCallAdvisor` 是 Advisor 链里的拦截器，负责识别模型发起的工具调用、交给 Manager 执行，再把工具结果返回给模型。可以简单理解为：说明书、执行器、调度链路。

## 19. 为什么 Voice Client 要支持流式 ToolCall？

答：

> 语音面试追求低延迟，AI 回复要边生成边推送，并且可以按完整句子触发 TTS。如果等待完整回答生成完再播，用户体验会很差。Voice Client 支持流式响应和工具调用，同时语音会话的历史由业务层维护，所以不额外加 Memory Advisor。

## 20. ApiPathResolver 解决了什么问题？

答：

> 它解决 OpenAI-compatible 厂商 baseUrl 路径不一致的问题。Spring AI 默认会拼 `/v1/chat/completions`，但 DashScope、Kimi、GLM 等 baseUrl 可能已经带 `/v1` 或 `/v4`。如果不处理，会变成 `/v1/v1/chat/completions`，导致 404。`ApiPathResolver` 检查 baseUrl 末尾是否已有版本段，如果有，就把路径改成 `/chat/completions` 和 `/embeddings`。

## 21. 你怎么验证 ApiPathResolver 是正确的？

答：

> 有两个层次。`ApiPathResolverTest` 测纯逻辑，比如 baseUrl 是否识别 `/v1`、`/v3`、尾部斜杠和空白。`LlmProviderRegistryPathIntegrationTest` 用本地 `HttpServer` 接收真实请求，验证 Registry 通过 Spring AI 发出去的 path 不会重复 `/v1`。

## 22. 这个 AI 模块和 RAG 有什么关系？

答：

> RAG 里有两类模型调用：Embedding 和生成。Embedding 通过 `LlmProviderRegistry.getDefaultEmbeddingModel()` 提供，`LlmEmbeddingConfig` 再把它代理成 Spring AI 的 `EmbeddingModel` Bean，供 VectorStore 使用。生成阶段则通过 ChatClient 调用大模型。这样 RAG 不绑定某个固定厂商。

## 23. Embedding Provider 为什么和 Chat Provider 分开？

答：

> 因为聊天模型和向量模型的能力、价格、维度都不同。比如聊天可以用 qwen-plus，Embedding 用 text-embedding-v3。RAG 检索对向量模型稳定性很敏感，所以默认 Chat Provider 和默认 Embedding Provider 独立配置更合理。

## 24. 如果用户把聊天模型填成 embeddingModel 怎么办？

答：

> `createEmbeddingModel` 会先校验 supportsEmbedding 和 embeddingModel，再用 `looksLikeChatModel` 判断模型名是否像聊天模型，例如 qwen、glm、deepseek、kimi 等前缀。如果疑似填错，会抛业务异常并提示推荐的 Embedding 模型。

## 25. 你这个 AI 模块用了哪些设计模式？

答：

> `LlmProviderRegistry` 体现 Registry、Factory、Lazy Loading 和 Cache；`ApiPathResolver` 是适配器思路；`LlmEmbeddingConfig` 用代理模式把动态 EmbeddingModel 暴露成 Spring Bean；`StructuredOutputInvoker` 是门面/模板式封装，把重复的调用流程统一起来；Advisor 链本身类似责任链。

## 26. 你遇到过什么真实问题并解决了？

答：

> 一个典型问题是 Provider 测试连接成功，但真实业务调用 404。原因是管理后台测试连接自己拼路径，而 Spring AI 默认又拼 `/v1`，导致 DashScope 这种已带 `/compatible-mode/v1` 的 baseUrl 被拼成 `/v1/v1/chat/completions`。我后来抽出 `ApiPathResolver`，并用本地 HttpServer 写了路径回归测试。

## 27. 当前模块有什么不足？

答：

> 我会诚实说几个点。第一，Provider 不存在的部分路径还会抛 `IllegalArgumentException`，可以统一成 `BusinessException`。第二，结构化输出的观测日志目前主要按默认 Provider 记录，最好在 `invoke` 中显式传 providerId/model。第三，部分早期结构化业务还可以迁移到 Plain Client。第四，PromptSanitizer 可以补攻击样本库和更细的命中原因日志。第五，多实例部署时 `reload()` 需要配置中心或广播机制。

## 28. 如果让你继续优化这个模块，你会做什么？

答：

> 我会按优先级做五件事。第一，统一异常模型，把 Provider 配置错误都转成明确业务错误码。第二，把所有结构化输出调用迁移到 Plain Client，并在 DTO 解析后加 Bean Validation。第三，完善 AI 调用观测，显式记录实际 providerId、model、token 和成本。第四，建立 Prompt 注入红队样本和结构化输出失败样本回归测试。第五，多实例场景接配置中心或消息广播，让 Provider 热加载在集群内一致。

## 29. 怎么用一句话体现这个模块的价值？

答：

> 这个模块把大模型调用从“业务里直接调 API”升级成“可切换、可复用、可观测、可治理的 AI 基础设施”。

## 30. 面试中最推荐的收尾

可以这样收：

> 所以我认为这个模块最重要的不是用了哪个模型，而是把 AI 应用落地时的共性问题抽出来了：Provider 管理、结构化输出稳定性、Prompt 安全、工具调用、多厂商兼容和观测治理。上层业务只需要表达自己的面试场景，底层模型能力可以持续替换和演进。
