## 一、项目角色分析

### 1.1 监控体系在类中的角色

StructuredOutputInvoker 的监控体系提供了**三层可观测性**，从技术运维到业务分析到问题追溯逐层深入。它不是业务逻辑的一部分，但对生产环境的稳定运行至关重要。

### 1.2 配置管理在类中的角色

通过 `StructuredOutputProperties` 实现**配置驱动的行为控制**，使得重试策略、监控开关等行为可以在不改代码的情况下调整，支持不同环境使用不同策略。

## 二、代码调用与交互

### 2.1 三层监控在 invoke() 中的调用位置

```
invoke() 执行流程：

初始化阶段:
  startNanos = System.nanoTime()          ← 全局计时起点
  contextTag = normalizeContextTag(logContext) ← 标签规范化
  traceId = TraceIdFilter.currentTraceId()   ← 链路追踪

重试循环内（每次尝试）:
  recordAttempt(contextTag, STATUS_SUCCESS)   或 STATUS_FAILURE

成功退出:
  recordInvocation(contextTag, STATUS_SUCCESS, startNanos)
  recordBusinessAiMetrics(logContext, executedAttempts, true, startNanos)
  recordAiInvocation(traceId, logContext, ..., true, ..., null, null, ...)

失败退出（所有重试耗尽）:
  recordInvocation(contextTag, STATUS_FAILURE, startNanos)
  recordBusinessAiMetrics(logContext, executedAttempts, false, startNanos)
  recordAiInvocation(traceId, logContext, ..., false, ..., errorCode, lastError, ...)
```

### 2.2 依赖关系

```
recordAttempt() ─────────────► MeterRegistry.counter().increment()
recordInvocation() ──────────► MeterRegistry.counter() + .timer().record()
isMetricsAvailable() ────────► 检查 metricsEnabled && meterRegistry != null

recordBusinessAiMetrics() ───► AiMetricsRecorder.recordStructuredInvocation()
  ├── resolveDefaultProviderId() → LlmProviderProperties.getDefaultProvider()
  └── resolveModel(providerId)   → LlmProviderProperties.getProviders().get(id).getModel()

recordAiInvocation() ─────────► AiInvocationLogService.recordInvocation()
  ├── resolveDefaultProviderId()
  └── resolveModel(providerId)
    ↓
  AiInvocationLogCreateRequest (数据库持久化)

normalizeContextTag() ────────► NON_ALNUM_PATTERN + MULTI_UNDERSCORE
```

### 4.2 normalizeContextTag() — 六步规范化

```java
"简历评分"                                        // 原始输入
    ↓ 1. null/空白 → "unknown"
"简历评分"                                        // 非空，继续
    ↓ 2. toLowerCase + trim + 空格转下划线
"简历评分"                                        // 中文不变，已经是小写
    ↓ 3. 非字母数字字符 → 下划线
"简历评分"                                        // 中文被正则 [^a-z0-9_]+ 匹配，会变成纯下划线...
```

实际上中文会被 `NON_ALNUM_PATTERN` 全部替换为下划线，这是其局限性。在 Micrometer 标签中这会降低可读性，更适合英文上下文标签。

```
"Resume Grading"                                 // 原始输入
    ↓ 2. "resume_grading"
    ↓ 3. "resume_grading"                         // 全是字母数字
    ↓ 4. "resume_grading"                         // 无连续下划线
    ↓ 5. "resume_grading"                         // 无首尾下划线
    ↓ 6. 长度 ≤ 48 → "resume_grading"             // 无需截断
```

### 4.3 isMetricsAvailable()

```java
private boolean isMetricsAvailable() {
    return metricsEnabled && meterRegistry != null;
}
```

需要**同时满足**两个条件。配置开关可让运维在 Micrometer 不可用时通过配置关闭指标采集，而不需要重启或修改代码。

### 4.4 resolveModel() — 配置查找

```java
private String resolveModel(String providerId) {
    if (llmProviderProperties == null) return null;
    Map<String, ProviderConfig> providers = llmProviderProperties.getProviders();
    if (providers == null || providerId == null || !providers.containsKey(providerId)) {
        return null;
    }
    return providers.get(providerId).getModel();
}
```

四层 null 检查确保在任何配置缺失的情况下返回 null 而非抛出 NPE。

### 5.1 配置流向

```
application.yml
  app.ai.structured-max-attempts: 2
  app.ai.structured-include-last-error: true
  ...

      ▼

      │
      ▼

```

### 5.2 指标方法的调用时序

```
invoke() 开始
  startAt: recordAttempt(F) recordAttempt(F) recordAttempt(S) ─┐
                                                               │
  endResult: recordInvocation(S) ───────┐                     │
                                        │                     │
  endResult: recordBusinessAiMetrics(..)┐                     │
                                        │                     │
  endResult: recordAiInvocation(..) ────┘   attempt-level  ───┘
                                          invocation-level
                                          
时序说明:
  · recordAttempt 在每次尝试后立即调用（成功/失败都记录）
  · recordInvocation 只在最终结果确定后调用一次
  · recordBusinessAiMetrics 和 recordAiInvocation 同理，只在最终调用
```

## 六、关键关注点

### 6.1 构造函数中的边界保护

```java
this.maxAttempts          = Math.max(1, ...);   // 防止配置为 0 导致一次都不执行
this.errorMessageMaxLength = Math.max(20, ...);  // 防止太短导致错误信息无意义
```

这是防御性编程的体现——即使运维配置错误，代码也不会退化到无法工作的状态。

### 6.2 可选依赖的 null safety

三个外部服务全部 `@Autowired(required = false)`：

```java
// 每个方法入口：
if (aiInvocationLogService == null) return;     // 静默跳过
if (aiMetricsRecorder == null) return;
if (!isMetricsAvailable()) return;              // 双条件判断
```

这样设计使得本类可以在非 Spring 环境或部分依赖缺失时仍然正常工作，不需要 Mock 或条件装配。

### 6.3 audit 日志的 fail-silent 策略

```java
try {
    aiInvocationLogService.recordInvocation(...);
} catch (Exception e) {
    log.warn("AI 调用观测日志写入失败: traceId={}", traceId, e);
    // 不抛异常，不中断主流程
}
```

审计日志是"尽力而为"的附加功能，其失败不应影响业务主流程。

## 七、设计决策理由

### 7.1 为什么分为三层监控而非合并？

- **关注点分离**：运维关注延迟/QPS，业务关注模型效果，开发关注 Prompt 质量
- **独立故障域**：Micrometer 挂了不影响审计日志写入，反之亦然
- **独立开关**：可以根据需要选择性开启/关闭某一层

### 7.2 为什么用 @Autowired(required = false) 而非 @ConditionalOnBean？

- **更简单**：不需要 Spring Boot 的条件注解，减少配置复杂性
- **更灵活**：即使 Bean 存在，也可以通过配置开关决定是否使用
- **更安全**：`required = false` 不会在 Bean 缺失时导致启动失败

### 7.3 为什么标签规范化需要限制 48 字符？

Micrometer 标签会作为 Prometheus label 存储，过长的标签值会显著增加时间序列数据库的存储开销。48 字符是在可读性和存储成本间的折中。

## 八、流程总结

StructuredOutputInvoker 的配置由 StructuredOutputProperties 通过 @ConfigurationProperties 从 YAML 自动绑定，构造函数一次性读取所有配置并进行边界保护（maxAttempts 下限 1、errorMessageMaxLength 下限 20），所有字段设为 final 实现不可变线程安全。三类可选依赖（MeterRegistry、AiMetricsRecorder、AiInvocationLogService）均以 @Autowired(required = false) 注入，每个使用这些依赖的方法入口都有 null 检查确保静默降级。监控体系分为三层：第一层 recordAttempt/recordInvocation 通过 Micrometer 上报调用次数、尝试次数和延迟指标到 Prometheus/Grafana 用于运维监控，其中 attempt 统计每次 LLM 调用、invocation 只统计最终结果；第二层 recordBusinessAiMetrics 委托 AiMetricsRecorder 记录带 Provider 和 Model 维度的业务级指标，用于不同厂商模型的成功率对比和成本分析；第三层 recordAiInvocation 委托 AiInvocationLogService 将完整调用上下文（含 traceId、systemPrompt、userPrompt、错误码、耗时）持久化到数据库用于事后审计和 Prompt 优化，写入失败仅打 warn 日志采用 fail-silent 策略不中断主流程。normalizeContextTag() 通过六步规范化（null→"unknown"、转小写、空格转下划线、非字母数字清理、连续下划线合并、长度截断）将业务上下文转为指标友好的标签格式，resolveDefaultProviderId 和 resolveModel 从 LlmProviderProperties 中安全解析配置供监控方法使用。整个配置和监控体系以"防御性设计 + 可选依赖 + 独立故障域"为原则，确保在任何配置缺失或依赖不可用时系统仍能正常运行。
