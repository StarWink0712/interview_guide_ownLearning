### 二、为什么需要异常？

#### 核心问题：正常流程被意外打断，如何优雅地告诉前端？

举个例子：

```
用户请求下载一个不存在的简历
    ↓
Controller → ResumeService.findById()
    ↓
数据库里没有这条记录！

此时有两个选择：
  ❌ 方案 A：返回 null，Controller 自己判断 null → 写一堆 if 判断
  ❌ 方案 B：返回特殊值如 -1，但 -1 是正常数据还是异常？
  ✅ 方案 C：直接抛异常！throw new BusinessException(RESUME_NOT_FOUND, "简历不存在")
```

**异常的本质是"阻断正常流程 + 携带错误信息 + 跳到统一的错误处理处"**。这是核心，本质就是阻挡正常的流程

#### 对比：有异常 vs 没有异常

**没有异常（方案 A）**：错误处理散落各处，代码混乱：

```java
// Service 层
public ResumeEntity findById(Long id) {
    return resumeRepo.findById(id).orElse(null);  // 返回 null
}

// Controller 层：每个接口都要手写判断
@GetMapping("/{id}")
public Result<ResumeResponse> getResume(@PathVariable Long id) {
    ResumeEntity entity = resumeService.findById(id);
    if (entity == null) {
        return Result.error(2001, "简历不存在");  // 到处重复这段代码
    }
    return Result.success(convert(entity));
}
```

**有异常（方案 C）**：错误处理集中在 `GlobalExceptionHandler`：

```java
// Service 层：出问题直接抛
public ResumeEntity findById(Long id) {
    return resumeRepo.findById(id)
        .orElseThrow(() -> new BusinessException(ErrorCode.RESUME_NOT_FOUND, "简历不存在"));
}

// Controller 层：只管正常逻辑，异常完全不用管
@GetMapping("/{id}")
public Result<ResumeResponse> getResume(@PathVariable Long id) {
    ResumeEntity entity = resumeService.findById(id);
    return Result.success(convert(entity));
}

// GlobalExceptionHandler 自动拦截所有 BusinessException
// 统一转成 Result.error(code, message) 返回给前端
```

### 三、这套体系的运转流程

```
Service 层出错
    ↓ throw new BusinessException(ErrorCode.RESUME_NOT_FOUND, "简历xxx不存在")
    ↓
GlobalExceptionHandler.handleBusinessException() 捕获
    ↓ 提取 e.getCode()=2001, e.getMessage()="简历xxx不存在"
    ↓
return Result.error(2001, "简历xxx不存在")
    ↓ HTTP 200
    ↓ 前端收到：
{
    "code": 2001,
    "message": "简历xxx不存在",
    "data": null
}
```

前端只需要看 `code` 是不是 0（0=成功，非0=失败），然后根据 `message` 弹提示即可。

### 四、GlobalExceptionHandler 处理的异常类型一览

| 异常类型                              | 处理的错误码             | 场景                        |
| --------------------------------- | ------------------ | ------------------------- |
| `BusinessException`               | 业务自身错误码            | 简历不存在、面试已过期等业务错误          |
| `MethodArgumentNotValidException` | 400 (BAD\_REQUEST) | `@Valid` 校验失败             |
| `MaxUploadSizeExceededException`  | 400                | 文件太大                      |
| `IllegalArgumentException`        | 400                | 非法参数                      |
| `ResourceAccessException`         | 7001/7002          | AI 服务网络断开/超时              |
| `RestClientException`             | 7004/7005          | AI 服务 401 密钥无效 / 429 调用超限 |
| `NoResourceFoundException`        | 404                | 访问了不存在的 API 路径            |
| `Exception`（兜底）                   | 500                | 未知错误                      |

**关键设计选择**：所有异常都返回 **HTTP 200**，用 `code` 字段区分成功/失败。这样的好处是前端只需解析 JSON 的 `code` 字段，不需要同时处理 HTTP 状态码和业务错误码两套体系。

### 五、ErrorCode 分域设计

| 域        | 范围    | 示例                                    |
| -------- | ----- | ------------------------------------- |
| 通用       | 1xxx  | BAD\_REQUEST(400)、NOT\_FOUND(404)     |

| AI 服务    | 7xxx  | AI\_SERVICE\_TIMEOUT(7002)            |

看错误码的前缀就能立刻知道是哪个模块出的问题，方便排查。

### 六、总结

**为什么需要异常？** 因为正常流程总会遇到意外情况——数据库查不到、文件上传失败、AI 调用超时等等。如果不做异常处理：

1. **代码混乱**：每个 Controller 方法都要写大量 if/else 判断
2. **前端体验差**：报错格式不统一，前端要兼容各种返回格式
3. **问题难排查**：没有错误码体系，日志里全是堆栈找不到具体原因

这套体系统一了"拦截 → 分类 → 包装 → 返回"的全流程，让开发者只需在 Service 层 `throw`，别的什么都不用管。
