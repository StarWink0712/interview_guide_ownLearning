# 异步任务与语音指标怎么讲

## 1. 为什么把异步和语音放一起讲

异步任务和语音面试看起来是两个不同业务，但在可观测性上有共同点：

- 都不是简单的一次 HTTP 请求。
- 都涉及长链路和后台处理。
- 都容易出现“用户只感觉失败或卡顿，但后端要拆阶段定位”的问题。

异步任务关注：

- 任务有没有创建？
- 消费者有没有处理？
- 有没有重试？
- 最终失败是否升高？

语音面试关注：

- ASR 是否及时出最终文本？
- LLM 首 token 是否慢？
- LLM 回复总耗时是否高？
- TTS 是否慢或返回空音频？
- 一轮对话总耗时是否影响用户体验？

## 2. AsyncTaskMetricsRecorder 怎么讲

`AsyncTaskMetricsRecorder` 是 Redis Stream 异步任务的生命周期指标记录器。

它记录五类事件：

| 方法 | 指标 | 含义 |
|---|---|---|
| `recordCreated(...)` | `app.async.task.created` | 任务写入 Stream 成功 |
| `recordProcessing(...)` | `app.async.task.processing` | Consumer 开始处理 |
| `recordCompleted(...)` | `app.async.task.completed` | 任务成功完成 |
| `recordFailed(...)` | `app.async.task.failed` | 任务最终失败 |
| `recordRetry(...)` | `app.async.task.retry` | 任务进入重试 |

标签：

- `task_type`
- `stream`

面试一句话：

> 我给 Redis Stream 异步任务加了生命周期指标，从生产、处理中、完成、重试到最终失败都能统计。这样可以按任务类型和 Stream 管道看吞吐、失败率和重试情况。

## 3. 它在 Producer 里怎么用

`AbstractStreamProducer` 发送任务时：

```text
buildMessage(payload)
  -> buildMessageWithTrace(payload)
  -> redisService.streamAdd(...)
  -> 成功: recordCreated()
  -> 失败: recordFailed()
```

关键点：

- 成功写入 Redis Stream 才算 created。
- 写入失败会记录 failed，并执行 `onSendFailed(...)`。
- 入队时会把当前请求 traceId 写进消息。

面试回答：

> 对异步任务来说，任务创建不是调用了 send 方法就算成功，而是 Redis Stream 确认写入成功才算 created。所以 Producer 在 streamAdd 成功后记录 created，失败时记录 failed，并由子类回调处理业务状态。

## 4. 它在 Consumer 里怎么用

`AbstractStreamConsumer` 消费消息时：

```text
收到消息
  -> 恢复 traceId 到 MDC
  -> parsePayload
  -> markProcessing
  -> recordProcessing
  -> processBusiness
  -> markCompleted
  -> recordCompleted
  -> ack

异常:
  -> retryCount < maxRetries
     -> recordRetry
     -> retryMessage
     -> ack 当前消息

  -> retryCount >= maxRetries
     -> recordFailed
     -> markFailed
     -> ack 当前消息
```

这个流程可以回答两个问题：

### 4.1 为什么失败后还 ACK 当前消息

因为重试是通过重新投递一条带更高 `retryCount` 的消息实现的。

如果不 ACK 当前消息，旧消息还留在 pending 中，可能造成重复消费或堆积。

### 4.2 为什么要先 recordRetry 再重新入队

因为 retry 是一次明确的生命周期事件。

如果只记录最终 failed，无法知道任务失败前是否经历了大量重试。

## 5. 异步任务指标能定位什么问题

### 5.1 created 上升，processing 不上升

说明任务不断入队，但消费者没处理。

可能原因：

- Consumer 没启动。
- 消费者组异常。
- Redis Stream 消费阻塞。
- 线程池问题。

### 5.2 processing 上升，completed 不上升，retry 上升

说明消费者在处理，但业务逻辑不断失败。

可能原因：

- LLM 调用失败。
- 文件解析失败。
- 向量化失败。
- 数据库更新异常。
- 关联实体不存在或状态不一致。

### 5.3 failed 上升

说明超过最大重试次数后最终失败。

需要查：

- 任务类型 `task_type`。
- Stream 名称 `stream`。
- traceId 关联日志。
- 对应业务实体状态。

## 6. 当前异步指标的边界

当前 `AsyncTaskMetricsRecorder` 主要使用 Counter。

它能告诉你：

- 创建了多少任务。
- 处理了多少任务。
- 完成了多少任务。
- 重试了多少任务。
- 失败了多少任务。

但它不能直接告诉你：

- 当前 Stream 里积压多少条。
- Pending List 有多少未 ACK 消息。
- 某个 Consumer 落后多少。
- 当前正在处理的任务数。

这些更适合用 Gauge。

面试可以这样讲：

> 当前实现覆盖了生命周期事件计数，但如果要做更完整的生产监控，我会继续补 Redis Stream backlog、pending 数量、consumer lag 这些 Gauge，用来判断队列是否堆积。

## 7. VoiceMetricsRecorder 怎么讲

`VoiceMetricsRecorder` 是一个通用语音指标工具类。

它不固定具体指标名，而是提供三个方法：

| 方法 | 用途 |
|---|---|
| `recordTimerSinceNanos(...)` | 从 `System.nanoTime()` 起点计算耗时 |
| `recordTimerMillis(...)` | 直接记录毫秒耗时 |
| `incrementCounter(...)` | 递增事件计数 |

这种设计更灵活，因为语音链路指标点很多：

- ASR。
- 片段合并。
- LLM 首 token。
- LLM 总耗时。
- TTS。
- 整轮对话。
- 错误计数。

面试回答：

> 语音面试链路指标点变化比较多，所以我没有为每个指标都写一个固定方法，而是封装了通用的 Timer 和 Counter 方法，调用方传入指标名和标签。这样 WebSocket 处理器可以在 ASR、LLM、TTS、turn 这些不同阶段灵活埋点。

## 8. 语音面试指标链路

`VoiceInterviewWebSocketHandler` 里已经接入了多个指标。

### 8.1 ASR 阶段

指标：

- `app.voice.interview.asr.final_segments`
- `app.voice.interview.asr.merge_wait`

关注问题：

- 用户说话后，ASR 最终片段是否能及时收到。
- 多个 ASR 片段合并是否等待太久。

### 8.2 LLM 阶段

指标：

- `app.voice.interview.llm.first_token_latency`
- `app.voice.interview.llm.duration`
- `app.voice.interview.llm.calls`

关注问题：

- 首 token 慢不慢。
- 总生成耗时高不高。
- 流式和非流式模式差异。

首 token 很重要，因为它直接影响用户感知：

> 用户不一定等到整段话生成完才感受到速度，第一段回复什么时候出现才是实时体验的关键。

### 8.3 TTS 阶段

指标：

- `app.voice.interview.tts.duration`
- `app.voice.interview.tts.empty_audio`

关注问题：

- 合成音频是否慢。
- TTS 是否返回空音频。
- 分块推送和合并推送模式下耗时是否不同。

### 8.4 整轮对话

指标：

- `app.voice.interview.turn.duration`
- `app.voice.interview.turn.completed`
- `app.voice.interview.errors`

关注问题：

- 用户说完一句到 AI 完整响应完成，一轮总耗时是多少。
- 成功和失败比例如何。
- turn 级别错误是否上升。

## 9. BusinessMetricsQueryService 的闭环

`BusinessMetricsQueryService` 会从 `MeterRegistry` 中读取：

```text
app.voice.interview.turn.duration
```

并计算语音面试平均轮次延迟。

这说明语音指标不只是写进去，还会被业务监控页面读取。

面试表达：

> 语音面试的轮次耗时不是写到数据库再统计，而是直接从 Micrometer 的 Timer 中读均值，适合做实时监控概览。没有 MeterRegistry 或没有数据时返回 0，保持降级能力。

## 10. 语音链路如何定位卡顿

用户反馈：“语音面试卡。”

可以按指标拆：

1. `asr.merge_wait` 高：ASR 片段合并等待慢。
2. `llm.first_token_latency` 高：模型首 token 慢，用户等待开口时间长。
3. `llm.duration` 高：模型生成完整回复慢。
4. `tts.duration` 高：语音合成慢。
5. `tts.empty_audio` 增加：TTS 服务异常或返回空。
6. `turn.duration` 高：整体体验慢，需要继续拆阶段。

面试回答：

> 语音链路不能只看接口耗时，因为它是 ASR、LLM、TTS 串起来的实时体验。我把它拆成多个阶段记录指标，用户说卡顿时，可以先看 turn duration，再下钻到 ASR、LLM 首 token、LLM 总耗时、TTS 耗时。

## 11. VoiceMetricsRecorder 的风险点

### 11.1 标签参数没有强校验

`VoiceMetricsRecorder` 接收 `String... tags`。

调用方需要保证是偶数个参数：

```text
"status", "success", "streaming", "true"
```

如果传成奇数个，Micrometer 可能产生警告或默认处理。

下一步可以封装更强类型的方法，或者在 Recorder 内部校验：

```text
if (tags.length % 2 != 0) {
  log.warn(...)
  return;
}
```

### 11.2 需要避免高基数标签

语音链路千万不要把这些放进 metrics 标签：

- sessionId
- userId
- traceId
- 原始语音文本

否则时间序列会爆炸。

当前代码主要用：

- status
- streaming
- stage

这是比较安全的。

### 11.3 部分失败细节还可以更细

当前 turn 失败会记录：

- `turn.duration` with failure
- `turn.completed` with failure
- `errors` with stage=turn

但如果要更细，还可以按阶段记录：

- ASR failure。
- LLM failure。
- TTS failure。
- WebSocket send failure。

## 12. 异步和语音一起的面试总结

> 异步任务和语音面试都是长链路，不能只看接口是否成功。异步任务这边，我用 `AsyncTaskMetricsRecorder` 记录 Redis Stream 任务从 created、processing、completed、retry 到 failed 的生命周期，并用 task_type 和 stream 做标签，能看到哪个管道重试或失败多。语音面试这边，我用 `VoiceMetricsRecorder` 记录 ASR、LLM、TTS 和整轮 turn 的 Timer/Counter，尤其记录了 LLM 首 token 延迟和整轮耗时，因为这直接影响实时体验。它们共同的设计原则是：业务代码只表达“某阶段完成或失败”，指标记录统一交给 Recorder，并且所有监控都可选降级，不影响主业务。
