# observability 面试官高频问题与参考答案

## 1. 你为什么要做 observability 模块？

回答：

> 因为这个项目不是普通 CRUD，它的核心链路依赖 LLM、RAG、Redis Stream、WebSocket、ASR/TTS 等不稳定或长链路组件。用户反馈通常只会说“AI 慢”“问答不准”“语音卡”，但后端需要把问题拆成可定位的阶段。所以我做了 observability 模块，用 traceId 串日志，用 Micrometer 指标看延迟、失败率、重试率和空召回率，再用持久化调用日志按 traceId 复盘单次请求。

## 2. 这个模块主要有哪些类？

回答：

> 主要有五个类。`TraceIdFilter` 负责请求级 traceId 生成、透传和 MDC 注入；`AiMetricsRecorder` 记录 AI 结构化输出的调用次数、延迟、重试和失败；`RagMetricsRecorder` 按 query rewrite、retrieval、answer 三段记录 RAG 指标；`AsyncTaskMetricsRecorder` 记录 Redis Stream 任务的 created、processing、completed、failed、retry；`VoiceMetricsRecorder` 提供语音面试通用 Timer 和 Counter 方法，用于 ASR、LLM、TTS 和整轮对话耗时。

## 3. TraceIdFilter 的完整流程是什么？

回答：

> 请求进入时先看 header 里有没有 `X-Trace-Id`，有就复用，没有就生成 UUID。然后把 traceId 放进 SLF4J MDC，响应头也写回同一个 `X-Trace-Id`。请求继续执行时所有日志都可以通过 logback 的 `%X{traceId}` 自动输出。最后在 finally 里 remove MDC，防止线程池复用导致 traceId 污染下一次请求。

## 4. 为什么要用 MDC？

回答：

> MDC 和日志框架天然集成，写入一次后，当前线程后续所有日志都能自动带 traceId。相比每个方法都手动传 traceId，MDC 对业务代码侵入小，也不容易漏。需要注意的是 MDC 是线程本地上下文，所以请求结束必须清理，异步线程也要显式传递和恢复。

## 5. 异步任务怎么传递 traceId？

回答：

> 异步任务会跨线程，MDC 不会自动传递。项目里 Producer 入队时从 `TraceIdFilter.currentTraceId()` 取当前请求 traceId，放进 Redis Stream 消息字段。Consumer 消费时从消息里取出 traceId，写回自己的 MDC，处理完 finally 恢复旧值。这样从 HTTP 请求到后台消费的日志可以用同一个 traceId 串起来。

## 6. 你的 traceId 是完整分布式链路追踪吗？

回答：

> 不是完整 OpenTelemetry 意义上的分布式 Trace。当前实现是轻量级日志链路追踪，只有 traceId，没有 spanId、parentSpanId、采样和瀑布图。它适合当前单体服务加异步任务的排查场景。如果未来拆成多个微服务，我会接 OpenTelemetry，把 span 层级和跨服务拓扑补上。

## 7. 为什么用 Micrometer，而不是直接写 Prometheus？

回答：

> Micrometer 相当于指标领域的 SLF4J。业务代码面向 Micrometer 的 `MeterRegistry`，底层可以接 Prometheus、Datadog 或其他系统。这样代码不和某一个监控后端绑定，后续迁移监控系统时改依赖和配置即可，不需要改业务埋点代码。

## 8. Counter、Timer、Summary 怎么选？

回答：

> Counter 用来记录事件发生次数，比如调用次数、失败次数、重试次数；Timer 用来记录耗时分布，比如 AI 调用延迟、RAG 检索耗时、语音 TTS 耗时；Summary 用来记录每次请求的数值分布，比如 RAG 每次检索命中了多少个文档块。不能用 Counter 表示当前队列长度，这种当前值更适合 Gauge。

## 9. AI 指标里为什么要区分 attempt 和 invocation？

回答：

> attempt 表示每一次实际模型调用，包括重试；invocation 表示一次业务调用的最终结果。比如第一次结构化解析失败、第二次成功，那么 attempt 有一次 failure 和一次 success，但 invocation 只有一次 success。这样可以同时观察用户视角成功率和模型输出稳定性。如果最终成功率高但 attempt failure 高，说明系统靠重试兜住了，但延迟和成本会增加。

## 10. AiMetricsRecorder 的标签为什么是 scenario、provider、model、status？

回答：

> 这四个标签能定位 AI 问题的主要维度。scenario 用来看哪个业务场景慢或失败，比如简历评分、面试评估；provider 用来看哪个 LLM 厂商不稳定；model 用来看具体模型版本表现；status 用来区分成功和失败。这样线上问题不是猜，而是可以在指标上直接看到是某个 Provider 慢，还是某个场景慢。

## 11. 为什么不把 traceId、sessionId 放进 Metrics 标签？

回答：

> 因为 traceId、sessionId 是高基数字段，每个值都可能生成新的时间序列，会让监控系统压力暴涨。Metrics 适合放低基数标签，比如 status、provider、model、topK。traceId 和 sessionId 更适合放日志或数据库明细里，用来查单次请求。

## 12. RAG 为什么要拆成 rewrite、retrieval、answer 三段指标？

回答：

> 因为 RAG 慢或答不上来可能发生在不同阶段。Query rewrite 慢通常是 LLM 调用问题；retrieval 空结果通常是召回、topK、minScore、向量化或 query 改写问题；answer 慢通常是上下文过长或模型响应问题。拆成三段后，用户说“知识库慢”时可以快速定位是哪一段慢。

## 13. 为什么要单独记录 RAG no result？

回答：

> 因为 HTTP 成功不代表 RAG 业务成功。接口可能正常返回“没有找到相关内容”，从技术上是 200，但对用户来说就是没答上来。所以我单独记录 `app.rag.no_result.count`，用于观察零命中率。零命中率突然升高，通常说明检索召回或知识库向量化出了问题。

## 14. RAG 的 hit count 为什么用 Summary？

回答：

> hit count 是每次请求命中的文档块数量，它不是一个单纯事件次数，而是一个数值分布。用 Summary 可以看平均值、最大值、分位数等统计；再配合 no result Counter，就能同时看到命中分布和零命中事件。

## 15. AI/RAG 指标和数据库观测日志有什么区别？

回答：

> 指标用于趋势和告警，比如最近 5 分钟失败率、P99 延迟、零命中率。数据库观测日志用于复盘单次请求，比如某个 traceId 的 prompt、provider、model、error、检索到的文档块。Metrics 里不能放 prompt、traceId 这种高基数或大字段，明细日志可以承载这些内容。

## 16. AsyncTaskMetricsRecorder 能发现什么问题？

回答：

> 它能看异步任务生命周期。如果 created 上升但 processing 不上升，说明任务入队了但消费者没处理，可能是 Consumer 没启动或消费组异常。如果 processing 上升但 completed 不上升、retry 上升，说明业务处理持续失败。如果 failed 上升，说明任务超过最大重试次数后最终失败，需要按 task_type、stream 和 traceId 查具体原因。

## 17. 当前异步任务指标还缺什么？

回答：

> 当前主要是生命周期 Counter，能看创建、处理、完成、重试和失败。但还缺 Gauge，比如 Redis Stream 当前长度、pending 数量、consumer lag、当前处理中任务数。这些指标更适合判断队列是否积压，是后续生产化监控要补的。

## 18. 语音面试为什么要记录 first token latency？

回答：

> 语音场景里用户感知的不是总耗时一个指标。LLM 首 token 决定 AI 多久开始回应，直接影响“有没有卡住”的感觉。总耗时可能还可以，但首 token 很慢，用户仍然会觉得系统迟钝。所以我在流式 LLM 回复时记录了 `app.voice.interview.llm.first_token_latency`。

## 19. 用户说语音面试很卡，你怎么排查？

回答：

> 我会先看 `app.voice.interview.turn.duration` 判断整体一轮是否变慢。然后拆阶段看：`asr.merge_wait` 是否高，`llm.first_token_latency` 是否高，`llm.duration` 是否高，`tts.duration` 是否高。如果 `tts.empty_audio` 上升，说明 TTS 服务可能异常。这样能把“卡”拆成 ASR、LLM、TTS 或 WebSocket 处理问题。

## 20. 为什么 Recorder 都允许 MeterRegistry 为空？

回答：

> 监控是增强能力，不能成为业务启动和运行的强依赖。测试环境或某些本地环境可能没有 MeterRegistry，所以构造函数用 `@Autowired(required = false)`，记录方法里为空就直接 return。这样监控不可用时业务照常运行，避免监控故障影响核心流程。

## 21. 这个设计有什么亮点？

回答：

> 我觉得亮点有三个。第一是按业务链路拆指标，不是只做接口总耗时，AI、RAG、异步、语音都有自己的阶段指标。第二是 Metrics 和明细日志分层，聚合问题用 Micrometer，单次复盘用 traceId 和数据库日志。第三是异步 traceId 传递，Producer 把 traceId 写入 Redis Stream，Consumer 恢复到 MDC，避免请求和后台任务日志断链。

## 22. 当前实现有什么不足？

回答：

> 第一，当前是轻量 traceId，不是完整 OpenTelemetry。第二，代码层面已经做了 Micrometer 埋点，但当前依赖里没有显式看到 Actuator 和 Prometheus registry，所以 Prometheus/Grafana 属于可对接基础，还需要补生产配置。第三，RAG 指标主要观测运行质量和召回情况，不直接评估答案语义正确性。第四，异步任务还缺 backlog、pending、consumer lag 这些 Gauge。

## 23. 如果让你继续完善，你会做什么？

回答：

> 我会分四步。第一，补 Actuator、Prometheus registry 和 `/actuator/prometheus` 暴露配置。第二，做 Grafana Dashboard，分别看 AI、RAG、异步任务、语音链路。第三，补告警规则，比如 AI 失败率、RAG 零命中率、异步失败数、语音 P95 延迟。第四，接入 OpenTelemetry 或至少补 spanId，让跨服务和多阶段耗时更清晰。

## 24. 30 秒压缩版

回答：

> `common/observability` 是项目的可观测性基础设施。请求入口用 `TraceIdFilter` 生成或透传 `X-Trace-Id`，写入 MDC，日志通过 logback 自动带 traceId；异步任务入队时把 traceId 写到 Redis Stream，消费时恢复。指标上我用 Micrometer 封装了 AI、RAG、异步任务、语音四类 Recorder。AI 看 provider/model/scenario 的延迟、失败和重试；RAG 按 rewrite、retrieval、answer 三段看耗时、命中数和空结果；异步任务看 created、processing、completed、retry、failed；语音看 ASR、LLM 首 token、LLM 总耗时、TTS 和整轮 turn 耗时。当前是轻量 traceId 加 Micrometer 埋点，生产接 Prometheus/Grafana 还需要补 Actuator 和 registry 配置。
