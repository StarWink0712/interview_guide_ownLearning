这个项目在消息可靠性方面做了**多层防护**，基本覆盖了消息丢失的主要场景。让我逐一说明：

---

## 消息可能丢失的三个环节

```
  Producer                Redis              Consumer
  ────────              ───────             ────────
  ①发送时丢失          ②Redis宕机丢失        ③处理时丢失
```

---

## ① Producer 发送时丢失 → 事务后提交 + 发送失败回调

**问题**：Producer 消息发出去了，但 Consumer 还没来得及处理，Producer 那边的事务还没提交。

**项目方案**：[TransactionAfterCommitExecutor](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/transaction/TransactionAfterCommitExecutor.java)

```java
// 不是先发消息再存数据库，也不是先存数据库再发消息
// 而是：数据库事务提交之后，再发消息
afterCommitExecutor.execute(() -> {
    String messageId = sendTask(payload);
    if (messageId != null) {
        asyncTaskService.markEnqueued(result.task().id(), messageId);
    }
});
```

如果发送失败（Redis 连不上），`sendTask` 返回 `null`，走到 `onSendFailed`：

```java
// AnalyzeStreamProducer 里
protected void onSendFailed(AnalyzeTaskPayload payload, String error) {
    updateAnalyzeStatus(payload.resumeId(), FAILED, error);
    asyncTaskService.markFailed(payload.taskId(), error);
    // → 简历表标记 FAILED，异步任务标记 FAILED，等人工重试
}
```

## ② Redis 宕机 → 消息可能丢失

**这个项目没有做彻底防护。**

Redis 持久化依赖于 Redis 自身的 RDB/AOF 配置。如果 Redis 突然宕机且没开 AOF，Stream 里未消费的消息会丢失。

但这个项目的设计假设是单机 Redis（`redissonClient` 单连接），且 `AsyncTaskStreamConstants` 里没有做 Redis 集群或哨兵配置的痕迹。

**面试话术**：可以承认当前项目这个点是薄弱环节，然后说生产环境中应该配置 Redis AOF `appendfsync everysec` + Redis Sentinel 主从复制。

---

## ③ Consumer 处理时丢失 → 这个项目做了最充分的工作

这是最重要的防护层，项目通过 **三重机制** 解决：

### 3.1 ACK 确认机制

消息被拉取后**不会立刻删除**，而是进入 PEL（Pending Entries List）。只有 Consumer 显式调用 XACK 后，消息才真正被移出 PEL。

```
XREADGROUP 拉取消息  →  消息进入 PEL  →  processMessage() 处理
                                             │
                                        成功 → XACK → 从 PEL 移除 ✅
                                        失败 → 不 ACK → 消息留在 PEL
```

### 3.2 失败自动重试（最多 3 次）

```java
// AbstractStreamConsumer.processMessage() 中
catch (Exception e) {
    if (retryCount < MAX_RETRY_COUNT) {          // < 3
        retryMessage(payload, retryCount + 1);   // XADD 新消息（retryCount+1）
        // 新消息重新进入 Stream，等待再次被消费
    } else {
        markFailed(payload, error);              // >= 3，标记最终失败
    }
    ackMessage(messageId);                       // 不管重试还是失败，都 ACK 原消息
}
```

新消息和原消息的 retryCount 不同：

```
原消息：{taskId:789, resumeId:456, retryCount:0}  → 处理失败
         ↓
新消息：{taskId:789, resumeId:456, retryCount:1}  → 重新入队
         ↓ 又失败
新消息：{taskId:789, resumeId:456, retryCount:2}  → 重新入队
         ↓ 又失败  
新消息：{taskId:789, resumeId:456, retryCount:3}  → 最后一次消费
         ↓ 仍然失败 → retryCount(3) >= 3 → markFailed → 不再重试
```

### 3.3 Pending 消息定时恢复（兜底）

如果 Consumer 处理到一半 JVM 崩溃了（OOM / kill -9），消息已经 XREADGROUP 但没来得及 ACK。这些消息残留在 PEL 中，由 [PendingMessageRecoveryService](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/asynctask/service/PendingMessageRecoveryService.java) 负责恢复：

```java
// 两个触发时机：
@EventListener(ApplicationReadyEvent.class)   // ① 应用启动后立即恢复
public void recoverOnStartup() { ... }

@Scheduled(fixedDelay = 60_000)              // ② 每 60 秒自动恢复
public void recoverPendingMessages() {
    for (AbstractStreamConsumer<?> consumer : consumers) {
        consumer.recoverPendingMessages(
            60000,  // 只认领空闲超过 60 秒的消息
            10      // 每次最多 10 条
        );
    }
}
```

底层 Redis 命令：

```
XAUTOCLAIM resume:analyze:stream analyze-group 
    analyze-consumer-a3f2b01c 60000 COUNT 10
```

认领回来的消息重新调用 `processMessage()` 走完整处理流程。

## 四、消息丢失防护总结

| 丢失环节 | 项目方案 | 是否兜底 |
|----------|---------|---------|
| Producer 发送失败 | 事务后提交 + onSendFailed 标记状态 | ✅ |
| Redis 宕机 | 依赖 Redis 自身持久化（当前未做强防护） | ⚠️ |
| Consumer 处理失败（retry < 3） | 自动重新入队重试 | ✅ |
| Consumer 处理失败（retry >= 3） | 标记 FAILED，人工介入 | ✅ |
| Consumer JVM 崩溃 | PEL 定时恢复（XAUTOCLAIM） | ✅ |
| ACK 自身失败 | 消息留 PEL，下次定时恢复重新 ACK | ✅ |

## 五、面试话术

可以这样总结：

> 「消息丢失防护我们做了三层。
>
> **第一层在生产者端**，用事务后提交保证数据库写入和消息发送的一致性，发送失败会立即标记任务 FAILED。
>
> **第二层在消费者端**，利用 Redis Stream 的 PEL 机制和 XACK 确认，确保消息处理成功才真正从 Stream 中移除。处理失败会自动重新入队重试，最多 3 次，超过后标记 FAILED 等待人工介入。
>
> **第三层是兜底恢复**。应用启动时和每 60 秒定时扫描 PEL 中的空闲消息，通过 XAUTOCLAIM 把它们重新拉回来处理，防止消费者崩溃导致消息残留。
>
> 目前还需要补强的一环是 Redis 自身的持久化配置，生产环境应该开启 AOF 和 Sentinel 主从复制。」
