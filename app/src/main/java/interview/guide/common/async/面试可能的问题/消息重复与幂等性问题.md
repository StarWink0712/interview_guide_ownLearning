# 消息重复消费与幂等性 — 完整面试回答（带代码）

***

## 一、定调

> 「消息重复消费是分布式消息系统里绕不开的问题。我们的策略是"不假设消息不重复，而是让重复消费变得安全"。具体来说，在 Producer 端做写前去重，在 Consumer 端做两道幂等校验，形成三层防护。」

***

## 二、什么情况会重复消费？

先讲清楚重复从哪来，面试官会觉得你考虑周全：

| 重复来源              | 具体场景                                           |
| ----------------- | ---------------------------------------------- |
| **Producer 重发**   | 网络超时，Producer 以为没发成功，实际 Redis 已写入              |
| **Consumer 重试**   | AI 调用失败了，retryMessage 重新 XADD 一条消息             |
| **XAUTOCLAIM 恢复** | 消费者崩溃恢复，PendingMessageRecoveryService 认领回来自动重试 |
| **手动重试**          | 运维后台点"重试"按钮，调用 `retryTask()`                   |

## 三、第一层：Producer 端写前去重

这是**最前端的防线**，从源头减少重复消息进入 Stream。

[AsyncTaskService.java#L132-L147](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/asynctask/service/AsyncTaskService.java#L132-L147)：

```java
@Transactional
public AsyncTaskEnqueueResult createOrReusePendingTask(
    AsyncTaskType taskType,
    String businessId,
    String streamKey,
    String payloadJson
) {
    return taskRepository
        // 查询：同一个 taskType + 同一个 businessId + 活跃状态（PENDING 或 PROCESSING）
        .findFirstByTaskTypeAndBusinessIdAndStatusInOrderByCreatedAtDesc(
            taskType,                    // RESUME_ANALYZE
            businessId,                 // "456"
            ACTIVE_STATUSES             // PENDING, PROCESSING
        )
        // 查到了 → 返回已有任务，created = false
        .map(entity -> new AsyncTaskEnqueueResult(toDTO(entity), false))
        // 没查到 → 创建新任务，created = true
        .orElseGet(() -> createTask(taskType, businessId, streamKey, payloadJson));
}
```

[AnalyzeStreamProducer.java#L66-L87](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/resume/listener/AnalyzeStreamProducer.java#L66-L87) 调用侧：

```java
public void sendAnalyzeTask(Long resumeId, String content) {
    AsyncTaskEnqueueResult result = asyncTaskService.createOrReusePendingTask(...);

    if (!result.created()) {
        // ← 已有活跃任务，直接返回，不重复发消息！
        log.info("简历分析任务已存在，跳过重复入队: resumeId={}, taskId={}",
            resumeId, result.task().id());
        return;
    }

    // created = true 才会走到这里，发消息
    AnalyzeTaskPayload payload = new AnalyzeTaskPayload(result.task().id(), resumeId, 0);
    afterCommitExecutor.execute(() -> {
        sendTask(payload);
    });
}
```

**核心逻辑**：

```
用户上传同一份简历两次
    │
    ▼
第一次：createOrReusePendingTask → 没查到活跃任务 → 创建新任务(taskId=789, status=PENDING) → created=true → 发消息 ✅
    │
    ▼
第二次（几秒后）：createOrReusePendingTask → 查到了 taskId=789 还在 PENDING → created=false → return ❌ 不发消息
```

**为什么能防住**：数据库里 `activeFlag=true` + `activeKey=RESUME_ANALYZE:456` 的唯一约束，同一份简历在活跃状态下只会有一条任务记录。

## 四、第二层：Consumer 端实体存在性校验

即使 Producer 层没防住（比如极端并发下两个请求同时插入），Consumer 处理时还有第二道防线。

[AnalyzeStreamConsumer.java#L139-L154](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/resume/listener/AnalyzeStreamConsumer.java#L139-L154)：

```java
protected void processBusiness(AnalyzePayload payload) {
    Long resumeId = payload.resumeId();

    // 第二层幂等检查：实体还在不在？
    ResumeEntity resume = resumeRepository.findById(resumeId)
        .orElseThrow(() -> new AsyncTaskCancelledException("简历已被删除: resumeId=" + resumeId));
    // ↑ 如果用户在上传后删了简历，这条消息走到这里会抛出 AsyncTaskCancelledException
    // ↑ 父类 catch 后走 markCancelled + ACK，不重试，不报错
```

**覆盖场景**：

```
时间线：
T=0s   Producer 发送消息 1（taskId=789, resumeId=456）
T=1s   Producer 因为某种原因又发送了消息 2（taskId=790, resumeId=456）
T=2s   用户删除了简历 456
T=3s   Consumer 消费消息 1 → resumeRepository.findById(456) → 查到了 → AI 分析 → 成功
T=4s   Consumer 消费消息 2 → resumeRepository.findById(456) → 查不到了 → AsyncTaskCancelledException
       → markCancelled + ACK → 不重试，不报错 ✅
```

## 五、第三层：Consumer 端状态已完成检查（最重要）

这是**最后也是最关键**的一道防线，防止已完成的任务被重复执行。

```java
protected void processBusiness(AnalyzePayload payload) {
    Long resumeId = payload.resumeId();
    ResumeEntity resume = resumeRepository.findById(resumeId)
        .orElseThrow(() -> new AsyncTaskCancelledException("简历已被删除"));

    // 第三层幂等检查：已经完成的分析不再重复做
    if (resume.getAnalyzeStatus() == AsyncTaskStatus.COMPLETED
            && persistenceService.getLatestAnalysis(resumeId).isPresent()) {
        log.info("简历分析结果已存在，跳过重复处理: resumeId={}", resumeId);
        return;   // ← 直接返回，不走下面的 AI 调用！
    }

    // 下面是耗时的 AI 调用逻辑
    String resumeText = resolveResumeText(resume);
    ResumeAnalysisResponse analysis = gradingService.analyzeResume(resumeText);
    persistenceService.saveAnalysis(resume, analysis);
}
```

**这道防线覆盖了最危险的场景——XAUTOCLAIM 恢复导致的重复消费**：

```
场景：消费者 JVM 崩溃，消息未 ACK

T=0s   Consumer 拉取消息(retryCount=0)
       → markProcessing → analyzeStatus = PROCESSING
       → AI 调用中...
       → AI 返回结果
       → markCompleted → analyzeStatus = COMPLETED
       → persistenceService.saveAnalysis(分析结果) → 数据写入
       → 正要执行 ackMessage() → JVM OOM 崩溃！
       
       ⚠️ 消息在 PEL 中，没有 ACK

T=60s  PendingMessageRecoveryService 定时任务触发
       → XAUTOCLAIM 认领这条消息
       → processMessage() 重新处理
       → markProcessing → analyzeStatus 从 COMPLETED 改回 PROCESSING ← 这里有问题！
       → processBusiness()
           → 检查：analyzeStatus == COMPLETED? 
              ↑ 哦不对，markProcessing 刚把它改成了 PROCESSING...
```

这里有个潜在竞态，但由于 `markProcessing` → `processBusiness` ✅ `markCompleted` 在同一个线程顺序执行，且：

```java
// 检查的是双重条件：
if (resume.getAnalyzeStatus() == AsyncTaskStatus.COMPLETED
        && persistenceService.getLatestAnalysis(resumeId).isPresent()) {
    return;  // 分析结果确实存在 → 跳过
}
```

**两个条件必须同时满足**：状态是 COMPLETED **且**分析结果表有数据。即使状态因为 XAUTOCLAIM 恢复被短时间改回 PROCESSING，在被其他线程拉到处理时，分析结果表已经有数据了，双重校验能兜底。

## 六、三层防护总结

```
用户请求
    │
    ▼
┌─────────────────────────────────────────────┐
│ 第一层：Producer 写前去重                      │
│ createOrReusePendingTask()                   │
│ 同一 taskType + businessId 已有活跃任务 → 跳过   │
│ 防：用户重复点击、前端重试                      │
└─────────────────────────────────────────────┘
    │ 通过了
    ▼
消息进入 Redis Stream
    │
    ▼
┌─────────────────────────────────────────────┐
│ 第二层：Consumer 实体存在性校验                │
│ resumeRepository.findById(resumeId)           │
│ 查不到 → AsyncTaskCancelledException → ACK    │
│ 防：消费前实体已被删除                         │
└─────────────────────────────────────────────┘
    │ 通过了
    ▼
┌─────────────────────────────────────────────┐
│ 第三层：Consumer 状态已完成检查                │
│ analyzeStatus == COMPLETED && 分析结果存在     │
│ → return，不重复 AI 调用                      │
│ 防：XAUTOCLAIM 恢复、重试导致的重复消费          │
└─────────────────────────────────────────────┘
    │ 通过了
    ▼
真正执行业务逻辑（AI 分析、向量化等）
```

## 七、面试话术

> 「幂等性我们做了三层。
>
> **Producer 端**，通过 `async_task` 表的 `activeFlag` + `activeKey` 做写前去重。同一个业务对象在活跃状态下只允许一条任务记录。用户重复上传时，`createOrReusePendingTask` 返回 `created=false`，直接跳过不发消息。对应的 SQL 是查 `task_type + business_id + status IN (PENDING, PROCESSING)`。
>
> **Consumer 端第一道**，处理前先检查实体是否存在。如果用户在上传后删了简历，消息消费时 `findById` 查不到，抛出 `AsyncTaskCancelledException`，标记 CANCELLED 后 ACK，不重试不报错。
>
> **Consumer 端第二道**，也是最关键的，检查任务是否已完成。即使因为 XAUTOCLAIM 恢复或重试导致同一条任务被消费多次，`processBusiness` 开头会检查 `analyzeStatus == COMPLETED` 且分析结果已存在，满足条件就直接 return，不会重复调用 AI。
>
> 这三层防护的思路是"纵深防御"：不假设上一层 100% 可靠，每一层都有自己的检查逻辑。即使 Producer 去重被并发绕过，Consumer 的两道检查也能兜底。」
