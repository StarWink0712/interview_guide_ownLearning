## 二、整体链路：消息在哪些环节可能丢失

```
Producer                Redis              Consumer
────────              ───────             ────────
① 发送时失败         ② Redis 宕机         ③ 处理中途崩溃
   ↓                     ↓                   ↓
事务后提交+          AOF 持久化          ACK + PEL + 重试
发送失败回调          (待补强)            + 定时 XAUTOCLAIM
```

## 三、Producer 端：事务后提交 + 失败回调

### 为什么不是发完消息再存数据库？

```
❌ 错误做法：先发消息再存数据库
    producer.send(消息)  →  Consumer 收到 → 查数据库 → 数据还没到 → 任务失败

❌ 错误做法：先存数据库再发消息  
    db.save(简历) → producer.send(消息) → Redis 挂了 → 消息丢了，简历已入库无人处理
```

### 我们的方案：事务提交后发消息

```java
public void sendAnalyzeTask(Long resumeId, String content) {

    AsyncTaskEnqueueResult result = asyncTaskService.createOrReusePendingTask(

    );
    if (!result.created()) {
        return;  // 已有活跃任务，幂等跳过
    }

    // 第二步：等数据库事务提交后，再发消息
    AnalyzeTaskPayload payload = new AnalyzeTaskPayload(result.task().id(), resumeId, 0);
    afterCommitExecutor.execute(() -> {
        String messageId = sendTask(payload);
        if (messageId != null) {
            asyncTaskService.markEnqueued(result.task().id(), messageId);
        }
    });
}
```

### afterCommitExecutor 的实现原理

[TransactionAfterCommitExecutor.java](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/transaction/TransactionAfterCommitExecutor.java)：

```java
public void execute(Runnable task) {
    if (!TransactionSynchronizationManager.isSynchronizationActive()) {
        task.run();   // 没事务就直接执行
        return;
    }
    // 注册一个回调：等当前事务提交后再执行
    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                task.run();  // 事务提交成功 → 才发消息
            }
        }
    );
    // 如果事务回滚了 → afterCommit 不执行 → 消息不发 → 完美！
}
```

**这样保证了**：数据库里一定有这条简历记录，Consumer 一定能查到。

### 如果 afterCommit 里发消息失败了呢？

```java
// AbstractStreamProducer.sendTask() 内部

    String messageId = redisService.streamAdd(streamKey(), message, maxLen);
    return messageId;
} catch (Exception e) {
    log.error("发送任务失败: {}", e.getMessage(), e);

    return null;    // ← 返回 null
}

// 回到 afterCommitExecutor 的回调里

    String messageId = sendTask(payload);
    if (messageId != null) {
        // 发送成功
        asyncTaskService.markEnqueued(result.task().id(), messageId);
    }
    // 发送失败 → messageId 为 null → 什么都不做
    // 但 onSendFailed 已经把数据库状态标记为 FAILED 了
});
```

`onSendFailed` 回调在 AnalyzeStreamProducer 子类里：

```java
protected void onSendFailed(AnalyzeTaskPayload payload, String error) {

    // → UPDATE resume SET analyze_status = 'FAILED', analyze_error = '...'

    // → UPDATE async_task SET status = 'FAILED', last_error = '...'
}
```

**结果**：发送失败了，数据库里能查到状态是 FAILED，人工可以重试。

## 四、Consumer 端：ACK 确认 + 重试机制

这是防护最密集的一层。

### 4.1 ACK 确认机制

消息被 XREADGROUP 拉取后，**不会从 Stream 中删除**，而是进入 PEL（Pending Entries List）。只有 Consumer 显式调用 XACK 后，消息才真正从 PEL 移除。

[AbstractStreamConsumer.java#L163-L213](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/async/AbstractStreamConsumer.java#L163-L213) 核心流程：

```java
private void processMessage(StreamMessageId messageId, Map<String, String> data) {
    // ① 消息已通过 XREADGROUP 拉取，此时在 PEL 中
    T payload = parsePayload(messageId, data);

    try {
        // ② 正常路径：标记处理中 → 执行业务 → 标记完成 → ACK
        markProcessing(payload);        // DB: PENDING → PROCESSING
        processBusiness(payload);       // 调用 AI 分析
        markCompleted(payload);         // DB: PROCESSING → COMPLETED
        ackMessage(messageId);          // XACK → 从 PEL 移除 ✅

    } catch (AsyncTaskCancelledException e) {
        // ③ 取消路径：实体被删了
        markCancelled(payload, reason);  // DB: → CANCELLED
        ackMessage(messageId);           // XACK → 不重试

    } catch (Exception e) {
        // ④ 失败路径：区分重试和最终失败
        if (retryCount < MAX_RETRY_COUNT) {        // < 3
            retryMessage(payload, retryCount + 1); // XADD 新消息（retryCount+1）
        } else {                                    // >= 3
            markFailed(payload, error);             // DB: → FAILED
        }
        ackMessage(messageId);  // 原消息 ACK（新消息已在 Stream 里或已标记失败）
    }
}
```

**四条路径全部执行 ACK**：正常、取消、重试、最终失败。PEL 不会泄漏。

```java
protected void retryMessage(AnalyzePayload payload, int retryCount) {
    // 重新构建消息，retryCount + 1
    Map<String, String> message = Map.of(
        "taskId",     payload.taskId().toString(),
        "resumeId",   payload.resumeId().toString(),
        "retryCount", String.valueOf(retryCount)  // 1 → 2 → 3
    );
    // 重新 XADD 到同一个 Stream
    String messageId = redisService().streamAdd(
        AsyncTaskStreamConstants.RESUME_ANALYZE_STREAM_KEY,
        message,
        AsyncTaskStreamConstants.STREAM_MAX_LEN
    );
    asyncTaskService.markRetrying(payload.taskId(), retryCount, messageId);
}
```

时间线示例：

```
T=0s   原消息(retryCount=0) 拉取 → AI 调用超时 → XADD 新消息(retryCount=1) → ACK 原消息
T=5s   新消息(retryCount=1) 拉取 → AI 再次超时 → XADD 新消息(retryCount=2) → ACK
T=10s  新消息(retryCount=2) 拉取 → AI 超时     → XADD 新消息(retryCount=3) → ACK
T=15s  新消息(retryCount=3) 拉取 → AI 超时     → retryCount(3) >= 3 → markFailed → ACK
```

## 五、兜底恢复：PEL 定时 XAUTOCLAIM

如果 Consumer 在处理中途 JVM 崩溃了（OOMKilled / kill -9）：

```
状态：
  消息已 XREADGROUP → 在 PEL 中
  但还没执行到 ackMessage → 消息残留

此时如果不恢复，这条消息永远卡在 PEL 里。
```

[PendingMessageRecoveryService.java](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/asynctask/service/PendingMessageRecoveryService.java)：

```java
@Slf4j
@Service
@RequiredArgsConstructor
public class PendingMessageRecoveryService {

    // Spring 自动注入所有 AbstractStreamConsumer 的子类 Bean
    private final List<AbstractStreamConsumer<?>> consumers;

    // 触发时机 ①：应用启动后立即恢复（恢复上次崩溃残留的消息）
    @EventListener(ApplicationReadyEvent.class)
    public void recoverOnStartup() {
        recoverPendingMessages();
    }

    // 触发时机 ②：每 60 秒定时恢复（恢复运行期间超时的消息）
    @Scheduled(fixedDelay = 60_000, initialDelay = 60_000)
    public void recoverPendingMessages() {
        int recovered = 0;
        for (AbstractStreamConsumer<?> consumer : consumers) {
            try {
                recovered += consumer.recoverPendingMessages(
                    AsyncTaskStreamConstants.PENDING_IDLE_TIMEOUT_MS,  // 60000ms
                    AsyncTaskStreamConstants.PENDING_RECOVERY_BATCH_SIZE  // 10
                );
            } catch (Exception e) {
                log.warn("恢复 pending 消息失败: consumer={}",
                    consumer.getClass().getSimpleName(), e);
            }
        }
        if (recovered > 0) {
            log.info("Redis Stream pending 消息恢复完成: recovered={}", recovered);
        }
    }
}
```

`recoverPendingMessages()` 在父类中实现：

```java
// AbstractStreamConsumer.java
public int recoverPendingMessages(long idleTimeoutMs, int count) {
    // XAUTOCLAIM：认领 PEL 中空闲超过 60 秒的消息
    Map<StreamMessageId, Map<String, String>> messages = 
        redisService.streamAutoClaim(streamKey(), groupName(), consumerName, idleTimeoutMs, count);

    if (messages.isEmpty()) return 0;

    // 重新走完整处理流程（包含幂等保护：已 COMPLETED 的会跳过）
    messages.forEach(this::processMessage);
    return messages.size();
}
```

核心 Redis 命令：

```
XAUTOCLAIM resume:analyze:stream analyze-group analyze-consumer-a3f2b01c 60000 COUNT 10
```

认领回来的消息重新调用 `processMessage()`。因为 `processBusiness` 里有幂等检查：

```java
// AnalyzeStreamConsumer.processBusiness() 中

    log.info("简历分析结果已存在，跳过重复处理");
    return;  // ← 之前已经成功处理过的消息，不会重复分析
}
```

## 六、当前方案的薄弱环节（诚实承认）

| 环节 | 问题 | 生产环境改进方案 |
|------|------|----------------|
| Redis 自身持久化 | 默认 RDB 快照，间隔内宕机会丢消息 | 开启 AOF `appendfsync everysec` |
| Redis 单点 | Redis 挂了所有管道停摆 | Redis Sentinel 主从 + 自动故障转移 |
| ACK 本身失败 | 项目只打日志，依赖下次 XAUTOCLAIM 恢复 | 增加 ACK 重试队列，独立定时任务重试 XACK |
| 没有独立死信 Stream | retry >= 3 只标记数据库 FAILED | 转发到 `resume:analyze:dead` 死信 Stream |

## 七、完整面试话术

> 「消息丢失防护我们做了端到端的三层。
>
> **Producer 端**，通过 TransactionAfterCommitExecutor 把消息发送注册为 Spring 事务的 afterCommit 回调。事务提交成功才发消息，保证 Consumer 一定能查到数据。如果 Redis 连不上导致发送失败，onSendFailed 回调会把数据库状态标记为 FAILED，后续可以人工重试。
>
> **Consumer 端**，利用 Redis Stream 的 PEL 机制，消息被拉取后必须显式 XACK 才能移除。处理成功、实体被删、重试新消息入队、超过重试上限标记失败——这四条路径全部执行 ACK，确保 PEL 不会残留垃圾。失败时会重新 XADD 一条 retryCount+1 的新消息到同一个 Stream，最多重试 3 次，超过后标记 FAILED 等待人工介入。
>
> **兜底恢复层**，PendingMessageRecoveryService 在应用启动时和每 60 秒定时执行 XAUTOCLAIM，认领 PEL 中空闲超过 60 秒的消息重新处理。这覆盖了消费者 JVM 崩溃的场景——消息已拉取但没来得及 ACK，下次启动或定时任务会自动找回。
>
> 当前需要补强的一环是 Redis 自身的持久化，生产环境应该配置 AOF `everysec`。另外 ACK 本身失败时目前只记日志，依赖定时恢复兜底，后续可以加上 ACK 重试机制。」
