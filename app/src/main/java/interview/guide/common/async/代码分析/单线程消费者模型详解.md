# 单线程消费者模型详解

---

## 1. 核心概念：线程与消费者的关系

### 1.1 消费者只是一个名字

Redis Stream 里记录的消费者（如 `analyze-consumer-a3f2b01c`）**不是进程、不是线程、不是 Java 对象，纯粹就是一个字符串**。它的作用类似于工号牌——线程干活时向 Redis 自报家门用的标识：

```
线程："我是 analyze-consumer-a3f2b01c，请给我一条消息"
Redis："好的，记下了。消息 1747300002000-0 已投递给你，加入你的 PEL"
```

### 1.2 三者对应关系

```
1 个应用实例
    │
    └── 1 个 AbstractStreamConsumer Bean（Java 对象，Spring 管理）
            │
            ├── 1 个单线程线程池 (ThreadPoolExecutor, core=1, max=1)
            │     │
            │     └── 1 条守护线程  ← 真正干活的是它
            │           ├── 向 Redis 拉取消息
            │           ├── 同步调用 processMessage()
            │           │     ├── parsePayload()      ← 解析消息
            │           │     ├── processBusiness()   ← 调 LLM / 向量化
            │           │     ├── markCompleted()     ← 更新数据库
            │           │     └── ackMessage()        ← ACK 确认
            │           └── 进入下一轮循环或等待
            │
            └── 1 个 consumerName (String)  ← 只是线程跟 Redis 说的"我叫啥"
                  └── init() 中生成：consumerPrefix + 8位UUID
```

**关键结论**：

- **线程**：所有动作的执行者——拉消息、调 LLM、写 DB、ACK，全在一条线程上串行完成
- **consumerName**：线程的"工号牌"，Redis 用它记账（PEL 归属、idle_time、pending_count）
- **AbstractStreamConsumer Bean**：Java 层面管理生命周期（`@PostConstruct` 启动、`@PreDestroy` 关闭）

## 2. 单线程池设计

### 2.1 线程池配置

```java
// AbstractStreamConsumer.init() 第 79-92 行
this.executorService = new ThreadPoolExecutor(
    1,                              // corePoolSize：核心线程数 1
    1,                              // maximumPoolSize：最大线程数 1
    0L,                             // keepAliveTime：无多余线程，无效参数
    TimeUnit.MILLISECONDS,
    new LinkedBlockingQueue<>(),    // 无界队列（实际上只提交一个任务）
    r -> {
        Thread t = new Thread(r, threadName());  // 自定义线程名
        t.setDaemon(true);                       // 守护线程
        return t;
    },
    new ThreadPoolExecutor.AbortPolicy()         // 安全兜底，实际不会触发
);
```

### 2.2 为什么设计为单线程（四个核心原因）

#### 原因一：消息顺序性

同一个任务实体（如同一份简历）可能有多条关联消息。多线程并行消费会导致乱序处理、状态错乱。单线程保证消息严格按 Stream 顺序一条一条处理——前一条完成并 ACK 之后才拉下一条。

#### 原因二：避免数据竞争

子类的 `processBusiness` 会操作数据库中的任务状态：

```
多线程可能出现：
  线程 A：读取任务状态 = PENDING
  线程 B：读取任务状态 = PENDING（脏读）
  线程 A：更新为 COMPLETED
  线程 B：又更新为 COMPLETED（覆盖！）
```

单线程天然消除这类竞态，不需要加锁。

#### 原因三：业务特性——低频慢任务

消费者处理的是向量化、AI 评分、AI 出题评估，都是**低频慢任务**（一个任务可能几十秒甚至几分钟）。一个单线程轮询拉消息完全够用，多线程只会增加复杂度和出错风险。

#### 原因四：横向扩展靠多实例

需要提升消费能力时，不是给一个消费者加线程，而是**启动多个应用实例**。Redis Stream 的消费者组天然支持多个消费者竞争消费同一 Stream，自动负载均衡。

### 2.3 守护线程的含义

```java
t.setDaemon(true);
```

守护线程的特点是 JVM 退出时不会等待它完成。这里合理——应用关闭时 `@PreDestroy` 会通过 `running = false` 主动停消费循环、`executorService.shutdown()` 关线程池。不需要 JVM 多等这一步。

## 3. 完整调用流程

### 3.1 从启动到第一条消息

```
Spring 容器启动
    │
    ▼
依赖注入完成
    │
    ▼
@PostConstruct → init()                         ← AbstractStreamConsumer 第 74 行
    │
    ├── consumerName = "analyze-consumer-" + UUID(8位)
    │   例: "analyze-consumer-a3f2b01c"         ← 只是一个 String
    │
    ├── 创建单线程守护线程池
    ├── running.set(true)
    │
    └── executorService.submit(this::startConsumer)
            │
            ▼  ← 线程池中唯一的那条线程从这里开始执行
        startConsumer()                          ← 第 119 行
            │
            ├── redisService.createStreamGroup(streamKey(), groupName())
            │   例: XGROUP CREATE resume:analyze:stream analyze-group
            │   如果组已存在 → log.warn 继续
            │
            └── consumeLoop()                   ← 第 136 行
                    │
                    ▼
                while (running.get()) {         ← 只要 running=true 就循环
                    │
                    redisService.streamConsumeMessages(
                        streamKey(),            ← "resume:analyze:stream"
                        groupName(),            ← "analyze-group"
                        consumerName,           ← "analyze-consumer-a3f2b01c"
                        BATCH_SIZE,             ← 10
                        POLL_INTERVAL_MS,       ← 1000ms
                        this::processMessage    ← 消息处理器回调
                    )
                }
```

### 3.2 单条消息的处理流程

消息拉取成功后，**在同一条线程上同步调用** `processMessage`：

```
线程（唯一那条工作线程）
    │
    ▼
redisService.streamConsumeMessages(...)
    │
    │  Redis 返回消息后，同步回调：
    │
    ▼
processMessage(messageId, data)                 ← 第 181 行
    │
    ├── 阶段1: MDC TraceId 管理
    │   ├── 备份当前 MDC traceId
    │   └── 从消息中取 traceId 写入 MDC
    │
    ├── 阶段2: 解析载荷
    │   └── parsePayload(messageId, data) → T payload
    │       null → ack + return
    │
    ├── 阶段3: 读重试次数
    │   └── parseRetryCount(data)
    │
    ├── 阶段4: 执行业务（仍在同一条线程上）
    │   ├── markProcessing(payload)        ← 更新数据库 PROCESSING
    │   ├── processBusiness(payload)       ← 调 LLM / 向量化 / 评分
    │   ├── markCompleted(payload)         ← 更新数据库 COMPLETED
    │   └── ackMessage(messageId)          ← ACK 确认
    │
    └── finally: 恢复 MDC traceId
    │
    ▼
回到 consumeLoop()，继续 while 循环
    → 下一条消息 / 等待 Redis 返回（最多 1000ms 超时）
```

**关键**：`processBusiness` 中调用 LLM 可能耗时 30 秒，这 30 秒期间线程**不会拉新消息**——它在同步等 LLM 返回。这就是"串行消费"的含义。

## 4. 线程与 Redis 的交互细节

### 4.1 拉取消息时线程做了什么

```java
redisService.streamConsumeMessages(
    streamKey(),      // "resume:analyze:stream"
    groupName(),      // "analyze-group"
    consumerName,     // "analyze-consumer-a3f2b01c"
    10,               // 每次最多 10 条
    1000,             // 阻塞等待最多 1000ms
    this::processMessage
);
```

底层执行的是 Redis 命令：

```
XREADGROUP GROUP analyze-group analyze-consumer-a3f2b01c
    COUNT 10
    BLOCK 1000
    STREAMS resume:analyze:stream >
```

- `>` ：表示只取从未投递过的新消息
- `COUNT 10` ：一次最多拉 10 条
- `BLOCK 1000` ：没消息时阻塞等待最多 1 秒

### 4.2 Redis 收到 XREADGROUP 后做了什么

```
1. Redis 查 analyze-group 的 last_delivered_id
   上次投到 1747300001000-0，这次从下一条开始

2. 找到新消息 1747300002000-0、1747300003000-0（最多 COUNT 条）

3. 把这两条消息加入 PEL：
   1747300002000-0 → consumer: analyze-consumer-a3f2b01c
   1747300003000-0 → consumer: analyze-consumer-a3f2b01c
   都标记为"已投给 a3f2b01c，等待 ACK"

4. 更新 last_delivered_id = 1747300003000-0

5. 把消息返回给线程
```

### 4.3 ACK 时线程做了什么

```java
// ackMessage() 第 310-316 行
redisService.streamAck(streamKey(), groupName(), messageId);
```

底层命令：

```
XACK resume:analyze:stream analyze-group 1747300002000-0
```

Redis 收到后：从 PEL 中删除这条记录，`analyze-consumer-a3f2b01c` 的 `pending_count` 减 1。

### 4.4 不 ACK 会怎样

如果线程在 `processBusiness` 执行中崩溃（应用挂了），消息永远留在 PEL：

```
PEL:
  1747300002000-0 → consumer: analyze-consumer-a3f2b01c
  投递时间: 1747300002500
  投递次数: 1
  ↑ 永远等待 ACK
```

`recoverPendingMessages()` 通过 `XAUTOCLAIM` 命令认领这些孤儿消息：

```
XAUTOCLAIM resume:analyze:stream analyze-group analyze-consumer-a3f2b01c 60000 COUNT 10

Redis 返回：空闲超过 60 秒的消息，认领给当前消费者
这些消息的 consumer 从旧名改为新名，投递次数 +1
```

## 5. 单实例 vs 多实例

### 5.1 单实例部署

```
应用实例 A
    │
    └── 1 条线程 = 1 个 consumerName = 1 个消费者
          │
          └── 串行拉取、串行处理、串行 ACK
```

### 5.2 多实例部署

```
resume:analyze:stream
    │
    └── 消费者组: analyze-group
          │
          ├── analyze-consumer-a3f2b01c  ← 实例 A 的线程
          ├── analyze-consumer-b7e8c02d  ← 实例 B 的线程
          └── analyze-consumer-c1d2e03f  ← 实例 C 的线程
```

- 每个实例各有一条线程、各一个 consumerName
- Redis Stream 消费者组保证：**同一条消息只投给一个消费者**
- 不同实例各自串行处理自己拿到的消息，互不干扰
- 如果实例 A 挂了，它的 pending 消息会被 `recoverPendingMessages` 认领到 B 或 C

## 7. 一句话总结

**`AbstractStreamConsumer` 启动一个单线程守护线程池，其中唯一的那条线程以某个 `consumerName`（UUID 字符串）的身份向 Redis Stream 的消费者组报到，循环拉取消息并同步执行完整的"解析 → LLM 调用 → 写库 → ACK"处理链路，全部操作在同一线程上严格串行。consumerName 只是线程向 Redis 自报家门的工号牌，Redis 用它记录 PEL 归属和消费统计。多实例横向扩展时，每条实例各有一条线程、各一个 consumerName，Redis 消费者组保证消息不重复投递，实现分布式下的并行消费。**
