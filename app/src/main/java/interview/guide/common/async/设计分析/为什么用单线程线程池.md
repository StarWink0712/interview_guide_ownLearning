核心原因有四个：

---

### 1. 消息顺序性

同一个任务实体（比如同一份简历）可能有多条关联消息，乱序处理会导致状态错乱。单线程保证 `consumeLoop` 里拿到的消息严格按 Stream 顺序一条一条处理，前一条 ACK 之后才处理下一条。

### 2. 避免数据竞争

子类的 `processBusiness` 会更新数据库中的任务状态（`markProcessing` → `processBusiness` → `markCompleted`）。如果多线程同时消费，可能出现：

```
线程 A：读取任务状态 = PENDING
线程 B：读取任务状态 = PENDING（脏读）
线程 A：更新为 COMPLETED
线程 B：又更新为 COMPLETED（覆盖）
```

单线程天然消除这种竞态。

### 3. 业务特性——低频异步任务

这些消费者处理的是向量化、AI 评分、AI 出题评估，都是**低频慢任务**（一个任务可能几十秒甚至几分钟），不像普通 API 需要高并发。一个单线程轮询拉消息完全够用，没必要开多线程增加复杂度。

### 4. 横向扩展靠多实例而非多线程

需要提升消费能力时，不是给一个消费者加线程，而是**启动多个应用实例**（每个实例各自的消费者线程）。Redis Stream 的消费者组天然支持多个消费者竞争消费同一 Stream，每个消费者一次只拿一条消息，自动负载均衡。这样比单机多线程更安全，也符合分布式扩展思路。

```
同一个 Redis Stream
      │
      ├── 实例 A 的消费者线程（每次拉 1 条）
      ├── 实例 B 的消费者线程（每次拉 1 条）
      └── 实例 C 的消费者线程（每次拉 1 条）

Redis Stream 消费者组保证同一条消息只被一个消费者拿到
```

---

总结：**单线程是顺序保证和防竞态的最低成本方案，低频任务的特性让它不会成为瓶颈，多实例部署负责横向扩展。**
