# common/async 面试官高频问题与参考答案

## 1. 这个模块你会怎么介绍？

回答：

> 这是项目里的异步任务基础设施模块，主要服务于 AI 面试平台里的耗时任务，比如简历分析、知识库向量化、面试评估和语音面试评估。它用 Redis Stream 做消息流转，用异步任务表做状态和幂等，用 `AbstractStreamProducer` 和 `AbstractStreamConsumer` 抽象生产和消费模板，统一处理入队、消费、ACK、重试、取消、pending 恢复和 traceId 透传。

## 2. 为什么这个项目需要异步任务？

回答：

> 因为很多操作涉及文件解析、LLM 调用、Embedding、报告生成，耗时不稳定。如果同步放在 HTTP 请求里，用户体验差，接口容易超时，失败后也不方便恢复。异步后接口只负责创建任务并快速返回，后台消费者慢慢处理，前端可以查任务状态。

## 3. 为什么选 Redis Stream，而不是普通线程池？

回答：

> 线程池只能解决单 JVM 内异步，服务重启任务就没了，也不支持多实例消费和 ACK 恢复。Redis Stream 有持久化消息、消费者组、ACK、PEL 和 XAUTOCLAIM，更适合跨实例的后台任务。当前项目已经依赖 Redis，所以引入成本也低。

## 4. 为什么不用 Kafka 或 RocketMQ？

回答：

> Kafka、RocketMQ 更适合高吞吐、复杂消息治理和大规模微服务场景。这个项目是单体 Spring Boot 应用，异步任务量主要来自 AI 后台任务，吞吐不是极端高，团队部署复杂度也要控制。Redis Stream 能满足消费者组、ACK、pending 恢复和轻量重试，和现有 Redis 依赖复用，性价比更高。后续如果消息规模、延迟要求、死信治理更复杂，可以迁移到 Kafka 或 RocketMQ。

## 5. Redis Stream 消费者组在这里起什么作用？

回答：

> 消费者组让同一个 Stream 下的多消费者可以分摊消息。每个 Consumer 启动时会生成唯一 consumerName，并加入对应 group。Redis 会把新消息投递给组内消费者，消息被读到后进入 pending，ACK 后才从 pending 移除。这样多实例部署时可以水平扩容。

## 6. 你们怎么防止任务重复入队？

回答：

> Producer 侧通过 `AsyncTaskService.createOrReusePendingTask()` 做去重。它按 `taskType + businessId` 查询是否已有活跃任务，如果有就返回 `created=false`，业务 Producer 直接跳过发送。这样用户重复点击或者接口重复调用时，不会为同一个业务对象创建多条活跃任务。

## 7. 你们怎么防止任务重复执行？

回答：

> 消息层不能保证完全不重复，所以业务层做幂等。Consumer 执行业务前会检查业务是否已经完成，比如简历是否已有分析结果、知识库是否已向量化、面试是否已评估。如果已经完成，就跳过处理并 ACK。这样 pending 恢复或 ACK 失败导致的重复消费不会产生重复结果。

## 8. 这个模块能保证 exactly-once 吗？

回答：

> 不能。Redis Stream 加 ACK 更接近至少一次投递。只要存在消费者崩溃、ACK 失败、pending 恢复，就可能重复处理。项目的策略是 at-least-once 加业务幂等，而不是追求消息中间件层面的 exactly-once。

## 9. ACK 什么时候执行？

回答：

> 正常情况下，业务处理成功并且状态更新完成后才 ACK。取消和失败终态也会在状态更新后 ACK。重试时会先重新 XADD 一条新 retry 消息并更新任务重试状态，再 ACK 当前消息。这样避免“先 ACK 后业务失败”导致消息丢失。

## 10. ACK 失败怎么办？

回答：

> ACK 失败会被记录日志，消息仍留在 PEL。后续 pending 恢复服务会通过 XAUTOCLAIM 重新认领并处理。这会带来重复处理可能，所以业务侧必须幂等。
>
> ACK 失败不会导致消息丢失，而是会导致消息仍然留在 PEL 中，后续可能被重复投递。我的处理方式是业务成功后先更新数据库状态，再 ACK；ACK 失败就记录日志并重试，如果仍失败，由 Pending 恢复任务重新领取。消费者通过 taskId 和任务状态做幂等，发现任务已成功就不重复执行业务，只补 ACK。

## 11. 什么是 PEL？

回答：

> PEL 是 Redis Stream 消费者组里的 Pending Entries List。消息被消费者读到但还没 ACK 时，会记录在 PEL。消费者崩溃后，消息不会自动丢失，而是留在 PEL 里，等待后续被 XAUTOCLAIM 认领恢复。

## 12. pending 消息如何恢复？

回答：

> 项目里有 `PendingMessageRecoveryService`，启动完成后恢复一次，运行中每 60 秒恢复一次。它遍历所有 `AbstractStreamConsumer`，调用 `recoverPendingMessages()`，内部通过 `RedisService.streamAutoClaim()` 执行 XAUTOCLAIM，把空闲超过阈值的 pending 消息认领回来，再走同一套 `processMessage()` 处理逻辑。

## 13. 为什么主消费循环只读 neverDelivered 消息？

回答：

> 主循环负责消费新消息，pending 消息属于已经投递但没确认的消息，需要根据 idle timeout 判断是否接管。如果主循环混着读 pending，容易影响正常消费语义。所以新消息走 `neverDelivered()`，旧 pending 走恢复服务。

## 14. 为什么消息体只放 ID，不放完整内容？

回答：

> 因为简历文本、知识库文档、面试上下文可能很大。Redis Stream 适合作为任务触发器，不适合存大对象。消息只放 taskId、businessId、具体业务 ID 和 retryCount，Consumer 再从数据库或对象存储读取内容。这样消息轻量，重试成本低，也不容易撑爆 Redis。

## 15. 为什么要有异步任务表？

回答：

> Redis Stream 只负责消息流转，不适合承载完整业务状态。任务表可以记录任务类型、业务 ID、messageId、状态、重试次数、失败原因、是否活跃。前端能查进度，后台能做幂等和人工重试，排查问题也更方便。

## 16. 为什么要事务提交后再发送消息？

回答：

> 如果业务事务还没提交，Redis 消息已经发出，Consumer 可能立刻消费，此时查数据库可能查不到业务数据或任务记录。通过 afterCommit 发送，可以保证数据库提交后再让后台消费。它不是严格分布式事务，但能避免最常见的消息先到、数据未提交问题。

## 17. Redis 和 DB 不在同一个事务，怎么处理一致性？

回答：

> 当前项目采用最终一致性：先落 DB，事务提交后发 Redis 消息，失败时更新任务状态。这个能覆盖大多数场景，但极端情况下仍可能出现 DB 已提交但消息未发的情况。生产级可以进一步引入 Outbox 表，由投递器扫描补偿，做到更强的最终一致性。

## 18. 重试机制是怎样的？

回答：

> Consumer 捕获普通异常后读取 retryCount。如果小于 `MAX_RETRY_COUNT=3`，就重新 XADD 一条 retryCount+1 的消息，并把任务状态更新回 PENDING。如果达到上限，就标记 FAILED 或 DEAD\_LETTER，并 ACK 当前消息。

## 19. 为什么重试不是直接 sleep 后再处理？

回答：

> 如果在消费者线程里 sleep，会占用唯一消费线程，降低吞吐，也不利于状态可见。重新入队后，当前处理闭环结束，任务表记录 retryCount 和新 messageId。后续如果要延迟重试，可以加 `nextRetryAt` 或延迟队列，而不是阻塞消费线程。

## 20. `FAILED` 和 `DEAD_LETTER` 有什么区别？

回答：

> `FAILED` 表示业务处理失败且自动重试耗尽，消息流转本身是正常的。`DEAD_LETTER` 表示连重新投递重试消息都失败了，任务无法继续靠 Stream 流转，需要人工介入。当前项目的 dead letter 是任务状态，不是独立死信队列。

## 21. 为什么要有 `AsyncTaskCancelledException`？

回答：

> 它用来区分“业务取消”和“系统异常”。比如异步任务开始前，简历或知识库已经被用户删除了，继续重试没有意义。抛这个异常后，Consumer 会标记 CANCELLED 并 ACK，不走自动重试。

## 22. TraceId 在异步任务里怎么传？

回答：

> Producer 入队时从 `TraceIdFilter.currentTraceId()` 取当前请求 traceId，写进消息字段。Consumer 处理时把消息里的 traceId 写回 MDC，finally 里恢复原值。这样用户请求日志和后台消费日志可以串起来，且不会污染线程池里的下一条消息。

## 23. 为什么每个 Consumer 是单线程？

回答：

> 单线程让每条业务管道的处理顺序和状态流转更简单，也避免同一个实例内过多并发 LLM 调用或文件解析。当前项目规模下更稳。如果任务量增加，可以通过多实例消费者组扩容，或者把父类改成可配置并发数。

## 24. 单线程会不会性能不够？

回答：

> 有这个边界。当前适合中小规模异步任务。如果知识库向量化或 AI 评估量明显增加，需要增加并发消费者、拆分 Stream、按任务类型配置线程池、限制 LLM 并发，并监控 Stream 积压长度。

## 25. pending idle timeout 设为 60 秒有什么风险？

回答：

> 如果一个正常任务本身超过 60 秒还没 ACK，恢复服务可能误以为消费者挂了，然后 XAUTOCLAIM 重复处理。生产上要根据任务耗时调大阈值，或者加 heartbeat、租约续期、处理中状态检查，避免误恢复。

## 26. Stream maxLen=1000 有什么考虑？

回答：

> maxLen 控制 Redis Stream 长度，避免无限增长。当前任务量不大时可以接受。但如果短时间积压超过 1000，可能不够安全。生产上应根据峰值流量、处理耗时和 Redis 内存调大，并配合积压监控。

## 27. 如果 Consumer 处理业务时关联实体被删除怎么办？

回答：

> 子类会先查业务实体，比如简历、知识库、面试会话。如果查不到，就抛 `AsyncTaskCancelledException`。父类捕获后标记任务取消并 ACK。因为实体不存在不是临时故障，重试没有意义。

## 28. 如果消息字段坏了怎么办？

回答：

> `parsePayload()` 返回 null 时父类会 ACK 当前消息，避免坏消息反复进入 pending 或阻塞恢复。这个选择适合当前系统。更完善的做法是同时写入坏消息记录或 dead-letter stream，方便排查。

## 29. 如果应用突然重启，正在处理的任务怎么办？

回答：

> 如果还没 ACK，消息会留在 PEL。应用启动后 `PendingMessageRecoveryService` 会恢复空闲 pending 消息。任务可能重复执行，所以业务侧要幂等。任务表里的 PROCESSING 状态也可以帮助排查中断任务。

## 30. 这个模块和业务模块如何解耦？

回答：

> common 层只定义 Producer 和 Consumer 模板，不知道简历、知识库、面试的具体逻辑。业务模块继承模板后实现 streamKey、payload 解析、业务处理和状态更新。这样公共可靠性逻辑复用，业务逻辑仍然留在各自模块。

## 31. 你会如何继续优化这个模块？

回答：

> 我会从四个方向优化。第一，引入 Outbox，解决 DB 和 Redis 投递的最终一致性补偿。第二，增加延迟退避重试，避免第三方服务故障时立即重试放大压力。第三，增加独立 dead-letter stream 和告警。第四，为不同任务类型配置并发数、pending idle timeout 和 LLM 并发限流。

## 32. 如果面试官让你总结这个模块的亮点

回答：

> 亮点有四个。第一，用模板方法统一了四条异步管道的生产和消费逻辑，减少重复代码。第二，用任务表加 Redis Stream 做状态和消息职责分离。第三，可靠性上有 ACK、重试、取消、pending 恢复和业务幂等。第四，工程可观测性上有 traceId 透传、messageId 记录、失败原因记录和指标回调。

## 33. 如果面试官追问这个模块的不足

回答：

> 不足也很明确。它不是 exactly-once，依赖业务幂等；DB 和 Redis 不是分布式事务，极端场景需要 Outbox；当前没有独立死信队列，只有任务表死信状态；重试没有退避；pending idle timeout 对长任务需要调优；单线程消费者吞吐有限。这些都是后续能演进的方向。

## 34. 最推荐背诵的一段话

> 我在这个模块里把异步 AI 任务抽象成了任务表状态机加 Redis Stream 消息流。Producer 负责创建或复用任务，并在事务提交后投递轻量消息；Consumer 负责按统一模板消费消息，处理业务、更新状态、ACK、重试和 pending 恢复。它不是 exactly-once，而是 at-least-once 加业务幂等。这样既能让用户请求快速返回，又能保证后台任务可追踪、可重试、可恢复。
