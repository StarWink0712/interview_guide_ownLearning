### 第一类：为什么用 Redis Stream（几乎是必问）

#### Q1：「为什么选 Redis Stream 而不是 RabbitMQ 或 Kafka？」

**回答要点**：

- 项目本身重度依赖 Redis（限流、缓存、会话），引入额外中间件增加运维成本
- Redis Stream 是 Redis 5.0 原生支持的，不需要额外部署
- 项目规模不大，不需要 Kafka 的海量吞吐能力

#### Q2：「Redis Stream 和 Redis 的 List 做队列有什么区别？」

**回答要点**：

- List 没有消费者组，消息只能被一个消费者消费，不支持 ACK
- Stream 支持消费者组、PEL（待确认列表）、ACK 确认、消息回溯
- Stream 支持阻塞读取（XREAD BLOCK），不用客户端忙轮询

- **Consumer 状态检测**：已 COMPLETED 且有分析结果则跳过 → [AnalyzeStreamConsumer.java#L143-L147](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/resume/listener/AnalyzeStreamConsumer.java#L143-L147)

#### Q5：「PEL 是什么意思？消息什么时候从 PEL 里移除？」

**回答要点**：

- PEL = Pending Entries List，已投递但未 ACK 的消息列表
- XREADGROUP 拉取消息 → 进入 PEL
- XACK 确认 → 从 PEL 移除
- 消费者崩溃 → 消息留 PEL → XAUTOCLAIM 恢复

#### Q6：「ACK 失败了怎么办？」

**回答要点**（项目中是静默失败 + 兜底恢复）：

- `ackMessage()` 失败只打日志 → [AbstractStreamConsumer.java#L247-L253](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/async/AbstractStreamConsumer.java#L247-L253)
- 消息仍在 PEL 中 → 下次 `recoverPendingMessages()` 会重新拉取处理
- 但因为 `processBusiness` 已做幂等保护（已 COMPLETED 则跳过），重复 XAUTOCLAIM 不会导致脏数据

### 第三类：Spring 集成与线程模型

#### Q7：「你们的消费者和 Spring 是怎么集成的？怎么启动和停止？」

**回答要点**：

- `@PostConstruct init()` 启动消费线程 → [AbstractStreamConsumer.java#L71-L93](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/async/AbstractStreamConsumer.java#L71-L93)
- `@PreDestroy shutdown()` 优雅关闭 → [AbstractStreamConsumer.java#L100-L107](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/async/AbstractStreamConsumer.java#L100-L107)
- `@EventListener(ApplicationReadyEvent)` 启动时恢复 PEL 消息
- `@Scheduled(fixedDelay=60_000)` 定时恢复

#### Q8：「为什么要用单线程消费？多线程不行吗？」

**回答要点**：

- 单线程保证消息按 FIFO 顺序处理，避免同一个实体的并发操作
- 如果要多线程，可以在同一消费者组部署多个应用实例，Redis Stream 自动负载均衡
- 单实例内单线程 + 多实例部署 = 安全性 + 可扩展性

#### Q9：「为什么要用守护线程？」

**回答要点**：

- 防御性设计：正常关闭走 `running.set(false)` + `executorService.shutdown()` 优雅退出
- 万一 `@PreDestroy` 失效（比如 Spring 上下文关闭异常），守护线程让 JVM 至少能退出，不会变成僵尸进程
- 这是纵深防御：正常路径优雅关 + 异常路径暴力兜底

### 第四类：重试与死信设计

#### Q10：「重试机制怎么设计的？为什么是 3 次？」

**回答要点**：

- `MAX_RETRY_COUNT = 3` → [AsyncTaskStreamConstants.java#L56](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/constant/AsyncTaskStreamConstants.java#L56)
- 重试方式是重新 XADD 到同一个 Stream（retryCount + 1）
- 3 次是业界常用平衡点：少于 3 次可能因网络抖动误判，多于 3 次大概率是持久故障
- 超过 3 次标记 `DEAD_LETTER` 或 `FAILED`，等待人工介入

#### Q11：「有死信队列吗？」

**回答要点**：

- 有 `DEAD_LETTER` 状态（`AsyncTaskStatusDTO.DEAD_LETTER`），在重试入队失败时使用
- 但当前没有独立的死信 Stream，只在数据库标记
- 后续可以优化：retry >= 3 的消息转发到独立的 `resume:analyze:dead` Stream

### 第五类：事务一致性

#### Q12：「为什么消息要在事务提交后发送？」

**回答要点**（项目中用 `TransactionAfterCommitExecutor`）：

- 如果先发消息再提交事务：Consumer 拿到消息 → 查数据库 → 数据还没到 → 任务失败
- 如果先提交事务再发消息：Consumer 一定查得到数据
- `TransactionSynchronizationManager.registerSynchronization` → `afterCommit()` 回调中发送
- 极端情况：事务提交成功但 `afterCommit` 里发消息失败 → `onSendFailed` 标记 FAILED，可重试

#### Q13：「你在 Service 里调用 Producer，Service 本身就在事务里，这是不是违反了"事务内不能调外部 API"的规范？」

**回答要点**：

- 这个问题问得很好。项目中用了 `TransactionAfterCommitExecutor` 把发送延迟到事务提交后，所以**实际上消息发送并不在事务内进行**
- 这正好避免了规范里禁止的"事务内调用外部 API（LLM、S3、Redis Stream）"的问题

### 第六类：架构设计

#### Q14：「为什么是 4 个独立的 Stream 而不是 1 个 Stream 用消息类型区分？」

**回答要点**：

- 隔离性：一个管道的故障不影响其他管道（简历分析挂了不影响向量化）
- 独立的消费者组和重试策略
- 独立的监控指标

#### Q15：「生产者和消费者怎么配对？消息格式怎么保证一致？」

**回答要点**：

- Producer 和 Consumer 共享 `AsyncTaskStreamConstants` 中的字段名、Stream Key、Group Name → [AsyncTaskStreamConstants.java](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/constant/AsyncTaskStreamConstants.java)
- 消息是 `Map<String, String>` 格式，简洁灵活
- 字段名用常量引用，编译期检查，不会拼错

#### Q16：「如果消费者挂了，消息怎么办？」

**回答要点**：

- 消息在 PEL 中，不会丢
- 应用重启时 `recoverOnStartup()` 立即恢复
- 运行期间 `@Scheduled(fixedDelay=60_000)` 每 60 秒定时恢复
- 场景：OOMKilled / kill -9 / 网络闪断

### 第七类：性能与监控

#### Q17：「这个方案的单机吞吐量怎么样？怎么扩展？」

**回答要点**：

- 单线程单实例消费，适合项目当前规模（不是高并发场景）
- 扩展方式：同一消费者组部署多个应用实例 → Redis Stream 自动在消费者间分发消息
- STREAM\_MAX\_LEN=1000 自动裁剪，防止无限增长

#### Q18：「怎么监控消息队列的运行状态？」

**回答要点**：

- Micrometer 指标（`app.async.task.processing/completed/failed/retry`）→ [AsyncTaskMetricsRecorder.java](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/observability/AsyncTaskMetricsRecorder.java)
- TraceId 全链路追踪：生产者 MDC → 消息字段 traceId → 消费者 MDC
- 结构化日志：始终带 `taskDisplayName()` + `payloadIdentifier()` + `messageId`

### 面试官可能追问的陷阱题

| 陷阱                          | 你的回答                                                                                     |
| --------------------------- | ---------------------------------------------------------------------------------------- |
| 「Redis Stream 和 Kafka 哪个好？」 | 不说谁好谁坏，说**场景适配**：Kafka 适合海量日志、事件溯源；我们这个项目 Redis 已经在了，Stream 是零成本引入，没必要为几千条日活消息搭 Kafka 集群 |
| 「单线程是不是性能瓶颈？」               | 当前规模不是瓶颈；需要扩展时部署多实例，Redis Stream 消费者组天然支持水平扩展                                            |
| 「消息丢了怎么办？」                  | 三层防护（发送端 cb + 消费端 ACK/重试 + 定时 PEL 恢复），但 Redis 自身持久化是待补强项                                 |
| 「重复消费怎么处理？」                 | 三层幂等：Producer 去重 + Consumer 实体存在性检查 + Consumer 状态已完成检查                                   |
