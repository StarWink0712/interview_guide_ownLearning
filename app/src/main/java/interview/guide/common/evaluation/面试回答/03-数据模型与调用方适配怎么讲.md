# 数据模型与调用方适配怎么讲

## 1. 这个模块为什么只定义两个公开 record

`common/evaluation` 对外暴露的核心数据模型很少：

- `QaRecord`
- `EvaluationReport`

这是一种刻意设计。

面试中可以这样说：

> 我没有让统一评估服务直接依赖文字面试或语音面试的实体，而是定义了最小公共模型。只要调用方能把自己的数据转成 `QaRecord`，就能复用同一套评估引擎。

## 2. `QaRecord` 怎么讲

```java
public record QaRecord(
    int questionIndex,
    String question,
    String category,
    String userAnswer
) {}
```

字段含义：

| 字段 | 说明 |
| --- | --- |
| `questionIndex` | 题目索引，通常和业务题号一致 |
| `question` | 问题内容 |
| `category` | 题目分类，如 Java、MySQL、项目深挖 |
| `userAnswer` | 用户回答，null 表示未回答 |

为什么用 record？

> 它是纯数据载体，不需要可变状态。用 record 可以让字段不可变，构造和访问都简洁，也符合 Java 现代写法。

## 3. `EvaluationReport` 怎么讲

```java
public record EvaluationReport(
    String sessionId,
    int totalQuestions,
    int overallScore,
    List<CategoryScore> categoryScores,
    List<QuestionEvaluation> questionDetails,
    String overallFeedback,
    List<String> strengths,
    List<String> improvements,
    List<ReferenceAnswer> referenceAnswers
) {}
```

它包含三层结果：

| 层级 | 字段 |
| --- | --- |
| 总览层 | sessionId、totalQuestions、overallScore、overallFeedback |
| 统计层 | categoryScores、strengths、improvements |
| 逐题层 | questionDetails、referenceAnswers |

面试回答：

> 报告结构不是只给总分，而是兼顾“管理视角”和“学习视角”。总分和分类分帮助用户快速判断能力分布；逐题反馈和参考答案帮助用户复盘具体知识点。

## 4. `CategoryScore` 怎么讲

```java
public record CategoryScore(
    String category,
    int score,
    int questionCount
) {}
```

它表示某一类题的平均得分和题数。

例如：

```text
Java 并发: 平均分 75, 题数 3
MySQL: 平均分 68, 题数 2
项目经验: 平均分 82, 题数 4
```

面试价值：

> 分类分比总分更有指导意义。用户知道总分 70 还不够，最好能知道自己是并发弱、数据库弱，还是项目表达弱。

## 5. `QuestionEvaluation` 怎么讲

```java
public record QuestionEvaluation(
    int questionIndex,
    String question,
    String category,
    String userAnswer,
    int score,
    String feedback
) {}
```

这是前端报告页和 PDF 导出最直接消费的内容。

它解决：

- 每题得了多少分。
- 为什么得这个分。
- 哪些点答对了。
- 哪些点没讲到。

面试回答：

> 逐题反馈是面试复盘的核心。否则用户只看到总分，不知道下一步该补哪里。

## 6. `ReferenceAnswer` 怎么讲

```java
public record ReferenceAnswer(
    int questionIndex,
    String question,
    String referenceAnswer,
    List<String> keyPoints
) {}
```

它和 `QuestionEvaluation` 分开，是因为：

- 评价用户答案和生成参考答案是两个不同视角。
- 前端可以按需展示参考答案。
- 持久化时也能分别处理。

面试回答：

> 我把“你的回答怎么样”和“这题应该怎么答”拆开。前者是反馈，后者是学习材料。这样报告不只是打分工具，也是复习工具。

## 7. 文字面试如何适配

调用方是 `AnswerEvaluationService`。

流程：

1. 接收 `List<InterviewQuestionDTO>`。
2. 转为 `List<QaRecord>`：

```java
questions.stream()
    .map(q -> new QaRecord(q.questionIndex(), q.question(), q.category(), q.userAnswer()))
    .toList();
```

3. 通过 `InterviewSkillService` 构建参考答案基线。
4. 调用：

```java
unifiedEvaluationService.evaluate(chatClient, sessionId, qaRecords, resumeText, referenceContext)
```

5. 把 `EvaluationReport` 转成 `InterviewReportDTO`。

面试回答：

> `AnswerEvaluationService` 本身不做 LLM 评估，它只是文字面试 DTO 和通用评估模型之间的适配器。这样职责很干净。

## 8. 语音面试如何适配

调用方是 `VoiceInterviewEvaluationService`。

它从语音消息构造 `QaRecord`：

- `aiGeneratedText` 作为问题。
- `userRecognizedText` 作为用户回答。
- 根据 AI 文本简单推断分类。
- 空回答用 null。

分类推断规则当前比较简单：

| AI 文本包含 | 分类 |
| --- | --- |
| 项目、实习、工作经历 | 项目深挖 |
| 自我介绍、介绍一下自己 | 自我介绍 |
| 职业规划、为什么、优缺点 | HR问题 |
| 其他 | 技术问题 |

面试回答：

> 语音面试的原始数据不是标准题目列表，而是多轮对话消息。所以语音评估服务先把每轮 AI 提问和用户转写变成 `QaRecord`，再复用统一评估引擎。

要补充边界：

> 当前语音分类是基于关键词的简单推断，适合兜底展示。后续可以在语音面试生成问题时就保存结构化 category，避免事后靠文本推断。

## 9. 为什么 EvaluationReport 不直接复用 InterviewReportDTO

因为 `InterviewReportDTO` 是文字面试模块的对外 DTO，而 `common/evaluation` 需要同时服务：

- 文字面试。
- 语音面试。
- 未来可能的 HR 面试、专项训练、练习模式。

如果 common 直接依赖 `InterviewReportDTO`，就会反向依赖业务模块，破坏分层。

面试回答：

> common 层应该定义自己的稳定模型，而不是依赖某个业务模块的 DTO。业务模块要什么格式，由适配器自己转换。

## 10. 事务边界怎么讲

`UnifiedEvaluationService` 本身不加 `@Transactional`。

这是合理的，因为它做的是：

- LLM 远程调用。
- Prompt 渲染。
- 内存合并。

按照项目规范：

> 不要在事务方法里调用外部 API。

语音评估服务的注释里也明确：

- LLM 调用在事务外。
- 保存评估结果才进入事务方法。

面试回答：

> 评估引擎不持有数据库事务，避免 LLM 调用时占用数据库连接。调用方在拿到报告后，再用事务保存结果。

## 11. 当前数据模型的边界

| 边界 | 当前实现 | 下一步 |
| --- | --- | --- |
| score 没有范围校验 | LLM 返回多少就用多少 | 构建报告前 clamp 到 0 到 100 |
| questionIndex 没强制唯一 | 假设调用方保证 | 入参校验重复 index |
| category 可为空 | 当前直接作为 Map key | 空分类归为“未分类” |
| userAnswer null 表示未回答 | 语义清晰，但总分口径要明确 | 产品层决定未回答是否计入总分 |
| referenceAnswer 可能为空 | 失败时空字符串 | 可标注“参考答案生成失败” |

## 12. 高频追问

### Q1：为什么用 record，而不是普通 class？

回答：

> 这些都是不可变数据载体，没有复杂行为。record 简洁、线程安全语义更清晰，也减少 getter、构造器、equals 等样板代码。

### Q2：为什么不让 UnifiedEvaluationService 直接接收 InterviewQuestionDTO？

回答：

> 那样 common 层会依赖 interview 业务模块，语音面试也不能复用。抽一个 `QaRecord` 后，所有面试形态都能接进来。

### Q3：为什么参考答案和逐题评价分开？

回答：

> 逐题评价回答“用户答得怎么样”，参考答案回答“这题应该怎么答”。这是两个不同用途，分开后前端展示和后续持久化更灵活。

### Q4：语音面试分类为什么靠关键词推断？

回答：

> 这是当前实现的轻量兜底。语音消息本身没有结构化题目分类，只能从面试官提问文本推断。后续最好在生成语音题目时就记录 category，评估时直接使用结构化分类。

## 13. 面试表达小结

> 这个模块的数据模型设计重点是“最小公共抽象”。`QaRecord` 屏蔽不同面试来源，`EvaluationReport` 屏蔽不同展示和持久化目标，中间统一由评估引擎处理。
