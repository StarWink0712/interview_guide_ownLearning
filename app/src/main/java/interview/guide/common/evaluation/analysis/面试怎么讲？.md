# 面试中如何讲 UnifiedEvaluationService 模块

---

## 一、一段话总结（口头回答模板）

> 我负责了面试平台的统一评估引擎 `UnifiedEvaluationService`，它是一个文字面试和语音面试共用的核心服务。整体设计上采用了**三阶段流水线架构**：第一阶段将全量问答记录按配置的批次大小（默认 8 题）分批调用 LLM 评估，每批返回逐题评分、综合评语、优势和改进建议；第二阶段通过内存合并逻辑将所有批次结果聚合并去重，缺失项零分兜底；第三阶段以合并结果为兜底数据再次调用 LLM 做二次汇总，生成统一的全局综合评语，LLM 失败时自动降级到批次聚合结果。整个过程中内置了**多层降级兜底策略**——单批次失败零分兜底、二次汇总失败降级到批次拼接，核心原则是宁可降低评估质量也绝不中断评估流程。技术上用 `StructuredOutputInvoker` 封装了 LLM 结构化输出调用，内置最多 3 次重试和 JSON 自动修复机制，配合 `PromptTemplate` 动态注入简历上下文和技能参考基线，保证不同场景下 LLM 都能拿到完整评估上下文。

## 二、面试中怎么展开讲？——分步讲解思路

### 第 1 步：先讲背景和定位（10 秒）

**你要传递的信息**：

- 这是一个通用评估引擎，放在 `common/evaluation` 包下
- 文字面试和语音面试共用同一套评估逻辑
- 调用方（`AnswerEvaluationService`、`VoiceInterviewEvaluationService`）只负责 DTO 适配，评估完全委托给我

**口头表达示例**：

> 这个模块是面试评估的核心引擎，放在 common 层，文字面试和语音面试都要用它。调用方只需要把各自的 DTO 转成通用的 QaRecord 给我，我负责全部评估逻辑，最后把通用的 EvaluationReport 还给调用方，调用方做一次格式转换就行。这样实现了评估算法和业务场景的解耦。

---

### 第 2 步：讲三阶段流水线（重点，60 秒）

**你要传递的信息**：

- 阶段一：分批评估（为什么要分批？LLM 上下文窗口有限）
- 阶段二：内存合并（零分兜底、去重限制 8 条）
- 阶段三：二次汇总（为什么需要二次汇总？）

**口头表达示例**：

> 评估流程我设计成了三个阶段。
>
> 第一个阶段是分批评估。为什么不分批一次性全给 LLM？因为如果用户面了 30 道题，全量问答串起来可能超出 LLM 的上下文窗口。所以我按配置文件中的 batchSize（默认 8 题）把问答分成多批，每批独立调 LLM。每批返回结构化 JSON，包含这 8 道题的逐题打分、反馈、参考答案，还有一个这批的整体评语和优势改进。
>
> 第二阶段是内存合并。每个批次的结果直接合并——逐题评分按原始顺序拼、优势改进用 LinkedHashSet 去重保留顺序、综合评语用换行拼接。这里有个关键兜底：如果某个批次 LLM 调用失败了，这一批的题目全部给零分和默认话术，不会中断流程。
>
> 第三阶段是二次汇总。因为每个批次的 LLM 只能看到自己的 8 道题，它的综合评语是有局限性的。所以我再把所有批次的合并结果——分类得分摘要、每道题的亮点、兜底评语——作为上下文，再调一次 LLM 让它基于全局视角出统一评语。如果这次也失败了，就直接用第二阶段的拼接结果，不中断。

---

### 第 3 步：讲降级策略（体现高可用设计，30 秒）

**你要传递的信息**：

- 两层降级：单批次失败 → 零分兜底；二次汇总失败 → 批次拼接
- 核心思路：宁可降低评估质量，也绝不中断评估

**口头表达示例**：

> 整个流程有两层降级兜底。第一层：单个批次 LLM 调用失败，这个批次所有题按零分处理，其他批次照常评估。第二层：二次汇总的 LLM 调用失败，直接用各批次评语拼接和去重后的优势改进作为最终结果，不走 LLM。
>
> 这样设计的原因是：评估报告的完整性比精度更重要——用户交了 30 道题，你给他只评了 8 道的结果算怎么回事？所以我的原则是宁可有几道题零分，也要保证 30 道题的完整报告出来。

---

### 第 4 步：讲技术细节（展示能力，30 秒）

**你要传递的信息**：

- `StructuredOutputInvoker` 封装了重试 + JSON 修复
- `PromptTemplate` 动态注入简历、参考基线
- `BeanOutputConverter` 做 JSON 反序列化
- 配置通过 `@ConfigurationProperties` 集中管理

**口头表达示例**：

> 技术上几个点可以展开说。LLM 的调用我封装了一个 `StructuredOutputInvoker`，它不是简单的调 API，而是内置了最多三次重试，每次重试会把上次的 JSON 解析错误喂回给 LLM，同时追加严格 JSON 输出指令，提高成功率。另外我还做了一个 JSON 本地修复逻辑——LLM 返回的 JSON 里经常有字符串内的引号没转义，我用状态机扫描修复后再尝试解析，这步纯粹在本地完成，不走网络。
>
> Prompt 我用的是 Spring AI 的 StringTemplate 模板格式，放在 resources 下，通过 `PromptTemplate.render()` 动态注入变量——简历文本、参考基线都通过 Map 传进去，超长文本自动截断，防止超出 token 限制。
>
> 配置方面没有用 `@Value` 散落各处，而是集中到 `InterviewEvaluationProperties` 这个 `@ConfigurationProperties` 类里，batchSize、Prompt 路径都在一个地方管理。

---

### 第 5 步：如果有追问——准备几个可能的问题

#### Q1：为什么不把分批评估做成并行的？

> 当前是串行的，因为虚拟线程有并发限制，而且 LLM API 有速率限制。但架构上改并行很容易——`evaluateInBatches()` 方法里的 for 循环就是天然的并行点，改成 `parallelStream()` 或用 `CompletableFuture` 就可以。目前没做是因为题目量通常不大（10~20 道），串行时间也在可接受范围内。

#### Q2：二次汇总为什么不和第一次评估合并成一次调用？

> 如果一次给 LLM 30 道题让它"既逐题评分又出全局评语"，有两个问题：一是 token 太多可能超上下文窗口，二是任务太复杂输出可控性差。分两次调——先逐题评分（任务明确、输出结构化强），再基于摘要出全局评语（上下文小、任务聚焦）——效果更可控。

#### Q3：零分兜底会不会太粗暴？有没有更好的方式？

> 零分兜底确实会拉低总分，但至少报告是完整的。更好的方式是重试多次或者换一个 LLM provider 重试，`StructuredOutputInvoker` 已经做了 3 次重试。如果要做得更细，可以在重试全部失败后调用一个更便宜、更快的模型做降级评估，而不是直接给零分。这个在当前版本没有实现，是一个后续优化点。

#### Q4：batchSize 是怎么定的？为什么默认是 8？

> 8 题只是一个经验值，不是拍脑袋定的。8 道题（加上回答）大概 2000~3000 tokens，加上系统 Prompt 和简历上下文总共 4000~5000 tokens，大部分模型上下文窗口轻松覆盖但又不会被占满，给模型留下足够的生成空间。这个值在配置文件里可以随时调。
