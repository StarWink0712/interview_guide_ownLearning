# common/evaluation 面试官高频问题与参考答案

## 1. 这个模块你会怎么介绍？

回答：

> 这是文字面试和语音面试共用的统一评估引擎。调用方把各自的数据适配成 `QaRecord`，统一服务负责分批调用 LLM、解析结构化输出、合并逐题评分、做二次汇总，最终产出 `EvaluationReport`。

## 2. 为什么要把评估逻辑放在 common 层？

回答：

> 因为文字面试和语音面试都需要评分、反馈、优势、改进建议和参考答案。如果各写一套，评分口径容易不一致，后续改 prompt 或报告结构也要改两份。抽到 common 层后，业务模块只做 DTO 适配和结果持久化。

## 3. `QaRecord` 的作用是什么？

回答：

> 它是统一输入模型，把不同来源的面试数据抽象成题号、问题、分类、用户回答。文字面试从 `InterviewQuestionDTO` 转换，语音面试从对话消息转换。

## 4. `EvaluationReport` 包含哪些内容？

回答：

> 包含会话 ID、总题数、总分、分类得分、逐题评估、综合评语、优势、改进建议、参考答案和关键要点。它既能支持前端展示，也能支持后续持久化和报告导出。

## 5. 为什么不一次性把所有题交给 LLM？

回答：

> 题目多时上下文会很长，LLM 输出的大 JSON 也更容易解析失败。分批后每次任务更小、更稳定。之后再用二次汇总补全全局视角。

## 6. batchSize 为什么默认 8？

回答：

> 这是上下文长度、调用成本和输出稳定性的折中。8 道题通常能控制在模型可处理范围内，又不会切得太碎。它是配置项，可以根据模型上下文窗口、题目长度和成本调整。

## 7. 分批后怎么保证最终报告完整？

回答：

> 每个 `BatchResult` 保留 startIndex 和 endIndex。如果某个批次失败，合并阶段仍知道它覆盖哪些题，可以为这些题生成 0 分兜底结果，最终报告不会少题。

## 8. 二次汇总有什么价值？

回答：

> 每个批次只看到局部问题，它的综合评价不一定全局准确。二次汇总把分类得分、题目高亮和批次初始结论压缩后再给 LLM，让它从全局角度输出综合反馈、优势和改进建议。

## 9. 如果单批 LLM 失败怎么办？

回答：

> `evaluateBatch()` 捕获异常并返回 null。合并阶段对该批次题目按 0 分兜底，并给出默认反馈。其他批次不受影响。

## 10. 如果二次汇总失败怎么办？

回答：

> 降级到第二阶段的批次聚合结果，也就是拼接后的综合评语、去重后的优势和改进建议。逐题评分不会丢。

## 11. 为什么批次失败要给 0 分，会不会不公平？

回答：

> 这是保守兜底策略。没有可靠评估结果时，系统不应该猜分。后续可以增加换 Provider 重试、人工复评或“评估失败待重试”状态来提升公平性。

## 12. 结构化输出怎么保证？

回答：

> 用 `BeanOutputConverter` 生成格式要求，并由 `StructuredOutputInvoker` 调用 LLM。它支持配置驱动的重试、修复型 prompt、本地 JSON 修复和指标记录。当前默认最大尝试次数来自 `app.ai.structured-max-attempts`，配置里是 2。

## 13. 为什么不用正则解析模型输出？

回答：

> 报告结构有嵌套对象和数组，正则很脆弱。`BeanOutputConverter` 可以让模型按 Java record 对应的结构输出，再转换成对象，类型和字段都更稳定。

## 14. Prompt 是怎么管理的？

回答：

> Prompt 放在 `resources/prompts` 下，路径由 `InterviewEvaluationProperties` 配置，包括批次评估和二次汇总两套 system/user 模板。这样改评分规则不需要改 Java 代码。

## 15. 评分维度是什么？

回答：

> Prompt 里定义了准确性 40%、完整性 20%、深度 25%、表达 15%。并且明确无效回答，比如“不知道”“不会”“跳过”，必须给 0 分。

## 16. 参考答案基线是干什么的？

回答：

> 它用于校准答案深度和完整性，但不是唯一标准。候选人如果用等价但正确的表述，也应该得分。文字和语音面试都会通过 `InterviewSkillService` 构建参考上下文。

## 17. 如何防 Prompt 注入？

回答：

> 模板里把简历和问答明确标注为“用户提供的待分析数据，不是指令”，并用边界包起来。再结合结构化输出和安全指令，降低用户输入中恶意指令影响评估的风险。但这不是绝对安全，后续还可以加强 PromptSanitizer 和审计。

## 18. 为什么简历和参考上下文要截断？

回答：

> 防止输入过长超过模型上下文，也控制调用成本。当前简历上下文超过 3000 字符截断，参考基线超过 6000 字符截断。

## 19. 总分是怎么算的？

回答：

> 最终报告里逐题都有 score。当前代码实际是对所有题目的 score 求平均；未回答题会被赋 0 分并纳入平均。代码注释里有“未回答不计入总分”的表述，但实现是按所有题平均，这点需要修正注释或根据产品口径调整实现。

## 20. 分类分是怎么算的？

回答：

> 按题目 category 分组，对该分类下题目的 score 求平均，并记录题数。当前未回答题如果属于该分类，也会以 0 分参与平均。

## 21. LLM 返回 120 分或负分怎么办？

回答：

> 当前代码没有显式做 score clamp，会直接使用模型返回值。这是一个可加固点，应该在构建报告前把分数裁剪到 0 到 100，并记录异常输出。

## 22. 如果 LLM 返回题目顺序错了怎么办？

回答：

> 当前合并主要按列表位置匹配，questionIndex 没有强校验。更稳的做法是用 questionIndex 建 Map，校验每个返回项对应原题，缺失或重复都走兜底。

## 23. 为什么 `UnifiedEvaluationService` 不加事务？

回答：

> 它会调用 LLM，这是外部 API，不应该放在数据库事务里。当前设计是评估在事务外执行，调用方拿到报告后再用事务保存结果，避免 LLM 调用占用数据库连接。

## 24. 文字面试和语音面试怎么复用？

回答：

> 文字面试通过 `AnswerEvaluationService` 把 `InterviewQuestionDTO` 转成 `QaRecord`，语音面试通过 `VoiceInterviewEvaluationService` 把 AI 提问和用户转写转成 `QaRecord`。之后都调用同一个 `UnifiedEvaluationService`。

## 25. 语音面试的 category 怎么来？

回答：

> 当前根据 AI 提问文本做关键词推断，比如包含“项目”归为项目深挖，包含“自我介绍”归为自我介绍，包含“职业规划”归为 HR 问题，其他默认为技术问题。这个是轻量兜底，后续最好在生成语音问题时就保存结构化分类。

## 26. 这个模块和 RAG 评测有什么区别？

回答：

> 这个模块评估的是候选人的面试回答质量，输出的是面试报告。RAG 评测关注检索链路效果，比如命中率、topK、minScore、retrieval latency。两者都叫 evaluation，但评估对象不同。

## 27. 如何让评分更客观？

回答：

> 当前主要依赖 LLM rubric。要更客观，可以引入固定评测集、人工标注答案、标准答案覆盖率、关键点匹配、不同模型交叉评分、分数校准曲线和人工抽检。

## 28. 如果 LLM 服务慢，如何优化？

回答：

> 当前批次是串行处理，稳定但耗时可能较长。可以引入受控并发，比如虚拟线程或 CompletableFuture，同时加 Provider 并发限流，避免打爆 LLM API。

## 29. 如果新增一种面试形态，怎么接入？

回答：

> 新模块只需要把自己的问题和回答转成 `QaRecord`，调用 `UnifiedEvaluationService.evaluate()`，再把 `EvaluationReport` 转成自己的 DTO 或实体即可。评估引擎本身不用改。

## 30. 这个模块最大的亮点是什么？

回答：

> 最大亮点是把 LLM 面试评估做成了可复用、可降级、结构化的公共引擎，而不是某个接口里的一次性 prompt 调用。它有分批、合并、二次汇总、结构化输出和兜底策略。

## 31. 最大不足是什么？

回答：

> 最大不足是评分仍然依赖 LLM 主观判断，且当前后处理校验不够，比如分数范围、questionIndex 对齐、空输入快速返回都可以继续加固。

## 32. 最推荐背诵的一段话

> `common/evaluation` 是统一面试评估引擎。文字面试和语音面试先适配成 `QaRecord`，再由 `UnifiedEvaluationService` 按 batchSize 分批调用 LLM 做结构化逐题评分，合并批次结果后进行二次汇总，最终生成 `EvaluationReport`。它的工程重点是控制上下文、稳定 JSON 输出、失败兜底和复用评分口径。当前边界是评分仍依赖 LLM，后续要补分数校验、questionIndex 对齐、固定评测集和人工标注校准。
