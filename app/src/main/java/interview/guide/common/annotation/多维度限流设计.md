<br />

和 LLM 没关系，三种维度只是**按什么粒度来数请求次数**。

***

以简历上传接口为例，假设限流规则是 **每分钟最多 3 次**：

## GLOBAL — 所有用户共用一个计数器

```
Redis Key: ratelimit:{ResumeController:upload}:global

用户A 上传了 → 计数器 1/3
用户B 上传了 → 计数器 2/3  （和A共享）
用户C 上传了 → 计数器 3/3
用户D 上传了 → 超过上限，被拒绝

一分钟内不管谁发请求，加起来最多 3 次
```

**防的是**：整个系统被刷爆。比如有人开 100 个账号同时上传简历，GLOBAL 限制保证服务端总负载不超标。全局都是用的同样的redis的key，所以无论是什么后端什么前端，只要是上传简历，都是要走这个key的，那就统一限流

***

## IP — 每个 IP 地址独立计数

```
Redis Key: ratelimit:{ResumeController:upload}:ip:1.2.3.4
Redis Key: ratelimit:{ResumeController:upload}:ip:5.6.7.8

用户A（IP=1.2.3.4）上传了 → 该 IP 计数器 1/3
用户A 又上传了           → 该 IP 计数器 2/3
用户B（IP=5.6.7.8）上传了 → 另一个 IP 计数器 1/3（互不影响）

同一台机器/同一个网络的人共享这 3 次配额
```

**防的是**：单台机器或单个网络不停刷接口。不同 IP 的人互不影响。IP 限流 → 认的是 IP 地址，不管你是谁
同一个 WiFi 下的多个账号 → 共享配额

***

## USER — 每个登录用户独立计数

```
Redis Key: ratelimit:{ResumeController:upload}:user:10001
Redis Key: ratelimit:{ResumeController:upload}:user:10002

用户A（userId=10001）上传了 → 该用户计数器 1/3
用户B（userId=10002）上传了 → 另一个用户计数器 1/3（互不影响）

即使是同一个 IP，不同用户各自有 3 次配额
```

**防的是**：单个用户恶意刷接口。正常用户之间互不影响。USER 限流 → 认的是用户 ID，不管你在哪
同一个账号换了手机 / 换了网络 → 配额跟着账号走

***

## 三者通常组合使用

以知识库查询接口为例，同时标注三条规则：

```java
@RateLimit(dimension = Dimension.GLOBAL, count = 100, interval = 1, timeUnit = MINUTES)
@RateLimit(dimension = Dimension.IP,     count = 10,  interval = 1, timeUnit = MINUTES)
@RateLimit(dimension = Dimension.USER,   count = 5,   interval = 1, timeUnit = MINUTES)
public Result<?> queryKnowledgeBase(...) { ... }
```

含义：

| 维度     | 限制        | 含义                   |
| ------ | --------- | -------------------- |
| GLOBAL | 每分钟 100 次 | 全系统总共 100 次/分钟，不管谁发的 |
| IP     | 每分钟 10 次  | 同一个 IP 最多 10 次/分钟    |
| USER   | 每分钟 5 次   | 同一个用户最多 5 次/分钟       |

这三条是 **AND 关系**，全部通过才放行：

```
一次知识库查询请求到达
    │
    ├── GLOBAL 检查：当前系统总请求数 < 100？  → 通过
    ├── IP 检查：    这个 IP 的请求数 < 10？    → 通过
    └── USER 检查：  这个用户的请求数 < 5？     → 通过
    │
    ▼
全部通过 → 执行查询

任一不通过 → 拒绝，返回错误码 8001
```
