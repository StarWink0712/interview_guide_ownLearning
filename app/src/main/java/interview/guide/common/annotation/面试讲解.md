## 面试讲解思路 

建议按 **"痛点 → 方案 → 实现 → 亮点"** 四层来讲，控制在 3-5 分钟。

***

### 第一层：为什么需要限流（30 秒）

> "这个面试平台的 AI 接口（出题、评估）调一次比较贵也慢，同时文件上传、知识库查询这些接口也不能被打爆。所以我设计了一套声明式限流组件，用注解就能给任意接口加限流，支持全局限流、按 IP 限流、按用户限流三个维度自由组合。"

***

### 第二层：整体架构（1 分钟）

> "核心是两个部分：一个 `@RateLimit` 注解，支持 `@Repeatable` 可重复标注，每条注解代表一个独立维度的限流规则，包含维度、窗口大小、最大请求数、降级方法名等属性。另一个是 `RateLimitAspect` 切面，用 `@Around` 拦截带注解的 Controller 方法，拿到方法上所有限流规则后逐条执行——规则之间是 AND 关系，全部通过才放行，任何一条不通过就触发降级或抛异常。"

***

### 第三层：滑动窗口实现（1.5 分钟）

> "每条规则用一个 Redis Lua 脚本做滑动时间窗口。Redis 里为每条规则维护两个键：一个 String 存剩余令牌数，一个 Sorted Set 存历史消费记录，member 是 '请求ID:消耗数'，score 是毫秒时间戳。
>
> 脚本执行流程：先读剩余令牌 → ZRANGEBYSCORE 查出窗口外的过期记录 → 统计过期令牌并归还 → 判断够不够 → 够就 ZADD 写新记录、SET 更新令牌 → 不够就返回 0。
>
> 这里用 Sorted Set 而不是计数器，是因为每条记录有精确时间戳，能做到真正的滑动窗口，消除固定窗口的边界突发问题。整个 Lua 脚本在 Redis 单线程里原子执行，读写判断无竞态条件。"
>
> 可以补一句："为了兼容 Redis Cluster，Key 用了 Hash Tag `{ClassName:MethodName}` 把同一方法的所有限流 Key 强制落在同一个 slot。"

***

### 第四层：亮点收尾（30 秒）

> "还有几个细节：Redis 重启后 evalsha 缓存丢失，切面里有 NOSCRIPT 自动重载机制；限流触发时优先调用降级方法兜底，不直接抛异常；每次请求带 UUID 去重，防止网络重试重复计数。整个组件被 5 个 Controller 使用，业务代码一行不改，只加注解即可。"

***

## 面试官可能追问的问题

### 基础类

**Q1：固定窗口和滑动窗口有什么区别？为什么选滑动窗口？**

> 固定窗口按自然时间周期重置计数器（比如每分钟清一次），在窗口边界有突发问题——比如 12:00:59 和 12:01:01 各打满 10 次，实际 2 秒内打了 20 次。滑动窗口每条记录带精确时间戳，始终看"过去 N 秒内的记录数"，边界是完全平滑的。

**Q2：为什么用 Lua 脚本而不是 Java 代码做判断？**

> 两个原因：一是原子性，Redis 单线程执行 Lua，读令牌→判断→扣减三步无竞态条件；二是性能，一次网络往返完成全部操作，不需要多次 get/set。

**Q3：`@Repeatable`** **是什么？为什么要用？**

> Java 8 的可重复注解机制，允许同一个方法上写多个同类型注解，编译器自动用 Container 包装。我用它实现多维度组合限流，比如一个接口同时加 GLOBAL 和 IP 双重限制。

***

### 深入类

**Q4：为什么** **`:value`** **和** **`:permits`** **要分开两个键？只用一个 Sorted Set 不行吗？**

> 可以只用 Sorted Set，每次查 count 做 ZCARD。但分开的好处是 String 的 GET 操作比 Sorted Set 的 ZCARD 更快，高并发下减少计算开销。`:value` 是 O(1) 读，`:permits` 仅在有过期记录时才触发 ZRANGEBYSCORE。

**Q5：高并发下，这个方案有没有性能瓶颈？**

> 瓶颈在 Redis 单线程执行 Lua 脚本，但一条 Lua 脚本通常 < 1ms，单机 Redis 能撑 10 万+ QPS。如果更大规模，可以给不同接口分配不同 Redis 节点，或者改用本地令牌桶 + Redis 异步同步的混合方案。

**Q6：Redis 挂了怎么办？是直接放行还是拒绝？**

> 当前实现是异常直接抛出，请求会失败。这是 fail-safe vs fail-fast 的取舍，我倾向 fail-fast——限流组件本身出问题不应该让系统裸奔。如果要做高可用，可以加 Redis Sentinel 或 Cluster 保证 Redis 本身的高可用。

***

### 扩展类

**Q7：如果要支持"不同用户等级不同限额"怎么改？**

> 在注解里加一个 `quotaKey` 属性，从请求上下文或用户信息中动态取值。切面生成 Key 时从 `@RateLimit` 取配额值而不是写死的 count，或者把限额配置放到 Redis/数据库里动态读取。

**Q8：有没有考虑过用 Sentinel 或者 Guava RateLimiter？**

> Guava RateLimiter 是单机限流，分布式环境下各实例独立计数，不能精确控制全局总量。Sentinel 功能全但重，依赖控制台。我这里的场景刚好是中等规模、需要分布式精确限流、不想引入额外中间件，Redis + Lua 是最轻量的方案。

**Q9：Lua 脚本里的** **`string.match(v, ":(%d+)$")`** **正则有性能问题吗？**

> Sorted Set 里过期记录的量取决于窗口大小和 QPS，通常一次 ZRANGEBYSCORE 也就数十条，正则开销可忽略。如果真的量很大，可以考虑用 HINCRBY 代替遍历累加。

**Q10：`timeout`** **字段为什么没用上？你打算怎么实现？**

> 预留字段，当前是直接拒绝模式。如果要实现等待，可以在切面里加一个循环：配额耗尽时 Thread.sleep 一小段时间后重试 Lua 脚本，直到超时。但虚拟线程场景下 sleep 不占 OS 线程，影响不大。
