# 业务落点、异常降级与边界怎么讲

## 1. 为什么这些接口要限流

限流不是为了“显得系统高级”，而是保护系统资源。

在这个项目里，限流主要保护三类接口：

```text
1. 高成本 AI 接口
   简历分析、面试出题、回答评估、JD 解析、知识库问答

2. 高成本文件/向量接口
   简历上传、知识库上传、知识库重新向量化

3. 管理配置接口
   LLM Provider 增删改查、连接测试、ASR/TTS 配置测试
```

面试表达：

> 我的限流策略不是所有接口一刀切，而是优先保护容易被频繁触发、会调用外部 AI 服务、或者会占用文件解析和向量化资源的接口。

## 2. 当前 Controller 里的典型使用

### 2.1 简历上传

```java
@PostMapping(value = "/api/resumes/upload", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
@RateLimit(dimension = RateLimit.Dimension.GLOBAL, count = 5)
@RateLimit(dimension = RateLimit.Dimension.IP, count = 5)
public Result<Map<String, Object>> uploadAndAnalyze(...)
```

怎么讲：

> 简历上传会触发文件接收、格式解析、去重、AI 分析和结果落库，所以加了 GLOBAL 和 IP 双重限流。GLOBAL 防止接口整体被打爆，IP 防止单个客户端反复上传。

### 2.2 简历重新分析

```java
@RateLimit(dimension = RateLimit.Dimension.GLOBAL, count = 2)
@RateLimit(dimension = RateLimit.Dimension.IP, count = 2)
```

怎么讲：

> 重新分析通常是用户手动重试，频率应该更低，所以阈值比上传更保守。

### 2.3 创建面试会话

```java
@RateLimit(dimension = RateLimit.Dimension.GLOBAL, count = 5)
@RateLimit(dimension = RateLimit.Dimension.IP, count = 5)
public Result<InterviewSessionDTO> createSession(...)
```

怎么讲：

> 创建面试会话会生成题目、初始化会话状态，有时还会结合简历/JD 调用 AI，所以要限制频率。

### 2.4 提交面试答案

```java
@RateLimit(dimension = RateLimit.Dimension.GLOBAL, count = 10)
public Result<SubmitAnswerResponse> submitAnswer(...)
```

怎么讲：

> 提交答案是面试主流程中的高频接口，阈值比创建会话高一些。当前只配置了 GLOBAL，后续可以加 USER 或 IP 维度，防止单个会话刷提交。

### 2.5 知识库查询和流式查询

```java
@RateLimit(dimension = RateLimit.Dimension.GLOBAL, count = 10)
@RateLimit(dimension = RateLimit.Dimension.IP, count = 10)
public Result<QueryResponse> queryKnowledgeBase(...)

@RateLimit(dimension = RateLimit.Dimension.GLOBAL, count = 5)
@RateLimit(dimension = RateLimit.Dimension.IP, count = 5)
public Flux<String> queryKnowledgeBaseStream(...)
```

怎么讲：

> RAG 查询涉及向量检索、Prompt 组装和 LLM 生成。流式查询会持续占用连接和生成资源，所以流式接口阈值更低。

### 2.6 知识库上传和重新向量化

```java
@RateLimit(dimension = RateLimit.Dimension.GLOBAL, count = 3)
@RateLimit(dimension = RateLimit.Dimension.IP, count = 3)
public Result<Map<String, Object>> uploadKnowledgeBase(...)

@RateLimit(dimension = RateLimit.Dimension.GLOBAL, count = 2)
@RateLimit(dimension = RateLimit.Dimension.IP, count = 2)
public Result<Void> revectorize(...)
```

怎么讲：

> 上传知识库会触发文件解析、对象存储、异步向量化；重新向量化更重，所以阈值更低。

### 2.7 JD 解析

```java
@RateLimit(dimension = RateLimit.Dimension.IP, count = 5)
public Result<List<CategoryDTO>> parseJd(...)
```

怎么讲：

> JD 解析是单个用户触发的 LLM 调用，所以当前按 IP 限流即可。后续登录体系完善后，可以改成 USER 维度更准确。

### 2.8 Provider 管理接口

`LlmProviderController` 大量使用 GLOBAL 限流：

```text
列表/详情：30/s
创建/更新/删除：5/s
测试连接：10/s
热加载：5/s
ASR/TTS 配置：读 30/s，写 5/s，测试 10/s
```

怎么讲：

> Provider 管理接口虽然不是普通用户高频接口，但连接测试会访问外部模型服务，配置修改会影响全局模型调用，所以也要限流，避免误操作或脚本刷管理接口。

## 3. 多维规则为什么是 AND 关系

示例：

```java
@RateLimit(dimension = GLOBAL, count = 5)
@RateLimit(dimension = IP, count = 5)
```

切面逐条执行：

```text
GLOBAL 通过？
  否 -> 拒绝
  是 -> 继续

IP 通过？
  否 -> 拒绝
  是 -> 执行业务方法
```

面试表达：

> 多条规则是 AND 关系，不是 OR。因为只要任意一个维度触达上限，就说明请求存在风险。比如全局还没满，但某个 IP 已经刷爆，也应该拒绝。

## 4. fallback 降级怎么讲

触发限流时：

```java
return handleRateLimitExceeded(joinPoint, rule, key);
```

处理顺序：

```text
1. rateLimit.fallback() 不为空？
2. 找同名降级方法
   先找参数列表完全一致的方法
   再找无参方法
3. 找到后通过反射调用
4. 找不到或调用失败，抛 RateLimitExceededException
```

适合 fallback 的场景：

```text
读接口
  返回缓存、空列表、友好提示

非核心推荐接口
  返回默认推荐结果

状态查询接口
  返回稍后重试提示
```

不太适合 fallback 的场景：

```text
上传文件
创建资源
修改配置
提交答案
```

因为这些接口通常需要明确成功或失败，不能假装处理成功。

面试表达：

> fallback 不是所有接口都应该配。读接口可以降级返回缓存，写接口我更倾向于直接拒绝，避免用户误以为操作成功。

## 5. RateLimitExceededException 怎么进入统一响应

`RateLimitExceededException`：

```java
public class RateLimitExceededException extends BusinessException
```

固定错误码：

```text
ErrorCode.RATE_LIMIT_EXCEEDED = 8001
```

全局异常处理：

```java
@ExceptionHandler(BusinessException.class)
@ResponseStatus(HttpStatus.OK)
public Result<Void> handleBusinessException(BusinessException e) {
    return Result.error(e.getCode(), e.getMessage());
}
```

最终响应：

```json
{
  "code": 8001,
  "message": "请求过于频繁，请稍后再试",
  "data": null
}
```

HTTP 状态是 200，这是项目统一响应规范。

面试表达：

> 限流异常不是直接返回 429，而是进入项目统一业务异常体系，返回 HTTP 200 + 业务错误码 8001。这样前端只需要按 Result 的 code 处理业务状态。

如果面试官问“为什么不用 HTTP 429”：

> 从 REST 语义上 429 更标准，但这个项目统一约定业务异常 HTTP 200，由 code 区分。这个选择有利于前端统一处理和部分网关兼容。如果是对外开放 API，我会考虑返回真实 429，并在 body 里也保留业务 code。

## 6. Redis 挂了怎么办

当前实现：

```text
NOSCRIPT
  自动重新加载 Lua 脚本并重试

Redis 连接失败/超时/其他异常
  直接向上抛出
```

面试中可以这样回答：

> 当前代码对 Redis 脚本缓存失效做了容错，这是最常见的 Redis 重启后脚本 SHA 丢失问题。但对 Redis 连接失败还没有显式降级策略。后续我会按业务重要性设计两种模式：fail-open 和 fail-closed。

两种策略：

| 策略 | 含义 | 适合场景 |
|---|---|---|
| fail-open | Redis 异常时临时放行 | 更重视可用性，接口成本不太高 |
| fail-closed | Redis 异常时拒绝请求 | 更重视保护后端，比如 AI 高成本接口 |

更合理的项目方案：

```text
高成本 AI 接口
  Redis 异常 -> 返回“服务繁忙”

普通读接口
  Redis 异常 -> 放行或本地限流兜底

增加日志和告警
  Redis 异常不应该静默
```

## 7. IP 维度的安全边界

当前 `getClientIp()` 会读取：

```text
X-Forwarded-For
X-Real-IP
Proxy-Client-IP
WL-Proxy-Client-IP
RemoteAddr
```

风险：

> 如果应用直接暴露给公网，客户端可以伪造 `X-Forwarded-For`。所以生产环境应该由 Nginx/API Gateway 在最外层清理并覆盖这些头，应用只信任网关传入的头。

面试回答：

> 代码层面做了常见代理头兼容，但真正安全要依赖部署架构：外层网关统一设置真实客户端 IP，后端不直接暴露。

## 8. USER 维度的安全边界

当前获取方式：

```text
request attribute userId
X-User-Id header
anonymous
```

风险：

> 如果没有认证过滤器把可信 userId 放到 request attribute，单纯信任 `X-User-Id` 请求头是不安全的。

面试回答：

> USER 维度在组件层已经支持，但生产使用时应该接认证模块，比如 JWT 过滤器解析用户身份后写入 request attribute，而不是直接相信前端传来的 Header。

## 9. 测试怎么讲

项目里有三类相关测试：

### 9.1 注解元数据测试

`RateLimitScriptTest` 验证：

- `@Retention(RUNTIME)`；
- `@Target(METHOD)`；
- `@Repeatable`；
- 默认值；
- 自定义值；
- 多条注解读取。

### 9.2 Redis Lua 集成测试

`RateLimitIntegrationTest`：

- 需要真实 Redis；
- 当前标了 `@Disabled`；
- 验证令牌充足时允许，耗尽时拒绝；
- 验证多规则下任一规则不足即拒绝；
- 验证不同维度独立计数。

面试诚实说法：

> Redis 限流集成测试需要真实 Redis，所以默认禁用，开发时可以启动 Redis 后手动打开运行。注解本身和异常类有普通单元测试。

### 9.3 异常测试

`RateLimitExceededExceptionTest` 验证：

- 默认构造函数错误码 8001；
- 自定义 message；
- cause；
- 继承 `BusinessException`。

## 10. 当前实现的边界与下一步

### 10.1 timeout 字段未生效

下一步：

```text
支持 timeout > 0 时短暂自旋/睡眠重试
或支持排队等待
但要避免阻塞虚拟线程/请求线程过久
```

### 10.2 Lua 返回值不是真正剩余配额

下一步：

```text
如果前端或日志需要展示剩余次数
可以把 Lua return 改成 current_val - permits
拒绝时返回 0
```

### 10.3 requestId 去重能力有限

当前：

```text
每次 around 都生成 UUID
Lua 用 request_id:permits 作为 member
```

它能保证同一个脚本调用里 member 唯一，但如果网络异常后外部重新发起 HTTP 请求，会生成新的 requestId，仍会重复计数。

下一步：

```text
如果需要严格幂等去重，应由客户端或网关传入 requestId/idempotencyKey
切面读取并传给 Lua
```

### 10.4 Redis 异常策略还可以配置化

下一步：

```text
app.ratelimit.redis-failure-strategy = OPEN / CLOSED
针对不同接口或维度配置不同策略
```

### 10.5 USER 维度需要认证模块配合

下一步：

```text
JWT/Session Filter -> request.setAttribute("userId", userId)
RateLimitAspect 只读取可信 attribute
减少对 X-User-Id header 的依赖
```

## 11. 面试收尾

可以这样总结：

> 这个限流模块的核心价值是把高成本接口保护做成了声明式能力。业务 Controller 只写注解，限流维度、窗口、阈值和降级都在注解里表达；切面统一拦截；Redis Lua 保证分布式原子性；异常进入统一 Result 体系。它已经覆盖项目里 AI、文件、RAG、Provider 管理等高风险接口，同时也保留了 timeout、USER 维度和 fallback 等扩展点。
