# 限流注解模块总览怎么讲

## 1. 面试中先讲业务问题 

不要一上来就说“我写了一个注解”。更好的开场是：

> 在这个面试平台里，有些接口天然是高成本接口，比如简历上传会触发文件解析和 AI 分析，知识库查询会触发向量检索和大模型生成，创建面试会话会生成题目，JD 解析也会调用 LLM。如果这些接口被频繁刷新、脚本刷接口，轻则浪费模型调用成本，重则拖垮 Redis、数据库或大模型服务。所以我做了一个声明式限流组件，用 `@RateLimit` 标注 Controller 方法，通过 AOP 拦截和 Redis Lua 滑动窗口实现分布式限流。

一句话：

```text
@RateLimit 不是单纯的 Java 注解，而是系统保护高成本 AI 接口的入口。
```

## 2. 这个模块在系统里的位置

完整链路不是只有 `RateLimit.java`，而是：

```text
Controller 方法
  @RateLimit(...)
        |
        v
RateLimitAspect AOP 环绕拦截
        |
        v
生成限流 Key：ratelimit:{ClassName:MethodName}:dimension[:value]
        |
        v
Redisson evalSha 执行 rate_limit_single.lua
        |
        v
Redis 滑动窗口扣令牌
        |
        v
通过 -> joinPoint.proceed()
拒绝 -> fallback 或 RateLimitExceededException(8001)
        |
        v
GlobalExceptionHandler -> HTTP 200 + Result.error(code, message)
```

面试中可以强调：

> `common.annotation` 只定义了限流规则的声明方式，真正执行在 `common.aspect.RateLimitAspect`，算法在 `resources/scripts/rate_limit_single.lua`，异常在 `RateLimitExceededException`。这几个组合起来才是一套完整的声明式限流方案。

## 3. @RateLimit 注解本身设计了什么

`RateLimit` 是方法级注解：

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
@Repeatable(RateLimit.Container.class)
public @interface RateLimit
```

核心属性：

| 属性          | 含义                  | 当前使用情况         |
| ----------- | ------------------- | -------------- |
| `dimension` | 限流维度：GLOBAL、IP、USER | 已使用            |
| `count`     | 窗口内最大请求数            | 已使用            |
| `interval`  | 时间窗口大小              | 已使用，默认 1       |
| `timeUnit`  | 时间单位                | 已使用，默认 SECONDS |
| `timeout`   | 等待令牌超时时间            | 当前预留，切面没有等待逻辑  |
| `fallback`  | 限流触发时的降级方法名         | 已支持反射调用        |

最常见写法：

```java
@RateLimit(dimension = RateLimit.Dimension.GLOBAL, count = 5)
@RateLimit(dimension = RateLimit.Dimension.IP, count = 5)
public Result<?> uploadAndAnalyze(...) { ... }
```

这表示：

```text
全局每秒最多 5 次
并且每个 IP 每秒最多 5 次
两条规则都通过才放行
任意一条不通过就限流
```

## 4. 为什么要支持 @Repeatable

如果没有可重复注解，一个接口只能配置一条限流规则：

```java
@RateLimit(count = 5)
```

但真实业务通常需要多维度保护：

```text
GLOBAL 维度
  防止整体接口被打爆

IP 维度
  防止单个客户端恶意刷接口

USER 维度
  防止登录用户滥用资源
```

所以 `@RateLimit` 使用 Java 8 的 `@Repeatable`：

```java
@Repeatable(RateLimit.Container.class)
```

切面通过：

```java
method.getAnnotationsByType(RateLimit.class)
```

统一获取单条或多条规则。

面试表达：

> 我没有把全局限流、IP 限流写成两个不同注解，而是用 `@Repeatable` 让同一个注解可重复标注。每条注解代表一个独立规则，切面逐条执行，规则之间是 AND 关系。

## 5. 三种 Dimension 怎么讲

### 5.1 GLOBAL

Key：

```text
ratelimit:{ResumeController:uploadAndAnalyze}:global
```

作用：

> 限制某个接口整体吞吐，比如简历上传全局每秒 5 次，保护后端文件解析、AI 分析和数据库资源。

### 5.2 IP

Key：

```text
ratelimit:{ResumeController:uploadAndAnalyze}:ip:127.0.0.1
```

作用：

> 限制单个客户端来源，避免某个 IP 恶意刷新接口。

IP 获取顺序：

```text
X-Forwarded-For
X-Real-IP
Proxy-Client-IP
WL-Proxy-Client-IP
request.getRemoteAddr()
```

### 5.3 USER

Key：

```text
ratelimit:{SomeController:someMethod}:user:123
```

用户 ID 获取：

```text
request attribute: userId
请求头: X-User-Id
否则: anonymous
```

当前项目里主要使用 GLOBAL 和 IP，USER 维度属于已实现但需要认证体系配合才能更可靠使用。

## 6. 实际业务落点

当前项目中 `@RateLimit` 主要保护这些接口：

| 模块          | 接口类型                    | 为什么要限流            |
| ----------- | ----------------------- | ----------------- |
| 简历模块        | 上传简历、重新分析               | 文件解析 + AI 分析成本高   |
| 模拟面试        | 创建会话、提交答案               | 出题/评估涉及 AI 调用     |
| 知识库         | 查询、流式查询、上传、重新向量化        | RAG 检索、LLM、向量化都较重 |
| 面试技能        | JD 解析                   | JD 解析调用大模型        |
| Provider 管理 | 配置增删改查、连通性测试、ASR/TTS 测试 | 防止管理接口和模型连通性测试被刷  |

面试表达：

> 我不是对所有接口都机械加限流，而是优先加在资源成本高、可被用户频繁触发、或会调用外部 AI 服务的接口上。

## 7. 为什么用 Redis + Lua

如果只在 Java 内存里限流：

```text
单机可以
多实例部署时每个实例各算各的，限流不全局
```

如果用普通 Redis 多条命令：

```text
读当前计数
删除过期记录
判断配额
扣减令牌
设置过期时间
```

多条命令之间可能被其他请求打断，并发下不原子。

所以使用 Lua：

> Redis 执行 Lua 脚本是原子的，脚本内部完成过期令牌回收、配额判断、扣令牌、设置过期时间，避免并发竞争。

## 8. 为什么是滑动窗口

固定窗口的问题：

```text
00:00:59 允许 5 次
00:01:00 又允许 5 次
边界附近 1 秒内可能打出 10 次
```

滑动窗口：

```text
每次请求都看 now - interval 到 now 这段真实时间窗口
过期请求被回收
窗口内数量不超过 count 才放行
```

面试回答：

> 滑动窗口比固定窗口更平滑，能避免窗口边界突刺。这个项目里用 Redis Sorted Set 存每次请求的时间戳，按 score 删除过期记录，再判断当前窗口内是否还有可用令牌。

## 9. 面试推荐 2 分钟回答

如果面试官问：“你这个限流注解怎么实现的？”

可以这样回答：

> 我做的是一个声明式分布式限流组件。业务 Controller 只需要标注 `@RateLimit`，比如简历上传接口同时标注 GLOBAL 和 IP 两条规则。这个注解是方法级注解，运行时保留，并且通过 `@Repeatable` 支持多条规则。
>
> 真正执行限流的是 `RateLimitAspect`。它用 `@Around` 拦截带注解的方法，通过 `method.getAnnotationsByType(RateLimit.class)` 拿到所有规则，然后逐条生成 Redis Key。Key 里用了 Redis Cluster Hash Tag，例如 `ratelimit:{ResumeController:uploadAndAnalyze}:ip:1.2.3.4`，保证同一方法的多个限流 Key 能落到同一个 slot，方便 Lua 原子执行。
>
> 算法层面使用 Redis Lua 脚本实现滑动时间窗口。脚本内部用 String 保存当前可用令牌数，用 Sorted Set 保存窗口内请求记录；每次请求先回收过期记录，再判断令牌是否足够，足够就扣减并写入本次请求，不足就返回 0。切面拿到结果后，所有规则都通过才执行原方法，任一规则不通过就优先调用 fallback，没配置 fallback 就抛 `RateLimitExceededException`，由全局异常处理器返回统一错误码 8001。
>
> 这个设计的价值是业务零侵入、支持多维限流、适合分布式部署，并且对高成本 AI 接口起到保护作用。

## 10. 当前实现需要诚实说明的边界

| 点         | 当前实现                             | 面试中怎么诚实讲                       |
| --------- | -------------------------------- | ------------------------------ |
| `timeout` | 注解字段存在，但切面没有等待令牌逻辑               | 目前是预留扩展字段，当前策略是失败即拒绝           |
| Lua 返回值   | 脚本返回 `1/0`，注释里有“剩余配额”的描述         | 实际语义是是否通过，不是剩余配额               |
| Redis 异常  | `NOSCRIPT` 会重载脚本，其他 Redis 异常直接抛出 | 可后续设计 fail-open/fail-closed 策略 |
| USER 维度   | 支持从 attribute/header 取用户 ID      | 需要认证网关或登录态保证可信                 |
| IP 头      | 支持代理头，但 X-Forwarded-For 可伪造      | 生产应由网关/Nginx 覆盖可信头             |
| fallback  | 支持同参数/无参反射调用                     | fallback 失败后会记录日志并抛限流异常        |

这部分一定要讲清楚，尤其是 `timeout`。不要说“支持等待令牌”，目前代码没有真正等待。
