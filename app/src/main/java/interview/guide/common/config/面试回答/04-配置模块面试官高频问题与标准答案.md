# common/config 面试官高频问题与标准答案

## 1. 你怎么介绍 `common/config` 这个模块？

回答：

> 这是项目的配置和基础设施装配层。它把跨模块共享的配置集中管理，比如简历上传、跨域、对象存储、AI Provider、Embedding、JSON 序列化和 Swagger 文档。简单配置用 `@ConfigurationProperties` 绑定成类型安全对象，需要框架实例的地方用 `@Configuration + @Bean` 注册到 Spring 容器。

## 2. 为什么配置类要放在 common 包？

回答：

> 因为这些配置不是某一个业务模块私有的。比如 CORS、ObjectMapper、S3Client、LLM Provider 都会被多个模块使用。放在 common 下可以避免每个模块重复定义，也让基础设施配置有统一入口。

## 3. `@ConfigurationProperties` 相比 `@Value` 好在哪里？

回答：

> `@Value` 适合少量简单配置，但配置多了会散落在各个 Service。`@ConfigurationProperties` 可以按前缀把一组配置绑定成对象，支持嵌套类、Map、List，也方便校验和测试。比如 `app.ai.providers` 这种多 Provider 配置，用 `@Value` 就很难维护。

## 4. 项目里哪些地方用了 `@ConfigurationProperties`？

回答：

> `AppConfigProperties` 绑定简历上传配置，`CorsProperties` 绑定跨域来源，`StorageConfigProperties` 绑定 RustFS/S3 参数，`LlmProviderProperties` 绑定 AI Provider、Advisor、安全和动态配置路径。

## 5. 为什么不用硬编码 S3 endpoint 和 bucket？

回答：

> endpoint、bucket、accessKey、secretKey 都会随环境变化，而且 accessKey/secretKey 是敏感信息。放到配置里可以通过环境变量覆盖，开发环境用 RustFS/MinIO，生产环境也可以切换到其他 S3 兼容服务。

## 6. `S3Config` 中 `forcePathStyle(true)` 是什么？

回答：

> 它强制使用路径风格访问，比如 `http://localhost:9000/bucket/key`。MinIO、RustFS 这类本地 S3 兼容服务通常更适合路径风格。如果不用它，SDK 可能访问 `http://bucket.localhost:9000/key`，导致 DNS 解析失败。

## 7. `StorageConfigProperties` 和 `S3Config` 的区别是什么？

回答：

> `StorageConfigProperties` 只是配置数据对象，负责承载 endpoint、bucket、密钥等参数；`S3Config` 是配置类，根据这些参数创建 `S3Client` Bean。一个管配置数据，一个管 Bean 装配。

## 8. `S3Config` 和 `FileStorageService` 的区别是什么？

回答：

> `S3Config` 只创建客户端，不处理业务文件。`FileStorageService` 才负责上传、下载、删除、生成文件 key、检查 bucket 等文件存储逻辑。这样配置装配和基础设施服务职责分开。

## 9. CORS 配置解决什么问题？

回答：

> 前端 React/Vite 和后端 Spring Boot 端口不同，浏览器会触发跨域限制。`CorsConfig` 注册 `/api/**` 的跨域规则，允许配置中的前端来源访问后端 API，并支持常见 HTTP 方法、请求头和凭证传递。

## 10. 为什么 CORS 不能直接允许所有来源？

回答：

> 当前开启了 `allowCredentials=true`，支持携带 Cookie 或 Authorization。浏览器规范不允许 `Access-Control-Allow-Origin:*` 和 credentials 同时使用，所以要配置明确的 origins 白名单。安全上也不建议生产环境全放开。

## 11. WebSocket 的跨域是不是也由 `CorsConfig` 管？

回答：

> 不是完全由它管。`CorsConfig` 注册的是 `/api/**` 的 HTTP 跨域。语音面试 WebSocket 路径是 `/ws/voice-interview/{sessionId}`，它在 `WebSocketConfig` 里单独配置 `setAllowedOrigins`，但复用了同一个 `CorsProperties`。

## 12. `LlmProviderProperties` 解决了什么问题？

回答：

> 它把多模型配置集中起来，包括默认 Provider、默认 Embedding Provider、各厂商 baseUrl/apiKey/model、Embedding 模型、Advisor 开关、安全配置和运行时配置路径。业务模块不用关心这些细节，只通过 `LlmProviderRegistry` 获取 ChatClient 或 EmbeddingModel。

## 13. 为什么 Provider 要设计成 Map？

回答：

> 因为 Provider 数量是可扩展的。用 `Map<String, ProviderConfig>` 后，key 就是 providerId，比如 dashscope、glm、deepseek。新增 Provider 时只要加配置块，不需要改 Java 字段结构。

## 14. Chat 模型和 Embedding 模型为什么要分开？

回答：

> Chat 模型负责生成文本，Embedding 模型负责生成向量。RAG 场景里必须用 Embedding 模型写入 pgvector，再用 Chat 模型生成回答。两者模型名、接口和输出维度都不同，所以配置里要分开 `model` 和 `embeddingModel`。

## 15. `LlmEmbeddingConfig` 为什么要用代理 Bean？

回答：

> Spring AI 的 VectorStore 需要注入一个 `EmbeddingModel` Bean，但项目的默认 Embedding Provider 可能动态变化。代理 Bean 每次调用都委托给 `LlmProviderRegistry.getDefaultEmbeddingModel()`，既满足 Spring 注入，又保留动态 Provider 能力。

## 16. 为什么要排除 Spring AI 的 OpenAI 自动配置？

回答：

> Spring AI 默认自动配置更适合单 Provider 项目。这个项目需要支持多个 OpenAI-compatible 厂商，所以由 `LlmProviderRegistry` 自己创建 ChatClient 和 EmbeddingModel。排除默认自动配置可以避免 Bean 冲突和错误的单 Provider 绑定。

## 17. `AdvisorConfig` 是干什么的？

回答：

> 它控制 Spring AI Advisor 链，比如工具调用、对话记忆、日志、安全防护和 PromptSanitizer。这样这些能力可以通过配置开启关闭，而不是写死在代码里。

## 18. 为什么 MessageChatMemory 默认关闭？

回答：

> 面试平台会有很多用户和会话，如果默认开启全局记忆，容易出现会话串扰。记忆能力应该按业务会话显式设计，而不是全局默认打开。

## 19. API Key 怎么保证安全？

回答：

> 当前配置通过环境变量占位符注入 API Key，不直接写死在代码里。Provider 管理模块还支持加密密钥配置，数据库模式下可以对 API Key 加密存储。生产上还可以结合密钥管理系统或容器 Secret。

## 20. `JacksonConfig` 有什么用？

回答：

> 它提供全局 `ObjectMapper` Bean，让系统里需要 JSON 处理的地方使用统一对象映射器。这样后续如果要统一时间格式、枚举策略、空值策略，可以集中配置。

## 21. 当前 `JacksonConfig` 有什么不足？

回答：

> 当前实现比较基础，是直接 `new ObjectMapper()`。另外注释里提到 tools.jackson，但实际 import 是 `com.fasterxml.jackson.databind.ObjectMapper`，注释需要修正。生产上如果有 LocalDateTime 等时间字段，应该用 `Jackson2ObjectMapperBuilder` 或显式注册 JavaTimeModule。

## 22. `OpenApiConfig` 的作用是什么？

回答：

> 它注册 OpenAPI 元信息，比如标题、描述和版本。真正的接口路径和参数由 SpringDoc 扫描 Controller 生成。这个配置主要服务于 Swagger UI，让前后端联调更方便。

## 23. Swagger 生产环境应该怎么处理？

回答：

> 开发和测试环境可以开放；生产环境不建议裸露 Swagger。可以关闭、加权限，或者只允许内网访问。同时可以补充 Authorization Header 的 security scheme，方便调试受保护接口。

## 24. 你们的配置支持 `.env` 吗？

回答：

> 当前配置大量使用环境变量占位符，比如 `${AI_BAILIAN_API_KEY}`、`${APP_STORAGE_ENDPOINT}`。README 和项目规范提到 bootRun 会读取根目录 `.env`，Provider 管理模块也有 `config-env-path` 用于运行时写入 env 文件。但仅从 `common/config` 代码看，不能把 `.env` 加载机制说成全部由这里完成，它可能由启动脚本或其他配置负责。

## 25. 配置错误如何快速发现？

回答：

> 当前很多错误会在实际使用时发现，比如 S3 连接失败、Provider API Key 缺失、Embedding 维度不一致。更理想的是给 Properties 加 `@Validated` 和 `@NotBlank`，再加启动期配置一致性检查，让关键错误在应用启动阶段失败。

## 26. 如何处理不同环境的配置差异？

回答：

> 默认值适合本地开发，敏感值和环境差异通过环境变量覆盖。比如本地 storage endpoint 可以是 localhost RustFS，生产可以改成真实对象存储地址；CORS 本地是 Vite 地址，生产是正式前端域名。

## 27. 如果新增一个上传文件类型，要改哪里？

回答：

> 改 `app.resume.allowed-types` 配置即可。`ResumeUploadService` 读取 `AppConfigProperties` 做校验，不需要改上传服务代码。

## 28. 如果新增一个 LLM Provider，要改哪里？

回答：

> 如果是 OpenAI-compatible API，通常只需要新增 `app.ai.providers.{providerId}` 配置，填 baseUrl、apiKey、model、是否支持 embedding 等信息。业务调用通过 providerId 路由，不需要改每个业务模块。

## 29. 配置模块体现了哪些设计原则？

回答：

> 第一是配置外置化，避免硬编码。第二是类型安全绑定，避免散落 `@Value`。第三是职责分离，Properties 只承载配置，Config 类负责装配 Bean，业务 Service 负责业务逻辑。第四是可扩展性，多 Provider、多环境、多存储后端都可以通过配置演进。

## 30. 这个模块的不足和下一步怎么说？

回答：

> 我会补三类优化。第一，给 Properties 加 `@Validated` 和字段约束，实现配置 fail-fast。第二，把 CORS origins 改成 List，减少字符串 split 的边界问题。第三，完善 Jackson 和 OpenAPI 的生产配置，比如 JavaTimeModule、统一时间格式、Swagger 鉴权 scheme 和生产环境访问控制。

## 31. 最推荐背诵的一段话

> `common/config` 是项目的配置治理层。它用 `@ConfigurationProperties` 把 YAML 和环境变量映射成类型安全对象，用 `@Configuration + @Bean` 注册 S3Client、CorsFilter、EmbeddingModel、ObjectMapper 和 OpenAPI 等基础设施 Bean。这样业务层不用硬编码配置，也不用自己创建底层客户端。尤其是 AI Provider 配置，通过 Map 支持多厂商、多模型和 Embedding 能力扩展，后续切换模型或环境基本可以通过配置完成。
