同源策略是浏览器最核心、最基础的安全机制。它的设计初衷很简单：**一个来源的脚本，在没有明确授权的情况下，不能去读取另一个来源的敏感数据**。你现在遇到的 `http://localhost:5173` 无法直接请求 `http://localhost:8080/api/...`，正是因为这一策略在起作用。下面我从几个层面把它讲透。

---

## 一、什么叫“同源”？

一个“源”（origin）由三部分组成：

- **协议**（protocol）：如 `http` 或 `https`
- **域名**（host）：如 `localhost` 或 `www.example.com`
- **端口**（port）：如 `5173`、`8080`，如果没显式写出，HTTP 默认 `80`，HTTPS 默认 `443`

**当且仅当协议、域名、端口号全部完全一致时，两个 URL 才属于同源。**  
任何一个不同，就是“跨源”（cross-origin）。

举例说明，假设我们正处在 `http://localhost:5173` 这个页面：

| 被访问的 URL                        | 是否同源？ | 原因                           |
|-----------------------------------|----------|------------------------------|
| `http://localhost:5173/user`      | ✅ 同源    | 协议、域名、端口完全相同                  |
| `http://localhost:8080/api/data`  | ❌ 跨源    | **端口不同**（5173 vs 8080）        |
| `https://localhost:5173/api/data` | ❌ 跨源    | **协议不同**（http vs https）       |
| `http://127.0.0.1:5173/api/data`  | ❌ 跨源    | **域名不同**（localhost vs 127.0.0.1） |
| `http://example.com:5173`         | ❌ 跨源    | **域名不同**                      |

因此你遇到的情况：前端页面运行在 `http://localhost:5173`，后端接口在 `http://localhost:8080`，虽然都在本机，但因为**端口不同**，浏览器判定它们不同源，从而触发了跨域限制。

---

## 二、同源策略到底限制了什么？

同源策略并非阻止所有跨域“请求”，而是严格限制**跨源读取**。具体限制三类行为：

### 1. DOM 访问受限
不同源的页面不能通过脚本互相操作 DOM。  
比如你在 `a.com` 中用 `<iframe>` 嵌入了 `b.com`，那么 `a.com` 的 JavaScript **无法读取**这个 iframe 里的 `document` 内容，除非 `b.com` 显式通过某些方式允许。

### 2. 数据存储隔离
Cookie、LocalStorage、IndexedDB 等浏览器存储，都以源为边界。  
`http://localhost:5173` 的脚本无法读取 `http://localhost:8080` 的 Cookie 或 LocalStorage。即使是子域名之间（如 `a.example.com` 和 `b.example.com`）默认也互相隔离。

### 3. 网络请求的响应读取受限（你遇到的核心问题）
这是最常见、影响最大的限制：  
**通过 JavaScript 发出的 HTTP 请求（如 `XMLHttpRequest`、`fetch`、axios），默认不能读取不同源的响应内容。**

注意一个关键细节：请求其实**可能已经发出去了**，服务器也正常处理并返回了数据，但浏览器会拦截掉响应，不交给你的前端代码，并在控制台抛出类似：
```
Access to fetch at 'http://localhost:8080/api/...' from origin 'http://localhost:5173' has been blocked by CORS policy...
```
的错误。

某些“简单请求”甚至不会被拦截发出，而复杂请求会先发一个 **预检请求（preflight，OPTIONS）**，只有在预检通过后才会发出真正请求。

**同源策略并不阻止以下这些跨域行为**（它们都不涉及读取跨域资源的响应内容）：
- 用 `<script>`、`<img>`、`<link>`、`<video>` 等标签加载跨域资源（但不能用 JS 读其中内容）。
- 表单提交（`<form>` 的 action 指向不同源）。
- 重定向。

---

## 三、为什么要有同源策略？——安全上的必要性

如果没有同源策略，Web 安全会彻底崩塌。考虑一个典型攻击场景：

1. 你登录了网上银行 `https://bank.com`，浏览器保存了该域的认证 Cookie。
2. 你不小心打开了一个恶意网站 `https://evil.com`。
3. `evil.com` 里的脚本偷偷执行：
   ```js
   fetch('https://bank.com/account/transfer', {
     method: 'POST',
     body: 'to=hacker&amount=10000'
   });
   ```
4. 由于浏览器在发送请求时会自动带上 `bank.com` 的 Cookie，这笔转账请求就会被银行服务器接受并执行。
5. **但更危险的是**，如果没有同源策略，`evil.com` 还可以直接 `fetch('https://bank.com/account/balance')` 然后读取到你账户余额的 JSON 数据，因为请求自带了 Cookie，服务器会返回正常响应，而恶意脚本可以读取并窃取这些敏感信息。

同源策略直接阻止了第5步：**跨域脚本即使能发出请求（第3步），也无法读取响应内容**，从而保护了用户数据。至于第4步那种单纯“发请求但不需要读响应”的攻击，就需要靠 **CSRF 防御**（比如同步令牌、SameSite Cookie 等）来补充，同源策略主要管住“看”这一关。

## 四、开发中如何解决跨域问题（以 localhost:5173 → localhost:8080 为例）

虽然同源策略是必要的安全防线，但在开发时前后端分离部署在不同端口是常态，必须用合理的方式“绕过”它。常见方案有三种：

### 1. 后端设置 CORS 头（真正的标准解决方案）
后端在响应中添加 `Access-Control-Allow-Origin` 等头，明确告诉浏览器：“我允许某个源来读取我的响应”。

例如在 Spring Boot 中可以：
```java
@CrossOrigin(origins = "http://localhost:5173")
```
或者全局配置。其他后端框架类似。对于需要携带 Cookie 的请求，还需要配合 `Access-Control-Allow-Credentials: true`，且 `Allow-Origin` 不能是 `*`。

CORS 会产生额外请求（预检 `OPTIONS`），后端需要正确响应。

### 2. 开发服务器代理（最推荐的前端开发方案）
前端开发工具（Vite、Webpack Dev Server 等）都提供了代理功能。**原理是让浏览器认为所有请求都发给同源的前端开发服务器（比如 `http://localhost:5173`），由这个服务器转发到后端，从而完美避开浏览器的同源策略。**

在 Vite 项目 (`vite.config.js`) 中配置代理非常简洁：
```js
export default {
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,
        // 可选：重写路径
        // rewrite: (path) => path.replace(/^\/api/, '')
      }
    }
  }
}
```
配置后，前端代码只需请求 `fetch('/api/...')`，实际请求会被 Vite 的 dev server 转发到 `http://localhost:8080/api/...`。浏览器从始至终只与 `localhost:5173` 通信，没有跨域。这是本地开发最舒服的实践。

### 3. JSONP（仅限历史遗留项目）
利用 `<script>` 标签不受同源策略限制的特点，只能发 GET 请求，且需要后端配合返回函数调用格式。现在基本不推荐使用。

### 4. 生产环境方案
部署时，通常会让前后端同源，例如通过 Nginx 将 `/api` 代理到后端服务，前端静态文件和后端 API 共享同一个域名和端口，自然不存在跨域问题。

---

## 五、总结

- **同源策略** = 协议 + 域名 + 端口，三者必须完全一致。
- 它禁止不同源页面之间通过 JS 读取 DOM、存储和网络响应，核心是**保护用户数据不被恶意网站窃取**。
- `localhost:5173` 和 `localhost:8080` 端口不同，因此不同源，前端直接 `fetch` 后端会被浏览器拦截。
- 开发阶段的最佳实践是**利用前端开发服务器的代理功能**，让浏览器认为请求都是发给自己的，从而绕过策略。
- 部署后可通过反向代理或 CORS 头正常通信。

理解了同源策略，你就掌握了 Web 安全的第一块基石，也就能从容应对所有“跨域报错”了。
