# 面试官高频追问与标准答案

## 1. `RateLimitAspect` 是干什么的？

答：

> 它是 `@RateLimit` 注解的运行时执行器。Controller 方法上声明限流规则，`RateLimitAspect` 用 AOP 在方法执行前拦截请求，读取规则、生成 Redis Key、执行 Lua 脚本判断是否超限。通过则执行原方法，不通过则调用 fallback 或抛 `RateLimitExceededException`。

## 2. 为什么限流逻辑要用 AOP？

答：

> 限流是横切能力，不应该写进每个 Controller 方法里。AOP 可以围绕方法执行，直接读取方法注解、方法参数和目标类，也方便支持 fallback。这样业务代码只声明规则，不关心 Redis 和限流算法。

## 3. 为什么不是用 Spring MVC Interceptor？

答：

> Interceptor 更偏 HTTP 请求层，适合按 URL 做统一拦截。这里的规则是方法级注解，而且要支持可重复注解、读取方法参数、查找同类 fallback 方法，所以 AOP 更贴合。

## 4. `@Around` 切点为什么要匹配 `RateLimit.Container`？

答：

> 因为 `@RateLimit` 支持 `@Repeatable`。一个方法上有多个 `@RateLimit` 时，编译器底层会生成 `RateLimit.Container`。切点同时匹配单注解和容器注解，才能覆盖单维和多维限流。

## 5. `around` 方法的核心步骤是什么？

答：

> 先从 `joinPoint` 获取方法签名，拿到类名和方法名；再用 `method.getAnnotationsByType(RateLimit.class)` 获取所有规则；然后为本次请求生成时间戳和 requestId；接着逐条规则生成 Key 并执行 Lua；所有规则通过才 `joinPoint.proceed()`，任一规则失败就进入限流处理。

## 6. 多条规则之间是什么关系？

答：

> AND 关系。全部通过才放行，任意一条不通过就拒绝。比如接口全局配额还有，但当前 IP 配额没了，也应该拒绝。

## 7. 为什么要用 Redis？

答：

> 因为项目可能多实例部署，本地内存限流只能限制单个 JVM。Redis 是共享状态，所有应用实例都能访问同一份限流数据，所以可以做分布式限流。

## 8. 为什么要用 Lua 脚本？

答：

> 限流判断不是单条 Redis 命令，它包含过期请求回收、令牌判断、扣减、记录请求、设置过期时间等步骤。Lua 能把这些步骤放在 Redis 内原子执行，避免并发下超发。

## 9. 这个 Lua 是什么算法？

答：

> 是滑动时间窗口。脚本用 Sorted Set 记录窗口内每次请求的时间戳，每次请求到来时先删除窗口外的过期记录并回收令牌，再判断当前窗口内是否还有令牌。相比固定窗口，滑动窗口能避免窗口边界突刺。

## 10. Lua 里为什么有两个 key？

答：

> `:value` 是 String，保存当前可用令牌数；`:permits` 是 Sorted Set，保存窗口内请求记录，score 是时间戳。`value` 方便快速扣减和回收，`permits` 用于按时间滑动窗口。

## 11. Redis Key 为什么设计成 `ratelimit:{ClassName:MethodName}:dimension`？

答：

> `ClassName:MethodName` 表示方法级限流作用域，dimension 表示 GLOBAL、IP、USER 不同维度独立计数。花括号是 Redis Cluster Hash Tag，保证派生出的 `:value` 和 `:permits` 在同一个 slot，Lua 脚本可以正常执行。

## 12. `evalSha` 比 `eval` 好在哪里？

答：

> `eval` 每次都要传完整 Lua 脚本，`evalSha` 只传脚本 SHA1。应用启动时通过 `scriptLoad` 把脚本加载到 Redis，后续执行只传 SHA，减少网络传输和解析开销。

## 13. Redis 报 `NOSCRIPT` 怎么处理？

答：

> Redis 重启或执行 `SCRIPT FLUSH` 后，之前的 SHA1 会失效。代码捕获包含 `NOSCRIPT` 的 RedisException，重新 `scriptLoad` 加载脚本，再用新的 SHA 重试一次。

## 14. Redis 连接失败怎么办？

答：

> 当前代码只对 `NOSCRIPT` 做显式容错，其他 Redis 异常会向上抛出。这是现有边界。后续可以做成可配置策略：高成本 AI 接口用 fail-closed，Redis 不可用时拒绝；普通读接口可以 fail-open 或本地限流兜底。

## 15. Lua 返回的是剩余配额吗？

答：

> 不是。当前 Lua 实际返回 `1` 表示通过，`0` 表示拒绝。代码注释里有“剩余配额”的说法，这是早期设计遗留。面试里应该按真实实现讲，如果需要剩余配额，可以改 Lua 返回 `current_val - permits`。

## 16. `requestId` 有什么用？

答：

> 它作为 Sorted Set member 的一部分，让每次请求记录唯一，避免同一时间戳下 member 冲突。当前 requestId 是切面内部生成的 UUID，不能实现跨 HTTP 重试的严格幂等；如果需要，要从请求头读取稳定的 Idempotency-Key。

## 17. `generateKey` 如何区分 GLOBAL/IP/USER？

答：

> GLOBAL 直接用 `:global`；IP 会追加 `getClientIp()` 取到的客户端 IP；USER 会追加 `getCurrentUserId()` 取到的用户 ID。这样三个维度是独立 Redis Key，互不影响。

## 18. IP 是怎么获取的？

答：

> 代码依次读取 `X-Forwarded-For`、`X-Real-IP`、`Proxy-Client-IP`、`WL-Proxy-Client-IP`，最后回退到 `request.getRemoteAddr()`。如果 `X-Forwarded-For` 有多个 IP，取第一个。

## 19. IP Header 会不会被伪造？

答：

> 会。所以生产上应该由 Nginx 或 API Gateway 覆盖这些 Header，后端只信任网关传来的真实 IP，不能让应用直接暴露公网并信任客户端随便传的 `X-Forwarded-For`。

## 20. USER 维度现在安全吗？

答：

> 组件支持 USER 维度，会先读 request attribute `userId`，再读 `X-User-Id` Header。但真正安全要靠认证过滤器把可信 userId 放到 attribute。只信任 Header 不安全，所以当前项目主要用 GLOBAL 和 IP。

## 21. 限流触发后怎么处理？

答：

> 切面进入 `handleRateLimitExceeded`。如果注解配置了 fallback，就反射查找同类方法，优先找参数列表一致的，再找无参的。找到就调用；找不到或调用失败，就抛 `RateLimitExceededException`。

## 22. fallback 为什么放在同一个类里？

答：

> 当前实现用 `joinPoint.getTarget().getClass()` 查找 fallback，同类方法最简单直接，也便于和接口放在一起维护。后续如果降级逻辑复杂，可以支持指定 Bean 或抽成降级服务。

## 23. fallback 适合哪些接口？

答：

> 适合读接口，比如返回缓存、默认值或友好提示。不适合上传、创建、删除、修改配置这类写接口，因为这些接口需要明确成功或失败，降级返回成功会造成数据状态误解。

## 24. fallback 方法签名有什么要求？

答：

> 当前支持两种：参数列表和原方法完全一致，或者无参。返回值需要和原方法兼容，但代码目前没有启动时校验，写错会运行时出问题。后续可以增加校验。

## 25. `RateLimitExceededException` 如何返回前端？

答：

> 它继承 `BusinessException`，错误码是 `RATE_LIMIT_EXCEEDED(8001)`。全局异常处理器捕获 `BusinessException` 后返回统一 `Result.error(code, message)`，项目约定业务异常 HTTP 状态仍是 200。

## 26. 为什么不返回 HTTP 429？

答：

> HTTP 429 语义上更标准，但本项目统一业务异常走 HTTP 200 + code，前端处理更一致。如果是对外开放 API，可以考虑返回真实 429，同时 body 里保留业务 code。

## 27. `timeout` 字段现在有没有在切面里用？

答：

> 没有。`timeout` 在 `@RateLimit` 注解里是预留字段，当前 `RateLimitAspect` 没有等待令牌的逻辑，配额不足就立即拒绝或降级。这个点要诚实说明。

## 28. 当前实现有哪些可以优化？

答：

> 第一，修正 Lua 返回值注释，或者真的返回剩余配额。第二，实现或删除 `timeout` 字段。第三，Redis 故障策略配置化，支持 fail-open/fail-closed。第四，USER 维度只信任认证过滤器写入的 userId。第五，支持 SpEL 自定义 key，把 knowledgeBaseId、sessionId 等业务参数纳入限流粒度。第六，多维限流可以合并成一次 Lua 调用，减少 Redis 往返。

## 29. 这段代码最体现工程能力的点是什么？

答：

> 它把限流做成了一个完整的基础设施能力：AOP 零侵入拦截、可重复注解多维规则、Redis Lua 原子滑动窗口、Redis Cluster Hash Tag、`evalSha` 性能优化、`NOSCRIPT` 容错、fallback 降级和统一业务异常返回。

## 30. 一句话收尾

答：

> `RateLimitAspect` 的价值是把“高成本接口保护”从业务代码中抽离出来，用 AOP + Redis Lua 做成分布式、声明式、可复用的限流执行层。
