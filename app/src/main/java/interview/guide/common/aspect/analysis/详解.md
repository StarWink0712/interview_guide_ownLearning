## 二、架构设计分析

### 2.1 设计模式

✅ **切面-oriented Programming (AOP)**：通过 `@Around` 通知拦截带注解的方法，实现横切关注点分离。

✅ **可重复注解模式**：使用 `@Repeatable` 支持同一方法多个限流维度。

✅ **模板方法模式**：Lua 脚本封装滑动窗口算法核心逻辑，Java 侧负责参数组装和结果处理。

### 2.2 Redis Key 设计

```
ratelimit:{ClassName:MethodName}:dimension[:具体值]
```

**优点**：

- 使用 Hash Tag `{ClassName:MethodName}` 确保同一方法的多个限流 Key 落在同一 Redis Slot，便于集群部署。
- 维度分离（GLOBAL/IP/USER）支持细粒度限流策略。

## 三、关键实现逻辑分析

### 3.1 滑动时间窗口算法（Lua 脚本）

```
关键步骤：
1. 获取当前可用令牌，不存在则初始化为 max_tokens
2. 通过 ZRANGEBYSCORE 回收过期的请求记录
3. 检查可用令牌是否足够
4. 扣减令牌并记录本次请求（ZADD 到有序集合）
5. 设置过期时间为窗口的 2 倍
```

### 3.2 执行流程

```
@Around 拦截
    ↓
提取类名+方法名
    ↓
获取所有 @RateLimit 注解
    ↓
逐条执行限流规则
    ↓
任一规则失败 → handleRateLimitExceeded()
    ↓
全部通过 → joinPoint.proceed()
```

## 四、潜在问题与风险

### 🔴 严重问题

#### 1. **Lua 脚本返回值与 Java 侧预期不匹配**

**位置**：[rate\_limit\_single.lua#L60](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/resources/scripts/rate_limit_single.lua#L60)

Lua 脚本始终返回 `1`（成功）或 `0`（失败），但 [RateLimitAspect.java#L125](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/aspect/RateLimitAspect.java#L125) 注释声称返回 "剩余配额"：

```java
// 执行 Redis Lua 限流脚本，返回剩余配额
Long result = executeRateLimitScript(key, nowMs, requestId, intervalMs, rule.count());
```

**影响**：

- `result` 始终为 `0` 或 `1`，无法获取实际剩余配额
- 降级策略仅在 `result == 0` 时触发，逻辑上可行但语义不清晰

**建议**：修改 Lua 脚本返回 `current_val - permits`，让 Java 侧准确判断配额状态。

#### 2. **降级方法异常被静默吞没**

**位置**：[RateLimitAspect.java#L268-270](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/aspect/RateLimitAspect.java#L268-L270)

```java
} catch (Exception e) {
    log.error("降级方法执行失败: {}", rateLimit.fallback(), e);
}
```

**问题**：降级方法执行失败后，代码继续执行抛出通用的 `RateLimitExceededException`，原始异常被丢失。

**建议**：

```java
if (fallbackMethod != null) {
    try {
        return fallbackMethod.invoke(...);
    } catch (InvocationTargetException e) {
        throw (Throwable) e.getCause();  // 抛出降级方法的原始异常
    }
}
```

### 🟡 中等风险

#### 3. **IP 伪造风险**

**位置**：[RateLimitAspect.java#L322-356](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/aspect/RateLimitAspect.java#L322-L356)

`X-Forwarded-For` 头部可被客户端任意伪造，攻击者可绕过 IP 限流。

**缓解措施**：

- 生产环境由 Nginx 在最外层覆盖所有代理头部
- 建议添加配置项控制是否信任代理头部

#### 4. **反射调用降级方法的参数传递**

**位置**：[RateLimitAspect.java#L262-266](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/aspect/RateLimitAspect.java#L262-L266)

```java
if (fallbackMethod.getParameterCount() > 0) {
    return fallbackMethod.invoke(joinPoint.getTarget(), joinPoint.getArgs());
}
```

**问题**：

- 未检查降级方法参数类型是否与原始方法兼容
- 可能抛出 `IllegalArgumentException`

#### 5. **每次请求生成 UUID**

**位置**：[RateLimitAspect.java#L115](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/aspect/RateLimitAspect.java#L115)

```java
String requestId = UUID.randomUUID().toString();
```

**影响**：高并发场景下 UUID 生成有一定性能开销。

**优化**：可考虑使用 `ThreadLocalRandom` 或更轻量的 ID 生成策略。

### 🟢 轻微问题

#### 6. **缺少 Redis 连接异常处理**

`executeRateLimitScript` 方法仅处理 `NOSCRIPT` 异常，Redis 连接超时等异常会直接向上抛出，可能导致服务不可用。

#### 7. **convertToLong 异常处理过于宽松**

**位置**：[RateLimitAspect.java#L216-230](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/aspect/RateLimitAspect.java#L216-L230)

解析失败返回 `null`，会被误判为限流触发，影响可用性。

#### 8. **getClientIp() 逻辑可简化**

**位置**：[RateLimitAspect.java#L332-348](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/aspect/RateLimitAspect.java#L332-L348)

## 五、优化建议

### 5.1 Lua 脚本优化

| 优化项  | 当前实现     | 建议改进         |
| ---- | -------- | ------------ |
| 返回值  | 返回 0/1   | 返回剩余配额，便于监控  |
| 过期清理 | 每次调用遍历清理 | 可考虑惰性清理或后台任务 |
| 错误处理 | 无        | 添加异常情况日志     |

### 5.2 Java 侧优化

1. **添加配置化**：限流 Key 前缀、超时时间等可通过 `@ConfigurationProperties` 配置。
2. **增加监控指标**：使用 Micrometer 暴露限流触发次数、当前配额等指标。
3. **批量 Key 执行**：多维度限流可考虑 Pipeline 批量执行，减少网络往返。
4. **熔断机制**：Redis 不可用时提供可配置的降级策略（放行/拒绝）。

### 5.3 安全性增强

1. 验证降级方法权限（`setAccessible` 可能暴露私有方法）
2. 添加限流规则来源校验，防止恶意配置
3. IP 限流增加 GeoIP 校验，识别异常 IP 来源
