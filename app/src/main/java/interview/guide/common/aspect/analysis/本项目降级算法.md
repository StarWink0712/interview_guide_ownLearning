 该项目并没有配置降级算法，所以后续需要自己补充。

## `handleRateLimitExceeded`（第 251-276 行）

限流触发后的处理入口，分两级：**优先降级 → 兜底抛异常**。

```java
if (rateLimit.fallback() != null && !rateLimit.fallback().isEmpty()) {
```

先判断 `@RateLimit` 注解的 `fallback` 属性是否配置了降级方法名。没配置或为空字符串，直接跳到抛异常。

```java
Method fallbackMethod = findFallbackMethod(joinPoint, rateLimit.fallback());
if (fallbackMethod != null) {
    if (fallbackMethod.getParameterCount() > 0) {
        return fallbackMethod.invoke(joinPoint.getTarget(), joinPoint.getArgs());
    } else {
        return fallbackMethod.invoke(joinPoint.getTarget());
    }
}
```

找到降级方法后，分两种情况调用：

| 降级方法类型         | 调用方式                   | 场景举例          |
| -------------- | ---------------------- | ------------- |
| 带参（参数列表和原方法一致） | `invoke(target, args)` | 原方法参数直接传给降级方法 |
| 无参             | `invoke(target)`       | 返回一个固定兜底结果    |

`invoke` 的返回值直接作为原方法的结果返回，对调用方完全透明——前端不知道发生了限流降级。

```java
} catch (Exception e) {
    log.error("降级方法执行失败: {}", rateLimit.fallback(), e);
}
```

降级方法内部出错时，不用它的结果，继续往下走到抛异常。降级是"尽力而为"，不是"必须成功"。

```java
throw new RateLimitExceededException("请求过于频繁，请稍后再试");
```

最终兜底。这个异常会被全局异常处理器 `GlobalExceptionHandler` 捕获，统一返回 `Result.error(8001, "请求过于频繁，请稍后再试")`。

***

## `findFallbackMethod`（第 283-303 行）

用反射在**原方法所在的 Controller 类**中查找降级方法，匹配优先级：**参数一致 → 无参 → 找不到返回 null**。

```java
Class<?> targetClass = joinPoint.getTarget().getClass();
Class<?>[] parameterTypes = signature.getParameterTypes();
```

获取目标类和原方法的参数类型列表。

```java
try {
    Method method = targetClass.getDeclaredMethod(fallbackName, parameterTypes);
    method.setAccessible(true);
    return method;
```

第一优先级：找一个**方法名相同、参数类型列表完全一致**的方法。如果 Controller 这样写：

```java
@RateLimit(dimension = GLOBAL, count = 10, fallback = "uploadFallback")
public Result<UploadResponse> upload(UploadRequest req) { ... }

// 参数列表一致（UploadRequest），优先匹配这个
public Result<UploadResponse> uploadFallback(UploadRequest req) {
    return Result.error("上传请求过多，请稍后再试");
}
```

```java
} catch (NoSuchMethodException e) {
    try {
        Method method = targetClass.getDeclaredMethod(fallbackName);
        method.setAccessible(true);
        return method;
```

第二优先级：找不到参数一致的，退而求其次找**无参方法**：

```java
// 无参兜底
public Result<UploadResponse> uploadFallback() {
    return Result.error("服务繁忙");
}
```

```java
} catch (NoSuchMethodException ex) {
    log.warn("未找到降级方法: {}.{} (需无参或参数列表一致)", ...);
    return null;
```

都找不到返回 null，调用的上层 `handleRateLimitExceeded` 会跳过降级直接抛异常。

## 完整决策树

```
限流触发
    │
    ▼
 fallback 属性是否配置？
    │
   否 ──► throw RateLimitExceededException
    │
   是 ──► findFallbackMethod()
          │
          ├─ 找到参数一致的方法 → invoke(target, args) → 返回降级结果
          ├─ 找到无参方法 → invoke(target) → 返回降级结果
          └─ 找不到 / invoke 报错 → throw RateLimitExceededException
```

***

## 使用示例

```java
@RateLimit(dimension = IP, count = 3, fallback = "uploadFallback")
public Result<UploadResponse> uploadResume(UploadRequest req) {
    // 正常上传逻辑
}

// 降级方法：参数列表和原方法一致，可以拿到请求参数打日志
public Result<UploadResponse> uploadFallback(UploadRequest req) {
    log.warn("上传限流降级: fileName={}", req.fileName());
    return Result.error(ErrorCode.RATE_LIMIT_EXCEEDED, "上传请求过多，请{0}秒后重试");
}
```

当该 IP 超过 3 次/秒，前端依然收到 200 的 JSON 响应，里面是 `Result.error`，而不是抽象的 500 或连接被拒，用户体验更好。
