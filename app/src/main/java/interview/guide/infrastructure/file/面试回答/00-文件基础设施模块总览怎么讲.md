# infrastructure/file 文件基础设施模块总览怎么讲

## 1. 一句话定位

`infrastructure/file` 是项目里的通用文件基础设施层，负责把上层业务上传的文件变成“可校验、可去重、可解析、可存储、可重新读取”的稳定资源。

面试中可以这样开场：

> 这个模块不是某一个业务的文件上传逻辑，而是简历模块和知识库模块共用的文件处理底座。上层业务只关心“上传简历”或“上传知识库”，底层统一处理文件大小校验、MIME 类型检测、SHA-256 去重、Apache Tika 文本解析、文本清洗、RustFS/S3 对象存储和后续下载解析。

## 2. 为什么放在 infrastructure

简历和知识库都有相似的文件处理需求：

| 业务场景 | 共性能力 |
| --- | --- |
| 简历上传 | 校验文件、检测类型、计算 hash、解析文本、上传 RustFS、保存 fileKey |
| 知识库上传 | 校验文件、检测类型、计算 hash、解析文本、上传 RustFS、异步向量化 |
| 重新分析/重新向量化 | 从 RustFS 下载原文件，再用 Tika 重新解析文本 |
| 删除资源 | 删除数据库记录前后，需要删除对象存储中的文件 |

如果这些能力都写在 `resume` 和 `knowledgebase` 模块里，会出现大量重复代码，也会让文件解析策略、存储 key 规则、错误处理和清洗规则不一致。

所以这里采用的分层是：

```text
业务模块
  ResumeUploadService / KnowledgeBaseUploadService
        |
        v
模块适配层
  ResumeParseService / KnowledgeBaseParseService
        |
        v
infrastructure/file
  FileValidationService
  ContentTypeDetectionService
  FileHashService
  DocumentParseService
  TextCleaningService
  FileStorageService
```

面试表达：

> 我把文件处理抽到基础设施层，是为了让业务层只做编排和状态流转，不直接关心 Tika、S3 SDK、MIME 检测、hash 算法这些技术细节。这样简历和知识库能复用同一套文件能力，后续换对象存储或调整解析策略时也只改一处。

## 3. 目录下有哪些核心类

| 类 | 职责 | 面试里怎么说 |
| --- | --- | --- |
| `FileValidationService` | 校验文件是否为空、大小是否超限、类型是否允许 | 上传入口的第一道业务校验 |
| `ContentTypeDetectionService` | 基于 Apache Tika 检测真实 MIME 类型 | 不盲信浏览器传来的 `Content-Type` |
| `FileHashService` | 计算 SHA-256 hash | 用文件内容指纹做去重，减少重复分析和存储 |
| `DocumentParseService` | 用 Tika 提取 PDF、Word、TXT、MD 等文档文本 | 把二进制文件转成 AI/RAG 可消费的文本 |
| `TextCleaningService` | 清理 Tika 提取出的噪声文本 | 去掉图片路径、控制字符、分隔线，提升 AI 输入质量 |
| `NoOpEmbeddedDocumentExtractor` | 禁用 Tika 嵌入文档解析 | 避免图片、附件、临时路径污染正文 |
| `FileStorageService` | 基于 S3 兼容协议上传、下载、删除、查询文件 | 对接 RustFS，统一对象存储访问 |

## 4. 典型调用链

### 简历上传链路

```text
ResumeUploadService.uploadAndAnalyze
  -> FileValidationService.validateFile
  -> ResumeParseService.detectContentType
      -> ContentTypeDetectionService.detectContentType
  -> FileValidationService.validateContentTypeByList
  -> ResumePersistenceService.findExistingResume
      -> FileHashService.calculateHash
  -> ResumeParseService.parseResume
      -> DocumentParseService.parseContent
      -> TextCleaningService.cleanText
  -> FileStorageService.uploadResume
  -> ResumePersistenceService.saveResume
  -> AnalyzeStreamProducer.sendAnalyzeTask
```

### 知识库上传链路

```text
KnowledgeBaseUploadService.uploadKnowledgeBase
  -> FileValidationService.validateFile
  -> KnowledgeBaseParseService.detectContentType
      -> ContentTypeDetectionService.detectContentType
  -> FileValidationService.validateContentType
  -> FileHashService.calculateHash
  -> KnowledgeBaseRepository.findByFileHash
  -> KnowledgeBaseParseService.parseContent
      -> DocumentParseService.parseContent
      -> TextCleaningService.cleanText
  -> FileStorageService.uploadKnowledgeBase
  -> KnowledgeBasePersistenceService.saveKnowledgeBase
  -> VectorizeStreamProducer.sendVectorizeTask
```

一句话概括：

> 文件基础设施层把“上传来的二进制文件”处理成两类资产：一类是 RustFS 里的原文件，一类是数据库或异步任务里使用的纯文本内容。

## 5. 核心设计亮点

| 亮点 | 说明 |
| --- | --- |
| 复用性 | 简历和知识库共用同一套文件解析、存储、校验、hash 能力 |
| 类型检测更可信 | 使用 Tika 基于文件内容检测 MIME，而不是只信 HTTP 头 |
| 去重成本低 | SHA-256 基于内容生成文件指纹，重复上传可以直接复用历史结果 |
| 解析质量可控 | Tika 解析后统一走文本清洗，减少图片路径、控制字符、分隔线等噪声 |
| 存储路径规范 | 对象 key 使用业务前缀、日期路径、短 UUID 和安全文件名 |
| 异常统一 | 基础设施异常转换为 `BusinessException`，符合项目全局异常处理规范 |

## 6. 面试中重点讲清楚的边界

这个模块不要讲成“万能文件系统”，要诚实说明边界：

| 边界 | 当前情况 | 可以怎么优化 |
| --- | --- | --- |
| 扫描版 PDF | Tika 只能提取已有文本层，扫描件可能提取为空 | 增加 OCR fallback |
| 大文件解析 | `BodyContentHandler` 限制最大提取文本 5MB | 大文件可做分段解析或流式 chunk |
| 文件 URL | `getFileUrl` 拼接的是静态访问地址 | 生产环境可改成预签名 URL |
| 对象存储一致性 | 业务层做数据库保存失败后的补偿删除 | 可增加失败补偿任务和定期清理孤儿文件 |
| MIME 校验 | 知识库支持扩展名兜底 | 更严格场景可以同时要求 MIME 和扩展名匹配 |
| hash 去重 | 是文件级去重，不是语义级去重 | 可增加文本 hash 或语义相似度去重 |

## 7. 两分钟面试表达模板

> `infrastructure/file` 是项目的文件基础设施层，主要服务于简历上传和知识库上传。它把文件处理的共性能力抽出来，包括文件大小校验、MIME 类型检测、SHA-256 去重、Apache Tika 文本解析、文本清洗，以及基于 S3 兼容协议的 RustFS 对象存储。
>
> 上传链路里，业务模块先调用 `FileValidationService` 校验空文件和大小，再通过 `ContentTypeDetectionService` 用 Tika 检测真实 MIME 类型。然后用 `FileHashService` 计算文件内容 hash 做去重。新文件会交给 `DocumentParseService` 用 Tika 提取文本，解析时禁用嵌入文档提取，并配置 PDF 按坐标排序和关闭图片提取。提取出的文本再经过 `TextCleaningService` 去掉图片路径、控制字符、分隔线等噪声。最后通过 `FileStorageService` 上传到 RustFS，生成 `resumes/yyyy/MM/dd/uuid_filename` 或 `knowledgebases/yyyy/MM/dd/uuid_filename` 这样的对象 key。
>
> 这个设计的价值是把文件技术细节和业务编排解耦。简历和知识库都可以复用同一套底层能力，上层只负责保存元数据、触发分析或向量化任务。它的边界是 Tika 对扫描版 PDF 支持有限，生产环境还可以增加 OCR、预签名 URL、对象存储删除补偿和更严格的文件安全扫描。

## 8. 一句话总结

> 这个模块把文件上传从“保存一个 MultipartFile”升级成了“校验、识别、去重、解析、清洗、存储、可复用”的文件处理基础设施。
