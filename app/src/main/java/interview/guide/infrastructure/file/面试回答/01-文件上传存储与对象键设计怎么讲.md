# 文件上传存储与对象键设计怎么讲

## 1. 一句话定位

`FileStorageService` 是项目的对象存储门面，基于 S3 兼容协议对接 RustFS，统一提供简历和知识库文件的上传、下载、删除、存在性检查、文件大小查询和访问 URL 生成。

面试中可以这样说：

> 我没有把文件直接存到应用服务器本地，而是通过 S3 兼容协议存到 RustFS。业务模块只拿到 `fileKey` 和 `fileUrl`，后续重新分析、重新向量化或删除时都通过这个 key 操作对象存储。

## 2. 为什么用对象存储

如果把用户上传文件直接存本地，会有几个问题：

1. 多实例部署时，本地磁盘无法共享。
2. 应用容器重启或迁移时文件容易丢。
3. 文件和业务数据库生命周期不同，不适合混在一起。
4. 知识库文件可能较大，本地磁盘扩容和备份不方便。

RustFS 提供 S3 兼容接口，代码里可以直接用 AWS S3 SDK：

```text
S3Client
  -> PutObjectRequest
  -> GetObjectRequest
  -> HeadObjectRequest
  -> DeleteObjectRequest
```

面试表达：

> 选择 S3 兼容存储的原因是解耦应用和文件资源。数据库只保存元数据、`storageKey` 和访问 URL，原始文件交给对象存储管理，这样更适合多实例部署和后续扩展。

## 3. 上传入口怎么设计

`FileStorageService` 对外提供两个业务语义入口：

| 方法 | 存储前缀 | 使用场景 |
| --- | --- | --- |
| `uploadResume(MultipartFile file)` | `resumes` | 简历文件上传 |
| `uploadKnowledgeBase(MultipartFile file)` | `knowledgebases` | 知识库文件上传 |

它们内部都委托给私有方法：

```text
uploadFile(file, prefix)
```

这样做的好处是：

1. 对业务层保留语义清晰的方法名。
2. 底层上传逻辑只维护一份。
3. 不同业务文件可以按前缀隔离。

上传核心流程：

```text
originalFilename = file.getOriginalFilename()
fileKey = generateFileKey(originalFilename, prefix)
PutObjectRequest(bucket, key, contentType, contentLength)
s3Client.putObject(request, RequestBody.fromInputStream(...))
return fileKey
```

## 4. 对象 key 是怎么生成的

当前对象 key 格式：

```text
{prefix}/{yyyy/MM/dd}/{uuid8}_{safeName}
```

例子：

```text
resumes/2026/07/01/a1b2c3d4_ZhangSan.pdf
knowledgebases/2026/07/01/e5f6g7h8_JavaInterview.md
```

设计考虑：

| 组成 | 作用 |
| --- | --- |
| `prefix` | 按业务类型隔离文件 |
| `yyyy/MM/dd` | 按日期分散对象 key，方便管理和排查 |
| `uuid8` | 避免同名文件覆盖 |
| `safeName` | 保留原文件名可读性，同时去掉不安全字符 |

面试表达：

> key 不是直接使用原文件名，因为用户可能上传同名文件，也可能包含中文、空格、路径分隔符等特殊字符。我用业务前缀、日期目录、短 UUID 和安全文件名组合，既避免冲突，也方便按业务和日期排查对象。

## 5. 中文文件名怎么处理

`sanitizeFilename` 会调用 `convertToPinyin`：

1. 汉字转成无声调拼音。
2. 每个汉字拼音首字母大写。
3. 非汉字字符如果是字母、数字、点号、下划线、连字符就保留。
4. 其他字符替换为 `_`。

这样：

```text
张三简历.pdf
```

会变成类似：

```text
ZhangSanJianLi.pdf
```

这解决了两个问题：

1. 对象 key 更稳定，避免中文路径在不同网关或客户端里编码不一致。
2. 仍然保留一定可读性，排查时能看出原文件大致含义。

## 6. 下载、删除和存在性检查

下载流程：

```text
downloadFile(fileKey)
  -> fileExists(fileKey)
  -> GetObjectRequest(bucket, key)
  -> s3Client.getObjectAsBytes(...).asByteArray()
```

如果文件不存在，抛：

```text
BusinessException(ErrorCode.STORAGE_DOWNLOAD_FAILED, "文件不存在: " + fileKey)
```

删除流程：

```text
deleteFile(fileKey)
  -> fileKey 为空则跳过
  -> fileExists(fileKey) 为 false 则跳过
  -> DeleteObjectRequest(bucket, key)
  -> s3Client.deleteObject(...)
```

这里有一个设计点：

> 删除时先做存在性检查，文件不存在就记录 warn 并跳过，这让删除操作更接近幂等。比如业务重试删除、或者数据库记录里保存了旧 key，不会因为对象已经没了就直接失败。

## 7. 和业务事务的一致性怎么处理

`FileStorageService` 本身只负责对象存储操作，不控制数据库事务。业务层负责补偿。

简历上传里：

```text
先上传 RustFS
再保存数据库
如果数据库保存失败
  -> storageService.deleteResume(fileKey)
```

知识库上传里也是类似：

```text
先上传 RustFS
再保存知识库元数据
如果保存失败
  -> storageService.deleteKnowledgeBase(fileKey)
```

面试表达：

> 对象存储和数据库不是一个事务资源，所以我没有假装能做强一致事务，而是在业务编排层做补偿删除。对象上传成功但数据库保存失败时，会尽量删除刚上传的对象，降低孤儿文件风险。

## 8. ensureBucketExists 怎么讲

`ensureBucketExists` 会：

1. 先 `headBucket` 检查桶是否存在。
2. 不存在时调用 `createBucket` 创建。
3. 其他 S3 异常只记录错误日志。

它适合开发或启动初始化场景，避免第一次上传时桶不存在。

面试时要诚实说明：

> 这个方法当前对普通 `S3Exception` 只记录日志，没有向上抛出。如果生产环境要求启动即失败，可以改成抛业务异常或在健康检查里检测对象存储可用性。

## 9. 当前实现的边界

| 边界 | 当前情况 | 优化方向 |
| --- | --- | --- |
| 访问 URL | `getFileUrl` 直接拼 endpoint、bucket、key | 私有桶建议改预签名 URL |
| 上传安全 | 当前负责存储，不做病毒扫描 | 可接入文件安全扫描 |
| 删除一致性 | 删除失败直接抛业务异常，业务层部分场景继续处理 | 可增加删除补偿任务 |
| 大文件下载 | `downloadFile` 一次性读成 byte[] | 大文件可改流式下载 |
| bucket 初始化 | `ensureBucketExists` 对部分异常只打日志 | 生产可改启动失败或健康检查失败 |

## 10. 面试回答模板

> 文件存储这块我封装了一个 `FileStorageService`，它基于 AWS S3 SDK 对接 RustFS。对业务层暴露的是 `uploadResume`、`uploadKnowledgeBase`、`deleteResume`、`deleteKnowledgeBase` 这些有业务语义的方法，内部复用通用的上传和删除逻辑。
>
> 上传时我不会直接用原文件名作为 key，而是生成 `业务前缀/日期/短UUID_安全文件名` 这样的对象 key。业务前缀区分简历和知识库，日期方便排查和生命周期管理，UUID 避免同名覆盖，安全文件名会把中文转拼音并过滤特殊字符。
>
> 对象存储和数据库不是同一个事务，所以一致性通过业务层补偿处理。比如文件上传成功但数据库保存失败，会调用删除方法补偿清理对象。当前边界是访问 URL 还是简单拼接，生产环境可以进一步改成私有桶加预签名 URL，并补充对象删除失败的异步补偿。
