# 面试官高频追问与参考答案

## 1. 你这个文件模块整体是怎么设计的？

答：

> 我把文件处理抽成了基础设施层，服务于简历和知识库两个业务模块。它不是单纯上传文件，而是提供一整套通用能力：文件大小和空文件校验、Tika MIME 类型检测、SHA-256 文件去重、Tika 文档解析、文本清洗、RustFS/S3 对象存储、下载后重新解析和删除文件。
>
> 上层业务模块只做业务编排，例如保存简历元数据、触发简历分析任务、保存知识库元数据、触发向量化任务。底层技术细节，比如 S3 SDK、Tika、hash、文件名安全处理，都集中在 `infrastructure/file` 里。

## 2. 为什么要把文件能力抽到 infrastructure？

答：

> 因为简历和知识库都有类似的文件处理链路，如果各写一套，会造成解析规则、存储 key、异常处理、清洗策略不一致。抽到基础设施层之后，业务层只需要调用统一服务，后续替换对象存储、调整 Tika 配置、增加 OCR 或文件安全扫描时，只需要改基础设施层。

## 3. 上传一份简历时，文件模块参与了哪些步骤？

答：

> 简历上传时，先用 `FileValidationService` 校验文件非空和大小上限；再通过 `ResumeParseService` 委托 `ContentTypeDetectionService` 检测 MIME 类型；接着 `ResumePersistenceService` 调用 `FileHashService` 计算 SHA-256 hash 做去重；如果是新文件，就用 `DocumentParseService` 提取文本并由 `TextCleaningService` 清洗；最后用 `FileStorageService.uploadResume` 上传到 RustFS，数据库保存 `storageKey` 和 `storageUrl`。

## 4. 知识库上传和简历上传在文件处理上有什么区别？

答：

> 共性是都走校验、MIME 检测、hash 去重、Tika 解析、文本清洗和对象存储。区别是简历最大 10MB，知识库最大 50MB；简历允许类型来自配置，知识库类型判断内置支持 PDF、Word、TXT、Markdown、RTF，并对 Markdown 做扩展名兜底；简历解析结果用于 LLM 分析，知识库解析结果用于后续向量化和 RAG。

## 5. 为什么不用本地磁盘存文件？

答：

> 本地磁盘不适合多实例部署，实例重启或迁移也容易导致文件不可用。对象存储更适合保存用户上传的原始文件，数据库只保存文件元数据和 `fileKey`。当前项目用 RustFS，它兼容 S3 协议，所以代码通过 AWS S3 SDK 就能完成上传、下载、删除和 head 查询。

## 6. FileStorageService 的对象 key 是怎么设计的？

答：

> key 格式是 `业务前缀/日期/短UUID_安全文件名`。例如 `resumes/2026/07/01/a1b2c3d4_ZhangSan.pdf`。业务前缀区分简历和知识库，日期方便排查和生命周期管理，UUID 避免同名覆盖，安全文件名会把中文转拼音并过滤特殊字符，避免对象 key 出现编码或路径问题。

## 7. 为什么中文文件名要转拼音？

答：

> 主要是为了让对象 key 更稳定。中文文件名在不同客户端、网关、控制台里可能有编码展示问题。转成无声调拼音后仍然保留可读性，同时特殊字符会替换成下划线，降低路径和 URL 兼容风险。

## 8. 对象存储和数据库怎么保证一致性？

答：

> 对象存储和数据库不是同一个事务资源，所以当前用业务层补偿。简历或知识库上传时，先上传 RustFS，再保存数据库。如果数据库保存失败，就调用 `deleteResume` 或 `deleteKnowledgeBase` 补偿删除刚上传的对象。这个方案不能保证绝对强一致，但能降低孤儿文件概率。

## 9. 为什么要用 Tika 检测 MIME 类型？

答：

> 因为文件扩展名和 HTTP `Content-Type` 都不完全可信。用户可以把任意文件改成 `.pdf`，客户端也可能传错 Content-Type。Tika 会读取文件内容并结合文件名判断真实 MIME 类型，比只看后缀更可靠。

## 10. FileValidationService 和 ContentTypeDetectionService 怎么分工？

答：

> `ContentTypeDetectionService` 负责识别文件是什么类型，底层用 Tika。`FileValidationService` 负责判断这个文件在当前业务下能不能上传，比如是否为空、是否超过大小、MIME 是否在白名单、Markdown 扩展名是否允许。一个偏技术识别，一个偏业务规则。

## 11. 为什么知识库允许扩展名兜底？

答：

> 主要是为了兼容 Markdown。不同环境下 `.md` 文件可能被识别成 `text/plain`、`text/markdown` 或其他文本类型。如果只看 MIME，可能误拒绝合法 Markdown。所以知识库校验在 MIME 不通过时，会再检查 `.md`、`.markdown`、`.mdown` 扩展名。

## 12. 为什么要做 SHA-256 hash？

答：

> hash 用于文件级去重，避免同一份简历或知识库重复解析、重复上传、重复调用 LLM 或 embedding。它基于文件内容计算，不依赖文件名，所以用户把同一个文件改名后再次上传，仍然能识别为重复文件。

## 13. SHA-256 hash 有什么边界？

答：

> 当前是文件级去重，只能识别字节完全相同的文件。如果用户把同一份简历重新导出成 PDF，内容可能一样但字节不同，hash 就不同。后续可以增加解析文本 hash，或者用 embedding 相似度做语义级去重，但成本和误判风险也更高。

## 14. DocumentParseService 是怎么解析文件的？

答：

> 它用 Tika 的 `AutoDetectParser` 做统一解析入口，用 `BodyContentHandler` 提取正文并限制最大文本长度。解析上下文里注册了 `NoOpEmbeddedDocumentExtractor`，避免解析图片和附件；同时配置了 `PDFParserConfig`，关闭内联图片提取，并按坐标排序文本，改善多栏 PDF 简历的文本顺序。解析后统一交给 `TextCleaningService` 清洗。

## 15. 为什么要禁用 Tika 的嵌入文档解析？

答：

> 因为嵌入资源对 AI 分析通常没有意义，反而会引入噪声，比如 `image123.png`、临时文件路径或附件内容。对于简历分析和知识库向量化，我更关心正文文本，所以通过 `NoOpEmbeddedDocumentExtractor` 让 Tika 跳过嵌入资源。

## 16. TextCleaningService 清理了哪些内容？

答：

> 它先做语义去噪：去控制字符、图片文件名行、图片 URL、`file://` 路径、整行分隔线。然后做格式规范化：统一换行符、去掉行尾空格、压缩连续空行、去掉首尾空白。这样可以减少 token 浪费，也能提升 RAG 向量化文本质量。

## 17. 为什么文本清洗对 AI 很重要？

答：

> AI 输出质量很依赖输入质量。Tika 原始文本里如果混入图片路径、临时文件、控制字符和大量分隔线，既浪费 token，也会干扰模型理解。知识库向量化时，这些噪声还会进入 embedding，影响召回质量。所以我把清洗作为 Tika 后的固定步骤。

## 18. 扫描版 PDF 怎么办？

答：

> 当前 Tika 只能提取 PDF 文本层。如果是扫描版 PDF，没有文本层，解析结果可能为空，上层会提示“无法从文件中提取文本内容”。生产级可以增加 OCR fallback，比如 PaddleOCR、Tesseract 或云 OCR，把图片里的文字识别出来再进入清洗和分析链路。

## 19. 大文件会不会有内存问题？

答：

> 当前简历限制 10MB，知识库限制 50MB。解析文本用 `BodyContentHandler` 限制最大提取文本 5MB，hash 也提供了 `InputStream` 流式版本。不过 `downloadFile` 当前会一次性把对象读成 byte[]，如果未来支持更大文件，可以改成流式下载、分段解析和分块向量化。

## 20. 文件删除是幂等的吗？

答：

> `FileStorageService.deleteFile` 对空 key 直接跳过，对不存在的文件记录 warn 后跳过，所以在对象不存在的情况下不会直接失败。这让重复删除或补偿删除更安全。但如果 S3 删除请求本身失败，会抛 `BusinessException(ErrorCode.STORAGE_DELETE_FAILED, ...)`。

## 21. 这个模块有哪些设计模式或工程思想？

答：

> `FileStorageService` 是对象存储门面，屏蔽 S3 SDK 细节；`DocumentParseService` 是解析流程模板，把 Tika 配置、嵌入资源控制、PDF 配置和清洗串起来；`FileValidationService` 用策略参数 `Predicate<String>` 支持不同业务的 MIME 和扩展名校验；`FileHashService` 用方法重载适配不同输入源。整体思想是把技术细节下沉到基础设施层，上层业务只做编排。

## 22. 这个模块当前有什么不足？

答：

> 第一，没有 OCR，扫描版 PDF 解析不了。第二，`downloadFile` 一次性返回 byte[]，更大文件需要流式化。第三，文件 URL 目前是简单拼接，生产环境建议用私有桶和预签名 URL。第四，文件安全只做了大小和类型校验，没有病毒扫描或宏检测。第五，对象存储删除失败可以增加补偿任务或定期清理孤儿文件。

## 23. 如果让你继续优化这个文件模块，你会怎么做？

答：

> 我会按优先级做几件事：先加 OCR fallback，解决扫描版 PDF；再把大文件下载和解析改成流式或分块，避免 byte[] 占用过高；然后把访问 URL 改成预签名 URL，增强权限控制；接着接入文件安全扫描；最后增加对象存储和数据库的一致性补偿任务，比如定期扫描数据库没有引用的孤儿文件。

## 24. 怎么用一句话体现这个模块的价值？

答：

> 这个模块把文件上传从“接收并保存一个文件”升级成了“校验、识别、去重、解析、清洗、存储和复用”的文件处理基础设施，让简历分析和知识库 RAG 都能建立在稳定的文件输入之上。
