# SHA-256 哈希去重怎么讲

## 1. 一句话定位

`FileHashService` 统一提供 SHA-256 文件指纹计算能力，用于简历和知识库的文件级去重。

面试中可以这样说：

> 文件 hash 的作用是避免同一份文件重复解析、重复上传和重复调用 AI。它基于文件内容计算，而不是基于文件名，所以用户把同一个文件改名后再次上传，也能识别为重复文件。

## 2. 为什么要做文件 hash 去重

AI 面试平台里重复文件会带来明显成本：

| 重复动作 | 浪费 |
| --- | --- |
| 重复上传原文件 | 对象存储空间浪费 |
| 重复 Tika 解析 | CPU 和 IO 浪费 |
| 重复简历分析 | LLM token 和调用费用浪费 |
| 重复知识库向量化 | embedding 调用和 pgvector 存储浪费 |

所以上传链路里会先计算文件内容 hash，再查数据库是否已有相同文件。

简历链路：

```text
ResumeUploadService
  -> ResumePersistenceService.findExistingResume(file)
      -> FileHashService.calculateHash(file)
      -> resumeRepository.findByFileHash(hash)
```

知识库链路：

```text
KnowledgeBaseUploadService
  -> FileHashService.calculateHash(file)
  -> knowledgeBaseRepository.findByFileHash(hash)
```

## 3. 为什么选择 SHA-256

SHA-256 适合文件指纹场景：

1. 输出固定 256 bit，十六进制字符串长度 64。
2. 碰撞概率极低，足够用于普通业务去重。
3. Java 标准库 `MessageDigest` 原生支持。
4. 不依赖文件名、上传时间、用户输入等外部信息。

面试表达：

> 这里的 hash 不是为了加密，而是为了生成内容指纹。SHA-256 的碰撞概率足够低，标准库支持也很好，用来做文件级去重比较合适。

## 4. 三种输入形式

`FileHashService` 支持三个重载：

| 方法 | 场景 | 特点 |
| --- | --- | --- |
| `calculateHash(MultipartFile file)` | Web 上传文件 | 先 `file.getBytes()`，再委托 byte[] 版本 |
| `calculateHash(byte[] data)` | 已在内存中的文件内容 | 一次性 `digest(data)` |
| `calculateHash(InputStream inputStream)` | 大文件或流式场景 | 8KB buffer 分块 `digest.update` |

设计亮点：

> 对外用重载适配不同输入来源，内部核心算法一致，避免业务层自己判断怎么计算 hash。

## 5. 流式 hash 怎么讲

`InputStream` 版本逻辑：

```text
MessageDigest digest = MessageDigest.getInstance("SHA-256")
byte[] buffer = new byte[8192]
while ((bytesRead = inputStream.read(buffer)) != -1) {
  digest.update(buffer, 0, bytesRead)
}
return bytesToHex(digest.digest())
```

关键点：

1. 不需要一次性把整个文件读入内存。
2. 内存占用主要是 8KB buffer。
3. 适合未来更大的知识库文件或流式处理场景。

面试表达：

> 虽然当前 `MultipartFile` 版本会先读成 byte[]，但我也保留了 `InputStream` 版本。大文件场景可以直接走流式 hash，内存占用是常量级的。

## 6. bytesToHex 为什么要自己转换

`MessageDigest` 返回的是 byte 数组，不适合直接存数据库或日志展示，所以要转成十六进制字符串：

```text
byte[] -> 64 位 hex 字符串
```

代码里：

```text
StringBuilder result = new StringBuilder(bytes.length * 2)
for (byte b : bytes) {
  result.append(String.format("%02x", b))
}
```

`%02x` 的含义是：

1. 按十六进制输出。
2. 不足两位时前面补 0。
3. 使用小写字母。

## 7. 异常处理怎么讲

可能出现两类异常：

| 异常 | 场景 | 处理 |
| --- | --- | --- |
| `IOException` | 读取上传文件或输入流失败 | 记录日志，抛 `BusinessException` |
| `NoSuchAlgorithmException` | JVM 不支持 SHA-256 | 记录日志，抛 `BusinessException` |

虽然 SHA-256 在标准 JVM 中基本一定存在，但代码仍然做了防御性处理。

## 8. 文件级去重和语义级去重的区别

这个点面试很容易被追问。

| 类型 | 判断依据 | 能识别什么 | 不能识别什么 |
| --- | --- | --- | --- |
| 文件级去重 | 原始文件字节 hash | 完全相同文件 | 内容相同但格式不同、重新导出的文件 |
| 文本级去重 | 解析后文本 hash | 文本内容相同 | 排版差异造成的解析差异 |
| 语义级去重 | embedding 相似度 | 内容高度相似 | 成本更高，可能误判 |

当前实现是文件级去重。

面试表达：

> 当前去重是文件级的，它能准确识别字节完全相同的文件，但不能识别“内容相同、重新导出后字节不同”的文件。如果要进一步优化，可以增加解析文本 hash 或 embedding 相似度判断。

## 9. 当前实现的边界

| 边界 | 当前情况 | 优化方向 |
| --- | --- | --- |
| MultipartFile hash | 使用 `file.getBytes()` 一次性读入内存 | 大文件上传可改为 `getInputStream()` 流式 hash |
| 去重粒度 | 文件级 hash | 增加文本 hash 或语义去重 |
| hash 时机 | 上传链路中同步计算 | 大文件可异步或分块计算 |
| 碰撞处理 | 默认相信 SHA-256 | 极端场景可同时比较文件大小和部分内容 |

## 10. 面试回答模板

> 文件去重我用的是 `FileHashService`，核心是基于 SHA-256 计算文件内容指纹。它不依赖文件名，所以用户改名上传同一份文件，hash 仍然一样。简历上传时，`ResumePersistenceService` 会用 hash 查已有简历；知识库上传时，`KnowledgeBaseUploadService` 会用 hash 查已有知识库，避免重复解析、重复存储、重复调用 LLM 或 embedding。
>
> 实现上提供了三个重载：`MultipartFile`、`byte[]` 和 `InputStream`。`InputStream` 版本用 8KB buffer 分块更新 `MessageDigest`，适合大文件场景，内存占用是常量级。最后把 digest 的 byte 数组转成 64 位十六进制字符串保存。
>
> 这个方案的边界是它只能做文件级去重，不能识别内容相同但重新导出、字节不同的文件。后续如果要更智能，可以增加解析文本 hash 或语义相似度去重。
