
## 一、这个本地存储到底是什么

### 1. 通俗类比

传统认知里的"存文件"是存到硬盘的某个目录：

```
/var/uploads/resumes/张三的简历.pdf
/var/uploads/resumes/李四的简历.docx
```

这个项目用的 MinIO 不一样——它是一个**独立运行的文件存储服务**，有自己的进程、端口、API，就像一个"文件专用数据库"：

```
浏览器 → Spring Boot → MinIO（独立服务，端口9000）
                         ├── interview-guide（桶，类似数据库）
                         │   ├── resumes/2025/06/a1b2c3d4_JianLi.pdf
                         │   └── knowledgebases/2025/06/...
```

MinIO 跟你现在用的 PostgreSQL 本质是一样的：**一个独立的后端服务，通过网络协议访问**。只不过 PostgreSQL 存结构化数据，MinIO 存文件。

### 2. MinIO 是个什么东西

MinIO 是一个开源的对象存储服务，完全兼容 AWS S3 的 API。你可以把它理解成"自己服务器上跑的 S3"。

启动它只需要一行 Docker 命令：

```bash
docker run -p 9000:9000 -p 9001:9001 \
  -e MINIO_ROOT_USER=admin \
  -e MINIO_ROOT_PASSWORD=password \
  minio/minio server /data --console-address ":9001"
```

跑了之后，你的服务器上就有了一个 `http://localhost:9000` 的对象存储服务，支持标准 S3 协议的所有操作。

### 3. 项目里怎么用的

三样东西配合工作：

```
application.yml                → 配好 MinIO 的地址、用户名、密码
    ↓
S3Config.java                  → 用 AWS S3 SDK 创建客户端，连到 MinIO
    ↓
FileStorageService.java        → 用客户端做上传、下载、删除
```

实际代码调用链：

```
用户上传简历 PDF
  → ResumeUploadService.uploadAndAnalyze()
    → storageService.uploadResume(file)
      → s3Client.putObject(bucket="interview-guide", key="resumes/2025/06/abc123_简历.pdf", body=文件内容)
        → MinIO 收到请求，存到本地磁盘 /data/interview-guide/resumes/2025/06/abc123_简历.pdf
```

文件实际存在 MinIO 容器的 `/data` 目录下，但 Java 代码完全不关心物理路径，只通过 key 访问。

### 4. 为什么不直接 `new File("/tmp/resume.pdf")` 存本地

最根本的问题：**多台服务器没法共享**。

```
# 两台服务器的情况
用户上传 → Nginx 负载均衡 → 服务器A（文件存在 /data/resume.pdf）
                           服务器B（没有这个文件！）
```

对象存储解决了这个：不管请求落到哪台服务器，都往同一个 MinIO 地址发请求，文件存在 MinIO 那一台机器上，所有应用实例共享。

## 二、面试中怎么讲

### 核心三板斧

**第一句：选型理由**

> "对象存储方案我们用 S3 兼容协议做了抽象，开发环境跑 MinIO 容器，生产通过环境变量切换到云服务商的对象存储。选 S3 协议的原因是它是行业标准，阿里云 OSS、AWS S3、腾讯云 COS 全部兼容，换云零代码改动。"

**第二句：架构设计**

> "通过 FileStorageService 封装了所有文件操作，上层业务代码只调 upload/delete/download 三个语义化方法。存储的配置通过 `@ConfigurationProperties` 集中管理，敏感信息从环境变量注入，不入版本控制。"

**第三句：为什么不用本地文件系统**

> "本地文件系统有水平扩展的问题——多实例部署时文件在单台机器上，其他实例访问不到。而且服务器宕机会丢文件、没有版本管理、没有自动备份。对象存储天然支持多节点共享、自带副本冗余。"

### 加分点

如果面试官追问，可以深入说：

**1. 开发到生产的无缝切换**

> "配置里 endpoint 默认值写的是 `localhost:9000`，通过环境变量 `APP_STORAGE_ENDPOINT` 覆盖。开发时本地 Docker 跑 MinIO，CI 测试环境也是一个 MinIO 容器，上生产把环境变量改成阿里云 OSS 的地址就行。代码一行不碰。"

**2. forcePathStyle 的坑**

> "对接非 AWS 官方的 S3 存储时，AWS SDK 默认用虚拟主机风格 URL 解析 Bucket，会在 DNS 层面拼 `bucket.localhost:9000`，直接解析失败。打开 `forcePathStyle(true)` 改成路径风格 `localhost:9000/bucket` 就兼容了。这个细节很多第一次对接的人会卡半天。"

**3. 补偿事务**

> "对象存储不在数据库事务范围内，所以我们做了补偿逻辑——文件上传 RustFS 成功后，如果后面的数据库入库失败，会调用 `compensateUploadedResume()` 把刚上传的文件删掉，保证不会产生孤儿文件。"

### 一句话总结

> "本质就是用一个 S3 协议标准做了一层存储抽象：本地开发跑 MinIO 零成本，上生产改环境变量接入云存储零改动，上层业务代码完全无感知。"
