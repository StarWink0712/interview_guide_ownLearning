## InterviewSessionCache 分析总结

### 一、定位

InterviewSessionCache 是面试模块的 **Redis 缓存专用层**，建立在 RedisService 之上，专门管理模拟面试会话的缓存生命周期。它不是一个通用的 Redis 工具，而是紧密绑定面试业务语义的缓存组件——理解它的关键不在于"用了什么 Redis 命令"，而在于"为面试会话设计了一套怎样的缓存模型"。

<br />

把面试会话缓存到redis中，当面试过程中断，会断开连接，再启动的时候会先从redis缓存中获取会话信息，缓存设置为固定前缀interview:session:sessionId，以sessionid为索引查询，同时缓存有简历与会话的映射表，以简历id为key，缓存简历与会话的关系。缓存的都是string类型，前面说的是key，value是会话对象序列化后的二进制数据，映射缓存的value是会话id的字符串，读写时可以通过泛型自动反序列化（默认用jackon json与kryo）。过期时间都设置为24小时。

<br />

面试会话缓存到 Redis 中，当面试过程中断或连接断开时，下次启动会先从 Redis 缓存中获取会话信息恢复现场。缓存 Key 为 `interview:session:{sessionId}`，以 `sessionId` 作为唯一索引查询，Value 是 `CachedSession` 对象经 Redisson 默认 Jackson JSON Codec 序列化后的二进制数据，读写时通过泛型自动反序列化，过期时间设为 24 小时。同时维护一份简历与活跃会话的映射缓存，Key 为 `interview:resume:{resumeId}`，Value 是对应的 `sessionId` 字符串，但该映射不是永久存在，只在会话状态为 `CREATED` 或 `IN_PROGRESS` 时才建立，一旦会话变为 `COMPLETED` 或 `EVALUATED` 就自动删除，确保同一份简历同一时间最多只有一个活跃映射。用户答题过程中每次更新状态、题目索引或问题列表时，TTL 都会随之刷新重置为 24 小时，不会在答题中途过期。需要注意的是 `CachedSession` 内部的问题列表存在两层序列化：`List<InterviewQuestionDTO>` 先由 `ObjectMapper` 转成 JSON 字符串存入 `questionsJson` 字段，然后整个 `CachedSession` 对象再被 Redisson 序列化存入 Redis String，读取时反向两层反序列化还原。

<br />

```
InterviewSessionService
        │
        ▼
InterviewSessionCache  ←── RedisService  ←── RedissonClient  ←── Redis
        │
        ├── 会话数据缓存 (interview:session:{sessionId})
        └── 简历-会话映射 (interview:resume:{resumeId})
```

### 二、数据模型设计

**1. 内嵌静态类** **`CachedSession`**

[第 67-100 行](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/infrastructure/redis/InterviewSessionCache.java#L67-L100) 定义了一个 `Serializable` 的内部类作为缓存的载体，设计上有几个关键决策：

| 决策             | 说明                                                                                          |
| -------------- | ------------------------------------------------------------------------------------------- |
| 问题列表存 JSON 字符串 | `questionsJson` 字段而非对象，因为 Redisson 默认用 JDK 序列化存储对象，嵌套 `List<DTO>` 序列化不可控，手动 JSON 化更可靠       |
| 构造时序列化         | `CachedSession` 构造器中直接调用 `objectMapper.writeValueAsString(questions)` 将问题列表转为 JSON，将序列化时机前移 |
| 反序列化封装为方法      | `getQuestions(ObjectMapper)` 不是 getter，而是显式传入 ObjectMapper 做反序列化，失败直接抛 `BusinessException`  |
| `@Data` + 无参构造 | `@Data` 提供 getter/setter，保留 public 无参构造供 Redisson 反序列化使用                                    |

**2. 两种 Redis Key 设计**

```
interview:session:{sessionId}   → CachedSession 对象（主缓存，TTL 24h）
interview:resume:{resumeId}     → sessionId 字符串（映射，TTL 24h）
```

"简历→会话"映射的设计目的：用户可能因断网、关闭页面等原因中断面试，再次进入时系统通过简历 ID 快速查到未完成的会话 ID，实现**面试断点续答**。

### 三、核心流程拆解

**1. 保存会话（`saveSession`）**

```
saveSession(sessionId, resumeText, resumeId, questions, index, status)
    │
    ├── ① 创建 CachedSession（构造器中 questions → JSON）
    ├── ② redisService.set(key, cachedSession, 24h)
    └── ③ 如果有 resumeId 且状态为未完成 → saveResumeSessionMapping()
```

第 116 行的条件判断 `isUnfinishedStatus(status)` 保证了只有 `CREATED` 和 `IN_PROGRESS` 状态的会话才建立映射，已完成的会话不占用反向索引。

**2. 查找未完成会话（`findUnfinishedSessionId`）**

[第 200-214 行](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/infrastructure/redis/InterviewSessionCache.java#L200-L214) 是这个类最精妙的方法：

```
resumeId → redisService.get("interview:resume:{resumeId}") → sessionId
    │
    ├── sessionId 存在 → 二次验证会话是否存在且未完成
    │       ├── 通过 → 返回 sessionId
    │       └── 不通过 → 清理过期映射（防御性清理）
    └── sessionId 不存在 → 返回 empty
```

这里做了**读时修复**：映射指向的会话可能已过期或被删除（映射和会话之间不是原子操作），查询时若发现会话已不存在或已完成，主动清理脏映射。这是最终一致性场景下的惰性修复策略，避免堆积无效映射。

**3. 状态更新时的映射维护**

三个更新方法都遵循同一模式——读-改-写，并根据状态变化决定是否维护映射：

| 方法                    | 映射维护逻辑          |
| --------------------- | --------------- |
| `updateSessionStatus` | 状态变更为已完成 → 移除映射 |
| `updateCurrentIndex`  | 不涉及状态变更，不操作映射   |
| `updateQuestions`     | 不涉及状态变更，不操作映射   |

**4. 删除会话（`deleteSession`）**

[第 185-195 行](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/infrastructure/redis/InterviewSessionCache.java#L185-L195) 先通过 `getSession` 取出 `resumeId`，清理映射，再删除主缓存。顺序很重要——如果先删主缓存，就再也拿不到 `resumeId` 来清理映射了。

**5. 映射删除的安全性保护**

[第 247-254 行](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/infrastructure/redis/InterviewSessionCache.java#L247-L254) 的 `removeResumeSessionMapping` 在删除映射前做了值比对：

```java
String currentSessionId = redisService.get(key);
if (sessionId.equals(currentSessionId)) {
    redisService.delete(key);
}
```

只有当前映射的值确实是这个 `sessionId` 时才删除。这是为了处理一个边界场景：用户对同一份简历先后创建了两个面试会话 A 和 B，映射被 B 覆盖。如果 A 完成时不做比对就直接删除映射，B 的映射会被误删，导致 B 也找不到。

***

### 四、设计亮点

1. **读时修复（Repair-on-Read）**：`findUnfinishedSessionId` 在返回结果前做二次验证，发现脏数据立即清理，不需要额外的定时任务。
2. **值比对防误删**：`removeResumeSessionMapping` 的 equals 判等，防止误删其他会话建立的映射（同简历多会话场景）。
3. **问题列表的 JSON 序列化封装**：将序列化/反序列化逻辑内聚在 `CachedSession` 内部，缓存层使用者不需要感知 JSON 转换细节。
4. **状态驱动的映射生命周期**：映射的创建和销毁完全由会话状态驱动——`CREATED/IN_PROGRESS` 时建立，其他状态时移除，逻辑自洽。
5. **TTL 统一管理**：24 小时过期作为一个静态常量 `SESSION_TTL`，会话和映射使用相同的 TTL，避免映射永不过期的情况。

***

### 五、可改进点

| 问题                    | 位置                      | 说明                                                                             |
| --------------------- | ----------------------- | ------------------------------------------------------------------------------ |
| 读-改-写非原子              | `updateSessionStatus` 等 | 先 `get` 再 `set`，并发更新时可能丢失修改。可用 Redis Hash 的 `hSet` 做字段级更新，或使用 Lua 脚本做 CAS      |
| `updateQuestions` 吞异常 | 第 176-178 行             | 序列化失败仅 `log.error`，调用方无感知，问题列表可能静默丢失                                           |
| 映射 TTL 与会话相同          | 第 244 行                 | 会话过期后映射可能残存（Redis 过期非精确），`findUnfinishedSessionId` 的读时修复能兜底但非完全可靠              |
| 无缓存预热/穿透保护            | 全局                      | `getSession` 直接查 Redis，大量并发查询同一不存在的会话时会击穿到 DB。可加入 `getOrLoad` 模式或 Bloom Filter |

***

### 六、一句话总结

InterviewSessionCache 是一个为面试场景量身定制的缓存层，核心数据结构是"会话缓存 + 简历→会话反向索引"的双 Key 模型，实现了面试断点续答功能；在映射维护上通过"读时修复 + 值比对防误删 + 状态驱动生命周期"保证了缓存一致性；但更新操作采用的读-改-写模式在并发场景下存在丢失更新的风险，更适合当前单用户会话的低并发场景。
