## 阻塞体现在哪里

阻塞读取的关键是这行：

```java
.timeout(Duration.ofMillis(blockTimeoutMs))
```

设了 `timeout` 之后，Redisson 底层调用的是 Redis 的 **`XREADGROUP` 命令并带 `BLOCK` 参数**。效果是：

```
没有 timeout               有 timeout
────────────               ────────────
stream.readGroup(...)      stream.readGroup(...
  → 没消息立刻返回 empty       .timeout(2000ms))
                              → 没消息就挂起 2 秒
                              → 期间有新消息到达，立即返回
                              → 2 秒后仍无消息，返回 empty
```

**阻塞发生在 Redis 服务端**，而不是 Java 代码里 `Thread.sleep()`。消费者的 TCP 连接保持打开，Redis 服务端持有这个请求，有消息时主动推送回来。

另外 `StreamReadGroupArgs.neverDelivered()` 表示只读取**从未投递过的**新消息（不读 pending 中的重试消息），和阻塞无关。

---

## 为什么要用阻塞读取

对比两种消费模式：

| 模式 | 实现方式 | 问题 |
|------|----------|------|
| **轮询** | 循环调 `readGroup()`，没消息就 `Thread.sleep(100ms)` 再查 | CPU 空转、延迟最高 100ms、无意义的网络往返 |
| **阻塞** | 设 `timeout`，Redis 服务端挂起等待 | 零 CPU 开销、消息到达即时返回、一次网络往返 |

打个比方：

- **轮询** = 每隔 5 秒打电话问快递站"我的快递到了吗？"→ 大部分电话白打，浪费双方时间
- **阻塞** = 告诉快递站"我在这等着，到了叫我"→ 不浪费任何通信，到货第一时间通知

在你的项目里，异步任务管道（向量化、简历分析等）的消息产生频率不高但要求**即时处理**，阻塞读取是最优方案——没有消息时消费者线程几乎零开销挂起，消息一来立刻唤醒处理。
