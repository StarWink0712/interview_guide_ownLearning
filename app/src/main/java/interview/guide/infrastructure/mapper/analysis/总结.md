<br />

这几个mapper的作用是将服务端所用的entity转变成返回给前端的DTO类型，和数据库并没有交互。

是的，理解完全正确。总结来说：

1. **这几个 Mapper 是纯粹的 Java 对象转换层**，基于 MapStruct 编译期生成转换代码，负责 Entity ↔ DTO 之间的字段映射
2. **不涉及任何数据库交互**——数据库读写由 `Repository`（JPA）层负责，Mapper 只处理已经查出来的内存对象
3. **转换方向**主要有两种：
   - **正向**：`Entity → DTO`，Service 层从 Repository 拿到 Entity 后，调 Mapper 转为 DTO 再返回给前端
   - **反向**：`DTO/Request → Entity`，前端提交的数据通过 Mapper 映射回 Entity 再持久化（如 `ResumeMapper.toAnalysisEntity`、`InterviewMapper.updateSessionFromReport`）
4. **JSON 字段**（如 `strengthsJson`）直接在 Mapper 中 `ignore`，由 Service 层单独序列化/反序列化，Mapper 只负责平铺字段的搬运

Mapper 分析总结

这 4 个 Mapper 都基于 **MapStruct**（`@Mapper(componentModel = "spring")`），在 `infrastructure/mapper` 层负责 **Entity ↔ DTO** 的转换，避免直接暴露 Entity 给前端。以下是各 Mapper 的职责摘要：

### 整体设计模式总结

```
Controller ──调用──▶ Service ──调用──▶ Mapper ──转换──▶ DTO ──返回──▶ 前端
                         │
                         ▼
                    Repository ──读取──▶ Entity
```

- **统一规范**：全部使用 MapStruct `componentModel = "spring"`，自动注入为 Spring Bean
- **JSON 分离原则**：实体的 JSON 字段（如 `xxxJson`）不在 Mapper 中直接映射，统一由 Service 层做序列化/反序列化后作为参数传入
- **null 安全**：评分类字段通过 `@Named` 工具方法做 null→0 默认值处理
- **组合映射**：复杂 DTO（如 `SessionDetailDTO`、`InterviewDetailDTO`）由 Mapper 提供 `default` 方法手动组合多个数据源
- **模块隔离**：每个业务模块（知识库/RAG聊天/简历/面试）各自维护独立的 Mapper，职责清晰
