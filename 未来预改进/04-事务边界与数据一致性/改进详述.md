# 事务边界与数据一致性 - 改进详述

## 一、为什么做

本项目涉及数据库、Redis、对象存储、LLM、Embedding、WebSocket 等多种外部资源。传统 CRUD 项目里一个 `@Transactional` 往往够用，但在 AI 应用里，如果事务边界不清晰，会出现：

- 事务中调用外部 API，长时间占用数据库连接。
- 对象存储上传成功但数据库保存失败，产生孤儿文件。
- 数据库状态变成 PENDING，但 Redis 入队失败。
- 旧向量删除成功，新向量化失败，导致知识库不可检索。
- 重试时重复保存评估结果。

这个模块目标是梳理所有外部 IO 与数据库事务的边界，让系统状态更稳定。

## 二、目标效果

实现后：

- 事务方法只包含数据库读写。
- LLM、S3、Embedding、Redis 入队都在事务外或通过 afterCommit 执行。
- 文件上传失败、DB 保存失败、任务入队失败都有补偿策略。
- 重新分析、重新向量化、评估任务都具备幂等能力。
- 状态流转清晰可追踪。

## 三、重点问题

### 1. reanalyze 事务内做外部 IO

`ResumeUploadService.reanalyze()` 中有 `@Transactional`，但内部可能从对象存储下载并解析文件，还会发送 Redis Stream 任务。

建议拆分：

```text
事务外下载/解析
-> 事务内更新 resumeText 和状态
-> 事务提交后发送 Stream
```

### 2. vectorizeAndStore 事务内做 Embedding

`KnowledgeBaseVectorService.vectorizeAndStore()` 标了 `@Transactional`，但 `vectorStore.add(batch)` 可能触发外部 Embedding 调用。

建议拆分：

```text
事务外分块和 Embedding
-> 事务内删除旧向量和写入新向量
-> 更新状态
```

如果 Spring AI 的 `VectorStore.add` 同时负责 Embedding 和写 DB，不容易拆，则至少缩小事务，不要把整个方法标事务。

### 3. 上传文件与 DB 保存不一致

简历和知识库上传时，先上传对象存储，再保存 DB。如果 DB 保存失败，可能留下孤儿文件。

建议：

- DB 保存失败时删除对象存储文件。
- 或先保存 DB 元数据为 INIT，再上传文件，上传成功后更新状态。

### 4. 入队失败状态处理

Stream 入队失败后会标记 FAILED，但如果 DB 保存和入队没有 afterCommit，可能出现事务回滚但任务已入队。

建议：

- 事务提交后再入队。
- 使用 Spring `TransactionSynchronizationManager.afterCommit`。
- 或引入 Outbox Pattern。

## 四、推荐方案：Outbox Pattern

对于任务入队，推荐最终升级为 Outbox：

```text
业务事务内：
  保存业务数据
  保存 outbox_event

后台调度：
  扫描未发送 outbox_event
  发送 Redis Stream
  标记 SENT
```

优势：

- DB 和“待发送事件”在同一个事务里。
- Redis 短暂不可用时不会丢任务。
- 可以重试发送。
- 面试表达很有后端深度。

## 五、技术亮点

面试表达：

> 我专门梳理了 AI 项目中的事务边界，避免在事务里调用 LLM、Embedding、对象存储这类外部服务。对于异步任务入队，我计划使用 afterCommit 或 Outbox Pattern，保证数据库状态和消息发送的一致性。
