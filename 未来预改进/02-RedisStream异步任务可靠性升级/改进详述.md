# Redis Stream 异步任务可靠性升级 - 改进详述

## 一、为什么做

当前项目用 Redis Stream 做了简历分析、知识库向量化、面试评估、语音面试评估等异步任务，这是一个很好的后端亮点。但现在更像“基础可用版”，距离生产级任务系统还有优化空间。

主要问题：

- 消费者只读取 `neverDelivered` 消息，服务宕机后 pending 消息可能永久卡住。
- Stream 消息里直接塞全文内容，知识库文本很大时会给 Redis 带来压力。
- 任务失败后只标记实体状态，缺少统一任务视图和死信队列。
- 任务重试缺少退避策略。
- 同一个实体可能重复入队，幂等保护不够清晰。

这个模块目标是把异步系统从“能跑”升级成“可恢复、可追踪、可重试、可管理”。

## 二、目标效果

实现后，可以做到：

- 服务重启后自动恢复超时 pending 消息。
- 失败超过次数后进入 Dead Letter Queue 或失败任务表。
- Stream 消息只传 ID，消费者自行从 DB 或对象存储读取内容。
- 任务有统一管理接口：查看、重试、取消。
- 同一业务 ID 重复入队时可以幂等处理。
- 面试时能讲清楚 Redis Stream 的 PEL、ACK、Claim、DLQ。

## 三、设计方向

### 1. Stream 消息轻量化

当前：

```text
message = { resumeId, content, retryCount }
message = { kbId, content, retryCount }
```

建议：

```text
message = { taskId, businessId, retryCount }
```

正文内容放在：

- DB 字段，例如 `resumeText`。
- 对象存储，例如原始知识库文件。
- 任务表，例如 `AsyncTaskEntity.payloadJson`，只保存必要参数。

### 2. 引入统一任务表

新增 `AsyncTaskEntity`，用于统一记录任务状态。

建议字段：

- `id`
- `taskType`
- `businessId`
- `streamKey`
- `messageId`
- `status`
- `retryCount`
- `maxRetryCount`
- `nextRetryAt`
- `lastError`
- `createdAt`
- `updatedAt`

### 3. Pending 恢复

Redis Stream Consumer Group 有 PEL。消费者读到消息但未 ACK 时，消息会进入 pending。

建议增加：

- 启动时扫描 pending。
- 超过指定 idle 时间后 claim。
- claim 后重新处理或重新入队。

### 4. 死信队列

超过重试次数后：

- 更新业务实体状态为 FAILED。
- 写入 `AsyncTaskDeadLetterEntity`。
- 可选：发送到 `xxx:dlq:stream`。

### 5. 幂等处理

建议为任务增加幂等 key：

```text
taskType + businessId
```

例如：

- `RESUME_ANALYZE:123`
- `KB_VECTORIZE:456`
- `INTERVIEW_EVALUATE:session-xxx`

同一个业务对象如果已经 PROCESSING，可以拒绝重复入队或覆盖旧任务。

## 四、技术亮点

### 亮点 1：宕机可恢复

面试表达：

> Redis Stream 消费时我不仅处理新消息，还处理 pending list。服务在 ACK 前宕机后，下一次启动会扫描超时 pending 消息并 claim 回来继续处理，避免任务永久卡住。

### 亮点 2：统一任务中心

面试表达：

> 简历分析、知识库向量化、面试评估虽然是不同业务，但底层统一抽象成 AsyncTask，统一管理状态、重试次数、失败原因和手动重试。

### 亮点 3：大消息治理

面试表达：

> 我没有把大文本直接塞进 Redis Stream，而是只传 taskId 和业务 ID，消费者从数据库或对象存储读取内容，避免 Redis 承担大对象存储压力。

## 五、推荐最小版本

第一版优先做：

- 修复 `AnalyzeStreamConsumer` 当前的重复方法和 TODO stub 问题。
- Stream 消息只传业务 ID。
- 消费者处理前从 DB 或对象存储读取内容。
- 增加 pending 消息恢复。
- 增加统一任务查询接口。

DLQ 和退避重试可以第二版再做。
