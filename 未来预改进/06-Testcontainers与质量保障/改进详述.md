# Testcontainers 与质量保障 - 改进详述

## 一、为什么做

当前项目涉及 PostgreSQL + pgvector、Redis、S3 兼容对象存储、Spring AI、文件解析、WebSocket 等组件。仅靠 H2 和 Mock 很难覆盖真实行为：

- pgvector 查询和 H2 完全不同。
- Redis Stream pending/ack/retry 需要真实 Redis。
- S3 上传下载需要真实对象存储或兼容服务。
- 文件解析需要真实测试文件。
- RAG 检索需要真实向量表。

这个模块目标是让项目具备更强的自动化验证能力，避免“本地手测能跑，换环境就坏”。

## 二、目标效果

实现后：

- 集成测试可以自动启动 PostgreSQL + pgvector。
- Redis Stream 的生产、消费、ACK、重试可以自动验证。
- 对象存储上传下载可以自动验证。
- RAG 检索可以用小型测试知识库验证。
- CI 或本地一条命令跑关键链路测试。

## 三、测试分层

### 单元测试

适合：

- DTO 转换。
- Prompt 变量构造。
- 评分合并逻辑。
- 文本清洗。
- 文件校验。

### 切片测试

适合：

- Repository 查询。
- Controller 参数校验。
- Mapper 转换。

### 集成测试

适合：

- Redis Stream。
- PostgreSQL + pgvector。
- S3 兼容存储。
- 文件解析。
- RAG 查询。

## 四、建议引入 Testcontainers

容器：

- PostgreSQL with pgvector。
- Redis。
- MinIO。

测试基类：

```text
BaseIntegrationTest
├── PostgreSQLContainer
├── GenericContainer redis
└── MinIOContainer 或 GenericContainer minio
```

通过 `@DynamicPropertySource` 注入：

- datasource url。
- redis host/port。
- storage endpoint/accessKey/secretKey。

## 五、关键测试场景

### Redis Stream

- 生产者能发送任务。
- 消费者能处理任务并 ACK。
- 业务异常后会重试。
- 超过最大重试后标记 FAILED。
- pending 消息恢复逻辑可用。

### RAG

- 上传小型知识库。
- 向量化成功。
- 查询相关问题命中对应文档。
- 查询无关问题返回无结果模板。

### 文件与对象存储

- 上传文件到 MinIO。
- 下载文件内容一致。
- DB 保存失败时对象存储补偿删除。

### 结构化输出

- 模拟模型返回非法 JSON。
- 验证 `StructuredOutputInvoker` 能重试或本地修复。
- 达到最大重试后抛 `BusinessException`。

## 六、技术亮点

面试表达：

> 这个项目不是只靠 Mock 测试。我引入 Testcontainers 跑真实 PostgreSQL + pgvector、Redis 和 MinIO，覆盖 Redis Stream 异步任务、RAG 检索、对象存储上传下载这些真实依赖场景。
