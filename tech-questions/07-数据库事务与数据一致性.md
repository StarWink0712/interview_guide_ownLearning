# 数据库事务与数据一致性

## 1. 面试官：项目为什么选择 PostgreSQL，它承担了哪些角色？

我的回答：

PostgreSQL 既提供成熟的 ACID 事务、索引和关系约束，又可通过 pgvector 扩展支持向量检索，适合把业务数据与中等规模 RAG 索引放在同一技术体系。我的项目用 JPA 保存简历、面试、消息、任务、提醒和观测明细，用 JDBC 删除带 JSON metadata 的向量，pgvector 使用 HNSW、余弦距离和 1024 维。这样部署和事务模型较统一，不必额外维护向量数据库。当前 `ddl-auto=update` 适合开发，不适合生产变更审计；向量规模很大时也要评估专用向量引擎、分区和读写分离。

代码依据：

- `app/src/main/resources/application.yml` — PostgreSQL 与 pgvector 配置
- `app/src/main/java/interview/guide/modules/knowledgebase/repository/VectorRepository.java` — 向量 JDBC
- `docker/postgres/init.sql` — pgvector 初始化
- `docker-compose.yml` — `pgvector/pgvector:pg16`

## 2. 面试官：项目如何划分事务边界，为什么把 PersistenceService 单独拆出？

我的回答：

事务应只包住需要原子提交的数据库读写，范围越小，锁和连接占用越少。我的项目把上传解析、S3、LLM 和 Prompt 编排留在普通 Service，把 `saveResume`、`saveAnalysis`、`saveAnswer`、`updateSessionStatus` 等写操作放入独立 PersistenceService 并标注 `@Transactional`。这样外部 I/O 完成后才开启短事务，也避免同类内部调用事务方法导致 Spring AOP 代理失效。当前仍需逐个审计大型 Service 的注解和仓储调用。生产上我会为每个用例明确事务入口、隔离级别和可重试冲突。

代码依据：

- `app/src/main/java/interview/guide/modules/resume/service/ResumePersistenceService.java` — 事务写入
- `app/src/main/java/interview/guide/modules/interview/service/InterviewPersistenceService.java` — 会话事务
- `app/src/main/java/interview/guide/modules/resume/service/ResumeUploadService.java` — 事务外编排
- `app/src/main/java/interview/guide/modules/interview/service/AnswerEvaluationService.java` — 模型与落库分离

## 3. 面试官：为什么数据库事务中不能包含耗时的大模型或对象存储调用？

我的回答：

数据库事务期间会占用连接、持有行锁和 MVCC 快照，外部网络调用几十秒甚至超时会降低连接池吞吐，扩大死锁与回滚成本。我的项目在简历上传中先解析和上传对象，再进入短事务；向量化先删除旧数据的短事务，随后在事务外请求 embedding；统一评估先拿到模型结果，再保存报告。这样外部服务失败不会让数据库长期挂起。代价是跨阶段不再强一致，需要状态机和补偿。生产上我会给外部调用明确超时与幂等键，并坚持“读取快照—外部计算—条件写回”的三段式。

代码依据：

- `app/src/main/java/interview/guide/modules/resume/service/ResumeUploadService.java` — 上传编排
- `app/src/main/java/interview/guide/modules/knowledgebase/service/KnowledgeBaseVectorService.java` — 向量化事务边界
- `app/src/test/java/interview/guide/modules/knowledgebase/service/KnowledgeBaseVectorServiceTransactionTest.java` — 事务测试
- `app/src/main/java/interview/guide/common/evaluation/UnifiedEvaluationService.java` — 外部评估

## 4. 面试官：数据库、Redis 和对象存储之间如何实现一致性？

我的回答：

三个系统没有共同本地事务，我的项目采用事实源、状态机和补偿实现最终一致性。原文件先上传 S3，再短事务保存元数据；若落库失败，上传 Service 删除刚写入的 storageKey。数据库是长期事实源，Redis 会话丢失可回源重建；异步任务先有数据库状态，再在提交后写 Stream。删除时也尝试清理对象和关联数据。当前补偿删除失败主要记录日志，缓存双写与消息发送仍有空窗，不能宣称强一致。生产上应增加补偿任务、outbox、缓存版本和定期对账，把孤儿对象与卡住任务自动修复。

- `app/src/main/java/interview/guide/modules/knowledgebase/service/KnowledgeBaseUploadService.java` — 知识库补偿
- `app/src/main/java/interview/guide/infrastructure/redis/InterviewSessionCache.java` — 可重建缓存
- `app/src/main/java/interview/guide/common/transaction/TransactionAfterCommitExecutor.java` — 提交后动作

## 5. 面试官：事务提交后发送消息解决了什么问题，发送失败怎么办？

我的回答：

after-commit 避免消费者在数据未提交或最终回滚时执行任务。我的项目通过 `TransactionAfterCommitExecutor` 注册 Spring `TransactionSynchronization.afterCommit`，提交成功后才由 Producer XADD；发送异常时子类会更新分析、向量或评估状态并记录错误。它仍有数据库已提交、进程在发送前崩溃的空窗，回调失败也不会让原事务回滚。当前 Pending 恢复只处理已经进入 Stream 的消息，无法发现漏发。因此生产上需要扫描长期 PENDING/QUEUED 且无 messageId 的任务，或者更彻底地使用事务 Outbox。

代码依据：

- `app/src/main/java/interview/guide/common/transaction/TransactionAfterCommitExecutor.java` — `afterCommit()`
- `app/src/main/java/interview/guide/modules/knowledgebase/listener/VectorizeStreamProducer.java` — `onSendFailed()`
- `app/src/main/java/interview/guide/modules/resume/listener/AnalyzeStreamProducer.java` — 消息状态更新
- `app/src/main/java/interview/guide/modules/asynctask/service/PendingMessageRecoveryService.java` — 恢复边界

## 6. 面试官：Outbox Pattern 如何补齐当前消息一致性空窗？

我的回答：

Outbox Pattern 在同一个数据库事务中同时写业务数据和待发布事件，独立发布器扫描未发布记录写入消息系统，成功后标记 published；即使进程崩溃，事件仍在数据库，可重复投递。我的项目当前只有 AsyncTask 业务表和 after-commit 回调，没有专用 outbox 发布状态、锁定批次与补投器，因此只能部分发现任务，不能保证每次业务变更都有消息。若完善，我会让上传事务写 `outbox_event`，发布器用 `FOR UPDATE SKIP LOCKED` 批量领取，XADD 后记录 messageId；消费者继续幂等，过期 outbox 定期归档。

代码依据：

- `app/src/main/java/interview/guide/modules/asynctask/service/AsyncTaskService.java` — 当前状态管理

## 7. 面试官：项目如何使用幂等键和唯一索引，哪些地方仍不够？

我的回答：

幂等键把重复请求映射到同一业务结果，数据库唯一约束则在并发下提供最终防线。我的项目对简历和知识库使用 fileHash 唯一索引，对 AsyncTask 的 activeKey 建唯一索引，复用同一类型与 businessId 的活动任务；面试答案对 sessionId 与 questionIndex 建唯一约束，提醒对 schedule、channel、timing 建唯一约束。这些设计比“先查再写”可靠。仍不足的是 RAG messageOrder 只有普通索引，部分会话提交没有请求幂等 token，重复 Stream 副作用也未全部条件化。生产上应补唯一约束并正确处理冲突返回已有结果。

代码依据：

## 8. 面试官：乐观锁和悲观锁如何选择，项目实际用了哪一种？

我的回答：

乐观锁通过 version 条件更新发现冲突，适合冲突较少、希望高并发的聚合；悲观锁在事务内先锁行，适合必须串行且临界区短的抢占。我的项目在提醒调度的 `findDueForUpdate` 使用 `PESSIMISTIC_WRITE`，同一时间只有一个实例能把到期提醒从 PENDING 改为 QUEUED。核心会话实体没有统一 `@Version`，Redis 会话更新也主要是读改写，因此并发提交可能覆盖。生产上我会给面试会话、RAG 会话等聚合根加乐观版本，对短任务领取继续使用条件更新或悲观锁，避免把外部发送放在锁内。

## 9. 面试官：JSON 字段和关系表各有什么优缺点，项目如何取舍？

我的回答：

JSON 适合整体读写、结构变化快的聚合快照，关系表适合约束、查询、排序和局部更新。我的项目把面试 questions、report、abilityProfile 和 adaptiveTrace 序列化为 JSON 字符串存在会话实体，恢复时整体读取；答案、RAG 消息、任务和调用明细则单独建表。这样迭代 DTO 快、减少 join，但数据库难以按能力维度查询，旧 JSON 结构升级也缺乏 schema 约束。生产上我会给 JSON 增加 schemaVersion，把高频检索字段提升为列或子表，并用迁移程序兼容旧版本，而不是无限堆积不可查询文本。

## 10. 面试官：强一致和最终一致如何取舍，系统如何做补偿与对账？

我的回答：

用户答案、唯一任务和提醒抢占等本地事实需要数据库事务强一致；缓存、对象副本、向量索引和异步报告允许短时间不一致，只要最终能收敛。我的项目通过短事务、状态枚举、补偿删除、消费者幂等和 Pending 恢复实现部分最终一致，但还没有统一对账中心。生产上我会定义每条链路的不变量，例如 COMPLETED 任务必须存在结果、向量 COMPLETED 必须 chunkCount>0、数据库 storageKey 必须能访问；定时巡检违反项并生成补偿任务。这样一致性不是一句“最终会一致”，而是有状态、超时、检测、修复和告警的闭环。

- `app/src/main/java/interview/guide/modules/asynctask/model/AsyncTaskEntity.java` — 任务状态机
- `app/src/main/java/interview/guide/modules/knowledgebase/model/KnowledgeBaseEntity.java` — 向量状态

# 本章总结

项目以 PostgreSQL 事务保护本地事实，把 LLM、对象存储和 Redis 操作移出长事务，再用唯一约束、状态机、补偿和 after-commit 构造最终一致性。

当前仍缺完整 outbox、聚合根乐观锁与统一对账补偿，生产化必须把这些空窗变成可检测、可重试的状态。

# 核心主线

强一致只覆盖数据库内关键事实，跨系统通过幂等、事件、补偿和对账实现可验证的最终一致。
