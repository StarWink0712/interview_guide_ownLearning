# 消息队列与异步任务

## 1. 面试官：项目为什么使用消息队列，而不是同步处理或本地线程池？

我的回答：

消息队列把任务提交与执行解耦，支持跨进程消费、持久化、重试和削峰；本地线程池只在当前 JVM 内调度，进程退出后排队任务会丢失，也不便统一查询状态。我的项目把简历分析、文档向量化、文字和语音最终评估、面试提醒放入 Redis Stream，HTTP 请求先保存业务事实并快速返回，消费者可稍后调用耗时模型。局部并行如两类题目生成才使用虚拟线程。这样既隔离模型波动，又能恢复未确认消息。当前 Stream 仍依赖单 Redis，生产上需要持久化、主从切换、积压监控和更完整 outbox。

## 2. 面试官：Redis Stream 的核心数据模型是什么，项目如何使用 Consumer Group？

我的回答：

Redis Stream 是追加日志，每条消息有递增 ID 和 field-value 数据；Consumer Group 维护组内最后投递位置与 Pending Entries List，使多个消费者分摊消息并显式 ACK。我的项目为每类任务定义独立 stream、group 和 consumer 前缀，生产者在发送前确保组存在，消费者用随机 consumerName 读取 `>` 新消息。组内同一条新消息只交给一个消费者，多个应用实例可以横向分担；不同组则各自消费完整流。当前消息最大长度近似限制为 1000，适合轻量任务，不承担长期事件归档；审计状态另存 AsyncTask 表。

## 3. 面试官：生产者发送一条异步任务的完整流程是什么？

我的回答：

我的项目先由业务 Producer 校验实体并调用 `AsyncTaskService.createOrReusePendingTask`，按任务类型和业务 ID 复用活动任务；随后构造只含 taskId、业务 ID、retryCount 和 traceId 的轻量消息。若当前有数据库事务，就通过 `TransactionAfterCommitExecutor` 在提交后执行 `AbstractStreamProducer.sendTask`；公共模板确保 Stream/Group 存在，XADD 后记录 messageId、任务 QUEUED 状态和指标。发送失败调用子类 `onSendFailed` 更新业务状态。长文本不进入 Redis，而由消费者凭 ID 从数据库或对象存储读取，降低消息内存与重试成本。

## 4. 面试官：消息发送成功但数据库事务回滚怎么办？

我的回答：

如果事务未提交就发送消息，消费者可能读到尚不存在的实体，或者在业务回滚后仍执行副作用。我的项目通过 `TransactionAfterCommitExecutor` 检查 Spring 事务同步状态：有活动事务就注册 `afterCommit`，只有提交成功才 XADD；回滚不会执行回调。没有事务时则立即发送。这个设计解决“消息先于数据可见”的顺序问题，并有单测验证。它不是分布式事务：数据库提交后、Redis 写入前进程崩溃仍会漏发。生产环境应使用事务 Outbox 或扫描未入队任务补投，而不是宣称 Exactly Once。

## 5. 面试官：如何分析消息是否会丢失，项目已经覆盖哪些阶段？

我的回答：

消息可靠性要分生产前、Redis 持久化、投递、处理和 ACK 五段。我的项目在生产前先落业务与任务表，XADD 失败会更新失败状态；Redis Stream 在 ACK 前把消息放入 PEL，消费者崩溃可 XAUTOCLAIM；业务异常先重投新消息再 ACK 旧消息，避免直接删除；成功后才标记完成并 ACK。仍有两个缺口：after-commit 到 XADD 的进程崩溃空窗，以及 Redis 单节点故障或未正确配置 AOF/复制时的数据风险。生产上要加 outbox、Redis 高可用与持久化、队列对账和长期 QUEUED 告警。

## 6. 面试官：重复消息从哪里产生，项目如何实现消费幂等？

我的回答：

至少一次投递下，消费者处理完成但 ACK 前崩溃、Pending 被重新认领、重试消息与原消息并存或人工重试都会造成重复。我的项目主要依靠 taskId、业务 ID 和数据库状态降低风险：消费者在处理前检查实体是否存在、任务是否取消，简历与向量任务会判断已 COMPLETED 且结果存在后直接跳过，`createOrReusePendingTask` 也减少重复入队。它还不是所有副作用的完整幂等，例如提醒 `markProcessing` 不拒绝已 SENT 状态，邮件可能重复。生产上应增加业务唯一键、数据库唯一索引和条件状态更新。

## 7. 面试官：为什么 Redis Stream 之外还需要 AsyncTask 数据表？

我的回答：

消息队列负责传输，任务表负责业务可见状态和长期审计，二者职责不同。我的项目的 `AsyncTaskEntity` 保存任务类型、businessId、payload 摘要、Stream messageId、PENDING、QUEUED、PROCESSING、RETRYING、COMPLETED、FAILED、CANCELLED、DEAD_LETTER、重试次数和错误信息。管理接口可以查询、取消和人工重试，前端也能展示状态；Stream 消息被 ACK 或裁剪后，任务历史仍然存在。当前状态表与 Redis 不是原子更新，可能出现数据库显示 QUEUED 但没有消息，或消息存在而状态滞后。生产上要做状态对账，并用 outbox 统一投递源。

## 8. 面试官：消费失败如何重试，什么时候进入死信状态？

我的回答：

重试应区分临时故障和永久错误，并限制次数避免毒消息无限循环。我的项目的公共消费者捕获业务异常后读取 retryCount；未超过上限时，子类重新 XADD 一条 retryCount+1 的消息，把任务标为 RETRYING，再 ACK 原消息；达到最大三次后调用 `markFailed` 或 `markDeadLetter` 保存截断错误并 ACK。实体删除等 `AsyncTaskCancelledException` 不重试，直接取消。当前重试基本是立即重新入队，没有指数退避、延迟队列和错误分类，Provider 限流时可能快速重复失败。生产上会按错误类别设置退避、最大时间窗和人工重放。

## 9. 面试官：什么是 Pending Entries List，为什么不能只读取新消息？

我的回答：

PEL 记录 Consumer Group 已投递但尚未 ACK 的消息，包括所属消费者、空闲时间和投递次数。若只读取 `>` 新消息，进程在处理途中宕机后，旧消息会一直留在 PEL，不会自动作为新消息再次出现。我的项目正常消费成功后 ACK，异常未完成的消息可由 `recoverPendingMessages` 使用 XAUTOCLAIM 认领，再走同一解析、状态检查、业务处理和 ACK 流程。PEL 提供的是恢复线索，不代表业务一定可安全重做；消费者仍需幂等。监控上还应统计 pending 数量、最大 idle 和重投次数。

## 10. 面试官：消费者宕机后，项目如何自动恢复未确认消息？

我的回答：

我的项目由 `PendingMessageRecoveryService` 收集所有 `AbstractStreamConsumer` Bean，在应用启动完成后立即扫描一次，之后每 60 秒扫描。它为每个消费者组调用 XAUTOCLAIM，认领 idle 超过 60 秒的消息，单批最多 10 条，并重新执行消费逻辑；某个消费者恢复失败不会阻断其他管道。这样覆盖 kill -9、网络断开和应用重启后的 PEL 残留。边界是正常任务若处理超过 60 秒也可能被另一实例误认领，形成并发执行。生产上应按任务类型设置超时、使用执行租约或心跳，并使业务写入可幂等。

## 11. 面试官：项目能保证消息按顺序消费吗？

我的回答：

单个 Stream 的消息 ID 按追加顺序增长，当前每个消费者实例只有一个长期消费循环，批次内也逐条处理，因此单实例通常保持读取顺序。但 Consumer Group 的目标是分摊消息，多实例或多个消费者时，不同消息可以并行处理，完成顺序不再等于写入顺序；失败重试又会生成一个更晚的新 ID。我的项目的简历、知识库等任务大多按不同 businessId 独立，不依赖全局有序。若同一业务必须顺序执行，我会按 businessId 分区到固定 Stream，或在数据库中用版本号拒绝旧事件，而不是依赖偶然的单线程。

## 12. 面试官：什么情况下无法保证全局有序，如何设计局部有序？

我的回答：

全局有序要求所有消息串行通过一个分区和一个消费者，会牺牲吞吐与可用性；多 Stream、多组、多消费者、重试和网络延迟都会打破完成顺序。我的项目有多条独立 Stream，任务类型之间本就没有全局顺序；同一实体的重新分析与删除若并发，主要依赖消费者重新检查实体状态来避免错误写回。生产上我只保证必要的聚合根有序：消息携带 entityVersion 或 sequence，按 businessId hash 分区，消费者条件更新 `where version=expected`，过期事件直接丢弃。跨业务全局顺序通常没有实际价值，不应为它牺牲所有并发。

## 13. 面试官：消息积压是怎样产生的，如何发现和处理？

我的回答：

当生产速率持续高于消费速率，或下游 LLM、Embedding、数据库变慢时就会积压；毒消息重试和消费者停机也会扩大 backlog。我的项目单个 `AbstractStreamConsumer` 实例基本串行处理，AI 任务又耗时，因此突发上传很容易让 Stream 长度和 Pending 上升。现有 `AsyncTaskMetricsRecorder` 记录任务 created、processing、completed、retry、failed，但缺少明确的 Stream lag、backlog 和 oldest-message-age Gauge。生产上我会先告警这些指标，再限流生产端、按任务类型扩消费者、批处理 embedding，并对低优先级任务降级或暂停。

## 14. 面试官：多个消费者如何扩容，扩容时要注意什么？

我的回答：

Consumer Group 会把同组新消息分配给不同 consumer，因此可以增加应用实例或同一实例的消费 worker 来扩吞吐。我的项目 consumerName 带随机 UUID，天然支持多实例加入同一 group；但每个 Bean 只启动一个单线程循环，单实例并发有限。扩容不能只加线程，还要看 Provider QPS、数据库连接、对象存储带宽和同一 businessId 的并发冲突。我的生产方案会按任务类型建立独立并发上限与舱壁，先保证幂等和版本控制，再增加 worker；缩容前要停止拉新消息、等待在途任务结束，让 PEL 可被安全接管。

## 15. 面试官：为什么选 Redis Stream，而不是 Kafka 或 RabbitMQ？

我的回答：

Redis Stream 适合已有 Redis、消息规模中小、需要 Consumer Group 与 Pending 恢复的轻量系统，部署和开发成本低。我的项目本来就用 Redis 做缓存与限流，异步任务量有限，消息只传业务 ID，因此 Stream 能满足当前需求。RabbitMQ 在路由、确认、延迟队列和死信交换机上更成熟；Kafka 更适合超高吞吐、长时间保留、分区顺序和事件回放。当前 Stream 最大长度约 1000、Redis 单节点、重试需应用自己实现，不适合作为长期事件总线。如果任务量和审计回放需求显著上升，我会评估 Kafka；复杂投递路由则更偏 RabbitMQ。

# 本章总结

项目用 Redis Stream 将耗时 AI 任务从请求线程中解耦，并通过 Consumer Group、PEL、XAUTOCLAIM、重试和 AsyncTask 状态表形成至少一次处理链路。

当前不能宣称 Exactly Once：after-commit 仍有漏发空窗，幂等覆盖不完整，重试无退避，积压指标和 Redis 高可用也需要补齐。

# 核心主线

以轻量持久消息传递业务 ID，用任务状态、Pending 恢复和业务幂等把至少一次投递收敛为可控结果。
