# 安全认证与权限控制

## 1. 面试官：项目当前是否已经实现登录认证和权限控制？

我的回答：

我的项目当前没有完整实现这一部分。构建文件没有 Spring Security，代码中没有 SecurityFilterChain、JWT/OIDC 校验、方法授权或可信 Principal；部分实体虽然有 userId，语音服务会回退到默认用户，限流还可直接读取 `X-User-Id`。因此管理端 Provider 配置、任务重试、简历和知识库接口缺少真正身份与资源所有权验证。现有 CORS、限流和 Prompt 清洗都不能替代认证。生产化第一步应接入 OIDC/JWT，统一从认证上下文取得 userId，并默认拒绝未授权访问。

代码依据：

- `app/build.gradle` — 当前无 Spring Security
- `app/src/main/java/interview/guide/modules/voiceinterview/service/VoiceInterviewService.java` — 默认 userId
- `app/src/main/java/interview/guide/common/aspect/RateLimitAspect.java` — `X-User-Id`
- `app/src/main/java/interview/guide/modules/llmprovider/controller/LlmProviderController.java` — 敏感管理接口

## 2. 面试官：如果补认证，你会选择 Session、JWT 还是 OIDC？

我的回答：

Session 便于服务端撤销但需要共享存储；JWT 自包含、适合多实例，但撤销和权限变更有延迟；OIDC 在 OAuth2 上提供标准身份，适合接企业或第三方认证。我的项目是 React SPA 加 Spring Boot API，还包含 WebSocket，生产上我优先选择 OIDC Authorization Code + PKCE，由后端验证短期 access token，并在必要时用 Redis 保存撤销或会话状态。当前 `HttpSessionHandshakeInterceptor` 只复制 Session 属性，没有形成认证。无论方案如何，token 都不应放在可记录的 WebSocket URL 长期参数中，可使用一次性短票据。

代码依据：

- `frontend/src/App.tsx` — SPA 路由
- `app/src/main/java/interview/guide/modules/voiceinterview/config/WebSocketConfig.java` — 当前握手拦截器
- `app/build.gradle` — 待补安全依赖
- `app/src/main/java/interview/guide/infrastructure/redis/RedisService.java` — 可用撤销状态基础

## 3. 面试官：管理接口如何设计 RBAC 和最小权限？

我的回答：

RBAC 把权限赋给角色，再把角色赋给用户；最小权限要求普通用户只能访问自己的材料与会话，管理员也只获得必要运维能力。我的项目设置页可以管理 LLM Provider、ASR/TTS 配置，管理端还能查看 AI trace、RAG 评测和重试任务，这些当前没有角色保护。生产上我会定义 USER、OPS、AI_ADMIN 等角色：用户访问个人业务；OPS 只能看脱敏指标与任务；AI_ADMIN 才能修改密钥和默认模型。Controller 路由与 Service 资源校验都要授权，并记录谁在何时修改了什么，不能只靠前端隐藏菜单。

代码依据：

- `app/src/main/java/interview/guide/modules/llmprovider/controller/LlmProviderController.java` — Provider 管理
- `app/src/main/java/interview/guide/modules/asynctask/AsyncTaskController.java` — 任务重试
- `app/src/main/java/interview/guide/modules/aiobservability/AiObservabilityController.java` — Trace 与评测
- `frontend/src/pages/AdminDashboardPage.tsx` — 当前管理入口

## 4. 面试官：多租户和资源所有权应如何落地？

我的回答：

多租户隔离不能只在 Controller 接收 userId，而要让每次查询和更新都带可信 tenant/user 条件。我的项目多数 Resume、KnowledgeBase 和 Interview 实体没有统一 tenantId，语音虽然有 userId，也允许请求参数为空后使用默认值，因此当前不是多租户系统。生产上我会在核心表增加 tenantId、ownerId 和组合索引，Repository 方法强制按 tenant 查询，Service 对关联资源再次校验；对象 key 和向量 metadata 也加入 tenant，RAG filter 同时限制 tenantId 与 kbId。高安全场景还可用 PostgreSQL Row Level Security 做最后防线。

代码依据：

- `app/src/main/java/interview/guide/modules/resume/model/ResumeEntity.java` — 当前无 tenantId
- `app/src/main/java/interview/guide/modules/knowledgebase/model/KnowledgeBaseEntity.java` — 当前无 tenantId
- `app/src/main/java/interview/guide/modules/voiceinterview/model/VoiceInterviewSessionEntity.java` — 当前 userId
- `app/src/main/java/interview/guide/modules/knowledgebase/service/KnowledgeBaseVectorService.java` — metadata filter

## 5. 面试官：WebSocket 为什么需要单独鉴权，怎样防止会话劫持？

我的回答：

WebSocket 握手后会长期保持连接，普通 REST 过滤器的单次检查不等于后续消息始终可信；攻击者若猜到 sessionId，可能连接他人语音会话。我的项目当前路径直接包含 sessionId，握手只使用 `HttpSessionHandshakeInterceptor`，Handler 查询会话但没有验证 Principal 与 owner，也没有一次性连接票据。生产上我会在 REST 创建会话后签发短期、单会话、单次使用 token，握手验证签名、Origin、用户和 session owner；连接建立后把 Principal 固定到 attributes，每条控制消息只使用服务端绑定身份，并限制并发连接和重放。

代码依据：

- `app/src/main/java/interview/guide/modules/voiceinterview/config/WebSocketConfig.java` — 握手配置
- `app/src/main/java/interview/guide/modules/voiceinterview/handler/VoiceInterviewWebSocketHandler.java` — `afterConnectionEstablished()`
- `app/src/main/java/interview/guide/modules/voiceinterview/controller/VoiceInterviewController.java` — 会话创建
- `frontend/src/api/voiceInterview.ts` — WebSocket URL 使用

## 6. 面试官：CORS、CSRF 和认证之间是什么关系？

我的回答：

CORS 是浏览器跨源读取限制，不阻止 curl 或后端客户端；CSRF 利用浏览器自动携带 Cookie 发起跨站请求；认证回答“是谁”，授权回答“能做什么”。我的项目统一限制 `/api/**` 的 allowed origins，并允许 credentials，但尚无认证和 CSRF 策略，因此 CORS 只减少浏览器误调用。若采用 Cookie Session，必须启用 CSRF token、SameSite 和安全 Cookie；若 SPA 用 Authorization Bearer token，CSRF 风险较低但仍要防 XSS 窃取 token。WebSocket 还要单独校验 Origin，不能直接照搬 REST CORS。

代码依据：

- `app/src/main/java/interview/guide/common/config/CorsConfig.java` — CORS 配置
- `app/src/main/java/interview/guide/common/config/CorsProperties.java` — Origin 白名单
- `app/src/main/java/interview/guide/modules/voiceinterview/config/WebSocketConfig.java` — WebSocket Origin
- `frontend/src/api/request.ts` — 当前请求客户端

## 7. 面试官：Provider API Key 如何保护，当前实现有什么边界？

我的回答：

API Key 不应明文返回、写日志或随源码提交，落库时应使用认证加密并由外部密钥管理。我的项目的 `ApiKeyEncryptionService` 使用 AES-GCM，Provider DTO 返回掩码，主密钥从环境变量读取；还支持 `require-encryption-key` 强制模式，运行时配置写到用户目录而非 jar 内资源。当前开发默认允许主密钥为空，Compose 和 YAML 也含默认开发凭据，若直接用于生产风险很高。生产上应使用 KMS/Vault 注入和轮换密钥，限制解密权限，配置修改写审计，并禁止把密钥出现在异常和观测明细中。

代码依据：

- `app/src/main/java/interview/guide/modules/llmprovider/service/ApiKeyEncryptionService.java` — AES-GCM
- `app/src/main/java/interview/guide/modules/llmprovider/service/LlmProviderConfigService.java` — 掩码与保存
- `app/src/main/resources/application.yml` — 加密开关
- `.env.example` — 环境变量模板

## 8. 面试官：Prompt Injection 和 Tool Calling 会带来哪些安全风险？

我的回答：

Prompt Injection 可诱导模型忽略系统约束，Tool Calling 又把文本攻击升级为真实副作用，因此工具必须最小权限和参数校验。我的项目对简历、JD、问题做规则清洗与边界包裹，RAG 添加“资料是数据不是指令”的安全约束；默认 ChatClient 可注册 SkillsTool，但结构化 plain 客户端不带工具。当前 Skill 主要是知识资源，没有高风险写操作，仍没有工具审批、用户授权和调用策略引擎。生产上我会将只读与写工具分级，写操作要求服务端再次授权或人工确认，并记录完整 tool name、参数摘要和结果。

代码依据：

- `app/src/main/java/interview/guide/common/ai/PromptSanitizer.java` — 输入清洗
- `app/src/main/java/interview/guide/common/ai/PromptSecurityConstants.java` — 固定安全约束
- `app/src/main/java/interview/guide/common/ai/AgentUtilsConfiguration.java` — `SkillsTool`
- `app/src/main/java/interview/guide/common/ai/LlmProviderRegistry.java` — plain/default 隔离

## 9. 面试官：上传文件和对象存储有哪些安全风险？

我的回答：

风险包括伪造 MIME、恶意解析文件、病毒、路径穿越、超大文件、未授权下载和公共 URL 泄露。我的项目已做大小限制、Tika 实际 MIME 白名单、随机 storageKey、嵌入文档禁用和对象存储隔离；但没有病毒扫描和解析沙箱，Compose 初始化还把 MinIO bucket 设置为公共读，数据库接口也缺资源所有权验证。生产上新文件应进入 quarantine bucket，杀毒和解析通过后再转正式桶；桶默认私有，下载通过鉴权接口或短期签名 URL；对象 key 不包含敏感文件名，并记录访问审计。

代码依据：

- `app/src/main/java/interview/guide/infrastructure/file/FileValidationService.java` — 文件校验
- `app/src/main/java/interview/guide/infrastructure/file/DocumentParseService.java` — 解析限制
- `app/src/main/java/interview/guide/infrastructure/file/FileStorageService.java` — 对象 key
- `docker-compose.yml` — 当前公共 bucket

## 10. 面试官：用户材料、日志和限流标识如何兼顾隐私与审计？

我的回答：

隐私要求最小化收集、限定用途和保留期，审计要求能回答谁访问了什么、何时发生、结果如何。我的项目保存简历文本、语音转写、RAG 消息和 AI 调用明细，traceId 可关联问题；观测日志通常保存长度、哈希或截断预览，而不是无限复制全文。当前没有完整用户授权、数据保留与删除审计，RAG chunk 预览仍可能含敏感内容；IP/USER 限流标识也缺可信身份。生产上我会分类字段、加密敏感列、日志脱敏、设置 retention 和用户删除流程，审计访问本身也要 RBAC，并避免在指标标签放 userId。

代码依据：

- `app/src/main/java/interview/guide/modules/aiobservability/service/AiInvocationLogService.java` — AI 明细
- `app/src/main/java/interview/guide/modules/aiobservability/service/RagRetrievalLogService.java` — chunk 预览
- `app/src/main/java/interview/guide/common/observability/TraceIdFilter.java` — traceId
- `app/src/main/java/interview/guide/common/aspect/RateLimitAspect.java` — IP/USER 标识

# 本章总结

项目已有 CORS、限流、文件校验、Prompt 清洗和 API Key 加密等安全基线，但尚无真正的认证、RBAC、多租户和资源所有权闭环。

生产上线必须先建立可信身份，再保护 WebSocket、管理接口、对象下载和观测数据；任何输入清洗都不能替代授权。

# 核心主线

从可信身份出发执行最小权限和资源隔离，再以密钥、输入、存储、日志和审计的纵深防御降低 AI 应用风险。
