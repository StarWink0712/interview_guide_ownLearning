# 项目介绍与系统架构

## 1. 面试官：请从技术视角介绍这个项目的核心能力和完整链路。

我的回答：

我的项目是一个智能面试平台，核心功能是用户可以上传自己的简历，根据简历内容调用llm出面试题，然后逐个回答，并对答案进行统一评估。同时支持语音面试，前后端通过websocket连接，传递语音wac字节数组，同时调用阿里云的ASR和TTS语音识别和语音合成服务，由llm进行出题。同时支持RAG知识库问答，用户可以上传pdfword等文档，对其向量化后存到postgresql和rustfs对象存储中，用户问问题时进行向量化检索查找对应的文档内容合并到提示词中给llm进行回答。

<br />

我的项目是一个模块化单体 AI 面试平台，核心不是单一聊天接口，而是把文件处理、模型调用、检索、异步任务和实时语音组成闭环。简历或知识库文件先经校验、Tika 解析和 S3 兼容存储，再由 Redis Stream 驱动分析或向量化；文字面试结合简历、Skill 资料和历史题生成问题，并逐轮评估；RAG 用 pgvector 召回上下文；语音链路通过 WebSocket 串联 PCM、ASR、流式 LLM 和 TTS。PostgreSQL 保存事实数据，Redis 承担缓存、限流和消息协调，统一 LLM Registry 屏蔽 Provider 差异。

## 2. 面试官：为什么采用模块化单体，而不是直接拆成微服务？

我的回答：

模块化单体是在一个部署单元内按业务边界组织代码，先获得清晰职责，再避免过早承担网络通信和分布式事务成本。我的项目只有一个 Gradle 应用模块，但简历、面试、知识库、Provider、异步任务、日程和语音分别拥有 Controller、Service、Repository，共享 `common` 与 `infrastructure`。当前规模下它便于本地调试、事务管理和一次部署；Redis Stream 又使耗时消费者未来可以先独立扩容。项目没有注册中心、服务发现、网关熔断或跨服务追踪，所以我不会称它为微服务。生产量上升后，我会优先按语音连接和 AI 消费任务的容量边界拆分。

## 3. 面试官：项目的分层架构如何落地，各层怎样避免职责混乱？

ai调用层，包括llm注册中心，结构化llm调用输出器，异步任务层，日志记录层，幂等控制层等。具体业务分为简历管理层，面试会话层，rag层，语音面试层，面试日志层等。

我的回答：

分层的核心是让入口、业务编排、持久化和技术设施分别变化。我的项目中 Controller 负责路由、`@Valid`、限流与响应包装；Service 编排模型、文件、缓存和仓储；Repository 基于 Spring Data JPA；Tika、S3、Redis、PDF 与 MapStruct 放在基础设施层。为缩短事务，复杂模块又把纯业务编排与 `PersistenceService` 分开，例如上传服务先执行外部 I/O，再调用事务方法落库。优点是测试可以替换依赖，异常与 DTO 也有统一出口。当前个别 Service 和 WebSocket Handler 仍然偏大，后续会按协议适配、状态机和持久化继续拆分。

## 4. 面试官：PostgreSQL、Redis 和对象存储在系统中如何分工？

Redis主要做限流还有消息队列，postgre存业务数据，同时加了pervector插件后存向量数据库，rustfs对象存储存用户的文件和上传的知识库文档。

<br />

我的回答：

不同存储应匹配数据寿命和访问模式。我的项目用 PostgreSQL 保存简历、会话、答案、报告、任务和观测明细，并借助 pgvector 保存可检索向量；Redis 保存带 TTL 的面试会话、滑动窗口限流状态，并通过 Stream 传递异步任务；S3 兼容存储保存 PDF、Word 等大文件。这样大二进制不占关系库，缓存丢失也能从数据库恢复，消息只传 ID 而不复制长文本。当前 Compose 中三类依赖都是单节点，MinIO bucket 甚至采用开发期公共读配置；生产环境需要私有桶、备份、复制、故障切换和容量监控。

## 5. 面试官：系统如何决定同步处理还是异步处理？

简历评估，向量化，语音面试评估，面试会话最终评估都用消息队列异步评估，目的是为了削峰平谷，也让这些耗时的操作不阻碍主线程。

<br />

我的回答：

同步适合用户必须立即得到结果、耗时可控的操作；异步适合长耗时、可重试且允许稍后查询的任务。我的项目把文件元数据保存、答案提交和普通查询放在同步链路，而简历评分、知识库向量化、文字与语音最终评估放入 Redis Stream。上传接口先可靠保存文件与数据库记录，随后返回任务状态，前端再轮询结果；RAG 与语音对话需要即时反馈，则使用 SSE 或 WebSocket 流式返回。这样缩短 HTTP 占用并隔离模型波动。边界是即时自适应评估仍在答题请求内，流量增大时可拆成可补算的子任务。

## 6. 面试官：Spring AI 在项目架构中承担了哪些职责？

我的回答：

## 7. 面试官：文字面试和语音面试如何复用能力，又为什么没有完全共用一套流程？

无法复用，二者协议都不同，文字面试前端通过http请求发起面试请求，llm根据面试题目数量一次出完全部的题目返回给前端。而语音面试是需要通过stream流式调用llm的，这样可以把llm返回的内容实时推送给前端，同时同步调用TTS语音一句句的合成返回给前端。

<br />

我的回答：

复用应发生在稳定的领域能力，而不是强行统一不同协议。我的项目让文字和语音最终评估都转换成 `QaRecord`，共同调用 `UnifiedEvaluationService`，因此批量评分、维度总结和失败聚合口径一致；技能资料、Provider Registry、Prompt 安全和观测基础也被共享。文字链路以明确题目索引和答案提交为主，语音链路则需要处理 ASR partial/final、话语合并、阶段切换、流式 LLM 与 TTS，所以保留独立状态机和持久化实体。这样既避免复制评分逻辑，也不让实时协议污染普通请求。后续可继续统一评测 rubric，而不是合并两种会话模型。

## 8. 面试官：系统对外部依赖失败采用什么总体策略？

我的回答：

外部依赖不可控，因此我按“核心事实不能丢、增强能力可降级”设计。我的项目先保存用户文件或答案，再调用可失败的 AI 增强；出题失败可回退本地通用题，RAG 查询改写失败继续使用原问题，自适应评估失败不阻断答案提交，最终报告交给可重试 Stream。数据库、Redis 和对象存储异常则使用业务错误码、补偿删除或任务失败状态。当前也有过度降级：简历评分把异常变成零分结果，语音 LLM 把错误变成普通文本，可能误报成功。生产化时我会统一错误分类，让可接受降级与基础设施失败拥有不同状态和告警。

## 9. 面试官：当前系统最可能先遇到哪些性能瓶颈？

其实就是问这个系统的性能瓶颈在哪？我认为一般是llm和asr与tts的配额与延迟，齐次是redis消息队列，吞吐量是不如rocketmq和kafka的。而llm调用受到llm提供方的现在，单次调用延迟较高，即模型服务通常会限制qps，并发数以及每分钟token数等。

<br />

可以这样回答，重点不是简单说“LLM 慢”，而是说明它为什么会成为系统吞吐量的上限。

我的回答：

性能瓶颈是系统中处理能力最低、最先限制整体吞吐量的环节。我的项目最可能首先受到 LLM、Embedding、ASR 和 TTS 等外部 AI 服务限制，其中 LLM 尤其明显。

主要有四个原因：

第一，LLM 单次调用延迟高。普通数据库或 Redis 操作通常是毫秒级，而生成面试题、评估答案可能需要几秒甚至几十秒。结构化输出解析失败时还会重新调用模型，延迟和消耗都会叠加。

第二，LLM 吞吐量受 Provider 配额限制。模型服务通常限制 QPS、并发数或每分钟 Token 数。即使我使用 Java 21 虚拟线程，也只能降低线程等待成本，不能提高模型服务本身的处理能力。大量请求同时进入时，最终可能收到 429 限流。

第三，一个业务操作可能包含多次模型调用。例如面试出题会并行生成简历题和技能题，自适应面试还要进行单轮评价、能力画像更新和下一题决策；最终报告又需要分批评价和综合总结。因此一个用户请求可能放大为多次 LLM 请求。

第四，LLM 的响应长度和上下文长度会影响耗时。简历、历史消息、技能资料和 RAG 上下文越长，输入 Token 越多；回答越长，生成时间也越长。

所以我不会仅靠增加应用线程解决问题。我的项目当前通过 Redis Stream 异步执行简历分析、向量化和最终评估，通过分批评估、上下文截断、失败降级以及语音 TTS 并发限制降低压力。

如果继续生产化，我会先监控各阶段的 P95/P99 延迟、Provider 429 数量、Token 使用量和在途请求数，再按 Provider 设置 Semaphore 或舱壁并发限制，增加超时、熔断、缓存和备用模型。只有监控数据证明 LLM 是最慢且最先饱和的环节，才能最终确认它是实际瓶颈。

<br />

## 10. 面试官：如果把当前项目演进到生产系统，你会如何分阶段推进？

我的回答：

我会按风险闭环推进。第一阶段补 Spring Security、资源所有权、私有对象存储和强制密钥加密；第二阶段修复简历异常误报、after-commit 入队空窗、重复消息幂等和并发会话更新；第三阶段恢复禁用的语音测试，接通 Actuator、Prometheus、告警和容量指标；第四阶段按压力拆分语音网关与异步消费者，部署 PostgreSQL、Redis 和对象存储高可用，并加入 Provider 熔断与降级。当前 Compose 只是可复现单机环境，不是生产集群。这个顺序先保障数据安全与正确性，再优化性能，避免用扩容掩盖一致性缺陷。

# 本章总结

项目是以 Spring Boot 模块化单体为核心、由 PostgreSQL、Redis、对象存储和统一 AI 网关协作的多形态 AI 应用。技术设计强调短事务、异步隔离、流式反馈和共享基础能力。

当前架构适合快速迭代，但不应被描述为微服务或高可用系统；生产化重点是安全、一致性、观测和容量隔离。

# 核心主线

用模块化单体承载业务事实，以异步和流式边界隔离昂贵且不稳定的 AI 外部调用。
