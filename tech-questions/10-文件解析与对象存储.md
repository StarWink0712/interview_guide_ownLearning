# 文件解析与对象存储

## 1. 面试官：文件上传为什么需要业务层和框架层两级大小限制？

我的回答：

框架层限制保护服务器在请求解析阶段不接收过大 multipart，业务层限制则能按文件用途制定不同规则并返回明确错误。我的项目在 `application.yml` 把全局上传限制设为 50MB，以支持知识库；简历上传在 `ResumeUploadService` 单独限制 10MB，知识库使用 50MB，并统一调用 `FileValidationService` 检查空文件、文件名和大小。这样不会为了知识库放宽简历规则。当前 Nginx、Spring 和前端超时/大小需要保持一致，否则请求可能在更前层被拒绝。生产上还应限制并发上传和总租户配额。

代码依据：

- `app/src/main/resources/application.yml` — multipart 50MB
- `app/src/main/java/interview/guide/modules/resume/service/ResumeUploadService.java` — `MAX_FILE_SIZE`
- `app/src/main/java/interview/guide/infrastructure/file/FileValidationService.java` — `validateFile()`
- `frontend/src/api/request.ts` — 上传超时

## 2. 面试官：为什么不能相信文件扩展名和浏览器 Content-Type？

我的回答：

扩展名和请求头都由客户端提供，攻击者可以把可执行文件改名为 PDF，浏览器也可能标错 MIME。我的项目读取真实文件字节，通过 Apache Tika Detector 识别内容类型，再与 PDF、DOC、DOCX、TXT 白名单比对；原始文件名只用于展示和生成安全存储名，不决定解析器。这样降低伪装文件进入解析链路的风险。检测仍不是病毒扫描，也无法保证 Office 宏和恶意 PDF 安全。生产环境应在隔离区保存新文件，接入杀毒与内容安全扫描，通过后再进入解析和公开下载流程。

代码依据：

- `app/src/main/java/interview/guide/infrastructure/file/ContentTypeDetectionService.java` — 实际 MIME 检测
- `app/src/main/java/interview/guide/infrastructure/file/FileValidationService.java` — 类型白名单
- `app/src/main/java/interview/guide/modules/resume/service/ResumeParseService.java` — 解析入口
- `app/src/main/resources/application.yml` — 允许类型

## 3. 面试官：Apache Tika 在项目中如何解析不同格式？

我的回答：

Tika 通过统一 Parser 接口自动识别并抽取多种文档文本，避免为 PDF、Word 和纯文本分别维护库。我的项目使用 `AutoDetectParser`、Metadata 和 BodyContentHandler，PDF 解析配置为按位置排序、不提取内联图片，Word 等嵌入内容由 `NoOpEmbeddedDocumentExtractor` 阻止；解析结果再交给清洗服务。这样简历和知识库复用一套解析基础设施。当前 Tika 只得到逻辑文本，复杂表格、双栏和扫描 PDF 质量有限。生产上会按 MIME 选择专用解析/OCR，并记录页码与章节结构供 RAG 引用。

代码依据：

- `app/src/main/java/interview/guide/infrastructure/file/DocumentParseService.java` — `AutoDetectParser`
- `app/src/main/java/interview/guide/infrastructure/file/NoOpEmbeddedDocumentExtractor.java` — 禁用嵌入文档
- `app/src/test/java/interview/guide/infrastructure/file/DocumentParseServiceTest.java` — 解析测试
- `app/src/test/java/interview/guide/infrastructure/file/DocumentParseIntegrationTest.java` — 格式集成测试

## 4. 面试官：如何防止文档解析造成内存、CPU 或嵌套资源攻击？

我的回答：

不受控解析器可能遭遇压缩炸弹、超大文本、递归嵌入文件和恶意格式，必须限制输入与输出资源。我的项目先限制上传大小，`DocumentParseService` 又限制最大提取文本约 5MB，关闭嵌入文档和 PDF 图片抽取，解析异常统一转成业务错误；这能减少常见资源风险。当前解析仍在应用进程内，没有强制 CPU 时间、独立内存和进程级隔离，一份构造文件仍可能拖慢 JVM。生产上我会把解析放进沙箱 worker，设置 deadline、容器资源限制和熔断，并在入口做病毒扫描。

代码依据：

- `app/src/main/java/interview/guide/infrastructure/file/DocumentParseService.java` — 文本上限与解析配置
- `app/src/main/java/interview/guide/infrastructure/file/FileValidationService.java` — 输入大小
- `app/src/main/java/interview/guide/infrastructure/file/NoOpEmbeddedDocumentExtractor.java` — 嵌入限制
- `app/src/main/java/interview/guide/common/exception/ErrorCode.java` — 文件错误码

## 5. 面试官：文本清洗为什么是独立步骤，过度清洗有什么风险？

我的回答：

解析器输出常含控制字符、重复空行、图片文件名、file URL、HTML 和版式分隔线，这些噪声会浪费 token、干扰简历评分和 RAG 切块。我的项目用 `TextCleaningService` 统一规范换行、过滤不可见控制字符、移除图片/URL/无意义分隔并提供 HTML 清理，简历与知识库共享。独立组件便于测试和迭代。清洗过度也会删除有意义的代码 URL、负号列表或表格结构，改变原文语义。生产上应按文档类型选择规则，保留原始文本与清洗版本，并用差异样本测试召回和模型质量。

代码依据：

- `app/src/main/java/interview/guide/infrastructure/file/TextCleaningService.java` — `cleanText()`
- `app/src/test/java/interview/guide/infrastructure/file/TextCleaningServiceTest.java` — 清洗测试
- `app/src/main/java/interview/guide/modules/resume/service/ResumeParseService.java` — 简历调用
- `app/src/main/java/interview/guide/modules/knowledgebase/service/KnowledgeBaseParseService.java` — 知识库调用

## 6. 面试官：内容哈希如何实现文件去重，有什么局限？

我的回答：

内容哈希对文件字节计算稳定摘要，同名不同内容不会冲突，不同名但完全相同的文件会得到同一结果。我的项目使用 SHA-256，简历和知识库实体都对 fileHash 建唯一索引，上传前先查询已有记录，避免重复存储、解析和模型调用；数据库唯一约束又防止并发请求同时插入。它只能识别字节级重复，PDF 元数据变化、重新导出或文本等价但编码不同都会产生新 hash。若需要语义去重，我会额外对规范化文本计算 hash，并把近似重复作为提示而不是自动合并。

代码依据：

- `app/src/main/java/interview/guide/infrastructure/file/FileHashService.java` — SHA-256
- `app/src/main/java/interview/guide/modules/resume/model/ResumeEntity.java` — 唯一 hash
- `app/src/main/java/interview/guide/modules/knowledgebase/model/KnowledgeBaseEntity.java` — 唯一 hash
- `app/src/main/java/interview/guide/modules/resume/service/ResumePersistenceService.java` — 查重

## 7. 面试官：为什么使用 S3 兼容对象存储，而不是本地磁盘或数据库 BLOB？

我的回答：

对象存储适合大文件、按 key 访问、容量横向扩展和与应用实例解耦；本地磁盘在多实例下不可共享，数据库 BLOB 会放大备份、日志和连接压力。我的项目通过 AWS S3 SDK 对接 MinIO 或 RustFS，`FileStorageService` 统一上传、下载、删除、bucket 检查和 URL 构造，因此未来可切换云 S3 兼容服务。数据库只保存 storageKey、文件名、hash 和解析文本。当前开发部署仍是单节点，公共读 bucket 也不安全；生产上应使用私有桶、多副本和签名 URL。

代码依据：

- `app/src/main/java/interview/guide/infrastructure/file/FileStorageService.java` — S3 操作
- `app/src/main/java/interview/guide/common/config/S3Config.java` — S3Client 配置
- `app/src/main/java/interview/guide/common/config/StorageConfigProperties.java` — 存储属性
- `docker-compose.yml` — MinIO 服务

## 8. 面试官：对象 Key 如何设计，怎样防止路径和文件名问题？

我的回答：

对象 Key 应唯一、可分区、不可由用户直接控制，并保留必要可读性。我的项目使用配置前缀、日期、UUID 和清洗后的原文件名生成 key，中文文件名可通过 pinyin4j 转换，避免同名覆盖和部分 S3 兼容实现的编码问题；业务数据库只引用 key，不把客户端路径直接拼接到本地文件系统。这样降低路径穿越与碰撞风险。当前 URL 构造和 bucket 公共读会暴露长期地址，文件名仍可能泄露材料信息。生产上我会用不含原名的随机 key，下载时设置 Content-Disposition，并签发短期授权 URL。

代码依据：

- `app/src/main/java/interview/guide/infrastructure/file/FileStorageService.java` — Key 生成与上传
- `app/src/main/java/interview/guide/common/config/StorageConfigProperties.java` — bucket 配置
- `app/build.gradle` — pinyin4j 与 AWS SDK
- `docker-compose.yml` — 当前 bucket 权限

## 9. 面试官：对象上传成功但数据库保存失败，项目如何补偿？

我的回答：

对象存储和 JPA 没有共同事务，我的项目采用显式补偿：上传 Service 记录新生成的 storageKey，解析和上传完成后调用事务 PersistenceService；如果数据库保存抛异常，catch 块会尝试删除该对象，再原样抛业务异常。简历和知识库都使用这一模式，并有 Mockito 测试验证补偿删除。这样多数失败不会留下孤儿文件。补偿自身也可能因存储故障失败，当前主要记录日志，不能保证最终清理。生产上应写补偿任务表或 outbox，定期扫描没有数据库引用的对象，并让删除操作幂等重试。

代码依据：

- `app/src/main/java/interview/guide/modules/resume/service/ResumeUploadService.java` — 上传补偿
- `app/src/main/java/interview/guide/modules/knowledgebase/service/KnowledgeBaseUploadService.java` — 上传补偿
- `app/src/test/java/interview/guide/modules/resume/service/ResumeUploadServiceTest.java` — 补偿测试
- `app/src/test/java/interview/guide/modules/knowledgebase/service/KnowledgeBaseUploadServiceTest.java` — 补偿测试

## 10. 面试官：重分析、下载和删除文件时有哪些一致性与扩展问题？

我的回答：

重分析或重向量化不能依赖 Stream 保存长文本，因此我的项目凭 storageKey 重新下载原文件、解析后执行任务；下载接口从数据库取得元数据与对象字节；删除简历时先尝试删除对象和关联面试，再删除数据库记录，知识库还要清理向量。这样原文件是可重建事实源。边界是对象删除失败可能留下孤儿，数据库记录已删后用户无法再次定位；大文件整体读入 byte[] 也不适合超大规模。生产上应采用流式上传下载、分段传输、删除标记与异步回收，并对对象引用和保留策略定期对账。

代码依据：

- `app/src/main/java/interview/guide/modules/resume/service/ResumeParseService.java` — `downloadAndParseContent()`
- `app/src/main/java/interview/guide/modules/resume/service/ResumeDeleteService.java` — 删除流程
- `app/src/main/java/interview/guide/modules/knowledgebase/service/KnowledgeBaseDeleteService.java` — 文档与向量删除
- `app/src/main/java/interview/guide/modules/knowledgebase/service/KnowledgeBaseListService.java` — `downloadFile()`

# 本章总结

文件链路通过双层大小限制、真实 MIME 检测、Tika 解析、文本清洗、SHA-256 去重和 S3 兼容存储构成，并用补偿处理数据库与对象存储的跨系统失败。

生产化还需 OCR、沙箱解析、病毒扫描、私有签名下载、流式传输和孤儿对象对账。

# 核心主线

把不可信文件先验证和隔离，再提取可复用文本，并以对象存储作为能够重建后续 AI 数据的原始事实源。
