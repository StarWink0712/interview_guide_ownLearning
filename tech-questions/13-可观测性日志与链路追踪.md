# 可观测性、日志与链路追踪

## 1. 面试官：日志、指标和链路追踪分别解决什么问题？

我的回答：

日志记录离散事件和错误上下文，指标用于聚合趋势、告警与容量判断，链路追踪把一次请求跨阶段关联起来。我的项目三者都有基础：SLF4J 结构化日志记录 sessionId、taskId 等字段；Micrometer Recorder 覆盖 AI、RAG、异步任务和语音耗时；`TraceIdFilter` 生成或透传 traceId，异步消息继续携带它；AI 与 RAG 明细还会落 PostgreSQL。当前 traceId 只是轻量关联 ID，不是带 span 层级的 OpenTelemetry；Prometheus 也尚未接通。生产上应让三类信号互相跳转，而不是重复存相同内容。

代码依据：

- `app/src/main/java/interview/guide/common/observability/TraceIdFilter.java` — 请求 traceId
- `app/src/main/java/interview/guide/common/observability/AiMetricsRecorder.java` — AI 指标
- `app/src/main/java/interview/guide/modules/aiobservability/service/AiInvocationLogService.java` — AI 明细日志
- `app/src/main/resources/logback-spring.xml` — 日志格式

## 2. 面试官：HTTP 请求的 traceId 如何生成、透传和清理？

我的回答：

traceId 应在请求入口确定，并放入日志上下文和响应，方便客户端报告问题。我的项目的 `TraceIdFilter` 优先读取 `X-Trace-Id`，缺失时生成 UUID，写入 MDC 和响应头；Filter 链结束后在 finally 清理 MDC，避免线程复用导致下一请求串号。业务日志无需每次手工拼 traceId，AI 和 RAG 服务也能从 MDC 获取。当前没有严格校验客户端传入值的长度和字符，也没有 spanId、采样或 W3C Trace Context。生产上会限制头格式，并接入 OpenTelemetry 生成标准 trace/span。

代码依据：

- `app/src/main/java/interview/guide/common/observability/TraceIdFilter.java` — `doFilterInternal()`
- `app/src/test/java/interview/guide/common/observability/TraceIdFilterTest.java` — 生成、透传和清理测试
- `app/src/main/java/interview/guide/modules/aiobservability/service/AiInvocationLogService.java` — MDC trace 读取

## 3. 面试官：异步任务换线程、换进程后如何继续传播 traceId？

我的回答：

MDC 基于线程上下文，直接提交线程池或写消息后不会自动传播，必须显式复制。我的项目的 `AbstractStreamProducer` 从 MDC 读取 traceId 并写入 Stream field；消费者处理每条消息前保存原 MDC、恢复消息 traceId，结束时清理并还原。这样上传请求、生产者、消费者和模型调用可以用同一 traceId 检索。消息缺少 traceId 时会生成或使用安全默认。当前虚拟线程、Reactor 流和第三方 SDK 回调中的 MDC 仍可能丢失，生产上应使用上下文快照或 OpenTelemetry Context，而不是依赖裸 ThreadLocal。

代码依据：

- `app/src/main/java/interview/guide/common/async/AbstractStreamProducer.java` — `buildMessageWithTrace()`
- `app/src/main/java/interview/guide/common/async/AbstractStreamConsumer.java` — `processMessage()`
- `app/src/main/java/interview/guide/common/constant/AsyncTaskStreamConstants.java` — traceId 字段
- `app/src/main/java/interview/guide/common/observability/TraceIdFilter.java` — trace 源头

## 4. 面试官：为什么要区分一次逻辑 AI 调用和底层 Provider 多次尝试？

我的回答：

一次业务调用可能因网络重试产生多个 HTTP 请求，如果全部当成业务调用，会把成功率、QPS 和成本口径算错。我的项目用 `AiProviderObservationAdvisor` 包围一次 ChatClient 逻辑 invocation，创建 invocationId 并记录最终状态、总耗时和 retryCount；RestClient interceptor 与 WebClient filter 则记录每一次真实 attempt，包含 HTTP 状态和错误分类。二者通过 invocationId 关联。例如第二次重试成功，应统计一个成功业务调用和两个 Provider 尝试。当前响应式上下文跨线程仍需持续验证，生产上还要把 token 与费用归属到 invocation。

代码依据：

- `app/src/main/java/interview/guide/common/ai/AiProviderObservationAdvisor.java` — invocation 观测
- `app/src/main/java/interview/guide/common/ai/AiProviderHttpObservationInterceptor.java` — HTTP attempt
- `app/src/main/java/interview/guide/common/ai/AiProviderWebClientObservationFilter.java` — 流式 attempt
- `app/src/main/java/interview/guide/common/ai/AiProviderObservationContext.java` — 关联上下文

## 5. 面试官：为什么 AI 调用明细要落数据库，保存完整 Prompt 是否合适？

我的回答：

数据库明细适合按 trace 复盘具体失败、比较 Provider 和离线评测，时序指标只能告诉我们总体异常。我的项目保存场景、Provider、模型、成功状态、延迟、错误、prompt 长度或哈希等调用信息；Provider invocation 与 attempt 分表，RAG 检索也有独立明细。这样管理端可查看时间线。完整 Prompt 可能包含简历、语音转写和私有文档，不应无边界持久化；项目已有预览和截断思路，但尚缺统一脱敏与保留策略。生产上应默认存哈希、模板版本和必要摘要，敏感全文需单独授权、加密和限期删除。

代码依据：

- `app/src/main/java/interview/guide/modules/aiobservability/model/AiInvocationLogEntity.java` — 业务 AI 明细
- `app/src/main/java/interview/guide/modules/aiobservability/model/AiProviderInvocationLogEntity.java` — Provider invocation
- `app/src/main/java/interview/guide/modules/aiobservability/model/AiProviderAttemptLogEntity.java` — Provider attempt
- `app/src/main/java/interview/guide/modules/aiobservability/service/AiProviderObservationLogService.java` — 持久化

## 6. 面试官：RAG 链路需要记录哪些信息才能定位召回问题？

我的回答：

RAG 需要记录原问题、改写问题、知识库范围、topK、阈值、候选数量、分数、chunk 来源和各阶段耗时，才能区分解析、召回与生成问题。我的项目为查询生成 traceId，`RagRetrievalLogService` 保存检索主记录和截断后的 chunk 预览，包含 knowledgeBaseId、rank、score；前端 RAG Chat 先接收 trace SSE 事件，可跳转管理端查看时间线。当前只保存预览，复杂问题可能需要受控查看完整 chunk；也没有在线标注“这次命中是否相关”。生产上会加入用户反馈和错误标签回流评测集。

代码依据：

- `app/src/main/java/interview/guide/modules/aiobservability/service/RagRetrievalLogService.java` — `recordRetrieval()`
- `app/src/main/java/interview/guide/modules/aiobservability/model/RagRetrievalLogEntity.java` — 检索主记录
- `app/src/main/java/interview/guide/modules/aiobservability/model/RagRetrievedChunkLogEntity.java` — chunk 明细
- `app/src/main/java/interview/guide/modules/knowledgebase/RagChatController.java` — trace SSE 事件

## 7. 面试官：项目的 Micrometer 指标如何设计，Recorder 封装有什么价值？

我的回答：

Micrometer 是指标门面，业务面对 Counter、Timer 和 DistributionSummary，不与 Prometheus 等具体后端绑定。我的项目将 AI、Provider、RAG、异步任务和语音指标分别封装在 Recorder 中，业务只调用 `recordXxx`；标签使用 scenario、provider、model、status、stage 等低基数字段，Registry 可选，缺失时静默降级。这样指标命名和标签规则集中，也方便单测。当前静默降级意味着生产误配时可能完全没有指标却不启动失败。生产环境可要求 MeterRegistry 必须存在，并对关键 Recorder 自检。

代码依据：

- `app/src/main/java/interview/guide/common/observability/AiMetricsRecorder.java` — AI 指标
- `app/src/main/java/interview/guide/common/observability/RagMetricsRecorder.java` — RAG 指标
- `app/src/main/java/interview/guide/common/observability/AsyncTaskMetricsRecorder.java` — 任务指标
- `app/src/main/java/interview/guide/common/observability/VoiceMetricsRecorder.java` — 语音指标

## 8. 面试官：项目是否已经完整接入 Prometheus 和 Grafana？

我的回答：

我的项目当前没有完整实现这一部分。代码已经以 Micrometer Recorder 埋点，管理端也能从数据库明细和部分内存指标生成业务摘要；但 `app/build.gradle` 没有显式引入 Actuator 和 `micrometer-registry-prometheus`，YAML 没有 management endpoint 配置，Compose 也没有 Prometheus、Alertmanager 或 Grafana。因此不能说已经部署监控平台。生产上要补依赖，只在内网或独立管理端口暴露 health/prometheus，配置 scrape、SLO buckets、Dashboard 和告警，并验证多实例指标聚合，而不是只看单机 Registry。

## 9. 面试官：为什么指标标签不能使用 sessionId、userId 或 traceId？

我的回答：

每个唯一标签组合都会创建一条时间序列，sessionId、userId、traceId 近乎无限增长，会消耗应用内存、监控存储并拖慢查询，这就是高基数问题。我的项目的 Recorder 主要使用有限集合的 provider、model、status、stage、taskType 和 streaming 标签，把具体 traceId 放日志与数据库明细，设计方向正确。model 和错误分类仍需控制枚举化，不能直接把完整异常消息作为 label。生产上应为标签建立白名单与长度限制，用 exemplars 或日志链接从聚合指标跳到具体 trace，而不是把明细塞进标签。

代码依据：

- `app/src/main/java/interview/guide/common/observability/AiProviderMetricsRecorder.java` — Provider 标签
- `app/src/main/java/interview/guide/common/observability/RagMetricsRecorder.java` — RAG 标签
- `app/src/main/java/interview/guide/common/ai/AiProviderObservationSupport.java` — 错误分类
- `app/src/main/java/interview/guide/modules/aiobservability/model/AiProviderInvocationLogEntity.java` — trace 明细归宿

## 10. 面试官：你会为这个系统设计哪些 SLI、SLO 和告警？

我的回答：

SLI 是实际测量值，SLO 是目标，告警应关注用户影响和错误预算。我的项目可定义：REST 成功率与 P95、AI invocation 成功率和首 token/P95、RAG 非空召回率与检索 P95、Stream backlog/oldest age/失败率、语音 ASR 到首音频延迟、活跃连接和断线率。当前 Recorder 已覆盖不少耗时与结果，但缺 Stream lag、连接 Gauge、Prometheus 采集和正式 SLO。生产上我会先为核心链路设可实现目标，再做多窗口 burn-rate 告警；Provider 失败率高但 fallback 成功时应单独告警，不应直接等同用户失败。

代码依据：

- `app/src/main/java/interview/guide/common/observability/AiMetricsRecorder.java` — AI SLI 基础
- `app/src/main/java/interview/guide/common/observability/RagMetricsRecorder.java` — RAG SLI 基础
- `app/src/main/java/interview/guide/common/observability/VoiceMetricsRecorder.java` — 语音延迟
- `app/src/main/java/interview/guide/modules/monitoring/service/BusinessMetricsQueryService.java` — 当前摘要口径

# 本章总结

项目已经形成 traceId、结构化日志、AI/RAG 明细和 Micrometer Recorder 的观测基础，能够从一次请求关联到异步任务和 Provider 尝试。

当前还不是完整的可观测平台：缺 OpenTelemetry span、Prometheus/Grafana、积压与连接指标、正式 SLO，以及敏感日志的统一治理。

# 核心主线

用指标发现总体异常，用 trace 和明细解释单次问题，并让同步、异步、检索和模型调用共享同一关联上下文。
