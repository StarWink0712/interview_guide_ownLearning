# 测试、部署与高可用

## 1. 面试官：项目的测试策略如何分层？

我的回答：

测试应按成本与真实性分层：纯逻辑用单元测试，Spring/JPA 交互用轻量集成测试，数据库方言、Redis 和对象存储用容器测试，少量关键链路再做端到端。我的项目使用 JUnit 5、Mockito、AssertJ 测结构化输出、自适应、任务状态、补偿和指标；默认 test profile 使用 H2；标记 `container` 的测试通过 Testcontainers 启动真实 PostgreSQL/pgvector、Redis 和 MinIO。这样日常反馈快，CI 又能验证真实基础设施。当前语音端到端和浏览器交互覆盖不足，仍需 fake 服务与协议测试。

代码依据：

- `app/build.gradle` — 测试依赖与任务
- `app/src/test/java/interview/guide/testsupport/BaseIntegrationTest.java` — 容器测试基类
- `app/src/test/java/interview/guide/common/ai/StructuredOutputInvokerTest.java` — 单元测试
- `app/src/test/java/interview/guide/modules/knowledgebase/KnowledgeBaseRagIntegrationTest.java` — RAG 集成测试

## 2. 面试官：Mockito 单元测试适合验证什么，不适合验证什么？

我的回答：

Mockito 适合隔离外部依赖，验证编排分支、参数、状态变化和补偿调用，运行快且结果确定。我的项目用它验证数据库保存失败后是否删除 S3 对象、StructuredOutput 解析失败是否重试、自适应服务失败是否安全降级、提醒是否生成正确计划。它不能证明 SQL 方言、事务锁、Redis Lua、S3 协议或真实模型输出兼容，因此不能只看 mock 测试数量判断可靠性。我的做法是让单测覆盖业务决策，再用 Testcontainers 和少量契约测试覆盖边界；对模型则固定响应测解析，真实 API 只做受控冒烟。

代码依据：

- `app/src/test/java/interview/guide/modules/resume/service/ResumeUploadServiceTest.java` — 上传补偿
- `app/src/test/java/interview/guide/common/ai/StructuredOutputInvokerTest.java` — 重试分支
- `app/src/test/java/interview/guide/modules/interview/adaptive/AdaptiveInterviewServiceTest.java` — 降级
- `app/src/test/java/interview/guide/modules/interviewschedule/reminder/service/InterviewReminderServiceTest.java` — 提醒计划

## 3. 面试官：为什么 H2 不能替代 PostgreSQL 与 pgvector 的容器测试？

我的回答：

H2 启动快，适合基础 Repository 和 Spring 上下文，但 SQL 方言、锁、JSON、索引和扩展行为与 PostgreSQL 不同，也不支持真实 pgvector。我的项目普通测试使用 H2 `create-drop`，关闭 pgvector schema 初始化；容器测试则运行 `pgvector/pgvector:pg16`，验证扩展创建、余弦距离和实际 RAG，并同时启动 Redis、MinIO。这样不会在 H2 上假通过后上线失败。生产关键查询、悲观锁和 vector metadata 删除都应放进 PostgreSQL 测试。H2 仍可保留给快速反馈，但不能作为数据库兼容性的证明。

代码依据：

- `app/src/test/resources/application-test.yml` — H2 配置
- `app/src/test/java/interview/guide/testsupport/BaseIntegrationTest.java` — pgvector 容器
- `app/src/test/java/interview/guide/testsupport/PostgresPgvectorIntegrationTest.java` — 向量扩展测试
- `app/src/main/java/interview/guide/modules/knowledgebase/repository/VectorRepository.java` — PostgreSQL 特定查询

## 4. 面试官：普通测试和容器测试如何在 Gradle 中隔离？

我的回答：

耗时测试应单独标记和执行，让开发默认反馈稳定，CI 再完整验证。我的项目的 `test` 任务使用 JUnit Platform 并排除 `container` 标签；自定义 `integrationTest` 任务复用 test classes，只包含 `container`，并设置在普通测试之后运行。`BaseIntegrationTest` 标记 `@Tag("container")`，Testcontainers 在没有 Docker 时可禁用。这样 `./gradlew :app:test` 不会意外启动三种容器，而 CI 可以显式运行 `:app:integrationTest`。生产流水线应两个阶段都执行，并保存测试报告与容器日志。

代码依据：

- `app/build.gradle` — `test` 与 `integrationTest`
- `app/src/test/java/interview/guide/testsupport/BaseIntegrationTest.java` — `@Tag("container")`
- `app/src/test/java/interview/guide/common/async/RedisStreamIntegrationTest.java` — Redis 容器测试
- `app/src/test/java/interview/guide/infrastructure/file/FileStorageServiceIntegrationTest.java` — 存储测试

## 6. 面试官：如何测试大模型这种非确定性外部服务？

我的回答：

不能要求真实模型每次返回完全相同文本，应分层测试协议和质量。我的项目单元测试用 mock ChatClient 返回固定 JSON，验证 Prompt 变量、BeanOutputConverter、修复重试和业务归一化；`ApiPathResolver` 还有本地 HTTP server 契约测试，避免 URL 拼错。当前真实模型测试较少，也没有统一黄金问题集。生产上我会让 CI 默认使用 fake server 覆盖 401、429、超时、流中断和非法 JSON；离线评测固定模型版本、温度和数据集，比较准确率、格式成功率、token 与延迟；真实 API 冒烟单独运行，不阻断每次提交。

代码依据：

- `app/src/test/java/interview/guide/common/ai/StructuredOutputInvokerTest.java` — 固定响应测试
- `app/src/test/java/interview/guide/common/ai/ApiPathResolverTest.java` — URL 单测
- `app/src/test/java/interview/guide/common/ai/LlmProviderRegistryPathIntegrationTest.java` — 本地 HTTP 契约
- `app/src/main/java/interview/guide/modules/aiobservability/service/RagEvaluationService.java` — 离线评测基础

## 7. 面试官：Docker Compose 当前解决了什么问题，又不代表什么？

我的回答：

Compose 解决的是环境可复现与依赖编排，不自动等于生产高可用。我的项目正式 Compose 启动 pgvector/PostgreSQL、Redis、MinIO、bucket 初始化、Spring Boot 和 Nginx 前端，配置健康检查、depends_on 与命名卷；开发 Compose 只启动 PostgreSQL、Redis 和 RustFS，方便本地 bootRun。这样新环境能快速得到一致依赖。当前每个组件都是单实例，凭据和公共 bucket 偏开发配置，没有滚动升级、备份恢复、自动扩缩或跨主机容灾。因此我只称它为容器化部署基线，不称为生产集群。

代码依据：

- `docker-compose.yml` — 完整环境
- `docker-compose.dev.yml` — 开发依赖
- `app/Dockerfile` — 后端镜像
- `frontend/Dockerfile` — 前端镜像

## 8. 面试官：健康检查、就绪检查和优雅停机应该怎样设计？

我的回答：

存活检查判断进程是否需重启，就绪检查判断是否能接收新流量，优雅停机则先摘流量再排空在途任务。我的项目 Compose 为 PostgreSQL、Redis、MinIO 配置健康检查，并用 depends_on 等待依赖；后端自身没有显式 Actuator health/readiness 配置。Stream Consumer 有 shutdown，WebSocket Handler 会关闭执行器和连接，但容器编排没有完整 draining 流程。生产上应引入 Actuator liveness/readiness，检查数据库与关键配置但避免把暂时性 Provider 故障直接判死；收到 SIGTERM 后停止拉新消息、拒绝新 WebSocket，等待任务和音频在限时内结束。

代码依据：

- `docker-compose.yml` — 依赖健康检查
- `app/src/main/java/interview/guide/common/async/AbstractStreamConsumer.java` — `shutdown()`
- `app/src/main/java/interview/guide/modules/voiceinterview/handler/VoiceInterviewWebSocketHandler.java` — `destroy()`
- `app/build.gradle` — 当前无 Actuator Starter

## 9. 面试官：当前系统要实现高可用，各组件分别需要什么改造？

我的回答：

高可用不是多启动几个应用实例，而是消除单点并处理状态归属。我的项目需要 PostgreSQL 主从、备份与故障切换，Redis Sentinel/Cluster 与持久化，对象存储多副本；后端 REST 可无状态扩容，但 WebSocket、ASR 和语音 SessionState 在本机，需要 sticky session 或 session owner 路由；Scheduler 要确保幂等或分布式认领；Provider 调用需要熔断和备用模型。当前这些未完整实现。生产上还要跨可用区部署、演练 Redis/DB/Provider 故障，并验证恢复点和恢复时间，而不是只做正常流量压测。

代码依据：

- `docker-compose.yml` — 当前单实例组件
- `app/src/main/java/interview/guide/modules/voiceinterview/handler/VoiceInterviewWebSocketHandler.java` — 本机连接状态
- `app/src/main/java/interview/guide/modules/interviewschedule/reminder/repository/InterviewReminderRepository.java` — 调度认领
- `app/src/main/java/interview/guide/common/ai/LlmProviderRegistry.java` — 当前 Provider 选择

## 10. 面试官：生产 CI/CD、数据库迁移和灾备还需要补什么？

我的回答：

生产流水线应执行编译、单测、容器测试、前端构建、镜像扫描和部署验证，并让数据库 schema 可审计、可回滚。我的项目当前依赖 JPA `ddl-auto=update` 和 pgvector `initialize-schema=true` 方便开发，没有 Flyway/Liquibase 迁移；Compose 有命名卷但卷不是备份，README 也未形成恢复演练。生产上我会关闭自动建表，用版本化迁移创建索引与扩展，先做向后兼容发布；镜像使用固定 digest 和非 root 用户；数据库与对象存储定期备份并实际恢复验证。最后增加负载、故障注入和回滚演练作为发布门槛。

代码依据：

- `app/src/main/resources/application.yml` — `ddl-auto` 与 pgvector 初始化
- `app/build.gradle` — 当前无迁移工具
- `docker/postgres/init.sql` — 当前初始化脚本
- `docker-compose.yml` — 命名卷

# 本章总结

项目已建立单元测试、H2 测试和 Testcontainers 真实基础设施测试，并通过 Docker Compose 提供可复现环境。

当前缺口集中在语音回归、真实限流测试、应用健康端点、数据库迁移、高可用拓扑、灾备演练和完整 CI/CD 门禁。

# 核心主线

用分层测试证明代码与基础设施行为，用可复现部署缩小环境差异，再通过迁移、健康检查、冗余和演练走向高可用。
