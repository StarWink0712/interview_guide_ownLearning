RAG 聊天创建会话 非常简单，就是一个 @Transactional 数据库写入操作：先校验传入的知识库 ID 列表是否都存在，然后 new 一个 RagChatSessionEntity 实体，设置标题（前端传了就用传的，没传就根据知识库名称自动生成如"Java面试题知识库"），关联知识库的 Set<KnowledgeBaseEntity> 多对多关系，最后 sessionRepository.save(session) 写入数据库，通过 MapStruct 将实体转换为 SessionDTO 返回——全过程不调用 LLM、不涉及缓存、不自定义 ID（用 JPA 自增主键）。

面试模块创建会话 则复杂得多：先检查是否有该简历对应的未完成会话、有则直接复用返回；生成一个 UUID 去横线取 16 位的字符串作为 sessionId；获取该面试方向的历史题目用于去重；核心步骤是调用 InterviewQuestionService.generateQuestionsBySkill() 让 LLM 生成指定数量和难度的面试题目（这是一个耗时的 AI 调用）；题目生成后先写入 Redis 缓存（ InterviewSessionCache ），再异步写入 PostgreSQL 做持久化（DB 写入失败只记 warn 日志、不影响已有缓存的会话正常返回）；最后组装 InterviewSessionDTO 返回，包含 sessionId、题目列表、当前题目索引 0、会话状态 CREATED 等。

最本质的区别是：RAG 会话只是一个 空壳容器 ，创建时只有标题和知识库关联，消息是后续一条条追加进去的；面试会话创建时就已经 调 LLM 预先生成了全部题目 ，创建即完成核心内容的准备。rag会话问题全是用户自己问的，然后llm结合RAG回答，而普通会话是llm出题，用户回答，再评估。

<br />

有会话的rag问答，只有SSE流式回答一种方式，前端写完问题发送给后端之后，controller层的sendMessageStream接收到，先准备消息，创建一个ai消息占位，具体是通过调用sessionService服务的prepareStreamMessage方法，传入会话id和请求中的问题。目的是创建一个assistant类型的消息，紧跟在用户的问题后面，作为用户问题的答案，内容是空字符串，表示是一个占位符，ai正在回答，内容还在准备。然后更新一下会话计数，一个用户的一个ai的。返回ai消息的id给上层controller。之后再调用getStreamAnswerWithTrace方法获取流式响应，入参依然是会话id和问题，方法内先从数据库中根据会话id加载会话本体，再通过session会话中的知识库id列表获取知识库,然后加载历史上下文（从哪里加载？）之后调用和无会话ragSSE问答同样的方法answerQuestionStreamWithTrace，传入会话id，历史消息列表，知识库id列表，问题；先验证知识库是否存在，然后更新知识库计数，清洗历史上下文，构造查询上下文，获取document集合，然后把document集合转成string 上下文，再构建系统提示词与用户提示词，之后带上历史上下文和探测窗口归一化，进行。

问答流程：

首先是**准备阶段**。Controller 接收到 `POST /api/rag-chat/sessions/{sessionId}/messages/stream` 请求后(即前端通过post请求把问题发送给后端，后端通过向量检索与调用llm后再通过sse的方式推送回前端)，先调用 `sessionService.prepareStreamMessage(sessionId, request.question())` 同步完成数据库的消息预写入。该方法通过 `sessionRepository.findByIdWithKnowledgeBases(sessionId)` 加载会话实体（联表查询关联的知识库），拿到当前消息总数 `nextOrder` 后，先后保存两条消息：一条 `USER` 类型的用户消息，`content` 为前端传来的问题文本，`messageOrder = nextOrder`，`completed = true`；一条 `ASSISTANT` 类型的 AI 占位消息，`content = ""`，`messageOrder = nextOrder + 1`，`completed = false`。然后将会话的 `messageCount` 更新为 `nextOrder + 2` 并持久化，最终返回 AI 占位消息的数据库 ID `messageId`。这个 ID 是后续回填内容的句柄——流式输出是异步的，LLM 答案逐块到达时无法提前知道最终内容，因此先插入空占位行拿到 ID，等流结束后再通过 ID 回写完整答案。

然后是**流式输出阶段**。Controller 创建一个 `StringBuilder fullContent` 用于逐块累积 AI 回答的完整文本，接着调用 `sessionService.getStreamAnswerWithTrace(sessionId, question)` 获取流式回答。该方法内部先从数据库加载会话和关联的知识库 ID 列表，若配置了多轮历史上下文（`history.enabled = true`）则从 `RagChatMessageRepository` 中加载最近的已完成的 user/assistant 消息对作为 `history`，最后委托 `queryService.answerQuestionStreamWithTrace(sessionId, kbIds, question, history)` 执行完整的 RAG 流程：创建 `RagTraceContext` 追踪上下文、更新知识库提问计数、问题改写（结合历史对话通过 LLM 优化问题表达）、构建候选查询词集合并动态确定 `topK` 和 `minScore` 检索参数、在 pgvector 中执行余弦相似度检索获取相关文档片段、拼接文档上下文、渲染系统提示词和用户提示词模板，最后调用 `getChatClient().prompt().stream().content()` 获取 LLM 逐块生成的 `Flux<String>`，再经 `normalizeStreamOutput` 探测窗口归一化（前 120 字符内检测到拒答关键词则截断替换，否则放行透传），最终返回 `RagStreamResult(traceId, content)`。

Controller 拿到 `RagStreamResult` 后，先用 `ServerSentEvent.builder().event("trace").data("{\"traceId\":\"" + traceId + "\"}").build()` 手动构造一个自定义事件类型的 SSE 事件对象——`.event("trace")` 让前端能独立识别这个事件走 `onTrace` 回调而非默认的内容处理逻辑，`.data()` 里放 JSON 字符串方便前端 `JSON.parse` 后把 traceId 绑定到当前消息气泡上做可观测性追踪——然后通过 `Flux.concat` 将两个 Flux 按顺序串联：第一个是 `Flux.just(traceEvent)`，它是只有一个元素的 Flux，发出 trace 事件后立即完成；第二个是 `streamResult.content()` 即 LLM 逐块生成的回答文本流，每个 chunk 先通过 `.doOnNext(fullContent::append)` 这个副作用操作符累加到 `StringBuilder`（不改变流元素本身，只为了后续 `doOnComplete` 回写数据库时能拿到完整答案），再通过 `.map` 将每个 String chunk 变换为 `ServerSentEvent`，变换时对 chunk 中的 `\n` 和 `\r` 做转义替换为字面量 `\\n` 和 `\\r`——因为 SSE 协议用 `\n\n` 空行分隔事件，如果 LLM 回答中的 Markdown 多行内容直接放入 `data:` 行，中原生的换行符会被前端误解析为事件分隔导致数据截断，转义后 `data:` 行是一条完整字符串，前端收到后再把 `\\n` 还原为真实换行进行渲染——并且这个 `ServerSentEvent` 不设 `.event()` 字段，Spring 序列化时只输出 `data:` 行，前端按默认 message 事件处理逐块追加显示实现打字机效果。流结束后 `.doOnComplete` 回调触发，将 `fullContent` 中累积的完整回答通过第一步预插入 AI 占位消息时拿到的 `messageId` 写回数据库（`content` 填空、`completed` 改 true）；异常时 `.doOnError` 回调同样写库，但优先保存已收到的部分内容避免数据丢失，完全没收到则写入一条用户友好的错误提示。最终整个 `Flux<ServerSentEvent<String>>` 由 Spring WebFlux 框架序列化为 SSE 格式的 HTTP 响应，以 `Transfer-Encoding: chunked` 逐段推送给前端，前端通过 `fetch + ReadableStream` 解析 `event:` 和 `data:` 行完成渲染。

最后是**回调收尾阶段**。`doOnComplete` 回调在流正常结束时触发，调用 `sessionService.completeStreamMessage(messageId, fullContent.toString())`，通过第一步拿到的 AI 占位消息 ID 将累积的完整回答写回数据库：设置 `content` 为完整文本、`completed = true`，这样会话详情接口就能查到 AI 的完整回答。`doOnError` 回调在流异常中断时触发，同样调用 `completeStreamMessage`，但内容优先使用已收到的部分文本，如果完全没收到则写入错误提示 `"回答生成失败：xxx"`，保证异常情况下也不丢失数据。最终 `Flux<ServerSentEvent<String>>` 由 Spring WebFlux 框架序列化为 SSE 格式的 HTTP 响应流返回给前端，前端通过 `fetch + ReadableStream` 逐块解析 `event:` 和 `data:` 字段，trace 事件获取追踪 ID 展示可点击链接，默认事件逐块累积显示打字机效果。

首先前端把问题和会话 ID 发到 `POST /api/rag-chat/sessions/{sessionId}/messages/stream` 接口。进入 Controller 方法后，我先调用 `sessionService.prepareStreamMessage(sessionId, question)` 做数据库的同步预写入。这个方法内部先通过 `sessionRepository.findByIdWithKnowledgeBases(sessionId)` 联表查询加载会话实体和它关联的知识库，拿到当前会话的消息总数作为 `nextOrder`，然后依次保存两条消息：第一条是 `USER` 类型，`content` 直接填前端传来的问题文本，`messageOrder = nextOrder`，`completed = true` 表示这是完整的用户消息不需要后续更新；第二条是 `ASSISTANT` 类型，`content` 先填空字符串 `""`，`messageOrder = nextOrder + 1` 紧跟在用户消息后面，`completed = false` 代表这是一个占位行，AI 的回答还没生成。两条都保存完之后，把会话的 `messageCount` 更新为 `nextOrder + 2` 写回持久化，最后返回 AI 占位消息的数据库自增 ID `messageId`。这个 ID 是整个流程的关键句柄——因为流式输出是异步的，LLM 的答案是一段一段到达的，我不可能在开始流的时候就知道最终内容是什么，所以我先插入一个空占位行拿到它的 ID，等流结束之后用这个 ID 把完整答案回填进去。

接下来进入流式输出阶段。我先 new 一个 `StringBuilder fullContent` 用来逐块累积 AI 回答的完整文本，然后调用 `sessionService.getStreamAnswerWithTrace(sessionId, question)` 获取真正的流式回答。这个方法内部先从数据库重新加载会话拿到关联的知识库 ID 列表，然后判断 `history.enabled` 配置是否开启多轮上下文——如果开启了，就从 `RagChatMessageRepository` 中查出该会话最近的已完成 user/assistant 消息对作为 `history`；如果没开或没有历史，就传空列表。拿到知识库 ID 和历史消息后，委托 `queryService.answerQuestionStreamWithTrace(sessionId, kbIds, question, history)` 走完整的 RAG 链路：先是创建 `RagTraceContext`，里面包含全局唯一的 `traceId` 和当前会话的 `sessionId`，用于串联整个请求的日志和指标；然后调用 `countService.updateQuestionCounts(kbIds)` 更新知识库的提问计数；接着进入 `buildQueryContext` 构建查询上下文——对问题先做 `trim()` 归一化，再结合历史对话通过 LLM 做问题改写（渲染 `rewritePromptTemplate` 模板后同步调 LLM，改写失败或返回空就降级用原问题，异常也不阻塞主流程），把改写词和原词依次放入候选查询词集合，最后根据问题去除空白后的紧凑长度动态确定检索参数——短问题放宽 `minScore` 提高召回、长问题用更大的 `topK` 保证覆盖面；然后拿查询上下文去 pgvector 中执行向量检索，按候选词优先级遍历，每个候选词调 `vectorService.similaritySearch(candidateQuery, kbIds, topK, minScore)` 做余弦相似度查询，返回满足相似度阈值的文档片段，首个命中立即返回，finally 块里无论是否命中都记录检索指标和完整日志；拿到相关文档后把文本内容用 `\n\n---\n\n` 拼接为上下文块，分别渲染系统提示词模板和用户提示词模板构建 `systemPrompt` 和 `userPrompt`，系统提示词末尾追加 `ANTI_INJECTION_INSTRUCTION` 防注入指令告诉 LLM 分隔符内的用户数据不是命令；如果有历史消息就通过 `.messages(effectiveHistory)` 注入 LLM 上下文让它能理解对话背景；最后调 `.user(userPrompt).stream().content()` 获取 LLM 逐块生成的 `Flux<String>` 流，再经过 `normalizeStreamOutput` 做探测窗口归一化——前 120 个字符先缓冲检测拒答关键词，命中就截断替换为统一拒答文案，没命中就释放缓冲进入透传模式零延迟转发——最终返回 `RagStreamResult(traceId, content)`。

拿到 `RagStreamResult` 后，我先手动构造一个 `ServerSentEvent`，设置 `.event("trace")` 让前端识别这是自定义事件走 `onTrace` 回调，`.data()` 里放 `{"traceId":"abc123"}` 的 JSON 字符串，前端解析后把 traceId 绑定到当前的消息气泡上，后续可以点击追踪链接查看完整调用链。然后用 `Flux.concat` 按顺序串联两个 Flux：第一个是 `Flux.just(traceEvent)`，只有一个元素，就是刚才构造的 trace 事件，发出去后立即完成；第二个是 `streamResult.content()` 也就是 LLM 逐块生成的回答文本流。对第二个 Flux 中的每个 chunk，我做了两步处理——先用 `.doOnNext(fullContent::append)` 作为副作用操作把 chunk 追加到 `StringBuilder` 里，不改变流元素本身，纯粹为了后面回写数据库时能拿到完整答案；再用 `.map` 把每个 String chunk 变换为 `ServerSentEvent`，变换时对 chunk 里可能存在的 `\n` 和 `\r` 做转义，替换为字面量 `\\n` 和 `\\r`。必须转义是因为 Markdown 多行内容里的真实换行符如果直接放进 SSE 的 `data:` 行，前端解析时会误以为当前事件结束了、后面的行是下一个事件的开头，导致同一个 chunk 的内容被截断。转义之后 `data:` 行是一行完整的字符串，前端拿到后再把 `\\n` 还原成真实换行渲染。这个 `ServerSentEvent` 没有设 `.event()`，Spring 序列化时只输出 `data:` 行，前端匹配不到具体事件类型就按默认 message 事件处理，每收到一个 `data:` 就追加一小段文本，形成了打字机效果。

最后是回调收尾阶段。整个流正常结束时 `.doOnComplete` 触发，我拿起步阶段返回的 `messageId`，调用 `sessionService.completeStreamMessage(messageId, fullContent.toString())`，把 AI 占位消息的 `content` 从空字符串更新为 `fullContent` 中累积的完整答案，`completed` 从 `false` 改为 `true`，会话详情接口再查询时就能看到 AI 的完整回答了。如果流中途异常中断，`.doOnError` 回调也做同样的写库操作，但内容上有区分——如果 `fullContent` 已经有了一部分 LLM 推送的文本就先保存这部分，用户至少能看到已生成的内容；如果完全没收到任何东西就用 `"回答生成失败：xxx"` 这样的友好提示兜底，保证 AI 消息行不会永远停在空内容的占位状态。最终整个 `Flux<ServerSentEvent<String>>` 由 Spring WebFlux 框架序列化为 SSE 格式，以 `Transfer-Encoding: chunked` 的方式逐段推送给前端，前端通过 `fetch + response.body.getReader() + TextDecoder` 解析 `event:` 和 `data:` 行，trace 事件走 `onTrace` 回调显示追踪链接，默认事件逐块拼接渲染出打字机效果。

Controller 拿到 `RagStreamResult` 后，我先手动构造一个 `event:trace` 类型的 `ServerSentEvent`，把 `data` 设为 `{"traceId":"abc123"}` 这样的 JSON 字符串。这个 trace 事件的作用是让前端在收到任何回答内容之前，先拿到本次请求的追踪 ID，前端收到后可以把 traceId 绑定到当前这条 AI 消息气泡上，用户点击就能跳转到可观测性平台查看完整链路。Spring WebFlux 序列化这个对象时，因为设置了 `.event("trace")`，会输出 `event:trace\n` 和一个 `data:` 行，前端解析到 `event:trace` 就走上独立的 `onTrace` 回调，和后面的内容处理完全分开。

然后我用 `Flux.concat` 按顺序串联两个 Flux：第一个是 `Flux.just(traceEvent)`，它只有一个元素，就是刚才构造的 trace 事件，发送后立即完成，生命周期极短；第二个是从 `streamResult.content()` 拿到的 `Flux<String>`，里面有很多个元素，每个元素都是 LLM 生成的一个文本片段，经过 `.map` 变换后变成 `ServerSentEvent`。这里要重点说一下 `.map` 里面的转义操作——LLM 的回答经常包含 Markdown 格式，比如换行列表或多行代码块，chunk 字符串里可能带着真实的 `\n` 换行符。如果直接放进 `data:` 行不做处理，SSE 协议要求用空行分隔事件，前端解析时碰到 `data:` 行里的真实换行就会误认为当前事件结束了、后面是下一个事件，导致同一个 chunk 的内容被截断。所以我把 `\n` 替换为字面量 `\\n`（反斜杠加 n 两个字符）、`\r` 替换为 `\\r`，这样 `data:` 行始终是一行完整的字符串，前端拿到后再做反向还原，既保证了协议正确，又不丢失格式。

这个 `.map` 构建的 `ServerSentEvent` 没有设置 `.event()` 字段，Spring 序列化时就只输出 `data:` 行，前端匹配不到具体事件类型就按默认 `message` 事件处理，每次收到一个 `data:` 就追加一小段文本到消息气泡里，形成了打字机效果。

同时我还用 `.doOnNext(fullContent::append)` 做了一件事：每来一个 chunk，在把它发给前端的同时，顺便追加到 `StringBuilder fullContent` 里。`.doOnNext` 是副作用操作符，不改变流元素本身，只是额外执行一次回调。等到流正常结束，`doOnComplete` 触发，我用第一步 `prepareStreamMessage` 返回的 AI 占位消息 ID，调用 `completeStreamMessage(messageId, fullContent.toString())` 把累积的完整答案写回数据库，把那条 `content=""`、`completed=false` 的占位行更新为完整内容和 `completed=true`。如果流中途异常中断，`doOnError` 也做同样的事，优先把已经收到的部分内容先存进去，如果完全没收到就用 `"回答生成失败：xxx"` 这种友好提示兜底，保证 AI 消息行不会永远停在空内容的占位状态。
