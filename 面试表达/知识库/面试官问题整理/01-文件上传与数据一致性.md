# 文件上传与数据一致性

## 1. 知识库模块主要解决什么问题，包含哪些能力？

**回答：** 知识库模块是面试辅导平台的核心功能之一，整体使用 Spring Boot 4.0、Java 21 虚拟线程、Spring AI 2.0、PostgreSQL pgvector 和 Redis Stream，前端使用 React 18 与 TypeScript。模块主要分成知识库构建、直接问答和 RAG 聊天会话三部分，同时提供文件上传下载、分类、检索、使用统计和异步向量化等能力。

<br />

知识库模块的核心作用是用户可以上传资料文档来建立自己的知识库，然后通过文档和llm来进行问答，自己考察自己有没有掌握知识库内的内容。用户可以上传word，pdf，md等文档，先对文档进行大小，一致性，mime类型验证，然后提取文本内容存数据库，同时把文件传到rust对象存储中，然后把对象存储中的标记和地址存到数据库中，同时通过异步任务进行向量化，向量化是先对文档进行切分，切分的逻辑是按照固定大小进行切分，每800个token作为一个块然后为每个chunk块填写好metadata元数据表格，之后调用阿里云的embedding模型每批10个chunk进行批量向量化，最后把向量化好后的每个chunk的document交给向量数据库添加；模型用的是阿里云的embedding3模型，用的最大维度1024，连同metadata一起写到向量数据库中。因为向量化是异步任务，所以向量化失败的话会进行消息的三次重试。

## 2. 知识库文件上传接口的完整流程是什么？

**回答：** 前端上传 `MultipartFile`，并可传入自定义 `name` 和 `category`。请求先经过全局和 IP 限流，再进入 `uploadService.uploadKnowledgeBase()`：校验 50MB 大小限制，检测 PDF、DOCX、TXT 等 MIME 类型，计算 SHA-256 哈希去重，通过 Apache Tika 提取纯文本，把原文件上传到 RustFS，保存文件元数据到 PostgreSQL，创建异步任务记录，最后在数据库事务提交后向 Redis Stream 发送向量化任务。

## 3. 上传时为什么既要校验文件大小，又要校验 MIME 类型？

**回答：** 大小校验通过检测文件字节数，将单文件限制在 50MB，避免超大文件占用过多内存、网络和解析资源。MIME 类型白名单只放行 PDF、DOCX、TXT 等支持的格式，防止不支持或危险类型进入 Apache Tika 和对象存储流程。这两项属于文件进入系统前的安全校验。

## 4. 文件去重是怎么实现的？

**回答：** `fileHashService.calculateHash()` 先把文件转换为字节数组，再计算 SHA-256 摘要，以哈希值作为内容指纹查询数据库。命中已有记录时直接返回原有结果，并把 `duplicate` 标记为 `true`，不再重复解析、上传和向量化。它按文件内容去重，不依赖用户是否修改过文件名。

## 5. Apache Tika、RustFS 和 PostgreSQL 在上传流程中分别负责什么？

**回答：** Apache Tika 负责把 PDF、DOCX 或 TXT 等文件解析成纯文本，为后续分块和向量化提供原材料；RustFS 保存原始二进制文件，并返回唯一的 `fileKey` 和对应 `fileUrl`；PostgreSQL 保存原始文件名、大小、MIME 类型、`storageKey`、`storageUrl`、SHA-256、name 和 category 等业务元数据。

<br />

Apache tika负责解析文件成string文本，rustfs存原件，至于为什么用rustfs，因为直接存磁盘不方便管理和读取，而用了对象存储，不需要关心文件存储在具体哪个磁盘和路径，对象存储会维护好文件的存储标识和内部路径，可以通过封装好的对象存储客户端方法直接调用。postgresql的作用是作为向量数据库用来存储向量化的数据。

## 6. 为什么原文件已经解析过，消费者还要从 RustFS 下载后重新解析？

**回答：** Redis Stream 消息只携带知识库 ID 等轻量标识，不携带可能有几万字符的文本。消费者收到任务后，根据 `kbId` 查询知识库实体，再从 RustFS 下载原文件，并通过 Tika 重新得到文本。这样可以避免大文本占用 Redis 内存和消息传输带宽，同时让原始文件成为可重复处理的数据来源。

<br />

这是必然的，不能把原文这种占大空间的内容放到消息里面，只能再去对象存储中获取原件进行解析。当然这里不是重新解析文本，因为向量化之前，也只是验证文件类型，并不会解析文本内容，向量化之后才会把切分成chunk的文本内存存到数据库中。

## 7. RustFS 上传成功但数据库保存失败时怎么办？

**回答：** RustFS 和 PostgreSQL 不属于同一个本地事务，数据库回滚不能自动删除已经上传的对象。因此 `persistenceService.saveKnowledgeBase()` 失败时会调用 `compensateUploadedKnowledgeBase()`，主动删除 RustFS 中刚上传的文件，避免产生数据库没有记录、对象存储却残留文件的孤儿数据。

<br />

二者属于不同的事务体系，如果rustfs成功了数据库失败了，可以进行简单的尝试，或者直接就从rustfs中删除，然后告诉前端上传失败请重试。

## 8. 为什么向量化不能放在上传接口里同步完成？

**回答：** 文件下载、文本切分以及调用 Embedding API 都比较耗时，如果放在上传请求中同步执行，用户需要长时间等待，接口也容易超时。因此上传阶段只保存文件和元数据，再通过 Redis Stream 异步完成向量化；前端通过 `async_tasks` 表中的任务状态查看处理进度。

<br />

向量化很耗时间，可以让异步线程慢慢向量化，如果前端上传完直接用这个文档直接去用来问答的话，可以先查询向量化状态，然后告诉前端请稍等。

## 9. 为什么 Redis Stream 消息必须在数据库事务提交后发送？

**回答：** 上传方法处于数据库事务中，如果保存元数据后立刻执行 XADD，消费者可能马上拿到 `kbId`，但此时事务尚未提交，消费者查询数据库就找不到知识库记录。系统通过 `afterCommitExecutor.execute()` 把消息发送延迟到事务成功提交之后，确保消费者开始处理时数据已经可见。日程提醒不需要这种处理，是因为它的消息投递本来就在事务外执行。

## 10. 向量化消息体为什么只放轻量标识？

**回答：** 消息只包含 `taskId`、`businessId`、`kbId` 和 `retryCount`，其中 `businessId` 与 `kbId` 相同，首次重试次数为 0。文档文本可能达到几万字符，如果直接放入 Redis Stream，会增加 Redis 内存占用、网络传输和消息持久化成本。消费者需要内容时，用 `kbId` 查询元数据并从 RustFS 下载原文件。

## 11. async\_tasks 表在知识库上传中有什么作用？

**回答：** 发送消息前会创建一条类型为 `KB_VECTORIZE`、状态为 `PENDING` 的异步任务记录，同一个 `kbId` 的 PENDING 任务有幂等保护，不会重复创建。消费过程中任务状态会变为 PROCESSING、COMPLETED 或 FAILED，前端可以轮询该表展示向量化进度，并在失败后提供重新向量化入口。
