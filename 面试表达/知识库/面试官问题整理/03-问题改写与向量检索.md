# 问题改写与向量检索

## 1. 一次 RAG 查询为什么要先创建 RagTraceContext？

**回答：** 核心查询方法开始时先记录 `System.nanoTime()`，再创建包含 `traceId` 和 `sessionId` 的 `RagTraceContext`。`traceId` 是全局唯一请求标识，用来串联本次改写、检索、LLM 调用的日志和指标；直接问答的 `sessionId` 为 null，RAG 聊天会话则传真实 ID，使检索日志能够关联到具体会话。

<br />

即创建一个traceid，作为这个rag查询的标识，日志log打印什么的都用这个标识，这样就知道是哪一次查询了

<br />

## 2. 进入检索前会做哪些前置处理？

**回答：** 系统先检查知识库 ID 列表和问题是否为空，问题会经过 `trim()` 归一化；无效请求直接返回统一拒答并记录指标。校验通过后更新所选知识库的提问计数，供前端展示使用热度，然后调用 `buildQueryContext()` 构建归一化问题、改写问题、候选查询词和动态检索参数。

<br />

数据库中会维护一个表，来记录知识库文档的调用次数，rag测试的时候也会测试命中文档数量，匹配的文档的数量。

## 3. 为什么用户问题不能总是直接拿去做向量检索？

**回答：** 用户输入可能比较口语化、包含指代或缺少明确关键词，例如多轮会话中的“那第二种方法呢”。这种文本直接生成查询向量可能无法准确匹配文档，因此系统通过 LLM 把问题改写成更适合检索的表达；有会话时还结合历史消息消解指代。

<br />

用户问的问题偏口语化的或者偏简写的，虽然意思一样但是文字可能与文档中完全不同，所以需要对其进行改写。

## 4. 问题改写的完整流程是什么？

**回答：** `rewriteQuestion()` 先检查 `app.ai.query.rewrite.enabled` 开关和问题是否为空。启用时把当前问题与格式化历史渲染进 `knowledgebase-query-rewrite.st` 模板，通过 `getChatClient().prompt().user(rewritePrompt).call().content()` 同步调用 LLM。成功后使用改写结果并记录日志与耗时指标；返回空或发生异常时降级为原问题，不阻断主 RAG 链路。

<br />

改写失败就降级用原来的。

## 5. 历史消息在问题改写时如何控制长度？

**回答：** 历史会被格式化为“用户: xxx\n助手: xxx”的文本，帮助模型理解当前问题指向。为了防止改写 Prompt 过长，每条助手回复最多截取 200 个字符；直接问答传空历史，只有 RAG 聊天会话在配置开启时加载最近已完成的 user/assistant 消息。

<br />

历史消息是历史问答的内容，不能太长，如果过长的化可以先调用llm对其进行摘要压缩。

## 6. 为什么问题改写失败后要降级使用原问题？

**回答：** 改写只是提高召回率的增强步骤，不应该成为知识库问答的硬依赖。配置关闭、模型返回空或调用异常时，都直接用原问题继续检索，同时记录改写失败和耗时指标。这样即使改写模型暂时不可用，主问答流程仍然可以工作。

## 7. 候选查询词集合为什么使用 LinkedHashSet？

**回答：** 系统先加入改写问题，再加入归一化原问题。`LinkedHashSet` 同时保证插入顺序和去重：检索时优先尝试更适合召回的改写词，如果改写结果与原问题相同也不会执行两次相同查询；改写词无命中时还可以使用原问题兜底。

<br />

查询候选词集合是原问题和改写后的问题，即两个问题组成集合，用linkedhashset是为了保证插入顺序，即先插入改写后的，如果改写问题命中率低，那就还可以用原问题；而命中率是通过向量匹配时的minscore分手确定的，如果没有大于等于这个最小分数的就代表没有匹配到。

## 8. topK 和 minScore 分别控制什么？

**回答：** `topK` 是返回文档片段数量的上限，越大提供给 LLM 的素材越多，但 Prompt 和 token 成本也越高；`minScore` 是 0 到 1 之间的最低余弦相似度阈值，低于它的片段直接丢弃，阈值越高过滤越严格。两者共同决定召回数量和相关性。

## 9. 当前动态检索参数是怎么配置的？

**回答：** 系统先用 `question.replaceAll("\\s+", "").length()` 计算去除空白后的长度。长度不超过 4 的短问题使用 `topK=20、minScore=0.25`；5 到 12 个字符使用 `topK=12、minScore=0.28`；超过 12 个字符使用 `topK=8、minScore=0.28`。短问题上下文少，因此扩大候选数量并降低阈值提高召回；长问题信息更完整，使用较小 topK 控制上下文长度。

## 10. pgvector 向量检索的执行过程是什么？

**回答：** `retrieveRelevantDocs()` 按候选词顺序遍历，跳过空白候选词，对每个有效查询调用 `vectorService.similaritySearch(candidateQuery, kbIds, topK, minScore)`。pgvector 使用余弦相似度，在指定知识库 ID 范围内返回不超过 topK 且分数不低于 minScore 的 `Document` 片段。

## 11. 为什么首个候选词命中后就立即返回？

**回答：** 改写词被放在候选列表最前面，通常已经是最适合检索的表达。一旦它返回有效文档，继续用原问题查询会增加一次向量计算和数据库访问，还可能产生重复候选，因此首个有效命中就立即返回；只有前面的候选无结果时才尝试后面的兜底词。

<br />

这里是做的最简单，直接用改写后的返回，没有进行复杂的设计，生产环境下应该用改写后的和未改写的都进行查询，然后结果合并去重精排序，因为开发者并不知道改写后的结果到底是好还是坏。开发者也可以用RLHS对llm进行进行微调，培养一下改写的能力。

<br />

## 12. 为什么检索日志一定放在 finally 中记录？

**回答：** 无论命中、无命中还是检索过程中发生异常，都需要留下可观测信息，因此记录逻辑放在 `finally`。一类数据上报到指标采集器，包括 rewriteEnabled、topK、命中数、成功状态和耗时；另一类完整写入数据库，包括 traceId、sessionId、原始问题、改写问题、候选词、知识库 ID、topK、minScore、文档列表、命中数和耗时，便于排查“为什么没搜到”或“为什么结果不相关”。

## 13. 多知识库查询如何限制文档范围？

**回答：** 请求携带一个或多个知识库 ID，检索时将完整 `kbIds` 列表传给 `similaritySearch`，利用向量记录 metadata 中的 `kb_id` 过滤候选范围。因此同一个问题可以同时从多个选定知识库召回片段，而不会检索到用户没有选择的知识库内容。
