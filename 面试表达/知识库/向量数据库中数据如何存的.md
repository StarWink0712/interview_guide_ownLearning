你的项目用的是 Spring AI 的 `PgVectorStore`，表由框架自动创建和管理，不需要手写 JPA Entity。

表名是 `vector_store`，结构大致如下：

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE vector_store (
    id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),   -- 主键，唯一标识一个文本块
    content   TEXT,                                          -- 文本块原文
    metadata  JSONB,                                         -- 元数据（kb_id、文件名、chunk序号等）
    embedding vector(1024)                                   -- 1024维向量，embedding模型的输出
);

-- 向量索引，加速相似度检索
CREATE INDEX ON vector_store USING hnsw (embedding vector_cosine_ops);
```

### 各字段说明

**`id`**：UUID 主键，Spring AI 自动生成。

**`content`**：原始文本块的内容。比如一篇 PDF 被切成 50 个片段，每个片段是一条记录，`content` 存那段原文。这是检索命中后返回给 LLM 做上下文的实际文本。

**`metadata`**（JSONB）：结构化元数据，Spring AI 用它来过滤。这个项目里至少存了：

- `kb_id`：所属知识库 ID，删除知识库时用它来 `DELETE FROM vector_store WHERE metadata->>'kb_id' = ?`
- 其他可能的信息：源文件名、chunk 序号、创建时间等

**`embedding`**：1024 维浮点数向量，是调用 embedding 模型（如来也是 `text-embedding-v3`）把 `content` 文本转成的向量。这是相似度检索的核心——用户的查询问题也转成 1024 维向量，然后在这个列上做 COSINE 相似度计算，找出最接近的文本块。

**索引**：`hnsw` 索引 + `vector_cosine_ops` 余弦距离算子。HNSW（分层可导航小世界图）是目前主流的高维向量近邻搜索算法，比传统的 IVFFlat 检索更快、精度更高。

### 检索流程

一次 RAG 查询在数据库层做的事：

```sql
-- 用户问题"JVM垃圾回收" → embedding_model → 1024维向量 [0.12, -0.34, 0.56, ...]
-- 然后：
SELECT id, content, metadata, 
       1 - (embedding <=> '[0.12,-0.34,0.56,...]'::vector) AS similarity
FROM vector_store
WHERE metadata->>'kb_id' IN ('1', '2')
  AND 1 - (embedding <=> '[0.12,-0.34,0.56,...]'::vector) >= 0.7  -- minScore
ORDER BY embedding <=> '[0.12,-0.34,0.56,...]'::vector
LIMIT 5;  -- topK
```

`<=>` 是 pgvector 扩展的余弦距离运算符，`1 - 距离 = 相似度`。HNSW 索引让这个查询在高维向量上做到毫秒级。
