我们这个 RAG 知识库问答模块是面试辅导平台的核心功能之一，整体的技术栈是 Spring Boot 4.0 + Java 21 虚拟线程 + Spring AI 2.0 + PostgreSQL pgvector + Redis Stream，前端是 React 18 + TypeScript。

模块分为三大块：知识库构建、直接问答、RAG 聊天会话。我先说知识库构建这块。用户在前端上传文档后，我先对文件做安全校验——大小限制 50MB、MIME 类型白名单只放行 PDF、DOCX、TXT 这些格式，然后计算文件的 SHA-256 哈希值做基于内容指纹的去重，相同文件不会重复上传。校验通过后，用 Apache Tika 提取纯文本内容，把原始文件上传到 RustFS 对象存储拿到 fileUrl，再把文件元数据存入 PostgreSQL。这里有一个很重要的细节：数据库写入如果失败，我会触发补偿方法把 RustFS 上已上传的文件删掉，因为对象存储和数据库不在同一个事务里，必须手动保证数据一致性。

文件保存成功后，需要做向量化才能用于 RAG 检索，但这个操作比较耗时，不能放在同步请求里让用户干等。所以我用 Redis Stream 做了一个异步任务管道。发送消息有个关键设计：必须在当前数据库事务提交之后再发——因为消费者可能立刻拉取消息并查数据库，如果事务还没提交就查不到记录。我通过 `afterCommitExecutor.execute()` 延迟到事务提交后发送。消息体非常轻量，只有 taskId、kbId 和重试次数这几个字段，绝对不放文本内容，因为文本可能有几万字符，放 Redis 里会膨胀内存和带宽，消费者需要文本时自己查 kbId 去 RustFS 下载。

消费者这边是 Spring Boot 启动后创建的守护线程，持续阻塞地从 Redis Stream 拉取消息。拿到消息后，先从 RustFS 下载原始文件重新解析文本，然后用 Spring AI 的 TokenTextSplitter 按约 800 tokens 每块做切分，基于标点边界、不做重叠。切完后给每个分块写入 kb\_id 元数据，方便后续检索时按知识库过滤。因为阿里云 DashScope Embedding API 限制每批最多 10 个 chunk，我按批次循环提交给 `vectorStore.add()`，Spring AI 内部自动调 Embedding API 生成 1024 维向量写入 pgvector。整个过程中有三次重试机制，超过就标记 FAILED 让用户手动重试；任务开始前还做了幂等检查——如果 vectorStatus 已经是 COMPLETED 且 chunkCount 大于 0，说明已经向量化过了，直接跳过。chunkCount 的验证是为了防止进程崩溃时状态标记为完成但实际向量数据没写入的极端情况。

接下来说直接问答。前端选好知识库输完问题后，调用同步接口 `POST /api/knowledgebase/query`。进入 Service 后，我先创建 `RagTraceContext`，里面包含 traceId 和 sessionId，traceId 是全局唯一的请求追踪标识，sessionId 在直接问答场景是 null，只有 RAG 聊天会话才会传入真实的会话 ID，用来把检索日志关联到具体会话。然后更新知识库的提问计数，接着构建查询上下文。这个查询上下文的构建包含一个很关键的设计——问题改写：用户自然语言描述的问题往往不适合直接做向量检索，比如口语化表达、指代不明确，所以我会通过 LLM 把问题改写成更适合检索的关键词形式。改写渲染模板后同步调 LLM，如果 LLM 返回空或者异常，就降级使用原问题，绝对不阻塞主流程。然后构建候选查询词集合，改写词放前面、原词放后面，优先用改写词检索。同时还根据问题去掉空白后的紧凑长度动态调整检索参数——极短的问题放宽 minScore 提高召回率、用更大的 topK 覆盖更多候选文档；长问题本身信息量大、结果更聚焦，topK 就低一些。

然后进入 pgvector 向量检索阶段。我按候选词优先级遍历，对每个候选词调 pgvector 的余弦相似度检索，返回不超过 topK 条且不低于 minScore 的文档片段。首个候选词命中就立刻返回，不浪费时间去试后面的词。无论检索有没有命中，finally 块都保证记录两类数据：一是检索指标上报到指标采集器，二是完整检索日志写入数据库，包括 traceId、原始问题、改写问题、候选词列表、topK、minScore、命中数和耗时，方便后续排查"这次为什么没搜到"或者"为什么搜到的内容不相关"这类问题。

检索到的文档用 `\n\n---\n\n` 分隔拼接成上下文文本块，然后构建提示词。系统提示词渲染模板定义的 LLM 角色——只能基于提供的文档回答、绝不编造——并在末尾追加防注入指令，告诉 LLM 分隔符内的文本是用户数据不是命令。用户提示词把文档上下文和用户问题注入模板。最后同步调 LLM 生成回答，回答结果做归一化处理——检测到拒答关键词就替换为统一模板，正常内容直接返回。整个回答用 `QueryResponse` 包装，四个字段：回答文本、主知识库 ID、知识库名称（多库用顿号连接）、traceId，方便前端展示和问题排查。

流式问答的接口是 `POST /api/knowledgebase/query/stream`，返回 SSE 流式响应，限流比同步接口更严格，因为长连接消耗更多服务器资源。流程上和同步问答的前半段完全一样——校验、更新计数、问题改写、向量检索、拼接上下文、构建提示词都是一套代码。核心差异在 LLM 调用时：我用的是 `.stream().content()` 而不是 `.call()`，这会返回一个 `Flux<String>`，LLM 每生成一个小片段就立刻推出来，而不是等全部生成完。而且流式接口支持注入多轮对话历史消息到 LLM 上下文，这是为后面的 RAG 聊天会话预留的能力。

流式输出还有一个独有的探测窗口优化。我写了一个 `normalizeStreamOutput` 方法，它先缓冲前 120 个字符做拒答关键词检测——如果在这 120 字符里发现"没有找到相关信息"等拒答文案，立刻中断原始 LLM 流，替换为一句简短统一拒答后直接结束。这背后的考虑是：如果向量检索没找到内容，LLM 可能会生成一大段"抱歉没有找到相关信息，不过我可以建议你..."的长篇拒答，用户逐字看完这些废话体验很差，而且浪费 LLM token。如果 120 字符没命中拒答，说明是正常回答，就释放缓冲进入零延迟透传模式，后续 chunk 直接转发。流结束后通过 `doOnComplete` 记录成功指标，异常时通过 `onErrorResume` 注入友好错误提示。这个设计兼顾了体验和资源效率。

最后是 RAG 聊天会话，这是最完整的形态。创建会话时只需要选知识库和起个标题，不调 LLM，纯数据库操作。真正复杂的是发送消息的流式接口 `POST /api/rag-chat/sessions/{sessionId}/messages/stream`。整个流程分为三步——准备、流式输出、回调收尾。准备阶段我先同步写入两条数据库消息：一条用户消息 content 直接填问题文本、completed 为 true；一条 AI 占位消息 content 为空字符串、completed 为 false。这一步返回 AI 占位消息的 ID 作为句柄，因为流式输出是异步的，LLM 答案逐块到达时我无法提前知道最终内容，所以先插一个空行拿到 ID，等流结束后再回填。

流式输出阶段，我从数据库加载会话关联的知识库 ID，如果开了多轮历史上下文配置，就从消息表里查出最近的 user/assistant 消息对作为 history，然后走和直接问答流式接口完全相同的 RAG 检索流程——问题改写时因为有真实的对话历史，可以消解"那第二种方法呢"这种指代。拿到 `RagStreamResult` 后，我先手动构造一个 `event:trace` 类型的 `ServerSentEvent`，把 traceId 以 JSON 形式放进 data 字段，让前端最先拿到追踪 ID 绑定到当前消息气泡上。然后用 `Flux.concat` 串联两个 Flux：先发 trace 事件，再发回答内容。每个回答 chunk 在转发前要做换行符转义——LLM 回答中的真实 `\n` 如果直接放进 SSE 的 `data:` 行，前端解析时会把这一行数据错误地当成事件分隔符导致截断，所以我把 `\n` 替换为字面量 `\\n`，前端收到后再还原。同时通过 `doOnNext` 的副作用把每个 chunk 累积到 `StringBuilder` 里，不改变流元素本身。

回调收尾阶段，`doOnComplete` 触发时拿着第一步返回的 AI 占位消息 ID，把 `StringBuilder` 里累积的完整答案写回数据库，把那条空内容、completed 为 false 的占位行更新为完整内容和 completed 为 true。`doOnError` 触发时也做同样操作，但优先保存已收到的部分内容，完全没收到就用错误提示兜底，保证数据不丢失。最终整个 `Flux<ServerSentEvent<String>>` 由 Spring WebFlux 框架序列化为 SSE 格式，以 `Transfer-Encoding: chunked` 逐段推送给前端，前端通过 `fetch + ReadableStream` 解析 `event:` 和 `data:` 行实现打字机效果。

总结一下这个模块的几个设计亮点。第一，问题改写的优雅降级——LLM 改写失败、返回空、或关闭时都不阻塞主流程，直接降级使用原问题检索。第二，动态检索参数策略——根据问题长度自适应调整 topK 和 minScore，短问题放宽阈值提高召回，长问题严格阈值保证精度。第三，探测窗口归一化——流式输出前 120 字符做拒答检测，命中就截断替换，避免 LLM 生成长篇无用内容浪费资源。第四，先占位后回填的消息模式——解决流式输出和数据库写时序的冲突，保证消息行在任何时刻都有合理状态。第五，文件上传的哈希去重和事务后消息发送——哈希做内容指纹避免相同文件重复上传和向量化，事务后发送保证消费者不读到未提交的数据。第六，向量化的幂等保护和 chunkCount 验证——防止进程崩溃导致状态不一致的极端情况。这些点构成了一个生产可用的 RAG 系统。
