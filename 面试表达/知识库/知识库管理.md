知识库有完整的上传下载，分类，检索，统计，以及向量化等处理。

知识库文件上传：前端上传文件，后端通过controller接收到后，先通过全局限流与ip限流，然后调用uploadService服务上传文件，入参为MultipartFile文件本体，name文件名，以及category目录（即上传的文件类别，比如java面试文档，项目文档）。在上传方法内部，先调用fileValidationService服务验证文件有没有超过最大50MB限制（原理就是检测文件字节数），然后调用parseService服务检测文件类型，然后再通过哈希服务检测文件是否已经存在（将文件转成字节数组，再计算hash值，再以哈希值去数据库中查重），即去重。都通过以后，调用parseService.parseContent服务，将文件内容转换成字符串，然后保存文件本体到rustfs中，拿到filekey，之后再通过filekey获取fileurl文件地址。然后解析文件元数据，包括文件原始名称，文件大小，文件类型，key，url等信息，还有哈希值到SQL数据库中。之后发送向量化任务到redisstream，把知识库文本向量化，消息体依然是由轻量标识组成，异步任务id，业务id（与kbid一样），kbid代表知识库id，消费者以此查数据库实体，查rustfs下载文件，当前重试次数。

消息发送到redis时，必须等前面的db事务结束后再发送，即先等待存文件元数据等操作存储到数据库之后（因为发送消息操作是在事务注解内，可能会导致数据还没有存好就消费消息），才能把消息发送给消息队列，如果不这样的话，消费者消费消息时，拿着kbid去数据库中查找，但是数据库事务还没有完成，就会导致消息处理失败，之前的异步日程提醒是不需要这样的，因为日程提醒在事务外，所有执行时事务必然是提交了的。同时会在异步任务表中记录向量化这个任务，因为向量化比较耗时，前端可以查异步任务表看进度。

向量化异步任务消费：消费者在springboot启动后，就会持续循环从redisstream中拉取消息进行处理。拿到消息id后，先调用markprocessing方法标记任务正在处理，然后执行processBussiness方法执行业务逻辑。先用kbid从数据库中查询知识库实体然后做幂等性检查，看状态是不是已经完成了并且chunkcount大于0（即完成了但是因为进程崩溃，向量数据没有写进去），如果未处理就从rustfs中下载原文件，得到content字符串文件本体；之后调用vectorService的vectorizeAndStore方法，传入kbid和content进行向量化。

进入方法内部：先删除知识库的旧向量数据，然后将文本分块（过程会根据token配置启动切分），然后给每一块都添加知识库id标识(string形式)，document是分块后的格式，由spring AI提供。然后根据分块个数，分批每批10个进行向量化，调用vectorStore.add方法传入batch块。

文本分块是通过spring ai的tokentextspillter把全文转换成document，默认的分块大小是800token，最小字符数350，最小嵌入长度5，最大10000块，基于CL100K\_BASE编码，并尽量在标点处截断。同时要记好各种各样的分块策略，以及不同的分块策略的区别。

知识库文件上传的整体流程如下：前端上传文件后，后端 Controller 接收请求，首先经过全局限流和 IP 限流校验，然后调用 `uploadService.uploadKnowledgeBase()` 方法执行业务逻辑，入参为 MultipartFile 文件本体、可选的 name 文件名以及可选的 category 分类（如 Java 面试文档、项目文档等）。进入上传方法内部后，第一步调用 `fileValidationService.validateFile()` 校验文件大小是否超过 50MB 上限（通过检测文件字节数判断）；第二步调用 `parseService.detectContentType()` 检测文件 MIME 类型是否在允许范围内（PDF、DOCX、TXT 等）；第三步调用 `fileHashService.calculateHash()` 计算文件的 SHA-256 哈希值，将文件转为字节数组后生成哈希摘要，再以该哈希值去数据库中查询是否已存在同名文件，实现去重。如果命中已存在的记录，则直接返回已有结果并标记 duplicate 为 true。如果为新文件，则继续第四步：调用 `parseService.parseContent()` 通过 Apache Tika 将文件内容提取为纯文本字符串，供后续向量化使用；第五步调用 `storageService.uploadKnowledgeBase()` 将文件的原始二进制内容上传到 RustFS 对象存储，返回唯一的 fileKey，再通过 fileKey 获取对应的 fileUrl 文件访问地址；第六步调用 `persistenceService.saveKnowledgeBase()` 将文件元数据保存到 PostgreSQL 数据库，包括原始文件名、文件大小、MIME 类型、RustFS 的 storageKey 和 storageUrl、文件哈希值、name 和 category 等，如果此步发生异常，会自动调用补偿方法 `compensateUploadedKnowledgeBase()` 将已上传到 RustFS 的文件删除，避免产生孤儿文件。第七步调用 `vectorizeStreamProducer.sendVectorizeTask()` 发送向量化任务到 Redis Stream，但由于此时位于数据库事务范围内，如果直接 XADD 消息到 Redis，消费者可能立刻拉取消息并尝试查询数据库，而事务尚未提交导致查不到数据。因此采用事务后提交模式，通过 `afterCommitExecutor.execute()` 将消息发送延迟到当前数据库事务成功提交之后，确保消费者拿到消息时数据库数据已落盘。同时，发送前会在 async\_tasks 异步任务表中创建一条类型为 KB\_VECTORIZE、状态为 PENDING 的任务记录（同一 kbId 的 PENDING 任务有幂等保护，不会重复创建），前端可通过轮询该任务表查询向量化进度。发送到 Redis Stream 的消息体是轻量级的键值对，仅包含 taskId（异步任务 ID）、businessId（业务标识，与 kbId 相同）、kbId（知识库 ID）和 retryCount（重试次数，首次为 0），不包含文档文本内容——文本可能数万字符，放入 Redis 会严重膨胀内存和带宽。

向量化异步任务的消费端在 Spring Boot 启动后通过 `@PostConstruct` 创建守护线程，进入持续阻塞式拉取循环，从 Redis Stream 中实时获取消息。收到消息后，父类模板方法按固定流程执行：先调用 `markProcessing()` 将异步任务表状态和知识库实体的 vectorStatus 分别更新为 PROCESSING，然后进入 `processBusiness()` 执行业务逻辑。在业务处理中，首先通过 kbId 从数据库查询知识库实体，若实体已被删除则抛出 `AsyncTaskCancelledException` 取消任务；接着进行幂等检查，若 vectorStatus 已为 COMPLETED 且 chunkCount 大于 0（chunkCount 验证是为了防止进程崩溃时状态被标记为完成但向量数据实际未写入的极端情况），则直接跳过处理。否则调用 `parseService.downloadAndParseContent()` 从 RustFS 下载原始文件并通过 Tika 重新解析为纯文本字符串，然后委托 `vectorService.vectorizeAndStore()` 执行核心向量化逻辑。进入该方法内部后，第一步调用 `deleteByKnowledgeBaseId()` 通过原生 SQL 删除该知识库的所有旧向量数据；第二步使用 Spring AI 的 TokenTextSplitter 将文本按约 800 tokens 每块进行分块（基于标点边界切分，无重叠），得到一组 Document 对象列表；第三步为每个分块的 metadata 中写入 kb\_id 标识（统一转为 String 类型存储，确保后续过滤查询时类型一致）；第四步由于阿里云 DashScope Embedding API 限制每批最多 10 个 chunk，需要向上取整计算批次数量，然后循环将每批 Document 提交给 `vectorStore.add()`，Spring AI 内部会自动调用 Embedding API 生成 1024 维向量，并连同 metadata 一起写入 pgvector 数据库。如果向量化过程中发生异常，消费者会自动进行重试（父类控制最多 3 次），每次重试时将 retryCount 递增后重新 XADD 到 Redis Stream 尾部；超过最大重试次数后标记为 FAILED（死信），用户可手动点击"重新向量化"重新入队。处理成功后调用 `markCompleted()` 将异步任务表状态更新为 COMPLETED，同时更新知识库实体的 vectorStatus 和 chunkCount 字段，前端轮询到完成状态后即可在 RAG 对话中使用该知识库进行语义检索。

知识库文件上传的整体流程是这样的。前端上传文件后，请求先经过全局限流和 IP 限流校验，然后进入我的 `uploadService.uploadKnowledgeBase()` 方法，入参有三个：`MultipartFile` 文件本体、可选的 `name` 自定义名称、可选的 `category` 分类（比如"Java 面试文档"或"项目文档"）。

进入方法后，第一步我调用 `fileValidationService.validateFile()` 校验文件大小，上限是 50MB，通过检测文件字节数判断是否超限。第二步调用 `parseService.detectContentType()` 检测文件的 MIME 类型，只允许 PDF、DOCX、TXT 等格式，不在白名单里就拒绝。第三步我调用 `fileHashService.calculateHash()` 计算文件的 SHA-256 哈希值——先把文件转成字节数组，生成哈希摘要，然后拿这个哈希值去数据库查是否已有相同文件存在，实现基于内容指纹的去重。如果命中已存在的记录，我直接返回已有结果并把 `duplicate` 标记为 `true`，不重复上传。

如果是新文件，继续第四步：调用 `parseService.parseContent()` 通过 Apache Tika 把文件内容提取为纯文本字符串，这是后续向量化的原材料。第五步调用 `storageService.uploadKnowledgeBase()` 把文件原始二进制上传到 RustFS 对象存储，返回一个唯一的 `fileKey`，再通过这个 key 获取对应的 `fileUrl` 文件访问地址。第六步调用 `persistenceService.saveKnowledgeBase()` 把文件元数据持久化到 PostgreSQL，字段包括原始文件名、文件大小、MIME 类型、RustFS 的 `storageKey` 和 `storageUrl`、文件哈希值、`name` 和 `category`。这一步如果发生异常，我会触发补偿方法 `compensateUploadedKnowledgeBase()`，把已经上传到 RustFS 的文件删掉，避免产生孤儿文件——因为 RustFS 和数据库不在同一个事务里，必须手动补偿。

第七步是发送向量化任务到 Redis Stream。但这里有个事务时序问题：当前还在数据库事务范围内，如果直接 XADD 消息到 Redis，消费者可能立刻拉取并执行，而此时数据库事务还没提交，消费者去查数据库会找不到这条知识库记录。所以我把消息发送延迟到当前事务成功提交之后，通过 `afterCommitExecutor.execute()` 来执行。同时，发送前我会在 `async_tasks` 表中创建一条类型为 `KB_VECTORIZE`、状态为 `PENDING` 的任务记录——同一个 `kbId` 的 PENDING 任务有幂等保护，不会重复创建——前端可以轮询这个任务表来查看向量化进度。发到 Redis Stream 的消息体是非常轻量的键值对，只包含 `taskId`（异步任务 ID）、`businessId`（和 `kbId` 相同）、`kbId`（知识库 ID）和 `retryCount`（重试次数，首次为 0），绝对不包含文档文本内容——文本可能有几万个字符，放进 Redis 会严重膨胀内存和带宽，消费者需要文本时自己去数据库查 `kbId` 然后从 RustFS 下载。

接下来是消费者这边。Spring Boot 启动后通过 `@PostConstruct` 创建守护线程，进入一个持续阻塞的拉取循环，从 Redis Stream 实时获取消息。收到消息后，父类模板方法按固定流程走：先调用 `markProcessing()` 把异步任务表状态和知识库实体的 `vectorStatus` 都更新为 `PROCESSING`，然后进入 `processBusiness()` 执行真正的业务逻辑。在业务处理中，我先通过 `kbId` 从数据库查知识库实体，如果实体已被删除，就抛出 `AsyncTaskCancelledException` 取消任务；接着做幂等检查，如果 `vectorStatus` 已经是 `COMPLETED` 而且 `chunkCount` 大于 0——这里验证 `chunkCount` 是为了防止进程崩溃时状态被意外标记为完成但实际向量数据没写入的极端情况——那么直接跳过处理，不重复向量化。

否则就正式开始处理。我先调用 `parseService.downloadAndParseContent()` 从 RustFS 下载原始文件，再次通过 Tika 重新解析为纯文本字符串，然后委托 `vectorService.vectorizeAndStore()` 执行核心的向量化逻辑。这个方法里，第一步用原生 SQL `deleteByKnowledgeBaseId()` 删掉该知识库的所有旧向量数据，确保不会新旧混在一起；第二步用 Spring AI 的 `TokenTextSplitter` 把文本按约 800 tokens 每块进行切分，切分基于标点边界、不做重叠，得到一组 Document 对象；第三步给每个分块的 metadata 里写入 `kb_id` 标识，统一转成 String 类型存储，保证后续过滤查询时类型一致不出错；第四步因为我用的阿里云 DashScope Embedding API 限制每批最多 10 个 chunk，所以向上取整算出总批次数，然后循环把每批 Document 交给 `vectorStore.add()`，Spring AI 内部会自动调 Embedding API 生成 1024 维向量，连同 metadata 一起写入 pgvector 数据库。

如果向量化过程中发生异常，消费者会自动重试，父类控制最多 3 次，每次把 `retryCount` 递增后重新 XADD 到 Redis Stream 尾部；超过最大重试次数就标记为 `FAILED`，当作死信处理，用户可以在前端手动点"重新向量化"重新入队。处理成功后，调用 `markCompleted()` 把异步任务表状态更新为 `COMPLETED`，同时更新知识库实体的 `vectorStatus` 和 `chunkCount` 字段。前端轮询到完成状态后，这个知识库就可以在 RAG 对话中正常进行语义检索了。
