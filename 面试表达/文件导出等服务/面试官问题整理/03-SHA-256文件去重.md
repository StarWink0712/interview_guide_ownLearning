# SHA-256 文件去重

## 1. 文件去重为什么选择 SHA-256？

**回答：** `FileHashService` 使用 SHA-256 为文件内容生成稳定指纹。它不依赖文件名，用户即使修改文件名，只要字节内容相同，哈希仍然一致。简历和知识库都可以在解析、上传、LLM 分析或 Embedding 之前先查重，避免重复消耗存储和 AI 资源。

## 2. SHA-256 最终在数据库中保存成什么格式？

**回答：** SHA-256 输出 256 位，也就是 32 字节的二进制摘要。`bytesToHex` 通过 `String.format("%02x", b)` 把每个字节转换成两个十六进制字符，最终得到固定 64 位字符串，因此 `resumes.file_hash` 使用 `VARCHAR(64)` 保存。

## 3. 为什么数据库还要给 file_hash 建唯一索引？

**回答：** 应用层会先按 hash 查询，但两个并发请求仍可能同时判断为不存在并继续写入。数据库唯一索引作为最后一道约束，可以在底层阻止相同内容并发插入，弥补单纯“先查再写”存在的竞态条件。

## 4. 简历和知识库分别如何使用文件哈希？

**回答：** 简历上传时，`ResumePersistenceService` 用 hash 查询已有简历，命中就返回历史分析结果；知识库上传时，`KnowledgeBaseUploadService` 用 hash 查询已有知识库。这样可以避免重复解析、重复存储、重复调用 LLM 评分或 Embedding 向量化。

## 5. FileHashService 为什么提供三种重载？

**回答：** `MultipartFile` 版本适合 Controller 上传场景，内部先调用 `getBytes()`；`byte[]` 版本适合已经下载到内存的数据，直接调用 `MessageDigest.digest(data)`；`InputStream` 版本适合大文件流式计算，使用固定缓冲区逐段调用 `digest.update()`，最后调用 `digest()` 得到摘要。

## 6. InputStream 版本为什么更适合大文件？

**回答：** 它每次只读取 8192 字节，也就是 8KB，并把分块持续更新到 MessageDigest 的内部状态。无论文件多大，主要内存占用始终是一个 8KB 缓冲区和 32 字节摘要状态，属于常量级；相比之下 `MultipartFile.getBytes()` 会一次把完整文件加载到内存。

## 7. 当前 MultipartFile 哈希实现有什么风险？

**回答：** `MultipartFile` 版本调用 `file.getBytes()`，空间复杂度随文件大小增长，大文件并发上传时可能引发较高内存占用甚至 OOM。当前简历大小限制为 10MB，所以暂时可控；如果上限继续增加，应直接使用 `file.getInputStream()` 调用流式哈希实现。

## 8. SHA-256 文件级去重有什么边界？

**回答：** 它只能判断字节是否完全相同。同一份简历分别导出两次 PDF 时，文件内部时间戳或元数据可能不同，即使可见文本相同，SHA-256 也会不同，因此会被识别为两份文件。

## 9. 如何进一步实现内容级或语义级去重？

**回答：** 可以在 Tika 解析和文本清洗后，再对规范化纯文本计算 hash，从而识别二进制不同但正文相同的文档；如果还要识别表达略有变化但语义相似的内容，可以进一步增加向量语义相似度去重。
