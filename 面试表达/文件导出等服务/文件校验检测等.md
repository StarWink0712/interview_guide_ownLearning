用户在上传完简历后，在简历上传服务会触发简历文件的检验等处理逻辑，包括校验文件，检测类型，计算hash，解析文本，上传文件到rustfs，保存filekey等操作。ResumeParseService被ResumeUploadService调用，传入的参数是MultipartFile，即要处理的文件，包括验证文件类型和解析文本等方法。知识库上传服务业会调用

验证文件类型由ContentTypeDetectionService服务处理，注入一个Apache tika的检测器实例，利用tika就可以检测出真实MIME真实类型是PDF还是word，而不是简单的通过文件名后缀，简历类型验证和知识库文件验证都可以调用这个服务。

再用resumeparseService服务，解析简历文本内容，而在这个服务内部，是通过调用documentParseService服务的解析方法，传入文件即可。至于document服务内的依然是通过tika进行解析，先把文件转成inputstream输入流然后，tika会创建一个自动检测解析器 AutoDetectParser，还会创建一个内容处理器handler，用于接收简历正文，然后再创建一个元数据对象用于存储文件的属性信息，内容处理器handler就是用来存储最终读到的结果的，tostring之后就可以得到结果，，最后设置一下pdf的配置，关闭图片提前，按位置给文本排序，等最后通过handler.tostring()就可以拿到提取的文本内容了。

解析完简历文本之后，再调用storageService服务将简历原件存入到rustfs中，同时也会调用persistenceService服务把解析出的简历文本存入到sql数据库中。解析的简历文本存储到数据库中的表设计有两个表，一个是resume解析表，主要有主键id，文件名，字节数，MIME类型，简历id，然后一个简历可能会有多条评估记录，所以再用一个简历评估表，用简历id关联两个表。然后rustfs数据库类似于一个文件存储系统，是一个独立的服务端，有ip和端口，将简历原件存储到本地rustfs中后可以获得简历对应的filekey和fileurl即简历标识key和其存储在磁盘上的位置。最后调用生产者，传入简历id和简历文本，发送到redis中，发布llm解析简历的任务。

<br />

用户上传简历文件后，首先在 `ResumeUploadService` 中调用 `FileValidationService` 校验文件是否为空、大小是否超过 10MB 限制，然后通过 `ResumeParseService` 的 `detectContentType` 方法委托给基础设施层的 `ContentTypeDetectionService`，后者内部注入了一个 Apache Tika 的 `Tika` 检测器实例，调用 `tika.detect(inputStream, fileName)` 通过文件内容（而非文件名后缀）检测出真实 MIME 类型是 PDF 还是 Word，检测通过后调用 `ResumePersistenceService` 的 `findExistingResume` 方法计算文件 SHA-256 哈希值并在 `resumes` 表中查询是否已存在，若存在则直接返回历史分析结果走重复简历处理分支，若不存在则继续往下。接着调用 `ResumeParseService` 的 `parseResume` 方法，它内部委托给 `DocumentParseService` 的 `parseContent` 方法，该方法先把 `MultipartFile` 转为 `InputStream` 输入流，然后用 Tika 创建 `AutoDetectParser` 自动检测解析器，同时创建一个 `BodyContentHandler` 作为内容处理器（限制最大 5MB，只接收正文），再创建一个 `Metadata` 元数据对象用于存储文件属性信息，接着创建 `ParseContext` 解析上下文并往里面塞三样配置——显式指定 `Parser.class` 增强健壮性、设置 `NoOpEmbeddedDocumentExtractor` 禁用嵌入文档提取避免图片路径噪声、设置 `PDFParserConfig` 关闭图片提取并按坐标排序文本改善多栏布局解析，最后调用 `parser.parse(inputStream, handler, metadata, context)` 执行解析并通过 `handler.toString()` 拿到提取的纯文本内容，再由 `TextCleaningService` 清洗一遍。拿到解析后的简历文本后，调用 `FileStorageService` 的 `uploadResume` 方法将原始文件上传到 RustFS 对象存储服务端，获得对应的 `fileKey`（文件标识键）和 `fileUrl`（存储路径 URL），同时调用 `ResumePersistenceService` 的 `saveResume` 方法将简历信息（包括 SHA-256 哈希、原始文件名、文件大小、MIME 类型、RustFS 存储键和 URL、Tika 解析出的 `resumeText` 纯文本）写入 PostgreSQL 的 `resumes` 表，初始 `analyzeStatus` 设为 `PENDING`。存储入库都完成后，最后调用 `AnalyzeStreamProducer` 的 `sendAnalyzeTask` 方法，将简历 ID 和简历文本作为任务发布到 Redis Stream 中，由另一端的 `AnalyzeStreamConsumer` 异步消费并调用 LLM 进行 AI 评分分析，分析完成后将评分结果存入 `resume_analyses` 表（通过 `resume_id` 外键关联 `resumes` 表，同一份简历可有多条历史分析记录），同时更新 `resumes` 表的 `analyzeStatus` 为 `COMPLETED`。

<br />

用户上传简历文件后，系统首先通过 `ContentTypeDetectionService` 基于 Apache Tika 检测文件的真实 MIME 类型（读取魔数字节而非信任 HTTP Content-Type），然后计算 SHA-256 哈希检查是否已存在相同文件，若重复则直接返回历史分析结果。新文件通过 `DocumentParseService` 使用 Tika 的 `AutoDetectParser` 提取纯文本（禁用嵌入文档解析、PDF 按位置排序输出、限制最大 5MB），解析后的 `resumeText` 同时存入 RustFS 对象存储和 PostgreSQL 数据库的 `ResumeEntity.resumeText` 列中。接着通过 `AnalyzeStreamProducer` 将任务消息写入 Redis Stream `resume:analyze:stream`，立即返回 PENDING 状态给前端。异步消费者 `AnalyzeStreamConsumer` 从 Stream 拉取消息后，从数据库读取简历文本，调用 `ResumeGradingService` 通过 LLM 执行结构化输出评分——系统 Prompt 和用户 Prompt 从 `resources/prompts/` 的 StringTemplate 模板加载，注入简历全文，LLM 返回包含五维度评分（项目经验 40 分、技能匹配度 20 分、内容完整性 15 分、结构清晰度 15 分、表达专业性 10 分）及综合总结、优势列表、改进建议的结构化 JSON，通过 `StructuredOutputInvoker` 做最多 3 次重试和 JSON 修复后反序列化为 `ResumeAnalysisResponse`，最终持久化到 `ResumeAnalysisEntity` 表，消费者同步更新任务状态为 COMPLETED，用户即可在前端查看完整的简历评分报告。
