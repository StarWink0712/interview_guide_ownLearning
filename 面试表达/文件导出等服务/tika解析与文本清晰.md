文档解析这块我用了 Apache Tika 的 `AutoDetectParser`，因为项目同时支持 PDF、Word、TXT、Markdown 等格式，Tika 可以统一完成格式识别和文本提取。解析时我没有直接用默认配置，而是做了几个针对 AI 输入质量的优化：用 `BodyContentHandler` 只提取正文并限制最大文本长度；注册 `NoOpEmbeddedDocumentExtractor` 禁用嵌入资源解析，避免图片文件名和临时路径污染正文；PDF 解析关闭内联图片提取，并开启按坐标排序，改善多栏简历的文本顺序。
提取出的原始文本还会经过 `TextCleaningService` 清洗，去掉控制字符、图片文件名、图片 URL、`file://` 路径和分隔线，再统一换行、去除行尾空格、压缩连续空行。这样简历分析和知识库向量化拿到的是更干净的文本，减少 token 浪费和语义噪声。

一般情况下，llm本身是不能直接消费pdf或word的二进制内容的，所以上传完文件后需要解析，我用了Apache tika做统一解析入口，再加一层文本清洗，把图片路径，控制字符还有无意义的分割线等内容过滤掉，让后续简历分析和知识库向量化拿到更干净的文本。

tika的好处是支持多种格式，比如pdf，word，markdown，txt等格式。如果一个格式都接一个解析器，都会有很多分支。tika的自动检测解析器可以自动识别格式，选择对应的解析器，输出统一的string文本。一次做完格式检测和内容解析。有刚上传的文件解析，即将file文件（即输入流）调用对应的解析器从输入流二进制信息中读取文件类型和字符串文本内容。

还有从rustfs存储中下载文件拿到字节数组文件后的解析，用文件名称和字节数组进行解析，方法就是把字节数组（即rustfs中存的原文件，任何文件存储的都是以字节数组形式）转成输入流，再调用tika解析原简历输入流一样的方法进行解析（即tika可以从输入流中解析出文件内容信息，输入流就是文件的二进制信息），本质就是下载存储中的源文件后先从字数数组转成输入流，再调用tika解析。

文本清晰主要是通过正则表达式清晰图片路径，控制字符，以及html标签等内容清除掉。

文件去重用hashSHA-256算法，将文件file转成字节数组，然后计算哈希值，得到十六位哈希数组

文件去重我用的是 `FileHashService`，核心是基于 SHA-256 计算文件内容指纹。SHA-256 输出的是 256 位即 32 字节的二进制摘要，经过 `bytesToHex` 方法逐字节转换为两位十六进制字符（`String.format("%02x", b)`），最终得到固定 64 位的十六进制字符串，数据库 `resumes` 表的 `file_hash` 字段类型正是 `VARCHAR(64)` 并加了唯一索引，利用数据库唯一约束在底层兜底防止并发写入同一文件。它不依赖文件名，所以用户改名上传同一份文件，hash 仍然一样。简历上传时，`ResumePersistenceService` 会用 hash 查已有简历；知识库上传时，`KnowledgeBaseUploadService` 会用 hash 查已有知识库，避免重复解析、重复存储、重复调用 LLM 或 embedding。

实现上提供了三个重载：`MultipartFile` 版本内部先调 `file.getBytes()` 拿到完整字节数组再调用 `MessageDigest.digest(data)` 一次性计算；`byte[]` 版本直接对字节数组调用 `digest`；`InputStream` 版本用 8192 字节即 8KB 的 buffer 分块调用 `digest.update(buffer, 0, bytesRead)` 流式更新，适合大文件场景，不管文件多大内存占用始终是一个 8KB 数组加一个 32 字节的 MessageDigest 内部状态，常量级。每次 `update` 后内部状态累加，最后 `digest()` 返回最终的 32 字节摘要。MultipartFile 版本其实不是最优的，因为 `file.getBytes()` 会把整个文件读进内存，大文件有 OOM 风险，但简历上传上限 10MB 且在可控范围内，所以先这样用着。

这个方案的边界是它只能做文件级去重，不能识别内容相同但重新导出导致字节不同的文件，比如同一份简历 PDF 导出两次，内部元数据时间戳不同，SHA-256 就不一样了。后续如果要更智能，可以增加解析后纯文本的 hash 或语义相似度去重。
