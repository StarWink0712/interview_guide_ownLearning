## 十分钟完整口播稿

其实核心就是 llm注册中心；限流模块；消息队列异步任务模块；普通面试；rag知识库，知识库问答与测试；语音面试；其中带有几个简历评估与面试评估。要知道各个模块最可能问的，比如llm注册中心相关的，调用失败重试，llm网关，限流，降级等；消息消费的涉及到消息队列选型，消息队列性质；rag相关的文档如何切分如何存的，rag评测是怎么做的；还有一些基础八股，rag和llm以及agent相关的八股。

面试官您好，我这个项目是一个 AI 面试辅助平台，主要面向准备技术面试的求职者。它要解决的不是单一的简历 CRUD，也不是一个普通的聊天页面，而是把求职者面试前、面试中、面试后的几个关键动作串成一个闭环。

很多求职者准备面试时会遇到几个问题。第一，简历质量自己很难判断，比如项目经历是否突出、技术栈是否匹配岗位、有没有明显风险点。第二，练习面试时题目经常比较泛，和自己的简历、目标岗位、真实 JD 结合不够。第三，练完之后缺少系统化复盘，只知道答得好不好，但不知道是基础知识、项目表达、系统设计还是沟通表达出了问题。第四，学习资料、项目文档、面试记录比较分散，复习效率低。

所以我把这个系统设计成一个面试准备闭环：用户先上传简历，系统解析简历并做 AI 分析；然后用户选择 Java 后端、系统设计、算法、大厂专项等 Skill 方向，也可以结合目标岗位 JD 创建模拟面试；面试过程中系统会生成问题、记录回答、支持追问和即时评估；结束后生成综合评估报告；如果用户想补弱，可以把项目文档、学习资料、八股文上传到知识库，通过 RAG 问答来针对性复习；如果用户收到了真实面试邀请，还可以用日程模块解析公司、岗位、时间和会议链接，统一管理提醒。

技术架构上，后端是 Spring Boot 4 和 Java 21，使用 JPA 操作 PostgreSQL，向量检索用 PostgreSQL 的 pgvector，Redis 负责会话缓存、接口限流和 Redis Stream 异步任务，AI 接入用 Spring AI，文件解析用 Apache Tika，原文件存储到 RustFS 这种 S3 兼容对象存储，PDF 报告导出用 iText。前端是 React、TypeScript、Vite 和 TailwindCSS。整体分层是 Controller、Service、Repository，再加上 infrastructure 层和 common 公共能力层，Controller 只做路由和参数校验，业务编排放到 Service，文件、Redis、PDF、AI 调用这些通用能力做成基础设施。

我比较想重点讲三个核心模块：简历分析、模拟面试和知识库 RAG。这三个模块最能体现项目主线，也能把后端工程设计讲清楚。

先说简历分析模块。用户上传简历之后，后端并不是简单保存文件，而是有一条完整链路。Controller 接到文件后，先通过限流注解控制高成本接口访问频率，然后进入 ResumeUploadService。Service 里会做文件空值、大小、格式校验，支持 PDF、Word、Markdown、TXT 等类型。文件类型不是只看扩展名，还会做真实 MIME 检测，避免用户把不支持的文件改后缀上传。

校验通过后，系统会用 SHA-256 对文件内容计算哈希，再查数据库里是否已有相同 hash。这里用内容哈希而不是文件名去重，因为同一份简历可能换个名字重复上传。命中重复时可以直接返回已有分析结果，减少存储成本和 AI 调用成本。没有重复时，系统用 Apache Tika 解析正文，再通过文本清洗去掉控制字符、图片路径、多余空行等噪声。如果解析出来是空文本，比如扫描版 PDF，就会直接抛业务异常。

原文件不会直接存数据库，而是上传到 RustFS，对象存储返回 fileKey 和 fileUrl。数据库只存文件名、大小、hash、存储地址、解析文本和状态。这里还有补偿逻辑，如果对象存储上传成功但数据库入库失败，会回删已上传文件，避免出现孤儿文件。

AI 分析这一步我没有放在上传接口里同步等待，而是投递到 Redis Stream。生产者不会把整段简历文本塞进消息体，只写 taskId 和 resumeId，真正的简历文本留在数据库里。这样 Stream 消息比较轻，不会撑 Redis 内存。消费者拿到消息后，再查 ResumeEntity，读取简历文本，调用 ResumeGradingService 组装 Prompt，通过 StructuredOutputInvoker 调用大模型做结构化输出，从内容完整性、结构清晰度、技能匹配度、表达专业性、项目经验等维度打分，最后把评分、优势和建议落库。消费者最多重试 3 次，如果简历在分析前被删除，会识别为任务取消并 ACK 丢弃。这块设计的核心是把耗时和不稳定的 AI 调用从 HTTP 请求里解耦出来，同时保留任务状态、失败重试和前端轮询能力。

第二块是模拟面试模块。这个模块的核心不是随机出题，而是尽量让问题贴近用户的简历、目标岗位和历史练习情况。用户创建面试会话时，会传 skillId、难度、题目数量、可选简历 ID、JD 文本和 LLM Provider。后端会先检查 Redis 里是否已有这个简历未完成的会话，如果有就恢复，避免用户刷新后丢失进度；没有的话再新建会话。

新建时系统会查询历史题目，把同一 skill 或同一简历下最近考过的问题整理进 Prompt，要求模型尽量避免重复。出题服务会根据是否有简历分流：没有简历时按 Skill 定义的考察分类分配题目；有简历时大约 60% 题目来自简历项目经历，剩余来自面试方向本身。这里用 Java 21 的虚拟线程并行生成简历题和方向题，因为调用 LLM 属于 I/O 密集型任务，大部分时间在等网络返回，虚拟线程能用更低成本提升并发。

出题时用的是 plain ChatClient，也就是不带工具调用和额外记忆的客户端，避免结构化 JSON 输出被工具调用干扰。系统 Prompt 里会追加输出格式要求，BeanOutputConverter 负责把模型返回转换成 QuestionListDTO。如果 JSON 解析失败，StructuredOutputInvoker 会先尝试本地修复常见问题，比如字符串中未转义引号，然后按配置重试；最终失败时抛 BusinessException，而不是 RuntimeException。

用户答题时，服务会先从 Redis 取会话缓存，校验 questionIndex，然后把答案写回缓存，再做数据库 upsert，把每道题的答案存到 interview\_answers 表中。每提交一题会触发一次即时评估，AdaptiveInterviewService 会调用 TurnEvaluationService 给本题评分，再用 AbilityProfileService 更新能力画像，最后由 AdaptiveDecisionService 判断下一步策略，比如追问、提高难度、切换分类。这个即时评估失败不会阻断用户答题，只记录日志并返回空结果。

当最后一题提交后，会话状态变为 COMPLETED，综合评估任务再通过 Redis Stream 异步投递。消费者会加载整场面试的问题和答案，交给 UnifiedEvaluationService 做分批评估、批次合并和二次汇总，生成总分、分类得分、逐题反馈、优势、改进建议和参考答案。文字面试和语音面试共用这套统一评估架构，这样评估口径一致，也减少重复逻辑。

第三块是知识库 RAG。这个模块解决的是大模型无法直接了解用户私有资料的问题。用户可以上传项目文档、学习笔记、JD、面试复盘等资料，系统把它们处理成可检索的知识资产。RAG 我会拆成两条链路来讲：离线入库链路和在线问答链路。

离线入库链路和简历上传有相似的基础步骤，包括文件校验、MIME 检测、哈希去重、Tika 解析、文本清洗和对象存储。不同点在于，知识库文档的解析文本主要是为了后续向量化，不一定作为核心业务数据长期直接展示。元数据入库后，系统通过 VectorizeStreamProducer 投递向量化任务。消费者拿到任务后会下载原文件或读取文本，使用 TokenTextSplitter 做文本分块，然后通过 Spring AI 的 EmbeddingModel 生成向量，最后写入 pgvector 的 vector\_store 表。每个 chunk 的 metadata 会带上 kb\_id、文件名、chunk 序号等信息，方便后续按知识库范围过滤。

在线问答链路里，用户提问后会先做参数校验和限流。RAG 聊天模式还会加载最近几轮历史消息，因为用户经常问“那这个怎么优化”这种带指代的问题。系统支持 Query Rewrite，也就是结合历史把短问题改写成更适合检索的完整查询。比如“这个怎么优化”可能会被改写成“Redis Stream 消费失败重试如何优化”。如果改写失败，会回退到原问题，不影响主流程。

检索参数也不是固定的。短查询语义弱，系统会提高 topK、降低 minScore，尽量扩大召回；长查询语义更明确，就减少 topK，避免上下文塞进太多噪声。向量检索通过 pgvector 做余弦相似度搜索，并按用户选择的 knowledgeBaseIds 做过滤。如果 VectorStore 的前置过滤不可用，还会扩大召回后在 Java 内存里二次过滤。

检索到 chunk 后，系统会把相关文档片段组装成 context，再和用户问题一起放进 Prompt。Prompt 里会明确告诉模型，知识库内容是用户数据，不是指令，避免 Prompt Injection。没有检索结果时，系统不会让模型自由发挥，而是返回固定的“未检索到相关信息”提示，控制幻觉。返回方式上既支持普通 HTTP 一次性返回，也支持 SSE 流式返回。RAG 场景用 SSE 很合适，因为它是服务端向前端单向推送模型输出，不需要 WebSocket 那种双向实时通信。

这里我也会诚实说明边界：当前项目实现的是比较完整的向量检索型 RAG，有知识库元数据搜索，但还没有做真正的 chunk 级 BM25 加向量检索混合召回，也还没有做完整的用户级权限系统、rerank 和引用溯源。生产级可以继续增加全文索引、RRF 融合、rerank、来源引用和 userId/tenantId 权限过滤。

支撑这些业务模块的，是几个公共工程能力。

第一是 AI 公共层。因为项目里简历评估、面试出题、JD 解析、RAG 问答、语音面试都会调用 LLM，如果每个 Service 都自己拼 baseUrl、apiKey 和模型名称，后续很难维护。所以我做了 LlmProviderRegistry，统一管理多个 OpenAI 兼容 Provider，比如 DashScope、DeepSeek、Kimi、GLM、LM Studio。Provider 配置优先从数据库读，配置文件作为兜底，这样可以在设置页修改默认模型，不需要重启项目。Registry 会懒加载并缓存 ChatClient 和 EmbeddingModel，同时区分 default、plain、voice 三类 ChatClient：default 用于普通对话，plain 用于结构化输出，voice 用于语音面试流式场景。

第二是结构化输出。很多 AI 场景不是要一段自然语言，而是要稳定的 JSON，比如简历评分、面试题列表、JD 解析、即时评估。StructuredOutputInvoker 负责追加防注入指令，调用 plain ChatClient，解析 BeanOutputConverter，失败时做 JSON 修复和重试，最终失败统一抛 BusinessException。这个组件让业务层不用每次重复写解析和兜底逻辑。

第三是 Redis Stream 异步任务。项目里主要有三类耗时任务：简历分析、知识库向量化、面试评估。选择 Redis Stream 是因为项目本身已经依赖 Redis，用它可以复用基础设施，部署成本比 Kafka 或 RocketMQ 低；同时它支持 Consumer Group、ACK、Pending List，足够支撑中等规模异步任务。每个消费者继承 AbstractStreamConsumer，统一处理消息读取、PROCESSING/COMPLETED/FAILED 状态、ACK、最多 3 次重试和异常记录。我的选型原则不是说 Redis Stream 一定比专业 MQ 好，而是在这个单体项目和中等任务量下，它更轻量、更够用。后续如果系统拆成多服务，消息量明显增长，或者需要长期日志回放，再考虑 Kafka 或 RocketMQ。

第四是接口限流。AI 相关接口成本高，比如简历上传、知识库问答、创建面试、JD 解析，如果被频繁刷新会浪费模型调用成本，甚至拖垮数据库和 Redis。所以项目里做了声明式分布式限流组件。Controller 方法标注可重复的 @RateLimit，可以同时配置 GLOBAL、IP、USER 多个维度。RateLimitAspect 用 @Around 拦截方法，生成 Redis Key，再通过预加载的 Lua 脚本实现滑动时间窗口。Lua 里用 String 保存当前令牌数，用 Sorted Set 保存窗口内请求记录，脚本原子执行，所有维度都通过才执行原方法，任一维度超限就抛 RateLimitExceededException，由全局异常处理器统一返回错误码。

第五是可观测性。项目里有 TraceIdFilter，在请求进来时生成 traceId 并放进 MDC，后续日志都能带上这个 traceId。AI 调用侧也做了 Provider 级观测，记录一次 ChatClient 逻辑调用的最终结果，以及底层每一次真实 HTTP attempt 的重试详情。RAG 还会记录 trace，包括原问题、改写问题、topK、minScore、命中 chunk、相似度分数和检索耗时。这样当 RAG 回答不准时，可以定位到底是 query rewrite 错了、检索没命中、阈值设置不合理，还是模型生成环节出了问题。

除了这三大核心模块，项目还有两个扩展亮点。

一个是语音面试。它更接近真实面试场景，链路比文字面试复杂。用户先通过 REST 创建语音会话，后端生成 sessionId 并返回 WebSocket URL。前端建立 WebSocket 后，服务端会启动和 DashScope ASR 的连接，前端持续把音频片段发给后端，后端转发给 ASR，ASR 的 partial 结果用于实时字幕，final 结果累积到 mergeBuffer。用户点击提交后，后端把完整文本保存下来，调用 LLM 生成面试官回复，再通过 TTS 合成语音，最后通过 WebSocket 推给前端播放。这里要处理连接状态、消息大小、回声冷却、并发提交锁、暂停恢复和结束评估。语音面试结束后也会投递异步评估任务，复用统一评估框架。

另一个是面试日程。它看起来像 CRUD，但业务上是把真实面试节点和训练系统连接起来。用户粘贴面试邀请后，系统通过规则和 AI 双引擎解析公司、岗位、时间、会议链接，放到日历里管理，还支持状态流转和提醒。这样用户不是孤立地练习，而是围绕真实面试安排做准备。

如果总结这个项目，我认为它的重点不是“我调了一个大模型”，而是把传统 Java 后端能力和 AI 应用场景结合起来，做成一个完整业务系统。里面涉及文件处理、对象存储、异步任务、Redis Stream、向量检索、Prompt 安全、结构化输出、实时 WebSocket、统一异常、限流和监控。我的主要收获是：AI 项目真正难的地方不是一次调用模型，而是模型调用前后的工程治理，比如输入怎么清洗、结果怎么稳定解析、失败怎么重试、任务怎么异步化、成本怎么控制、效果怎么评估、问题怎么排查。

后续如果继续优化，我会优先做几件事。第一，RAG 增加 chunk 级全文索引、混合检索、rerank 和引用溯源。第二，补强用户权限和多租户隔离，把 userId、tenantId 写入文档 metadata。第三，给 LLM Provider 做更完整的熔断、降级和备用 provider 切换。第四，语音链路继续优化端到端延迟、降噪和弱网体验。第五，扩展 RAG 评测集，用命中率、MRR、上下文相关性和幻觉率来持续评估效果。

所以我介绍这个项目时，核心会落在一句话上：它是一个围绕求职者面试准备闭环设计的 AI 面试平台，而不是简单的功能堆叠。业务上它串起简历、岗位、面试、评估、知识库和日程；技术上它把 Java 后端的可靠性设计和 AI 调用治理结合起来。

## 两分钟压缩版

如果面试官只让简单介绍，可以压缩成这一版：

> 我做的是一个 AI 面试辅助平台，主要面向准备技术面试的求职者。它围绕“简历分析、模拟面试、评估复盘、知识库补弱、日程管理”形成一个完整闭环。用户先上传简历，系统做文件校验、Tika 解析、对象存储、hash 去重，然后通过 Redis Stream 异步调用 AI 生成简历评分和建议。接着用户可以选择 Java 后端、系统设计、算法等 Skill 方向，结合简历和 JD 创建模拟面试，系统会做个性化出题、历史题去重、多轮追问、即时评分和综合评估。知识库模块则支持用户上传项目文档和学习资料，经过分块、Embedding 和 pgvector 入库后，通过 Query Rewrite、向量检索、Prompt 组装和 SSE 流式返回实现 RAG 问答。项目还扩展了 WebSocket 语音面试、面试邀请解析、多 Provider 配置、限流、异步任务监控和 AI 调用观测。这个项目的重点不是简单调用大模型，而是围绕真实业务场景，把文件处理、异步任务、向量检索、LLM 稳定性、实时通信和可观测性这些后端能力组合起来。

## 一分钟压缩版

> 这是一个面向求职者的 AI 面试辅助平台，核心是把面试准备做成闭环：简历上传后做解析和 AI 分析，用户再基于简历、JD 和 Skill 方向进行模拟面试，系统记录回答、支持追问和评估报告；学习资料可以上传到知识库，通过 pgvector 向量检索和大模型生成 RAG 回答；真实面试邀请可以进入日程管理。技术上我重点做了 Tika 文件解析、RustFS 对象存储、Redis Stream 异步任务、Spring AI 多 Provider、结构化输出重试、RAG 检索、WebSocket 语音面试、接口限流和可观测性。这个项目不是单纯调模型，而是把 AI 能力工程化到一个完整的 Java 后端业务系统里。

## 高频追问快答

### 问：为什么简历分析要异步？

因为简历分析包含文件解析、外部 AI 调用和结构化结果解析，耗时不可控，也可能失败。同步处理会让上传接口阻塞太久。异步后，上传接口只负责保存文件、创建任务并返回 PENDING，AI 分析由 Redis Stream 消费者处理，前端可以轮询任务状态，失败也能统一重试和标记。

### 问：为什么用 Redis Stream，不用 Kafka 或 RocketMQ？

这个项目是单体应用，异步任务主要是简历分析、知识库向量化和面试评估，任务量中等，已经依赖 Redis。Redis Stream 的 Consumer Group、ACK、Pending List 和重试机制已经够用，部署运维成本低。Kafka 更适合高吞吐事件流和长期日志回放，RocketMQ 更适合复杂事务消息、延迟消息等场景，目前项目用不到那么重的能力。

### 问：你的 RAG 链路完整吗？

当前实现了完整的向量检索型 RAG：文档上传、校验、解析、清洗、对象存储、异步分块、Embedding、pgvector 入库、Query Rewrite、动态 topK 和 minScore、知识库 ID 过滤、Prompt 组装、LLM 生成、SSE 流式返回和 RAG Trace。边界是还没有做 chunk 级 BM25 混合检索、rerank、来源引用和完整权限系统，这些属于后续生产级增强方向。

### 问：怎么控制大模型幻觉？

第一，没有检索结果时直接返回固定无结果提示，不让模型自由发挥。第二，Prompt 明确要求基于知识库上下文回答，并把用户文档声明为数据不是指令。第三，RAG Trace 记录命中 chunk、分数和查询改写，便于排查回答不准的原因。后续可以补充引用来源、rerank 和离线评测集来继续降低幻觉。

### 问：多模型 Provider 为什么要抽象？

项目里简历评估、出题、JD 解析、RAG、语音面试都会调用模型。如果模型配置写死在业务 Service 里，切换厂商和模型会很麻烦。LlmProviderRegistry 统一管理 ChatClient 和 EmbeddingModel，配置优先从数据库读取，支持动态切换默认 Provider。业务层只关心拿 ChatClient，不绑定具体厂商。

### 问：结构化输出为什么需要单独封装？

因为很多场景需要模型返回 JSON，而 LLM 输出不稳定，可能带 Markdown 代码块、解释文字、未转义引号或者字段缺失。如果每个业务模块都自己解析，会有大量重复代码。StructuredOutputInvoker 统一追加格式约束和防注入指令，做 JSON 修复、重试和 BusinessException 兜底，提升结构化调用稳定性。

### 问：限流怎么做？

项目提供可重复的 @RateLimit 注解，支持 GLOBAL、IP、USER 三种维度。RateLimitAspect 拦截方法后，对每条规则生成 Redis Key，通过预加载 Lua 脚本做滑动时间窗口计数。Lua 脚本原子执行，所有限流维度都通过才进入业务方法，任一维度超限就返回统一错误码。高成本接口如简历上传、RAG 查询、创建面试、JD 解析都加了限流。

### 问：语音面试难点是什么？

难点在实时链路和状态管理。前端通过 WebSocket 发送音频，后端转发给 ASR，partial 结果用于实时字幕，final 结果累积，用户提交后再调用 LLM 和 TTS 返回语音。这里要处理 ASR/TTS 连接、回声冷却、并发提交、消息大小、暂停恢复、会话缓存和最终异步评估。

### 问：这个项目和普通 CRUD 最大区别是什么？

普通 CRUD 主要是数据增删改查。这个项目有文件解析和对象存储，有外部 AI 调用，有 Redis Stream 异步任务，有 pgvector 向量检索，有 WebSocket 实时通信，有限流、统一异常、Provider 抽象和可观测性。它更像一个业务流程型系统，重点是把多个后端能力组合成一个稳定可用的 AI 应用。
