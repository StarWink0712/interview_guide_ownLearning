# 限流需求与整体方案

## 1. 为什么项目需要限流？

**回答：** 简历上传会触发文件解析和 AI 分析，知识库查询涉及向量检索和 LLM 生成，创建面试会话需要生成题目，JD 解析也会调用模型。如果这些高成本接口被频繁刷新，轻则浪费模型调用成本，重则拖垮 Redis、数据库和文件处理等其他组件，因此需要在进入业务方法前进行限流。

<br />

要限流很简单，因为llm调用，rag向量检索以及文档向量化都是成本较高的操作，如果高成本接口被频繁刷新，轻则是浪费模型调用成本，重则是可能拖垮redis数据库等组件。llm调用也有并发限制，所以是需要限流的。

## 2. 哪些接口需要重点限流？

**回答：** 当前主要限流的接口包括简历上传、简历重新分析、创建面试会话、提交面试答案、知识库查询和流式查询、知识库上传和重新向量化，以及 JD 解析。这些接口要么涉及文件解析，要么会访问向量数据库或调用 LLM，资源成本相对较高。

<br />

简历上传，简历分析，创建会话这些都是需要限流的，就算有的比如创建会话是不需要调用llm的，但是是需要用到redis和数据库的，要把会话信息上传到redis缓存和数据库中。

## 3. 为什么使用注解实现限流？

**回答：** 项目把限流设计成声明式组件，Controller 只需要在目标方法上标注 `@RateLimit`，不需要在每个业务方法里手动编写 Redis 和 Lua 调用。真正的限流逻辑集中在 `RateLimitAspect` 中统一维护，实现业务零侵入，同时便于多个接口复用同一套分布式限流能力。

<br />

因为spring的aop切画，可以让公共业务不干扰核心业务插入其中，限流这种周边业务可以利用aop，底层是动态代理进行增强，执行原方法时，先执行around通知方法，利用lua脚本，根据业务标识去redis中利用滑动窗口算法看当前窗口内还允许多少个请求。

## 4. `@RateLimit` 支持哪些限流维度？

**回答：** 注解支持 GLOBAL、IP 和 USER 三种维度。GLOBAL 表示整个接口共享一个限流额度，不区分请求 IP 和用户；IP 按客户端 IP 分别限流；USER 按用户 ID 分别限流。对应 Key 类似 `ratelimit:{ResumeController:upload}:global`、`ratelimit:{ResumeController:upload}:ip:1.2.3.4` 和 `ratelimit:{ResumeController:upload}:user:10001`。

<br />

三个维度 一个是全局维度  整个接口无论是谁访问什么ip访问都一起限流；然后是ip限流，即前端ip，还有一个是user用户限流，因为可能一个ip上有多个用户。

## 5. 注解中可以配置哪些参数？

**回答：** 限流参数包括时间窗口内的最大请求数、窗口大小、时间单位、等待令牌的超时时间，以及限流触发后的降级方法。例如上传简历方法配置 GLOBAL、count=5，就表示在对应时间窗口内全局最多允许五次请求。

<br />

最大请求数，窗口大小，我设置的是1秒，然后等待令牌的超时时间等，还有限流触发后的降级方法，降级方法要根据业务确定，我这里是直接告诉前端请稍后再试，有的其他的业务比如非要紧查询业务可以先返回缓存，写接口直接拒绝。

## 6. 多条限流规则是什么关系？

**回答：** 同一方法可以通过 `@Repeatable` 同时声明多条规则，例如简历上传同时配置 GLOBAL 和 IP。规则之间是 AND 关系，请求必须先满足全局额度，也满足当前 IP 或用户额度，所有规则都通过后才能执行原业务方法。

## 7. 请求被限流后如何降级？

**回答：** 任意规则不通过时优先调用注解配置的 fallback，没有 fallback 就抛出 `RateLimitExceededException`，由全局异常处理器返回统一错误码 8001。读接口可以降级返回缓存或提示稍后重试；写接口更适合直接拒绝，避免用户误以为操作已经成功。

<br />

限流了就走fallback降级方法
