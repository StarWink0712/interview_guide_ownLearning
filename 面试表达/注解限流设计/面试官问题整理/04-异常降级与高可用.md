# 异常、降级与高可用

## 1. 什么是 NOSCRIPT 异常？

**回答：** Lua 脚本通过 `SCRIPT LOAD` 缓存在 Redis 中，Redis 重启后脚本缓存可能被清空。如果应用仍使用原来的 SHA1 调用 `EVALSHA`，Redis 就会返回 `NOSCRIPT No matching script. Please use EVAL.`，表示当前实例中已经找不到对应脚本。

## 2. NOSCRIPT 为什么可以自动恢复？

**回答：** NOSCRIPT 只是脚本缓存丢失，不代表 Redis 服务或限流数据结构本身发生了不可恢复故障。代码捕获该异常后重新执行一次 `SCRIPT LOAD` 获取新的 SHA1，再重试 `EVALSHA` 即可恢复。

## 3. 非 NOSCRIPT Redis 异常怎么处理？

**回答：** 连接超时、READONLY、OOM 和 CLUSTERDOWN 等异常不是重新加载脚本能够解决的，因此代码不会针对这些错误反复加载 Lua，而是直接向上抛出，交给全局异常处理器返回系统错误。连接问题需要等待 Redis 恢复，READONLY 需要切换主节点，OOM 需要扩容或清理数据，CLUSTERDOWN 则需要修复集群。

## 4. Redis 宕机时限流应该 fail-open 还是 fail-closed？

**回答：** 需要根据接口风险决定，不能统一处理。高成本接口应该 fail-closed，Redis 不可用时直接拒绝，保护数据库、LLM 和文件解析资源；低风险读接口可以 fail-open，优先保证可用性；更好的折中是在 Redis 异常时临时使用本地限流。

## 5. 哪些接口应该 fail-closed？

**回答：** 简历上传、AI 评分、知识库问答和 Provider 连通性测试等高成本接口适合 fail-closed。Redis 不可用时返回“系统繁忙，请稍后再试”，避免限流失效后大量请求直接冲击更昂贵的后端资源。

## 6. 哪些接口可以 fail-open？

**回答：** 普通配置查询、列表查询等低风险读接口可以在 Redis 不可用时暂时放行。这些接口资源成本较低，可以优先保证系统可用性，而不是因为限流组件故障导致全部读取能力不可用。

## 7. Redis 异常时如何做本地兜底限流？

**回答：** 可以临时退化为单机内存限流，例如使用 Caffeine，或者使用 `ConcurrentHashMap + 时间窗口` 保存本实例的请求状态。它不再是分布式精确限流，但比 Redis 故障后完全放开所有请求更安全。

<br />

redis异常就表明无法限流了，无关紧要的请求可以直接降级关闭，也可以本地进行限流。本地用caffeine做一个缓存，也可以用滑动窗口，本地用一个并发map集合代替zset，再用map存所有的string和value代表令牌数。

## 8. 为什么要设置短超时并记录监控指标？

**回答：** Redisson 的连接超时和命令超时不能设置得过长，否则每个业务请求都会阻塞在限流检查上。还需要对 Redis 连接失败、限流触发和降级次数记录日志及 Micrometer 指标，及时发现限流组件异常。

## 9. Sentinel 和 Cluster 分别适合什么限流场景？

**回答：** Redis Sentinel 提供主从和自动故障转移，应用统一写主节点，限流数据不会因为连接不同节点而分裂，适合当前限流场景优先考虑。Redis Cluster 提供分片和高可用，适合限流 Key 数量很多、Redis 压力较大的场景，但 Lua 脚本访问的所有 Key 必须落在同一 Slot，因此 Key 设计需要使用 Hash Tag。

<br />

redis哨兵集群和cluster集群不同，前者哨兵集群主要是解决主从节点和自动故障转移的问题；后者是对redis数据进行分散的，key太多可以分散到其他节点上；redis的大key和热key也是这个道理，key太热就每个都存储，比如点赞可以拆开多个节点都点赞，然后求和把所有节点的值相加即可。
