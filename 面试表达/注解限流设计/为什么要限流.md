### 为什么要限流？

很多接口比如简历上传会触发文件解析和ai分析，知识库查询要涉及到向量检索和llm生成，创建面试会话服务要生成题目，jd解析也会调用llm，需要调用llm的地方很多，如果这些接口被频繁刷新，轻则浪费模型调用成本，重则拖垮redis，数据库等其他组件。所以需要对llm调用做限流，一般可以通过注解的形式，加载到需要限流的方法上，同时用redislua实现分布式限流。

<br />

对于ratelimit限流注解本身，设计了三种限流维度，全局限流，ip限流，user用户限流；限流参数包括窗口内最大请求数，时间窗口大小，时间单位，等待令牌超时时间，还有限流时触发的降级方法。全局限流是包含整个端口，无论发起请求的前端的ip和用户，都走这一个限流接口，rediskey的设计是ratelimit:{ResumeController:upload}:global；ip是只针对发起请求的前端的ip，无论多少个用户，key设计为Redis Key: ratelimit:{ResumeController:upload}:ip:1.2.3.4
Redis Key: ratelimit:{ResumeController:upload}:ip:5.6.7.8；而user级限流是针对的用户id，key设计为Redis Key: ratelimit:{ResumeController:upload}:user:10001。

比如在上传简历的方法上面加上@ratelimit(dimension=global,count=5 这个限流注解，就会对全局进行限流，时间窗口内只能是5次。在redis中，设计的key只是前缀，后面还有两个redis健，一个是value，string类型，代表当前剩余令牌数，另一个是permits是sorted set类型，代表历史消费记录，set中每个元素有两部分组成，一个是member 由uuid+请求的令牌数生成的请求唯一标识，另一个是score分数，代表请求顺序（即请求时间戳，时间是有顺序的）。

具体设计可以看 lua\_数据结构.md

<br />

然后是lua脚本设计还有SHA1摘要，还有滑动窗口设计。

<br />

lua脚本设计：lua脚本由本地写好之后，第一次加载到数据库中，数据库会生成此脚本的SHA1摘要，这样后续再进行这个lua脚本的调用，不必多次传输lua脚本，传输sha1摘要，redis就能从自己的缓存中找到对应的lua脚本。

而调用lua脚本执行限流机制时，需要传递六个参数，第一个是keys限流key，剩下五个参数是 申请令牌数 当前毫秒时间戳，窗口大小，最大令牌数，请求唯一id。在redis内部，由限流key做前缀会维护两个健，即value和sorted set；脚本执行时，先从value中读取出当前剩余令牌数，如果不存在就初始化为最大令牌数，然后通过当前时间戳和窗口大小和zrangebyscore找出当前set中已经过期的请求，清除出去，把释放的令牌数加到value里面，但是不能超过最大，最后判断剩余令牌数够不够当前消耗（一般一个请求用一个令牌），如果不够就通知切面拒绝请求，足够就通过zadd更新set还有更新value。最后要给两个key设置过期时间，防止长时间请求不调用占用redis内存。窗口的大小设置的是1s，默认值。

<br />

> 我做的是一个声明式分布式限流组件。业务 Controller 只需要标注 `@RateLimit`，比如简历上传接口同时标注 GLOBAL 和 IP 两条规则。这个注解是方法级注解，运行时保留，并且通过 `@Repeatable` 支持多条规则。
>
> 真正执行限流的是 `RateLimitAspect`。它用 `@Around` 拦截带注解的方法，通过 `method.getAnnotationsByType(RateLimit.class)` 拿到所有规则，然后逐条生成 Redis Key。Key 里用了 Redis Cluster Hash Tag，例如 `ratelimit:{ResumeController:uploadAndAnalyze}:ip:1.2.3.4`，保证同一方法的多个限流 Key 能落到同一个 slot，方便 Lua 原子执行。
>
> 算法层面使用 Redis Lua 脚本实现滑动时间窗口。脚本内部用 String 保存当前可用令牌数，用 Sorted Set 保存窗口内请求记录；每次请求先回收过期记录，再判断令牌是否足够，足够就扣减并写入本次请求，不足就返回 0。切面拿到结果后，所有规则都通过才执行原方法，任一规则不通过就优先调用 fallback，没配置 fallback 就抛 `RateLimitExceededException`，由全局异常处理器返回统一错误码 8001。

<br />

现在主要用的几个限流请求有 简历上传（涉及到内容解析），简历重新分析，创建面试会话，提交面试答案，知识库查询与流式查询，知识库上传与重新向量化，jd解析。如果有多维规则的话，就是and关系，先满足全局限流还要满足ip限流等。

<br />

如果请求被拒绝，可以走降级方法，比如降级操作可以先返回缓存，或者返回提示让稍后再来。读接口可以降级返回缓存，写接口我更倾向于直接拒绝，避免用户误以为操作成功。

<br />

如果redis挂了，redis重启导致的sha1摘要丢失，可以重新上传一次。如果是redis宕机了连不上了，一是可以考虑用分布式多节点，二是高风险接口就返回异常，低分析的普通读接口可以接一个本地限流，或者直接放行。

<br />

<br />

**高成本接口建议 fail-closed**：比如简历上传、AI 评分、知识库问答、Provider 连通性测试。Redis 不可用时直接返回“系统繁忙，请稍后再试”，保护数据库、LLM、文件解析这些更贵的资源。

- **低风险读接口可以 fail-open**：比如普通配置查询、列表查询。Redis 不可用时放行，优先保证可用性。
- **更好的折中是本地兜底限流**：Redis 异常时临时退化为单机内存限流，比如 Caffeine / ConcurrentHashMap + 时间窗口。它不再是分布式精确限流，但能避免 Redis 挂掉后完全裸奔。
- **设置短超时和告警**：Redisson 连接超时、命令超时不能太长，否则每个请求都卡在限流检查上；同时对 Redis 连接失败、限流降级次数打日志和 Micrometer 指标。
- **1. Redis Sentinel：主从 + 自动故障转移**\
  适合你的限流场景优先考虑。应用只写主节点，读写一致性简单；主 Redis 挂了，Sentinel 自动把从节点提升为主节点。限流数据不会因为应用随机连不同节点而分裂。

  **2. Redis Cluster：分片 + 高可用**\
  适合限流 key 很多、Redis 压力很大时。不同限流 key 分布到不同 slot 上，容量更高。但 Lua 脚本要求访问的 key 必须在同一个 slot。
