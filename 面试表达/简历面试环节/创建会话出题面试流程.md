### 本质

`RBucket` 是 Redisson 对 Redis String 的封装，序列化方式取决于 Redisson 配置（默认用 Kryo 或 Jackson 把整个 `VoiceInterviewSessionEntity` 对象序列化成字节数组存进 Redis）。Key 格式固定为 `voice:interview:session:` + 数据库自增主键，比如 `voice:interview:session:42`。TTL 1 小时，过期自动删除。

<br />

前端如果想开启面试，就点击开始面试按钮，controller接收到这个session请求，会创建一个会话，在这个创建会话方法上，有限流标识，全局限流和ip限流都有，切面限流会与redis交互，调用lua脚本，判断滑动窗口有没有到达限流上限，所有客户端合计每秒与同一个ip每秒都不能超过5次。之后会把前端传递过来的CreateInterviewRequest请求反序列化成record对象（因为前端传的是json格式，请求对象中如果有简历文本与简历id的话，就代表药依赖简历面试，会通过get请求和简历id去数据库中查找tika解析出的简历文本放到request中，发送给后端；也包含指定的llm提供商，之后创建会话时拿到指定的llm信息之后调用llm注册中心获取这个llm），之后调用面试会话服务InterviewSessionService创建会话，需要先通过缓存在redis中的会话信息，看有没有之前已经创建但是还没有完成的会话。app/src/main/java/interview/guide/infrastructure/redis/analysis/面试会话缓存分析.md这里讲了简历id和会话的缓存，即缓存了会话信息，也缓存了会话与简历id之间的映射。如果缓存中没有就再数据库中也找一下。如果还没有就创建新的会话（查找都依赖简历id，如果前端发起会话时指定了简历的话，既可以传简历面试也可以不传简历面试，但是skillid是必须的，即面试方向，比如后端开发）。

创建新的会话通过uuid生成16位的会话id，同时从request中拿到面试方向（即skillid）与面试难度，还可以通过简历id+面试方向从数据库中查询历史问题；之后就调用questionService服务，传入指定的llm提供商，简历文本，问题数量，面试方向和难度等信息，创建面试会话，返回拿到面试问题的list的集合。在questionService内部，generateQuestionBySkill方法会先判断有没有简历文本，如果有简历文本的话就根据生成60%的简历题，剩下的出方向题，比如java后端。然后用completableFuture，并行调用更深的generateResumeQuestions和genetateDirectionQuestions方法生成问题。然后用future.join让二者同时生成完成后，再合并到一起形成总问题的list集合，返回给前端。

<br />

在generateQuestions内部，通过指定的llm信息，难度，题目数量，等信息拼成Map格式的变量集合，再把集合拼成到用户提示词中，然后同时从获取到系统提示词（系统提示词主要包含：标准用于 你现在是一个面试官，根据下面的提示词出题，然后还有格式转换器输出的题目对象要求的格式，这样llm会出json格式的题目，服务端拿到之后方便转换成对象）。之后就可以调用结构化输出器传入llmchatclient客户端，还有用户提示词，系统提示词，结构化输出器以及出错时的错误码，在结构化输出器内部invoke方法就会调用llm生成问题。

<br />

completableFuture将两个生成问题的任务提交给questionExector线程中，主线程**通过join阻塞**等待问题生成完成。questionExecutor通过newVirtualThreadPerTaskExecutor方法创建一个虚拟线程池，这个服务bean销毁时，通过predestory注解销毁线程池。用虚拟线程池是因为出题任务本质是io密集型操作，调用llm后大部分时间都是在等网络返回，几乎不消耗cpu，虚拟线程在io阻塞等待网络响应时，会自动让出底层carrier线程，让其他虚拟线程继续运行。所以用极少量的系统资源（一个 carrier 线程可承载大量虚拟线程）就能支持高并发 LLM 调用。相比之下，传统线程池需要预设 corePoolSize/maxPoolSize，设置小了并发不够、大了浪费内存，而虚拟线程按需创建、用完即弃，不用操心线程数和队列大小，正好匹配这种"短暂阻塞、大量并发"的场景。

<br />

虚拟线程和传统线程池完全不同，`newVirtualThreadPerTaskExecutor()` **没有这些概念**：

| 传统线程池 (ThreadPoolExecutor)       | 虚拟线程 (newVirtualThreadPerTaskExecutor) |
| :------------------------------- | :------------------------------------- |
| corePoolSize / maxPoolSize 限制线程数 | **无限制**，每个任务创建一个虚拟线程，按需增减              |
| BlockingQueue 任务排队等待             | **无队列**，每个任务立即获得一个虚拟线程执行               |
| RejectedExecutionHandler 拒绝策略    | **无拒绝**，因为不限制数量，永远不会拒绝                 |
| 线程复用，池化                          | **不复用**，用完即弃（但创建成本极低，约几 KB 内存）         |

底层 carrier 线程由 JVM 内置的 `ForkJoinPool` 管理，默认 carrier 数量 = CPU 核数，但这对你透明。虚拟线程在遇到 IO 阻塞（如 LLM 网络调用）时会自动让出 carrier，其他虚拟线程可以复用同一个 carrier，所以几百甚至上万虚拟线程同时跑也没问题。

<br />

<br />

Controller 层依赖三个服务： InterviewSessionService （会话生命周期）、 InterviewHistoryService （历史详情和 PDF 导出）、 InterviewPersistenceService （数据库直接查询，如 SessionListItemDTO 列表，包含会话 ID、面试主题、难度级别、简历 ID、问题总数、状态等字段）。前端发起创建面试的请求为 POST /api/interview/sessions ，方法上叠加了两个 @RateLimit 注解—— GLOBAL 和 IP 维度各 count = 5 。 RateLimitAspect 切面拦截方法后，对每个维度依次执行 Redis Lua 脚本（ rate\_limit\_single.lua ），以 ratelimit:{ClassName:MethodName}:{dimension} 为 Key 做滑动窗口计数，任一维度超限即抛出 RateLimitExceededException ，全局返回 HTTP 200 + 对应错误码和提示信息。

限流通过后，Controller 接收 JSON 请求体，Spring 自动反序列化为 CreateInterviewRequest record 对象，字段包括 resumeText （可选简历文本）、 resumeId （可选简历 ID）、 questionCount （3-20 题，含 @Min/@Max 校验）、 skillId （必填，如 java-backend/frontend/custom）、 difficulty （junior/mid/senior，可选默认 mid）、 llmProvider （可选 LLM 提供商标识）、 forceCreate （是否强制新建忽略已有未完成会话）、 customCategories （JD 解析后的自定义分类列表）、 jdText （JD 原文）。Controller 调用 sessionService.createSession(request) 正式进入业务逻辑。

createSession 方法首先判断是否有 resumeId 且 forceCreate 不为 true——若满足条件，调用 findUnfinishedSession(resumeId) 查找未完成会话。该方法先在 Redis 中通过 sessionCache.findUnfinishedSessionId(resumeId) 查询简历 ID 与 sessionId 的映射索引（Redis 缓存了两层结构： CachedSession 本身存储会话完整数据，以及 resumeId → sessionId 的索引映射用于快速反查）；若 Redis 未命中，再通过 persistenceService.findUnfinishedSession(resumeId) 查询 interview\_sessions 表中状态为 CREATED 或 IN\_PROGRESS 的最近会话，找到后通过 restoreSessionFromEntity 将数据库实体中的 questionsJson 反序列化、构造 CachedSession 写回 Redis 缓存并刷新 TTL，然后转换为 InterviewSessionDTO 直接返回，前端即可恢复上次未答完的面试。如果没找到未完成会话或 forceCreate 为 true，则进入新建流程。

新建会话先用 UUID.randomUUID().toString().replace("-", "").substring(0, 16) 生成 16 位无连字符的 sessionId，然后从 request 取 skillId 和 difficulty （空时使用 InterviewDefaults 默认值）。接着调用 persistenceService.getHistoricalQuestions(skillId, resumeId) 从数据库查询历史上已考过的问题——有 resumeId 时按 resumeId + skillId 精确匹配最近 10 个会话，无简历时按 skillId 通用匹配；查询结果解析每个会话的 questionsJson ，提取所有非追问主问题的题目文本、类型和 topicSummary ，通过 LinkedHashSet 按题目文本去重后限制最多 100 条，拼成按类型分组的 Prompt 片段（如 "已考过的知识点：GENERAL: 题目1, 题目2..."），用于告诉 LLM 避免重复出题。随后调用核心出题方法 questionService.generateQuestionsBySkill(llmProvider, skillId, difficulty, resumeText, questionCount, historicalQuestions, customCategories, jdText) 。

generateQuestionsBySkill 方法内部，首先调用 skillService.getSkill(skillId) 获取 Skill 定义实体（包含技能名称、描述、分类列表、Persona 等元数据），或当 skillId 为 custom 且传入了 customCategories 时通过 buildCustomSkill 动态构造 Skill。然后调用 resolveDifficulty 将 difficulty 键映射为 Prompt 用的中文描述（"校招/0-1年经验" / "1-3年经验" / "3年+经验"）。接着通过 llmProviderRegistry.getPlainChatClient(llmProvider) 获取纯净 ChatClient（不含 SkillsTool 和对话记忆 Advisor，因为出题需要结构化 JSON 输出，避免工具调用干扰）。之后调用 buildHistoricalSection 将历史问题按类型分组、去重后拼接为 Prompt 片段。

接下来根据是否有简历文本 ( resumeText 非空) 分流： 无简历时 直接调用 generateDirectionOnly ，该方法调用 skillService.calculateAllocation 根据 Skill 的分类列表和题目总数计算每个分类的配额分配（如 Java 后端：Java 基础 3 题、Spring 2 题、数据库 2 题...），再调用 buildAllocationDescription 将配额渲染为 Markdown 表格，同时通过 buildReferenceSection 从 Skill 定义中获取参考内容，通过 buildJdSection 处理 JD 文本（经 PromptSanitizer 清洗后包裹安全分隔符）。然后将 questionCount 、 followUpCount 、 difficultyDesc 、 skillName 、 skillDescription 、 allocationTable 、 historicalSection 、 referenceSection 、 jdSection 等变量注入 skillUserPromptTemplate 渲染为用户提示词，系统提示词则由 skillSystemPromptTemplate 渲染后追加 GENERIC\_MODE\_SYSTEM\_APPEND （声明无简历、禁止出现"你在简历中提到"等表述）、 buildSkillPersonaSection （注入 Skill 的角色设定）、 outputConverter.getFormat() （JSON Schema 格式指令）三段拼接而成。 有简历时 则进入并行出题模式：简历题数量 resumeCount = max(1, round(questionCount × 0.6)) ，方向题数量 directionCount = questionCount - resumeCount 。用 CompletableFuture.supplyAsync 提交两个任务到 questionExecutor 虚拟线程池：一个调用 generateResumeQuestions ，使用 resumeUserPromptTemplate 和 resumeSystemPromptTemplate 模板，注入简历文本、技能描述、难度等变量，生成与候选人经历相关的题目；另一个调用 generateDirectionOnly 生成标准方向题。主线程通过 resumeFuture.join() 和 directionFuture.join() 阻塞等待两个 CompletableFuture 完成。

各自的生成方法内部最终都调用 structuredOutputInvoker.invoke(chatClient, systemPrompt, userPrompt, outputConverter, errorCode, errorPrefix, logContext, log) 与 LLM 交互。 StructuredOutputInvoker 的 invoke 方法首先在系统提示词末尾追加严格的 JSON 输出指令（禁止输出 Markdown 代码块、解释文字、注释等），然后通过 ChatClient.prompt().system().user().call().entity() 链式调用 LLM，返回的 JSON 字符串由 BeanOutputConverter<QuestionListDTO> 反序列化为 QuestionListDTO （内部包含 List<QuestionDTO> ，每个 QuestionDTO 含 question 、 type 、 category 、 topicSummary 、 followUps 字段）。若 LLM 返回的 JSON 解析失败， StructuredOutputInvoker 会自动进行本地 JSON 修复（修复未转义引号、截断尾部非法字符等），然后按配置重试（默认最多 3 次），重试时可选追加更严格的 JSON 指令或将上次错误信息注入 Prompt 帮助 LLM 纠正。全部重试失败后抛出 BusinessException(INTERVIEW\_QUESTION\_GENERATION\_FAILED) 。

LLM 返回的 QuestionListDTO 通过 convertToQuestions 转换：遍历每个 QuestionDTO ，过滤空题目，生成主问题 InterviewQuestionDTO （包含递增索引、题目文本、类型转大写、分类、topicSummary、 isFollowUp=false ），然后将其 followUps 列表经 sanitizeFollowUps 清洗（过滤空项、trim、截断至 followUpCount ）后逐个生成追问题（ isFollowUp=true ， parentQuestionIndex 指向主问题索引，分类标注为"原分类（追问1/2/3）"）。转换后的题目列表经 capToMainCount 截断——若 LLM 多生了主问题，保留前 N 个主问题及其紧随的追问，截断后续超配额题目。如果 LLM 返回空主问题或调用过程抛异常， generateDirectionOnly 会降级到 generateFallbackQuestions ：优先用 Skill 的分类循环生成通用问答题（"请谈谈你在 XX 方向的技术理解和实践经验"），末位再追加默认追问（"请结合真实场景展开说明" → "线上异常如何定位修复"）；无分类时使用内置的 6 道通用综合题兜底。

两个 CompletableFuture 完成后进入结果处理：若简历题 join 抛出 CompletionException （生成失败），取消方向题 future，降级为全方向题重新生成；若方向题 join 失败，检查简历题是否为空，空则全降级为兜底题，非空则直接返回简历题。两路成功则调用 mergeQuestionBatches 合并：将方向题的 questionIndex 和 parentQuestionIndex 整体加上简历题列表长度的 offset，然后拼接为一个总列表。最终返回合并后的 List<InterviewQuestionDTO> 。

回到 createSession ，拿到题目列表后 先写 Redis ：调用 sessionCache.saveSession(sessionId, resumeText, resumeId, questions, 0, CREATED) 将完整会话缓存到 Redis，包含 JSON 序列化后的问题列表（每个题目含默认空答案字段），并建立 resumeId → sessionId 的索引映射。然后 再写数据库 （try-catch 包住，失败只打 warn 日志不影响返回）： persistenceService.saveSession 在 @Transactional 中创建 InterviewSessionEntity ，设置 sessionId、totalQuestions、currentQuestionIndex=0、status=CREATED、questionsJson（将题目列表序列化为 JSON TEXT 存入）、llmProvider、skillId、difficulty，若有 resumeId 则通过 ResumeRepository.findById 关联简历实体。最终返回 InterviewSessionDTO （包含 sessionId、resumeText、totalQuestions、currentIndex=0、questions 列表、status=CREATED），前端拿到后进入答题界面展示第一题。

关于虚拟线程池： questionExecutor = Executors.newVirtualThreadPerTaskExecutor() 在构造器中创建，它是一个为每个提交的任务创建新虚拟线程的执行器。采用虚拟线程的核心原因在于，出题任务本质是 I/O 密集型操作——调用 LLM 后绝大部分时间都在等待网络响应，几乎不消耗 CPU 时间。虚拟线程在 I/O 阻塞等待网络返回时会自动让出底层 Carrier 线程（平台线程），允许其他虚拟线程继续运行，因此用极少量的系统资源（一个 Carrier 线程可承载数万个虚拟线程）就能支持高并发的 LLM 调用。相比之下，传统 ThreadPoolExecutor 需要预设 corePoolSize 和 maxPoolSize 以及队列大小，设置小了并发不够、大了浪费内存，而虚拟线程按需创建、用完即弃、零配置，正好契合"短期阻塞、大量并发"的 LLM 调用场景。 @PreDestroy 注解的 destroy() 方法在 Spring 销毁 Bean 时调用 questionExecutor.shutdownNow() 停止尚未结束的并行出题任务，防止内存泄漏。
