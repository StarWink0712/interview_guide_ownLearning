# 结构化输出、并发与会话持久化

## 1. StructuredOutputInvoker 如何调用 LLM 生成题目？

**回答：** 各出题方法最终调用 `structuredOutputInvoker.invoke(chatClient, systemPrompt, userPrompt, outputConverter, errorCode, errorPrefix, logContext, log)`。它先在系统 Prompt 末尾追加严格 JSON 指令，再通过 `ChatClient.prompt().system().user().call().entity()` 调用模型，由 `BeanOutputConverter<QuestionListDTO>` 把结果转换成题目 DTO。

## 2. 为什么还要额外强调禁止 Markdown 和解释文字？

**回答：** 即使提供了 JSON Schema，模型仍可能返回 Markdown 代码块、注释或解释文字，导致服务端反序列化失败。因此结构化输出器明确要求只能输出 JSON，禁止代码围栏、前后说明和注释，减少非业务文本污染结果。

## 3. LLM 返回的 JSON 不合法时如何处理？

**回答：** 解析失败后，结构化输出器先尝试本地修复，例如修复未转义引号、清理尾部非法字符等；仍失败则按配置重新调用模型，默认最多重试 3 次。重试时可以追加更严格的 JSON 指令，或把上一次错误信息注入 Prompt，帮助模型纠正格式。

## 4. 结构化出题全部重试失败后怎么办？

**回答：** 全部重试失败会抛出 `BusinessException(INTERVIEW_QUESTION_GENERATION_FAILED)`。方向题生成方法还提供业务降级逻辑：如果模型返回空主问题或生成异常，可以调用 `generateFallbackQuestions()` 返回本地兜底题，尽量保证会话仍然能够创建。

## 5. 本地兜底题是怎么生成的？

**回答：** 有 Skill 分类时，系统按分类循环生成“请谈谈你在 XX 方向的技术理解和实践经验”这类通用题，并追加“请结合真实场景展开说明”“线上异常如何定位修复”等默认追问；没有分类时使用内置的 6 道综合题兜底。

## 6. 简历题生成失败时如何降级？

**回答：** 如果 `resumeFuture.join()` 抛出 `CompletionException`，系统取消仍在执行的方向题 Future，然后重新走一次全方向出题。这样不会因为简历 Prompt 或模型调用失败而完全阻断会话创建，只是暂时失去简历个性化题目。失败的话可以改成重新调用llm，全部生成方向题。

## 7. 方向题生成失败时如何处理？

**回答：** 系统检查已经生成的简历题：如果简历题也为空，就整体降级为本地兜底题；如果简历题非空，则直接返回已有简历题。它优先保留可用结果，避免另一条并行分支失败导致全部结果丢失。

## 8. 两路题目成功后如何合并索引？

**回答：** `mergeQuestionBatches()` 先保留简历题列表，再把方向题追加到后面。追加前，将所有方向题的 `questionIndex` 和 `parentQuestionIndex` 整体加上简历题列表长度作为 offset，避免两批题目的索引和追问父索引发生冲突。

## 9. questionExecutor 为什么使用虚拟线程？

**回答：** LLM 出题是典型 I/O 密集任务，绝大部分时间在等待网络响应，CPU 消耗很低。`Executors.newVirtualThreadPerTaskExecutor()` 为每个任务创建轻量虚拟线程，I/O 阻塞时自动让出底层 Carrier 线程，使少量平台线程可以承载大量并发模型请求，非常适合简历题和方向题并行生成。

 

因为要同步生成方向题和简历题，要用completableFuture阻塞等待生成完成，而调用llm是io密集型操作，需要等待llm返回，所以可以用轻量虚拟线程，io阻塞时自动让出底层Carrier线程，使少量的平台线程可以承载大量的并发模型请求。

## 10. 虚拟线程执行器与传统线程池有什么区别？

**回答：** 虚拟线程执行器没有 `corePoolSize`、`maxPoolSize`、阻塞队列和拒绝策略，每个任务按需创建一个虚拟线程，用完即弃，创建成本只有几 KB。底层 Carrier 由 JVM 的 ForkJoinPool 管理，默认数量与 CPU 核数相关；传统线程池则需要手动权衡线程数、队列长度、并发能力和内存占用。

## 11. questionExecutor 如何在应用关闭时释放？

**回答：** Bean 销毁时，`@PreDestroy` 标记的 `destroy()` 调用 `questionExecutor.shutdownNow()`，停止尚未结束的并行出题任务，避免应用关闭后仍残留虚拟线程任务或相关资源。

虚拟线程池可以通过设置predestory注解，在bean消耗前，调用线程池的shutdownnow方法关闭现在正在执行的全部任务。这里要知道shutdown和shutdownnow的区别.带now的会直接清除等待队列中的任务，不再执行，正在执行的也会停止。而不带now的会运行正在执行的跑完，并且队列中的也会等待执行。核心就是不带now的已经提交的都可以处理，带now的是立刻停止，提交的正在执行的也要全都停下。

## 12. 新会话生成题目后为什么先写 Redis？

**回答：** `sessionCache.saveSession()` 先把 sessionId、简历信息、完整题目列表、当前索引 0 和 CREATED 状态写入 Redis，并建立 `resumeId → sessionId` 映射。前端答题主链路依赖缓存读取和更新，先写 Redis 可以确保题目生成后会话立即可用。

生成题目后先写到缓存中再写数据库中，因为前端查询可以先查缓存及时给前端，存数据库不着急。

<br />

## 13. 会话数据库中保存哪些字段？

**回答：** `persistenceService.saveSession()` 在事务中创建 `InterviewSessionEntity`，保存 sessionId、总题数、当前题号 0、CREATED 状态、序列化为 JSON TEXT 的 `questionsJson`、llmProvider、skillId 和 difficulty；有 resumeId 时再通过 `ResumeRepository` 关联简历实体。

<br />

会话数据库中要保存的有，总题目数，会话id，当前题号还有创建会话请求时的llmprovider，问题json模版等信息。

## 14. 数据库保存会话失败为什么只记录 warn？

**回答：** 当前设计把 Redis 作为实时面试的主工作状态，题目已经成功写入缓存后，数据库持久化放在 try-catch 中，失败只记录 warn，不影响已有会话返回。这样数据库短暂异常不会让用户丢失已经生成的题目，但也意味着后续需要通过监控或补偿关注缓存与数据库的一致性。

数据库保存失败的话只记录一下warn不抛出异常，先让前端完成面试，后续可以通过补偿事务进行补偿。

## 15. 创建会话最终返回哪些信息？

**回答：** 最终返回 `InterviewSessionDTO`，包含 sessionId、resumeText、totalQuestions、currentIndex=0、完整问题列表和 status=CREATED。前端收到后进入答题页面，并从第一道题开始展示。会返回完整问题列表，从第一题开始显示。
