# 会话创建与未完成会话恢复

## 1. 面试 Controller 为什么依赖三个不同的 Service？

**回答：** `InterviewSessionService` 负责创建、恢复、答题等会话生命周期；`InterviewHistoryService` 负责历史详情和 PDF 导出；`InterviewPersistenceService` 负责直接查询数据库，例如返回 `SessionListItemDTO` 列表，其中包含会话 ID、面试主题、难度、简历 ID、问题总数和状态等。这样 Controller 只做路由和委托，不承载业务逻辑。

## 2. 创建面试会话接口如何限流？

**回答：** 前端调用 `POST /api/interview/sessions`，方法上同时声明 GLOBAL 和 IP 两个 `@RateLimit`，各自每秒最多 5 次。`RateLimitAspect` 对每个维度执行 Redis Lua 滑动窗口脚本，Key 形如 `ratelimit:{ClassName:MethodName}:{dimension}`；任意维度超限就抛出 `RateLimitExceededException`，最终由全局异常处理返回 HTTP 200 和业务错误码。

<br />

接口限流用aspect横切面外加lua脚本进行限流，限流用滑动窗口算法，也可以用更高级的算法，比如换成令牌桶算法，令牌桶算法的优点是可以避免两个窗口的边界处流量蜂刺，同时可以运行一定的突发流量；也可以采用漏桶算法，这样可以严格平滑请求流量，但是不支持突发流量不友好。

## 3. CreateInterviewRequest 包含哪些字段？

**回答：** 请求被反序列化为 record，包含可选的 `resumeText`、`resumeId`，范围为 3 到 20 的 `questionCount`，必填的 `skillId`，可选且默认 mid 的 `difficulty`，可选 `llmProvider`，是否忽略已有会话的 `forceCreate`，以及由 JD 解析得到的 `customCategories` 和原始 `jdText`。

<br />

创建面试请求主要需要的字段有简历文本内容，即依靠简历创建面试会话，然后简历id，问题数量，出题模版skillid以及困难程度等信息。

## 4. 创建面试时简历和 skillId 分别是不是必填？

**回答：** 简历是可选的，用户既可以进行基于简历的个性化面试，也可以只按方向面试；传入简历 ID 时，会使用对应的 Tika 解析文本生成简历题。`skillId` 是必填的，用来指定面试方向，例如 `java-backend`、`frontend` 或 `custom`。

简历不是必填的，如果有简历的话前端可以选择用这个简历然后服务端去数据库中拿到简历文本之后填充到提示词中给llm，但是skill是必填的，比如面试java开发后端。

## 5. 为什么创建新会话前要先查未完成会话？

**回答：** 同一份简历可能已经有状态为 CREATED 或 IN\_PROGRESS 的面试。如果每次点击开始都重新调用 LLM 生成题目，会重复消耗模型资源，也无法继续上次进度。因此有 `resumeId` 且 `forceCreate` 不为 true 时，系统先查找最近的未完成会话，找到后直接恢复返回。 

也不是一定要创建新会话前先查未完成会话，未完成的直接取消也可以。

## 6. Redis 中为什么同时缓存会话本身和 resumeId 到 sessionId 的映射？

**回答：** `CachedSession` 保存问题列表、当前题号、状态、简历信息等完整会话数据，适合通过 sessionId 直接读取；另一层 `resumeId → sessionId` 索引用于创建请求根据简历快速反查未完成会话。没有这层索引，就需要扫描所有缓存或每次查询数据库。

## 7. Redis 没找到未完成会话时怎么恢复？

**回答：** `findUnfinishedSession(resumeId)` 在缓存未命中后查询 `interview_sessions`，寻找状态为 CREATED 或 IN\_PROGRESS 的最近会话。找到后，`restoreSessionFromEntity` 反序列化实体的 `questionsJson`，构造 `CachedSession` 重新写入 Redis 并刷新 TTL，再转成 `InterviewSessionDTO` 返回前端。

## 8. forceCreate 字段有什么作用？

**回答：** 默认情况下，有相同简历的未完成会话就直接复用。当前端明确设置 `forceCreate=true` 时，系统跳过 Redis 和数据库的未完成会话恢复流程，继续生成新的 sessionId 和新题目，适用于用户确实想重新开始一场面试的场景。

## 9. 新会话的 sessionId 和默认参数怎么生成？

**回答：** sessionId 使用 `UUID.randomUUID().toString().replace("-", "").substring(0, 16)` 生成 16 位无连字符字符串。`skillId` 和 `difficulty` 从请求读取，空值使用 `InterviewDefaults` 中的默认配置；随后再根据简历、方向、难度、题量、Provider 和历史题目调用出题服务。

## 10. 系统如何查询历史上已经考过的问题？

**回答：** `getHistoricalQuestions(skillId, resumeId)` 从数据库读取历史会话。有 resumeId 时按 `resumeId + skillId` 精确匹配最近 10 个会话，没有简历时按 skillId 通用匹配；然后解析各会话的 `questionsJson`，提取非追问的主问题文本、类型和 `topicSummary`。

## 11. 历史问题如何用于避免 LLM 重复出题？

**回答：** 查询到的主问题使用 `LinkedHashSet` 按题目文本去重，最多保留 100 条，再按类型分组拼成“已考过的知识点：GENERAL: 题目1、题目2……”这样的 Prompt 片段。生成新题时把它传给 LLM，明确要求避开已经考过的问题和知识点。
