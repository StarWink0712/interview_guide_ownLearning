你的理解基本正确，但有两个细节需要修正：

1. `structured-max-attempts=2` 表示**总共调用两次**，即首次调用加一次重试，不是重试两次。
2. Provider 网络重试发生在每一次 `ChatClient.call()` 内部，所以它嵌套在结构化输出重试里面。

准确流程是：

```
消费一条异步消息
  ↓
结构化尝试 1
  ↓
调用 ChatClient
  └─ 网络临时异常时，Provider RetryTemplate 内部重试
  ↓
成功获得 LLM 响应
  ↓
解析 JSON
  ├─ 成功 → 保存结果，任务完成
  └─ 失败 → 先尝试本地修复 JSON
              ↓ 仍失败
结构化尝试 2：追加“请只返回合法 JSON”的提示词，再调用 LLM
  └─ 这次调用也拥有自己的 Provider 网络重试
  ↓
两次结构化尝试都失败
  ↓
抛出 BusinessException
  ↓
Redis Stream 消费者捕获异常
  ↓
重新生成消息，retryCount + 1
  ↓
整个异步任务从头执行
```

Provider 重试也不是所有错误都重试，目前主要针对：

- `TransientAiException`
- `ResourceAccessException`
- 网络超时、连接失败、可恢复的服务端异常

参数错误、认证失败等永久性错误，原则上不应该进行 Provider 重试。

还有一个项目实现上的细节：`StructuredOutputInvoker` 当前捕获的是 `Exception`，所以 Provider 网络重试耗尽后，网络异常也可能被当作一次“结构化尝试失败”，进而再执行第二次结构化调用。两次都失败后才会传播到消息消费者。

因此面试中可以总结为：

> 项目采用三层嵌套重试。每次 LLM 调用内部通过 Provider RetryTemplate 处理网络瞬时故障；成功拿到响应但 JSON 解析失败时，通过修复 Prompt 再进行一次结构化输出调用；当内部重试全部耗尽，异常传播到 Redis Stream 消费者，由消息重试机制重新执行整个异步任务。消息最多重试三次，仍失败则进入失败或死信状态。


对应的核心代码在 \[AbstractStreamConsumer.java (line 219)]\(/Users/ogawaaya/Desktop/学习/interview\_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/async/AbstractStreamConsumer.java:219)。

第一次失败时不会立刻把任务标记为最终失败，而是：

1. 创建一条新的 Redis Stream 消息。
2. 新消息的 `retryCount` 加一。
3. 将异步任务状态重新设置为 `PENDING`。
4. ACK 当前失败的旧消息。
5. 消费者之后获取新消息，从头执行整个 `processBusiness()`。

项目配置：

```
public static final int MAX_RETRY_COUNT = 3;
```

因此实际最多执行四次：

```
retryCount=0：首次执行
retryCount=1：第一次消息重试
retryCount=2：第二次消息重试
retryCount=3：第三次消息重试
```

当 `retryCount=3` 的消息仍然失败时，就不会再次入队。以面试评估任务为例，会调用 `markDeadLetter()` 将任务标记为死信：\[EvaluateStreamConsumer.java (line 382)]\(/Users/ogawaaya/Desktop/学习/interview\_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/interview/listener/EvaluateStreamConsumer.java:382)。

但消息重试不只由 LLM 失败触发。当前父类捕获的是普通 `Exception`，所以以下异常也会触发整条消息重试：

- LLM 重试耗尽
- JSON 结构化输出重试耗尽
- 数据库查询或保存异常
- 文件解析、向量化异常
- 业务处理中的其他未捕获异常

只有一些特殊情况不会重试：

- `AsyncTaskCancelledException`：标记取消并 ACK。
- 消息格式无法解析：直接 ACK 丢弃。
- 达到消息最大重试次数：进入失败或死信状态。

需要特别注意：\*\*每次消息重试都会从头执行业务逻辑，LLM 的重试次数也会重新计算。\*\*例如第一次消息已经成功调用 LLM，但保存数据库时失败，下一次消息重试可能再次调用 LLM。因此消息业务需要做好幂等控制，避免重复调用、重复写入或重复发送。
