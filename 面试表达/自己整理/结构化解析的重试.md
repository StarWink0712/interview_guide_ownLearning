JSON 解析失败属于**结构化输出重试**，不是底层 Provider 重试，也不是消息重试。

你项目中的执行顺序是：

```text
LLM 返回文本
  ↓
BeanOutputConverter 解析 JSON
  ↓ 失败
尝试本地修复未转义引号
  ↓ 仍失败
修改 Prompt，再调用一次 LLM
  ↓ 仍失败
抛出 BusinessException
  ↓
外层消息消费者重新入队整条任务
```

具体来说：

1. 首先尝试正常解析 JSON。
2. 解析失败后，先在本地修复未转义的引号，不调用 LLM。
3. 本地修复仍失败，才追加“请只返回合法 JSON”等指令，再次调用 LLM。
4. 项目配置的 `structured-max-attempts` 默认为 `2`，即首次调用加一次重试：[application.yml:173](/Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/resources/application.yml:173)
5. 两次都解析失败，抛出 `BusinessException`：[StructuredOutputInvoker.java:88](/Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/common/ai/StructuredOutputInvoker.java:88)
6. 消息消费者捕获该异常后，才触发整条消息重试。

所以三层关系是：

| 失败类型 | 使用的重试 |
|---|---|
| 超时、连接失败、临时服务异常 | Provider 重试 |
| LLM 返回的 JSON 格式错误 | 结构化输出重试 |
| 上述重试耗尽，整项业务失败 | 消息重试 |

不过当前 `StructuredOutputInvoker` 的 `catch (Exception)` 范围较宽，网络异常也可能被当成结构化输出失败再次调用。更严谨的实现应该区分“LLM 请求异常”和“JSON 转换异常”，避免重复策略叠加。

对，你的理解基本正确。项目中存在三层重试机制：

| 层级 | 触发原因 | 重试范围 |
|---|---|---|
| Provider 重试 | 网络超时、连接失败、LLM 服务临时异常 | 只重新发起当前 LLM 请求 |
| 结构化输出重试 | LLM 返回内容无法解析为目标 JSON | 修正 Prompt 后重新调用 LLM |
| 消息重试 | 整个异步任务执行失败 | 将消息重新写入 Redis Stream，整个任务重新执行 |

调用关系是嵌套的：

```text
消息重试
  └─ 结构化输出重试
       └─ Provider 网络调用重试
```

不过有一点需要修正：你项目的 Provider 重试虽然使用了 Spring AI/Spring Retry 的重试能力，但不是简单使用 `spring.ai.retry` 的默认配置。

全局自动重试实际配置成了不重试：

```yaml
spring:
  ai:
    retry:
      max-attempts: 1
```

项目通过 `AiProviderRetryTemplateFactory` 自己创建 `RetryTemplate`，再注入 ChatModel，配置为最多 10 次重试和指数退避。因此面试时可以这样说：

> 项目设计了三层重试。Provider 层通过自定义 RetryTemplate 处理网络和 API 瞬时异常；结构化输出层处理 LLM 返回 JSON 无法解析的问题，会携带修复提示重新请求；异步任务层通过 Redis Stream 处理整个业务任务失败，将消息重新入队。三层职责不同，但会嵌套执行，因此需要控制总重试预算，防止重试次数叠加。

另外，当前 `StructuredOutputInvoker` 捕获的是所有 `Exception`，所以网络重试耗尽后，网络异常还可能触发结构化输出重试，最后再触发消息重试。设计上最好将 JSON 解析异常与网络调用异常分开处理。
