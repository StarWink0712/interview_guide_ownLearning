语音面试通过 WebSocket 建立双向实时链路。前端持续上传麦克风音频，服务端将音频发送给 ASR，并把部分识别结果实时推送为字幕；最终识别片段在内存中合并，用户点击提交后，将完整回答和数据库中的历史对话交给 LLM 生成追问。LLM 文本流式推送的同时，按句并行调用 TTS 并推送音频。本轮问答持久化到 PostgreSQL，Redis只缓存会话元数据；用户结束面试后，再通过 Redis Stream 异步生成最终评估。

但是每轮回答都持久化到sql的话，如果持久化失败可能会导致数据丢失，但是无法中断前端的面试，可以尝试进行短重试，如果还不行就可以先临时存到redis中，当前实时链路采用可用性优先策略，消息持久化失败只记录日志，不会中断用户的语音面试，但这可能造成对话历史和最终评估数据缺失。更完善的方案是对临时数据库异常进行短重试，仍失败时将带唯一 turnId 的对话事件写入 Redis Stream，由消费者幂等落库并进行失败重试，同时在 Redis 中暂存尚未落库的上下文，保证下一轮对话连续性。会话元数据已经采用数据库加 Redis 缓存的双写方式；对话记录没有简单双写，是为了避免 Redis 与数据库的一致性问题。若需要解决数据库临时故障，更适合先写 Redis Stream 作为可靠缓冲，再由消费者幂等落库，而不是把 Redis 缓存和数据库都当作永久数据源。其实没有同步双写是因为redis和sql还要新增补偿，校正机制，因为可能redis成功了但是数据库失败了，但是我感觉这种还是比较好的，因为这样可以避免数据丢失；但是如果redis就失败了

```
| PostgreSQL | Redis | 处理策略 |
|---|---|---|
| 正常 | 正常 | 正常写数据库并使用 Redis |
| 正常 | 失败 | 绕过 Redis，直接写数据库，面试继续 |
| 失败 | 正常 | 写入 Redis Stream 待落库，面试继续 |
| 失败 | 失败 | 暂停推进下一题，保留当前回答并持续重试 |
```
