# 暂停恢复与会话结束

## 1. 语音面试支持哪几种暂停与恢复方式？

**回答：** 系统支持用户主动暂停、定时任务检测空闲后自动暂停，以及用户主动恢复三种路径。主动暂停和恢复通过 REST 接口修改数据库状态；自动暂停由 Handler 根据连接最后活动时间触发，并额外释放 ASR 和 WebSocket 资源。

## 2. 用户主动暂停的完整流程是什么？

**回答：** 前端调用 `PUT /api/voice-interview/sessions/{sessionId}/pause`，reason 默认是 `user_initiated`。`VoiceInterviewService.pauseSession()` 直接通过 `findById` 查询数据库，不走缓存，确保状态最新；只有 `IN_PROGRESS` 会话可以暂停，否则抛异常。校验通过后将状态改为 `PAUSED`、记录 `pausedAt` 并保存数据库，最后删除 Redis 会话缓存。

用户传来暂停请求之后，先查一下数据库这个会话的状态，只有这个会话是在面试中才可以暂停。

## 3. 主动暂停后为什么要删除 Redis 缓存？

**回答：** 暂停前 Redis 中仍然可能缓存着 `IN_PROGRESS` 的会话。如果只更新数据库而不失效缓存，下次查询会直接命中旧状态，造成前端显示与数据库不一致。因此暂停落库后立即调用 `invalidateSessionCache`，迫使后续读取重新从数据库获得 `PAUSED` 状态。肯定要删除啊，腾出缓存的空间，下次再面试时再加载即可，如果不清除的话，下次面试会直接命中缓存中的旧状态，即会直接从缓存中读到会话仍然是正在面试中的状态。

## 4. 用户主动恢复的完整流程是什么？

**回答：** 前端调用 `PUT /api/voice-interview/sessions/{sessionId}/resume`。Service 同样直接查数据库，并只允许 `PAUSED` 状态恢复；随后把状态改为 `IN_PROGRESS`，记录 `resumedAt`，保存后通过 `cacheSession` 重写 Redis 缓存，TTL 为 1 小时。接口返回包含新 `webSocketUrl` 的 `SessionResponseDTO`，前端据此重新建立连接。

前端直接查数据库，然后同步到redis缓存中。

## 5. 恢复连接后为什么不会重新问开场问题？

**回答：** 前端使用恢复接口返回的新 URL 建立 WebSocket 后，`afterConnectionEstablished` 会再次执行。但 `triggerOpeningQuestionIfNeeded` 会先查询数据库中的历史消息，发现该会话已经有开场问题和问答记录后，就判断为重连或恢复场景并直接返回，因此面试从暂停前的位置继续。

进行开场问题前先检查一下数据库中有没有开场问题的记录即可。

## 6. 自动暂停是怎么检测的？

**回答：** Handler 使用 `@Scheduled(fixedRate = 30000)` 每 30 秒执行一次 `checkPauseTimeout()`，遍历 `lastActivityTime`。每次 `handleTextMessage` 收到 audio 或 control 消息都会更新时间戳，所以用户持续说话或操作时计时会不断重置。空闲 4 分 30 秒时先向前端发送 30 秒预警，超过 5 分钟仍无活动则触发超时暂停。

可以搞一个定时任务，每隔一段固定的时间，就去查本地map缓存（当前会话的最后一次收到消息的时间）看最近的消息更新戳是多少，如果超过5分钟就暂时关闭面试。这是三个map的之一，第一个map主要是缓存会话本身，第二个是缓存会话的状态，第三个就是缓存会话的更新时间。

## 7. 超时暂停会执行哪些清理操作？

**回答：** `handlePauseTimeout` 依次向前端发送暂停通知，调用 `pauseSession(sessionId, "timeout")` 将数据库状态改为 `PAUSED`，调用 `sttService.stopTranscription()` 停止 DashScope ASR，关闭前后端 WebSocket，并从 sessions、sessionStates 和 lastActivityTime 三个 Map 中移除该会话。

<br />

回答这种问题不能靠死记硬背，而是要思考，当一个服务关闭时，应该要做的工作有哪些。比如这里肯定是要让前端关闭窗口或者给前端提示，前端再点击提交问题等按钮时要有提示框说面试已经关闭请重新面试。同时数据库中会话的状态也要更新；然后与ASR和TTS的连接也要关闭。

## 8. 主动暂停和超时暂停最大的区别是什么？

**回答：** 主动暂停主要更新数据库状态并删除缓存，可能保留连接，因为用户可能很快恢复；超时暂停意味着用户已经 5 分钟没有活动，因此还会停止 ASR、关闭 WebSocket 并清理运行时 Map，避免长期占用 DashScope 连接和服务器资源。

## 9. 会话结束有哪些触发方式？

**回答：** 主动结束有两条入口：前端调用 `POST /api/voice-interview/sessions/{sessionId}/end`，或者通过 WebSocket 发送 `{"type":"control","action":"end_interview"}`。此外，网络中断或浏览器关闭会触发 `afterConnectionClosed`，其中的 `endSessionIfInProgress` 会兜底结束仍处于 `IN_PROGRESS` 的会话。

## 10. endSession 的核心流程是什么？

**回答：** 方法先查询会话，未找到时静默返回以容忍脏数据。找到后把 `endTime` 设为当前时间、`currentPhase` 和 `status` 设为 `COMPLETED`，使用 `Duration.between(startTime, now)` 计算精确到秒的 `actualDuration`，把 `evaluateStatus` 设为 `PENDING`，然后保存数据库并删除 Redis 缓存。最后向 Redis Stream 投递评估任务并立即返回。

## 11. WebSocket 异常关闭后如何清理资源？

**回答：** Spring 回调 `afterConnectionClosed()` 后，系统先移除三个运行时 Map；如果 `SessionState` 中的 LLM 虚拟线程仍在运行，就调用 `Thread.interrupt()` 中断等待。然后 `sttService.stopTranscription()` 通过 `conversation.endSession()` 通知 DashScope 结束、调用 `conversation.close()` 关闭 ASR WebSocket，并清理 QwenAsrService 内部的会话 Map 和锁。最后执行 `endSessionIfInProgress()` 兜底结束。

## 12. endSessionIfInProgress 如何防止重复结束和重复评估？

**回答：** 它只对数据库中状态仍为 `IN_PROGRESS` 的会话调用结束逻辑。用户正常点击结束后，`endSession` 已经把状态改为 `COMPLETED` 并投递过评估；随后浏览器发送 Close 帧触发 `afterConnectionClosed` 时，兜底方法看到状态不是 `IN_PROGRESS` 就直接返回，不会再次入队。同样，已经 `PAUSED` 的会话也不会被连接关闭流程重复处理。
