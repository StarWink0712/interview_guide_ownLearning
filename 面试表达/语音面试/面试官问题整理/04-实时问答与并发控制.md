# 实时问答与并发控制

## 1. afterConnectionEstablished 执行结束后，系统如何继续处理面试？

**回答：** 当前后端 WebSocket、服务端到 ASR 的 WebSocket都建立完成，欢迎消息和开场问题也发送后，Handler 不再主动运行，而是进入事件驱动等待状态。之后前端发来的音频或控制消息会触发 `handleTextMessage`，ASR、LLM 和 TTS 的结果则由各自的回调继续驱动流程。

<br />

## 2. handleTextMessage 为什么是面试过程的总入口？

**回答：** 前端把音频和控制操作都包装成 WebSocket 文本帧。Spring 每收到一帧就回调 `handleTextMessage(session, message)`。方法从 URI 提取 sessionId，记录消息大小，解析 JSON 的 `type` 字段，并更新 `lastActivityTime`；`audio` 交给 `handleUserAudio`，`control` 反序列化为 `WebSocketControlMessage` 后交给 `handleControl`，未知类型记录 warning 后忽略。

<br />

即无论是音频内容还是控制操作，只要是通过websocket，都要包装成websocket文本帧，spring收到帧后回调处理，提取消息类型，路由对应的处理逻辑。

## 3. 用*户音频是怎么发送给 ASR 的？*

**回答：** 前端采集麦克风 PCM 音频后 Base64 编码，作为 `audio` 类型文本帧发送。`handleUserAudio` 取出 data 字段并 Base64 解码为 PCM 字节数组，检查回声冷却后调用 ASR 的 `sendAudio(pcmData)`。如果发现 DashScope ASR 连接已经断开，系统会自动重连并重试发送一次。

## 4. 为什么 AI 播放语音时要丢弃用户音频？

**回答：** Handler 使用 `aiSpeaking` 标记做回声冷却。当 AI 正在播放 TTS 音频时，扬声器声音可能再次被麦克风采集；如果继续送入 ASR，AI 的问题会被识别成用户回答，形成回声循环。因此 `aiSpeaking=true` 时直接丢弃该段麦克风音频。

## 5. mergeBuffer 在实时问答中解决什么问题？

**回答：** ASR 的服务端 VAD 可能因为用户换气把一段回答切成多个 completed 片段，`mergeBuffer` 会把这些最终结果持续拼接。用户说话时，partial 只用于实时字幕；用户点击提交时，系统再从 `mergeBuffer` 原子地取出完整回答并清空，保证 LLM 收到的是用户这一轮的完整文本。

## 6. control 消息支持哪些操作？

**回答：** `handleControl` 当前支持三种 action：`submit` 取出本轮回答并触发 LLM 和 TTS 管线；`end_interview` 调用 `voiceInterviewService.endSession()` 结束会话并触发异步评估；`start_phase` 调用 `updatePhase()` 更新 `currentPhase`，再向前端发送阶段切换通知。

## *7. 用户点击提交时，为什么要使用 AtomicBoolean 的 CAS 锁？*

**回答：** 用户可能在短时间内重复点击提交，如果多个 LLM + TTS 管线同时运行，会重复消费回答、并发写同一 WebSocket，并打乱问答顺序。系统通过 `AtomicBoolean.compareAndSet()` 获取每个会话的处理锁；拿不到锁时 400ms 后重试，拿到后才取出 `mergeBuffer` 并启动本轮处理，管线结束后释放锁。

<br />

提交后服务端就有了全部的文本了，之后需要调用llm操作，但是不能让多个线程都去做这个功能，要不然就重复了，所以要控制并发，CAS操作拿到并发锁。boolean 原子标记是当前llm与tts管线是否在操作的标识，如果没有操作的话就去用cas获取锁。这里并不是通过监视器锁，而是用一个原子标记处理。

Handler 使用 `ConcurrentHashMap<sessionId, SessionState>` 为每个语音会话保存独立运行时状态，每个 `SessionState` 都有自己的 `AtomicBoolean`。因此 CAS 只串行化同一会话的 LLM 管线，不会阻塞其他会话并行处理。

## 8. 为什么 LLM + TTS 管线要放在虚拟线程中？

**回答：** LLM 请求和 TTS 合成都属于可能持续数秒甚至更久的阻塞 I/O。如果直接在 WebSocket IO 回调线程中执行，会阻塞后续消息处理。系统把 `triggerLlmResponse()` 放到虚拟线程执行，Handler 可以继续接收连接事件，同时虚拟线程负责数据库写入、模型调用、TTS 等完整管线。

<br />

放到虚拟线程中是因为llm与tts是io密集型操作，线程要阻塞等待io回复，所以用虚拟线程可以让底层实际线程去处理其他的io操作。

## 9. LLM 的 Prompt 包含哪些上下文？

**回答：** `DashscopeLlmService` 调用 LLM 时，Prompt 会包含当前面试阶段、难度、技能方向、历史对话记录，以及用户刚刚从 `mergeBuffer` 提交的完整回答，让 AI 面试官结合当前进度自然追问或切换问题，而不是把每轮当成孤立对话。

包含当前面试阶段的信息，技能方向历史上下文，用户提交的回答，还有要求，即让面试官结合这个回答生成下一个问题。

<br />

## 10. LLM 的回复为什么采用流式推送？

**回答：** LLM 生成过程中，每生成一句就调用 `sendTextMessage()` 把字幕推送给前端，用户可以立即看到 AI 面试官正在输出，体验更自然，不需要等完整回答生成。生成完毕后，系统再把完整的 AI 回复保存到数据库，随后进入 TTS 合成。

llm的回复采用流式推送自然是为了让前端可以实时显示字幕，最后再进行tts合成。

<br />

## 11. 一轮用户回答的完整处理流程是什么？

**回答：** 用户说话后，音频经前后端 WebSocket 发给服务端，再转发给 ASR；partial 结果实时展示，final 结果累积进 `mergeBuffer`。用户点击提交后，系统通过 CAS 锁取出并清空完整回答，在虚拟线程中保存用户消息，调用带阶段、难度、技能和历史上下文的 LLM，流式推送并保存 AI 回复，再调用 TTS 得到 PCM、转换成 WAV、Base64 编码后发给前端播放，最后释放锁，等待下一轮回答。

## 12. 用户消息和 AI 消息分别在什么时候落库？

**回答：** 用户点击提交并从 `mergeBuffer` 取出完整回答后，系统先把用户文本保存为 `VoiceInterviewMessageEntity`，再调用 LLM。LLM 完整生成结束后，再把 AI 回复保存到数据库。开场问题也会以 `userText=null、aiReply=开场文本` 的形式单独保存，用于恢复时判断是否已有历史并为后续 LLM 和评估提供完整记录。

<br />

用户点击提交后就直接落库，ai消息是在llm生成完成之后再落库。
