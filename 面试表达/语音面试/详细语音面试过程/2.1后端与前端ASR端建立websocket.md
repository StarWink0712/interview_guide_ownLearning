\*\*监视器锁的具体用法与原理：\*\*QwenAsrService 内部通过一个 `sessionLocks`（ConcurrentHashMap）为每个面试会话维护一个独立的互斥锁对象。`lockForSession` 方法使用 `computeIfAbsent` 以 sessionId 为 Key 惰性获取或创建一个纯 Object 实例并放入 Map，保证同一会话每次拿到的都是同一个锁引用。ASR 的三个生命周期方法——startTranscription、stopTranscription 和 restartTranscription——都使用 `synchronized(lockForSession(sessionId))` 保护，互斥的是 JVM 内置的 `synchronized` 监视器锁而非 Map 本身：多个线程可以同时从 Map 取出同一个锁对象的引用，但只有第一个线程能拿到该对象的 monitor 进入同步块，后续线程会在 synchronized 处阻塞等待。这把锁的核心价值是防止同一会话上出现并发启动导致重复建连接、启动与停止竞速导致新连接被旧操作误关、以及重连过程的 stop + start 被并发打断。stopTranscription 执行完毕后会主动从 sessionLocks 中移除该锁对象，避免随着会话累积导致内存泄漏。不同 sessionId 对应不同 Object 实例，因此不同会话之间不互斥，可以并行执行。这里看ASR服务代码，里面有两个并发map，一个存互斥锁，一个存ASR与服务端的websocket连接。而handler处理器中的三个map是存的前后端的连接

然后是第三步创建一个dashcope websocket的回调处理器，旨在与阿里云的ASR连接后，处理相关的操作。当websocket连接成功时就打印一下日志，收到DashScope服务端（即ASR）推送的json事件时（即将语音转成文本时）触发onevent方法，调用handlerServerEvent方法。此方法会通过case自动处理三种事件类型，判断是识别完成，中间结果，还是报错，然后路由给不同的回调，如果是最**终结果**，就把识别出来的最终结果传递给onFinal.accept(transcript)，然后进入到handler中的handlerSttResult方法内部，先从会话缓存（这个是前后端之间的）中获取会话缓存，然后获取当前会话状态，如果还在连接中，就把识别的文本缓存到mergeBuffer中累积，等用户点了提交按钮提交语音后，再把完整的文本全部给llm并把完整的文本推送给前端（非最终结果不走这一步，直接推送给前端），调用sendSubtitle方法把ASR识别的文本推送给前端，然后再进入到sendSubtitle中,内部构建一个推送给前端的WebsocketSubtitleMessage消息体，然后再调用sendMessage方法传入session和这个消息体，内部再调用session.sendMessage方法（websocket底层方法）把详细给前端。然后回到dashcope的回调处理器处，之后是websocket连接关闭时的触发的函数，会把map缓存中的会话（asr与服务端的）删掉，会检查一下之前保存的原子引用与要删的这个引用是否是同一个，避免删错，因为可能删掉由于旧链接断开又建立的新链接。第三步是设置回调处理器，并不是直接就运行了，因为还要在第四步第五步把引用实例作为会话的一部分缓存到map缓存中。然后就是第六步建立服务端与ASR的连接，启用守护线程建立与ASR的websocket连接：通过connect方法，设置识别语言为中文，采样率为16kHz，音频格式是pcm，然后设置一下会话配置，ASR的输出只需要文本，启用服务端VAD(让ASR自动判断语音起止)等，然后把这些配置设置给ASR DashScope，连接即建立完成；最后把线程设置为守护线程避免JVM退出时不会因为这个线程而阻塞jvm关闭，然后启动线程，等待连接完成。之后如果ASR推送给服务端文本的话，就会自动触发onEvent方法，进入到handler的handlerSttResult方法进行处理，推送给前端。
