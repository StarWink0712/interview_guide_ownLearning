# 语音面试完整流程总结

##

## 一、创建会话

前端点击创建语音会话后，发送 CreateSessionRequest 请求体，包含 roleType（模板 ID，如 java-backend 表示后端开发方向）、difficulty（初级/中级/高级）、resumeId、customJdText（用户粘贴的目标岗位 JD，让 LLM 出题更有针对性），以及四个面试阶段的布尔开关（introEnabled 默认关，techEnabled、projectEnabled、hrEnabled 默认开），还有一个 llmProvider 字段指定用哪个模型，未填则走后端默认 Provider。

后端 Controller 接到请求后调 VoiceInterviewService 的 createSession 方法。方法内先从请求中取出 skillId 和 llmProvider，未传则用常量默认值补齐。然后通过 Builder 构建 VoiceInterviewSessionEntity，填入 userId、roleType、skillId、difficulty、四个阶段开关、plannedDuration 等字段。currentPhase 的初始值不是请求直接传入的，而是按 INTRO → TECH → PROJECT → HR 的顺序找到第一个用户开启的阶段作为面试起点，四个全关才兜底返回 COMPLETED。

实体构建完后先 save 到 PostgreSQL，JPA 的 @PrePersist 回调会自动填充 createdAt、updatedAt、startTime。接着把实体缓存到 Redis，Key 为 voice:interview:session:{id}，TTL 设一小时，这样后续 WebSocket 实时通话过程中读会话信息就不用每次都查库了。最后调 buildSessionResponse 把实体转成 SessionResponseDTO 返回给前端，包含 sessionId、roleType、currentPhase、status、startTime、plannedDuration，以及最重要的 webSocketUrl。这个 URL 由 WebSocketConfig 中注册的端点路径 /ws/voice-interview/{sessionId} 拼接数据库自增主键而成，前端拿到后直接建 WebSocket 长连接，后续所有实时语音通话都走这条连接。

## 二、WebSocket 连接建立与语音链路配置

### 2.1 前后端 WebSocket 及服务端与 ASR 连接

前端拿到 webSocketUrl 后发起 WebSocket upgrade 请求，Spring 框架拦截后匹配到注册的 VoiceInterviewWebSocketHandler，握手成功后执行 afterConnectionEstablished 方法。方法内先从 URI 路径提取 sessionId，设置消息大小限制为 256KB（1 秒 PCM 约 36KB，256KB 覆盖正常 2 秒片段），然后用 ConcurrentWebSocketSessionDecorator 包装原始 WebSocketSession 防并发写入冲突，设置单条消息发送时限 10 秒、发送缓冲区 512KB。接着把会话存入三个 ConcurrentHashMap：sessions（sessionId → 并发安全 WebSocket 连接）、sessionStates（sessionId → SessionState 运行时状态）、lastActivityTime（sessionId → 最后一次收到消息的时间戳，用于超时检测）。

之后依次执行三件事：启动语音识别、发送欢迎消息、触发开场问题。启动语音识别时，服务端需要与 DashScope ASR 也建立一条 WebSocket 连接。调用 QwenAsrService 的 startTranscription 方法，传入 sessionId 和三个回调接口——onFinal 处理 VAD 判定用户停止说话后的最终识别结果，onPartial 处理用户还在说话时的中间识别结果，onError 处理连接或识别异常。在 startTranscription 方法内部，为每个会话创建一个**监视器锁**防止并发启动/停止/重连同一会话的 ASR。然后构建 DashScope 连接参数（模型名、URL、API Key），创建 WebSocket 回调处理器，在 onEvent 回调中通过 handleServerEvent 方法根据 JSON 事件类型分发——识别完成走 onFinal 回调（把文本堆到merge缓存中）、中间结果走 onPartial 回调（把文本实时推送到前端当字幕显示）、错误走 onError 回调。原子引用保存当前连接实例，onClose 时做引用对比防止误关新连接。最后通过 connect 方法建立与 DashScope ASR 的 WebSocket 连接，配置中文识别、16kHz 采样率、PCM 格式、启用服务端 VAD(VAD 就是 DashScope 内置的一个"静默计时器"，持续听到声音就延长计时，听不到声音就倒计时，倒计到 1 秒就判为一句话结束。) 等参数，在守护线程中完成握手。VAD是跑在ASR端的，其实就是通过websocket把语音字节数组给ASR时，ASR会判断是不是一句完整的话，然后告诉服务端（推送一个json事件），服务端触发ONFinal回调，把完整的一句话填充到mergeBuffer中

开场问题触发时，先检查对话历史是否为空（有历史说明是重连恢复场景，不发开场），再从数据库获取会话实体根据 skillId 选择开场问题模板。文本通过 sendTextMessage 推给前端先显示，同时 saveMessage 保存到数据库（userText 为 null 表示系统主动发言），然后调用 TTS 合成开场问题语音——优先从 @PostConstruct 预热的 openingAudioCache 缓存取 WAV，未命中则实时合成，最后 sendAudio 推送给前端播放。

### 2.2 TTS 连接配置

TTS 语音合成使用的是短连接模式。Spring Boot 启动时，QwenTtsService 的构造器从 VoiceInterviewProperties 中读取 model、apiKey、voice、format、sampleRate、mode、speechRate、volume 等配置并赋值给成员变量，@PostConstruct 的 init 方法仅校验 apiKey 不为空，此时并没有与 DashScope 建立任何 WebSocket 连接。

真正的连接在每次调用 synthesize 方法时才临时建立。方法内部分七个阶段：空文本直接返回空数组避免无效连接、构建 QwenTtsRealtimeParam 连接参数（model + apiKey）、创建 WebSocket 事件回调（onOpen 仅打日志、onEvent 处理音频分片和完成事件、onClose 解除阻塞）、建立 WebSocket 并 connect、updateSession 下发音色语速等配置、appendText + commit 触发服务端合成、CountDownLatch.await 同步等待。因为 TTS 需要即时把语音返回给前端，所以用 CountDownLatch 将异步 WebSocket 响应转为同步阻塞等待，设置 30 秒超时保护。在 handleServerEvent 方法内部，根据 TTS 服务端返回的 JSON 事件类型做 case 分发——收到 response.audio.delta 就把 Base64 音频分片解码为 PCM 追加到 ByteArrayContainer 容器中，收到 response.done 就 countDown 解除主线程阻塞，收到 error 也 countDown 防止死等。无论成功、超时还是异常，finally 块中确保关闭 WebSocket 连接。

TTS 用短连接的原因是 commit 模式下客户端一次性发送全部文本并下发配置，服务端合成完成后返回音频分片，之后连接就没有存在的意义了。不像 ASR 需要持续接收音频流，TTS 是来料加工用完就关。

### 2.3 暂停、恢复与结束

语音面试支持三种暂停恢复方式。用户主动暂停时，前端调 PUT /pause，Service 层直接从数据库查会话实体而非走缓存，校验只有 IN\_PROGRESS 状态才能暂停，然后设 status=PAUSED、记录 pausedAt、save 到数据库，关键一步是紧接着 invalidateSessionCache 删除 Redis 缓存——如果不删，缓存里还存着旧状态，下次查询会拿到过时数据。用户主动恢复时，前端调 PUT /resume，校验只有 PAUSED 状态才能恢复，改回 IN\_PROGRESS、记录 resumedAt、save 后重新 cacheSession 写 Redis，返回新的 webSocketUrl 让前端重新建立 WebSocket。重连后 afterConnectionEstablished 重新执行，triggerOpeningQuestionIfNeeded 通过 getHistory 查到有历史消息，判断为重连场景不重复发开场问题。

自动超时检测靠 @Scheduled(fixedRate=30000) 定时任务，每 30 秒遍历 lastActivityTime Map。每次 handleTextMessage 收到前端消息都会更新时间戳。空闲超过 4 分 30 秒发送 pause\_timeout\_warning 预警，超过 5 分钟触发 handlePauseTimeout：发暂停通知给前端 → pauseSession 改数据库状态 → stopTranscription 停止 ASR → session.close 关闭 WebSocket → 从三个 Map 移除会话。

会话结束有两种路径。用户主动结束可通过 HTTP REST（POST /end）或 WebSocket 控制消息（action:end\_interview），最终都调用 endSession 方法：设置 endTime=now、currentPhase=COMPLETED、status=COMPLETED、actualDuration 精确计算到秒、evaluateStatus=PENDING，save 到数据库并清除 Redis 缓存，然后通过 voiceEvaluateStreamProducer.sendEvaluateTask 将 sessionId 通过 Redis Stream XADD 入队到 voice:evaluate:stream，后台消费者异步执行 LLM 评估，endSession 立即返回不等待评估完成。

WebSocket 异常断开时，Spring 框架回调 afterConnectionClosed，分三步清理：从三个 Map 移除会话（若 SessionState 还在跑 LLM 管线则 Thread.interrupt 中断虚拟线程）；stopTranscription 停止 ASR 识别并关闭与 DashScope 的 WebSocket；endSessionIfInProgress 做兜底结束。endSessionIfInProgress 的幂等保护很关键——只有状态是 IN\_PROGRESS 才走结束流程，防止正常结束已改成 COMPLETED 后 WebSocket Close 帧又触发重复评估。

## 三、面试过程中——从用户说话到 AI 回复

afterConnectionEstablished 执行完之后，Handler 进入事件驱动等待状态。用户开口说话后，前端麦克风采集音频、Base64 编码成文本帧通过 WebSocket 发送，Spring 框架回调 handleTextMessage 方法。方法内提取 sessionId、记录消息大小（超过 200KB 打警告日志），解析 JSON 拿到 type 字段做分发。

<br />

在连接建立阶段，afterConnectionEstablished 已调用 QwenAsrService 的 startTranscription 方法，与 DashScope 建立了一条 ASR WebSocket 长连接，并注册了三个回调函数——onFinal（处理 VAD 判定用户停止说话后的最终识别文本）、onPartial（处理用户说话过程中的中间识别文本）、onError（处理识别或连接异常）。此后前端持续推送的每一帧音频，都会被服务端转发到这个长连接上实时识别。

语音推送是持续的——前端每 100ms 左右采集一帧 PCM 音频并通过 Base64 编码包装成 JSON，走前后端之间的 WebSocket 发给服务端。服务端 handleUserAudio 先把 Base64 解码还原成原始 PCM 字节数组，然后调用 ASR 服务的 sendAudio 把音频帧追加到与 DashScope 之间的 ASR WebSocket 长连接上，就像往流里倒水一样持续发送。DashScope 的服务端 VAD 在云端实时分析这段音频流：检测到语音能量时持续转写并推送中间文本，触发 onPartial 回调；检测到连续静默超过配置的 turnDetectionSilenceDurationMs（默认 1000 毫秒）时判定用户这句话结束，将完整的识别文本通过 completed 事件返回，触发 onFinal 回调。整个过程是边说话边识别，不需要等用户说完一整段才开始。

VAD 的断句判断完全由 DashScope 云端执行，不在项目服务端本地运行。在 ASR 连接建立时，服务端通过 updateSession 下发四个 VAD 相关参数给 DashScope——enableTurnDetection 设为 true 启用检测，turnDetectionType 设为 server\_vad 表示使用 DashScope 服务端内置的 VAD 引擎，turnDetectionThreshold 控制语音/非语音判定的灵敏度阈值，turnDetectionSilenceDurationMs 设为 1000 毫秒作为断句的核心依据：DashScope 持续分析音频流中每一帧的语音能量，当检测到连续静默超过 1 秒时，判定用户当前的这句话已经说完了，随即通过 WebSocket 推送一个 type 为 conversation.item.input\_audio\_transcription.completed 的 JSON 事件回服务端。服务端的 handleServerEvent 方法收到这个事件后，提取其中的 transcript 最终识别文本，调用 onFinal 回调，Handler 再将这段文本拼入 mergeBuffer。整个过程服务端不参与断句判断，只负责传递配置参数和响应 DashScope 的识别结果。

如果 type 是 audio（前端推送麦克风音频），调 handleUserAudio 处理。内部先做 AI 回声冷却检查——如果 aiSpeaking 为 true 或距上次 **AI 播放结束不到 800ms**，丢弃当前音频防止扬声器播放的 AI 声音被麦克风拾取形成回声循环。通过检查后 Base64 解码还原 PCM，调 ASR 的 sendAudio 发到 DashScope 识别。若 ASR 连接断了会自动 reStartDashScopeStt 重连并重试（最多 15 次每次 80ms 间隔）。ASR 识别结果通过回调异步返回：中间结果（onPartial）直接 sendSubtitle 推送实时字幕；最终结果（onFinal）调 appendFinalSttSegment 拼入 mergeBuffer 累积，同时推送拼接后的完整文本。mergeBuffer 的设计是因为 ASR 的 VAD 可能在用户一句话中间就触发（比如换了口气），导致一句话被切成多个 completed 片段。

如果 type 是 control，反序列化为 WebSocketControlMessage 后调 handleControl 分发。支持三种 action：submit 提交答案、end\_interview 结束面试、start\_phase 切换面试阶段。

用户点击提交是最核心的路径。handleControl 检测到 submit 后，先通过 AtomicBoolean CAS 操作拿并发锁防止多次触发，若锁已被占用则排期 400ms 后重试。拿到锁后从 mergeBuffer 原子取出全部累积文本并清空缓冲区，记录 ASR 合并等待耗时指标。然后在虚拟线程中执行 triggerLlmResponse，不阻塞 WebSocket IO 线程。

triggerLlmResponse 内部先标记 aiSpeaking=true 启动回声冷却保护，从数据库获取会话实体和对话历史，调用 DashscopeLlmService 的 chatStreamSentences 流式调用 LLM。LLM 每吐一个 token：先检查是否包含终止标点（。！？；!?;. 共八个字符），若是则截取完整句子通过 CompletableFuture 异步启动 TTS 合成，同时按 ≥180ms 间隔且 ≥12 字符增量的节流条件推送实时字幕给前端。流结束后兜底发送不以标点结尾的尾句。LLM 完整回复后，记录 llm.first\_token\_latency、llm.duration、llm.calls 指标，保存消息到 voice\_interview\_messages 表（messageType=DIALOGUE、phase、sequenceNum），然后等待所有 TTS Future 完成。分块模式下每句 TTS 完成立即 sendAudioChunk 推 WAV 给前端，合并模式下拼接全部 PCM 后一次性推送。TTS 内部流程和开场问题一样——临时建 WebSocket、commit 模式合成、同步等待返回 PCM、Handler 层 convertPcmToWav 加 44 字节 WAV 文件头。最后记录 turn.duration、turn.completed 指标，aiSpeaking=false、设 800ms 冷却期，finally 确保 CAS 锁释放。整个过程形成循环：用户说话 → ASR 识别 → mergeBuffer 累积 → 用户点提交 → LLM 流式回复（逐句触发 TTS）→ AI 语音播放 → 用户继续说话。

## 四、异步评估

面试结束后，系统不阻塞等 LLM 出评估报告，而是通过 Redis Stream 异步投递。endSession 末尾 evaluateStatus 已设为 PENDING，然后调 voiceEvaluateStreamProducer.sendEvaluateTask 将 sessionId 通过 XADD 入队到 voice:evaluate:stream。VoiceEvaluateStreamConsumer 继承 AbstractStreamConsumer，在后台线程轮询消费。消费前检查会话是否存在（已删除则标记 CANCELLED 并 ACK），检查评估结果是否已存在（幂等跳过），失败重试最多 3 次，超过标记 FAILED。

评估核心在 VoiceInterviewEvaluationService.generateEvaluation 方法，分七步：查会话实体和所有对话消息按序号升序；消息为空走 saveEmptyEvaluationTransactional 生成空评估（总分 0、反馈"暂无可评估内容"）；有消息则构建 QaRecord 列表，AI 文本作为 question、用户文本作为 answer，同时 inferCategory 基于关键词推断分类（"项目""实习"→ 项目深挖、"职业规划""优缺点"→ HR 问题、其余默认技术问题）；获取 LLM ChatClient；根据 skillId 构建评估参考上下文；调用 UnifiedEvaluationService.evaluate 执行分批 LLM 评估（三阶段流水线——分批评估、合并批次、二次汇总，批量失败零分兜底，汇总失败降级到批次聚合结果），此步骤必须在 @Transactional 外部执行避免长时间占用数据库连接；拿到 EvaluationReport 后通过 saveEvaluationTransactional 持久化到 voice\_interview\_evaluations 表，包含 overallScore、overallFeedback，以及四个 JSON 字段——questionEvaluationsJson 存逐题评分、strengthsJson 存优势列表、improvementsJson 存改进建议、referenceAnswersJson 存参考答案，用 JSON 字段而非固定列是因为对话轮数不固定。

评估完成后前端通过 GET /evaluation 轮询获取状态，2-3 秒一次。Controller 从会话实体的 evaluateStatus 判断进度——PENDING 显示排队中、PROCESSING 显示正在评估、COMPLETED 停止轮询加载 VoiceEvaluationDetailDTO 渲染评估面板、FAILED 显示错误信息并提供重新评估按钮。手动触发 POST /evaluation 做了三级幂等保护——COMPLETED 直接返回缓存结果、PENDING 或 PROCESSING 返回当前状态不重复入队、只有 FAILED 或 null 才触发新的评估任务。
