前端点击创建语音会话之后，请求体是 `CreateSessionRequest`，里面包含角色类型（也就是模板 ID，比如 `java-backend` 表示后端开发方向）、难度（初级/中级/高级）、简历 ID、自定义 JD 文本（用户把目标岗位的职位描述粘贴进来，LLM 拿到后出题会更有针对性），还有四个面试阶段的布尔开关——开场介绍默认关、技术面/项目面/HR 面默认开，以及最重要的 `llmProvider` 字段用来指定用哪个模型，没填的话后端走默认 Provider。

后端 Controller 接到请求后调 `VoiceInterviewService` 的 `createSession` 方法。方法里先从请求中取出 `skillId` 和 `llmProvider`，没传就用常量里的默认值补齐。然后通过 Builder 构建一个 `VoiceInterviewSessionEntity`，把用户 ID、角色类型、模板 ID、难度、四个阶段开关、计划时长这些字段填进去。这里有个关键点——`currentPhase` 初始阶段不是请求里直接传来的，而是按 INTRO → TECH → PROJECT → HR 的顺序找第一个用户开启的阶段作为面试起点，四个全关了才兜底返回 COMPLETED。

实体构建完之后先 `save` 到 PostgreSQL，JPA 的 `@PrePersist` 回调会自动把创建时间、更新时间、开始时间设成当前时间，Service 代码不用管。接着把实体缓存到 Redis，Key 是 `voice:interview:session:{id}`，TTL 设一小时，这样后续 WebSocket 实时通话过程中读会话信息就不用每次都查库了。

最后调 `buildSessionResponse` 把实体转成 `SessionResponseDTO` 返回给前端，里面包含会话 ID、角色类型、当前阶段、状态、开始时间、计划时长，以及最重要的 `webSocketUrl`。这个 URL 的前半段 `ws://localhost:8080/ws/voice-interview/` 是固定的，它来自 [WebSocketConfig](file:///Users/ogawaaya/Desktop/学习/interview_guide/interview-guide-optimize/app/src/main/java/interview/guide/modules/voiceinterview/config/WebSocketConfig.java#L58) 里注册的端点路径——`/ws/voice-interview/{sessionId}`，由 Spring WebSocket 框架在启动时把 `VoiceInterviewWebSocketHandler` 绑定到这个路径上。URL 的后半段 `{sessionId}` 是数据库自增生成的主键 ID，直接拼进去。前端拿到这个地址后直接建 WebSocket 长连接，后面所有的实时语音通话——ASR 识别结果推送、AI 回复朗读——都走这条连接，不经过 REST 接口了。

<br />

为什么会话要缓存到redis中？

面试属于频繁的读写的，比如每回答一题都要把答案存到会话中，然后再调用llm评估，所以把会话缓存到redis中，可以加速读写，然后是先更新缓存再更新数据库，如果数据库更新失败，就记录日志，后续根据日志人工处理，因为不能因为一个问题的保存失败就直接让用户停止面试。面试会话是高频读写的临时状态。创建后放入 Redis，可以降低数据库访问压力、快速维护题目进度和答案状态，同时支持多实例共享会话、断点续答和未完成会话快速查询；数据库负责持久化和缓存失效后的恢复。
