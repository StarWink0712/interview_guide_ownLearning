***

afterConnectionEstablished 方法执行完之后，前后端的 WebSocket 连接建好了，服务端到 ASR 的 WebSocket 也连上了，开场问题也推送出去了。此时 Handler 不再有代码在主动执行，进入**事件驱动等待状态**——之后的所有行为都由 Spring 框架回调触发。

前端用户开口说话后，麦克风采集音频，Base64 编码成文本帧，通过 WebSocket 发到服务端。Spring 框架收到这个文本帧后，自动回调 Handler 的 handleTextMessage 方法。这个方法每次收到前端发来的任意 WebSocket 文本帧都会被触发，是整个面试期间最核心的总入口。方法内部先从 URI 路径中提取 sessionId，记录一下消息大小（超过 200KB 会打警告日志），然后解析 JSON 拿到 type 字段做分发。目前支持两种 type：audio 和 control。

如果 type 是 audio，说明前端推送了一段麦克风音频数据，data 字段里面是 Base64 编码的 PCM 音频字节。方法拿到这个 data 之后调 handleUserAudio，这个方法负责把音频发给 ASR。handleUserAudio 内部会把 Base64 解码还原成原始 PCM 字节数组，然后检查一下回声冷却——如果当前 AI 正在播放 TTS 音频（aiSpeaking 标记为 true），就丢弃这段音频，防止扬声器播放的 AI 声音又被麦克风录进去形成回声循环。如果通过检查，就调 ASR 的 sendAudio 把 PCM 发给 DashScope 进行识别。如果发送过程中 ASR 连接断了（比如 DashScope 那边 WebSocket 超时），会自动触发重连，重试一次。

ASR 收到音频后开始识别，结果通过之前注册的回调异步返回。中间结果（用户还在说话，文本可能变）走 onPartial → handleSttResult(sessionId, text, false) → 直接调 sendSubtitle 推给前端当实时字幕。最终结果（VAD 检测到用户停嘴了）走 onFinal → handleSttResult(sessionId, text, true) → 调用 appendFinalSttSegment 把这段文本拼进 mergeBuffer 累积，同时把拼接后的完整文本推给前端。mergeBuffer 设计的目的是因为 ASR 的 VAD 可能在用户一句话中间就触发（比如换了口气），导致一句话被切成好几个 completed 片段，所以必须拼起来再送 LLM。

如果 type 是 control，说明前端发来了操作指令。控制消息被反序列化成 WebSocketControlMessage 对象，然后调 handleControl 分发。支持三种 action：submit 提交答案触发 LLM 和 TTS 管线、end\_interview 结束面试、start\_phase 切换面试阶段。

用户提交是最核心的路径。handleControl 检测到 submit 后，先通过 AtomicBoolean 的 CAS 操作拿到并发锁，防止用户短时间内点多次提交导致多个 LLM 管线同时跑。然后从 SessionState 的 mergeBuffer 中原子地取出全部累积的 ASR 识别文本并清空缓冲区。这个文本就是用户刚才说的一整段话的完整内容。

拿到文本后，在虚拟线程中异步执行 triggerLlmResponse 方法。这个方法负责跑完整的 LLM + TTS 管线，不能阻塞 WebSocket IO 线程。内部先把用户文本保存成 VoiceInterviewMessageEntity 落到数据库，然后调用 DashscopeLlmService 发 LLM 请求。LLM 的 Prompt 里包含了当前面试的阶段上下文、难度、技能方向、历史对话记录，以及用户刚才提交的那段文本，让 AI 面试官根据这些信息生成一个自然的面试官回复。llm完全回复完之后才会把生成的完整答案落库。

LLM 返回的回复文本也是一边生成一边推送给前端的——流式输出模式下，每生成一句话就调 sendTextMessage 推字幕，用户能看到 AI 面试官"正在打字"，体验更自然。LLM 全部生成完毕后，把 AI 的回复文本也保存进数据库。调用llm时通过stream流式调用，这样返回才是流式返回的，不需要等返回完毕再推送给答案给服务端。

<br />

这里要注意进如TTS合成阶段是llm每生成一句话都会掉用一次tts合成，等合成完就把语音给前端，要不然就会出现前端已经全部显示了文本，而语音还在合成，所以要逐句合成，通过正则表达式判断遇到句号问号等就算一句。

然后进入 TTS 合成阶段。调 QwenTtsService 的 synthesize 方法把 AI 回复文本（即下一题）转成 PCM 语音。这里的过程和开场问题里的 TTS 调用完全一样：构建参数 → 建立 WebSocket → 配置音色语速 → appendText + commit → CountDownLatch 同步等待 → 拿到完整 PCM → Handler 层 convertPcmToWav 转 WAV。合成完的 WAV 音频通过 sendAudio 方法 Base64 编码后塞进 JSON，走 WebSocket 文本帧推给前端，前端解码后通过 AudioContext 播放。

TTS 音频推送完之后，LLM 管线结束，释放 CAS 并发锁，用户可以继续说下一句话。整个过程就形成了一个循环：用户说话 → ASR 识别 → mergeBuffer 累积 → 用户点提交 → LLM 回复 → TTS 合成 → AI 语音播放 → 用户接着说下一句。llm回复是流式的，回复一句就合成一句语音，文本推送给前端。一句话的界限是遇到标点就是一句话。

如果前端发来的是 end\_interview 指令，handleControl 会调 voiceInterviewService 的 endSession 结束会话，把会话状态改成 COMPLETED，计算实际时长，然后通过 Redis Stream 投递异步评估任务。评估任务有单独的 Consumer 消费，走 LLM 生成多维度评分报告，不在实时链路里，所以不会阻塞用户退出。
