***

前端点击"添加面试"按钮后弹出输入框，用户把面试邀请邮件或短信的原始文本粘贴进去（比如飞书会议邀请、腾讯会议邀请、Zoom 邀请等），点击"解析文本"，前端将这段原始文本封装到 `ParseRequest` 对象中，同时前端可以选择指定来源格式（飞书、腾讯会议、Zoom）或者不指定让后端自动识别，然后发送 POST 请求到 `/api/interview-schedule/parse` 接口。

Controller 层的 parse 接口接收到请求后，调用 `InterviewParseService.parse()` 方法进入解析逻辑。方法内部首先检查前端传入的文本是否为 null 或空字符串，如果是则直接返回失败的 `ParseResponse`，包含错误码和提示信息"解析文本不能为空"。如果文本不为空，则进入规则解析阶段，调用 `tryRuleParsing(rawText, source)` 方法。这个方法分三种情况处理：情况一，如果前端显式指定了来源格式（source 参数不为空），直接跳到对应的解析器——飞书走 `parseFeishu()`、腾讯会议走 `parseTencent()`、Zoom 走 `parseZoom()`；情况二，如果没有指定来源，通过 `String.contains()` 检测文本中的特征关键词自动识别格式（比如文本中包含"飞书"、"Feishu"、"meeting.feishu.cn"就调用飞书解析器，包含"腾讯会议"、"会议号"就调用腾讯会议解析器，包含"Zoom"、"zoom.us"就调用 Zoom 解析器），识别到一个匹配的就尝试解析并通过 `isValidResult()` 检查结果是否提取到了至少一个关键字段（面试时间、会议链接、公司名称、岗位名称四选一即可）；情况三，如果特征都不匹配，就依次尝试三个解析器作为兜底策略。

三个解析器内部都是通过预编译的 `java.util.regex.Pattern` 正则表达式逐字段提取。以飞书为例：用 `TIME_PATTERN_FEISHU`（匹配"时间：2026-05-21 14:00"或"时段：2026-05-21 14:00"）提取面试时间，用 `LINK_PATTERN_FEISHU`（匹配 `https://meeting.feishu.cn/...`）提取会议链接，用 `COMPANY_PATTERN_FEISHU`（匹配"公司：xxx"或"单位：xxx"）提取公司名称，用 `POSITION_PATTERN_FEISHU`（匹配"岗位：xxx"或"职位：xxx"）提取岗位名称，用 `ROUND_PATTERN_FEISHU`（匹配"第二轮"、"第3场"）提取面试轮次。腾讯会议解析器则用 `TIME_PATTERN_TENCENT` 直接匹配"2026-05-21 14:00"格式的日期时间，用 `MEETING_ID_PATTERN_TENCENT` 匹配 9 位以上的会议号，用 `PASSWORD_PATTERN_TENCENT` 匹配 4 位以上密码，因为腾讯会议没有完整的 URL 链接，所以把会议号和密码拼装成文本存入 meetingLink 字段。Zoom 解析器则主要提取 `zoom.us/j/...` 链接和日期时间。每个解析器内部都套了 try-catch，任何字段解析异常不会阻断整体流程，已提取的字段仍会返回。

如果规则解析返回的结果通过了 `isValidResult` 校验（至少有一个关键字段有值），就直接返回该结果，跳过后面的 AI 解析。如果规则解析结果为空（所有解析器都没拿到任何有效字段），则降级到 AI 解析，调用 `parseWithAI(rawText, provider)` 方法。这个方法内部先通过 `LocalDateTime.now()` 获取当前日期（格式为 ISO\_LOCAL\_DATE，如"2026-07-09"），目的是让 LLM 能够推算相对时间——比如用户输入"明天下午两点面试"，LLM 可以基于当前日期推算出确切的"2026-07-10 14:00"。然后调用 `PromptSanitizer.sanitize(rawText)` 对用户输入做安全清洗，移除可能存在的恶意 Prompt 注入指令。接下来构建最终 Prompt：使用 String.format 将当前日期和清洗后的文本填入预先定义好的 `PARSE_PROMPT` 模板中，模板约定了 LLM 必须返回严格的 JSON 格式，包含 interviewTime、companyName、position、meetingLink、interviewType、roundNumber 等字段，且不能返回模板之外的任何多余内容。

构建好 Prompt 后，通过 `LlmProviderRegistry.getChatClientOrDefault(provider)` 获取 ChatClient（如果前端传了 provider 参数就用指定的，否则取配置文件中的默认 Provider），直接调用 `chatClient.prompt().user(prompt).call().content()` 拿到 LLM 返回的原始文本。这里之所以不需要用 `StructuredOutputInvoker`（结构化输出重试包装器），是因为 LLM 返回的是嵌入在文本中的 JSON 而不是直接的 Bean 映射，需要手动提取。拿到 LLM 返回的 content 后，先判空，然后调用 `extractJson(content)` 方法从中提取 JSON 字符串——兼容 LLM 常见返回格式，包括用 Markdown 代码块包裹的 \`\`\`json ... \`\`\` 格式和裸 JSON 格式。提取成功后使用 Jackson 的 `ObjectMapper.readValue(json, new TypeReference<Map<String, String>>())` 将 JSON 转为 `Map<String, String>` 结构，然后逐字段从 Map 中取值填充 `CreateInterviewRequest` 对象：interviewTime 需要经过 `parseDateTime` 方法解析为 `LocalDateTime`，roundNumber 通过 `parseRoundNumber` 方法把中文数字或阿拉伯数字转成 Integer，其余字段直接 set。如果 JSON 解析失败或 LLM 返回内容为空，则返回 null。

回到 Service 层的 `parse()` 方法，拿到规则解析或 AI 解析的结果后（此时是一个 `CreateInterviewRequest` 对象），将其包装到 `ParseResponse` 中，同时设置 `confidence` 字段（置信度）：如果是规则解析成功，confidence 设为 "HIGH"（因为正则匹配结果确定性强）；如果是 AI 解析成功，根据提取到的字段数量设置 "MEDIUM" 或 "LOW"；如果两者都失败则返回一个失败的 ParseResponse。Controller 层拿到 ParseResponse 后统一包装为 `Result<ParseResponse>` 通过 HTTP 200 返回给前端。

前端收到 ParseResponse 后，将其中的 data 字段（CreateInterviewRequest）渲染到表单中展示给用户确认——用户可以看到解析出来的公司名称、岗位、面试时间、会议链接、面试类型、面试轮次等信息，如果某个字段解析有误或为空，用户可以手动修改。此时解析出来的数据仅在前端展示，还没有落库。

用户确认无误后点击"创建面试日程"，前端将同一个 CreateInterviewRequest（可能经过用户手动修正）发送到 `POST /api/interview-schedule` 接口。Controller 的 create 方法先通过 `@Valid` 校验请求体字段合法性（@NotBlank、@NotNull 等），然后调用 `InterviewScheduleService.create(request)`。Service 的 create 方法内部先创建一个新的 `InterviewScheduleEntity` 对象（使用 @Builder 构建或 new 后逐字段 set），通过 `BeanUtils.copyProperties(request, entity)` 将 CreateInterviewRequest 中的字段值复制到实体中，然后手动设置一些 Request 中没有但 Entity 需要的默认字段：status 设为 `InterviewStatus.PENDING`（待面试）、createdAt 设为当前时间、调用 `normalizeReminderSettings(entity)` 规范化提醒设置（reminderEnabled 为 null 时默认 true，reminderEmail 为空字符串时设为 null）。之后调用 `interviewScheduleRepository.save(entity)` 将实体持久化到 PostgreSQL 的 interview\_schedules 表中（JPA save 方法会自动填充 id 和 updatedAt）。保存成功后调用 `reminderService.synchronizeReminders(entity)` 同步提醒计划，最后将 entity 转为 `InterviewScheduleDTO` 返回给 Controller，Controller 再包装为 `Result<InterviewScheduleDTO>` 返回给前端展示创建成功。

进入提醒模块，`synchronizeReminders` 方法先做三道前置检查：第一，如果全局配置 `planningEnabled` 为 false（整个提醒功能被关闭），直接调用 `cancelActiveReminders(scheduleId, reason)` 取消该日程下所有活跃状态的提醒并返回；第二，如果日程的 `reminderEnabled` 为 false（该日程单独关闭了提醒）或日程 status 不是 PENDING（面试已结束或已取消），同样取消所有活跃提醒并返回；第三，如果面试时间为 null（没有面试时间就无法计算提醒触发点），取消所有活跃提醒并返回。通过三道检查后，进入提醒计划生成阶段：首先为 IN\_APP 通道调用两次 `upsertPlan`，分别传入 ReminderTiming.DAY\_BEFORE 和 ReminderTiming.HOUR\_BEFORE，生成"提前一天"和"提前一小时"两条站内提醒。然后检查日程有没有配置 reminderEmail：调用 `trimOrNull(email)` 对邮箱地址做 trim 判空，如果结果为 null（没配邮箱），则调用 `cancelChannel(scheduleId, EMAIL, reason)` 取消该日程已有的邮件通道提醒并返回；如果配置了邮箱，则同样调用两次 upsertPlan 为 EMAIL 通道生成两条邮件提醒。所以一次 synchronizeReminders 调用最多生成 4 条提醒记录。

upsertPlan 方法接收四个参数——日程实体、提醒通道（IN\_APP/EMAIL）、提醒时机（DAY\_BEFORE/HOUR\_BEFORE）、收件人地址（站内为 null，邮件为邮箱地址）。方法内部先调用 `resolveRemindAt(schedule.getInterviewTime(), timing)` 计算提醒触发时间：如果是 DAY\_BEFORE 就用面试时间减去配置文件中的 `dayBeforeHours`（默认 24 小时），如果是 HOUR\_BEFORE 就用面试时间减去 `hourBeforeMinutes`（默认 60 分钟）；如果计算结果已经早于当前时间，则返回当前时间让提醒立即触发。然后生成提醒标题：DAY\_BEFORE 的标题是"{公司名}面试将在明天开始"，HOUR\_BEFORE 的标题是"{公司名}面试将在一小时后开始"。提醒内容是固定模板："您应聘的'{岗位名}'面试时间为 {面试时间}，请提前做好准备。" 接下来通过 `reminderRepository.findByScheduleIdAndChannelAndTiming(scheduleId, channel, timing)` 查找数据库中是否已存在同 (scheduleId, channel, timing) 组合的提醒记录——这个组合是唯一约束，如果找到就取出该记录用于更新，找不到就通过 Builder 创建一个新的 InterviewReminderEntity（初始状态 PENDING、retryCount = 0）。然后对比提醒时间和收件人是否发生了变化（deliveryChanged），将新计算的 remindAt、recipient、title、content 写入提醒实体。如果 deliveryChanged 为 true（时间或收件人变了），或者原提醒状态是 CANCELLED、FAILED（已终止的记录需要重新激活），就把状态重置为 PENDING、retryCount 清零、清空 lastError、sentAt、readAt，让这条提醒重新进入待处理队列。最后 save 到数据库。

提醒计划入库后，`InterviewReminderScheduler`（通过 `@Scheduled(cron = "0 * * * * *")` 默认每秒扫描一次）调用 `reminderService.claimDueReminderIds()` 查询到期提醒。这个方法使用悲观写锁 `PESSIMISTIC_WRITE` 查询 `status = PENDING AND remindAt <= NOW()` 的记录，按 remindAt 升序排列，每次最多取 batchSize（默认 50）条，批量将这些记录的状态改为 QUEUED，返回 ID 列表。Scheduler 拿到 ID 列表后，遍历调用 `producer.sendReminder(reminderId)` 将每条提醒投递到 Redis Stream（key: "interview-schedule:reminder:stream"），消息体包含 reminderId、businessId（与 reminderId 相同）、retryCount（首次为 0）、traceId（用于链路追踪）。

消费者 `InterviewReminderStreamConsumer` 在 `@PostConstruct` 时启动单线程守护线程池，进入死循环从 Redis Stream 拉取消息。父类 `AbstractStreamConsumer` 的 `processMessage` 模板方法编排完整处理流程：首先调用子类的 `parsePayload` 从消息体中提取 reminderId 封装为 ReminderPayload；然后调用 `markProcessing` 将提醒状态改为 PROCESSING（如果已 CANCELLED 则抛 AsyncTaskCancelledException 直接 ACK 跳过）；接着调用核心方法 `processBusiness`，这里先通过 `reminderService.getDeliveryContext(reminderId)` 获取投递上下文（不仅包含提醒本身的标题、内容、通道、收件人，还关联查询了对应日程的公司名称、岗位、面试时间、面试类型、会议链接、面试官、备注等完整信息），然后按通道分流——如果是 EMAIL 通道，调用 `emailSender.send(context)` 即 `SmtpReminderEmailSender.send()`，该方法使用 Spring JavaMailSender 构建 HTML 格式邮件（包含公司、岗位、时间、形式、会议信息、面试官、备注等区块，空字段自动隐藏），通过 SMTP 协议发送；如果是 IN\_APP 通道，当前只打日志记录"站内面试提醒已到达展示时间"，状态流转到 SENT 后前端通过调用 `GET /api/interview-schedule/reminders/in-app` 接口拉取提醒列表渲染展示（没有实时推送弹窗，用户需刷新或定时轮询才能看到）。成功执行后调用 `markCompleted` 将提醒状态改为 SENT 并记录 sentAt，最后 ACK 消息确认消费。如果 processBusiness 抛出 AsyncTaskCancelledException（日程已删除或状态不再 PENDING），则调用 markCancelled 将提醒改为 CANCELLED 并 ACK。如果是其他异常，判断 retryCount 是否小于 3：未超过则调用 retryMessage 重新构建消息体（retryCount+1）写入 Redis Stream 并将数据库状态重置为 QUEUED 等待下次调度；超过 3 次则调用 markFailed 将提醒标为 FAILED，记录截断后的错误信息（最多 1000 字符），然后 ACK。整个链路就是：解析→创建日程→生成提醒计划→定时扫描到期→Redis Stream 异步投递→SMTP 发邮件/前端拉取站内通知。

定时扫描链路从 `InterviewReminderScheduler` 开始，这是一个被 `@Component` 和 `@ConditionalOnProperty(name = "app.interview-reminder.dispatch-enabled", havingValue = "true")` 注解的 Spring Bean，只有当配置文件中该开关为 true 时才会被加载到容器中。类上同时标注了 `@Slf4j` 和 `@RequiredArgsConstructor`，通过构造器注入了 `InterviewReminderService` 和 `InterviewReminderStreamProducer` 两个依赖。核心方法是 `dispatchDueReminders()`，被 `@Scheduled` 注解修饰，cron 表达式默认值为 `0 * * * * *`（每分钟第 0 秒执行一次），可通过配置文件中的 `app.interview-reminder.scan-cron` 覆盖，zone 默认为 `Asia/Shanghai` 东八区。方法执行时先调用 `reminderService.claimDueReminderIds()` 认领到期提醒，该方法内部使用 `@Transactional` 注解保证原子性，通过 Repository 层定义的 `findDueForUpdate` 查询执行 `PESSIMISTIC_WRITE` 悲观写锁的 SQL（`SELECT ... FOR UPDATE`），条件为 `status = PENDING AND remindAt <= NOW()`，按 remindAt 升序排列，用 `PageRequest.of(0, batchSize)` 分页限制每次最多取 `properties.getBatchSize()`（默认 50）条记录。这样可以防止多实例部署时两个调度器节点并发认领同一批提醒。查到到期的 PENDING 记录后，遍历将它们的状态批量更新为 QUEUED，调用 `reminderRepository.saveAll(due)` 写回数据库，然后通过 Stream API 将实体集合映射为 ID 列表返回。Scheduler 拿到 ID 列表后，遍历调用 `producer.sendReminder(reminderId)` 将每个提醒 ID 投递到 Redis Stream。Producer 的 `sendReminder` 方法内部创建一个 `ReminderPayload(reminderId, retryCount=0)` 记录对象，然后调用父类 `AbstractStreamProducer.sendTask(payload)` 将载荷发送出去。父类的 sendTask 方法先调用子类实现的 `buildMessage(payload)` 将 ReminderPayload 转为 `Map<String, String>`，包含四个字段：reminderId（提醒 ID）、businessId（与 reminderId 相同，供父类模板方法统一处理业务标识）、retryCount（当前重试次数，首次为 "0"）、然后父类的 `buildMessageWithTrace` 额外从当前线程的 MDC 上下文中取出 traceId 追加到 Map 中用于全链路追踪。消息体构建完成后通过 `redisService.streamAdd(streamKey, message, STREAM_MAX_LEN)` 写入 Redis Stream，streamKey 由子类重写的 `streamKey()` 方法返回常量 `"interview-schedule:reminder:stream"`，STREAM\_MAX\_LEN 是全局常量限制 Stream 最大长度防止内存溢出。写入成功后日志记录 `"面试提醒任务已发送到Stream"` 及 messageId，如果写入失败（Redis 连接异常等）则回调子类的 `onSendFailed` 方法，直接将数据库中的提醒状态标记为 FAILED。与此同时，消费者 `InterviewReminderStreamConsumer` 在 Spring Boot 启动时通过 `@PostConstruct` 自动初始化——父类 `init()` 方法生成唯一的 consumerName（consumerPrefix + 8 位随机 UUID），创建单线程守护线程池（ThreadPoolExecutor，核心线程和最大线程均为 1，使用 LinkedBlockingQueue 无界队列，守护线程名称为 "interview-reminder-consumer"），设置运行标志 running 为 true，提交 `startConsumer` 任务。startConsumer 内部先调用 `redisService.createStreamGroup(streamKey, groupName)` 创建消费者组（如果组已存在会打印警告但不影响后续运行），然后进入 `consumeLoop` 死循环，循环内不断调用 `redisService.streamConsumeMessages(streamKey, groupName, consumerName, BATCH_SIZE, POLL_INTERVAL_MS, this::processMessage)`，每次从 Redis Stream 拉取最多 BATCH\_SIZE 条消息，POLL\_INTERVAL\_MS 为阻塞超时时间，拉取到的每条消息都会回调 `this::processMessage` 方法。

消息消费链路的核心是父类 `AbstractStreamConsumer` 的 `processMessage(StreamMessageId messageId, Map<String, String> data)` 模板方法，它编排了完整的处理骨架。第一步，备份当前线程 MDC 中的旧 traceId，然后从消息体的 data Map 中取出生产者写入的 traceId 写入 MDC，保证后续所有日志自动带上正确的链路追踪标识。第二步，调用子类重写的 `parsePayload(messageId, data)` 方法解析消息体：子类从 data 中取 `FIELD_REMINDER_ID` 字段，如果为 null 则打印警告并返回 null（父类收到 null 会直接 ACK 跳过），如果不为 null 则尝试 `Long.parseLong` 转为数字，转换失败同样返回 null 跳过；成功则包装为 `ReminderPayload(reminderId)` 记录对象。第三步，解析 retryCount 字段（调用 `parseRetryCount(data)`，不存在时默认为 0）。第四步进入业务处理 try 块：先调用子类重写的 `markProcessing(payload)`，子类委托 `reminderService.markProcessing(reminderId)`，该方法内部通过 `getReminder(reminderId)` 从数据库查询提醒实体（不存在抛 BusinessException），然后检查提醒状态——如果状态为 `CANCELLED`，说明提醒已被人为取消，抛出 `AsyncTaskCancelledException` 通知父类走取消流程；否则将状态设为 `PROCESSING`、清空 `lastError`、save 保存。然后调用子类重写的 `processBusiness(payload)`，这是真正的业务执行点：子类先调用 `reminderService.getDeliveryContext(reminderId)` 获取投递上下文，该方法内部先查提醒实体，再从 scheduleRepository 根据 scheduleId 查出完整日程实体，如果日程已删除或 status 不再是 PENDING 则抛 AsyncTaskCancelledException 放弃投递，通过后将提醒和日程的字段组装为 `ReminderDeliveryContext` 记录（包含 reminderId、scheduleId、channel、recipient、title、content、companyName、position、interviewTime、interviewType、meetingLink、interviewer、notes）。拿到上下文后按 `context.channel()` 分流：如果是 `EMAIL` 通道，调用 `emailSender.send(context)`；如果是 `IN_APP` 通道，当前只打印日志 `"站内面试提醒已到达展示时间"`。

进入邮件发送逻辑，`SmtpReminderEmailSender` 的 `send(context)` 方法先做前置校验——检查 `context.recipient()` 是否为 null 或空字符串，不通过则直接抛 `BusinessException(INTERVIEW_REMINDER_SEND_FAILED, "邮件提醒缺少收件地址")`。通过后进入 try 块：首先调用 `mailSender.createMimeMessage()` 创建 MIME 邮件对象，然后用 `MimeMessageHelper` 包装，第二个参数 false 表示不含附件，第三个参数指定 UTF-8 编码防止中文乱码。接着从 `properties.getEmail()` 中提取配置的发件人地址（fromAddress）、发件人显示名称（fromName）和邮件主题前缀（subjectPrefix），通过 `helper.setFrom(new InternetAddress(fromAddress, fromName, UTF-8))` 设置发件人、`helper.setTo(recipient)` 设置收件人、`helper.setSubject(subjectPrefix + " " + context.title())` 设置邮件主题（如"\[AI面试] 阿里巴巴面试将在明天开始"）、`helper.setText(buildHtml(context), true)` 设置 HTML 正文（第二个参数 true 表示内容类型为 text/html）。buildHtml 方法根据上下文字段的非空判断动态显示八个信息区块：标题（紫色 H2）、正文段落、公司、岗位、时间（格式化为"2026年07月09日 14:00"）、面试形式（null 时展示"未填写"）、会议信息（http/https 链接渲染为可点击的 a 标签，纯文本如"会议号: 123456"直接展示）、面试官、灰色背景备注栏，所有用户输入文本均经过 `HtmlUtils.htmlEscape` 转义防止 XSS 注入，最后附上"本邮件由 AI Interview 面试日程提醒服务自动发送"的灰色小字落款。邮件构建完成后调用 `mailSender.send(message)` 通过 SMTP 协议发送，成功后打印日志（日志中邮箱地址通过 maskEmail 脱敏为 `z***@company.com` 格式）。如果 try 块内抛出 `BusinessException`，直接原样再抛出；如果是其他异常（SMTP 连接超时、认证失败等），包装为 `BusinessException(INTERVIEW_REMINDER_SEND_FAILED, "发送面试提醒邮件失败: " + e.getMessage())` 抛出。这个异常抛回到父类的 `processMessage` 中被 `catch (Exception e)` 捕获：判断 retryCount 是否小于 MAX\_RETRY\_COUNT（3 次）——如果未超过，调用子类重写的 `retryMessage(payload, retryCount + 1)`，该方法重新构建 `Map.of(reminderId, businessId, retryCount)` 消息体并通过 `redisService.streamAdd` 再次写入 Redis Stream，同时调用 `reminderService.markRetrying(reminderId, retryCount)` 将数据库提醒状态重置为 QUEUED 并更新 retryCount；如果已超过 3 次，调用子类的 `markFailed(payload, error)` 将提醒状态设为 FAILED，记录截断后最多 1000 字符的错误信息。无论重试还是失败，当前消息都会 ACK 确认消费。如果 processBusiness 中抛的是 `AsyncTaskCancelledException`（提醒已取消或日程已删除），则走取消分支：调用 `markCancelled(payload, reason)` 将状态设为 CANCELLED 并记录原因，然后 ACK。成功流程则走 `markCompleted(payload)` 将状态设为 SENT 并记录 sentAt。所有分支最后都会在 finally 块中恢复 MDC 的旧 traceId，避免污染线程池中复用线程的日志上下文。

SSE 推送站内提醒（当前未实现，作为可选增强方案）的工作原理是：后端新增一个 `ReminderSseRegistry` 组件，内部用一个 `ConcurrentHashMap<String, SseEmitter>` 维护所有在线用户的连接，提供 `register(userId, emitter)` 方法将 SseEmitter 存入 Map 并注册 onCompletion/onTimeout/onError 清理回调，以及 `push(userId, data)` 方法根据 userId 查找对应 emitter 并调用 `emitter.send(SseEmitter.event().name("reminder").data(json, MediaType.APPLICATION_JSON))` 推送数据。在 Controller 层新增 `@GetMapping(value = "/api/interview-schedule/reminders/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)` 端点，方法内部创建 `new SseEmitter(Long.MAX_VALUE)` 超时设为永不超时，调用 `registry.register(userId, emitter)` 注册后将 emitter 作为返回值返回即可——Spring 检测到返回类型是 SseEmitter 后不会调用 `HttpMessageConverter` 转换，而是直接持有 Response 引用保持连接不关闭，响应头自动设为 `Content-Type: text/event-stream`、`Cache-Control: no-cache`、`Connection: keep-alive`。消费者 `processBusiness` 中 IN\_APP 分支改为调用 `sseRegistry.push(userId, context)`，context 的 record 会自动被 Jackson 序列化为 JSON 字符串写入连接，前端通过 `new EventSource("/api/.../stream")` 建立连接，用 `eventSource.addEventListener("reminder", (e) => { const data = JSON.parse(e.data); showNotification(data.title, data.content); })` 监听并在收到数据时弹出浏览器原生通知或页面内 Toast 组件。浏览器内置的 EventSource API 还自带断线重连机制——网络断开后会自动重新发起 GET 请求重建连接，无需手动编码。
