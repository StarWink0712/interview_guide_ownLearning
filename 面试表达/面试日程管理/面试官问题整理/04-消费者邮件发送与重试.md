# 消费者、邮件发送与重试

## 1. 提醒消费者是如何启动的？

**回答：** `InterviewReminderStreamConsumer` 继承 AbstractStreamConsumer，Spring Boot 启动后父类通过 `@PostConstruct` 初始化。它生成带随机 UUID 的 ConsumerName，创建核心线程和最大线程均为 1 的守护线程池，创建消费者组后进入循环，通过阻塞读取不断从 Redis Stream 拉取消息。

## 2. `AbstractStreamConsumer` 如何编排处理流程？

**回答：** 父类 `processMessage` 是模板方法，依次完成 TraceId 写入 MDC、`parsePayload`、解析 retryCount、`markProcessing`、`processBusiness`、`markCompleted` 和 ACK。子类只实现提醒业务相关的解析、状态更新、邮件发送和失败处理，从而复用统一的消费、日志、重试和确认流程。

## 3. 消息体解析失败时怎么处理？

**回答：** 子类从 Map 中读取 reminderId，字段为空或者无法转换成 Long 时记录警告并返回 null。父类收到空 Payload 后直接 ACK 跳过这条无效消息，避免格式错误的消息一直留在 PEL 中反复消费。

消息体解析失败其实就是要做好降级，可以直接ack跳过这个消息。

## 4. `markProcessing` 如何控制提醒状态？

**回答：** `markProcessing` 根据 reminderId 查询提醒实体，不存在时抛出业务异常；如果状态已经是 CANCELLED，就抛出 `AsyncTaskCancelledException` 进入取消流程；其他可处理状态会更新为 PROCESSING，清空 lastError 并保存，表示当前消费者已经开始投递。

## 5. DeliveryContext 包含什么，日程失效时怎么办？

**回答：** `getDeliveryContext` 会查询提醒及其关联日程，组装 reminderId、scheduleId、channel、recipient、title、content、公司、岗位、面试时间、面试形式、会议链接、面试官和备注等完整信息。如果日程已删除或者状态不再是 PENDING，则抛出 AsyncTaskCancelledException，取消提醒并 ACK，不再继续投递。

## 6. EMAIL 和 IN\_APP 通道分别如何处理？

**回答：** EMAIL 通道调用 `SmtpReminderEmailSender.send(context)`，通过 JavaMailSender 和 SMTP 发送邮件。IN\_APP 通道当前只记录“站内面试提醒已到达展示时间”，成功后状态更新为 SENT，前端通过 `GET /api/interview-schedule/reminders/in-app` 拉取提醒列表展示，目前没有实时推送弹窗。

## 7. SMTP 邮件是怎么构建和发送的？

**回答：** Sender 先校验收件地址，再使用 `mailSender.createMimeMessage()` 创建 MIME 邮件，通过 `MimeMessageHelper` 设置无附件、UTF-8、发件地址、发件名称、收件人、主题前缀和 HTML 正文，最后调用 `mailSender.send(message)` 通过 SMTP 发送。SMTP 超时、认证失败等普通异常会包装成 `BusinessException(INTERVIEW_REMINDER_SEND_FAILED)`。

收件地址可以在用户登录时在用户设置里面设置好邮件，然后存到数据库中的用户信息表。当要创建提醒时去数据库中查找这个邮件，通过java的mailSender创建mime邮件，设置无附件，UTF-8以及收件发件人等信息。

## 8. HTML 邮件如何避免 XSS 和泄露邮箱？

**回答：** HTML 正文根据上下文字段动态显示公司、岗位、时间、面试形式、会议信息、面试官和备注等区块，所有用户输入都通过 `HtmlUtils.htmlEscape` 转义，防止把恶意 HTML 或脚本写入邮件。发送成功日志中的邮箱会通过 maskEmail 脱敏，例如显示成 `z***@company.com`。邮件存储可以用加密的方式存储，避免用户信息泄露。

## 9. 消费成功后如何更新状态？

**回答：** processBusiness 正常完成后，父类调用 `markCompleted`，把提醒状态设置为 SENT 并记录 sentAt，然后执行 ACK 确认当前 Stream 消息。站内提醒和邮件提醒都遵循同一套成功状态流转。

## 10. 邮件失败、提醒取消和重试耗尽分别如何处理？

**回答：** 普通异常发生且 retryCount 小于 3 时，子类重新构造 retryCount+1 的消息写回 Stream，并通过 `markRetrying` 把数据库状态重置为 QUEUED；超过三次则标记 FAILED，并保存最多 1000 字符的错误信息。日程删除或提醒取消产生 AsyncTaskCancelledException 时标记 CANCELLED。无论重试、最终失败还是取消，当前消息都会 ACK；finally 中恢复原 MDC TraceId，避免线程复用造成日志上下文污染。

邮件发送失败可以通过消息重试机制进行三次重试，重试耗尽的话可以直接标记取消不再提醒或者降级用其他方式提醒。
