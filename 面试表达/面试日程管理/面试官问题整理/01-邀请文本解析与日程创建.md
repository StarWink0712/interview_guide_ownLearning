# 邀请文本解析与日程创建

## 1. 面试邀约文本的完整解析流程是什么？

**回答：** 用户点击“添加面试”，把飞书、腾讯会议、Zoom、邮件或短信中的原始邀约文本粘贴到输入框，前端封装成 `ParseRequest` 后请求 `/api/interview-schedule/parse`。Controller 调用 `InterviewParseService.parse()`，先校验文本，再尝试规则解析；规则没有提取到有效字段时降级到 LLM。解析结果包装成 `ParseResponse` 返回前端展示，用户确认或修改后再单独提交创建日程请求。

## 2. 为什么采用规则解析优先、AI 解析兜底？

**回答：** 飞书、腾讯会议和 Zoom 等常见模板的格式比较固定，可以用预编译正则快速、稳定、低成本地提取字段。规则结果只要至少包含面试时间、会议链接、公司名称、岗位名称中的一个关键字段，就直接返回并跳过 LLM；只有规则完全无法得到有效结果时才使用 AI，提高兼容性的同时减少模型调用成本。

## 3. 前端指定来源和自动识别来源分别怎么处理？

**回答：** 如果前端明确传入 Source，就直接调用对应的 `parseFeishu()`、`parseTencent()` 或 `parseZoom()`。如果没有指定，则根据“飞书”“Feishu”“meeting.feishu.cn”“腾讯会议”“会议号”“Zoom”“zoom.us”等特征词自动识别；仍然无法识别时，再依次尝试三个解析器作为规则兜底。

## 4. 飞书、腾讯会议和 Zoom 的规则解析分别提取什么？

**回答：** 飞书解析器通过正则提取面试时间、会议链接、公司、岗位和轮次；腾讯会议提取日期时间、九位以上会议号和四位以上密码，并把会议号和密码组合到 meetingLink 字段；Zoom 主要提取 `zoom.us/j/...` 链接和日期时间。每个解析器内部按字段处理异常，某个字段失败不会阻断已经成功提取的其他字段。

## 5. AI 兜底解析的完整流程是什么？

**回答：** 规则解析失败后调用 `parseWithAI(rawText, provider)`。方法获取当前日期，使用 PromptSanitizer 清洗原始文本，再把日期和文本填入解析模板；随后通过 `LlmProviderRegistry.getChatClientOrDefault(provider)` 获取模型并调用 `prompt().user(prompt).call().content()`。拿到内容后提取 JSON，转换成 `Map<String,String>`，再逐字段构造 `CreateInterviewRequest`。

## 6. 为什么 AI 解析要传入当前日期并清洗原始文本？

**回答：** 当前日期用于帮助模型把“明天下午两点”等相对时间换算成确定的 LocalDateTime。邀约邮件和短信属于外部不可信文本，可能夹带恶意指令，因此在进入 Prompt 前通过 PromptSanitizer 清洗，让模型只抽取时间、公司、岗位、地点等信息，不执行文本中的命令。

## 7. 为什么这里没有使用 StructuredOutputInvoker？

**回答：** 当前实现直接调用 ChatClient 获取 Content，再手动从文本中提取 JSON，因为模型返回的 JSON 可能包裹在 Markdown 的 `json` 代码块中，也可能是裸 JSON，并不是直接进行 Bean 映射。提取后再通过 ObjectMapper 转成 Map，并由业务代码完成字段转换。

## 8. LLM 返回结果如何转换成 CreateInterviewRequest 和置信度？

**回答：** `extractJson` 先兼容代码块和裸 JSON 两种格式，ObjectMapper 将 JSON 转成 `Map<String,String>`。interviewTime 通过 `parseDateTime` 转成 LocalDateTime，roundNumber 通过 `parseRoundNumber` 把中文或阿拉伯数字转成 Integer，其他字段直接填入 CreateInterviewRequest。规则解析成功时 confidence 为 HIGH；AI 成功时根据有效字段数量设置 MEDIUM 或 LOW；全部失败则返回失败 ParseResponse。

## 9. 为什么解析完成后不直接创建日程？日程是如何创建的？

**回答：** AI 或正则解析可能存在字段缺失或错误，所以解析阶段只把结果返回前端展示，允许用户修改公司、岗位、时间、链接和轮次，并不会直接落库。用户确认后再调用创建接口，Controller 使用 `@Valid` 校验，Service 把 Request 复制到 `InterviewScheduleEntity`，设置 PENDING、创建时间和提醒默认值，保存到 PostgreSQL，随后调用 `reminderService.synchronizeReminders(entity)` 生成提醒计划。
