前端点击添加面试，然后弹出文本框，把面试信息粘贴到框内，然后点击解析文本，前端会把要解析的文本封装到parseRequest对象内，后端parse 接收到这个请求，调用parseService服务的parse解析方法，进入到解析方法内。先检查前端传入的文本是不是空，如果是空就直接反失败。如果不为空，就先用规则解析进行解析（提前设置好有哪些规则，比如默认飞书模版，默认腾讯模版登），至于规则解析内部是用正则表达式等方式进行解析。不行的话，就调用llm识别，即ParseWithAi,在方法内部，先获取当前日期，然后清洗文本内容，防止内部有恶意指令，然后用提示词模版（解析面试日程），清洗后的待识别文本，构建最终提示词。然后通过llmproviderRegistry调用chatclient（这里不需要用结构化输出器的llm调用，直接用注册中心调用即可），然后用prompt方法调用，拿到llm返回的content内容，然后对内容进行检测，提取json将提取后的json内容转换成map结构，再逐字段填充createInterviewRequest，即创建/更新面试日程请求体,这个请求体实体，返回到service层之后，添加一些confidence信息，构造成parseresponse对象体，之后到controller层，再返回给前端。这里只是解析日程，前端用这个响应进行显示，但是还没有创建日程，之后再把这个request发给后端进行创建。

<br />

之后便是创建日程，前端拿到日程信息后，即request实体，之后点击创建面试日程，之后会controller层的create方法会接收到，再调用scheduleService服务的create方法，创建日程。在服务内部的create方法内，先创建一个面试日程实体，然后把request请求体中的信息都复制到实体中，然后设置一下实体的状态，比如待面试等；然后把实体存入数据库，最后调用remindService服务的synchronizeReminders服务，传入这个实体，后续做提醒。

<br />

然后进入到remindService服务，其synchronizeReminders方法，这个方法会检查有没有配置邮箱，如果没有邮箱，会创建两个站内提醒，在站内以弹窗的形式弹出进行提醒，提前一小时与提前一天；如果有邮箱，就会额外创建两个 发送给邮箱的提醒。创建提醒通过upserPlan方法，入参包括面试日程实体，提醒通道，提醒时机，收件人email地址，内部先从数据库中读取实体存储时的时间，用于计算提醒时间，然后生成提醒标题与提醒内容（面试将在一小时后开始，请做好准备），然后从数据库中查找看之前有没有这个提醒的对象的信息，如果有就取出来更新，没有就把创建的这个放进去。这里生成计划是第一步，之后通过定时扫描来进行提醒。

<br />

定时扫描：通过InterviewReminderScheduler.java 内部设置一个定时任务，每分钟执行一次扫描，扫描时，先调用remindService的clainmDueReminderIds方法认领到期的提醒，拿到到期提醒id的集合。在方法内部从数据库中查询所有已经到提醒时间，同时更新状态为queued，即代表在提醒队列中。然后将list集合返回给scheduler层，之后遍历集合，调用异步发送者，把任务发送到stream。同时消费者在springboot启动时主动拉取。这个消息体也是由reminderId，业务id，当前重试次数以及traceId组成。

这个到期时间可以设置成刚好两个小时，也可以早一分钟，这样扫描频率就算晚了一分钟扫描到，也不会延迟，最多延迟一秒服务端的准备时间。

扫描数量也要限制一下，如果要提醒的太多，扫描太久一次事务时长事务持有锁的时间就会过长，阻碍其他事务的操作。所以可以一次只扫描前50个索引。即削峰平谷，避免大量的消息涌入到数据库。

<br />

消费消息完成提醒：InterviewReminderStreamConsumer继承abstractconsumer方法来完成消息消费即任务提醒。父类中会循环拉取消息，然后调用解析消息的方法，这里重写了，parsePayLoad方法，从转为map格式的消息体中解析出reminderId字段,然后在父类的消费循环里，会调用markProcessing方法，进行标记消息在处理中，在子类中重写，调用reminderService服务的markProcessing方法去处理消息。在方法内部，先从数据库中根据提醒id去查询到提醒实体，然后对提醒实体的状态进行检查，如果是待处理就去处理，其他就抛出异常。然后把状态改成处理中。然后还是在父类消费者的循环中，会调用processBusiness方法，子类重写，先从数据库中获取投递上下文（日程完整信息+提醒信息），如果上下文的通道标识是email，就调用emailSender.send(context)方法去进行有机提醒，如果不是就服务端打印一下日志（或推送给前端展示一个提醒框，可以用三种方式）。

然后进入到emailSender.send方法内，用spring javaMailSender的smtp邮件投递实现（也可以用其他方式），先从上下文中验证邮件地址，通过了就用mailSender.createMimeMessgae创建出MIME邮件对象，然后设置一下不含附件，UTF-8编码等设置。然后从服务端配置中提取发件人地址，名称和邮件主题前缀。最后通过MimeMessageHelper设置一下发件人，收件人还有邮件正文，最后通过mailSender.send即SMTP协议发送邮件，发送失败会重试三次，因为是消费者设置了三次。

<br />

所以要先检查一下当前用户是否在线，即当前是否有sse连接，用户登录的时候就要建立这个连接并通过心跳机制进行保活，要不然无法主动向前端推送的。服务端定期发送心跳保活，前端监听连接状态并在断开后重连。

SSE不能由服务端主动建立连接，必须由客户端先建立并保持长连接。只要用户在线且连接存在，服务端就可以在面试前一小时通过该连接主动推送；如果需要在网页关闭或用户离线时也能收到提醒，就需要配合Web Push、App Push、短信或邮件，并将通知持久化以支持断线补偿。

SSE 的本质是前端发起一个普通的 HTTP GET 请求，服务端返回时故意不关闭连接，而是保持 TCP 连接不断开，并设置响应头 `Content-Type: text/event-stream`；之后服务端随时往这个连接里写 `data: {json字符串}\n\n`，浏览器的 `EventSource` API 收到数据后自动触发前端注册的 `addEventListener` 回调，从效果上看就是"后端主动推送给前端"。Spring 用 `SseEmitter` 封装了这个过程：Controller 返回 `SseEmitter` 对象时 Spring 会自动持有 Response 的引用不释放，后续任何地方拿到这个 `emitter` 调 `send()` 就相当于往那个未关闭的 HTTP 响应里追加数据，前端就能实时收到。

这是 `AbstractStreamProducer` 模板定义的一个通用字段，在不同业务场景下含义不同：

| 生产者      | businessId 含义       |
| :------- | :------------------ |
| 知识库向量化   | 知识库文档 ID            |
| 简历分析     | 简历 ID               |
| 面试评估     | 面试会话 ID             |
| **面试提醒** | 提醒 ID（= reminderId） |

对于提醒系统来说，要处理的"业务实体"就是提醒本身，所以 `businessId` 和 `reminderId` 是同一个值。它的作用是在 Consumer 端统一通过 `businessId` 来定位要处理的实体，方便模板方法做通用的日志、重试、状态追踪等逻辑，不需要每个子类都单独实现一套。
