# AI 公共基础层与 Provider 治理

## 1. 为什么要抽象 AI 公共基础层？

**回答：** 项目里的简历评估、面试分析、JD 解析、知识库问答和语音面试都需要调用 LLM。虽然业务场景不同，但底层都要处理模型厂商切换、结构化 JSON 解析、Prompt 注入防护以及调用监控和追踪等共性问题，所以我没有让各业务模块分别实现，而是把这些能力抽象成统一的 AI 公共基础层。

## 2. AI 模块主要解决了哪些共性问题？

**回答：** 主要解决四类问题：第一是多 Provider 配置和模型切换；第二是通过 `StructuredOutputInvoker` 提高 JSON 结构化输出的稳定性；第三是通过 `PromptSanitizer` 和 `PromptSecurityConstants` 防止外部文本反向控制模型；第四是记录 AI 调用日志和 Micrometer 指标，让调用耗时、成功失败、重试次数等信息能够被监控和追踪。这个模块的目标不是简单调用模型，而是把 AI 调用做成可替换、可复用、可治理、可观测的公共能力。

<br />

抽象成可替换可复用的ai层，方便统一管理，对内方便管理，对外提供统一的访问llm的接口。

## 3. `LlmProviderRegistry` 的职责是什么？

**回答：** `LlmProviderRegistry` 相当于 LLM Provider 注册中心，统一管理多个模型提供方。它根据 Provider 配置读取 `baseUrl`、`apiKey`、Chat 模型和 Embedding 模型等信息，再懒加载创建并缓存相应的 `ChatClient` 和 `EmbeddingModel`。它还根据业务场景提供默认对话型、结构化输出型和语音流式型等不同客户端。

## 4. Provider 配置为什么优先从数据库读取？

**回答：** Provider 配置会优先从数据库加载，没有时再从配置文件加载。数据库方式更适合运行时管理，因为修改 Provider、模型名称、BaseURL 或默认 Provider 时不需要停止应用；如果只放在配置文件中，修改配置通常需要重启服务。

<br />

从数据库读取是因为可以热插拔更新llm配置，可以直接把数据写入到数据库中，如果是从配置文件中加载的化就要重启服务。

## 5. ChatClient 和 EmbeddingModel 为什么使用懒加载缓存？

**回答：** 注册中心使用线程安全的 `ConcurrentHashMap` 缓存客户端，并采用“用到时再创建”的懒加载方式。没有被业务使用的 Provider 不会提前创建实例，已经创建的 `ChatClient` 和 `EmbeddingModel` 可以复用，避免每次模型调用都重新构建客户端。

## 6. 模型调用失败后是否需要清空客户端缓存？

**回答：** 不建议一次模型调用失败就清空全部缓存，因为缓存的是 `ChatClient` 和 `EmbeddingModel` 这类客户端配置对象，不是模型服务的健康状态。模型端宕机、网络超时、429 限流或 5xx 一般不是客户端对象失效导致的，重新创建 ChatClient 不能解决问题，反而可能造成频繁重建和性能抖动。

## 7. 临时异常和配置异常分别怎么处理？

**回答：** 对于超时、连接失败、限流和 5xx 等临时异常，保留现有缓存，先执行有限次数重试，同时记录失败指标和调用日志，必要时再做熔断、降级或切换备用 Provider。对于 API Key 错误、BaseURL 配错、模型名称不存在或者后台修改了 Provider 配置等配置类异常，才需要刷新缓存；当前通过 `registry.reload()` 在新增、修改、删除或切换默认 Provider 后清空缓存并重新懒加载，更细的优化是只清理指定 Provider 对应的缓存。

## 8. Provider 熔断和备用 Provider 切换怎么设计？

**回答：** 可以按 Provider 维护连续失败次数，超过阈值后把该 Provider 标记为暂时不可用，并进入一段冷却时间；冷却期间请求切换到默认或备用 Provider。冷却结束后进入半开状态进行探测，调用成功就恢复，失败则继续熔断。这里的原则是“调用失败不等于缓存失效”，临时故障主要通过重试、监控、熔断和备用 Provider 处理。

<br />

这个地方涉及到llm网关层，我现在的llm注册中心只做了简单的llm封装和调用，并没有做llm负载均衡，熔断灾备以及切换等操作。

## 9. 切换 Provider 后如何保持多轮对话上下文？

**回答：** 上下文不能只放在原 Provider 的会话或 ChatClient 内部，而应该由业务系统保存到数据库或 Redis。结构化输出场景本身是无状态的，每次都会携带完整的 System Prompt、User Prompt 和业务输入，切换后重新发送同一份 Prompt 即可；多轮对话需要根据 sessionId 读取最近 N 轮消息重新组装；历史过长时可以使用“System Prompt + 会话摘要 + 最近几轮对话 + 当前问题”；如果流式回答中途失败，通常丢弃未完成内容，使用备用 Provider 重新生成并记录 fallback。

<br />

多轮上下文不能保存在llm端，本地业务系统中应该保存好上下文，可以多级保存，每次问答的问题和答案都保存一下，然后再维护一个全文摘要。

## 10. 为什么 Embedding Provider 不能随意切换？

**回答：** 不同 Embedding 模型的向量维度和向量空间可能不兼容，因此知识库不能像 Chat 模型一样随意切换备用 Provider。通常需要保持同一个 Embedding Provider；如果必须切换，就需要使用新模型重新完成知识库向量化。

<br />

向量模型不能随意切换是肯定的，因为不同的向量模型 语义和向量之间的对应关系不同，并且维度也可能不同，不能混用。
