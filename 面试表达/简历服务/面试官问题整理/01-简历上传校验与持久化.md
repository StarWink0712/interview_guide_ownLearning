# 简历上传校验与持久化

## 1. 简历服务主要提供哪些能力？

**回答：** 简历服务提供上传与解析、查询全部简历、查看简历详情、异步 AI 评估以及把分析报告导出为 PDF 等能力。核心链路是上传后完成文件校验、去重、Tika 文本提取、RustFS 原件存储、数据库持久化，再通过 Redis Stream 异步调用 LLM。

<br />

简历服务相关的有简历上传和解析，然后调用结构化llm进行评估，生成的评估文本结果和简历id等信息存储到数据库中，只有前端主动查看时才可以看。简历评估是异步服务评估的，先发送到redis stream，然后消费者会监控stream中的区域进行然后用创建守护线程进行处理，同时设置有宕机重处理机制避免消息丢失，redis本地还有消息固化，同时也有重试机制，并且用到了事务消息，当数据库事务提交之后再去发送消息，但是和rocketmq的事务消息不同，rocket是可以主动去数据库中查找的，最后再发送给消费者（回顾复习rocket的事务消息）。

## 2. 上传简历后会不会自动创建面试？

**回答：** 不会。上传简历只会自动创建简历分析任务，先返回 PENDING，后台生成评分和优化建议。只有用户主动选择面试方向、难度、题目数量并点击开始面试后，系统才创建面试会话和个性化题目；面试结束后的综合报告使用另一条 Redis Stream 处理。

当用户上传完简历后，做完一系列的检测之后，然后把简历内容存数据库和rustfs之后，用户创建面试勾选好简历和技能难度等信息之后就会创建会话，会话缓存到redis和数据库中。

## 3. 简历上传接口如何限流？

**回答：** 入口是 `ResumeController.uploadAndAnalyze()`，路径为 `/api/resumes/upload`。Controller 对 GLOBAL 和 IP 两个维度分别限制 5 次，限流通过后才把文件交给 `ResumeUploadService.uploadAndAnalyze()`。

<br />

对简历上传和创建会话等都做了redis限流，核心是用lua脚本的滑动窗口算法，把lua脚本上传到redis中，之后切面层会根据注解信息，根据会话固定前缀做rediskey，redis内部用string当key，滑动窗口计数，先检查当前剩余令牌数是否够用然后检查已经过去的请求归还令牌，够用的话就放行，不够的就返回异常会调用降级方法处理，比如告诉前端稍后再试。

## 4. uploadAndAnalyze 的完整同步流程是什么？

**回答：** 方法先记录开始时间，再校验文件是否为空和是否超过 10MB，使用 Tika 检测真实 MIME 类型，计算 SHA-256 查询重复简历；新文件继续通过 Tika 提取文本，上传原件到 RustFS，保存文件元数据和 `resumeText` 到 PostgreSQL，创建异步任务并向 Redis Stream 投递轻量消息，最后向前端返回 PENDING。

## 5. 简历文件会做哪些基础校验？

**回答：** `FileValidationService` 检查文件是否为空以及大小是否超过 10MB。`ResumeParseService.detectContentType()` 再委托底层类型检测服务读取文件内容，识别真实 MIME 类型，并与配置的允许列表比较，只放行 PDF、Word、Markdown 等支持格式。

## 6. 为什么 MIME 类型不能只信任文件后缀或 HTTP Content-Type？

**回答：** 后缀和请求头都可以被修改，无法证明文件真实格式。系统使用 Apache Tika 根据文件魔数字节检测真实 MIME 类型，再与白名单校验，避免伪装成 PDF 或 Word 的其他文件进入解析链路。

检查文件类型要用tika根据文件魔数字节检测，不能只根据后缀，因为后缀是可以篡改的。

## 7. 简历去重是怎么实现的？

**回答：** `FileHashService` 对文件字节计算 SHA-256 内容指纹，`ResumePersistenceService.findExistingResume()` 再通过 `ResumeRepository` 查询数据库中的 `fileHash`。哈希命中表示文件内容相同，不需要再次解析、上传或调用 LLM。

简历去重是通过hash算法进行去重，通过SHA-256算法，先将文件转为字节数组之后，拿到的是32字节的摘要，然后转换成两位16进制的字符，最终得到64为十六进制字符串，在数据库的resume表中设置唯一hash字段进行问一下校验。知识库去重也是一样的处理。

## 8. 上传重复简历时系统怎么处理？

**回答：** 如果数据库中已经存在相同 SHA-256，系统直接返回历史 AI 分析结果，并把该简历的访问次数加一。前端可以立即看到之前的评分与建议，同时避免重复占用 RustFS、Redis 和模型资源。如果简历上传重复就可以直接给前端弹窗提醒，然后如果要查看简历评估内容就去数据库中找之前已经完成的。但是确定有没有完成评估会先查阅一次简历状态看是不是已经完成了评估。

## 9. 简历文本是怎么解析的？

**回答：** `ResumeParseService.parseResume()` 委托 `DocumentParseService` 使用 Apache Tika 的 `AutoDetectParser` 提取纯文本。解析时禁用嵌入文档，PDF 按位置排序，并限制最大正文长度。扫描版 PDF 没有文本层，如果解析结果为空会直接抛异常，当前需要后续通过 OCR 扩展。

文本解析就用tika的解析器从输入流中检测魔数文件类型和文件内容。

## 10. RustFS 和 PostgreSQL 分别保存什么？

**回答：** RustFS 保存简历原始二进制文件（以字节数组的形式存储），并返回 `fileKey` 和 `fileUrl`；PostgreSQL 的 `ResumeEntity` 保存 SHA-256、原文件名、文件大小、MIME 类型、存储键、访问 URL、Tika 解析出的 `resumeText` 以及分析状态。消费者可以直接从数据库读取文本，用户也可以查看原文。

## 11. 为什么简历解析文本要存入数据库？

**回答：** 对简历来说，文本本身是业务数据：LLM 评分需要把它注入 Prompt，前端可能需要展示简历原文，重新分析时也可以直接读取，避免再次从 RustFS 下载和解析。因此 `ResumeEntity` 专门保留 TEXT 类型的 `resumeText` 字段。文本本身是业务数据，根据简历出题时和简历评估时都可以去数据库中找简历文本内容。

## 12. RustFS 上传成功但数据库入库失败怎么办？

**回答：** 对象存储和数据库不在同一个事务中，数据库失败不能自动回滚 RustFS 对象。因此保存 `ResumeEntity` 失败时会执行补偿逻辑，删除已经上传的原文件，避免产生数据库没有记录但对象存储仍占空间的孤儿文件。

可以先上传对象存储再上传数据库，当数据库事务失败时再通过回调等方式删除rustfs中的数据，因为本来就是先上传rust的，要拿对应的filekey和fileurl。如果rust失败就进行重试，rust不成功也无法存数据库。

## 13. 为什么 Stream 消息不直接携带简历全文？

**回答：** Producer 先通过 `AsyncTaskService` 创建任务记录，消息体只放 `taskId` 和 `resumeId`。简历文本可能很长，放进 Redis Stream 会增加内存和网络开销；消费者根据 resumeId 查询 `ResumeEntity.resumeText`，只有文本缺失时才从 RustFS 下载并重新解析。

## 14. 为什么上传接口只返回 PENDING？

**回答：** LLM 多维度评分耗时不稳定，如果上传接口同步等待，会增加响应时间并容易超时。同步链路只负责把可靠数据和异步任务准备好，投递成功后立即返回 PENDING；前端通过轮询分析状态获取最终报告。
