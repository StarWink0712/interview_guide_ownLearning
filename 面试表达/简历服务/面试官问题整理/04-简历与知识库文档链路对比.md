# 简历与知识库文档链路对比

## 1. 简历上传和知识库上传有哪些共同步骤？

**回答：** 两条链路都经过文件验证、Tika 真实类型检测、SHA-256 哈希去重、Tika 文本解析、RustFS 原文件存储、数据库元数据持久化、Redis Stream 异步任务以及 PENDING 状态返回。共同能力由文件基础设施复用，差异主要在解析文本的角色和异步处理目标。

都需要验证文件大小，hash查重，tika类型检测，原文件存储，数据库元数据存储，知识库还多一个向量化，但是也要用到消息队列异步处理。

## 2. 两个上传接口和限流参数有什么区别？

**回答：** 简历入口是 `ResumeController /api/resumes/upload`，GLOBAL 和 IP 各限制 5 次；知识库入口是 `KnowledgeBaseController /api/knowledgebase/upload`，GLOBAL 和 IP 各限制 3 次。两者分别委托 `ResumeUploadService` 和 `KnowledgeBaseUploadService`。

这限流只是请求的限流，不是llm调用的限流，llm调用的限流可以做一个llm网关来处理。

## 3. 两类文件的大小上限有什么区别？

**回答：** 简历文件上限为 10MB，知识库文档上限为 50MB。知识库可能包含篇幅较长的技术文档，因此允许更大文件；简历通常较小，较低上限也能控制解析和哈希时的内存风险。

## 4. 两条链路是否使用不同的解析器？

**回答：** 业务入口不同，但底层解析能力相同。`ResumeParseService` 和 `KnowledgeBaseParseService` 都委托 `DocumentParseService` 与 `ContentTypeDetectionService`，使用 Apache Tika 完成真实 MIME 检测和正文提取。

## 5. 简历文本和知识库文本最本质的区别是什么？

**回答：** 简历文本是需要长期保留的业务数据，存入 `ResumeEntity.resumeText`，用于 LLM 评分、前端回看和重新分析；知识库文本是生成向量的中间原材料，`KnowledgeBaseEntity` 不设置 content 列，向量化完成后 RAG 主要使用 pgvector 中的文本块和向量。

简历文本会存数据库，而rag的不会，只拆分向量化后将三位一体的 向量，原文，元数据三者存向量数据库。

## 6. 两类原始文件如何保存？

**回答：** 两者原始二进制都保存到 RustFS。简历使用 `storageService.uploadResume()`，知识库使用 `storageService.uploadKnowledgeBase()`；数据库分别保存 fileHash、文件名、分类、storageKey 和 URL 等元数据，便于下载或重新解析。

## 7. 两条异步管道分别是什么？

**回答：** 简历使用 Redis Stream `resume:analyze:stream`，由 `AnalyzeStreamConsumer` 调用 LLM 评分；知识库使用 `knowledgebase:vectorize:stream`，由 `VectorizeStreamConsumer` 执行文本分块、Embedding 和 pgvector 写入。两类任务都采用轻量标识消息和最多 3 次重试。

## 8. 两个消费者如何取得待处理文本？

**回答：** 简历消费者优先读取数据库的 `resumeText`，缺失时才从 RustFS 下载重解析；知识库实体不存 content，因此向量化消费者根据 storageKey 从 RustFS 下载原文件并通过 Tika 重新解析。这个差异来自两种文本的持久化策略。

## 9. 简历异步处理最终做什么？

**回答：** `ResumeGradingService` 把简历文本注入 Prompt，使用 LLM 结构化输出项目经验、技能匹配、内容完整性、结构清晰和表达专业性五维评分，同时生成综合总结、优势和建议，最终保存为 `ResumeAnalysisEntity`。

## 10. 知识库异步处理最终做什么？

**回答：** `KnowledgeBaseVectorService` 先删除旧向量，再用 `TokenTextSplitter` 按标点边界切成约 800 tokens、无重叠的 Document；每块写入 `kb_id`，通过 DashScope Embedding API 生成 1024 维向量，每批最多 10 块，最后写入 Spring AI `PgVectorStore`。

## 11. 两类处理结果分别保存在哪里？

**回答：** 简历结果保存到关系型表 `ResumeAnalysisEntity`，包括 overallScore、scoreDetail、strengths 和 suggestions 等 JSON；知识库结果保存在 pgvector 向量表，每个 chunk 一行，包含原文、1024 维向量和带 `kb_id` 的 metadata。

## 12. 两种存储架构有什么区别？

**回答：** 简历采用关系型存储：`ResumeEntity` 保存元数据和正文，`ResumeAnalysisEntity` 保存分析结果。知识库采用混合存储：`KnowledgeBaseEntity` 只保存元数据和 chunkCount，真正用于检索的文本块与向量保存在 pgvector。

## 13. 两条链路的状态字段分别是什么？

**回答：** 简历使用 `analyzeStatus` 表示 PENDING、PROCESSING、COMPLETED、FAILED；知识库使用 `vectorStatus` 表示相同阶段，并额外保存 `chunkCount` 验证实际生成的向量块数量。两边失败任务最多重试 3 次，超限后标记 FAILED。

## 14. 知识库向量化完成后如何用于 RAG？

**回答：** 用户问题同样通过 Embedding 模型转换为 1024 维向量，`KnowledgeBaseVectorService.similaritySearch()` 在选定知识库范围内使用 COSINE 余弦相似度检索相关 chunk，把命中的文本片段注入 LLM Prompt，生成基于知识库内容的回答。

## 15. 为什么知识库不需要把全文再存一份到关系数据库？

**回答：** 原始文件已经保存在 RustFS，可以在重新向量化时下载解析；日常 RAG 查询使用 pgvector 中的 chunk 和向量，不需要扫描一整列全文。再保存完整 content 会增加数据库空间和数据同步成本，而简历正文需要直接展示和反复作为 LLM 输入，因此适合入库。

## 16. 如何用一句话概括两条链路的差异？

**回答：** 简历上传是“把文本当业务数据”，解析后持久化到关系数据库，再通过 LLM 生成结构化评分报告；知识库上传是“把文本当向量化原材料”，解析后切块生成 1024 维向量写入 pgvector，后续通过余弦相似度支持 RAG 语义检索。
