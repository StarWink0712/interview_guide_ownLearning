## 一、两条链路的完整流程

## 简历上传与 AI 分析

用户上传简历文件后，系统首先通过 `ContentTypeDetectionService` 基于 Apache Tika 检测文件的真实 MIME 类型（读取魔数字节而非信任 HTTP Content-Type），然后计算 SHA-256 哈希检查是否已存在相同文件，若重复则直接返回历史分析结果。新文件通过 `DocumentParseService` 使用 Tika 的 `AutoDetectParser` 提取纯文本（禁用嵌入文档解析、PDF 按位置排序输出、限制最大 5MB），解析后的 `resumeText` 同时存入 RustFS 对象存储和 PostgreSQL 数据库的 `ResumeEntity.resumeText` 列中。接着通过 `AnalyzeStreamProducer` 将任务消息写入 Redis Stream `resume:analyze:stream`，立即返回 PENDING 状态给前端。异步消费者 `AnalyzeStreamConsumer` 从 Stream 拉取消息后，从数据库读取简历文本，调用 `ResumeGradingService` 通过 LLM 执行结构化输出评分——系统 Prompt 和用户 Prompt 从 `resources/prompts/` 的 StringTemplate 模板加载，注入简历全文，LLM 返回包含五维度评分（项目经验 40 分、技能匹配度 20 分、内容完整性 15 分、结构清晰度 15 分、表达专业性 10 分）及综合总结、优势列表、改进建议的结构化 JSON，通过 `StructuredOutputInvoker` 做最多 3 次重试和 JSON 修复后反序列化为 `ResumeAnalysisResponse`，最终持久化到 `ResumeAnalysisEntity` 表，消费者同步更新任务状态为 COMPLETED，用户即可在前端查看完整的简历评分报告。

## 知识库文档上传与向量化

用户上传知识库文档（PDF、Word、Markdown 等）后，系统同样经过 Tika 类型检测和 SHA-256 去重，通过 `DocumentParseService` 提取文本内容。但与简历不同，解析后的文本**不存入数据库**——`KnowledgeBaseEntity` 只保存文件名、文件哈希、分类、RustFS 存储键等元数据，没有 `content` 列。文本通过 `VectorizeStreamProducer` 作为载荷写入 Redis Stream `knowledgebase:vectorize:stream`，消费者 `VectorizeStreamConsumer` 拉取后重新从 RustFS 下载文件并用 Tika 解析（因为 Stream 消息做了轻量化设计，不携带大段文本），然后调用 `KnowledgeBaseVectorService` 执行向量化流程：先用 `TokenTextSplitter` 按标点边界将文本切分为约 800 tokens 的块（无重叠），每块附加 `kb_id` 元数据用于后续过滤；然后通过阿里云 DashScope 的 Embedding API 将每块文本转为 1024 维向量，受 API 限制每批最多 10 个块分批写入 Spring AI 的 `PgVectorStore`（底层为 PostgreSQL 的 pgvector 扩展，采用 COSINE 余弦相似度索引）。向量化完成后更新 `KnowledgeBaseEntity.chunkCount` 记录分块数量，状态标记为 COMPLETED。此后当用户在 RAG 对话中提问时，`KnowledgeBaseVectorService.similaritySearch()` 将问题也转为 1024 维向量，通过 COSINE 相似度在 pgvector 中检索最相关的文本块，将检索结果注入 LLM 的 Prompt 上下文，实现了基于语义的精准知识检索。

```java
public void vectorizeAndStore(Long knowledgeBaseId, String content) {
    // 1. 删除该知识库的旧向量数据
    deleteByKnowledgeBaseId(knowledgeBaseId);
    // 2. TokenTextSplitter 分块（默认约 800 tokens/chunk，基于标点边界，无重叠）
    List<Document> chunks = textSplitter.apply(List.of(new Document(content)));
    // 3. 每个 chunk 添加 metadata: kb_id
    chunks.forEach(chunk -> chunk.getMetadata().put("kb_id", knowledgeBaseId.toString()));
    // 4. 分批向量化（阿里云 DashScope API 限制 batch ≤ 10）
    for (int i = 0; i < batchCount; i++) {
        List<Document> batch = chunks.subList(start, end);
        vectorStore.add(batch);  // Spring AI PgVectorStore
    }
}
```

## 三、流程差异总结

### 解析后文本的用途差异

**简历**：文本是"业务数据"。解析出的 `resumeText` 必须持久化到 `ResumeEntity.resumeText` 列，因为：

- 它被 `ResumeGradingService` 作为 LLM 的输入（Prompt 模板中 `{resumeText}` 变量）
- 用户可能需要查看简历原文
- 重新分析时优先从数据库读取，省去重复下载解析

**知识库**：文本是"中间产物"。解析出的 content 仅在向量化环节使用：

- 传给 `VectorizeStreamProducer` 入队到 Redis Stream
- 消费者从 RustFS 重新下载并解析（因为 Stream 消息做了轻量化，不再携带大段文本）
- 向量化完成后文本没有持久化价值——后续 RAG 查询走的是 pgvector 向量相似度搜索

### 存储方式差异

**简历**：纯关系型存储。`ResumeEntity`（简历元数据+文本）+ `ResumeAnalysisEntity`（AI 分析结果，JSON 字段存 strengths/suggestions），两张 PostgreSQL 表。

**知识库**：混合存储。`KnowledgeBaseEntity`（仅元数据：文件名、哈希、分类、存储键等）+ pgvector 向量表（分词后的向量嵌入，每 chunk 一行，带 `kb_id` metadata 用于过滤）。

### 后续处理差异

**简历**：调用 LLM 做结构化输出——根据 Prompt 模板对简历文本进行多维度评分（内容完整性、结构清晰度、技能匹配度、表达专业性、项目经验），输出 `ResumeAnalysisResponse`（总分 + 分项分 + 总结 + 优点列表 + 改进建议列表）。

**知识库**：不调用 LLM，而是调用 Embedding API 将文本块转为 1024 维向量，通过 `TokenTextSplitter`（基于标点边界，默认 800 tokens/chunk，无重叠）分块后分批写入 pgvector（每批最多 10 个，受阿里云 DashScope API 限制）。向量化完成后该知识库即可被 RAG 查询使用（`KnowledgeBaseVectorService.similaritySearch()` 执行 COSINE 相似度检索）。

两者有本质区别，虽然都用 Tika 解析文件，但**解析后的用途、存储方式、后续处理完全不同**。

## 核心区别：文本的"角色"不同

### 简历：文本是"业务数据"，需要持久化

```java
// ResumeUploadService：解析后文本存入数据库
String resumeText = parseService.parseResume(file);
savedResume = persistenceService.saveResume(file, resumeText, ...);  // ← resumeText 入库
```

简历文本必须入库，因为：

1. **LLM 评分需要它**——`ResumeGradingService` 从数据库读 `resumeText` 作为 Prompt 输入，做 5 维度打分（内容完整性、结构清晰度、技能匹配度、表达专业性、项目经验）
2. **用户可能回看**——前端展示简历原文和评分详情
3. **避免重复解析**——再次分析时直接从数据库读，不需要重新下载文件

### 知识库：文本是"中间产物"，用完即弃

```java
// KnowledgeBaseUploadService：解析后文本不存数据库
String content = parseService.parseContent(file);
savedKb = persistenceService.saveKnowledgeBase(file, name, category, ...);  // ← content 不入库
vectorizeStreamProducer.sendVectorizeTask(savedKb.getId(), content);        // ← 直接传给向量化任务
```

知识库文本不入库，因为：

1. **它只用于生成向量**——分块后用 Embedding API 转成 1024 维向量，存到 pgvector
2. **RAG 查询走向量**——用户问问题时，系统不搜原文而是做 COSINE 相似度检索，返回最相关的文本块
3. **原文从 RustFS 重新读**——异步消费者处理时，从对象存储下载原文件重新用 Tika 解析

## 存储架构对比

```
简历上传链路：
  MultipartFile
      │
      ▼  Tika 解析
  resumeText ──────────────→ ResumeEntity.resumeText (PostgreSQL TEXT 列)
      │
      ▼  异步 LLM 评分
  ResumeAnalysisEntity (PostgreSQL)
      ├── overallScore
      ├── scoreDetail (JSON)
      ├── strengths (JSON)
      └── suggestions (JSON)

知识库文档上传链路：
  MultipartFile
      │
      ▼  Tika 解析
  content ──→ Redis Stream ──→ 异步消费者
      │                            │
      │ 不存数据库                   ▼  TokenTextSplitter 分块
      │                        chunks[0..N] (每块约 800 tokens)
      │                            │
      │                            ▼  Embedding API
      │                        1024 维向量 × N
      │                            │
      │                            ▼  PgVectorStore.add()
      │                        pgvector 表 (COSINE 索引)
      │
  KnowledgeBaseEntity (PostgreSQL)
      ├── fileName, fileHash, category
      ├── storageKey (RustFS 路径)
      └── chunkCount (向量块数量)
      └── 没有 content 字段！
```

## 一句话总结

> 简历上传是**把文本当数据**——解析后持久化到关系型数据库，再用 LLM 打分生成结构化评分报告。知识库上传是**把文本当原材料**——解析后立即向量化为 1024 维嵌入，存入 pgvector 向量库，原文本身不保留在数据库中，后续 RAG 检索走的是向量相似度而非关键词匹配。
