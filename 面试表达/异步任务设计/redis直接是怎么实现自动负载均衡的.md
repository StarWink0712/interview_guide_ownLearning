Redis Stream 的负载均衡是通过原生的**消费者组**机制实现的，不需要业务代码做任何分配逻辑。一条 Stream（比如 `voice:evaluate:stream`）里存着所有消息，每条消息只有一个 messageId 和一份数据。在这个 Stream 之上可以创建多个消费者组，每个消费者组维护独立的消费进度（`last_delivered_id`），组与组之间互不影响，所以同一条消息可以被"简历评估组"和"语音评估组"各自消费一次。同一个消费者组内可以有多个消费者实例（比如部署了两个 pod），Redis 通过 `XREADGROUP` 命令将消息分发给组内消费者，每条消息只会投递到其中一个实例，不会重复投递，这就是负载均衡的核心——多个实例抢着消费，Redis 保证一人一条不打架。消费者拿到消息处理完后调 `XACK` 确认，消息从 PEL（Pending Entries List）中移除。如果某个消费者拿到消息后还没来得及 ACK 就挂了，这条消息会一直躺在 PEL 里，其他消费者可以通过 `XCLAIM` 命令把超时未确认的消息抢过来重新处理，实现故障转移和消息不丢。Stream 本身还有 `MAXLEN ~1000` 的自动裁剪机制，超过约 1000 条后最旧的消息会被自动删除，防止无限膨胀。所以整个链路就是：生产者 `XADD` 入队 → 消费者组 `XREADGROUP` 竞争消费 → 处理完 `XACK` 确认 → 超时未确认的被其他消费者 `XCLAIM` 兜底回收，整个过程由 Redis 服务端保证分发和可靠性，应用层只需要关心业务处理逻辑。
