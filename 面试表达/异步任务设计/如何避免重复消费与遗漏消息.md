消息重复消费的问题有很多，要从不同的源头进行控制。
比如生产者可能会多发消息，消费者也可以多次重复消费。

为了避免消息重复消费，在异步任务服务力，创建异步任务时，就会先从数据库中以任务类型，任务id加活跃状态查询，看是否已经存在已有的任务，如果以有的话，就直接返回已经有的任务，这样就可以避免生产者重复生成消息。比如用户先后上传了同一个简历两次，数据库里面用唯一键约束，就可以确保同一份简历在活跃状态下，只能有一个消息记录。

<br />

消费端的防重复消费，我设计了幂等性，第一层是处理前，拿到消息后，从中拿到简历id，然后去数据库中找简历实体，如果不存在就跑车异常，标记为任务取消后，ack消息，不重试也不报错。第二道防线是 处理消息业务前，先检查一下任务的状态，如果是已经完成了，就不再处理，标记是已经处理，并且分析结果表中也有对应的分析结果。

<br />

还有一个问题就是，如果消费者的消费线程在处理消息业务时，是先把任务状态更新成正在处理中的，然后执行业务，再标记为完成，最后ack消息，但是有可能jvm在处理完消息之后，还没有来得及ack消息，jvm宕机了，所以重启系统之后，PendingMessageRecoveryService 定时任务触发60s 会从PEL中检测留存的未ack的消息，会重新调用这个消息，重新进行消费，然后会再去结果表中，找，看之前有没有完成过简历解析，结果如果存在就表明这个是已经处理了。从pel中移除即可。

<br />

```
JVM 崩溃（msg1 在执行 processBusiness，未 ACK）
    │
    ▼
重启 → @EventListener 触发 recoverPendingMessages()
    │
    ├── XAUTOCLAIM 认领 msg1（空闲超过 60 秒）
    │
    └── processMessage(msg1) 重新执行
          │
          ├── markProcessing() → 更新状态
          ├── processBusiness()
          │     ├── 查简历实体 → 存在 ✅
          │     └── 查是否已完成 → 上次 JVM 崩在 processBusiness 之前，analyzeStatus != COMPLETED
          │       → 重新调用 LLM 分析 ✅
          │
          └── 本次成功 → markCompleted + ACK
```

消费丢失问题：消费丢失可能出现在多个环节，比如生产者发送给redis时失败，redis还没有持久化就宕机了，consumer消费的时候出现异常以及宕机，这三种情况。

对于第一种生产者端的情况，我设计了，先事务提交，再发送消息给redis，如果发送失败了，就会抛出异常，补货异常后，将数据库中的任务状态改成failed，这样之后可以用脚本自动实现有限次数的重试，如果多次重试都失败，可以人工介入，考虑是不是网络问题等情况。在consumer段，拉取消息后，消息并不会删除的，而是进入到pel列表中，只有显示ack后，才会把消息从pel中移除，但是消息始终都在stream中的固定的位置，因为是顺序消费的，所以不会重复消费（并且通过投递记录，记录进入过pel的，避免重复消费）中间失败了有重试机制进行处理，最终成功的话，才会进行ack。消息只有堆积到达到最大长度时，才会移除最初的一些消息，还有一个兜底机制，避免消息一直遗留在pel中，即pendingMessagRecovery服务，定时检测pel中遗漏的消息，进行重新消费，先去结果表检测一下是否已经完成，完成了就直接从pel中移除，没有完成就用检查的调度线程直接处理，不会再交给消费者线程 。

可以这样总结，面试里直接说这一段就很完整：

我在项目里把 Redis Stream 定位成**异步任务的分发通道**，而不是唯一的数据事实来源，真正的任务状态以数据库任务表为准。比如简历分析、知识库向量化、AI 评估这些任务，创建时会先在数据库里生成一条任务记录，保存 `taskId`、业务 ID、状态、重试次数等信息，然后再把 `taskId` 投递到 Redis Stream。如果投递 Redis 失败，不能直接认为业务失败，而是把任务标记成 `ENQUEUE_FAILED` 或待重试状态，后续由补偿任务重新投递；如果数据库提交成功后服务还没来得及投递 Redis 就宕机，也可以通过定时扫描长时间处于 `PENDING` 的任务来恢复。Redis 端即使开启 AOF、主从或哨兵，也只能降低消息丢失概率，不能完全保证刚写入但未持久化的消息不丢，所以我用数据库任务表兜底。消费端使用 Redis Stream 的 Consumer Group，消费者通过 `XREADGROUP` 拉取消息后，消息会进入 PEL，不会立刻删除，只有业务处理成功并更新数据库任务状态后才 `XACK`；如果消费者处理中异常或宕机，消息会留在 PEL，之后由 `PendingMessageRecovery` 定时扫描超时未 ACK 的消息并重新领取处理。需要注意 Redis Stream 是 at-least-once 语义，不是 exactly-once，所以异常恢复或补偿重投时可能重复消费，因此消费者必须通过 `taskId`、任务状态机、重试次数和唯一约束做幂等判断：已经成功的任务直接 ACK 跳过，未超时的处理中任务不重复处理，超时或待重试任务才重新执行，重新执行是由检查pel的调度线程直接消费处理，不会再让消费者线程来处理，也不是重新投递给stream。这样整体上就是：数据库保证任务最终可恢复，Redis Stream 负责异步分发，PEL 和补偿机制解决消费中断，幂等机制解决重复投递。
