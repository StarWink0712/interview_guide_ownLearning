# 消费者与线程模型

## 面试官可能问：Redis Stream 消费者是怎么设计的？

消费者通过一个父类模版，各个子类继承这个模版。父类需要引入redisservice服务，然后单线程消费者线程池服务。通过postconstruct注解，当springboot启动后，该模版bean完成依赖注入后，会创建消费者线程，名称是消费者业务前缀+八位uuid，然后创建一个单线程守护线程的线程池，这个单线程守护线程就作为消费者线程。线程池设置：核心线程数量是1，最大线程数量是1，队列设置为无限队列，拒绝策略是直接抛异常。

## 面试官可能问：消费者完整的消息处理流程是什么？

然后就启动消费循环：先在redisStream中创建消费者组，以streamkey名称和消费者组名称，然后进行消息消费循环。在消息消费循环中，会不断的从stream中拉取消息并处理，拉取到之后消息就被记入PEL中了。拉取到一个消息后，调用processMessage方法，进行解析。如果消息中有traceid，就先存入当前线程的MDC，这样后续的日志log.info中都会带上这个id，然后解析业务暑假，把payload的map形式转换成业务对象，比如任务id，消息id，重试次数这些信息解析出来，之后就是执行业务流程，标记数据库中任务状态为处理中，然后处理中的任务数+1，即记录一下指标，然后调用processBusiness执行具体的业务，传入payload，之后完成后打印日志，更新数据中任务状态为已完成，最后ack消息，如果任务出错，比如llm调用超时，网络异常，数据库写入失败等，就判断一下重试次数有没有超过最大重试次数，如果没有，就把消息重新发回给stream，并把重试次数+1，重新消费，到达上下的话就抛出异常，数据库中标记一下，后续人工处理。然后如果处理的过程中宕机了，重启后，就通过PendingMessageRecoveryService处理遗留在pel中的消息。

## 面试官可能问：Stream 中没有消息时，消费者会不会退出？

**消费者不会因为 Stream 为空就退出。** 它一直处于"阻塞等待 → 超时 → 重新阻塞等待"的循环中，直到有消息进来立刻处理。

## 面试官可能问：为什么消费者线程要设置成守护线程？

消费者线程设为守护线程，主要是防止死循环阻塞 JVM 退出。

消费循环是一个 `while(running)` 死循环，每次拉取消息用的是 Redis 阻塞读取（`XREADGROUP BLOCK`），线程大部分时间都卡在等待消息上。

正常关闭时，`@PreDestroy` 会先设置 `running.set(false)`，再调用 `executorService.shutdown()`，线程能安全退出。但如果关闭过程中出现意外——比如线程正卡在 Redis 阻塞读取、shutdown 没能让它及时退出——非守护线程会让 JVM 认为"还有工作没做完"，一直挂着不退出。而守护线程不存在这个问题，JVM 在非守护线程全部结束后直接退出，不管守护线程跑没跑完。

异常崩溃（kill -9 / OOMKilled）下两者都会被强制终止，之后启动时由 `PendingMessageRecoveryService` 恢复 PEL 中残留的消息。所以守护线程本质上是一个保险：在最坏情况下保证进程不会卡着退不出来。

## 面试官可能问：executorService.shutdown() 能不能立即停止消费线程？

`executorService.shutdown()` 不是强制杀线程，它只是**拒绝接收新任务 + 等待当前任务自然结束**。

***

## shutdown 的实际行为

```
shutdown()
  ├── ① 标记线程池为关闭状态，拒绝新任务提交
  └── ② 等待所有正在执行的任务自己跑完

当前任务（consumeLoop）：
  while(running.get()) {
      stream.readGroup(...)  ← 线程卡在这里，阻塞等待 Redis 返回消息
                                blockTimeoutMs = 5000ms（5秒超时）
  }
```

`running.get()` 已经是 false 了，但线程正卡在 `readGroup` 这个阻塞调用里，还没回到 while 判断那一行，所以**最早也要等 5 秒超时后才能退出**。

5 秒其实无所谓，问题在于极端情况——比如网络抖动导致阻塞读取一直没有超时返回，线程就永远退不出来。

***

## 如果是守护线程

JVM 不管这个线程有没有跑完，其他非守护线程都结束了就直接退出，5 秒都不用等。
