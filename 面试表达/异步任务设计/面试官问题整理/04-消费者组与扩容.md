# 消费者组与扩容

## 面试官可能问：项目中 Stream、消费者组和消费者实例是怎么对应的？

```
Redis Stream 管道              消费者组                   消费者实例
─────────────────             ──────────                ──────────
knowledgebase:vectorize:stream → vectorize-group    → vectorize-consumer-a3f2b01c
resume:analyze:stream          → analyze-group      → analyze-consumer-8e1d9f4a
interview:evaluate:stream      → evaluate-group     → evaluate-consumer-c7b3a5d2
voice:evaluate:stream          → voice-eval-group   → voice-evaluate-consumer-f6a2d01e
```

我项目里每类异步任务使用一个 Redis Stream，例如简历分析 Stream。Stream 中的每条消息会保存消息 ID，以及业务字段，比如简历 ID、任务 ID、用户 ID 等。每个 Stream 对应一个消费者组，消费者组下面可以有一个或多个消费者。

## 面试官可能问：为什么当前每个任务管道只使用一个单线程消费者？

在我当前项目里，每个任务管道只有一个消费者组，并且默认只有一个消费者线程顺序消费。因为简历解析、向量化、AI 评估都属于低频慢任务，一个任务可能需要几十秒，主要瓶颈在 AI 调用和文件处理，不是消息队列吞吐。所以单线程消费已经够用，也能减少并发处理带来的任务状态竞争问题。

## 面试官可能问：业务量变大后如何扩容？

如果后续业务量变大，扩展方式不是为同一个任务创建多个消费者组，因为多个消费者组会各自消费一遍消息，导致重复处理。正确方式是在同一个消费者组下增加多个消费者，比如部署多个服务实例，每个实例使用不同的 consumer name。Redis Stream 会把同一消费者组内的新消息分配给其中一个消费者，实现负载均衡。

但 Redis Stream 是 at-least-once 语义，不是 exactly-once。消费者处理成功但 ACK 前宕机时，消息可能被重新投递，所以我还需要通过 taskId、任务状态机、重试次数来保证幂等，避免重复处理造成数据错误，即数据库中存的是有任务的状态的，重复消费那里讲解的有。

## 面试官可能问：能不能通过增加消费者组提高同一个业务的吞吐量？

消费者组扩容问题

不可以。两个消费者组会**各自独立消费同一批消息**，导致一个任务被重复执行两次。

## 消费者组的本质

Redis Stream 的消费者组之间**完全独立，互不影响**：

```
Stream: resume:analyze
  msg1  msg2  msg3  msg4  ...

同一个消费者组内的多个消费者（竞争模式）
┌─────────────────────────────┐
│  Consumer Group: analyze    │
│  ├── 实例A → 拿到 msg1       │  msg1 只被组内一个消费者处理
│  ├── 实例B → 拿到 msg2       │
│  └── 实例C → 拿到 msg3       │
└─────────────────────────────┘

不同消费者组（广播模式）
┌─────────────────────────────┐
│  Consumer Group: analyze    │
│  └── msg1, msg2, msg3...    │ → 全部消息
└─────────────────────────────┘
┌─────────────────────────────┐
│  Consumer Group: analyze-2  │
│  └── msg1, msg2, msg3...    │ → 同样的全部消息，再跑一遍
└─────────────────────────────┘
```

同一条消息在两个组里各有一份独立进度，互不知晓，结果就是：简历 123 被 AI 分析了两次，浪费一次 LLM 调用成本。

## 面试官可能问：正确的扩展方式是什么？多消费者组适合什么场景？

## 正确的扩展方式

```
扩展 = 同一组内加消费者（多实例）
分组 = 不同组读同一 Stream 做不同的事（多用途）

正确：                          错误：
Group: analyze                  Group: analyze
  ├── 实例A（单线程）              └── 单线程
  ├── 实例B（单线程）            Group: analyze-2
  └── 实例C（单线程）              └── 单线程  ← 重复消费
```

多组可以用在**不同用途**上，比如：

```
Stream: resume:analyze
  ├── Group: analyze     → 调用 LLM 分析简历
  └── Group: audit-log   → 记录审计日志（只读不处理业务）
```

一个是业务处理，一个是旁路审计，各读各的、互不干扰。但如果两个组都是做简历分析，那就是重复执行了。

## 面试官可能问：多实例部署具体是什么样的？

对，就是同一套 Spring Boot 应用部署了三台服务器（或三个容器、三个 Pod）。

## 部署示意

```
┌─────────────────┐   ┌─────────────────┐   ┌─────────────────┐
│  实例 A          │   │  实例 B          │   │  实例 C          │
│  IP: 10.0.1.5   │   │  IP: 10.0.1.6   │   │  IP: 10.0.1.7   │
│                 │   │                 │   │                 │
│  AnalyzeConsumer│   │  AnalyzeConsumer│   │  AnalyzeConsumer│
│  (单线程)        │   │  (单线程)        │   │  (单线程)        │
│  ↓              │   │  ↓              │   │  ↓              │
└──────┬──────────┘   └──────┬──────────┘   └──────┬──────────┘
       │                     │                     │
       └─────────────────────┼─────────────────────┘
                             │
                    ┌────────┴────────┐
                    │   同一个 Redis    │
                    │                 │
                    │  Stream:         │
                    │  resume:analyze  │
                    │                 │
                    │  Consumer Group: │
                    │  analyze-group   │
                    │                 │
                    │  msg1 → 实例A    │
                    │  msg2 → 实例B    │
                    │  msg3 → 实例C    │
                    │  msg4 → 实例A    │
                    │  ...            │
                    └─────────────────┘
```

三台机器各自跑一个单线程消费者，Redis 消费者组保证同一条消息不会被两个实例同时拿走。想提吞吐量就加机器，不用改代码。
