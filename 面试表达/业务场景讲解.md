# AI 面试平台业务场景讲解

这份文档解决一个核心问题：在 Java 开发工程师面试中，怎么把这个项目的业务场景讲清楚。

面试时不要一开口就堆技术栈，比如“我用了 Spring Boot、Redis、pgvector、Spring AI”。更好的讲法是：先让面试官听懂这个系统解决什么问题、谁在用、完整业务流程是什么，再把技术设计自然带出来。

## 1. 一句话定位

推荐这样讲：

> 这是一个面向求职者和面试训练场景的 AI 面试辅助平台，围绕“简历分析、针对岗位的模拟面试、知识库答疑、语音面试和面试日程管理”形成一套从面试准备到复盘提升的闭环系统。

更口语一点：

> 简单说，它不是单纯的简历 CRUD，也不是一个只会调大模型的聊天页面，而是把求职者面试前、面试中、面试后的几个关键动作串起来：先分析简历，再按岗位生成面试问题，面试过程中记录和追问，结束后生成评估报告，最后通过知识库和历史记录帮助用户补短板。

## 2. 面试中最推荐的主线

最稳的主线是“求职者面试准备闭环”。

不要同时展开太多用户角色。虽然这个系统也可以服务 HR、培训机构、老师，但 Java 面试里讲太散会显得业务边界不清。建议先以求职者为核心用户来讲：

1. 用户上传自己的简历。
2. 系统解析简历内容，识别项目经历、技术栈、工作经历和风险点。
3. 用户选择目标岗位、面试方向或上传 JD。
4. 系统基于简历、岗位和 Skill 题库生成模拟面试问题。
5. 用户进行文字或语音模拟面试。
6. 系统记录问答过程，进行 AI 评分和能力维度分析。
7. 用户查看报告，定位薄弱点。
8. 用户把资料、八股文、项目文档上传到知识库，用 RAG 问答补充学习。
9. 如果用户有真实面试邀请，系统可以解析邀请信息并放入日程提醒。

这条线讲顺之后，项目的业务场景就很完整了。

## 3. 30 秒版本

如果面试官让你“简单介绍一下项目”，可以这样说：

> 我做的是一个 AI 面试辅助平台，核心业务是帮助求职者完成面试准备闭环。用户先上传简历，系统会解析简历并进行 AI 分析；然后用户可以选择 Java 后端、系统设计、算法等方向进行模拟面试，系统根据简历和岗位生成问题，并在用户回答后做评分和报告生成。项目还支持知识库 RAG 问答，用户可以上传学习资料或项目文档进行检索增强问答；另外也做了语音面试、面试日程管理、多模型配置和异步任务监控。后端上主要关注文件解析、异步任务、Redis Stream、向量检索、LLM 调用可靠性、WebSocket 实时语音和统一异常响应这些工程问题。

这个版本适合开场，不要讲太久，等面试官追问。

## 4. 2 分钟版本

如果面试官愿意听你展开，可以这样讲：

> 这个项目的业务背景是，很多求职者准备面试时会遇到几个问题：简历不知道哪里薄弱，面试问题和目标岗位不匹配，练习后没有系统化反馈，学习资料也比较分散。所以我把它设计成一个面试准备闭环平台。
>
> 第一块是简历管理。用户上传 PDF、DOCX 或 TXT 简历，系统会做文件校验、内容解析、文本清洗、对象存储上传和内容哈希去重，然后异步触发 AI 分析，生成简历评分和改进建议。
>
> 第二块是模拟面试。用户可以选择面试方向，比如 Java 后端、系统设计、算法或者大厂专项，也可以结合 JD 和简历上下文生成问题。面试过程中系统会记录每轮问答，支持追问、历史题去重，结束后异步生成评估报告。
>
> 第三块是知识库 RAG。用户可以上传项目文档、学习笔记或岗位资料，系统会分块、向量化并存入 pgvector，后续问答时通过向量检索召回相关内容，再交给大模型生成回答。
>
> 第四块是语音面试和日程管理。语音面试通过 WebSocket 传输音频，结合 ASR、LLM、TTS 做实时交互；日程管理用于解析真实面试邀请，提取公司、岗位、时间和会议链接。
>
> 从 Java 后端角度看，这个项目不是简单调用大模型，而是把文件处理、异步任务、缓存限流、向量检索、实时通信、统一异常和监控这些后端能力组合到一个完整业务场景里。

## 5. 5 分钟深挖版本

如果面试官问“你具体负责了什么”或者“业务流程怎么走”，可以按这个顺序讲。

### 5.1 业务背景

求职者准备技术面试时，通常有四类痛点：

1. 简历质量不可控：项目经历写得是否清楚、技术栈是否匹配岗位、有没有明显风险点，用户自己很难判断。
2. 练习不够贴近岗位：普通题库只能刷题，无法结合用户简历、目标岗位和真实 JD。
3. 反馈不系统：练完一场面试后，用户需要知道自己在基础知识、项目表达、系统设计、沟通表达上的问题。
4. 学习资料分散：简历、项目文档、八股文、公司 JD、面试记录分散在不同地方，复习效率低。

这个项目就是围绕这些痛点，把“简历分析 -> 模拟面试 -> 评估报告 -> 知识库补弱 -> 日程提醒”串成闭环。

### 5.2 核心用户

主用户可以这样定义：

- 求职者：用来分析简历、练习面试、查看反馈、管理真实面试安排。
- 培训机构或老师：用来批量辅助学生做简历诊断和面试训练。
- HR 或面试辅导人员：可以把它作为候选人筛选和面试准备辅助工具。

面试时建议优先讲“求职者”，因为这个角色最容易形成完整闭环。

### 5.3 核心业务闭环

```text
上传简历
-> 解析与清洗
-> AI 简历分析
-> 选择目标岗位 / Skill / JD
-> 生成模拟面试问题
-> 文字或语音面试
-> 回答评估与报告导出
-> 知识库补充学习
-> 面试日程管理
-> 下一轮练习迭代
```

这条链路很重要。只要你把这条链路讲顺，面试官就能听懂项目不是拼功能，而是围绕一个真实业务问题做系统设计。

## 6. 各模块应该怎么讲

### 6.1 简历管理模块

业务上解决什么：

> 用户上传简历后，系统自动解析内容，分析简历和目标岗位的匹配程度，给出评分、风险点和优化建议。

后端上可以展开什么：

- 文件上传：处理 PDF、DOCX、TXT 等格式。
- 文件校验：大小、类型、空文件、不支持格式。
- 文本解析：用 Tika 提取文本，再做清洗和截断。
- 去重：通过内容哈希避免重复上传。
- 对象存储：原始文件上传到 S3 兼容存储。
- 异步分析：简历上传后不阻塞等待 AI，投递 Redis Stream 任务。
- 结果落库：AI 分析结果保存到数据库，前端可查询进度和历史。

可以这样说：

> 简历模块不是简单保存文件。我把它拆成上传、校验、解析、存储、持久化和 AI 分析几个步骤。上传完成后先保存基础信息，再通过 Redis Stream 异步分析，避免用户接口长时间阻塞，也方便失败重试和状态跟踪。

### 6.2 模拟面试模块

业务上解决什么：

> 用户可以选择面试方向或目标岗位，系统生成贴近岗位和简历的问题，并根据用户回答生成多维度评估报告。

后端上可以展开什么：

- Skill 驱动出题：不同方向有不同题库和考察重点。
- JD 与简历上下文：让问题更贴近用户目标。
- 历史题去重：避免同一用户反复遇到同样问题。
- 多轮追问：模拟真实面试官深挖项目。
- 统一评估：文字面试和语音面试共用评估逻辑。
- 报告导出：评估结果可以异步生成 PDF。

可以这样说：

> 模拟面试模块的核心不是随机出题，而是根据用户选择的面试方向、目标岗位、简历内容和历史记录生成问题。面试结束后，系统会从技术准确性、表达完整度、项目深度和岗位匹配度等维度做评估。

### 6.3 知识库 RAG 模块

业务上解决什么：

> 用户可以把项目文档、学习资料、岗位 JD 或面试笔记上传到知识库，后续通过问答方式快速检索和学习。

后端上可以展开什么：

- 文档上传和解析。
- 文本分块。
- 向量化任务异步处理。
- pgvector 存储向量。
- 相似度检索召回上下文。
- SSE 流式返回回答。
- 会话管理和历史记录。

可以这样说：

> RAG 模块解决的是“大模型不知道用户私有资料”的问题。用户上传资料后，系统会先解析文档并分块，再异步向量化存入 pgvector。用户提问时，系统先做向量检索，把相关片段作为上下文交给大模型生成答案。

### 6.4 面试日程模块

业务上解决什么：

> 用户收到真实面试邀请后，可以让系统解析邀请内容，自动提取公司、岗位、时间、会议链接，并进入日历管理。

后端上可以展开什么：

- 规则解析 + AI 解析双方案。
- 日程状态流转：待面试、已完成、已取消、已过期。
- 定时任务自动处理过期日程。
- 日历视图和列表视图。

可以这样说：

> 日程模块看起来是 CRUD，但它有真实业务价值：把求职者的面试安排和训练系统接起来。用户不是孤立地练习，而是围绕真实面试节点做准备。

### 6.5 语音面试模块

业务上解决什么：

> 文字面试偏静态，语音面试更接近真实面试场景，可以训练用户的口头表达、临场反应和多轮沟通能力。

后端上可以展开什么：

- WebSocket 实时连接。
- 音频流上传。
- ASR 语音识别。
- LLM 生成面试官回复。
- TTS 语音合成。
- 多轮上下文管理。
- 暂停、恢复、结束和评估。

可以这样说：

> 语音面试模块的难点在实时交互链路。前端采集音频后通过 WebSocket 发送给后端，后端做 ASR 转写，再把文本和上下文交给 LLM 生成回复，最后通过 TTS 合成语音返回前端。这里要处理连接状态、音频延迟、上下文记录和会话生命周期。

### 6.6 多模型配置与监控模块

业务上解决什么：

> 不同用户或环境可能使用不同大模型服务，所以系统提供 Provider 配置、默认模型切换和 AI 调用观测能力。

后端上可以展开什么：

- 多 Provider 注册。
- 默认模型配置。
- API Key 安全保存。
- AI 调用日志。
- 异步任务状态查询。
- 业务指标监控。

可以这样说：

> 我没有把模型配置写死在代码里，而是抽象成 Provider。业务服务只关心获取 ChatClient，具体用 DashScope、DeepSeek、Kimi 还是本地 LM Studio，由配置决定，这样后续扩展模型比较方便。

## 7. 业务场景和技术点怎么对应

面试官最喜欢问“为什么这么设计”。你可以用下面这张表来回答：

| 业务问题 | 技术设计 | 回答重点 |
| --- | --- | --- |
| 简历和知识库文件可能很大，解析耗时 | 文件校验 + Tika 解析 + 对象存储 | 不能只保存 MultipartFile，要考虑格式、大小、清洗和原文件存储 |
| AI 分析耗时且可能失败 | Redis Stream 异步任务 | 不阻塞用户请求，支持状态跟踪、重试和失败处理 |
| 用户重复上传同一份简历 | 内容哈希去重 | 节省存储和 AI 调用成本 |
| 问答需要结合用户私有资料 | RAG + pgvector | 先检索相关文档片段，再让大模型生成回答 |
| 面试问题要贴近岗位 | Skill + JD + 简历上下文 | 不是随机题库，而是个性化出题 |
| 模拟面试需要多轮上下文 | 会话表 + Redis 缓存 | 管理当前会话状态和历史问答 |
| 语音面试要实时交互 | WebSocket + ASR + LLM + TTS | 处理音频流、字幕、AI 回复和播放 |
| 接口要防刷 | `@RateLimit` + Redis Lua | 滑动窗口限流，按 IP/用户/全局多个维度 |
| 大模型服务不稳定 | 结构化输出重试 + 降级 | 保证 JSON 输出可解析，失败时有兜底 |
| 多模型供应商切换 | LlmProviderRegistry | 业务层不绑定具体模型厂商 |

## 8. 推荐回答结构

以后面试官问“介绍一下你的项目”，你可以按这个结构走：

1. 项目定位：这是一个 AI 面试辅助平台。
2. 业务痛点：求职者简历诊断、面试练习、反馈复盘和资料学习是割裂的。
3. 业务闭环：简历上传 -> AI 分析 -> 模拟面试 -> 评估报告 -> 知识库补弱 -> 日程管理。
4. 你负责的模块：挑 2 到 3 个讲深，不要所有模块平均用力。
5. 技术难点：异步任务、RAG、LLM 稳定性、语音 WebSocket、统一异常和限流。
6. 结果和收获：系统把传统 Java 后端能力和 AI 应用场景结合起来。

可以背这个版本：

> 这个项目我一般按业务闭环来介绍。它面向的是准备技术面试的求职者，核心问题是简历分析、面试练习、反馈复盘和学习资料管理比较分散。所以我把系统设计成几个模块：用户先上传简历，系统解析文件并异步做 AI 分析；然后用户选择目标岗位或 Skill 方向进行模拟面试，系统结合简历、JD 和历史记录生成问题；面试结束后生成结构化评估报告；如果用户想补弱，可以把学习资料上传到知识库，通过 RAG 问答学习；真实面试邀请也可以进入日程模块管理。技术上，我重点处理了文件解析与对象存储、Redis Stream 异步任务、pgvector 向量检索、Spring AI 调用、多 Provider 配置、WebSocket 语音交互和统一异常限流这些问题。

## 9. 哪些内容不要一上来讲

不要这样开场：

> 我这个项目用了 Spring Boot 4、Java 21、Redis、PostgreSQL、pgvector、Spring AI、React、WebSocket、Tika、iText。

这种讲法的问题是：面试官听到的是技术清单，但不知道业务价值。

也不要这样讲：

> 这是一个 AI 项目，可以进行简历分析、模拟面试、知识库、语音面试、日程管理、模型配置、监控。

这种讲法像功能菜单，没有主线。

更好的方式是：

> 这个项目围绕求职者面试准备的完整流程来做，从简历诊断到模拟面试，再到报告复盘和知识库补弱。每个模块都对应一个具体业务节点。

## 10. 面试官可能追问的问题

### 问：这个项目的核心业务价值是什么？

答：

> 核心价值是把求职者面试准备过程闭环化。传统方式下，简历修改、刷题、模拟面试、复盘和资料查询是分散的。这个系统把简历、岗位、面试问题、回答记录、评估报告和知识库连接起来，让用户能围绕目标岗位持续迭代。

### 问：为什么要做知识库？直接问大模型不行吗？

答：

> 直接问大模型只能得到通用回答，无法结合用户自己的项目文档、简历内容和学习资料。知识库模块通过 RAG 先检索用户私有资料，再把相关内容放进上下文，回答会更贴近用户自己的项目和目标岗位。

### 问：为什么简历分析要异步？

答：

> 简历分析涉及文件解析、外部 AI 调用和结果结构化，耗时不可控，也可能失败。如果同步处理，上传接口会很慢，用户体验差。异步后，上传接口只负责保存文件和创建任务，AI 分析由 Redis Stream 消费者处理，前端可以查询任务状态，失败也能重试。

### 问：Redis 在这个项目里具体做什么？

答：

> Redis 有三类用途。第一是缓存面试会话状态，减少数据库频繁读写；第二是做接口限流，用 Lua 脚本保证滑动窗口计数的原子性；第三是用 Redis Stream 承载简历分析、知识库向量化、面试评估这类异步任务。

### 问：你这个项目和普通 CRUD 项目区别在哪里？

答：

> CRUD 只是基础。这个项目更像一个业务流程型系统：有文件上传和对象存储，有外部 AI 调用，有耗时任务和失败重试，有向量检索，有实时语音通信，也有统一异常、限流、监控和多模型配置。它考察的不只是增删改查，而是如何把多个后端能力组合到一个真实业务闭环里。

### 问：你会重点讲哪个模块？

推荐回答：

> 我会重点讲三个模块：简历分析、模拟面试和知识库 RAG。因为这三个模块能形成最清楚的业务闭环，也最能体现 Java 后端能力。语音面试和多模型配置可以作为扩展亮点来讲。

## 11. 你自己可以选择的重点模块

如果面试时间有限，不要平均讲所有模块。建议按下面优先级选择：

1. 简历分析模块：最容易讲清楚文件处理、异步任务、AI 调用和业务价值。
2. 模拟面试模块：最贴合项目主题，可以讲出题、追问、评估和报告。
3. 知识库 RAG 模块：最能体现 AI 项目特色，可以讲 pgvector、向量检索和 SSE。
4. Redis 限流与异步任务：最像 Java 后端高频考点。
5. 语音面试模块：作为亮点，但不要一开始就讲太深，除非面试官对实时通信感兴趣。

## 12. 最终推荐讲稿

下面是一段可以直接练习的完整讲稿：

> 我这个项目是一个 AI 面试辅助平台，主要面向准备技术面试的求职者。它解决的问题是，求职者在准备面试时，简历分析、岗位匹配、模拟面试、反馈复盘和资料学习通常是割裂的，所以我把系统设计成一个从面试准备到复盘提升的闭环。
>
> 业务流程上，用户先上传简历，系统会做文件校验、解析、清洗、对象存储和内容哈希去重，然后异步调用 AI 生成简历分析结果。接着用户可以选择 Java 后端、系统设计、算法等 Skill 方向，或者结合目标岗位 JD 进行模拟面试。系统会根据用户简历、岗位方向和历史题目生成问题，面试过程中支持多轮追问，结束后生成结构化评估报告。用户如果想针对薄弱点学习，可以把项目文档和学习资料上传到知识库，系统通过文档分块、向量化和 pgvector 检索实现 RAG 问答。除此之外，项目还支持语音面试和面试日程管理，让用户可以更接近真实面试场景。
>
> 从后端角度看，我重点关注的是这些业务背后的工程问题：文件解析和对象存储怎么做得可靠，AI 调用这种耗时任务怎么异步化，Redis Stream 怎么做任务投递、ACK 和失败重试，知识库怎么做向量检索，语音面试怎么通过 WebSocket 管理实时会话，以及系统怎么统一异常、限流和模型 Provider 配置。我的理解是，这个项目的价值不在于简单调用大模型，而是把传统 Java 后端能力和 AI 应用场景结合起来，形成一个完整可用的业务系统。

## 13. 一句话提醒

面试时记住这个顺序：

```text
先讲用户和痛点
再讲业务闭环
再讲你负责的模块
最后讲技术设计和难点
```

只要顺序对了，这个项目就会从“技术堆料”变成“有业务、有架构、有后端深度”的项目。
