# RAG 效果评估与准确性保障

这份文档重点回答以下面试问题：

- RAG 有没有评估效果？
- 如何确保检索准确性？
- TopK 取多少，依据是什么？
- Chunk 多大，为什么这样设置？
- 命中率是多少，如何评估？
- 如何处理大模型幻觉？
- 回答能不能引用来源？
- AI 找不到答案时如何降级？
- 当前项目哪些已经实现，哪些还没有实现？

## 1. 先给出真实结论

当前项目已经实现了一个 **RAG 评测最小闭环**，不是完全没有评估。

已经实现：

- RAG 离线评测集、评测用例和评测运行。
- 使用相同问题对比不同 `topK` 和 `minScore` 参数。
- 通过期望关键词判断检索结果是否命中。
- 统计关键词命中用例数、返回 chunk 数量和平均检索延迟。
- 记录线上 RAG Trace，包括原问题、改写问题、命中 chunk、score 和耗时。
- 记录 Query Rewrite、检索、回答生成阶段的 Micrometer 指标。
- 无检索结果时返回固定的“未找到相关信息”响应。
- Prompt 约束模型只能根据知识库内容回答。
- Prompt Injection 防护。

部分实现：

- 检索准确性评估：目前只做了“关键词是否出现在召回 chunk 中”的最小评估。
- 幻觉治理：目前主要依靠检索阈值、Prompt 约束和无结果拒答。
- 来源追踪：后台 Trace 能看到命中的知识库 ID、chunk、score 和 metadata，但最终用户回答中没有返回引用来源。
- 降级处理：已有 Query Rewrite 失败回退、无结果固定响应、流式错误响应，但还没有完整的多级检索降级策略。

尚未实现：

- 基于人工标注相关 chunk 的 `Precision@K`、`Recall@K`、MRR、nDCG。
- 对最终答案的正确性、相关性和忠实度评估。
- LLM-as-a-Judge 或人工评审流程。
- 真正的 BM25/关键词检索 + 向量检索混合召回。
- rerank 重排序。
- 最终回答的引用来源展示和引用正确性校验。
- 无答案问题的拒答准确率评测。
- 当前仓库中没有固定评测集的真实基线结果，因此不能直接说“当前命中率达到 90%”。

面试时推荐这样总结：

> 当前项目已经有一个可运行的 RAG 评测中心，可以用评测集比较不同 TopK 和 minScore 策略的关键词命中率和检索延迟，也有线上 RAG Trace 查看每次召回的 chunk 和 score。不过目前属于最小评测版本，主要评估检索召回，没有完整评估最终答案的正确性和忠实度，也还没有 rerank、引用来源和用户级权限过滤。下一步我会完善人工标注数据集，增加 Recall@K、Precision@K、答案忠实度和拒答准确率。

## 2. 当前项目的评估系统

项目中已经存在 `RagEvaluationService`，并且前端有 `RagEvalPage` 评测页面。

核心代码：

| 能力 | 代码位置 |
| --- | --- |
| RAG 评测服务 | `RagEvaluationService` |
| 评测集 | `RagEvalDatasetEntity` |
| 评测用例 | `RagEvalCaseEntity` |
| 评测运行 | `RagEvalRunEntity` |
| 单用例结果 | `RagEvalRunCaseResultEntity` |
| 评测 API | `AiObservabilityController` |

### 2.1 当前评测用例包含什么

每条评测用例包含：

```text
question
knowledgeBaseIds
expectedKeywords
```

示例：

```text
question:
Spring Boot 自动配置是什么？

knowledgeBaseIds:
[10]

expectedKeywords:
["自动配置", "classpath", "Bean"]
```

### 2.2 当前评测怎么运行

评测执行时：

1. 根据问题和知识库 ID 调用 `KnowledgeBaseVectorService.similaritySearch()`。
2. 使用指定的 `topK` 和 `minScore`。
3. 把召回的所有 chunk 文本拼接起来。
4. 使用大小写不敏感的 `String.contains()` 判断期望关键词是否存在。
5. 只要至少命中一个期望关键词，该用例就标记为命中。
6. 记录召回数量、关键词命中数量和检索耗时。
7. 汇总所有用例的命中率和平均延迟。

当前前端显示的命中率公式是：

```text
关键词命中率 = matchedCases / totalCases
```

### 2.3 当前评测指标准确代表什么

当前的“命中率”代表：

> 有多少评测问题，在召回的 chunk 中至少出现了一个期望关键词。

它可以用于：

- 快速验证知识库是否能召回目标内容。
- 对比不同 TopK 的效果。
- 对比不同 minScore 的效果。
- 作为代码改动后的回归测试。
- 发现某些问题完全检索不到内容。

它不能代表：

- 最终回答是否正确。
- 最终回答是否存在幻觉。
- 召回的所有 chunk 是否都相关。
- 是否召回了全部相关 chunk。
- 关键词虽然出现，但语义是否真的相关。
- 模型是否正确使用了召回内容。

所以面试时不能直接说：

> 我的 RAG 准确率是 90%。

更准确的说法是：

> 当前评测中心统计的是检索阶段的关键词命中率，不是最终回答准确率。它适合做最小回归评测，下一步需要补充人工标注的相关 chunk、标准答案和不可回答问题，才能评估 Recall@K、Precision@K、答案正确性和拒答准确率。

## 3. 如何确保检索准确性

检索准确性不能靠某一个参数保证，需要从数据、分块、检索、过滤、排序和评测多个环节共同治理。

当前项目已采用的方式：

1. 文件解析后做文本清洗，减少噪声。
2. 使用 TokenTextSplitter 分块。
3. 使用 Embedding 向量检索。
4. pgvector 使用 HNSW 和余弦距离。
5. 使用 Query Rewrite 改写短问题和追问。
6. 改写问题检索失败时，使用原问题再次检索。
7. 根据问题长度动态调整 TopK 和 minScore。
8. 通过知识库 ID 限定检索范围。
9. 记录每次命中的 chunk、score 和耗时。
10. 使用离线评测集比较参数策略。

仍需补强的方式：

1. 建立人工标注的相关 chunk 数据集。
2. 增加 BM25/全文索引，与向量检索组成混合检索。
3. 对初步召回结果增加 rerank。
4. 丰富 chunk metadata，例如文件名、页码、标题和 chunkIndex。
5. 根据文档类型使用不同分块策略。
6. 增加线上用户反馈，例如“有帮助/无帮助”。
7. 对零命中率、低 score 命中率和用户重问率设置告警。

推荐面试回答：

> 我不会说通过某一个 TopK 就能确保准确性。检索准确性是一个系统问题。当前项目从文本清洗、Query Rewrite、动态 TopK、相似度阈值、知识库范围过滤和离线评测几个方面控制质量。线上还记录每次召回 chunk 和 score，出现问题时可以追溯。生产化下一步会补充人工标注数据集、混合检索和 rerank。

## 4. TopK 应该取多少

### 4.1 TopK 是什么

TopK 表示向量检索时最多返回多少个相关 chunk。

TopK 太小：

- 可能漏掉真正相关的内容。
- 多段信息无法同时召回。
- 对复杂问题和跨章节问题不友好。

TopK 太大：

- 引入更多无关内容。
- Prompt 变长，增加 token 成本。
- 可能干扰模型，让回答更不稳定。
- 检索和生成延迟增加。

### 4.2 当前项目怎么设置

当前项目不是固定 TopK，而是根据问题长度动态设置：

| 问题类型 | 判断规则 | TopK | minScore |
| --- | --- | --- | --- |
| 短查询 | 去掉空白后长度 `<= 4` | 20 | 0.18 |
| 中等查询 | 长度 `<= 12` | 12 | 0.28 |
| 长查询 | 长度 `> 12` | 8 | 0.28 |

设计思路：

- 短问题语义不足，放宽召回范围，避免完全召回不到。
- 长问题语义更明确，减少召回数量，降低噪声。

需要诚实说明：

> 当前这些参数属于合理经验值和启发式策略，项目还没有通过固定真实评测集证明它们是最优参数。

### 4.3 TopK 应该如何通过评测确定

推荐建立同一套固定评测集，然后进行网格对比：

```text
TopK:
3, 5, 8, 12, 20

minScore:
0.18, 0.22, 0.28, 0.35, 0.45

Query Rewrite:
开启 / 关闭
```

每种组合至少记录：

- 关键词命中率。
- Recall@K。
- Precision@K。
- 平均检索延迟。
- 平均召回 chunk 数。
- 最终 Prompt token 数。
- 最终答案正确率。
- 最终答案忠实度。

选择 TopK 时，不是选择命中率最高的最大值，而是选择综合效果最好的拐点：

```text
在 Recall@K 足够高的前提下，
选择 Precision@K、生成质量、延迟和成本更好的最小 K。
```

示例：

| TopK | Recall@K | Precision@K | 答案正确率 | 平均延迟 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 3 | 72% | 80% | 70% | 80ms | 召回不足 |
| 5 | 86% | 72% | 84% | 95ms | 较好 |
| 8 | 93% | 61% | 89% | 115ms | 综合较优 |
| 12 | 95% | 45% | 88% | 150ms | 噪声增加 |
| 20 | 97% | 31% | 84% | 220ms | 成本和噪声过高 |

上表只是评测方法示例，不是当前项目真实数据。

推荐面试回答：

> 当前项目根据问题长度动态使用 TopK 20、12、8，这是一个经验策略。真正确定 TopK 时，我会在固定评测集上对 TopK 3、5、8、12、20 做对比，观察 Recall@K、Precision@K、答案正确率、延迟和 token 成本，选择综合收益出现拐点的位置，而不是直接取越大越好。

## 5. Chunk 多大，为什么

### 5.1 当前项目设置

当前项目使用：

```text
TokenTextSplitter.builder().build()
```

代码注释将默认分块描述为：

```text
每个 chunk 约 800 tokens
按标点边界切分
无显式重叠
```

需要注意：

> 当前实现依赖 TokenTextSplitter 的默认参数，没有在项目配置中显式声明 chunk size，也没有保存一份对不同 chunk 大小的真实评测结果。

因此面试时可以说当前采用约 800 tokens 的默认分块作为第一版，但不能说它已经被证明是最佳值。

### 5.2 Chunk 太大或太小的问题

Chunk 太小：

- 容易破坏完整语义。
- 问题和答案可能被切到两个 chunk。
- 需要召回更多 chunk 才能回答。
- 上下文拼接碎片化。

Chunk 太大：

- 一个 chunk 中包含多个主题。
- 向量表示会变得平均化，检索不精准。
- 召回后引入大量无关内容。
- Prompt token 成本增加。

### 5.3 应该如何确定 Chunk 大小

Chunk 大小需要根据文档类型决定。

| 文档类型 | 推荐起始策略 |
| --- | --- |
| FAQ、问答对 | 每个问答作为一个 chunk |
| 技术文档 | 按标题和段落切分，约 400-800 tokens |
| 代码文档 | 按类、方法、代码块切分 |
| PDF 教材 | 按章节、标题、段落切分，保留页码 |
| 表格 | 按表格整体或逻辑行分块 |
| 简短规章制度 | 可使用较大 chunk，避免规则被切断 |

建议实验：

```text
Chunk size:
300, 500, 800, 1200 tokens

Overlap:
0, 50, 100 tokens
```

评测每种组合的：

- Recall@K。
- Precision@K。
- 关键词命中率。
- 最终答案正确率。
- Prompt token 数。
- 平均检索和生成延迟。

推荐面试回答：

> 当前项目第一版使用 TokenTextSplitter 默认配置，代码注释里约 800 tokens，没有显式 overlap。这个值是工程起点，不是最终最优值。生产中我会按文档类型做语义分块，并在固定评测集上比较 300、500、800、1200 tokens 和不同 overlap，选择召回质量、语义完整性和 token 成本综合最好的方案。

## 6. 命中率怎么样，怎么评估

### 6.1 当前项目能不能回答真实命中率

当前仓库中能看到：

- RAG 评测框架。
- 评测页面。
- 评测服务单元测试。
- 关键词命中率计算逻辑。

但当前仓库没有：

- 固定的真实评测集内容。
- 已保存的真实评测运行数据。
- 一个可对外声称的基线命中率数字。

因此目前正确回答是：

> 项目已经具备测命中率的能力，但仓库里没有一份权威的真实评测集和基线结果，所以我不会直接声称命中率达到多少。下一步需要建立固定评测集，跑出可复现的 baseline。

### 6.2 当前命中率公式的局限

当前逻辑：

```text
召回结果中出现至少一个 expectedKeyword
-> 该用例命中
```

局限：

- 只命中一个宽泛关键词也会被判断成功。
- 关键词出现不代表语义相关。
- 同义词没有命中会被判断失败。
- 无法判断召回排序是否合理。
- 无法判断最终回答是否正确。

### 6.3 推荐补充的检索指标

#### Recall@K

```text
Recall@K = TopK 中召回的相关 chunk 数 / 所有应召回相关 chunk 数
```

用于回答：

> 真正相关的内容有没有被检索出来？

#### Precision@K

```text
Precision@K = TopK 中相关 chunk 数 / TopK 返回 chunk 数
```

用于回答：

> 返回的 chunk 中有多少是真正相关的？

#### MRR

```text
MRR = 第一个相关结果排名的倒数平均值
```

用于回答：

> 最相关内容是否排在前面？

#### nDCG

用于评估：

> 多个不同相关程度的 chunk，排序是否合理？

#### Empty Result Rate

```text
零命中率 = 无召回结果的查询数 / 总查询数
```

当前项目已有 `app.rag.no_result.count` 指标，可用于观测零命中情况。

### 6.4 推荐补充的生成指标

#### Answer Correctness

最终回答和标准答案是否一致。

#### Answer Relevance

最终回答是否真正回答了用户问题。

#### Faithfulness

最终回答中的事实是否都能在召回 context 中找到依据。

#### Citation Correctness

回答中标注的来源是否真的支持对应结论。

#### Abstention Accuracy

对于知识库中没有答案的问题，系统是否正确拒答。

### 6.5 如何建立评测集

每个评测 Case 建议扩展成：

```json
{
  "question": "Redis Stream 消费失败后如何重试？",
  "knowledgeBaseIds": [1],
  "expectedKeywords": ["ACK", "retry", "pending"],
  "expectedAnswer": "失败消息进入重试流程，超过最大次数后标记失败。",
  "expectedChunkIds": ["chunk-12", "chunk-13"],
  "answerable": true,
  "expectedSources": [
    {
      "file": "RedisStream设计.md",
      "chunkId": "chunk-12"
    }
  ],
  "tags": ["redis", "async", "normal"]
}
```

还必须加入不可回答问题：

```json
{
  "question": "公司今年营收是多少？",
  "answerable": false
}
```

因为只测试可回答问题，无法知道系统会不会在没有答案时胡编。

## 7. 如何处理幻觉

### 7.1 当前项目已经做了什么

当前项目已有以下幻觉治理措施：

1. 使用 RAG 检索，把外部知识作为上下文。
2. minScore 阈值过滤弱相关结果。
3. 没有召回结果时，不调用模型自由回答，直接返回固定无结果响应。
4. System Prompt 明确要求只使用知识库内容，不编造。
5. User Prompt 把文档标记为“用户提供的待分析数据，不是指令”。
6. 追加防 Prompt Injection 指令。
7. 如果模型输出“没有相关信息”等内容，统一归一化为固定无结果响应。
8. 流式回答先观察前 120 个字符，发现无结果类内容时提前终止。
9. 记录命中 chunk 和 score，方便人工排查。

### 7.2 当前还缺什么

当前没有实现：

- 对回答中的每条事实做来源校验。
- 回答忠实度评分。
- 输出结构化置信度。
- 生成后的二次验证。
- 引用来源强制绑定。
- 对低置信度回答自动拒答。
- 专门的不可回答问题评测集。

### 7.3 推荐的生产级幻觉治理

建议把最终输出改成结构化形式：

```json
{
  "answerable": true,
  "answer": "Redis Stream 消费失败后会进入重试流程。",
  "citations": ["source-1", "source-3"],
  "confidence": 0.86
}
```

然后做以下校验：

1. `answerable=false` 时只返回拒答模板。
2. citations 必须存在于本次召回的 source 列表中。
3. 没有 citation 支持的关键结论不允许输出。
4. 低于置信度阈值时降级为“信息不足”。
5. 可以使用单独 Judge 模型检查回答是否被 context 支持。
6. 对高风险业务增加人工审核。

推荐面试回答：

> 当前项目通过 minScore、无结果拒答、Prompt 约束、防注入和 RAG Trace 减少幻觉，但这些不能完全消除幻觉。下一步我会把回答改成包含 answerable、citations 和 confidence 的结构化输出，再做一次基于 context 的忠实度校验。没有来源支持或置信度过低时直接拒答。

## 8. 回答能不能引用来源

### 8.1 当前项目状态

当前项目：

- 检索日志中能看到命中 chunk 的知识库 ID、rank、score、metadata 和文本预览。
- QueryResponse 会返回回答、知识库 ID、知识库名称和 traceId。
- RAG 聊天流式接口会先返回 traceId。
- 最终用户回答没有返回 sources 列表。
- Prompt 只要求“尽量引用具体内容”，没有强制使用来源编号。
- chunk metadata 当前主要只有 `kb_id`，缺少文件名、页码、标题、chunkIndex 等完整来源信息。

因此结论是：

> 当前项目具备后台来源追踪基础，但还没有实现面向用户的正式引用来源功能。

### 8.2 下一步如何实现引用来源

第一步：丰富 chunk metadata。

建议至少保存：

```text
kb_id
source_file
source_title
page_number
section_title
chunk_index
storage_url
```

第二步：定义来源 DTO。

```java
public record RagSourceDTO(
    String sourceId,
    Long knowledgeBaseId,
    String fileName,
    Integer pageNumber,
    String sectionTitle,
    Integer chunkIndex,
    Double score,
    String preview
) {}
```

第三步：同步响应返回 sources。

```java
public record QueryResponse(
    String answer,
    Long knowledgeBaseId,
    String knowledgeBaseName,
    String traceId,
    List<RagSourceDTO> sources
) {}
```

第四步：流式回答发送 sources 事件。

```text
event: trace
data: {"traceId":"..."}

event: sources
data: [{"sourceId":"S1","fileName":"Redis.md","pageNumber":3}]

event: message
data: 回答内容...
```

第五步：Prompt 要求引用来源。

```text
每个关键结论后标注来源编号，例如 [S1]、[S2]。
不得引用本次 sources 列表中不存在的编号。
```

第六步：后端验证引用。

- 提取回答中的 `[S1]`、`[S2]`。
- 检查这些来源是否在本次检索结果中。
- 不存在的引用删除或触发重新生成。

推荐面试回答：

> 当前项目后台 Trace 已经能看到命中的 chunk 和 score，但最终回答还没有正式返回引用来源。下一步我会给 chunk 增加文件名、页码、标题和 chunkIndex metadata，把 sources 和 answer 一起返回；流式接口先发 sources 事件，再输出回答，并要求模型使用 [S1] 这种编号引用，最后由后端校验引用是否真实存在。

## 9. AI 找不到答案时如何降级

### 9.1 当前项目已有降级

当前已经实现：

1. Query Rewrite 失败时，回退使用原问题。
2. 改写问题没有有效命中时，尝试使用原问题检索。
3. VectorStore 前置知识库过滤失败时，回退为扩大召回后在 Java 内存过滤。
4. 没有检索结果时，直接返回固定无结果响应。
5. 模型返回无信息类内容时，归一化为固定无结果响应。
6. 流式回答失败时，返回明确错误提示。
7. RAG Trace 和日志写入失败时，不影响主业务。

当前固定无结果响应：

```text
抱歉，在选定的知识库中未检索到相关信息。请换一个更具体的关键词或补充上下文后再试。
```

### 9.2 推荐的多级降级策略

建议设计为：

```text
Level 1：正常向量检索
Query Rewrite + 标准 TopK + 标准 minScore

Level 2：检索重试
使用原问题重试

Level 3：受控放宽
适当提高 TopK，适当降低 minScore，但不能低于安全下限

Level 4：混合检索兜底
向量检索无结果时，使用 BM25/全文索引查精确关键词

Level 5：澄清问题
让用户补充关键词、文档范围或上下文

Level 6：明确拒答
返回“知识库中没有找到答案”，绝不让模型自由编造

Level 7：可选外部检索
只有用户明确允许，并且业务允许时，才切换到联网搜索或通用模型回答，
同时明确标记答案不来自内部知识库
```

注意：

- 降低 minScore 必须有下限，否则容易召回大量无关内容并加剧幻觉。
- 外部搜索不能悄悄启用，必须让用户知道来源发生变化。
- 对企业内部知识库，宁可拒答，也不能把外部模型常识伪装成内部事实。

推荐面试回答：

> 当前项目已有 Query Rewrite 回退、原问题重试和无结果固定响应。生产级我会设计成多级降级：先正常检索，再用原问题重试，然后在安全范围内适当扩大 TopK 或降低阈值，再尝试混合检索；仍没有结果就让用户补充问题或明确拒答。不会让模型在没有知识库证据时自由回答。

## 10. 下一步改进计划

### P0：先建立可信基线

目标：回答“当前效果到底怎么样”。

需要做：

1. 建立固定评测集，至少 100 条问题。
2. 每条用例增加 `expectedAnswer`。
3. 每条用例增加 `expectedChunkIds`。
4. 增加至少 20% 的不可回答问题。
5. 记录当前默认策略的 baseline。
6. 将评测结果导出为固定报告。

验收指标建议：

```text
Recall@8 >= 85%
Precision@8 >= 55%
不可回答问题正确拒答率 >= 90%
P95 检索延迟 <= 300ms
```

这些数字是下一步目标建议，不是当前项目真实结果。

### P1：完善参数实验

目标：用数据决定 TopK、minScore 和 Chunk。

需要做：

1. 对比 TopK：3、5、8、12、20。
2. 对比 minScore：0.18、0.22、0.28、0.35、0.45。
3. 对比 Chunk：300、500、800、1200 tokens。
4. 对比 overlap：0、50、100 tokens。
5. 对比 Query Rewrite 开启和关闭。
6. 把 strategy 扩展为包含 chunkSize、overlap、rewriteEnabled。

最终选择：

> 不是选择单项命中率最高的方案，而是选择召回、精确率、最终答案、延迟和成本综合最好的方案。

### P1：实现用户可见来源引用

目标：提高可信度和可解释性。

需要做：

1. chunk metadata 增加文件名、页码、标题、chunkIndex。
2. 新增 `RagSourceDTO`。
3. `QueryResponse` 返回 sources。
4. SSE 增加 sources 事件。
5. Prompt 要求使用 `[S1]` 来源编号。
6. 后端校验引用编号。

### P1：完善幻觉评测

目标：从“检索到了”升级为“回答可信”。

需要做：

1. 增加答案正确性评测。
2. 增加答案相关性评测。
3. 增加 Faithfulness 评测。
4. 增加 Citation Correctness 评测。
5. 增加拒答准确率评测。
6. LLM Judge 不能作为唯一标准，抽样人工复核。

### P2：提升检索效果

目标：改善精确关键词、类名、错误码和专业术语检索。

需要做：

1. 增加 chunk 级全文索引。
2. 实现 BM25/关键词召回。
3. 向量召回和关键词召回并行。
4. 使用 RRF 或加权分数融合。
5. 增加 rerank。

### P2：线上反馈闭环

目标：让真实用户行为反哺评测集。

建议记录：

- 用户是否点赞回答。
- 用户是否重新提问。
- 用户是否点击来源。
- 用户是否复制答案。
- 用户是否在短时间内改写同一个问题。
- 无结果率。
- 低相似度召回率。

把线上失败问题定期加入离线评测集。

> 这个项目不是完全没有 RAG 评估，我实现了一个最小的 RAG 评测中心。可以创建评测集，每条用例包含问题、目标知识库和期望关键词，然后用同一批问题比较不同 TopK 和 minScore 策略。系统会执行向量检索，判断召回的 chunk 是否包含期望关键词，统计关键词命中率、召回 chunk 数量和平均检索延迟。同时线上每次 RAG 查询都有 trace，可以看到原问题、改写问题、命中的 chunk、相似度分数和耗时。
