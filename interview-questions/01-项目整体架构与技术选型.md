# 项目整体架构与技术选型

## 1. 面试官：请用一条完整业务链介绍这个项目，而不是只罗列技术栈。

我的回答：

我的项目是一个覆盖“材料准备、模拟面试、复盘改进”的 AI 面试平台。用户上传简历后，后端先做文件校验、Tika 解析和 S3 兼容存储，再通过 Redis Stream 异步调用大模型评分；开始文字面试时，系统结合简历、技能资料和历史题目生成问题，逐题保存答案并做自适应评估，结束后异步生成报告。知识库模块把文档切块写入 pgvector，为 RAG 对话提供检索上下文；语音模块则以 WebSocket 串联浏览器 PCM、实时 ASR、流式 LLM 和 TTS。这样设计把耗时 AI 工作从同步 CRUD 中拆开，同时保留可恢复的任务状态和持久化结果。

## 2. 面试官：项目为什么采用单体应用按功能分包，而不是一开始拆微服务？

我的回答：

我这里采用的是单模块 Spring Boot、业务模块自包含的模块化单体。简历、面试、知识库、日程、语音各自拥有 Controller、Service、Repository，共享 AI 网关、文件、Redis、异常和观测基础设施。当前团队和业务规模下，这种结构没有服务间网络调用和分布式事务成本，调试、部署也更直接；同时功能边界已经通过包结构和 Service 接口体现，未来若某条链路成为独立容量瓶颈，可以先把 Redis Stream 消费者或语音服务拆出去。当前没有注册中心、服务发现、熔断器或 API Gateway，因此我不会把它描述成微服务架构。

## 3. 面试官：项目的分层如何落地，Controller、Service 和基础设施各承担什么职责？

我的回答：

我的项目总体遵循 Controller 委托、Service 编排、Repository 持久化。Controller 负责参数校验、限流注解和统一 `Result` 返回；Service 组合文件解析、对象存储、数据库与 AI 调用，并把事务写操作下沉到更小的 PersistenceService；Repository 使用 Spring Data JPA。跨模块能力放在 `infrastructure` 和 `common`，例如 Tika、S3、Redis、PDF、LLM Registry。优点是业务入口容易阅读，也能避免在长事务里调用外部服务。不过少数导出接口需要直接返回 `ResponseEntity<byte[]>`，少数大 Service 仍较重，后续还可继续按“外部调用阶段/短事务落库阶段”拆分。

## 4. 面试官：为什么同时使用 PostgreSQL、Redis 和对象存储，数据如何分工？

我的回答：

我把三类存储按数据特征分工：PostgreSQL 保存简历元数据、面试会话、答案、报告、任务和观测明细，pgvector 扩展又承担向量检索；Redis 保存有 TTL 的文字面试会话、滑动窗口限流数据，并用 Stream 传递异步任务；S3 兼容存储保存 PDF、Word 等原始文件。这样不会把大二进制塞进关系库，也不把需要长期审计的数据只放缓存。Redis 不是最终事实源，缓存丢失时可从数据库恢复；Stream 消息只携带业务 ID，消费者再读数据库或对象存储。当前 Compose 都是单节点，生产环境仍需补备份、复制和灾备方案。

## 5. 面试官：Java 21 虚拟线程在项目中解决了什么问题，是否意味着可以无限并发？

我的回答：

我的项目是典型 I/O 密集型：LLM、ASR/TTS、S3、Redis 和数据库都会等待网络，因此在 Spring 配置中开启虚拟线程，并在文字出题和语音流水线中显式使用虚拟线程执行器，降低大量阻塞调用占用平台线程的成本。它改善的是线程等待成本，不会扩大数据库连接池、模型配额或下游吞吐；如果无限提交任务，仍会把压力推给 LLM、Redis 或内存。项目在语音 TTS 上额外用 `Semaphore` 限制单会话并发，但文字出题和整体 AI 调用还缺统一并发舱壁。流量增大时我会增加有界队列、全局并发限制、超时和按 Provider 的隔离策略。

# 本章总结

项目的核心形态是模块化单体：以 Spring Boot 为业务中枢，用 PostgreSQL 保存事实数据、Redis 承担缓存与异步协调、S3 兼容存储承载原始文件，再把文字、RAG 和语音三类 AI 场景组织在统一基础设施之上。

当前架构适合快速迭代和单机部署，但虚拟线程、Redis Stream 与模块边界并不等于已经具备微服务和高可用能力，生产化仍需容量隔离、集群部署和灾备。

# 核心主线

以模块化单体组织业务，用不同存储和异步机制匹配不同数据与耗时任务。
