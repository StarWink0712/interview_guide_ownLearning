# 文字面试与自适应评估

## 1. 面试官：创建一场文字面试时，题目是如何生成并避免重复的？

我的回答：

我的项目先校验同一简历是否已有未完成会话，非强制创建时直接复用提示，随后生成短 UUID 会话号并读取所选技能。出题服务会查询该技能和简历最近最多 60 道历史题，作为排除集合；有简历时按约 60% 简历定制题与剩余技能方向题拆分，两支在虚拟线程中并行调用 plain ChatClient，再合并、去重、补足数量并追加配置的追问。若一支失败就用另一支，全部失败再生成本地兜底题。这样兼顾个性化、覆盖面和可用性，但语义相近题目前主要依靠文本与提示词约束，后续可用向量相似度做更强去重。

## 2. 面试官：技能分类、题目配额和参考资料是如何配合的？

我的回答：

我把技能内容从 Java 代码中移到 `app/src/main/resources/skills`。每个技能目录包含 `SKILL.md`、元数据和 references，`InterviewSkillService` 启动后扫描并缓存，解析分类、分类描述和权重，再按总题数计算各方向配额；`InterviewQuestionService` 针对每个方向选择对应参考资料、历史题与难度，渲染 StringTemplate 提示词并要求结构化输出。这样增加新技术方向主要是扩充资源，而不是修改出题流程。当前技能文件在运行期主要是只读缓存，变更后没有完整的热更新与版本追踪；生产上我会给技能包增加版本、审核和灰度发布。

## 3. 面试官：提交一题答案后，系统内部发生了什么？

我的回答：

我的项目先从 Redis 会话缓存读取当前题，缓存未命中时再从 PostgreSQL 恢复。提交后把答案作为 `InterviewAnswerEntity` 落库，更新当前索引与会话状态，同时同步缓存；之后调用自适应服务对本轮答案评分、更新能力画像并决定是否改变下一题。自适应失败采用安全降级，不阻断答题主流程。若还有题目就返回下一题和即时反馈；若已结束，则把会话标成完成并投递异步报告评估任务。当前缓存更新是读改写，且没有按 sessionId 的分布式锁，重复点击或并发提交可能竞争，后续应加入版本号、唯一约束或原子 Lua。

## 4. 面试官：自适应面试不是简单按分数升降难度，它具体由哪些步骤组成？

我的回答：

我的项目把自适应拆成三步。`TurnEvaluationService` 用 plain ChatClient 和结构化输出评价当前回答的正确性、深度、表达、缺失点等；`AbilityProfileService` 把本轮维度与历史画像做滚动聚合，并合并薄弱关键词；`AdaptiveDecisionService` 再根据题目、评分和画像让模型决定升降难度、追问或保持方向，模型失败时用分数阈值规则兜底。`AdaptiveInterviewService` 负责串联并把画像、决策和 trace JSON 持久化。优点是每步可测试、可解释；限制是能力聚合目前偏启发式，缺少经过标注数据校准的测量模型。

## 5. 面试官：为什么即时评估失败不能让提交答案接口失败？

我的回答：

我把“保存用户答案”视为核心事实，把“即时智能反馈”视为可降级增强。如果模型超时就回滚整次提交，用户会重复作答，还可能制造重复答案，因此答案先持久化，自适应入口 `evaluateAndDecideSafely` 捕获失败、记录日志并返回空结果，主流程仍推进。最终报告又由独立 Stream 任务生成，进一步隔离长耗时。这个选择提升了可用性，但也要求前端区分“本题已保存、反馈暂不可用”，目前反馈失败的重试和补算机制还不完整。后续我会把即时评估也记录为独立子任务，允许后台补偿而不是永久缺失。

## 6. 面试官：文字面试报告如何生成，为什么要分批评估再汇总？

我的回答：

我的项目把题目和答案转换为统一 `QaRecord`，并把技能参考资料作为评分基线交给 `UnifiedEvaluationService`。服务按默认 8 题一批调用模型，得到每题得分、优点、问题和建议，再补齐缺失结果；第二次模型调用负责综合能力维度、总结和总评，若总结失败则用批次结果本地聚合。分批能控制上下文长度，也让文字与语音复用同一评分口径。当前总分聚合对未回答题的处理仍较保守，且模型评分没有人工标注集校准；后续应明确未答题权重、固定 rubric，并用离线评测监控模型版本漂移。

代码依据：

## 7. 面试官：面试会话为什么同时存 Redis 和数据库，二者不一致怎么办？

我的回答：

我这里让 Redis 提供答题过程的低延迟读取和 24 小时 TTL，让 PostgreSQL保存可恢复、可查询的事实记录。读取时先查缓存，缺失则从数据库的 questions JSON、当前索引和状态重建；写入时创建会话会先写缓存再写数据库，数据库异常时当前代码仍可能保留并返回缓存会话，这是明确的一致性窗口。提交答案又涉及答案表、会话表和缓存三处状态，单机正常流程可用，但不是严格原子。后续我会先提交数据库事务，再通过 after-commit 更新/失效缓存，配合版本号和定期对账，避免返回只有缓存、没有数据库的“幽灵会话”。

代码依据：

# 本章总结

文字面试从技能与简历生成题目，经答案持久化、自适应单轮评估，最后进入异步统一报告。局部失败通过兜底题、规则决策和异步报告隔离，不让增强能力破坏核心答题事实。

当前主要工程边界是会话缓存一致性、并发提交和模型评分校准，而不是简单增加更多 Prompt。

# 核心主线

以可恢复会话承载答题事实，用分层模型评估逐轮调整问题并异步生成最终报告。
