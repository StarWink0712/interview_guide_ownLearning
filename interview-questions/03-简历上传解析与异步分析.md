# 简历上传、解析与异步分析

## 1. 面试官：请说明上传一份简历到看到 AI 分析结果的完整流程。

我的回答：

我的项目中，`ResumeController` 接收文件后先由 `FileValidationService` 检查大小和允许类型，再通过 Tika 实际探测内容类型，计算 SHA-256 做重复判断。新文件由 `DocumentParseService` 提取文本、清洗后上传 S3 兼容存储，随后短事务保存简历元数据；上传失败或落库失败会做补偿删除。成功后 `AnalyzeStreamProducer` 创建异步任务并在事务提交后写 Redis Stream。消费者只拿 taskId/resumeId，重新从数据库或对象存储读取正文，调用评分服务并保存分析，前端在简历库查询任务状态和结果。

- `app/src/main/java/interview/guide/modules/resume/service/ResumeUploadService.java`
- `app/src/main/java/interview/guide/modules/resume/listener/AnalyzeStreamProducer.java`
- `app/src/main/java/interview/guide/modules/resume/listener/AnalyzeStreamConsumer.java`

## 2. 面试官：为什么不能只相信扩展名或浏览器传来的 Content-Type？

我的回答：

我这里把客户端 Content-Type 只当作线索，真正校验使用 Apache Tika 基于文件字节探测 MIME，再与 PDF、DOC、DOCX、TXT 白名单比对，同时简历业务单独限制 10MB。这样能阻止把可执行文件改后缀伪装成文档，也避免前端错误标注类型导致解析器走错分支。之后解析同样由 Tika AutoDetectParser 完成，并关闭嵌入文档提取、限制最大文本量，降低压缩炸弹或嵌套内容风险。当前还没有病毒扫描、宏文档隔离和异步沙箱解析，面向公网时我会补 ClamAV、对象隔离区和更严格的解析超时/资源上限。

代码依据：

## 3. 面试官：简历去重为什么用内容哈希，如何处理“同名不同内容”和“不同名同内容”？

我的回答：

我的项目用文件字节的 SHA-256，而不是文件名作为去重键。因此同名但内容不同会生成不同哈希并正常入库，不同文件名但字节完全相同会命中已有简历，避免重复上传、存储和模型评分。哈希在持久化服务查询已有记录时使用，异步任务层又通过业务 ID 和活动状态复用任务，形成两层幂等。这个方案只能识别字节级重复，PDF 元数据变化、重新排版或内容等价但编码不同都会产生新哈希。若要做语义去重，我会在清洗文本后再计算规范化哈希，并把“疑似重复”交给用户确认，而不是直接合并。

## 4. 面试官：为什么 Stream 消息里不直接放完整简历文本？

我的回答：

我这里让 Stream 只传 taskId、resumeId、traceId 等轻量字段，正文已经保存在数据库或对象存储。这样避免大文本占用 Redis 内存、扩大网络复制和消息重试成本，也让消费者重试时始终读取当前持久化状态。生产者在数据库事务提交后才入队，避免消费者先看到消息却读不到实体；消费者还会检查任务取消、实体删除和已完成结果，满足重复投递下的幂等处理。边界是“数据库已提交、进程在 XADD 前崩溃”仍可能留下未入队任务，当前恢复服务只认领已有 Pending 消息，后续应引入 outbox 扫描补投。

## 5. 面试官：简历分析失败时会重试吗？请说明当前实现中的一个真实缺陷。

我的回答：

从异步框架看，消费者抛异常后会重新入队，最多重试三次，最终标记 DEAD_LETTER；但简历链路有一个真实语义缺陷：`ResumeGradingService.analyzeResume` 捕获了大范围异常，并返回零分和错误说明组成的 `ResumeAnalysisResponse`。消费者会把它当作正常结果保存并把任务标记 COMPLETED，因此 LLM 超时等错误可能绕过 Stream 重试。也就是说，框架已经实现重试，当前简历评分却部分削弱了它。我的改进是只对可接受的模型内容做降级，对网络、鉴权和超时抛 `BusinessException`，并区分 FAILED 与“分析完成但质量较低”。

# 本章总结

简历模块把文件安全、文本解析、对象存储、关系数据和异步 AI 分析串成可补偿的流程；内容哈希和任务状态共同承担去重与幂等。

当前最重要的边界是 after-commit 入队并非完整事务消息，以及评分服务吞掉异常会让部分失败被误标为完成。

# 核心主线

先可靠持久化文件与元数据，再用轻量 Stream 消息驱动可追踪的异步分析。
