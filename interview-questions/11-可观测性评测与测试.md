# 可观测性、评测与测试

## 1. 面试官：一次 HTTP 请求的 traceId 如何传播到异步任务？

我的回答：

我的项目在 `TraceIdFilter` 中读取客户端 `X-Trace-Id` 或生成新 UUID，写入响应头和 SLF4J MDC，因此同一同步请求的结构化日志可关联。生产者入队时把当前 traceId 放入 Redis Stream 字段；公共消费者取消息后保存原 MDC、恢复该 traceId，处理完成再清理并还原，避免线程复用造成串号。AI 调用和 RAG 检索日志也保存 traceId，前端 RAG Chat 会先接收一个 trace SSE 事件，便于跳转排查。当前这是轻量关联 ID，不是 OpenTelemetry span，没有跨进程父子层级、采样和自动拓扑。

代码依据：

- `app/src/main/java/interview/guide/common/observability/TraceIdFilter.java`
- `app/src/main/java/interview/guide/common/async/AbstractStreamProducer.java`
- `app/src/main/java/interview/guide/common/async/AbstractStreamConsumer.java`
- `app/src/main/java/interview/guide/modules/knowledgebase/RagChatController.java`
- `frontend/src/api/ragChat.ts`

## 2. 面试官：项目怎样区分“一次业务 AI 调用”和“底层多次 Provider 尝试”？

我的回答：

我的项目用两层观测模型。`AiProviderObservationAdvisor` 包围一次逻辑 ChatClient 调用，创建 invocationId，记录 provider、model、clientVariant、streaming、总耗时和最终状态；底层 RestClient interceptor 或 WebClient filter 每发出一次真实 HTTP 请求就记录 attempt，RetryTemplate 回调再增加重试计数。这样重试两次成功会显示一个成功 invocation、多个 attempt，不会把业务成功率错误计算成三次调用。明细写 PostgreSQL，聚合指标交给 Recorder。当前调用上下文依赖 ThreadLocal，响应式流和虚拟线程切换需要持续测试上下文传播。

代码依据：

- `app/src/main/java/interview/guide/common/ai/AiProviderObservationAdvisor.java`
- `app/src/main/java/interview/guide/common/ai/AiProviderHttpObservationInterceptor.java`
- `app/src/main/java/interview/guide/common/ai/AiProviderWebClientObservationFilter.java`
- `app/src/main/java/interview/guide/common/ai/AiProviderObservationContext.java`
- `app/src/main/java/interview/guide/modules/aiobservability/service/AiProviderObservationLogService.java`

## 3. 面试官：项目已经接入 Prometheus 和 Grafana 了吗？

我的回答：

我的项目当前没有完整实现这一部分。代码已封装 AI、Provider、RAG、异步任务和语音五类 Micrometer Recorder，使用 Counter、Timer、DistributionSummary，并尽量采用 provider、status、stage 等低基数标签；Registry 是可选依赖，缺失时业务静默运行。但 `app/build.gradle` 没有显式引入 Actuator 和 Prometheus registry，`application.yml` 没有 management endpoint，Compose 也没有 Prometheus/Grafana 服务，所以目前只是可对接的埋点基础。后续要补依赖、受保护的 scrape 端点、SLO bucket、采集配置、Dashboard 和告警规则。

## 4. 面试官：管理端业务监控的数据从哪里来，有什么扩展瓶颈？

我的回答：

我的项目提供 `MonitoringController` 和 `BusinessMetricsQueryService`，汇总最近 24 小时的 AI 调用、RAG 检索、异步任务以及语音内存指标，返回调用量、成功率、平均延迟、零命中率和任务状态等摘要。它适合开发期直接查看业务健康，不依赖外部监控平台；AI/RAG 的详细事件又能按 trace 查询。当前部分统计是把时间窗内明细 `findByCreatedAtAfter` 读入 JVM 后求平均，多实例语音内存数据也无法全局合并，大数据量下会慢且口径不一致。后续应改为数据库聚合或时序库查询，并明确窗口、NO_DATA 和多实例汇总语义。

代码依据：

## 5. 面试官：项目的测试为什么同时使用 H2 和 Testcontainers？

我的回答：

我的项目把快速反馈和真实基础设施验证分层。普通 `test` 使用 JUnit 5、Mockito、AssertJ 与 H2，覆盖结构化输出修复、自适应算法、任务状态、上传补偿、监控聚合等，默认排除 `container` 标签；`integrationTest` 继承 `BaseIntegrationTest`，启动真实 pgvector/PostgreSQL、Redis 和 MinIO，验证向量扩展、对象存储、Redis Stream 以及 RAG 集成。H2 启动快但不支持 pgvector、PostgreSQL JSON/锁语义，所以不能替代容器测试；容器测试更真实但慢且依赖 Docker，适合 CI 独立阶段。

- `app/src/test/java/interview/guide/testsupport/PostgresPgvectorIntegrationTest.java`

## 6. 面试官：当前自动化测试最明显的缺口是什么？

我的回答：

我的项目已有较丰富的 Service 单测和基础设施容器测试，但实时语音是明显短板。`VoiceInterviewServiceTest`、暂停恢复、`DashscopeLlmServiceTest`、PromptService 测试整类被 `@Disabled`，原因是重构后构造器或角色 Prompt 已变化；限流真实 Redis 集成测试也默认禁用。这意味着最复杂的 WebSocket 会话生命周期、断线恢复、LLM 流式与并发 TTS 缺少有效回归保障，不能因为测试文件存在就说已覆盖。我的优先级是先恢复这些测试，再用可控 fake ASR/LLM/TTS 做协议级测试，最后补少量真实沙箱端到端冒烟。

# 本章总结

可观测性主线由 traceId、AI 调用/尝试明细、RAG 检索日志和 Micrometer 埋点组成；测试则用快速单测与真实容器测试互补。

当前尚未真正接通 Prometheus/Grafana，业务摘要在大数据和多实例下也有口径问题；语音与限流的禁用测试是最明确的质量缺口。

# 核心主线

用 trace 解释单次问题、用指标发现总体趋势、用分层测试验证确定性逻辑和真实基础设施。
