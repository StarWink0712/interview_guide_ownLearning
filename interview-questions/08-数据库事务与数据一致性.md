# 数据库事务与数据一致性

## 1. 面试官：项目如何避免在数据库事务里调用 LLM 或对象存储？

我的回答：

我的项目把外部 I/O 编排与短事务写入拆开。例如简历上传先校验、解析和上传对象，再调用 `ResumePersistenceService.saveResume` 开启短事务；知识库向量化在事务外请求 embedding，只把删除旧向量和状态更新限制在短写操作；面试评估先调用模型形成 DTO，再由 PersistenceService 保存。这样避免网络调用期间占着数据库连接和锁，也降低超时导致的大事务回滚成本。RAG 评测的 `runDataset` 同样没有包住一个长事务，而是让检索计算与各次仓储写入分离；后续仍应持续审计新增外部调用。

- `app/src/main/java/interview/guide/modules/resume/service/ResumeUploadService.java`
- `app/src/main/java/interview/guide/modules/resume/service/ResumePersistenceService.java`
- `app/src/main/java/interview/guide/modules/knowledgebase/service/KnowledgeBaseVectorService.java`

## 2. 面试官：文件上传和数据库落库无法放在同一事务，项目如何保证一致性？

我的回答：

对象存储不参与 JPA 事务，因此我的项目采用 Saga 式补偿。简历和知识库都会先上传对象，再在短事务中保存元数据；如果落库失败，编排服务捕获异常并删除刚上传的 storageKey，再把原始业务异常向上抛出。删除业务则通常先尝试清理对象，之后删除关系数据。这个方案比假装存在跨资源事务更实际，也有测试验证落库失败时的补偿调用。边界是补偿本身也可能失败，当前主要记录日志，仍会产生孤儿对象；生产上应保存补偿任务、定期扫描未引用对象，并让删除操作可幂等重试。

## 3. 面试官：事务提交后入队解决了什么问题，还剩什么一致性空窗？

我的回答：

我使用 `TransactionAfterCommitExecutor`：存在活动事务时注册 `afterCommit` 回调，只有数据库真正提交后才 XADD；没有事务则立即执行。它解决了“消息先被消费者读到，而业务实体最终回滚或尚不可见”的竞态。生产者和对应测试已覆盖这一语义。但数据库提交与 Redis 写入仍不是原子操作，如果进程恰好在二者之间崩溃，任务表已存在却没有消息；afterCommit 中 XADD 失败也只是日志或状态处理，Pending 恢复无法帮助。完整方案是事务内写 outbox 表，由独立发布器可靠投递，或扫描长期未入队任务补偿。

代码依据：

- `app/src/main/java/interview/guide/common/transaction/TransactionAfterCommitExecutor.java`

- `app/src/main/java/interview/guide/modules/knowledgebase/listener/VectorizeStreamProducer.java`

## 4. 面试官：为什么有些面试字段存 JSON，有些数据单独建表？

我的回答：

我的项目把需要独立查询、排序和生命周期管理的数据规范化，例如面试答案、RAG 消息、异步任务和 Provider 调用明细都有单独实体；而题目列表、最终报告、能力画像和自适应 trace 更像一次会话的聚合快照，当前序列化为 JSON 字符串放在会话表，恢复会话时整体读取。这样开发快、减少多表 join，也保留了报告生成时的原始结构。缺点是数据库难以按某个能力维度检索和约束，JSON 结构升级也要兼容旧数据。若分析需求增多，我会为高频字段建列或子表，并给 JSON 增加 schemaVersion 与迁移策略。

## 5. 面试官：当前系统如何应对重复请求和并发更新，缺少哪些数据库级保护？

我的回答：

我的项目已经在多个层面做幂等：文件内容哈希查重、活动 AsyncTask 复用、消费者检查 COMPLETED、实体删除后取消消息、会话用业务 sessionId 查找。但我没有看到面试会话、RAG messageOrder 等核心并发路径统一使用 `@Version` 乐观锁；部分“先查再写”还依赖应用逻辑，若两个请求同时到达，可能重复提交答案、生成相同序号或覆盖缓存。流量增大时我会先补数据库唯一约束和幂等键，再为聚合根加版本字段，捕获冲突后返回已处理结果；只有极少数强互斥流程才使用 Redis 锁。

# 本章总结

项目没有追求跨 PostgreSQL、Redis、对象存储的伪原子事务，而是通过短事务、补偿、after-commit 和消费幂等构造最终一致性。

下一阶段应把隐含的一致性假设固化为数据库约束、版本控制、outbox 和可重试补偿任务。

# 核心主线

让数据库事务只保护本地事实，再用补偿与幂等连接外部存储和异步消息。
