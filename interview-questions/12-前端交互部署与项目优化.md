# 前端交互、部署与项目优化

## 1. 面试官：前端如何适配后端统一 Result，文件下载和流式接口为何例外？

我的回答：

我的项目前端用 Axios 实例统一 baseURL、超时和响应拦截：后端 HTTP 200 返回的 `Result` 若 code 为 200 就解包 data，否则抛出 message，页面只处理业务对象；上传单独设 5 分钟超时。文件下载需要 Blob 和响应头，因此可取得原始 Axios 实例；SSE 则必须读取浏览器 `ReadableStream`，使用 fetch 手工解析 event/data，不能经过会等待完整响应的通用 Axios 包装。这样普通 API 代码简洁，特殊协议仍保留控制力。代价是两套错误解析逻辑可能漂移，后续应抽出统一错误转换和 SSE parser。

代码依据：

- `frontend/src/api/request.ts`
- `frontend/src/api/knowledgebase.ts`
- `frontend/src/api/ragChat.ts`
- `frontend/src/api/resume.ts`

## 2. 面试官：前端如何处理 RAG SSE 的正文、换行和 trace 事件？

我的回答：

我的项目使用 POST 发送问题，因此不能直接用只支持 GET 的原生 EventSource，而是 fetch 后循环 `reader.read()`，用 TextDecoder 处理跨 chunk 缓冲。知识库单问答提取每个 `data:` 行并保留空行；RAG Chat 按空行切 event block，识别服务端先发送的 `event: trace`，解析 traceId 供管理端排查，普通 message 再恢复转义换行并追加到页面。这个实现已经处理了网络分块不等于消息边界的问题，但没有自动重连、Last-Event-ID 和统一取消控制。后续可封装 AbortController、超时和标准 SSE 解析库。

代码依据：

- `frontend/src/api/knowledgebase.ts`
- `frontend/src/api/ragChat.ts`
- `app/src/main/java/interview/guide/modules/knowledgebase/RagChatController.java`
- `app/src/main/java/interview/guide/modules/knowledgebase/KnowledgeBaseController.java`

## 3. 面试官：React 前端的页面组织和性能策略是什么？

我的回答：

我的项目前端基于 React 18、TypeScript、React Router 和 Tailwind。`App.tsx` 把简历、面试、知识库、日程、设置和管理端页面按路由组织，使用 `lazy` 与 `Suspense` 做页面级代码分割；包装组件负责读取 URL、location state、调用 API 和导航，公共布局与面试组件再复用。这样首屏不必下载所有管理页面代码，也让业务入口清晰。当前状态主要分散在页面 hooks 和 props，没有统一服务端状态缓存，重复进入页面会重新请求。数据规模和交互复杂后，我会引入 React Query 管理缓存、失效、重试与请求取消。

- `frontend/src/hooks/useInterviewSchedule.ts`

## 4. 面试官：浏览器音频采集有哪些真实实现和前端技术债？

我的回答：

我的项目通过 `getUserMedia` 获取麦克风，要求 16kHz 单声道并启用回声消除、降噪和自动增益；AudioContext 的 ScriptProcessor 把 Float32 转 Int16 PCM，每积累一秒转 Base64 发 WebSocket，同时 Analyser 展示音量。前端还从 CDN 加载 vad-web/ONNX，复用同一 MediaStream 触发 speech start/end。功能已经落地，但 `ScriptProcessorNode` 已过时，主线程做逐字节 Base64 也会产生 CPU 和 GC 压力，CDN 资源还是运行时外部依赖。后续应迁移 AudioWorklet、发送二进制帧、缩短可调 chunk，并把 VAD 资源自托管和锁版本。

代码依据：

- `frontend/src/components/AudioRecorder.tsx`
- `frontend/index.html`
- `frontend/src/api/voiceInterview.ts`
- `frontend/src/pages/VoiceInterviewPage.tsx`

## 5. 面试官：项目目前如何部署，是否已经具备高可用和服务治理？

我的回答：

我的项目已有 Dockerfile 和 Compose，可启动 pgvector/PostgreSQL、Redis、MinIO、bucket 初始化、Spring Boot 后端和 Nginx 前端；健康检查与 depends_on 控制基础设施就绪顺序，命名卷保存数据。开发 Compose 则只起 PostgreSQL、Redis 和 RustFS，便于本地 `bootRun`。但当前没有完整高可用与服务治理：所有依赖和应用都是单实例，没有负载均衡、自动扩缩、熔断、配置中心、备份恢复演练或滚动发布；WebSocket 内存状态也限制了直接横向扩容。因此我只把 Compose 称为可复现部署，不称为生产集群。

代码依据：

- `docker-compose.yml`
- `docker-compose.dev.yml`
- `app/Dockerfile`
- `frontend/Dockerfile`
- `frontend/nginx.conf`

## 6. 面试官：如果只能做一轮生产化优化，你会按什么顺序推进？

我的回答：

我会按风险而不是按“新功能吸引力”排序。第一，补 Spring Security、资源所有权、私有 bucket、密钥强制加密，先解决数据越权；第二，修复简历异常误报成功、入队空窗、会话并发提交和提醒多实例重复，建立 outbox/幂等约束；第三，恢复被禁用的语音测试，并接通 Actuator、Prometheus、告警和 backlog 指标；第四，再做 Provider 熔断/降级、语音断线宽限、二进制音频与水平扩容。当前项目功能面已较完整，真正瓶颈是安全、一致性与可观测闭环，而不是再增加一个尚未验证的 AI 模块。

# 本章总结

前端通过统一 Axios、手工 SSE 解析、路由懒加载和 Web Audio 支撑完整业务体验；Compose 则提供从依赖到前后端的可复现环境。

现阶段部署仍是单实例，前端语音采集也有过时 API 与传输膨胀问题。生产化优先级应先安全和一致性，再观测测试，最后做性能与高可用扩展。

# 核心主线

前端按协议选择合适交互方式，部署先保证可复现，再逐步补齐生产级安全、可靠性和扩展能力。
