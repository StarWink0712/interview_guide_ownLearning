# 面试日程与提醒

## 1. 面试官：项目如何把一段面试邀请文本解析成结构化日程？

我的回答：

我的项目采用“规则优先、AI 兜底”。`InterviewParseService` 先识别飞书、腾讯会议、Zoom 等常见链接和日期时间格式，规则命中可以减少模型成本并提高确定性；信息不完整时，再把经过 PromptSanitizer 处理的邀请文本交给指定或默认 ChatClient，要求返回公司、职位、时间、方式和备注等 JSON，随后做字段规范化。这样常见模板响应快，长尾格式仍有覆盖。当前 AI 分支主要手工剥离 Markdown code fence 后用 ObjectMapper 解析，没有统一复用 `StructuredOutputInvoker`，因此格式错误的重试和观测一致性还可加强。

代码依据：

- `app/src/main/java/interview/guide/modules/interviewschedule/service/InterviewParseService.java`
- `app/src/main/java/interview/guide/modules/interviewschedule/model/ParseRequest.java`
- `app/src/main/java/interview/guide/modules/interviewschedule/model/ParseResponse.java`
- `app/src/main/java/interview/guide/common/ai/PromptSanitizer.java`

## 2. 面试官：创建或修改面试日程时，提醒计划如何生成？

我的回答：

我的项目在日程持久化后，根据配置为“提前一天”和“提前一小时”分别规划提醒；每个时点至少有站内提醒，存在收件邮箱时再建立邮件提醒，因此一场日程通常可产生多条 channel/timing 组合。`InterviewReminderService` 会清理或重建尚未发送的计划，避免修改时间后旧提醒继续触发，并通过 planning-enabled 总开关控制是否规划。这样把“何时提醒”先持久化，而不是等定时器运行时临时推算。当前用户身份是弱化设计，邮箱也不是来自完整账户体系，后续要与真实用户和时区偏好绑定。

## 3. 面试官：提醒是怎样被扫描、投递和重试的？

我的回答：

我的项目用 `InterviewReminderScheduler` 按默认每分钟扫描到期且待发送的提醒，按 batch-size 分页处理，并由 Stream Producer 投递轻量消息；Consumer 读取提醒 ID 后再次确认状态，邮件渠道调用 `SmtpReminderEmailSender`，站内渠道则更新为已发送，前端通过未读数量和列表接口查询。发送异常走公共 Redis Stream 重试和 dead-letter 语义，成功后更新发送时间。这个流程已实现，但 `dispatch-enabled` 默认是 false，未配置 SMTP 时不会真实自动派发；站内提醒也不是 WebSocket/SSE 推送，而是前端查询。

## 4. 面试官：提醒调度在多实例下如何避免重复，是否已经做到端到端幂等？

我的回答：

我的项目即使多实例都运行 `@Scheduled`，到期提醒查询也使用 `PESSIMISTIC_WRITE`，并在同一事务中把 PENDING 改为 QUEUED，因此调度层会串行认领，避免同一记录被两个实例同时入队；日程过期更新则以 `status=PENDING` 的批量 SQL 保持幂等。端到端仍不完全：Stream 重投或 Pending 误认领可能产生重复消息，而 `markProcessing` 目前只拒绝 CANCELLED，没有拒绝已经 SENT/PROCESSING 的提醒，邮件可能重复发送。后续我会加状态条件更新、Provider 幂等键和发送审计。

## 5. 面试官：邮件发送失败和站内提醒未读状态分别怎样处理？

我的回答：

我的项目把投递状态与阅读状态分开：提醒实体记录 PENDING、SENT、FAILED 等发送状态及重试信息，站内提醒另外通过已读标记支持列表、未读计数和批量已读。邮件发送器使用 Spring Mail，并配置连接、读取和写超时；抛出的异常由 Stream 重试，达到上限后可在异步任务/提醒状态中排查。站内渠道当前本质是数据库通知，不依赖外部发送，所以“发送”只是使其可查询。边界是没有退信回执、邮件模板国际化和实时推送，生产上还应区分永久地址错误与可重试 SMTP 故障。

# 本章总结

日程模块用规则与 AI 解析外部邀请，用持久化提醒计划连接定时扫描、Redis Stream、邮件和站内通知，并通过状态字段支持查询与重试。

真实边界是自动派发默认关闭、多实例调度未加分布式互斥、站内通知依靠轮询而非实时推送。

# 核心主线

先把不确定邀请转成确定日程，再把提醒时点持久化并通过异步渠道可靠投递。
