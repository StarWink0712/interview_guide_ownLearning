# 01 公共骨架

## 本阶段目标

把临时字符串响应升级成统一 JSON 响应，并建立统一业务异常处理。

最终成功响应：

```json
{
  "code": 0,
  "message": "success",
  "data": "ok"
}
```

最终失败响应：

```json
{
  "code": 404,
  "message": "资源不存在",
  "data": null
}
```

## 文件创建顺序

必须按以下顺序写：

```text
1. CommonConstants
2. Result
3. ErrorCode
4. BusinessException
5. GlobalExceptionHandler
6. HealthController 改造
7. 测试
```

原因是后面的类依赖前面的类型。按依赖顺序写，编译错误最少。

## 1. `CommonConstants`

路径：

```text
common/constant/CommonConstants.java
```

职责：存放跨模块共用的稳定常量。

第一版只需要：

```java
public final class CommonConstants {

  private CommonConstants() {
  }

  public static final class StatusCode {

    public static final int SUCCESS = 0;
    public static final int SERVER_ERROR = 500;

    private StatusCode() {
    }
  }
}
```

先理解为什么构造函数是私有的：常量类不应该被实例化。

## 2. `Result<T>`

路径：

```text
common/result/Result.java
```

职责：统一所有 Controller 的返回结构。

需要实现：

```text
code
message
data
success()
success(data)
error(code, message)
```

建议先手写构造函数和静态工厂方法，不要直接复制参考项目。

写完后，用一个普通 JUnit 测试验证：

```java
Result<String> result = Result.success("ok");

assertThat(result.getCode()).isZero();
assertThat(result.getData()).isEqualTo("ok");
```

## 3. `ErrorCode`

路径：

```text
common/exception/ErrorCode.java
```

第一版不要把现项目全部错误码抄过来，只写当前需要的：

```java
public enum ErrorCode {
  BAD_REQUEST(400, "请求参数错误"),
  NOT_FOUND(404, "资源不存在"),
  INTERNAL_ERROR(500, "服务器内部错误"),
  INTERVIEW_SCHEDULE_NOT_FOUND(9001, "面试日程不存在");

  private final int code;
  private final String message;

  // 构造函数和 getter
}
```

原则：用到一个错误码，再增加一个。

## 4. `BusinessException`

路径：

```text
common/exception/BusinessException.java
```

职责：携带业务错误码和可读消息，由全局异常处理器统一转换。

至少提供：

```java
public BusinessException(ErrorCode errorCode)
public BusinessException(ErrorCode errorCode, String message)
```

虽然它继承 `RuntimeException`，业务代码仍应统一写：

```java
throw new BusinessException(ErrorCode.NOT_FOUND, "资源不存在");
```

不要在 Service 中直接写：

```java
throw new RuntimeException("资源不存在");
```

## 5. `GlobalExceptionHandler`

路径：

```text
common/exception/GlobalExceptionHandler.java
```

第一版只处理三类异常：

```text
BusinessException
MethodArgumentNotValidException
Exception
```

分别返回：

```text
业务错误码
BAD_REQUEST
INTERNAL_ERROR
```

注意：

- 未知异常必须记录完整堆栈。
- 不要把未知异常原始消息直接暴露给前端。
- `BusinessException` 原样保留业务 code 和 message。

## 6. 改造健康检查

将接口改为：

```java
@GetMapping("/health")
public Result<String> health() {
  return Result.success("ok");
}
```

增加一个临时异常接口：

```java
@GetMapping("/error-demo")
public Result<Void> errorDemo() {
  throw new BusinessException(ErrorCode.NOT_FOUND, "演示资源不存在");
}
```

验证：

```bash
curl http://localhost:8081/api/health
curl http://localhost:8081/api/error-demo
```

验证完成后可以删除 `error-demo`。

## 7. 测试顺序

先写纯单元测试：

```text
ResultTest
BusinessExceptionTest
```

再写 Spring MVC 测试：

```text
HealthControllerTest
```

重点断言：

```text
成功响应 code = 0
业务异常 code 正确
未知异常不泄露内部消息
```

## 本阶段请求链路

成功：

```text
HTTP 请求
  → Controller
  → Result.success
  → Jackson 序列化
  → JSON
```

失败：

```text
HTTP 请求
  → Controller/Service 抛出 BusinessException
  → GlobalExceptionHandler
  → Result.error
  → JSON
```

## 验收标准

- [ ] 所有接口返回 `Result<T>`。
- [ ] 业务异常不会返回堆栈给前端。
- [ ] 参数错误返回 `BAD_REQUEST`。
- [ ] 日志中保留未知异常完整堆栈。
- [ ] `./gradlew test` 通过。
- [ ] 能说清 `BusinessException` 被谁捕获。
